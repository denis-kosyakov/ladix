# Ladix — язык управления бизнесом

> Декларативно-императивный DSL для системы «Уклад»: метрики, KPI и бизнес-процессы в одном языке.

**Ladix** — предметно-ориентированный язык программирования для системы управления бизнесом «Уклад». В одной грамматике он объединяет три парадигмы. **Декларативная часть** описывает источники данных, метрики и KPI — что считать и из чего. **Императивная часть** даёт переменные, выражения, условия, циклы и функции для логики внутри метрик и процессов. **Процессная часть** описывает бизнес-процессы: шаги, исполнителей, сроки, переходы и действия — кто что делает и в каком порядке. **Триггеры** связывают эти миры: «когда метрика упала ниже порога — запусти процесс», «когда наступило событие — начни обработку».

Ladix **не язык общего назначения**: на нём не пишут веб-серверы и алгоритмы сортировки, он специализируется на описании «как устроен бизнес». Фронтенд языка (лексер, парсер, AST, семантический анализ) — собственный. Бэкенд исполнения модульный: в v1 работает встроенный простой движок, но синтаксис и UX рассчитаны на то, чтобы позже подменить его на внешний (Camunda/Kestra и т.п.), не ломая программы пользователя.

Реализация — на Go (1.25+), без CGO: один статический бинарник, кросс-компиляция под Windows/macOS/Linux одной командой. Состояние процессов хранится в SQLite (`modernc.org/sqlite`, чистый Go).

> **README — основной справочник по CLI Ladix.** Здесь живёт полный контракт команд, флагов и кодов возврата; в `SPEC.md` остаётся только короткий указатель сюда.

## Установка

Нужен только Go 1.25 или новее (минимум задан `src/go.mod`). Go-модуль лежит в подкаталоге `src/`, поэтому все команды сборки/тестов выполняются из него. Мост `-o ../ladix` кладёт бинарник в **корень** репозитория — там же, где `examples/` и `data/`, на которые ссылаются примеры. Сборка одной командой, без CGO и внешних C-библиотек:

```sh
cd src && go build -o ../ladix ./cmd/ladix
```

Получается статический бинарник `ladix` в корне репозитория. Запускайте его как `./ladix` из корня (см. «Запуск программы»).

**Кросс-компиляция** — той же командой с переменными окружения целевой платформы (CGO выключен по умолчанию, ничего доустанавливать не нужно); запускать тоже из `src/`, мост `-o ../` кладёт бинарник в корень:

```sh
cd src && GOOS=windows GOARCH=amd64 go build -o ../ladix.exe ./cmd/ladix
cd src && GOOS=darwin  GOARCH=arm64 go build -o ../ladix     ./cmd/ladix
cd src && GOOS=linux   GOARCH=amd64 go build -o ../ladix     ./cmd/ladix
```

## Запуск программы

Разовый прогон программы из файла. Запускайте из корня репозитория — там лежит собранный `./ladix` и каталог `data/`, на который ссылаются примеры с источниками:

```sh
./ladix run examples/hello.ladix
```

Пример программы (`examples/hello.ladix`):

```ladix
печать("Привет, Уклад!")
```

Вывод:

```
Привет, Уклад!
```

Полезный вывод программы (`печать`, сводки, итоги команд) идёт в **stdout**; диагностика ошибок — в **stderr**. Код возврата: `0` — успех, `1` — ошибка в самой программе Ladix (лексика/синтаксис/семантика/исполнение), `2` — ошибка вызова инструмента (плохие аргументы, файл не найден и т.п.). При нескольких ошибках программы код всё равно `1`.

## Запуск тестов

Автотесты — это стандартные Go `_test.go`-файлы рядом с кодом: в пакетах `src/internal/*/` (лексер, парсер, семантика, интерпретатор, движок и т.д.) и в `src/cmd/ladix/` (golden- и smoke-тесты CLI). Отдельного «каталога интеграционных тестов» нет: корневой `tests/` — честная заглушка-отсылка (README + AGENTS), он не наполняется кейсами. Все тесты живут в Go-модуле `src/`, поэтому прогон — из него:

```sh
cd src && go test ./...
```

Статический анализ — оттуда же:

```sh
cd src && go vet ./...
```

## Скоуп v1

**Что работает в v1:**

- **Ядро языка** — переменные с областями видимости (`пусть`), арифметика и логика с приоритетами, условия, циклы, пользовательские функции с параметрами, возвратом и рекурсией, вывод (`печать`). Понятные ошибки с указанием строки и колонки.
- **Метрики** — `источник`-объявления (на этапе v1 — JSON-файлы / mock-источники), `метрика` с агрегатами (`сумма`, `количество`, `среднее`, `мин`, `макс`), фильтрами (`где`) и периодами; вычисление через `ladix run` и `ladix metric`.
- **Процессы с человеком-в-цикле** — `процесс`, `шаг`, назначение исполнителю, сроки, переходы, действия (`присвоить`, `вызвать`, `уведомить`, `запустить процесс`). Шаг-человек переводит инстанс в ожидание; внешнее `ladix complete` будит процесс и продвигает его дальше.
- **Триггеры через `serve`** (фича 007) — `когда метрика ...`, `когда событие ...`, `когда расписание ...`. Демон-планировщик (`ladix serve`) оценивает их на тике; события подаются через `ladix emit`.

**Что отложено (v2; см. §12 SPEC):**

- `ladix start` — внешний запуск именованного процесса с аргументами из CLI (см. ниже «О команде `ladix start`»).
- Передача входного payload в процесс через `complete`.
- Период `последние N дней` (в v1 период — только адвербиальная константа: `ежедневно`/`еженедельно`/`ежемесячно`/`ежеквартально`/`ежегодно`, обязательно вместе с `по_дате`).
- Базовый каталог источников как флаг CLI, машинно-читаемый вывод (`--json`), HTTP-приём событий, cron-выражения в расписании, параллельные ветки процесса, модули, REPL детального синтаксиса.

В v1 нет отдельной команды старта процесса из CLI: процесс запускается либо из тела программы при `run` (синхронно; без `--db` — эфемерно, с `--db` — с сохранением состояния в SQLite), либо из тела триггера под `serve` (фича 007).

## Примеры

В каталоге `examples/` лежат как учебные программы, демонстрирующие ядро языка, так и бизнес-сценарии «Уклада» — всего 9 файлов.

**Учебные программы** (закрывают чеклист — переменные, арифметика, условия, циклы, функции, рекурсия, диагностика):

```
examples/hello.ladix         # вывод (печать)
examples/арифметика.ladix    # арифметика и приоритеты операторов
examples/условие.ladix       # если / иначе
examples/цикл.ladix          # цикл
examples/функция.ladix       # функция с параметрами и возвратом
examples/факториал.ladix     # рекурсия
examples/ошибка.ladix        # намеренно содержит ошибку — демонстрирует диагностику со строкой и колонкой
```

**Бизнес-сценарии** (метрики, процессы, триггеры) — опциональные демо: показывают, ради чего язык существует. Их вывод зависит от текущей даты / id инстанса, поэтому они идут как демо **без строгой проверки вывода** (числовую корректность метрик и жизненный цикл процессов покрывают unit-тесты движка с фиксированной датой):

```
examples/выручка.ladix       # источник + метрика + триггер «метрика < порог → процесс» (нужен data/sales.json в корне репо; запуск из корня)
examples/онбординг.ladix     # процесс с человеком-в-цикле, без источников
```

Фрагменты из этих файлов — ниже.

**Метрика над источником данных:**

```ladix
источник продажи:
    файл: "data/sales.json"

метрика выручка_месяца:
    источник: продажи
    где:      статус == "оплачен"
    агрегат:  сумма(сумма_заказа)
    период:   ежемесячно
    по_дате:  дата(дата_заказа)
```

```sh
./ladix metric examples/выручка.ladix выручка_месяца
```

Внутри `где` и `агрегат` поля записи источника пишутся просто именем (`статус`, `сумма_заказа`) — их область видимости задаёт привязка к источнику.

**Процесс с шагом-человеком и сроком:**

```ladix
процесс обработка_заявки:
    шаг проверить_заявку:
        исполнитель: "менеджер"
        срок:        2час
    шаг одобрить после проверить_заявку:
        присвоить статус = "одобрено"
        уведомить клиент("Ваша заявка одобрена")
```

Блоки открываются двоеточием и телом с отступом (Python-подобный синтаксис; фигурных скобок для блоков в Ladix нет). Длительности пишутся слитно с коротким суффиксом: `2час`, `30мин`, `3дн`.

**Триггер: метрика связывает декларативное с императивным:**

```ladix
когда метрика выручка_месяца < 3_000_000:
    запустить процесс разбор_падения(значение)
```

В теле триггера `значение` — предопределённое имя текущего значения метрики; здесь оно передаётся запускаемому процессу. Процесс `разбор_падения` должен быть объявлен в той же программе **с одним параметром** — в него и попадёт `значение`.

# CLI: полный справочник

## Общая модель

**Один статический бинарник `ladix`** (`cmd/ladix/`, `go build` без CGO). Никакого фонового установленного сервиса по умолчанию: демон поднимается только явной командой `ladix serve` (фича 007).

Модель — git-подобная: `ladix <команда> [аргументы и флаги команды]`.

```
ladix <команда> [args...] [--флаги...]
```

- Запуск без подкоманды, а также `help`/`--help`/`-h` (отдельной команды `help` в v1 нет) → строка использования в **stderr**, выход с кодом `2`.
- Неизвестная подкоманда → та же строка использования в **stderr**, выход с кодом `2` (без отдельного сообщения «неизвестная команда …» и без перечня команд).
- Имена команд — латиницей (kebab-case), как принято в Go CLI; пользовательские сообщения — на русском.
- Глобальных флагов до имени команды в v1 нет. Общие по смыслу параметры (`--db`, `--max-depth`) задаются как флаги соответствующих команд.
- Ввода со stdin нет. Программа всегда читается из файла-аргумента; пайпы (`cat prog.ladix | ladix run`) не поддерживаются.
- Машинно-читаемого режима (`--json`) в v1 нет; все пользовательские сообщения — на русском.

### Сводка команд

| Команда | `Store` | Аргументы | Ключевые флаги | Что делает |
|---|---|---|---|---|
| `run` | `MemoryStore` / `SQLiteStore` (с `--db`) | `<file.ladix>` | `--db`, `--max-depth` | Разовый прогон программы сверху вниз. |
| `metric` | `MemoryStore` | `<file.ladix> <имя>` | `--max-depth` | Вычислить и напечатать значение метрики. |
| `complete` | `SQLiteStore` | `<file.ladix> <task-id>` | `--db`, `--max-depth` | Завершить задачу, продвинуть инстанс. |
| `tasks` | `SQLiteStore` | `[исполнитель]` | `--db` | Показать открытые задачи (+ точный дедлайн). |
| `serve` | `MemoryStore` / `SQLiteStore` (с `--db`) | `<file.ladix>` | `--db`, `--interval`, `--max-depth` | **Фича 007.** Демон-планировщик триггеров. |
| `emit` | `SQLiteStore` | `<событие> [json]` | `--db` | **Фича 007.** Поставить внешнее событие в очередь. |

Команды делятся на два класса по необходимости персистентного состояния:

- **Самодостаточные** (`run` без `--db`, `metric`) — работают над `MemoryStore`, SQLite им не нужен.
- **Store-зависимые** (`run --db`, `complete`, `tasks`; с фичи 007 — `serve`, `emit`) — работают над общим `SQLiteStore`. Поток «человек-в-цикле» (`run --db` → `tasks` → `complete`) работает уже без демона; демон `serve` (фича 007) нужен только триггерам и событиям.

> **REPL** — интерактивная оболочка над интерпретатором; в v1 **не реализована** (бонус, фича не назначена). `ladix repl` печатает usage и завершает с кодом `2`.

### Общие флаги

- **`--db <путь>`** (`run`, `complete`, `tasks`; с фичи 007 — также `serve` и `emit`; у `metric` его нет). Путь к файлу SQLite-БД. У `complete` и `tasks` **дефолт: `ladix.db` в текущем каталоге**; `run` без флага работает над эфемерным `MemoryStore` и на диск не пишет. Несуществующий файл создаётся со схемой. Битая/несовместимая БД → старт прерывается сообщением `ladix: не удалось открыть хранилище '<путь>': <причина>`, exit `2`.
- **`--max-depth <N>`** (команды, исполняющие Ladix-код: `run`, `metric`, `complete`; с фичи 007 — `serve`). Лимит глубины рекурсии — предохранитель от бесконечной рекурсии в пользовательских функциях. **Дефолт: `10000`.** `N <= 0` → ошибка использования, exit `2`. Превышение лимита в рантайме — ошибка выполнения, exit `1`.
- **`--interval <duration>`** (только `serve` — **фича 007**). Период тика планировщика. См. `serve` ниже.

## `ladix run <file.ladix>`

**Синтаксис:** `ladix run путь/к/программе.ladix [--db путь] [--max-depth N]`

Разовый прогон программы. Закрывает учебный пункт «запуск программы из файла» и служит каналом демонстрации для README/examples.

- **Аргумент:** ровно один позиционный — путь к `.ladix`-файлу. Отсутствие аргумента или более одного → ошибка использования, exit `2`. Файл не существует/не читается → `ladix: не удалось прочитать файл "<путь>"`, exit `2`.
- **`Store`:** без `--db` — `MemoryStore` (эфемерный, не пишет на диск: инстансы процессов и задачи живут только в памяти прогона); с `--db` — `SQLiteStore`, мост к `tasks`/`complete`: инстансы и задачи переживают прогон. Открытие/инициализация схемы не удались → `ladix: не удалось открыть хранилище '<путь>': <причина>`, exit `2`.
- **Семантика прогона:**
  - Программа исполняется сверху вниз: top-level statement-ы (объявления и императивный код) в порядке исходника, начиная с первого.
  - `запустить процесс P(...)` синхронно доводит инстанс до первого ожидания/терминала и возвращает строку-id; человеческий шаг (`исполнитель:`) оставляет инстанс в состоянии «ожидает». Без `--db` такой инстанс дальше не двигается (нет общего `Store`); с `--db` он сохраняется в БД, и его будит внешний `ladix complete`.
  - **Сводка висящих задач:** если по завершении прогона остались открытые задачи, в stdout печатается заголовок `открытых задач: <N>` и по строке на задачу (тот же формат, что у `ladix tasks`). Висящие задачи — не ошибка: exit `0`.
  - **Повторный `run --db` того же файла создаёт новые инстансы:** id-счётчик персистентен, старые «ожидающие» инстансы остаются в БД и видны в `tasks`. Это норма v1.
  - Триггеры — **фича 007** (до неё конструкция `когда` фронтендом не поддерживается): метрика-триггеры получат один оценочный проход после загрузки источников; расписание/событие в `run` — no-op с логом «требует serve».
  - Детерминизм: `сегодня()` фиксируется на один прогон; источники читаются лениво и кешируются — два чтения одной метрики дают одно значение.
- **Пути источников** — от cwd процесса `ladix` (см. «Примечание о путях к источникам»).
- **Вывод:** `печать(...)` и системные сообщения — в stdout; диагностика ошибок — в stderr. Runtime-ошибка шага процесса помечает инстанс «провален», диагностика — канон §13, exit `1`.

## `ladix metric <file.ladix> <имя>`

**Синтаксис:** `ladix metric путь/к/программе.ladix имя_метрики [--max-depth N]`

Вычислить и напечатать значение одной метрики из программы.

- **Аргументы:** два позиционных — путь к `.ladix` и имя метрики. Неизвестное имя метрики → семантическая ошибка `неизвестная метрика '<имя>'`, exit `1`. Имя ссылается на не-метрику (переменную/функцию) → семантическая ошибка, exit `1`.
- **`Store`:** `MemoryStore` **безусловно** и без флага `--db` (движок собирается над ним — единый стек команд, docs/engine-model.md §EN-6). Метрика — чистая функция источников и в персистентной БД не нуждается.
- **Поведение:** лексер → парсер → семантика → вычисление указанной метрики; печать скаляра в строковом представлении. `период`-окно — относительно `сегодня()`. Пустое окно → `0`/`пусто` по правилу метрик.

## `ladix serve <file.ladix>` — фича 007

**Синтаксис:** `ladix serve путь/к/программе.ladix [--db путь] [--interval D] [--max-depth N]`

> **Фича 007.** Команда доступна в v1: демон-планировщик триггеров. Поток «человек-в-цикле» (`run --db` → `tasks` → `complete`) работает и без неё — `serve` нужен только триггерам по времени/метрикам/событиям.

Долгоживущий процесс-планировщик триггеров. Нужен **только** под триггеры по времени/метрикам/событиям; поток «человек-в-цикле» (создание задач шагами, их `complete`) работает и без демона.

- **Аргумент:** один позиционный — путь к `.ladix`-файлу. Демон берёт из него, какие триггеры/процессы/метрики обслуживать (симметрично `run`). Отсутствие позиционного файла → ошибка использования, exit `2`.
- **`--interval D`** — базовый интервал тикера. `D` парсится **Go `time.ParseDuration`** (служебный CLI-флаг, латиница, не Ladix-исходник — поэтому не лексер `Длительность` с её суффиксами, а стандартный Go-формат: `30s`, `1m`, `1h30m`). **Дефолт: `1m`.** Невалидный формат → ошибка использования, exit `2`.
- **`Store`:** без `--db` — эфемерный `MemoryStore` (состояние триггеров, очередь событий и инстансы теряются при рестарте); с `--db` — `SQLiteStore` (состояние переживает рестарт). Для долгоживущего демона, которому нужна durability и кросс-процессный `emit`, **рекомендуется `--db`**.
- **Жизненный цикл:** инициализирует схему БД при необходимости, поднимает одну горутину-тикер; завершение по SIGINT/SIGTERM → грациозный shutdown, exit `0`. Сбой инициализации (битая БД) → exit `2`.
- **Изоляция сбоев:** сбой одного триггера на тике обёрнут recover, логируется, демон не падает.

## `ladix complete <file.ladix> <task-id>`

**Синтаксис:** `ladix complete путь/к/программе.ladix t-XXXXXX [--db путь] [--max-depth N]`

Внешнее пробуждение инстанса: пометить задачу человека готовой и продвинуть процесс. Истина — в исходнике, БД хранит только состояние: `complete` строит движок из файла программы, поэтому файл — обязательный аргумент.

- **Аргументы:** ровно два позиционных — путь к `.ladix`-файлу и `<task-id>` (непрозрачная строка вида `t-…`; формат пользователь не парсит, берёт из вывода `tasks`/`run`). Меньше/больше → usage, exit `2`.
- **Компиляция файла:** лексер → парсер → семантика обязаны пройти чисто; ошибки → штатный барьер диагностики (stderr, exit `1`).
- **`Store`:** `SQLiteStore`, путь из `--db`, дефолт `ladix.db` (`MemoryStore` для `complete` бессмыслен — общего состояния нет). Не открылось → exit `2`.
- **Контракт (гарды по порядку; CLI-ошибки — одной строкой `ladix: <текст>` в stderr):**
  1. Задача существует: неизвестный id → `ladix: задача '<id>' не найдена`, exit `2`.
  2. Инстанс задачи существует: иначе → `ladix: инстанс '<id>' не найден`, exit `2` (битая/чужая БД).
  3. **Дрейф исходника против БД:** имя процесса инстанса не найдено в файле → `ladix: процесс '<имя>' не найден в определении`; имя шага не найдено → `ladix: шаг '<имя>' не найден в определении процесса '<имя>'`. Exit `2`, инстанс не тронут. Граница v1: исходник между запуском и `complete` не меняют.
  4. **Гард-догон:** уже завершённая задача при инстансе в «ожидает» на том же шаге — хвост сбоя «задача завершена, продвижение не успело» → идемпотентное до-продвижение, печать `задача <t-id> уже была завершена, инстанс до-продвинут`, exit `0`. Любая другая уже завершённая задача → `ladix: задача '<id>' уже завершена`, exit `2` (идемпотентность через явную ошибку, не молчаливый no-op).
  5. Инстанс ожидает именно эту задачу: иначе → `ladix: инстанс '<p-id>' не ожидает (статус '<статус>')` либо `ladix: задача '<t-id>' не соответствует текущему шагу инстанса '<p-id>'`, exit `2`.
  6. Задача атомарно помечается завершённой (печать `задача <t-id> завершена`), затем движок синхронно продвигает инстанс до следующего ожидания/терминала.
- **Итог в stdout:** `инстанс <p-id>: ожидает, шаг '<имя>'` (снова заснул; перед этим — строка создания новой задачи) либо `инстанс <p-id>: выполнен`. Exit `0` (включая ветку догона).
- **Провал:** runtime-ошибка продвижения (тело или атрибуты следующего шага) → инстанс персистируется как «провален», диагностика — канон §13 в stderr, exit `1`.
- **Коды:** нарушение гардов (неизвестный/уже завершённый `task-id`, дрейф, несоответствие шагу) — ошибка использования инструмента, exit `2`, инстанс не тронут; ошибка компиляции файла или продвижения — ошибка программы, exit `1`.
- **Права:** завершить может кто угодно по id — `исполнитель` совещательная метка. Входного payload нет: данные через `complete` в процесс не передаются.
- **Конкурентность:** параллельно с другими `complete` (а с фичи 007 — и с демоном `serve`) над тем же `--db` — сериализация записей через WAL + `busy_timeout`, не блокировки в коде; остаточная гонка двух одновременных `complete` ограничена гардами и догоном (документированная граница v1).

## `ladix tasks [исполнитель]`

**Синтаксис:** `ladix tasks [исполнитель] [--db путь]`

Показ открытых задач. Файл программы **не принимает** — всё берётся из БД (движок и интерпретатор не строятся). Точный дедлайн печатается только на CLI-поверхности (строки задач у `tasks` и сводки `run`); в самом языке Ladix дата-время не экспонируется, доступен только производный признак `просрочена`.

- **Аргумент:** необязательный позиционный `исполнитель` — фильтр. Без аргумента — все открытые задачи.
- **`Store`:** `SQLiteStore`, путь из `--db`, дефолт `ladix.db`.
- **Вывод:** по строке на задачу (разделитель полей — два пробела; тот же формат у сводки `run`):

  ```
  <t-id>  <p-id>  '<шаг>'  <исполнитель>  срок до <время>  ПРОСРОЧЕНА
  ```

  хвост `срок до <время>` — только при дедлайне (`<время>` — локальное, формат `2006-01-02 15:04`), пометка `ПРОСРОЧЕНА` — только у просроченных. Порядок — по возрастанию id. Пустой список — сообщение `открытых задач нет`. Exit `0` в обоих случаях.

## `ladix emit <событие> [json]` — фича 007

**Синтаксис:** `ladix emit ИмяСобытия '{"поле": значение}' [--db путь]`

> **Фича 007.** Команда доступна в v1 — источник внешних событий для демона `serve`. Пишет событие в очередь общего `Store` и выходит.

Источник внешних событий для `когда событие E`. Короткоживущий процесс: пишет событие в очередь общего `Store` и выходит; демон `serve` разбирает его на тике.

- **Аргументы:** первый позиционный `<событие>` — имя (обязателен; нет → exit `2`). Второй позиционный `[json]` — необязательный JSON-payload (одна строка-аргумент). Payload пишется в очередь **как есть, без валидации на стороне `emit`** (пустой допустим); корректность JSON демон `serve` проверяет при маппинге в `Запись` на тике. Лишний третий позиционный или неизвестный флаг → exit `2`.
- **Поведение:** событие ставится в очередь; печать id поставленного события (`e-…`) в stdout, exit `0`. Демон на тике парсит payload в запись (маппинг JSON→типы как у источников), исполняет тела совпавших триггеров, помечает обработанным. Доставка at-least-once: сбой демона между исполнением тела и пометкой обработанным → переобработка (повтор `запустить процесс` безвреден).
- **В `run`** событие — no-op (требует `serve`).

## О команде `ladix start` — **нет в v1**

Отдельная команда «запустить именованный процесс из CLI с аргументами» в v1 **отсутствует** — это решение объёма, а не отсутствие механизма. Запуск процесса в v1 идёт **только** из тела триггера (`запустить процесс`) либо из программы при `run`/`serve`. Канал передачи данных извне в систему уже существует (JSON-payload у `emit`).

Путь отступления (v2): `ladix start <процесс> [json-аргументы]` — естественное расширение, симметричное `emit` (короткоживущий процесс пишет «команду старта» в `Store`, демон подхватывает); синтаксис команд это не ломает.

## Коды возврата

| Код | Значение | Когда |
|---|---|---|
| **0** | Успех | Команда отработала штатно (включая `run` с висящими задачами, до-продвижение гард-догона `complete` и — с фичи 007 — `serve`, остановленный сигналом). |
| **1** | **Ошибка программы Ladix** | Любая из категорий диагностики (лексическая, синтаксическая, семантическая, типа, выполнения, процесса), возникшая **внутри** программы, — в том числе runtime-ошибка шага процесса (инстанс при этом помечается «провален»). Сообщение(я) в формате §13 SPEC; одна ошибка или K ошибок — код всё равно `1`. |
| **2** | **Ошибка использования / окружения CLI** | Плохие аргументы или флаги; неизвестная команда; файл-программа не найден/не читается; не удалось открыть хранилище (`--db`); гарды `complete` — неизвестный/уже завершённый `task-id`, инстанс не ожидает или шаг не совпал, дрейф исходника против БД; плохие позиционные/флаги у `serve`/`emit` (фича 007). Не ошибка кода Ladix — ошибка вызова инструмента. |

**Граница 1 vs 2:** если ошибка обнаружена **до или вокруг** исполнения программы Ladix (разбор аргументов, доступ к файлу/БД, валидация id на стороне команды) — это `2`. Если ошибка — результат лексики/синтаксиса/семантики/исполнения **самой программы** — это `1`. Непредвиденная внутренняя паника интерпретатора печатает «внутренняя ошибка интерпретатора» в stderr (без Go stack trace) и даёт exit `1`.

Подробности формата диагностики (заголовок «Ошибка в строке N, колонка M:», накопление нескольких блоков ошибок за прогон для лексера/парсера — блоки печатаются подряд, итоговой строки-сводки нет; fail-fast семантики) — в `SPEC.md` §13. Детальная модель исполнения процессов — в `docs/execution-model.md`; реализационный канон фичи 006 (контракты CLI, stdout и диагностик) — в `docs/engine-model.md`.

## Примечание о путях к источникам

Относительные пути в объявлениях источников (`файл: "data/sales.json"`) разрешаются **от текущего рабочего каталога**, из которого запущена команда `ladix`, а **не** от каталога `.ladix`-файла. Абсолютный путь — как есть. Поэтому пример с файлом-источником запускайте из корня репозитория, где лежит каталог `data/`:

```sh
./ladix run examples/выручка.ladix   # из корня репо, где находится ./data/sales.json
```

Это явная граница v1 (флаг базового каталога источников отложен в v2).
