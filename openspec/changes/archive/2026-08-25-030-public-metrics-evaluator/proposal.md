# Proposal: 030 — публичный исполнитель метрик (заказ Уклада, v0.2.0)

## Why

Уклад (потребитель библиотеки, серия «4a ladix-reports», series-design
утверждён владельцем 2026-08-24 — `uklad/docs/uklad_v4_series_ladix_design.md`)
исполняет metrics-подмножество IR в своём сервисе `automation`, но не может:
выражения `Metric.Where`/`Aggregate` — канонические строки, а их
исполнитель (`internal/eval`) непубличен. Писать второй интерпретатор по
SPEC — drift-риск двух семантик; гонять reference-CLI сайдкаром — слом
библиотечной модели (потребителю нужен свой store/RLS). Развилка Д-1
Уклада решена в пользу MINOR-расширения публичной поверхности — путь,
прямо предусмотренный `docs/module-contract.md` §MC-1 («при появлении
реальной потребности поверхность расширяется MINOR-релизом»).

Ссылки на артефакты Уклада — только мотивация. Контракт исполнителя
(сигнатура, форма «данных потребителя», тексты диагностик) фиксируется
самодостаточно в дельте спеки `metrics-evaluator` этого change
(ср. §MC-7: контракт со слов владельца — зафиксированное допущение).

## What Changes

- **Новый публичный пакет — исполнитель метрик** (третий пакет
  поверхности; форма API — решение design.md: evaluator-фасад над
  каноническими строками ИЛИ структурный expr-AST + walker; в обоих
  вариантах expr-AST, если он появляется, живёт В НОВОМ ПАКЕТЕ —
  пакет `ir` не меняется, канонические строки остаются форматом
  контракта IR, `ir.SchemaVersion` остаётся 1, §MC-5 не пересматривается).
  Релиз — MINOR, тег **`v0.2.0`**.
- **Контракт исполнителя (требования заказчика, series-design §6 Д-1):**
  - зафиксированная сигнатура (вход: выражения из `ir.Metric` + данные
    потребителя; выход: результат + диагностики);
  - **детерминизм**: одинаковый вход → одинаковый результат; без
    wall-clock, рандома и порядко-зависимости map-обходов (обращение
    исполнителя ко времени — только через инжектируемые часы; форма
    инжекции — design.md);
  - **error-модель со структурными позициями** (идиома
    `ir.Diagnostic`: severity/stage/message/pos, дословные русские
    тексты SPEC §13);
  - **граница билд-графа**: исполнитель НЕ тянет
    `internal/{store,engine,daemon}` и sqlite — расширение стража
    `boundary_test.go` на новый пакет (T3 по §MC-4).
- **Потолок сложности выражений** (глубина вложенности / число узлов) —
  **в исполнителе, НЕ в `Compile`**: существующие валидные программы
  обязаны компилироваться в тот же IR, что и раньше (гарантия ниже),
  поэтому семантический гард ставится на входе исполнения. Диагностика
  потолка — новый пользовательский текст, фиксируется дословно в дельте
  спеки; закрывается тестом-замком.
- **Семантическая стабильность как контракт:** golden result-фикстуры
  `(программа + вход) → результат` в тестах Ладикса — MINOR/PATCH-релиз
  не вправе менять результаты исполнения существующих программ
  (симметрично гарантии «старые программы компилируются в тот же IR»).
  У потребителя — своя вторая группа фикстур (series-design §5.5б).
- `ir.SchemaVersion` НЕ меняется (остаётся 1; всё аддитивно). Публичная
  поверхность становится РОВНО ТРИ пакета — правка §MC-1.

## Не-цели

- **Понижение директивы `go` в `go.mod`** — НЕ делается. Решение
  владельца зафиксировано в `docs/module-contract.md` §MC-6
  (`modernc.org/sqlite v1.52.0` требует `go 1.25.0`; замок
  `TestGoDirectiveMatchesDocumentedFloor`). Пересмотр потребовал бы
  отката sqlite и здесь не предпринимается.
- **Перевод выражений IR из канонических строк в структурный формат
  контракта** — это v2 с bump `ir.SchemaVersion` (§MC-5); не в этом
  change ни в каком виде.
- **Публичное исполнение процессов и триггеров** (не-metrics
  подмножества IR) — только метрики.
- **Изменения CLI** (`cmd/ladix`), рантайма (`internal/{engine,store,daemon}`),
  синтаксиса языка, лексера/парсера.
- **Публикация других internal-пакетов** сверх одного нового пакета
  исполнителя.
