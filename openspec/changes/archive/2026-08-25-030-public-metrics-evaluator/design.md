# Design: 030 — публичный исполнитель метрик

## Context

Мотивация — proposal.md «Why». Текущее состояние: семантика выражений живёт в
`internal/eval` (sqlite-free, зависит только от `ast`/`errors`/`value`);
конвейер метрики (окно → фильтр → агрегат) — канон §SM-8, чистая функция от
данных источника и даты «сегодня» (`Clock`, §SM-7). Канонические строки
выражений разбираются существующим лексером/парсером. Публичная поверхность —
`ladix` + `ir`, страж `boundary_test.go` (T3, §MC-4). Внутри модуля публичный
пакет МОЖЕТ импортировать `internal/*` (ограничение Go касается чужих модулей) —
этим и пользуемся, ничего не перенося.

## Goals / Non-Goals

**Goals:**
- Третий публичный пакет-исполнитель с контрактом по дельте спеки
  `metrics-evaluator` (детерминизм, диагностики, потолок, граница билд-графа).
- Ноль дублирования семантики: один интерпретатор для CLI и для потребителя.

**Non-Goals:**
- См. proposal.md «Не-цели» (go-директива, expr-AST как формат контракта,
  процессы/триггеры, правки CLI/рантайма).
- Публикация типов AST/value в любом виде — даже как «удобство».

## Decisions

### Д-1. Форма API: фасад над каноническими строками (НЕ экспорт expr-AST)

Новый пакет `metrics` (`github.com/denis-kosyakov/ladix/metrics`) даёт
функцию-фасад: вход — `ir.Metric` + записи потребителя + опции, выход —
результат + диагностики. Канонические строки разбираются ВНУТРИ фасада
существующими `internal/{lexer,parser}`.

Почему не «структурный expr-AST + walker»: экспорт AST делает представление
выражений публичным контрактом — замораживает внутренности, конфликтует с
§MC-5 (переход выражений в структуру — это v2 c bump SchemaVersion) и
раздувает поверхность v0.2.0. Фасад аддитивен, строки остаются форматом
контракта IR, `SchemaVersion = 1`. Alternative rejected.

### Д-2. Данные потребителя: записи в JSON-семантике

Вход — `[]map[string]any` со значениями в семантике маппинга JSON → типы
Ladix (SPEC §9.3; даты — строки по §9.4). Переиспользуется существующий
маппинг загрузчика источника (`internal/jsonval`-путь), чтобы публичный вход
и файловый источник CLI давали идентичные значения — это условие сценария
«Совпадение с reference-CLI». Недопустимое значение → те же тексты ошибок
загрузки/типов, что у CLI (реестры §8.3/§SM-9), новых текстов нет.
Альтернатива (собственный публичный тип Value) отвергнута: вторая система
типов = drift-риск и лишняя поверхность.

### Д-3. Часы: фиксированная дата в опциях, БЕЗ wall-clock и без интерфейса

Опции фасада несут обязательную дату «сегодня» (значение, не интерфейс).
Внутри адаптируется к часам `internal/eval`/§SM-7 (`FixedClock`-путь).
Wall-clock в пакете отсутствует КОНСТРУКТИВНО — детерминизм не «дисциплина»,
а свойство сигнатуры; тест-замок грепает пакет на `time.Now`. Почему не
интерфейс Clock: интерфейс приглашает нестабильные реализации и расширяет
поверхность; потребителю (batch-вычисление отчётов) нужна именно дата среза.
`engine.Clock` не переиспользуется — `internal/engine` вне билд-графа пакета.

### Д-4. Потолок сложности: в исполнителе, на разобранном expr-AST

После разбора канонической строки и ДО вычисления считаются глубина
вложенности (>100 — отказ) и число узлов (>10000 — отказ) обходом AST.
Тексты и пределы — дословно в дельте спеки. В `Compile` потолка нет
(гарантия «старые программы компилируются в тот же IR» — сценарий-замок).
Пределы недостижимы для рукописных метрик и щедры для agent-supplied текста.

### Д-5. Диагностики: `stage:"runtime"` строкой, ir без правок

Ошибки → срез в идиоме `ir.Diagnostic` со stage-значением `"runtime"` —
строкой на стороне пакета `metrics`, БЕЗ новой константы в `ir` (граница
диффа: `ir` пуст; словарь stage по контракту толерантен к неизвестным
значениям, doc.go). Константа `ir.StageRuntime` — кандидат на будущий MINOR,
не здесь. Позиции — в тексте канонической строки (строка 1 у однострочных,
колонки в рунах). Сигнатура Go-идиоматична: `(результат, []ir.Diagnostic,
error)`; на границе — recover-барьер (Принцип III), паника наружу не выходит.

### Д-6. Переиспользование, не рефактор

`internal/eval` трогается минимально: если для вызова конвейера §SM-8 с
инжектированными записями (вместо файлового источника) нужна новая точка
входа — она добавляется как НОВАЯ внутренняя функция, существующие пути CLI
не переписываются. Семантика — под замком golden result-фикстур и сценария
совпадения с CLI.

### Д-7. Схема полей источника — в опциях фасада

`ir.Program` не содержит объявлений источников, `ir.Metric.Source` — только имя,
поэтому схема `поля:` (в частности `<поле>: Дата`) в IR не доезжает. Без неё
ISO-строка остаётся `Строка` (§9.4) и любая метрика с `период:`/`по_дате:`
неисполнима. Решение владельца (2026-08-24): схема передаётся потребителем
явно — `Options.Fields map[string]string` (имя поля → имя типа Ladix). Внутри
переиспользуется существующий путь `applySchema`/`coerceField` из
`internal/eval`, поэтому тексты ошибок приведения и результат совпадают с CLI
дословно; новой семантики не вводится. Альтернатива «автопарсинг поля
`по_дате:`» отвергнута: правило вне канона и расхождение с CLI на источнике
без схемы. Неизвестное имя типа в `Fields` → `ErrInvalidOptions`.

### Д-8. Типизация чисел потребителя: по Go-типу, `json.Number` — по форме

§9.3 типизирует числа по ФОРМЕ ТОКЕНА, но в `[]map[string]any` формы нет
(`json.Unmarshal` даёт `float64` всему). Решение владельца (2026-08-24):
`int`/`int8..int64`/`uint`/`uint8..uint64` → `Целое`; `float32`/`float64` →
`Дробное`; `json.Number` → строго по форме токена (§9.3 дословно — этот путь
даёт побайтовый паритет с CLI, если потребитель декодировал с `UseNumber`);
`string` → `Строка`, `bool` → `Булево`, `nil` → `Пусто`, `[]any` → `Список`,
`map[string]any` → `Запись` (рекурсивно). Прочие Go-типы (`time.Time`, struct)
→ диагностика типа, не паника. Типизация по ЗНАЧЕНИЮ (`154000.0` → `Целое`)
отвергнута: прямо противоречит §9.3 и даёт дрейф семантики от CLI.

### Д-9. Порядок полей записи

`map` не упорядочен, а порядок полей виден пользователю в тексте
`неизвестное поле '<имя>' (известные: ...)`. Ключи каждой записи сортируются
лексикографически (`sort.Strings`) до построения `value.Запись` — детерминизм
по требованию спеки «без зависимости от порядка обхода map». Порядок САМИХ
записей — тот, в котором их передал потребитель (не сортируется).

### Д-10. Разбор канонических строк: синтетическая декларация метрики

`internal/{lexer,parser,ast}` — пустой дифф, а `parseExpression` не
экспортирован; при этом формы `период:` (`последние 30дн`, `прошлый месяц`)
разбираются контекстным `parsePeriodValue`, достижимым ТОЛЬКО из
`parseMetricDecl` (проверено спайком: обёртка `пусть _ = <expr>` на них
падает). Поэтому все четыре канонические строки разбираются одной
синтетической программой-декларацией метрики через публичные
`lexer.New(...).Tokenize()` / `parser.New(...).Parse()`; имена метрики и
источника в синтетический текст НЕ подставляются (берутся фиксированные
безопасные идентификаторы) — вход потребителя попадает в текст только как
тело выражения. Позиции узлов пересчитываются из координат обёртки в
координаты канонической строки (строка 1, колонка в рунах) вычитанием
известного постоянного смещения шаблона.

### Д-11. Публичная сигнатура (заморожена для v0.2.0)

```go
package metrics // github.com/denis-kosyakov/ladix/metrics

type Date struct{ Year, Month, Day int }

type Options struct {
    Today    Date              // обязательна: дата среза, окно периода строится от неё
    Fields   map[string]string // Д-7: схема полей источника, необязательна
    MaxDepth int               // 0 → DefaultMaxDepth интерпретатора
}

type Result struct {
    Type  string // имя типа Ladix: "Целое", "Дробное", "Строка", "Булево", "Пусто", "Дата", ...
    Text  string // каноническая печать — та же, что печатает `ladix metric`
    Value any    // Go-значение в JSON-семантике (Дата/Длительность/Период — строкой, равной Text)
}

func Evaluate(m ir.Metric, records []map[string]any, opts Options) (Result, []ir.Diagnostic, error)

var (
    ErrInvalidOptions = errors.New("...") // некорректные Options (дата, имя типа в Fields)
    ErrEvaluation     = errors.New("...") // метрика не вычислена; подробности — в диагностиках
    ErrInternal       = errors.New("...") // сработал recover-барьер (Принцип III)
)
```

`error` ненулев тогда и только тогда, когда результат не получен; все
пользовательские тексты живут в `[]ir.Diagnostic` (`Severity="error"`,
`Stage="runtime"`), сентинелы — только программные маркеры для `errors.Is`.

### Д-12. Предусловие `Analyze`

Конвейер `internal/eval` полагается на первый проход семантики (`Analyze`):
без него имена функций/агрегатов не резолвятся и попадают в ветку
«неизвестное поле». Фасад прогоняет `Analyze` по синтетической программе
Д-10 до вычисления; это внутренняя деталь, наружу не видна.

## Чек-лист Конституции

| Принцип | Вердикт |
|---|---|
| I (идиоматичный Go, без CGO, один бинарник) | PASS — новый пакет чистый Go, зависимостей 0 |
| II (ручной recursive descent) | PASS — парсер переиспользуется, новых парсеров нет |
| III (явные ошибки, recover-барьер на границе) | PASS — Д-5: диагностики + барьер фасада |
| IV (Position с 1, колонки в рунах) | PASS — Д-5: позиции в канонической строке |
| V (без пакетного состояния, инжекция зависимостей) | PASS — Д-3: дата инжектируется, wall-clock отсутствует |
| VI (tests-first, табличные + негативные) | PASS — tasks: замки до/вместе с кодом |
| VII (раскладка, поверхность аддитивно) | PASS — третий пакет, `ladix`/`ir` не тронуты |
| VIII (русские тексты дословно) | PASS — новые тексты дословно в дельте спеки, остальные из реестров |
| IX (спека — источник истины) | PASS — конфликт c §MC-6 снят (не-цель), §MC-5 не пересматривается |

## Risks / Trade-offs

- [Дрейф публичного конвейера и CLI-конвейера] → один внутренний код (Д-6) +
  сценарий-замок «Совпадение с reference-CLI» + golden-корпус.
- [Потолок бьёт по легальной программе] → пределы 100/10000 на порядки выше
  реальных метрик; негативный тест на граничные значения (100 — проходит,
  101 — отказ).
- [Потребитель передал не-JSON типы (time.Time, struct)] → валидация входа на
  границе, существующие тексты ошибок типов; фаззить не требуется — вход
  структурно перечислим.
- [Соблазн «подтащить» store для удобства] → страж T3 краснеет немедленно.

## Migration Plan

Аддитивный MINOR: merge в `master` → тег `v0.2.0`. Откат — не тегировать /
тег `v0.2.1` с фиксом; уже скомпилированные потребители не затронуты (старые
пакеты не менялись). Fallback потребителя (`Aggregate=count` без `Where`)
остаётся рабочим независимо от релиза.
