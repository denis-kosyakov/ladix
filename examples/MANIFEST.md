# Манифест демонстрационных программ

Каталог `examples/` содержит программы на Ladix: семь обязательных (закрывают чеклист
«Примеры»), две бизнес-демонстрации, витрину триггеров/метрик/процесса (US3), витрину ошибок
(US3), витрину коннекторов источника (010-A1: `тип:`/`поля:` для CSV/NDJSON/JSON-схемы) и
витрину оконных метрик (011-A2: `последние N <ед>`/`прошлый <noun>`).
**Обязательные 7** — эталон текущего ядра (v1): исполняются один-в-один через `ladix run`,
ожидаемый вывод проверяется как golden-фикстура. **Бизнес-демонстрации** показывают
декларативно-процессный синтаксис (`источник`, `метрика`, `процесс`, триггер `когда`):
`онбординг.ladix` исполняется движком процессов (фича 006), `выручка.ladix` — parse-clean +
run-demo метрика-триггера (фича 007a) — подробности в разделе ниже. **Витрина триггеров/метрик**
(`событие.ladix`, `расписание.ladix`, `метрики.ladix`, `процесс.ladix`) демонстрирует формы
триггеров событие/расписание, мультиисточник/мультиметрику и полный жизненный цикл процесса —
раздел «Витрина триггеров и метрик» ниже. **Витрина ошибок** (`ошибка_синтаксис.ladix`,
`ошибка_тип.ladix`, `ошибка_процесс.ladix`) показывает три разных класса диагностики (парсинг /
типы / процесс) — каждый падает в `ladix run` с **кодом 1** и двухстрочным каноном §13; раздел
«Витрина ошибок» ниже. Подробнее о форматах ошибок — §13; о CLI-командах — README, раздел CLI.

Общие соглашения для всех файлов:

- Кодировка UTF-8; русские идентификаторы и ключевые слова (§2).
- Отступы значащие, 4 пробела на уровень, табы запрещены (§2).
- Комментарии — `#` до конца строки (§2).
- Вывод только через `печать(...)`: аргументы через один пробел, в конце перевод строки.
  `Дробное` печатается с точкой (`1.0`, `3.4`, `2175.0`), `Список` — `[элементы через , ]`.
- Запуск **обязательных 7**: `ladix run examples/<файл>.ladix`, код возврата `0`
  (кроме `ошибка.ladix` — код `1`). Бизнес-демонстрации: `онбординг.ladix` теперь
  **исполняется** движком процессов (фича 006) — код `0`, байт-точный вывод сценария А (5 строк,
  id детерминированы `p-000001`/`t-000001`, маскируется только `<время>` дедлайна);
  `выручка.ladix` теперь parse-clean + run-demo метрика-триггера — код `0` (фича 007a); см. раздел ниже.

## Обязательные 7

| Файл | Назначение | Golden-stdout |
|---|---|---|
| `hello.ladix` | вывод (`печать`) | `Привет, Уклад!` |
| `арифметика.ladix` | арифметика и логика с приоритетами, переменные | `14 20` / `3 2` / `3.4` / `25` / `истина` / `истина` |
| `условие.ladix` | `если`/`иначе если`/`иначе`, области видимости | `категория: средний` / `чётная сумма` |
| `цикл.ladix` | `пока` и `для`, `прервать`/`продолжить` | `сумма чётных: 30` / `дорогие: [250, 400]` / `первая степень двойки > 16: 32` |
| `функция.ladix` | функция с параметрами и возвратом, ранний возврат | `2175.0` / `0` |
| `факториал.ladix` | рекурсия с базовым случаем | `120` / `1` |
| `ошибка.ladix` | понятная ошибка со строкой и колонкой | см. ниже (stderr, код возврата 1) |

Golden-stdout записан построчно (символ `/` — разделитель строк вывода, в файле это переводы строк).

### `ошибка.ladix` — точная диагностика

Программа синтаксически и семантически корректна, падает в рантайме. Проверяется **stderr** и
**код возврата 1** (§13). Деление на ноль — runtime-ошибка (правило продублировано в §4 и §13).

- Категория: деление на ноль (runtime).
- Позиция: строка 5, колонка 14 (счёт колонок с 1; колонка 14 указывает на оператор `/`).
- Код возврата: 1.

Эталонный stderr (двухстрочный формат):

```
Ошибка в строке 5, колонка 14:
деление на ноль
```

Опционально (если имплементация печатает исходную строку с кареткой — не обязательно по
контракту §13): после двух строк выводится строка-источник и `^` под оператором `/`.

## Бизнес-демонстрации (`онбординг` исполняется с фичи 006; `выручка` — с фичи 007a)

> **Статус.** Эти две программы демонстрируют декларативно-процессную часть Ladix —
> `источник`, `метрика`, `процесс`/`шаг`, триггер `когда`. Ядро разбирает объявления
> `источник`/`метрика` (фича 004), `процесс`/`шаг` (фича 005) и триггер `когда` (фича 007a);
> обе демо теперь исполняются:
>
> - `онбординг.ladix` теперь **исполняется** движком процессов (фича **006**): `ladix run`
>   завершается **кодом 0**, печатает байт-точный вывод сценария А (5 строк), создаёт инстанс
>   и человеческую задачу, упирается в человеческий шаг → статус `ожидает`. На свежем хранилище
>   id детерминированы (`p-000001`/`t-000001`), поэтому golden маскирует только `<время>`
>   дедлайна; зафиксировано тестом `cmd/ladix/main_test.go` (`TestRunOnboardingProcessDeferred`).
> - `выручка.ladix` теперь **parse-clean + run-demo** (фича **007a**): триггер `когда метрика …`
>   маршрутизируется в декларацию триггера, файл парсится чисто (раньше падал на «неожиданный
>   токен `когда`»), `ladix run` завершается **кодом 0**. При истинном условии метрика-триггер
>   срабатывает разово (fire-if-true) и запускает процесс. Регресс-замок `выручка.ladix` в
>   `parser/examples_test.go` инвертирован с parse-error на parse-clean (§TR-10.5).
>
> У `выручка.ladix` строгой golden-фикстуры нет (вывод дата-зависим — `период: ежемесячно`);
> детерминированный run-golden живёт в `cmd/ladix/trigger_golden_test.go`, который строит
> программы ВСТРОЕННО во временной директории (`t.TempDir()` + `os.WriteFile`), без окна и
> без testdata-фикстур (§TR-9 D-25). У `онбординг.ladix` есть golden сценария А с маской
> `<время>` (см. ниже).

| Файл | Назначение | Golden-stdout |
|---|---|---|
| `выручка.ladix` | источник + метрика + триггер «метрика → процесс» | parse-clean + run-demo (фича 007a), exit 0; строгой golden нет (вывод дата-зависим — `период: ежемесячно`) |
| `онбординг.ladix` | процесс с человеком-в-цикле, передача данных между шагами | код 0, golden сценария А (5 строк), id детерминированы, маска только `<время>` |

`выручка.ladix` использует фикстуру `data/sales.json` (в корне репозитория) и парсится чисто
(exit 0). Метрика-триггер `когда метрика выручка_месяца < 3_000_000:` исполняется разово в
`run` (fire-if-true): при истинном условии в среду тела инжектируется read-only `значение` =
вычисленная выручка, и `запустить процесс разбор_падения(значение)` создаёт инстанс с
человеческой задачей первого шага. Парсинг и семпроход детерминированы (не зависят от даты),
но stdout `run` зависит от системной даты (`период: ежемесячно` берёт окно от `сегодня()` →
истинность условия и состав вывода дата-зависимы), поэтому строгой stdout-фикстуры на `run
выручка.ladix` нет. Детерминизм закреплён ДВУМЯ замками в `cmd/ladix/trigger_golden_test.go`:
(1) встроенные fire-if-true программы во временной директории (`t.TempDir()` + `os.WriteFile`),
без окна и без testdata-фикстур; (2) `TestRevenueExampleFixedClockGolden` — прогон САМОГО
`выручка.ladix` через `runMetric(…, fixedClock2026, …)`: инжектированный FixedClock D=2026-05-31
ставит месячное окно на май 2026 → байт-точный stdout `2000000` (1_200_000 + 800_000) В ЛЮБОЙ
ДЕНЬ, без хардкода «сегодня». Отдельный канал проверки метрики — команда `metric` (README,
раздел CLI), которая под прод-Clock дата-зависима.

`онбординг.ladix` исполняется детерминированно (создаётся инстанс, авто-шаг `завести_доступы`
отрабатывает сразу, процесс упирается в человеческий шаг → статус `ожидает`). На свежем
хранилище id детерминированы (`p-000001`/`t-000001`), поэтому golden сценария А (5 строк,
exit 0) маскирует только `<время>` дедлайна; зафиксировано в `cmd/ladix/main_test.go`.
Полный жизненный цикл процессов (`run --db`/`tasks`/`complete`) проверяют unit-тесты движка со
Store, CLI-цепочка сценария Б и витринный `процесс.ladix` (см. ниже); подробнее — docs/engine-model.md.

`процесс.ladix` (US3 класс 4, фича 009) — витрина ПОЛНОГО жизненного цикла процесса на формах
005/006: процесс `выдача_заказа` с двумя человеческими шагами (`собрать_заказ` → `отгрузить`),
связанными `после`. Демонстрирует сценарий с `--db`: `ladix run --db <бд>` стартует инстанс и
открывает задачу первого шага; `ladix tasks --db <бд>` показывает её; `ladix complete <файл.ladix> <task-id>
--db <бд>` завершает шаг и **пробуждает** следующий (создаётся задача `отгрузить`, инстанс →
`ожидает`); повторный `tasks` показывает уже второй шаг; финальный `complete` доводит процесс до
`выполнен`. Парсится чисто (в parse-clean-наборе). Golden-замок последовательности —
`TestProcessLifecycleGolden` в `cmd/ladix/process_golden_test.go`: цепочка `realMain` против общей
БД в `t.TempDir()`, весь stdout через `maskIDs` (`<ID>`), шаги без `срок` → масок времени нет;
инверсия — если переход шага сломан или вывод разошёлся, замок краснеет.

## Витрина триггеров и метрик (US3, фича 009)

> Три примера на **уже поддержанных** формах языка (новой функциональности нет): два вида
> триггеров (`когда событие`, `когда расписание`) и мультиисточник/мультиметрика. Все три
> исполняются через `ladix run` с **кодом 0** и **детерминированным** выводом; каждый закреплён
> byte-точным golden-замком в `cmd/ladix/golden_test.go` и входит в parse-clean-набор
> `internal/parser/examples_test.go`.
>
> - `событие.ladix` — триггер `когда событие заявка_создана:` (форма 007a). Под `run` событийный
>   триггер не исполняется (его исполняет демон `serve`, фича 007b), а печатает строку-заглушку.
>   Тело (`запустить процесс …`) НЕ выполняется. Golden: `TestCLIGoldenEvent`.
> - `расписание.ladix` — два расписание-триггера: `когда расписание каждые 1дн:` и
>   `когда расписание в "09:00":` (формы 007a). Под `run` обе — заглушки (исполняет `serve`,
>   фича 007b), печатаются в порядке объявления. Golden: `TestCLIGoldenSchedule`.
> - `метрики.ladix` — **мультиисточник/мультиметрика**: два `источник` (`заказы`=`data/sales.json`,
>   `расходы`=`data/costs.json`) и три `метрика` БЕЗ `период`/`по_дате`, поэтому значения
>   **дата-независимы** (не берут окно от `сегодня()`). Метрика-триггеры (форма 007a) печатают
>   вычисленные значения через `значение`. Golden: `TestCLIGoldenMetrics` (прогон из корня репо
>   через `withRepoRoot`, чтобы относительные `data/*.json` резолвились).

| Файл | Назначение | Golden-stdout |
|---|---|---|
| `событие.ladix` | триггер `когда событие …` → процесс | `событие триггер 'заявка_создана' требует serve (фича 007b)`, exit 0 |
| `расписание.ladix` | триггеры `когда расписание каждые …` и `в "…":` | `расписание триггер '1дн' требует serve (фича 007b)` / `расписание триггер '09:00' требует serve (фича 007b)`, exit 0 |
| `метрики.ladix` | 2 источника + 3 метрики, мультиметрика (дата-независима) | `триггер 'выручка_оплачено < 10000000' сработал: выручка_оплачено = 2000000 (снимок) < 10000000 (порог) → истина` / `выручка оплаченных: 2000000` / `триггер 'число_заказов < 100' сработал: число_заказов = 3 (снимок) < 100 (порог) → истина` / `всего заказов: 3` / `триггер 'расходы_оплачено < 10000000' сработал: расходы_оплачено = 1000000 (снимок) < 10000000 (порог) → истина` / `расходы оплаченных: 1000000`, exit 0 |
| `контроль_плана.ladix` | полный золотой сценарий §2: CSV-источник + окно-метрика `выручка_30д` (последние 30дн) + триггер `когда метрика < 3_000_000` → 3-шаговый процесс `эскалация_плана` + эскалация дедлайна (016 B4a) + авто-шаги догона durable/exactly-once (M3-C2b) | дата-зависим (окно от `сегодня()`); golden пиннят FixedClock-замки `TestCLIControlPlanScalarFixedClock`/`TestCLIControlPlanRunFixedClock` (`control_plan_golden_test.go`). Метрика-старт под `run` (fire-if-true): триггер срабатывает (снимок `< 3_000_000`), открывается человеческая задача `связаться_с_клиентом`, эскалация — заглушка `требует serve (фича 007b)`, exit 0 |

`контроль_плана.ladix` (полный §2 хартии) — **золотой сквозной сценарий v2**, прошивающий
аналитику (M1) → триггер → автоматизацию (M2) → надёжность (M3), а не «срез M2/M3». Содержит
всё в одном файле: CSV-`источник заказы` (`data/orders.csv`, схема `поля:`), окно-метрику
`выручка_30д` (`период: последние 30дн`, `по_дате: дата_заказа`), метрика-триггер
`когда метрика выручка_30д < 3_000_000:` → `запустить процесс эскалация_плана(значение)`,
3-шаговый процесс `эскалация_плана` (человеческий шаг `связаться_с_клиентом` со `срок: 3дн` +
два авто-шага догона) и эскалацию дедлайна `когда задача просрочена в …`. Старт теперь
**метрика-driven** (литерал-старт убран): процесс запускает срабатывание метрика-триггера, а не
ручной литерал. `задача`/`просрочена` остаются обычными идентификаторами (D-AU-4), вид триггера
применяет парсер по контексту после `когда`.

Под `run` (fire-if-true): метрика-триггер срабатывает по снимку (`выручка_30д < 3_000_000` →
истина), открывается человеческая задача `связаться_с_клиентом`, эскалация дедлайна печатает
заглушку `… требует serve (фича 007b)` (исполняет демон `serve`, фича 007b/B4b — тело НЕ
выполняется под `run`). Полный жизненный цикл проходит через `serve`/`start`/`complete --данные`
(docs/quickstart.md §5). Вывод дата-зависим (окно от `сегодня()`), поэтому строгий доковый golden
здесь не приводится — детерминизм пиннят **FixedClock-замки** `TestCLIControlPlanScalarFixedClock`
и `TestCLIControlPlanRunFixedClock` (`control_plan_golden_test.go`).

Неявный контракт payload (**VITRINE-2**): авто-шаг `зафиксировать_итог` фиксирует
`итог = данные.итог` durable (split D-C-5), а `уведомить_crm` шлёт реальный эффект `crm`
выражением `"итог звонка: " + итог`. Поэтому `--данные '{"итог":…}'` (для `complete`) **должно
нести `итог` Строкой** — конкатенация `Строка + Строка` даёт эффект
`[уведомление] crm: итог звонка: перезвонит`. Без `--данные` отсутствующее поле открытой Записи
даёт `Пусто`, и шаг падает на конкатенации `'+' нельзя применить к Строка и Пусто` (exit 1).

Exactly-once (**VITRINE-3**): на рестарте демона эффект `уведомить_crm` переисполняется, но
outbox-леджер глушит повтор — POST в `crm` доставляется **РОВНО один раз**. Durable-гейт:
`TestStepEffectExactlyOnceRestart`.

`метрики.ladix` использует фикстуры `data/sales.json` и `data/costs.json` (в корне репозитория).
Метрики не используют `период`/`по_дате`, поэтому их значения постоянны независимо от системной
даты — в отличие от `выручка.ladix`, у которого `период: ежемесячно` делает stdout дата-зависимым.

## Витрина ошибок (US3, фича 009)

> Пять **негатив**-примеров демонстрируют пять РАЗНЫХ классов диагностики на штатном поведении
> (новой функциональности нет — это диагностика, а не фича). Каждый падает в `ladix run` с
> **кодом 1**, печатает РОВНО двухстрочный канон §13 («Ошибка в строке N, колонка M:» + сообщение
> класса) в stderr, без stdout и без Go stack trace. Каждый закреплён byte-точным негатив-замком
> в `cmd/ladix/golden_test.go` (полный stderr + код 1; пустой stderr+exit1 ложно НЕ проходит —
> различение классов идёт по фактическому тексту сообщения). Пиннинг строки/колонки/текста делает
> замок чувствительным: если пример перестал давать ИМЕННО свою ошибку — замок краснеет.
>
> - `ошибка_синтаксис.ladix` — **СИНТАКСИЧЕСКАЯ** ошибка: незакрытая скобка вызова `печать(имя`,
>   парсер упирается в конец файла. Падает на **ПАРСИНГЕ** → этот файл НЕ входит в parse-clean-набор
>   `internal/parser/examples_test.go` (он обязан не парситься). Замок: `TestCLINegativeSyntax`.
> - `ошибка_тип.ladix` — **ТИПОВАЯ** (семантическая) ошибка: сложение `Целое + Строка`. Парсится
>   **чисто** (в parse-clean-наборе), падает в **РАНТАЙМЕ** на несовместимости типов. Замок:
>   `TestCLINegativeType`.

## Витрина коннекторов источника (010-A1)

> Четыре демо активации `тип:`/`поля:` (010-A1): три **позитивных** коннектора в форматах
> CSV / NDJSON / JSON-со-схемой плюс один **негатив** с ошибкой схемы. Позитивные демо
> используют ОДИН эквивалентный набор записей в трёх формах (`data/orders.{csv,ndjson,json}`,
> в корне репозитория) под одной схемой `поля:` — поле `дата_заказа: Дата` (распознавание дат
> A1), `сумма_заказа: Дробное`, `статус: Строка`. Метрика `где статус == "оплачен"` + `сумма(…)`
> БЕЗ `период`/`по_дате` → значение **дата-независимо**, поэтому stdout детерминирован под
> прод-Clock (без `FixedClock`). Все три формата дают **байт-идентичный** скаляр
> `2300000.5` (1200000 + 800000.50 + 300000; отменённый 450000 отфильтрован) —
> эквивалентность форматов §SC-10 #2.
>
> - `источник_csv.ladix` — `тип: csv` + схема; ячейки CSV (все строки) коэрсятся в объявленные
>   типы. Golden: `TestCLIGoldenSourceCSV` (`cmd/ladix/golden_test.go`, прогон из корня репо через
>   `withRepoRoot`, SC-003 DoD-срез).
> - `источник_ndjson.ladix` — `тип: ndjson` + схема; один JSON-объект на строку, пустые строки
>   пропускаются (`data/orders.ndjson` их содержит). Целое `1200000` промоутится в `Дробное`.
> - `источник_json_схема.ladix` — `тип: json` + `поля:` поверх JSON-массива; схема типизирует
>   (распознаёт даты) и валидирует, для json опциональна.
> - `ошибочная.ladix` (НЕГАТИВ, §SC-10 #6) — поле `сумма_заказа: Целое` НЕ совпадает с дробным
>   `800000.50` в `data/orders.json` (запись 2) → коэрсия НЕ демоутит Дробное→Целое → ошибка
>   данных, exit 1, канон §13. Golden: `TestCLINegativeSourceSchema` (`cmd/ladix/golden_test.go`,
>   полный stderr + код 1, без Go stack trace).
>
> Эквивалентность форматов закреплена дополнительно на уровне eval-харнесса:
> `TestSourceFormatEquivalenceGolden` (`internal/eval/source_format_golden_test.go`) — один набор
> в `testdata/orders.{json,csv,ndjson}` под дата-зависимой метрикой `по_дате: дата_заказа` на
> `FixedClock 2026-05-31` → байт-точно равный скаляр во всех трёх формах. Негатив-замки ошибок
> данных и семантики (отсутствие поля / несовпадение типа / невалидная дата / CSV без столбца /
> неизвестный `тип:` / csv без `поля:` / неизвестный тип поля) — `cmd/ladix/source_negatives_test.go`.

## Витрина оконных метрик (011-A2)

> Шесть демо новой A2-функциональности — `период:` принимает **скользящее окно**
> `последние N <ед>` (`ед` ∈ `дн`/`нед`/`мес`) и **последний завершённый период**
> `прошлый <noun>` (`noun` ∈ `день`/`неделя`/`месяц`/`квартал`/`год`). Три **позитивных**
> демо над CSV-источником `data/orders.csv` (A1, в корне репозитория) + три **негатива**
> §MW-8 (недопустимая единица / неположительный размер / неизвестный noun).
>
> **Дата-зависимость.** Оконные метрики берут окно от `сегодня()` через `eval.Clock`,
> поэтому stdout под bare `ladix run` **дата-зависим** — строгой golden-фикстуры на
> системных часах НЕТ. Детерминизм фиксируется через harness с инъекцией
> **`FixedClock{2026,6,15}`** (НЕ конец месяца — §MW-D-WINDOW-EDGE): пиннинг `сегодня()`
> запрещён. По_дате ссылается на **голое Дата-поле** `дата_заказа` (схема `поля:`
> типизирует его как `Дата` — распознавание дат A1), БЕЗ обёртки `дата(...)`.
>
> - `окно_скользящее.ladix` — `период: последние 30дн` + триггер печатает `значение`.
>   Окно `(сегодня − 30дн, сегодня]` (нижняя граница ИСКЛЮЧЕНА — полуинтервал).
> - `окно_завершённое.ladix` — `период: прошлый месяц` (тот же календарный месяц, −1).
> - `выручка_30д.ladix` — **DoD-срез M1**: `последние 30дн` над `data/orders.csv`. На
>   `FixedClock{2026,6,15}` окно `(2026-05-16, 2026-06-15]` исключает заказы 2026-05-04
>   (1.2M) и 2026-05-12 (0.8M), оставляет 2026-05-27 (оплачен, 300000); 2026-05-19
