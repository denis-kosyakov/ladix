запустить процесс эскалация_плана(значение)` живёт только в Go-тесте
`src/internal/daemon/m2_endtoend_test.go` (`m2GoldenSrc`, `TestM2GoldenEndToEnd`).

**Что делаем.** Расширить `examples/контроль_плана.ladix` (вариант D-1=a) до полной
§2-цепочки: впаять аналитическую половину дословно из `выручка_30д.ladix` (тот же источник
`data/orders.csv`, та же окно-метрика `выручка_30д`), добавить триггер-связку, **убрать
хардкод-литеральный старт** (`пусть id = запустить процесс ...` + `печать`) — старт
становится метрика-driven. Ручной старт (B5) остаётся внешним путём через `ladix start`.

**Целевое содержимое `examples/контроль_плана.ladix` (копи-реди; точные комментарии — на
усмотрение импла, синтаксис — канон):**

```ladix
# Контроль плана продаж с эскалацией — золотой сквозной сценарий v2 (DoD §2 хартии).
# Прошивает аналитику (M1) → триггер → автоматизацию (M2) → надёжность (M3):
#   M1: CSV-источник со схемой полей + метрика как скользящее окно «последние 30дн».
#   связь: «когда метрика < план» запускает процесс, передавая снимок как аргумент.
#   M2: человеческий шаг+срок, эскалация дедлайна, payload (--данные), реальный эффект.
#   M3: эффект тела шага доставляется exactly-once через outbox даже на рестарте демона.
# Запуск — docs/quickstart.md §5 (serve/start/complete); данные — data/orders.csv.

# ── M1: аналитика ───────────────────────────────────────────────
источник заказы:
    файл: "data/orders.csv"
    тип: csv
    поля:
        дата_заказа: Дата
        сумма_заказа: Дробное
        статус: Строка

метрика выручка_30д:
    источник: заказы
    где:      статус == "оплачен"
    агрегат:  сумма(сумма_заказа)
    период:   последние 30дн
    по_дате:  дата_заказа

# ── связь: падение выручки ниже плана запускает процесс ─────────
когда метрика выручка_30д < 3_000_000:
    запустить процесс эскалация_плана(значение)

# ── M2: автоматизация (человек-в-цикле + эскалация + payload + эффект) ──
процесс эскалация_плана(факт):
    шаг связаться_с_клиентом:
        исполнитель: "менеджер"
        срок:        3дн
    # Авто-шаги догона (M3 §C-1, split D-C-5): durable-захват payload отдельно
    # от реального эффекта; на рестарте эффект переисполняется, но outbox
    # (exactly-once) глушит повтор — POST в crm РОВНО один раз.
    шаг зафиксировать_итог после связаться_с_клиентом:
        присвоить итог = данные.итог
    шаг уведомить_crm после зафиксировать_итог:
        уведомить crm("итог звонка: " + итог)

# ── эскалация дедлайна (исполняет демон serve; под run — заглушка) ──
когда задача просрочена в эскалация_плана.связаться_с_клиентом:
    уведомить руководитель(факт)
```

**Design-note: дата-зависимость и тест-стратегия (КРИТИЧНО для импла).** Окно
`последние 30дн` дата-зависимо → побайтный golden под голым `run`/SystemClock невозможен
(снимок метрики плывёт по дате). **Ловушка:** голый `run` сегодня даёт ровно `300000.0` (как и
golden) — это сиюминутное совпадение: окно `(d−30, d]` начиная с `2026-06-26` исключит
единственный оплаченный заказ `2026-05-27` → значение поедет к `0.0`. Поэтому golden ОБЯЗАН
быть на `FixedClock{2026,6,15}`, не на SystemClock — НЕ соблазняться голым `run`. Тест-стратегия:
- **T-GOLD-METRIC `[импл]`** — новый FixedClock-golden, пинит 3 фасета РАЗНЫМИ путями (важно —
  один `runMetric`-паттерн их все НЕ закроет):
  - (i) **скаляр** `выручка_30д = 300000.0` — паттерн `runMetric` (`metric_window_golden_test.go`,
    `TestCLIMetricWindowDoDGolden`: `FixedClock{2026,6,15}`, прогон из repo-root для `data/orders.csv`).
  - (ii) **строка explain** метрика-триггера + (iii) **метрика-driven старт** инстанса `p-000001`
    процесса `эскалация_плана` — только **RUN-путь** (`realMain([]{"run", …})` → `runFile` →
    `interp.Run` → `interp.RunTriggers` → `ExplainFire`), `runMetric` их НЕ эмитит (не зовёт
    `Run`/`RunTriggers`). Живой референс run-пути с инъекцией FixedClock — `clock_unify_test.go:52`
    (`runFile(prog, "", depth, nil, clock, &out, &err)`). Формат explain — канон
    `reliability-model.md §C-5.3`; точные байты — с живого бинаря, impl-time. **ВНИМАНИЕ:**
    очевидный кандидат `trigger_golden_test.go:507` (`TestRevenueExampleFixedClockGolden`) для
    (ii)/(iii) НЕ годится — он тоже зовёт `runMetric`, пинит лишь скаляр.
  - **Заменяет** существующий `TestCLIGoldenDeadlineEscalation` (см. ниже).
- **T-LIFECYCLE `[импл]`** — герметичный замок жизненного цикла (закрывает DOCSYNC-QS-1,

  `инстанс p-000001: выполнен`. Дедлайн маскируется (`<DT>`), дат в stdout эффекта нет.
- **Терминальные гейты остаются:** `TestM2GoldenEndToEnd` (§AU-12.C, эскалация+webhook POST)
