# Быстрый старт: первая метрика и первый процесс за 5 минут

Это пошаговое руководство для пользователя «Уклада». За пять минут вы соберёте Ladix
из исходников, запустите первую программу, посчитаете метрику над данными и проведёте
бизнес-процесс через шаг-человека от старта до завершения.

Всё ниже воспроизводимо из свежего клона репозитория и опирается на готовые файлы из
каталога `examples/`. Полный справочник по командам CLI — в [README](../README.md).

> Все команды выполняются из **корня репозитория**, кроме шага сборки (он начинается с
> `cd src`). Так и задумано: бинарник `./ladix`, каталоги `examples/` и `data/` лежат в
> корне рядом, а примеры с источниками ссылаются на `data/...` относительно текущего
> каталога.

---

## Шаг 1. Сборка

Нужен только Go 1.25 или новее (без CGO и внешних C-библиотек). Go-модуль лежит в
подкаталоге `src/`, поэтому собираем оттуда, а мост `-o ../ladix` кладёт готовый бинарник
в **корень** репозитория:

```sh
cd src && go build -o ../ladix ./cmd/ladix
```

После сборки вернитесь в корень репозитория — дальше все команды запускаются как `./ladix`
именно из корня:

```sh
cd ..
```

---

## Шаг 2. Первая программа

Разовый прогон готового примера `examples/hello.ladix`:

```sh
./ladix run examples/hello.ladix
```

Ожидаемый вывод:

```
Привет, Уклад!
```

Полезный вывод программы (`печать`, сводки) идёт в stdout; диагностика ошибок — в stderr.
Код возврата `0` означает успех.

---

## Шаг 3. Первая метрика

Метрика считает агрегат над источником данных. Готовый пример `examples/метрики.ladix`
объявляет два источника (заказы из `data/sales.json`, расходы из `data/costs.json`) и три
метрики над ними. Фрагмент:

```ladix
# Источник: заказы (записи { клиент, дата_заказа, сумма_заказа, статус })
источник заказы:
    файл: "data/sales.json"

# Метрика: выручка по оплаченным заказам
метрика выручка_оплачено:
    источник: заказы
    где:      статус == "оплачен"
    агрегат:  сумма(сумма_заказа)
```

Поля записи источника (`статус`, `сумма_заказа`) внутри `где` и `агрегат` пишутся просто
именем — их область видимости задаёт привязка к источнику.

Посчитать одну метрику командой `metric` (путь к файлу + имя метрики):

```sh
./ladix metric examples/метрики.ladix выручка_оплачено
```

Ожидаемый вывод:

```
2000000
```

Метрики из `метрики.ladix` объявлены **без `период`/`по_дате`**, поэтому их значение
детерминировано и не зависит от текущей даты. Можно посчитать и другие метрики из того же
файла:

```sh
./ladix metric examples/метрики.ladix число_заказов     # → 3
./ladix metric examples/метрики.ladix расходы_оплачено  # → 1000000
```

> Метрика с периодом (`период: ежемесячно` + `по_дате: ...`) считается относительно текущей
> даты, и тогда её значение зависит от данных и дня запуска. Для предсказуемого первого
> знакомства используйте метрики без периода, как в `метрики.ladix`.

## Шаг 4. Первый процесс

Процесс описывает шаги, исполнителей и переходы. Готовый пример `examples/процесс.ladix`
описывает выдачу заказа двумя человеческими шагами, связанными словом `после`:

```ladix
процесс выдача_заказа(номер_заказа):
    шаг собрать_заказ:
        исполнитель: "комплектовщик"
        присвоить заказ = номер_заказа
    шаг отгрузить после собрать_заказ:
        исполнитель: "логист"

пусть id = запустить процесс выдача_заказа("ЗК-42")
печать("запущена выдача заказа, id:", id)
```

Шаг с `исполнитель:` — это работа человека: процесс доходит до него и встаёт в ожидание.
Чтобы такой инстанс пережил прогон и его можно было продвинуть внешней командой, нужен флаг
`--db` (состояние сохраняется в файл SQLite; здесь — `demo.db`).

**4.1. Запуск процесса** создаёт инстанс и первую задачу:

```sh
./ladix run examples/процесс.ladix --db demo.db
```

Вывод:

```
[задача] t-000001 → комплектовщик, шаг 'собрать_заказ'
запущена выдача заказа, id: p-000001
открытых задач: 1
t-000001  p-000001  'собрать_заказ'  комплектовщик
```

**4.2. Список открытых задач** командой `tasks`:

```sh
./ladix tasks --db demo.db
```

Вывод:

```
t-000001  p-000001  'собрать_заказ'  комплектовщик
```

**4.3. Завершение первого шага** командой `complete` (путь к файлу + id задачи из вывода
выше). Это будит инстанс и продвигает его к следующему шагу:

```sh
./ladix complete examples/процесс.ladix t-000001 --db demo.db
```

Вывод:

```
задача t-000001 завершена
[задача] t-000002 → логист, шаг 'отгрузить'
инстанс p-000001: ожидает, шаг 'отгрузить'
```

**4.4. Завершение второго шага** доводит процесс до конца:

```sh
./ladix complete examples/процесс.ladix t-000002 --db demo.db
```

Вывод:

```
задача t-000002 завершена
инстанс p-000001: выполнен
```

Теперь `./ladix tasks --db demo.db` напечатает `открытых задач нет`. Файл `demo.db` можно
удалить (`rm demo.db`) — он держит только состояние процесса, истина всегда в исходнике.

> Идентификаторы `t-000001`/`p-000001` детерминированы для свежей БД (счётчик начинается с
> единицы). Если запускать `run --db` поверх существующей `demo.db`, создаются новые
> инстансы с бо́льшими номерами — это нормально.

Хотите процесс без БД и источников? Запустите `./ladix run examples/онбординг.ladix` —
эфемерный прогон (без `--db`) создаёт инстанс в памяти, печатает id и сводку висящих задач,
но не сохраняет их (внешний `complete` к эфемерному инстансу неприменим). У шагов этого
примера есть `срок:`, поэтому в строке задачи появится `срок до <время>` — это значение
зависит от даты запуска.

## Шаг 5. Автоматизация процессов

В шаге 4 процесс запускался из тела программы (`запустить процесс ...` при `run`). Здесь
показан **золотой сквозной сценарий v2**: метрика как скользящее окно «последние 30дн»
запускает процесс, процесс ведёт человека через несколько шагов, эскалация дедлайна сама
шлёт уведомление под демоном `serve`, а данные из `complete --данные` доезжают до реального
эффекта. Процесс стартует **внешней командой** `ladix start`, инстанс осматривается командой
`ladix inspect`. Витрина — пример `examples/контроль_плана.ladix`. Он **многошаговый**:
человеческий шаг `связаться_с_клиентом` со сроком `3дн`, затем авто-шаг `зафиксировать_итог`
читает поле `данные.итог` из payload, и наконец `уведомить_crm` производит реальный эффект.
Ниже — сокращённый фрагмент (полный файл с источником, метрикой-окном и обоими триггерами —
в [`examples/контроль_плана.ladix`](../examples/контроль_плана.ladix)):

```ladix
# связь: падение выручки ниже плана запускает процесс
когда метрика выручка_30д < 3_000_000:
    запустить процесс эскалация_плана(значение)

процесс эскалация_плана(факт):
    шаг связаться_с_клиентом:
        исполнитель: "менеджер"
        срок:        3дн
    шаг зафиксировать_итог после связаться_с_клиентом:
        присвоить итог = данные.итог
    шаг уведомить_crm после зафиксировать_итог:
        уведомить crm("итог звонка: " + итог)

# эскалация дедлайна (исполняет демон serve; под run — заглушка)
когда задача просрочена в эскалация_плана.связаться_с_клиентом:
    уведомить руководитель(факт)
```

В отличие от шага 4, здесь нет строки `запустить процесс ...` в теле программы — инстанс
рождается **триггером**. При `run` метрика-триггер оценивается один раз сразу после загрузки
источников (`fire-if-true`) и, если условие истинно, запускает процесс прямо в этом прогоне,
печатая строку-объяснение «почему». Триггер `когда задача просрочена в <Процесс>.<шаг>:` —
это эскалация дедлайна: его тело исполняет только демон `serve` (нужен живой таймер), под
`run` он печатает строку-заглушку:

```sh
./ladix run examples/контроль_плана.ladix
```

```
триггер 'выручка_30д < 3000000' сработал: выручка_30д = 300000.0 (снимок) < 3000000 (порог) → истина
[задача] t-000001 → менеджер, шаг 'связаться_с_клиентом', срок до <время>
задача триггер 'эскалация_плана.связаться_с_клиентом' требует serve (фича 007b)
открытых задач: 1
t-000001  p-000001  'связаться_с_клиентом'  менеджер  срок до <время>
```

Первая строка — это **always-on explain**: метрика-триггер всегда печатает, почему он
сработал (снимок метрики, порог, результат сравнения). Так пользователь видит «почему»
прямо под `run`/`serve`, без отдельного флага.

**5.1. Внешний запуск процесса** командой `start` (путь к файлу + имя процесса +
аргументы). Аргументы — типизированные литералы (`2500000` → `Целое`), их число
сверяется с параметрами процесса. У `start` дефолтное хранилище — SQLite-файл `ladix.db`
(в отличие от `run`, который без `--db` эфемерен):

```sh
./ladix start examples/контроль_плана.ladix эскалация_плана 2500000 --db demo.db
```

Вывод (две строки; `<время>` зависит от даты запуска — дедлайн `3дн` от «сегодня»):

```
[задача] t-000001 → менеджер, шаг 'связаться_с_клиентом', срок до <время>
запущен инстанс p-000001
```

Если число аргументов не совпало или процесс не объявлен — `start` сообщает об этом до
запуска, например: `ladix: процесс 'эскалация_плана' ожидает 1 аргументов, получено 0`
или `ladix: процесс 'неизвестный' не объявлен` (exit `2`).

**5.2. Снимок инстанса** командой `inspect` (id из вывода выше; файл не принимается — всё
читается из БД). Печатает статус, текущий шаг, переменные процесса и историю задач:

```sh
./ladix inspect p-000001 --db demo.db
```

```
инстанс p-000001: процесс эскалация_плана, статус ожидает, шаг 'связаться_с_клиентом'
переменные:
  факт = 2500000
задачи:
  t-000001 шаг 'связаться_с_клиентом' → менеджер, срок до <время>, открыта
```

Когда задача эскалирована (см. 5.3), её строка получает хвост `, эскалирована`. Неизвестный
id → `ladix: инстанс 'p-999999' не найден`, exit `2`.

**5.3. Эскалация дедлайна под `serve`.** Тело триггера эскалации исполняет только демон-
планировщик. Запускаем его над **тем же файлом БД** — флаг `--db` для `serve` **обязателен
явно**: без него `serve` поднимается над эфемерным хранилищем в памяти и не видит инстанс из
шага 5.1.

```sh
./ladix serve examples/контроль_плана.ladix --db demo.db
```

> На старте `serve` исполняет top-level тело программы (печать, глобалы), но метрика-триггер
> **новый инстанс на boot не порождает**: семантика серверной метрики — это **ребро**
> `ложь→истина`. Первый тик лишь праймит текущее значение без срабатывания, а постоянно
> истинное `выручка_30д < 3000000` после прайма уже не пересекает порог и не стартует процесс.
> Поэтому метрика-driven старт инстанса демонстрируется **через `run`** (см. golden выше —
> `fire-if-true` запускает процесс прямо в прогоне), а под `serve` метрика-триггер ждёт
> реального перехода через порог. Эскалация дедлайна ниже — это про **срок задачи**, не про
> метрику, и под `serve` работает как описано.

Демон оценивает триггеры на каждом тике. Как только задача `t-000001` пересечёт свой срок
(дедлайн `3дн`), 4-я фаза тика заметит просрочку и исполнит тело эскалации —
`уведомить руководитель(факт)` напечатает (с переменной процесса `факт`):

```
[уведомление] руководитель: 2500000
```

Эскалация срабатывает **ровно один раз на задачу**: демон помечает задачу как
эскалированную в БД (durable), поэтому повторные тики и даже перезапуск `serve` поверх того
же `demo.db` уведомление не дублируют. После этого `./ladix inspect p-000001 --db demo.db`
покажет строку задачи с хвостом `, эскалирована`. Остановить демон — `Ctrl-C`.

> Чтобы увидеть эскалацию быстро, не дожидаясь трёх суток, можно временно уменьшить `срок:`
> в копии примера (например, до `1мин`) и запустить `serve` с коротким `--interval`. Сам
> пример `контроль_плана.ladix` оставьте как есть — на нём держатся другие проверки.

**5.4. Передача данных в задачу** через `complete --данные '{...}'`. JSON-объект приходит в
догон процесса как read-only эфемерная Запись `данные` и доступен **только первому шагу
догона** (в БД не сохраняется). `контроль_плана.ladix` **многошаговый**: завершение
человеческого шага будит инстанс, авто-шаг `зафиксировать_итог` читает `данные.итог`, а
следующий авто-шаг `уведомить_crm` производит реальный эффект — конкатенирует строку и
шлёт её в crm. Поэтому payload здесь не просто завершает инстанс, а реально доезжает до
эффекта:

```sh
./ladix complete examples/контроль_плана.ladix t-000001 --данные '{"итог":"перезвонит"}' --db demo.db
```

```
задача t-000001 завершена
[уведомление] crm: итог звонка: перезвонит
инстанс p-000001: выполнен
```

Невалидный JSON отвергается до изменения состояния: `ladix: неверный JSON в --данные:
<деталь>`, exit `2` (инстанс остаётся ожидать).

**Без флага `--данные` догон падает — и `--данные` обязателен для осмысленного прохода.**
Доступ `данные.итог` сам по себе **не падает**: отсутствующее поле открытой Записи `данные`
даёт `Пусто`, и переменная `итог` становится `Пусто`. Ошибка возникает **шагом позже** — на
конкатенации `"итог звонка: " + итог` в шаге `уведомить_crm`: `'+' нельзя применить к Строка
и Пусто` (exit `1`). Поэтому, чтобы догон дошёл до эффекта `уведомить_crm`, поле `итог`
обязано быть Строкой — передавайте его через `--данные '{"итог":"..."}'`.

**5.5. Реальный HTTP-эффект (опционально).** По умолчанию `вызвать`/`уведомить` печатают
стаб (`[вызов] цель(...)`, `[уведомление] цель: ...`). С флагом `--вебхук <URL>` (или
переменной окружения `LADIX_WEBHOOK`) те же действия делают HTTP POST с телом
`{"цель": <цель>, "данные": [<аргументы>]}` на указанный URL — флаг доступен у `run`,
`start`, `complete` и `serve`:

```sh
./ladix serve examples/контроль_плана.ladix --db demo.db --вебхук https://example.test/hook
```

Невалидный URL → `ladix: неверный URL вебхука '<URL>'`, exit `2`.

Файл `demo.db` после знакомства можно удалить (`rm demo.db`) — он держит только состояние
процессов, истина всегда в исходнике.

## Шаг 6. События и расписания

Кроме метрики-триггера (шаг 5) демон `serve` реагирует ещё на два вида триггеров: **внешние
события** (`когда событие <Имя>:`) и **расписания** (`когда расписание ...:`). Под `run` они —
заглушки (нужен живой демон), но синтаксис и поток видны и без него.

**6.1. Внешние события.** Пример `examples/событие.ladix` объявляет реакцию
`когда событие заявка_создана:` → запустить процесс. Под `run` тело не исполняется:

```sh
./ladix run examples/событие.ladix
```

```
событие триггер 'заявка_создана' требует serve (фича 007b)
```

Событие в очередь демона ставит команда `ladix emit <событие> [json]`. Она пишет событие в
общий `Store` и выходит, печатая id поставленного события (`e-...`); демон `serve` над тем же
`--db` разберёт его на ближайшем тике и исполнит тело совпавшего триггера:

```sh
./ladix emit заявка_создана '{"клиент":"ООО Ромашка"}' --db demo.db
```

Без флага `--db` у `emit` дефолтное хранилище — `ladix.db`; чтобы демон увидел событие, и
`serve`, и `emit` должны работать над **одним и тем же** файлом БД.

**6.2. Расписания.** Пример `examples/расписание.ladix` показывает обе формы:
`когда расписание каждые 1дн:` (периодический интервал) и `когда расписание в "09:00":`
(ежедневно в указанное время). Под `run` обе — заглушки:

```sh
./ladix run examples/расписание.ladix
```

```
расписание триггер '1дн' требует serve (фича 007b)
расписание триггер '09:00' требует serve (фича 007b)
```

Под `serve` демон оценивает расписания на каждом тике и исполняет тело, когда наступает
очередной момент (интервал истёк или настал указанный час).
