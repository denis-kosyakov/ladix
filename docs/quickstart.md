# Быстрый старт: первая метрика и первый процесс за 5 минут

Это пошаговое руководство для пользователя «Уклада». За пять минут вы соберёте Ladix
из исходников, запустите первую программу, посчитаете метрику над данными и проведёте
бизнес-процесс через шаг-человека от старта до завершения.

Всё ниже воспроизводимо из свежего клона репозитория и опирается на готовые файлы из
каталога `examples/`. Полный справочник по командам CLI — в [README](../README.md).

> Все команды выполняются из **корня репозитория**, кроме шага сборки (он начинается с
> `cd src`). Так и задумано: бинарник `./ladix`, каталоги `examples/` и `data/` лежат в
> корне рядом, а примеры с источниками ссылаются на `data/...` относительно текущего
> каталога.

---

## Шаг 1. Сборка

Нужен только Go 1.22 или новее (без CGO и внешних C-библиотек). Go-модуль лежит в
подкаталоге `src/`, поэтому собираем оттуда, а мост `-o ../ladix` кладёт готовый бинарник
в **корень** репозитория:

```sh
cd src && go build -o ../ladix ./cmd/ladix
```

После сборки вернитесь в корень репозитория — дальше все команды запускаются как `./ladix`
именно из корня:

```sh
cd ..
```

---

## Шаг 2. Первая программа

Разовый прогон готового примера `examples/hello.ladix`:

```sh
./ladix run examples/hello.ladix
```

Ожидаемый вывод:

```
Привет, Уклад!
```

Полезный вывод программы (`печать`, сводки) идёт в stdout; диагностика ошибок — в stderr.
Код возврата `0` означает успех.

---

## Шаг 3. Первая метрика

Метрика считает агрегат над источником данных. Готовый пример `examples/метрики.ladix`
объявляет два источника (заказы из `data/sales.json`, расходы из `data/costs.json`) и три
метрики над ними. Фрагмент:

```ladix
# Источник: заказы (записи { клиент, дата_заказа, сумма_заказа, статус })
источник заказы:
    файл: "data/sales.json"

# Метрика: выручка по оплаченным заказам
метрика выручка_оплачено:
    источник: заказы
    где:      статус == "оплачен"
    агрегат:  сумма(сумма_заказа)
```

Поля записи источника (`статус`, `сумма_заказа`) внутри `где` и `агрегат` пишутся просто
именем — их область видимости задаёт привязка к источнику.

Посчитать одну метрику командой `metric` (путь к файлу + имя метрики):

```sh
./ladix metric examples/метрики.ladix выручка_оплачено
```

Ожидаемый вывод:

```
2000000
```

Метрики из `метрики.ladix` объявлены **без `период`/`по_дате`**, поэтому их значение
детерминировано и не зависит от текущей даты. Можно посчитать и другие метрики из того же
файла:

```sh
./ladix metric examples/метрики.ladix число_заказов     # → 3
./ladix metric examples/метрики.ladix расходы_оплачено  # → 1000000
```

> Метрика с периодом (`период: ежемесячно` + `по_дате: ...`) считается относительно текущей
> даты, и тогда её значение зависит от данных и дня запуска. Для предсказуемого первого
> знакомства используйте метрики без периода, как в `метрики.ladix`.

## Шаг 4. Первый процесс

Процесс описывает шаги, исполнителей и переходы. Готовый пример `examples/процесс.ladix`
описывает выдачу заказа двумя человеческими шагами, связанными словом `после`:

```ladix
процесс выдача_заказа(номер_заказа):
    шаг собрать_заказ:
        исполнитель: "комплектовщик"
        присвоить заказ = номер_заказа
    шаг отгрузить после собрать_заказ:
        исполнитель: "логист"

пусть id = запустить процесс выдача_заказа("ЗК-42")
печать("запущена выдача заказа, id:", id)
```

Шаг с `исполнитель:` — это работа человека: процесс доходит до него и встаёт в ожидание.
Чтобы такой инстанс пережил прогон и его можно было продвинуть внешней командой, нужен флаг
`--db` (состояние сохраняется в файл SQLite; здесь — `demo.db`).

**4.1. Запуск процесса** создаёт инстанс и первую задачу:

```sh
./ladix run examples/процесс.ladix --db demo.db
```

Вывод:

```
[задача] t-000001 → комплектовщик, шаг 'собрать_заказ'
запущена выдача заказа, id: p-000001
открытых задач: 1
t-000001  p-000001  'собрать_заказ'  комплектовщик
```

**4.2. Список открытых задач** командой `tasks`:

```sh
./ladix tasks --db demo.db
```

Вывод:

```
t-000001  p-000001  'собрать_заказ'  комплектовщик
```

**4.3. Завершение первого шага** командой `complete` (путь к файлу + id задачи из вывода
выше). Это будит инстанс и продвигает его к следующему шагу:

```sh
./ladix complete examples/процесс.ladix t-000001 --db demo.db
```

Вывод:

```
задача t-000001 завершена
[задача] t-000002 → логист, шаг 'отгрузить'
инстанс p-000001: ожидает, шаг 'отгрузить'
```

**4.4. Завершение второго шага** доводит процесс до конца:

```sh
./ladix complete examples/процесс.ladix t-000002 --db demo.db
```

Вывод:

```
задача t-000002 завершена
инстанс p-000001: выполнен
```

Теперь `./ladix tasks --db demo.db` напечатает `открытых задач нет`. Файл `demo.db` можно
удалить (`rm demo.db`) — он держит только состояние процесса, истина всегда в исходнике.

> Идентификаторы `t-000001`/`p-000001` детерминированы для свежей БД (счётчик начинается с
> единицы). Если запускать `run --db` поверх существующей `demo.db`, создаются новые
> инстансы с бо́льшими номерами — это нормально.

Хотите процесс без БД и источников? Запустите `./ladix run examples/онбординг.ladix` —
эфемерный прогон (без `--db`) создаёт инстанс в памяти, печатает id и сводку висящих задач,
но не сохраняет их (внешний `complete` к эфемерному инстансу неприменим). У шагов этого
примера есть `срок:`, поэтому в строке задачи появится `срок до <время>` — это значение
зависит от даты запуска.
