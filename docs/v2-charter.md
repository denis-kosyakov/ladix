# Хартия v2 — план эволюции Ladix от v1 к v2

> **Статус:** v2 M1-M3 отгружены; финализация. Источник истины для конвейера v1→v2.
> **Назначение:** заменить отсутствующий внешний критерий приёмки для v2 (внешняя приёмка
> касается только базы v1) — задать линию финиша, очередь работ, несущие инварианты и
> правила управления, по которым катится автономный конвейер фич.
> **Предшественник:** v1 полностью закрыт (specs 001–009, master). Эта хартия не повторяет
> закрытое; см. `SPEC.md §12`, `README.md` (раздел «Скоуп v1»), `docs/` модели.

---

## 1. Что такое «v2»

«v2» Ladix — это **продуктовый бэклог Уклада**, а не набор дополнительных возможностей generic-ТЗ.

- Таблица дополнительных возможностей `TASK.md` перечисляет generic-фичи построения языков (массивы, статтипизация,
  классы, модули, стдлиб, REPL, компиляция в байткод/LLVM, оптимизации, отладчик) и ни словом
  не касается метрик/процессов/триггеров/Уклада. `CHECKLIST.md` плоский (≈50 пунктов, все базовые,
  уже закрыты). Формальной опоры у v2 во внешних приёмочных артефактах нет.
- Реальный реестр v2 — **`SPEC.md §12 «Ограничения версии 1»`** (8 тематических групп отложенного,
  у каждого пункта прописан «путь отступления») и дублирующий его блок «Что отложено (v2)» в README.

**Несущее свойство:** все снятия §12 **аддитивны** — синтаксис v1-программ не ломается. Новые
ключевые слова уже зарезервированы в лексере (`параллельно`, `модуль`, `импорт`, `экспорт`,
`повторить`, `выбрать`, `пытаться`, `словить`, `бросить`, `асинхронно`, `ждать`, `тип`), блоки
атрибутов (`источник`, `шаг`) расширяются новыми ключами без поломки, фронтенд и контракт Store
не переписываются. Это и делает непрерывный автономный конвейер допустимым.

**Код опережает раннюю фиксацию:** исполнение тела шага (006), демон `serve` с триггерами и
рестарт-сканом (007) уже реализованы и смержены; блокер кеша `today`/`recordCache` закрыт через
`ResetRunState`. v2 стартует с высокой базы.

**Аудитория задаёт приоритет:** в продукте Ladix пишут не программисты, а бизнес-пользователи и
операторы Уклада. Для них качество диагностики (понятные ошибки при авторинге) и наблюдаемость
рантайма (почему триггер сработал, что вычислила метрика, на каком шаге застрял процесс) — прямая
продуктовая ценность, а не косметика. Поэтому v2 включает их в скоуп наравне с доменными фичами
(§3, §4). Побочно это закрывает дополнительные возможности «хорошее восстановление после ошибок»
и «отладчик/трассировка» — выравнивание, а не драйвер.

## 2. Линия финиша: золотой сквозной сценарий (= Definition of Done)

v2 считается достигнутой, когда **один продуктовый сценарий Уклада проходит зелёным end-to-end
и переживает рестарт демона**. Сценарий прошивает всю цепочку аналитика → автоматизация и тем
самым сам отбирает, какие пункты §12 входят в v2.

### Сценарий «Контроль плана продаж с эскалацией»

> Реальный источник (CSV-выгрузка заказов Уклада с объявленной схемой полей) → метрика выручки
> как **скользящее окно** → триггер на падение ниже плана запускает процесс → менеджер получает
> задачу со **сроком**, при просрочке срабатывает **эскалация** руководителю → менеджер закрывает
> задачу, **передавая результат звонка** в процесс → процесс делает **реальный** вызов/уведомление.
> Оператор может стартовать тот же процесс вручную (`ladix start`).

Иллюстративная программа (пометки `[v2/Mn]` — конструкции, активируемые соответствующей вехой;
точная форма v2-синтаксиса фиксируется в спецификации фичи, не здесь):

```ladix
# ── M1: аналитика ───────────────────────────────────────────────
источник заказы:
    файл:    "data/orders.csv"
    тип:     csv                       # [v2/M1] атрибут тип: (json | csv | ndjson)
    поля:                              # [v2/M1] объявление и валидация схемы
        дата_заказа:  Дата
        сумма_заказа: Дробное
        статус:       Строка

метрика выручка_30д:
    источник: заказы
    где:      статус == "оплачен"
    агрегат:  сумма(сумма_заказа)
    период:   последние 30дн           # [v2/M1] скользящее окно (v1: только ежемесячно/…)
    по_дате:  дата(дата_заказа)

# ── связь: триггер (v1) ─────────────────────────────────────────
когда метрика выручка_30д < 3_000_000:
    запустить процесс эскалация_плана(значение)

# ── M2: автоматизация ───────────────────────────────────────────
процесс эскалация_плана(текущая_выручка):
    шаг связаться_с_клиентом:
        исполнитель: "менеджер"
        срок:        2дн
        присвоить факт = текущая_выручка
    шаг зафиксировать_итог после связаться_с_клиентом:   # [v2/M3] авто-шаг: захват payload в durable-переменную
        присвоить итог = данные.итог
    шаг уведомить_crm после зафиксировать_итог:          # [v2/M3] авто-шаг: реальный эффект в теле шага
        уведомить crm("итог звонка: " + итог)            # [v2/M3-C2] exactly-once через outbox на рестарте

# [v2/M2-B4] эскалация по дедлайну (форма уточняется в фиче):
когда задача просрочена в эскалация_плана.связаться_с_клиентом:
    уведомить руководитель(факт)        # [v2/M2-B2] реальная доставка

# [v2/M2-B3] закрытие с payload:  ladix complete <файл> <id> --данные '{"итог":"перезвонит"}'
# [v2/M2-B5] ручной старт:        ladix start эскалация_плана 2500000
```

**Критерий «зелёный»:** прогон end-to-end (`serve` + реальный CSV-источник + сработавший триггер +
человеческий шаг + просрочка-эскалация + payload + реальный эффект **в теле шага**) даёт ожидаемый
результат и **переживает рестарт демона с живым инстансом** без потери/дублирования состояния.

> **Усиление M3 (гейт-критерий надёжности).** Реальный эффект живёт **в теле авто-шага**
> (`уведомить crm`, потребляющий payload человеческого шага через durable-переменную `итог`). На
> рестарте mid-advance движок переисполняет тело шага (`ReactivateInstance` → `advance` от
> `CurrentStep`) — это зазор **at-least-once**, который закрывает outbox (M3-C2b): эффект доставлен
> **exactly-once, POST ровно 1** через дедупликацию по ключу `инстанс + шаг + индекс_эффекта`.
> *Честная граница:* payload эфемерен (D-AU-3) — крах в узком окне между завершением человеческого
> шага и его захватом в durable-переменную теряет payload (вне scope outbox); exactly-once
> гарантируется для эффекта, читающего **уже сохранённую** переменную.

К DoD добавляются два среза для целевой аудитории (§1):
- **Диагностика:** ошибочная версия программы сценария даёт чистые, бизнес-понятные диагностики
  с номерами строк и без каскада фантомных сообщений на одной строке.
- **Наблюдаемость:** после прогона оператор командами инспекции/трассировки видит, *почему*
  сработал триггер (значение метрики против порога), *на каком шаге* инстанс и *историю* эскалации.

> Сценарий — единственная продуктово-определяемая часть хартии. Если доменная история должна быть
> другой, правится здесь; всё ниже от него производно.

## 3. Скоуп v2

### В скоупе (отбираются сценарием §2)

Источники-коннекторы и схема полей; ряды/скользящие окна метрик; реальные `вызвать`/`уведомить`;
захват результата вызова; payload задачи; эскалация дедлайна; `ladix start`; продакшен-надёжность
(версионирование определений, миграции схемы, exactly-once, стабильные ключи триггеров); по нужде
сценария — реестр ролей и серверная модель. **Диагностика авторинга** (восстановление парсера,
качество сообщений для бизнес-пользователя; покрывает §12 группу 4) и **наблюдаемость рантайма**
(инспекция инстанса, трассировка и объяснимость «почему сработало») — для целевой аудитории §1.

### Явно вне v2 первого среза (в хартию — чтобы конвейер имел границу)

| Вне скоупа | Причина |
|---|---|
| **Параллельные шаги (`параллельно`)** | Единственный XL-пункт с глубоким каскадом (переписывает `CurrentStep`→множество токенов, схему SQLite, гарды `complete` D-4/D-8, машину состояний fork/join). Исключение сохраняет инвариант «весь v2 аддитивен». Синтаксис `после` уже готов — берётся отдельной изолированной фичей позже. |
| Модули / `импорт` | Нужны при росте кодовой базы, не для сценария §2. |
| Статическая типизация | Конфликтует с динамической философией v1; чисто академическая возможность. |
| Long-tail выразительности (степень, тернарник, срезы, литералы Записи, hex/binary, …) | Эргономика языка; ядро формул/логики покрыто v1. Берётся точечно по запросу, не трек. |
| REPL, `тип(x)` | Дешёвые дополнительные возможности; могут идти отдельным некритичным треком, не блокируют v2. |
| `ДатаВремя`/таймзоны, почасовые окна метрик | Бизнес-учёт идёт по дням; редко нужно. |

## 4. Очередь вех (топологически отсортирована)

Конвейер = поезда вех. **Внутри вехи** фичи катятся автономно (паттерн §6). **На стыке вех** —
архитектурный гейт (дрейф-аудит + срез сценария). Порядок разрезает жёсткие зависимости.

| Веха | Фичи (каждая = 1 автономный прогон) | Гейт-критерий выхода |
|---|---|---|
| **M0 Хартия** *(этот документ)* | — | Хартия согласована владельцем — **✓ DONE** |
| **M1 Аналитика** | **A1** коннекторы источника: `тип:` (json/csv/ndjson) + объявление и валидация схемы `поля:` → **A2** ряды и окна метрик: период `последние N <ед>`, ряд значений, «последний завершённый период» | Метрика `выручка_30д` считается на реальном CSV-источнике; срез сценария до триггера зелёный — **✓ DONE** (specs 010–011) |
| **M-DX Диагностика** *(после M1)* | **DX1** восстановление парсера: подавление каскада фантомных диагностик на одной/смежной строке (§12 гр.4, трогает горячий инвариант panic-mode) → **DX2** качество сообщений: каталог ошибок, бизнес-понятные формулировки, расширенная `examples/ошибочная.ladix`; где дёшево — подсказки «возможно, вы имели в виду…» | Ошибочная версия программы сценария даёт чистые бизнес-понятные диагностики без каскада; каталог ошибок полон — **✓ DONE** (spec 012) |
| **M2 Автоматизация** | **B1** захват результата `вызвать` *(развилка §8)* — **первой**, гейтит интеграции → **B2** реальные `вызвать`/`уведомить` (реализация `ProcessRuntime.CallExternal`/`Notify`) → **B3** payload в `ladix complete` → **B4** эскалация дедлайна (новый вид триггера + сканер просроченных задач) → **B5** `ladix start <процесс> [аргументы]` → **B6** инспекция инстанса: `ladix inspect <id>` (статус/шаг/переменные/срок/история) на базе существующих `InstanceStatus`/`InstanceVariables` | Сценарий проходит end-to-end (файловый источник, реальный канал уведомления); оператор может инспектировать живой инстанс — **✓ DONE** (specs 013–018) |
| **M3 Надёжность/сеть** | **C1** хеш-версионирование определений + стабильные ключи триггеров → **C2** миграции схемы Store + outbox/exactly-once → **C3** *(развилка §8)* серверная модель: демон-владелец-БД + HTTP-приём событий + `--json` → **C4** монотонные часы / `WithClock` → **C5** трассировка/объяснение: trace вычисления метрики (строки/фильтр/агрегат/окно), объяснимость срабатывания триггера (снимок значение↔порог), durable журнал-аудит (пара к C2-outbox), `--json`-вывод (пара к C3) | Сценарий переживает рестарт демона с живым инстансом; реальный эффект доставлен exactly-once; наблюдаемость полна (inspect + explain + trace) → **v2 DONE** — **✓ DONE** (specs 019–022; C1 хеш-версионирование/стабильные ключи + C3 HTTP-приём/`--json` осознанно в бэклоге, §C-9) |

**Жёсткие зависимости (соблюдены порядком):** `B1` (захват результата) — до `B2` (интеграций),
иначе их переписывать; `B3` (payload) — до сценарного потребления человеческого ввода;
версионирование/миграции (`C1`/`C2`) активируются именно тогда, когда эффекты стали реальными
(`B2`), не раньше. Реестр ролей (`Роль`) подключается в M2, **только если** эскалация «руководителю»
упрётся в отсутствие ролей; иначе остаётся в backlog.

**M-DX и наблюдаемость.** M-DX размещена после M1 — покрывает самый объёмный новый авторинг-синтаксис
(схема `поля:`, окна метрик) плюс всю базу v1, которой авторы пользуются с первого дня. Поверх неё
действует сквозное правило (§7.6): новые конструкции M2 (например, триггер эскалации) поставляют
чистые диагностики сразу, без отдельного второго прохода. Наблюдаемость поставляется инкрементально —
минимальная инспекция (`B6`, M2, как только процессы стали реальными) и полная трассировка/аудит
(`C5`, M3, где есть durable-журнал и `--json`), — но имеет единый DoD (§2).

## 5. Несущие инварианты (цели drift-watch)

На каждом гейте дрейф-аудит проверяет, что **эти швы не сломаны** (а не только что фича совпала
со своим анкором). Они — фундамент модульного бэкенда (план «заменить движок на Camunda/Kestra,
сохранив синтаксис»).

### Инвариант 1 — граница `eval↔engine` минимальна и стабильна

Цикл разорван интерфейсом `ProcessRuntime`, объявленным в `eval`, реализованным в `engine`,
инжектируемым сеттером. `eval` НЕ импортирует `store`/`engine`. Текущая поверхность (8 методов):

```go
type ProcessRuntime interface {
    StartProcess(name string, args []value.Value) (string, error)
    AssignProcessVar(name string, v value.Value) error
    CallExternal(target string, args []value.Value) error
    CallExternalResult(target string, args []value.Value) (value.Value, error)
    Notify(target string, args []value.Value) error
    InstanceStatus(id string) (status string, ok bool, err error)
    InstanceVariables(id string) (vars value.Запись, ok bool, err error)
    UserTasks(assignee string) ([]value.Запись, error)
}
```

`CallExternalResult` (B1/§AU-3) добавлен в M2 как выражение-форма внешнего вызова (захват
результата `вызвать` webhook'а); базовые сигнатуры не тронуты — чистое аддитивное расширение.

Экспорт `eval` (стабильный): `SetProcessRuntime`, `Process`, `GlobalEnv`, `EvalExpr`,
`ExecStepBody`, плюс `Analyze`/`Run`/`EvalMetricByName`/`EvalMetricCondition`/`RunTriggers`/
`ResetRunState`. **Правило v2:** расширения добавляются НОВЫМИ методами интерфейса; существующие
сигнатуры и однонаправленность ребра `engine→eval` не меняются.

### Инвариант 2 — контракт Store аддитивен и Value-ориентирован

Store оперирует Go-структурами с `map[string]value.Value`; сериализация (type-tagged JSON) —
исключительно внутреннее дело `SQLiteStore`. Контракт уже доказал аддитивность (8 методов 006 →
+6 триггерных 007 → +1 `ListInstancesByStatus` (рестарт-скан) → M2: +1 `ListTasksByInstance` →
M3: +2 `LoadOutbox`/`SaveOutbox` (outbox exactly-once) = 18, без поломки базовых). **Правило v2:** новые потребности
персиста (payload, хеш определения, outbox, миграции) — НОВЫЕ методы; реализация изолирована,
движок про JSON/SQL не знает. Транзакционного комбо «завершить+продвинуть» намеренно нет —
корректность через идемпотентный догон (D-4).

### Инвариант 3 — фронтенд изолирован от бэкенда

Лексер/парсер/AST/семантика/интерпретатор выражений не зависят от движка/Store. Любая v2-фича,
трогающая рантайм, **не трогает** фронтенд — синтаксис v1-программ остаётся валидным.

> **Единственное исключение из «чистой аддитивности».** Веха M-DX (`DX1`) *модифицирует*, а не
> расширяет, поведение panic-mode восстановления парсера (инвариант FR-025 «подавление каскада»).
> Это единственный v2-пункт, меняющий горячий фронтенд-инвариант, → несёт риск регресса диагностик.
> Митигируется инверсией тест-замков (golden-каталог ошибок ломается при любом сдвиге формулировок)
> и узким скоупом DX1 (только same-line-каскад). Риск M, не XL; намного ниже исключённого `параллельно`.

## 6. Механика автономного прогона (паттерн 009)

Каждая фича внутри вехи — один автономный SpecKit-прогон:

```
Фаза 0   self-анкор от хартии вехи + decision-pack (предрешает вопросы скиллов)
Фазы 1–6 SpecKit: specify → plan → tasks → analyze, на каждой — дрейф-рой против анкора
         (tasks — усиленный контроль: проверка инверсии тест-замков)
Фаза 7   implement-рой по фазам (worktree + барьерный гейт)
Фаза 8   self-check: мутпробы, чистый клон, гейты go build/vet/test
Фаза 9   мерж --no-ff / пуш (или стоп-на-ветке)
Фаза 10  хендофф (7 разделов)
```

- *Выход вехи (гейт):* дрейф-аудит против инвариантов §5 + проверка, что срез сценария зелёный.

## 7. Правила управления

1. **DoD** — золотой сценарий §2 зелёный end-to-end, переживает рестарт демона. На гейте вехи —
   его срез; на финале M3 — целиком. Это терминальное условие конвейера (замена внешнего критерия приёмки).
2. **Топо-сорт зафиксирован** — M1 → M2 → M3; внутри M2 `B1` первой; `параллельно` вне очереди.
   Аддитивные снятия не наступают на ещё-не-снятые.
3. **Drift-watch против швов** — на каждом гейте аудит против инвариантов §5 (`ProcessRuntime`,
   контракт Store, изоляция фронтенда), а не только против анкора фичи. Ловит накопленный дрейф
   до того, как он зацементируется через несколько автономных фич.
4. **Версионирование (M3, факт-итог)** — после того как стабы стали реальными эффектами (`B2`),
   в M3 отгружены: миграции схемы Store (forward-only, `PRAGMA user_version`) и единые часы CLI
   (`WithClock`, C4). Осознанно осталось в бэклоге (§C-9, НЕ реализовано): хеш-версионирование
   определений в инстансе (C1) и стабильные ключи триггеров (хеш текста вместо `trg-<N>`).
   До хеш-версионирования честный at-least-once допустим (эффекты-стабы идемпотентны;
   exactly-once реального эффекта обеспечивает outbox C2).
5. **Гигиена коммитов** — фича на своей ветке; чистое дерево перед стадией; леджер в `.gitignore`;
   мерж `--no-ff`; запрет `git add .` в копии, общей с архитектором (риск подхвата чужих/мусорных
   правок); перед каждым гейтом — `git status` + `git show --stat` чисто.
6. **Диагностика и наблюдаемость не отстают от поверхности** — каждая фича, добавляющая синтаксис,
   поставляет для своих конструкций чистые диагностики (номер строки, без каскада, бизнес-понятная
   формулировка); каждая фича, добавляющая рантайм-решение (срабатывание триггера, вычисление
   метрики, переход инстанса), делает его инспектируемым. Сквозное правило поверх выделенных вех
   M-DX/`C5` — чтобы качество не накапливало долг между ними.

## 8. Отложенные развилки (решаются на входе соответствующей вехи)

| Развилка | Где решается | Варианты |
|---|---|---|
| **Захват результата `вызвать`** | Вход M2 (фича B1) | (а) магическое имя `результат` после вызова; (б) сделать `вызвать` выражением. Влияет на грамматику шага. |
| **Серверная модель** | Вход M3 (фича C3) | (а) остаёмся на CLI-над-общим-SQLite с аддитивными расширениями; (б) демон-владелец-БД + сетевой API (HTTP-события, `--json`, push-пробуждение вместо `ladix complete`-над-SQLite). M1/M2 идут на (а), поэтому развилка не блокирует старт. |
| **Реестр ролей / тип `Роль`** | Вход M2 | Берём только если сценарий §2 упрётся в эскалацию «руководителю» без разграничения; иначе backlog. |
| **Двойные часы** (`eval.Clock` дневной vs `engine.Clock` wall-clock) | Вход M3 (C4) — **✓ РЕШЕНО** | Латентный гэп закрыт в C4 (`merge 40583f6`, `clock_adapter.go`): единые инжектируемые часы CLI через `WithClock` устранили недетерминизм метрики, стартующей процесс с шагом-`срок`. |
| **Тон и каталог диагностик** | Вход M-DX (DX2) | Коды ошибок + текст vs только текст; регистр/тон формулировок для русскоязычной бизнес-аудитории; объём подсказок «возможно, вы имели в виду…». |
| **Формат наблюдаемости** | Вход M3 (C5) | Человекочитаемый `inspect`/`explain` vs машинный `--json`; durable-аудит отдельной таблицей Store vs переиспользование outbox-журнала (C2). |
