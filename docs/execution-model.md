# Модель исполнения процессов и триггеров

> Детальная **механика** исполнения процессов Ladix: структуры данных, интерфейс `Store`,
> жизненный цикл с точками персиста, драйвер исполнения, конкурентность, восстановление и
> планировщик триггеров. Семантику процессов и триггеров (*что* делает шаг/триггер) см. в
> **SPEC §11**; типы значений Ladix — **SPEC §4**; область видимости и `присвоить` — **SPEC §6**;
> управляющие конструкции — **SPEC §7**; источники — **SPEC §9**; метрики — **SPEC §10**;
> стандартная библиотека (функции домена) — **docs/stdlib.md**; CLI-команды — **README, раздел
> CLI**; типы Go-ошибок и раскладка пакетов — **ARCHITECTURE.md**; ревизии решений 006 и
> exact-match реестры stdout/диагностик — **docs/engine-model.md** (связывающий якорь фичи 006).
>
> **Реализация разнесена по фичам:** **006** — EM-1..EM-16 (процессная часть; канон ревизий —
> docs/engine-model.md §EN-0..§EN-10), **007** — EM-17 целиком + триггерные методы `Store` (EM-5)

>
> **Нумерация в этом документе локальная.** Заголовки `EM-1 … EM-17` принадлежат только этому
> файлу; внутренние ссылки даются как «EM-N». Любая ссылка вида «SPEC §11.x» указывает на
> спецификацию языка, а не на разделы этого документа.

## EM-1. Обзор: движок как библиотека над `Store`

Движок процессов — **обычный Go-пакет** (`internal/engine`), работающий поверх интерфейса `Store`.
Он не сетевой сервис и не глобальный синглтон (без глобального состояния). Это позволяет встраивать
один и тот же движок в разные процессы ОС:

| Сценарий запуска | `Store` | Кто двигает инстанс |
|---|---|---|
| `ladix run file.ladix` | `MemoryStore` | один процесс: программа исполняется сверху вниз, `запустить процесс` синхронно доводит инстанс до первого ожидания/терминала и возвращает управление (SPEC §7.4 — неблокирующе). Незавершённые задачи видны в выводе по завершении `run`. |
| `ladix run file.ladix --db путь` | `SQLiteStore` | то же, но состояние персистентно (мост в SQLite, Q2): повторный `run --db` того же файла создаёт **новые** инстансы (id-счётчик персистентен, D-10) — норма v1. |
| `ladix complete <file.ladix> <task-id> [--db путь]` | `SQLiteStore` | короткоживущий процесс: строит Engine из файла (Q3 — истина в исходнике, БД хранит только состояние), грузит инстанс, помечает задачу готовой, **сам** прогоняет движок до следующего ожидания/терминала, персистит, выходит. |
| `ladix tasks [исполнитель] [--db путь]` | `SQLiteStore` | не двигает: читает открытые задачи из БД (файл не принимает, Q3). |
| `ladix serve` (фича 007) | `SQLiteStore` | демон: планировщик триггеров (EM-17) запускает процессы; каждый синхронно доходит до первого ожидания внутри демона. Человеческие шаги завершаются отдельными процессами `ladix complete`. |
| `ladix emit <E> [json]` (фича 007) | `SQLiteStore` | короткоживущий процесс: пишет внешнее событие (имя + JSON-payload) в очередь `events` и выходит; демон `serve` разбирает на тике (EM-17.3). Источник для `когда событие`. |

**Ключевая идея:** «продвинуть процесс» — это синхронный вызов движка в том процессе ОС, который
инициировал событие (CLI-команда или тик демона). Сетевого слоя и обязательного демона для потока
«человек-в-цикле» нет. Демон (`serve`, фича 007) нужен только под триггеры по времени/метрикам.

> Команды CLI (`run`/`complete`/`tasks` — 006; `serve`/`emit` и флаг `--interval` — фича 007;
> `repl` — вне 006) и их флаги — **README, раздел CLI**; алгоритмы команд 006 по шагам — **§EN-6**.
> CLI-команда `start` в v1 **выкинута**: процесс запускается вызовом `запустить процесс` внутри
> программы (`run`) или триггером (`serve`, фича 007). Не путать с экспортируемым **методом**
> движка `Engine.Start` (EM-9) — это внутренний API, не команда.

## EM-2. `ProcessInstance`

```go
type Status string

const (
    StatusCreated   Status = "создан"      // персистирован, первый шаг ещё не активирован (транзиентно)
    StatusRunning   Status = "выполняется" // активный шаг исполняет тело
    StatusWaiting   Status = "ожидает"     // активный шаг создал Task, инстанс спит
    StatusDone      Status = "выполнен"    // все шаги готовы (терминал)
    StatusFailed    Status = "провален"    // runtime-ошибка шага/атрибута (терминал)
    StatusCancelled Status = "отменён"     // зарезервирован; в v1 недостижим (SPEC §12)
)

type ProcessInstance struct {
    ID          string                 // "p-NNNNNN" (D-10)
    ProcessName string                 // имя ProcessDecl
    Status      Status
    CurrentStep string                 // имя активного шага; при терминале — последний обработанный
    Variables   map[string]value.Value // переменные процесса; пусть-локали шага сюда НЕ попадают
    CreatedAt   time.Time              // engine-Clock (D-2)
    UpdatedAt   time.Time              // выставляет движок перед КАЖДЫМ SaveInstance
}
```

Статусы инстанса по-русски: `создан` / `выполняется` / `ожидает` / `выполнен` / `провален`;
`отменён` зарезервирован и в v1 недостижим (SPEC §12). Go-идентификаторы (`StatusCreated` и т.д.)
оставлены как есть.

- **`CurrentStep` — один указатель.** Параллельности нет (SPEC §11), активен ровно один шаг,
  исполнение строго по исходнику ⇒ «завершённые шаги» = все объявленные до `CurrentStep`.
  Множество-completed и DAG из `после` в исполнении v1 не нужны (`после` — только валидатор,
  SPEC §11). Движок резолвит имя→позицию по определению процесса.
- **`Variables`** — карта имя→значение. Параметры процесса кладутся сюда при создании как
  начальные переменные (SPEC §6, SPEC §11). `пусть`-локальные шага сюда **не** попадают (живут
  только в кадре исполнения шага, §EN-4).
- **`value.Value`** — Go-интерфейс, представляющий любое из 10 значений Ladix (SPEC §4). Движок и
  `Store` оперируют `value.Value`, не зная о формате хранения (см. EM-4).
- **`UpdatedAt` выставляет движок** перед **каждым** `SaveInstance` (`clock.Now()`, engine-Clock —
  D-2); реализации `Store` это поле не трогают.

## EM-3. `Task`

```go
type TaskStatus string

const (
    TaskPending   TaskStatus = "открыта"
    TaskCompleted TaskStatus = "завершена"
)

type Task struct {
    ID          string     // "t-NNNNNN" (D-10)
    InstanceID  string     // → ProcessInstance.ID
    StepName    string     // шаг, породивший задачу
    Assignee    string     // значение «исполнитель» (Строка, D-18)
    Deadline    *time.Time // CreatedAt + «срок» (D-19); nil, если «срок» не задан
    Status      TaskStatus
    CreatedAt   time.Time
    CompletedAt *time.Time // nil, пока открыта; выставляет MarkTaskCompleted (D-12)
}
```

- **Нет входного payload (v1).** Завершая задачу, человек не передаёт данные в процесс (SPEC §12).
  Канал данных между шагами — только переменные процесса.
- **`Deadline` — `time.Time` (полная точность), внутренний.** «Срок» (`Длительность`) прибавляется
  к моменту создания (единицы → Go-время фиксированными множителями, `мес` — календарно; D-19).
  **Просрочка вычисляется движком** (`clock.Now().After(*Deadline)`, engine-Clock — D-2), не
  Ladix-кодом: `сейчас()`/`ДатаВремя` в v1 нет (SPEC §12). Наружу (в Ladix) дедлайн как значение
  **не** экспонируется; экспонируется производное `просрочена: Булево` (см. EM-13). Точный дедлайн
  печатает только CLI-поверхность (строки задач `tasks` и сводки `run` — единый формат
  `FormatTaskLine`, D-22, §EN-7 строка 6); в язык Ladix дедлайн не течёт.
- **`TaskStatus`** — строки `открыта`/`завершена` (внутренние для `Task`, не путать со статусами
  инстанса EM-2).

## EM-4. Значения процесса и сериализация

Переменные процесса динамические (10 типов SPEC §4). Для `SQLiteStore` нужен формат хранения; выбран
**type-tagged JSON** — человекочитаемый (БД демона можно инспектировать), языконезависимый,
кругооборотит все типы.

| Тип Ladix | JSON-кодировка |
|---|---|
| Целое | `{"т":"Целое","зн":42}` |
| Дробное | `{"т":"Дробное","зн":3.14}`; **спецзначения — строки**: `"NaN"`, `"+Inf"`, `"-Inf"` (D-5) |
| Строка | `{"т":"Строка","зн":"привет"}` |
| Булево | `{"т":"Булево","зн":true}` |
| Пусто | `{"т":"Пусто","зн":null}` |
| Длительность | `{"т":"Длительность","зн":{"значение":5,"единица":"мин"}}` (пара значение+единица; единица обязательна — `1час ≠ 60мин`, а `мес` к секундам не сводится, SPEC §4) |
| Период | `{"т":"Период","зн":"ежемесячно"}` |
| Дата | `{"т":"Дата","зн":"2026-05-31"}` (ISO `YYYY-MM-DD`) |
| Список | `{"т":"Список","зн":[ <рекурсивно>, … ]}` |
| Запись | `{"т":"Запись","зн":[["ключ", <значение>], …]}` — **массив пар**, порядок `Keys()` (D-6) |

Запись кодируется массивом пар, а не плоским JSON-объектом: порядок ключей `value.Запись.Keys()`
обязан пережить round-trip (D-6). Верхний уровень (`Variables` инстанса — Go-map) кодируется
JSON-объектом с **ключами по возрастанию** (детерминизм, D-21).

**Граница абстракции:** type-tagged JSON — это **внутреннее дело `SQLiteStore`**. Интерфейс `Store`
(EM-5) принимает и отдаёт Go-структуры с `map[string]value.Value`; `MemoryStore` хранит `Value`
нативно, без всякого JSON. Движок про JSON/SQL не знает вообще — поэтому встроенный бэкенд позже
заменяется на Camunda/Kestra без правки движка.

## EM-5. Интерфейс `Store`

Контракт 006 нарезан (D-3): ровно 8 методов, канон — §EN-2 (дословно совпадает):

```go
type Store interface {
    SaveInstance(inst *ProcessInstance) error            // upsert: создание и обновление
    LoadInstance(id string) (*ProcessInstance, error)    // не найден → ErrInstanceNotFound

    SaveTask(t *Task) error
    LoadTask(id string) (*Task, error)                   // не найдена → ErrTaskNotFound
    ListPendingTasks(assignee string) ([]*Task, error)   // assignee=="" → все открытые; порядок — по возрастанию ID (D-15)
    MarkTaskCompleted(id string, completedAt time.Time) error // атомарно открыта→завершена (D-12); повтор → ErrTaskAlreadyCompleted

    NextInstanceID() (string, error)                     // mint "p-NNNNNN" (D-10)
    NextTaskID() (string, error)                         // mint "t-NNNNNN"
}

var (
    ErrInstanceNotFound     = errors.New("process instance not found")
    ErrTaskNotFound         = errors.New("task not found")
    ErrTaskAlreadyCompleted = errors.New("task already completed")
)
```

**Добавит фича 007 (триггеры и события, аддитивно):** методы `LoadTriggerState` /
`SaveTriggerState` / `NextEventID` / `EnqueueEvent` / `ListUnprocessedEvents` /
`MarkEventProcessed` и сентинел `ErrTriggerStateNotFound` — существующие 8 методов не меняются.
Их структуры `TriggerState`/`Event` определены в EM-17.2/EM-17.3; `MemoryStore` будет хранить их
эфемерно (в рамках одного `run`, EM-17.8), `SQLiteStore` — в таблицах `trigger_state`/`events`.
В 006 ничего из этого **не объявляется** (D-3).

- **Почему интерфейс, а не структура** — движок зависит только от контракта; `MemoryStore`
  (тесты/`run` без `--db`, миллисекунды) и `SQLiteStore` (`run --db`/`complete`/`tasks`; с 007 —
  `serve`) взаимозаменяемы; путь к Camunda/Kestra открыт.
- **`SaveInstance` — upsert.** Один метод на создание и обновление: движок не различает
  «вставить/обновить», это забота реализации (`INSERT … ON CONFLICT` в SQLite, перезапись в карте
  в Memory). Коллизии id исключены конструктивно персистентным счётчиком (D-10).
- **Сентинел-ошибки под `errors.Is`:** `LoadInstance` несуществующего id → `ErrInstanceNotFound`;
  вызывающий проверяет `errors.Is(err, ErrInstanceNotFound)`, а не сравнивает строки.
  `состояние_процесса(id)`/`статус_процесса(id)` так отличают «не найдено» от прочих ошибок (через
  `ProcessRuntime`, D-15) и дают Ladix-ошибку `процесс '<id>' не найден` (см. EM-13, §EN-8.A).
- **`MarkTaskCompleted` — атомарное завершение (D-12):** перевод `открыта`→`завершена` атомарен
  (SQLite: условный `UPDATE … WHERE status='открыта'` + проверка rows affected; Memory: под mutex);
  уже завершена → `ErrTaskAlreadyCompleted`. Проигравший гонку двух одновременных `complete`
  уходит в ветку догона D-4 (EM-9).
- **Id mint в Store** — `NextInstanceID`/`NextTaskID`: уникальность «в рамках Store» (SPEC §11)
  живёт в одном месте, счётчик **персистентный** (D-10): SQLite — таблица `counters` (EM-7),
  инкремент и выдача в одной транзакции; Memory — счётчик под mutex. Формат — EM-8.
- **Минимализм.** Транзакционного метода «завершить задачу + продвинуть инстанс атомарно» в
  интерфейсе нет намеренно — корректность при сбое между `MarkTaskCompleted` и продвижением
  инстанса обеспечивается идемпотентным гард-догоном в `complete` (D-4, EM-12), а не усложнением
  контракта. `SQLiteStore` волен внутри обернуть связанные записи в транзакцию.

## EM-6. `MemoryStore`

`internal/store/memory.go`. Карты `map[string]*ProcessInstance`/`map[string]*Task` + счётчики id —
всё под одним `sync.Mutex`. Никакой сериализации: `Value` лежат как есть. `MarkTaskCompleted` —
проверка статуса и перевод под тем же mutex (D-12). Назначение — `ladix run` без `--db` (одна
программа от старта до конца, эфемерно) и быстрые тесты lifecycle.

## EM-7. `SQLiteStore`

`internal/store/sqlite.go`, через `modernc.org/sqlite` (чистый Go, без CGO — кросс-компиляция одной
командой; **первая внешняя зависимость**, §EN-0). DDL (исполняется при открытии,
`CREATE TABLE IF NOT EXISTS`; дословно — §EN-2):

```sql
CREATE TABLE IF NOT EXISTS instances (
    id           TEXT PRIMARY KEY,
    process_name TEXT NOT NULL,
    status       TEXT NOT NULL,
    current_step TEXT NOT NULL,
    variables    TEXT NOT NULL,   -- type-tagged JSON (кодек ниже), ключи верхнего уровня по возрастанию (D-21)
    created_at   TEXT NOT NULL,   -- RFC3339 (time.RFC3339)
    updated_at   TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS tasks (
    id           TEXT PRIMARY KEY,
    instance_id  TEXT NOT NULL REFERENCES instances(id),
    step_name    TEXT NOT NULL,
    assignee     TEXT NOT NULL,
    deadline     TEXT,            -- RFC3339 (time.RFC3339) или NULL
    status       TEXT NOT NULL,
    created_at   TEXT NOT NULL,
    completed_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_tasks_pending ON tasks(assignee, status);
CREATE TABLE IF NOT EXISTS counters (
    name  TEXT PRIMARY KEY,       -- "instance" | "task"
    value INTEGER NOT NULL
);
INSERT OR IGNORE INTO counters(name, value) VALUES ('instance', 0), ('task', 0);
```

Сид `counters` исполняется вместе с `CREATE` при каждом открытии (без него `UPDATE` минта на
свежей БД обновил бы 0 строк). Mint id (D-10): `UPDATE`+чтение счётчика `counters` в одной
транзакции (сид гарантирует наличие строки); формат —
`fmt.Sprintf("p-%06d", n)` / `"t-%06d"` (EM-8). Таблицы `trigger_state`/`events` (EM-17.3) —
**фича 007**. Временные поля — строки `time.RFC3339`: `.Format(time.RFC3339)` на запись,
`time.Parse(time.RFC3339)` на чтение (секундная точность, НЕ `RFC3339Nano`; канон — §EN-2).

**WAL + busy_timeout (ключевое).** Несколько процессов ОС (короткоживущие
`ladix run --db`/`complete`/`tasks`; с 007 — демон `serve`) пишут в один файл. Стандартная
Go-практика без CGO:

```
PRAGMA journal_mode = WAL;     -- читатели не блокируют писателя, один писатель за раз
PRAGMA busy_timeout = 5000;    -- при занятой БД ждать до 5с, а не падать с SQLITE_BUSY
PRAGMA foreign_keys = ON;
```

WAL даёт «много читателей + один писатель»; `busy_timeout` сериализует редкие конкурентные записи без
явных блокировок в коде. В v1 этого достаточно (коллизии конкурентных `complete` — и, с 007, демона —
редки). Без CGO всё это — обычные `Exec`-вызовы при открытии соединения.

Путь к файлу БД — флаг `--db` команд `run`/`complete`/`tasks` (у `complete`/`tasks` дефолт
`ladix.db` в текущем каталоге; у `run` дефолта нет — без флага `run` работает на `MemoryStore`, Q2);
см. README, раздел CLI, и §EN-6.

## EM-8. Идентификаторы

- **Mint в `Store`**, непрозрачная строка, префикс типа: `p-…` (инстанс), `t-…` (задача).
  Пользователь формат не парсит (SPEC §11).
- **Схема (D-10):** префикс + **персистентный** монотонный счётчик Store, нуль-паддинг 6:
  `p-<NNNNNN>` / `t-<NNNNNN>` (например `p-000123`). SQLite — таблица `counters` (EM-7), инкремент
  и выдача в одной транзакции; Memory — счётчик под mutex. Случайный суффикс (`p-000123-a3f7`)
  **отменён** (D-10): уникальность в рамках Store гарантирует персистентный счётчик, «гигиена» в v1
  не нужна, а id остаются детерминированными/маскируемыми в golden-тестах (§EN-9).

## EM-9. Жизненный цикл: машина состояний и точки персиста

Формализация переходов SPEC §11 с отметками `SaveInstance` (▼ = персист). **Канон ревизии — §EN-3**
(псевдокод ниже совпадает дословно); перед каждым ▼ движок выставляет `UpdatedAt = clock.Now()`
(engine-Clock, D-2):

```
Start(P, args):                                  # реализация eval.ProcessRuntime.StartProcess; запуск ТИХИЙ (D-13)
    pd ← interp.Process(P)                       # гарантированно есть: семпроход резолвит имя (§PM-4)
    id ← st.NextInstanceID()
    inst ← {id, P, статус=создан, Variables=bind(pd.Params, args), CurrentStep=pd.Steps[0].Name, CreatedAt=clock.Now()}
    ▼ SaveInstance(inst)                         # «создан» (транзиентно)
    advance(inst)                                # синхронный прогон; ошибка → наверх (инстанс уже провален)
    return id

advance(inst):                                   # крутит шаги до ожидания/терминала
    processEnv ← кадр процесса (§EN-4)           # ОДИН на весь advance-прогон; stepEnv — свой на каждый шаг
    loop:
        шаг ← lookup(inst.ProcessName, inst.CurrentStep)   # по interp.Process; порядок = порядок исходника (§11.2)
        inst.статус = выполняется
        ▼ SaveInstance(inst)
        stepEnv ← NewEnvironment(processEnv)
        # (1) фаза атрибутов (D-9):
        assignee ← interp.EvalExpr(stepEnv, шаг.Assignee), обязан Строка (D-18)     # если атрибут есть
        срок     ← interp.EvalExpr(stepEnv, шаг.Deadline), обязан Длительность (D-18)
        # (2) тело:
        sig, err ← interp.ExecStepBody(processEnv, stepEnv, шаг.Body)   # каждое «присвоить» внутри ▼ персистит (хук §EN-4)
        если ошибка атрибута или err:
            inst.статус = провален
            ▼ SaveInstance(inst)
            return err                           # D-14: всплывает канон §13, exit 1
        # (3) развилка:
        если assignee задан:                     # человеческий шаг → заснуть
            t ← {st.NextTaskID(), inst.ID, шаг.Name, assignee, Deadline=CreatedAt+срок (D-19), CreatedAt=clock.Now()}
            ▼ SaveTask(t); печать строки создания Task (§EN-7, строки 3/4)
            inst.статус = ожидает
            ▼ SaveInstance(inst); return         # засыпание (EM-10)
        next ← следующий шаг по исходнику
        если next == ∅:
            inst.статус = выполнен
            ▼ SaveInstance(inst); return         # терминал; печати нет (тихо)
        inst.CurrentStep = next

Complete(taskID):                                # для CLI complete; синхронно
    t ← st.LoadTask(taskID)                      # ErrTaskNotFound → CLI exit 2
    inst ← st.LoadInstance(t.InstanceID)         # ErrInstanceNotFound → CLI exit 2
    # дрейф-гарды Q3 (до любых мутаций):
    pd ← interp.Process(inst.ProcessName)        # нет → «процесс … не найден в определении», exit 2
    CurrentStep ∈ pd.Steps?                      # нет → «шаг … не найден в определении …», exit 2
    если t.Status == завершена:                  # гард-догон D-4
        если inst.статус == ожидает И inst.CurrentStep == t.StepName:
            → печать строки 8 (§EN-7) ВМЕСТО строки 7, далее до-продвижение как ниже
              (без MarkTaskCompleted), CaughtUp=true, exit 0
        иначе → «задача '<id>' уже завершена», exit 2
    # гарды D-8 (открытая задача):
    если inst.статус != ожидает → «инстанс … не ожидает (статус …)», exit 2
    если inst.CurrentStep != t.StepName → «задача … не соответствует текущему шагу …», exit 2
    err ← st.MarkTaskCompleted(taskID, clock.Now())
    если errors.Is(err, ErrTaskAlreadyCompleted):           # проигравший гонку D-12
        перечитать inst; → ветка догона D-4 (выше)
    печать «задача <id> завершена» (§EN-7, строка 7)        # ДО advance: задача уже завершена фактом
    next ← следующий шаг по исходнику
    если next == ∅: inst.статус = выполнен; ▼ SaveInstance(inst)
    иначе: inst.CurrentStep = next; err ← advance(inst)      # может снова заснуть или провалиться
    если err: return err                                     # exit 1 (D-14); итоговой строки НЕТ
    печать итоговой строки инстанса (§EN-7, строки 9/10)
```

Ключевые ревизии против исходного эскиза: **фаза атрибутов — до тела** (D-9, SPEC §11.3; ошибка
атрибута = ошибка шага → `провален`); **гарды `complete`** (D-8: статус `ожидает` + совпадение
шага); **гард-догон** уже-завершённой задачи (D-4: хвост сбоя → идемпотентное до-продвижение,
exit 0); **`complete` строит Engine из файла** (Q3: `ladix complete <file.ladix> <task-id>`,
дрейф исходника против БД → exit 2, инстанс не тронут). Нарушение гардов → CLI-ошибка с **кодом
возврата 2**; тексты — exact-match реестр **§EN-8.B** (сводка — EM-16). Коды возврата CLI см.
README, раздел CLI, и §EN-6.

**Гранулярность персиста.** `SaveInstance` зовётся на: создание, каждое `присвоить` (через хук
`AssignProcessVar`, §EN-4), каждую смену статуса/продвижение шага, терминал. Для SQLite каждая —
мелкая запись (WAL это тянет). `присвоить` в цикле `пока` ⇒ много записей: в v1 принимаем ради
корректности «значение всегда в Store»; батчинг/дебаунс — оптимизация v2.

## EM-10. Драйвер исполнения и пробуждение

- **Засыпание** — это `return` из `advance` в статусе `ожидает` с персистированным инстансом.
  Никаких висящих горутин/таймеров на время ожидания человека: всё состояние в `Store`. Инстанс
  переживает рестарт демона.
- **Пробуждение** — внешнее событие `ladix complete <file.ladix> <task-id>` в отдельном процессе
  ОС: строит Engine из файла (Q3), грузит инстанс из `Store`, помечает задачу
  (`MarkTaskCompleted`, D-12), синхронно зовёт `advance` от следующего шага, персистит, выходит.
  Демону (фича 007) ничего сообщать не нужно — истина в SQLite; на своём следующем тике он видит
  актуальное состояние.
- **Встраиваемость.** `Start`/`Complete` — экспортируемые методы пакета `engine`, `advance` — его
  внутренний цикл (сигнатуры — §EN-3; метод `Start` не путать с выкинутой CLI-командой `start`,
  EM-1); переиспользуются и в CLI-командах, и в `serve` (фича 007). Это прямое следствие «движок —
  библиотека, не сервис».

## EM-11. Конкурентность

- **`ladix run`** (с `--db` и без) — один процесс ОС, всё синхронно в одной горутине: гонок нет.
- **`run --db` / `complete` / `tasks`** (с 007 — и демон `serve`) — разные процессы ОС над одним
  SQLite-файлом. Сериализацию записей обеспечивает WAL+`busy_timeout` (EM-7), а не блокировки в
  коде Ladix. Два одновременных `complete` одной задачи разводит атомарный `MarkTaskCompleted`
  (D-12): выигравший продвигает, проигравший уходит в догон D-4 — остаточная гонка «двойного
  advance» задокументирована как граница v1 (§EN-10).
- **Внутри демона (фича 007)** планировщик (EM-17) — горутина с `time.Ticker`; её работа
  (переоценить триггеры, запустить процессы) и любые встроенные вызовы движка сериализуются
  `sync.Mutex` вокруг прогона движка, чтобы два тика не лезли в один инстанс. Грациозная остановка
  демона — `context.Context`: тикер слушает `ctx.Done()` и выходит, не оставляя утечки горутины
  (детали тикера — EM-17.1).

## EM-12. Восстановление после сбоя

- **Персист на границах шага.** `присвоить` коммитит переменную процесса сразу (SPEC §6); локальные
  `пусть` шага не персистируются — при падении посреди шага теряется только незакоммиченный кадр
  шага, переменные процесса целы.
- **Рестарт-скан — фича 007.** Инстансы в `ожидает` корректны (проснутся по `complete`). Инстанс,
  застрявший в `выполняется`/`создан` (падение посреди шага), в 006 остаётся **залипшим** — носитель
  рестарт-скана, переактивирующего его с `CurrentStep` (`advance` прогоняет шаг заново), — демон
  фичи 007 (D-4, граница §EN-10).
- **At-least-once, честно.** Повторный прогон шага (догон D-4, будущий рестарт-скан) может повторить
  побочные эффекты **и мутации переменных процесса** (`присвоить x = x + 1` исполнится дважды,
  D-11): шаги пишутся идемпотентно по переменным — ответственность автора программы, граница v1
  (§EN-10). В v1 `вызвать`/`уведомить` — стабы-логи, их повтор безвреден. Для реальных систем (v2)
  это **at-least-once**; exactly-once (журнал эффектов / транзакционные outbox) — v2. Документируем
  явно, а не прячем.
- **Сбой между `MarkTaskCompleted` и продвижением инстанса** (EM-9 `Complete`): закрывается
  **гард-догоном в `complete`** (D-4) — повторный `complete` уже-завершённой задачи видит «инстанс
  `ожидает` на её шаге», распознаёт хвост сбоя и до-продвигает идемпотентно (exit 0, §EN-7
  строка 8). Поэтому транзакционный комбо-метод в `Store` не обязателен (EM-5).

## EM-13. Отображение в стандартную библиотеку

Сигнатуры и полное описание функций домена — **docs/stdlib.md**. Реализация — в eval через
интерфейс **`ProcessRuntime`** (D-15, §EN-4): builtin зовёт метод инжектированного рантайма,
engine транслирует вызов к `Store`:

| Функция Ladix | `ProcessRuntime` → `Store` |
|---|---|
| `статус_процесса(id) → Строка` | `InstanceStatus(id)` → `LoadInstance(id).Status`; `ErrInstanceNotFound` → Ladix-ошибка `процесс '<id>' не найден` (§EN-8.A, позиция вызова). |
| `состояние_процесса(id) → Запись` | `InstanceVariables(id)` → `LoadInstance(id).Variables` → `Запись` (имя→значение), ключи **по возрастанию имени** (D-21). Не найдено → та же ошибка. |
| `задачи_пользователя(исполнитель) → Список` | `UserTasks(исполнитель)` → `ListPendingTasks(исполнитель)` → `[]*Task` → `Список` из `Запись` (ниже), **по возрастанию id** (D-15); `""` → все открытые. |

**`Task` → `Запись`** (поверхность, видимая Ladix-коду):

```
{
  ид:         Строка,   # Task.ID
  процесс:    Строка,   # Task.InstanceID
  шаг:        Строка,   # Task.StepName
  исполнитель: Строка,  # Task.Assignee
  статус:     Строка,   # "открыта" / "завершена"
  просрочена: Булево     # движок: clock.Now().After(Deadline) (engine-Clock, D-2); при nil-дедлайне — ложь
}
```

Сырой `Deadline` в `Запись` **не** входит (нет `ДатаВремя`, SPEC §12); точный дедлайн показывает
только CLI-поверхность (строки задач `tasks` и сводки `run`, единый формат `FormatTaskLine` —
D-22, §EN-7 строка 6) — в язык Ladix дедлайн не течёт. `просрочена` — производное от Go-времени,
единственный наблюдаемый Ladix-коду признак просрочки (вместо несуществующего `сейчас()`).

## EM-14. Go-идиомы (зачем именно так)

- **`Store` — интерфейс, движок — пакет без глобалов.** Тестируемость (Memory за миллисекунды),
  заменяемость бэкенда, отсутствие глобального состояния.
- **`errors.Is` + сентинелы** вместо сравнения строк ошибок — стандарт Go для «различить вид ошибки»
  (`ErrInstanceNotFound`/`ErrTaskNotFound`/`ErrTaskAlreadyCompleted`; с 007 —
  `ErrTriggerStateNotFound`).
- **`time.Time`/`time.Duration`** для моментов/дедлайнов: полная точность внутри, day-усечение только
  там, где Ladix реально не имеет `ДатаВремя`.
- **Clock-интерфейс + инъекция опцией `WithClock`** (D-2) — вместо рассыпанного `time.Now()`:
  `SystemClock` — единственная точка системного времени движка, тесты подменяют часы фиксированным
  моментом (байт-точные golden, §EN-9). Не путать с `eval.Clock` (дневной, `value.Дата` для метрик).
- **WAL + `busy_timeout`** — канонический способ дать `modernc.org/sqlite` многопроцессный доступ без
  CGO и без ручных блокировок.
- **`context.Context` + `ctx.Done()`** для остановки демона без утечки горутин (тикер — EM-17.1;
  фича 007).
- **`*time.Time` (указатель) для nullable-полей** (`Deadline`, `CompletedAt`): `nil` = «не задано»,
  идиоматичнее «нулевого времени».

## EM-15. Границы: что не покрыто (→ v2)

- **Сетевой/IPC-слой** — не в v1.
- **Батчинг персиста, инкрементальность, exactly-once эффектов, отзыв осиротевших задач,
  транзакционный outbox** → v2.
- **Точные поля для миграций схемы SQLite, версии БД** → деталь имплементации.

Границы именно фичи 006 (что и почему отложено в 007: рестарт-скан, триггеры, арифметика
Длительности и др.) — **§EN-0/§EN-10**.

## EM-16. Диагностики lifecycle

**Exact-match канон текстов 006 — §EN-8** (диагностики: §EN-8.A — ошибки программы,
§EN-8.B — CLI) и **§EN-7** (системный stdout движка); тесты сверяют байт-точно по якорю.
Здесь — сводка по случаям (тексты дословно совпадают с §EN-8).

Заголовок рантайм-ошибки домена — по канону SPEC §13: «Ошибка в строке N, колонка M:» (где есть
позиция вызова в исходнике, например встроенная функция `статус_процесса`). CLI-ошибки команд —
одна строка **`ladix: <текст>`** в stderr, exit 2 (D-20), без позиции в исходнике.

| Случай | Уровень | Сообщение |
|---|---|---|
| `статус_процесса`/`состояние_процесса` неизвестного id | Runtime (заголовок «Ошибка в строке N, колонка M:») | `процесс '<id>' не найден` |
| `ladix complete` неизвестного task-id | CLI Error (exit 2) | `ladix: задача '<id>' не найдена` |
| `ladix complete` уже завершённой задачи (догон D-4 неприменим) | CLI Error (exit 2) | `ladix: задача '<id>' уже завершена` |
| `ladix complete`: инстанс задачи не найден (`LoadInstance` → `ErrInstanceNotFound`, битая/чужая БД) | CLI Error (exit 2) | `ladix: инстанс '<id>' не найден` |
| Гард D-8: инстанс не в статусе `ожидает` | CLI Error (exit 2) | `ladix: инстанс '<p-id>' не ожидает (статус '<статус>')` |
| Гард D-8: задача не соответствует текущему шагу | CLI Error (exit 2) | `ladix: задача '<t-id>' не соответствует текущему шагу инстанса '<p-id>'` |
| Дрейф Q3: процесс инстанса не найден в файле | CLI Error (exit 2) | `ladix: процесс '<имя>' не найден в определении` |
| Дрейф Q3: шаг инстанса не найден в определении | CLI Error (exit 2) | `ladix: шаг '<имя>' не найден в определении процесса '<имя>'` |

| Runtime-ошибка тела/атрибута шага (провал, D-14) | Runtime (канон §13, exit 1) | исходная ошибка **без добавочного текста**; в `Store` инстанс — `провален` |
| Сбой записи в `Store` из хука `присвоить`/запуска | Runtime | `сбой хранилища: <причина>` (обёртка `fmt.Errorf("...: %w", err)`, §EN-8.A) |
| Не-сентинельная ошибка `Store` на CLI-путях `complete`/`tasks` (включая ▼ `advance` из `Complete` и декод кодека битой БД) | CLI Error (exit 2) | `ladix: сбой хранилища: <причина>` (§EN-8.B, §EN-3) |

Успешный **гард-догон D-4** — не ошибка: exit 0 и строка
`задача <t-id> уже была завершена, инстанс до-продвинут` в stdout (§EN-7, строка 8).

## EM-17. Планировщик триггеров (фича 007)

> **Весь раздел EM-17 — фича 007, в 006 не реализуется** (§EN-0): ни `serve`/`emit`/`--interval`,
> ни триггерные методы `Store` (EM-5) с таблицами `trigger_state`/`events`, ни
> fire-if-true-проход в `run` (EM-17.8), ни фронтенд `когда`. Раздел сохранён как проектная
> база 007 и при её kickoff может быть ревизован.

Планировщик — часть демона `serve` (EM-1). Он реализует семантику триггеров **SPEC §11**: переход
метрик `ложь→истина`, доставку событий, расписание.

### EM-17.1. Обзор: что делает тик

Тикер (EM-11) на каждом тике вызывает `d.tick()`. Один тик — **последовательный** проход в
детерминированном порядке:

```
tick():
  1. drainEvents()       # разобрать накопленную очередь events (EM-17.3)
  2. evalMetrics()       # переоценить все метрика-триггеры, детект перехода (EM-17.2)
  3. checkSchedules()    # проверить все расписание-триггеры (EM-17.4)
```

Каждый сработавший триггер исполняет своё тело (EM-17.5). Триггеры одного вида обрабатываются в
**порядке объявления в исходнике** (детерминизм, SPEC §11). Сбой одного триггера изолирован
(EM-17.6) и не мешает остальным.

Базовый интервал тикера — флаг CLI `--interval` (дефолт `1m`, формат `time.ParseDuration`); см.
README, раздел CLI. Разрешение тика ≥ разрешения `в "ЧЧ:ММ"` (минуты) достаточно: `расписание в
"14:30"` сработает в пределах одного интервала. Грациозная остановка — `ctx.Done()` (EM-11).

### EM-17.2. Состояние перехода (`trigger_state`)

Чтобы поймать переход `ложь→истина` (метрика) и каденс (расписание), демон помнит состояние **между
тиками и между рестартами**: оно персистится в `Store`, симметрично остальному durable-состоянию.

```go
type TriggerState struct {
    TriggerID     string     // стабильный ключ триггера (EM-17.2.1)
    Kind          string     // "metric" | "schedule_every" | "schedule_at"
    LastBool      *bool      // metric: базовая линия; nil = ещё не праймлен
    LastFire      *time.Time // schedule_every: момент последнего срабатывания
    LastFiredDate *string    // schedule_at: дата "YYYY-MM-DD" последнего срабатывания
}
```

**Прайм без срабатывания.** Для метрика-триггера: если `LoadTriggerState` вернул
`ErrTriggerStateNotFound` (первая оценка), демон вычисляет условие и **молча** записывает базовую
линию (`LastBool`), не исполняя тело — даже если условие уже истинно. Срабатывание возможно только со
следующей оценки, на фактическом переходе `ложь→истина`. Персист базовой линии означает, что после
рестарта прайм не повторяется (SPEC §11).

**Заморозка базы при невычислимом условии.** Если на оценке метрика `пусто` / сравнение не-`Булево`
(SPEC §10) — `LastBool` не перезаписывается (`SaveTriggerState` пропускается), тело не исполняется
(SPEC §11).

#### EM-17.2.1. Идентификатор триггера

Триггеры анонимны (нет имени в грамматике). Стабильный ключ — **порядковый индекс объявления** в
исходнике: `TriggerID = "trg-<N>"` (N — 0-based порядок среди всех `TriggerDecl`). Прост и стабилен,
пока исходник не редактируется между рестартами.

Граница (фиксируется в SPEC §12): правка исходника, сдвигающая порядок триггеров, «съезжает»
сохранённое состояние (старое `trg-2` теперь относится к другому триггеру). Для v1 приемлемо (рестарт
с тем же файлом — норма). Альтернатива «ключ = хеш текста условия» (устойчива к переупорядочиванию,
сбрасывает базу при правке условия) — v2.

### EM-17.3. Очередь событий (`events`)

`ladix emit <E> [json]` — короткоживущий процесс (как `complete`): пишет событие в очередь `events`
общего `Store` (`EnqueueEvent`) и выходит. Демон разбирает очередь на тике (`drainEvents`).

```go
type Event struct {
    ID          string    // opaque, "e-…"
    Name        string    // имя события
    PayloadJSON string    // сырой JSON payload (маппинг → Запись при обработке)
    CreatedAt   time.Time
    Processed   bool
}
```

`drainEvents`:

1. `ListUnprocessedEvents()` → события в порядке поступления (FIFO по `CreatedAt`/rowid).
2. Для каждого: найти событие-триггеры с `EventTrigger.Name == E`.
3. Распарсить `PayloadJSON` в `Запись` (маппинг JSON→типы как у источников, SPEC §9; доступ к полю
   толерантный, SPEC §6), привязать к предопределённой `событие`.
4. Исполнить тело каждого совпавшего триггера (EM-17.5).
5. `MarkEventProcessed(id)`.

Событие без обработчиков — помечается processed (отбрасывается), лог «событие E без триггеров».
**At-least-once** (симметрично EM-12): сбой демона между исполнением тела и `MarkEventProcessed` →
событие переобработается при следующем старте (повтор `запустить процесс` безвреден —
fire-and-forget). Exactly-once — v2.

Эскиз схемы SQLite (в дополнение к EM-7):

```sql
CREATE TABLE trigger_state (
    trigger_id      TEXT PRIMARY KEY,
    kind            TEXT NOT NULL,
    last_bool       INTEGER,        -- 0/1/NULL (NULL = не праймлен)
    last_fire       TEXT,           -- RFC3339 или NULL
    last_fired_date TEXT            -- "YYYY-MM-DD" или NULL
);
CREATE TABLE events (
    id           TEXT PRIMARY KEY,
    name         TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    created_at   TEXT NOT NULL,
    processed    INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_events_pending ON events(processed, created_at);
```

### EM-17.4. Расписание

Демон смотрит на Go-wall-clock **внутри** (деталь имплементации, наружу как значение Ladix не течёт —
SPEC §12).

**`каждые D`** (`schedule_every`):
- Якорь: при первой регистрации (`ErrTriggerStateNotFound`) `LastFire ← now` (момент старта), без
  срабатывания.
- На тике: если `now >= LastFire + D` → сработать, `LastFire ← now` (факт срабатывания, дрейф не
  копим: `next = факт + D`).
- `LastFire` персистится — после рестарта каденс продолжается с сохранённого якоря (не сбрасывается
  на старт).

**`в "ЧЧ:ММ"`** (`schedule_at`):
- На тике: пусть `today = now.date`, `target = now.date в ЧЧ:ММ`. Если `LastFiredDate != today` И
  `now >= target` → сработать, `LastFiredDate ← today`.
- Раз в сутки. Если демон стартовал после `ЧЧ:ММ` — сработает в день старта (условие выполнено, дата
  ещё не отмечена); далее — на следующих сутках.

### EM-17.5. Исполнение тела и `advance`

Сработавший триггер исполняет тело (`Block`) интерпретатором в scope тела триггера (SPEC §11):
предопределённые `значение`/`событие`, read-only глобалы/метрики, локальные `пусть`. `запустить
процесс P(...)` внутри → EM-9 (`NextInstanceID`, создать `ProcessInstance`, `advance` до
ожидания/терминала), fire-and-forget. Несколько `запустить процесс` в одном теле — последовательно.

### EM-17.6. Изоляция сбоев (`recover`)

Каждый триггер на тике обёрнут `recover` (см. EM-12): runtime-ошибка или паника в одном триггере
**логируется и не роняет демон** — остальные триггеры этого тика и последующие тики продолжают
работать. Базовая линия метрики уже обновлена до тела (SPEC §11), поэтому сбойный триггер не
зацикливается на повторном `ложь→истина`.

### EM-17.7. Конкурентность

- Тик **последовательный** — один поток исполнения движка в демоне (EM-11). Метрика-триггеры,
  расписание, события на одном тике не пересекаются по времени.
- `ladix emit` пишет в `events` из **другого** процесса ОС; демон читает на тике. Кросс-процессная
  синхронизация — WAL + `busy_timeout` (EM-7), как для `complete`. Гонок нет: SQLite сериализует
  запись.
- `trigger_state` читается/пишется **только** демоном (на тике) — внешние процессы его не трогают.

### EM-17.8. Режим `run`

`ladix run` (MemoryStore, без тикера) делает **один** оценочный проход метрика-триггеров после
загрузки источников: базовая линия = `ложь` ⇒ истинное условие срабатывает один раз
(`fire-if-true`). `trigger_state` — в памяти, эфемерно. Расписание/событие в `run` — **no-op** с
логом «требует serve». Это даёт демо «метрика < порог → запустить процесс» прямо в `run` (SPEC §11).

### EM-17.9. Стоимость переоценки

Каждый тик пересчитывает все метрика-триггеры → пересчитывает их метрики (SPEC §10 — чистый пересчёт
на чтение; источник кешируется на запуск, SPEC §9). В v1 приемлемо. Кеш/инвалидация значений метрик
между тиками — v2 (EM-17.10).

### EM-17.10. Что планировщик НЕ покрывает (→ v2)

- **Cron-выражения** и сложное расписание (`каждые`/`в` — единственные формы, SPEC §12).
- **Приём событий по сети** (HTTP-эндпоинт): источник событий в v1 — только `ladix emit` через общий
  SQLite (Design Y отвергнут, SPEC §12).
- **Exactly-once** доставки событий и эффектов триггеров (at-least-once, EM-17.3).
- **Кеш значений метрик** между тиками / инкрементальный пересчёт (EM-17.9).
- **Стабильный ключ триггера при правке исходника** (хеш условия вместо индекса, EM-17.2.1).
