# Модель исполнения процессов и триггеров

> Детальная **механика** исполнения процессов Ladix: структуры данных, интерфейс `Store`,
> жизненный цикл с точками персиста, драйвер исполнения, конкурентность, восстановление и
> планировщик триггеров. Семантику процессов и триггеров (*что* делает шаг/триггер) см. в
> **SPEC §11**; типы значений Ladix — **SPEC §4**; область видимости и `присвоить` — **SPEC §6**;
> управляющие конструкции — **SPEC §7**; источники — **SPEC §9**; метрики — **SPEC §10**;
> стандартная библиотека (функции домена) — **docs/stdlib.md**; CLI-команды — **README, раздел
> CLI**; типы Go-ошибок и раскладка пакетов — **ARCHITECTURE.md**.
>
> **Нумерация в этом документе локальная.** Заголовки `EM-1 … EM-17` принадлежат только этому
> файлу; внутренние ссылки даются как «EM-N». Любая ссылка вида «SPEC §11.x» указывает на
> спецификацию языка, а не на разделы этого документа.

## EM-1. Обзор: движок как библиотека над `Store`

Движок процессов — **обычный Go-пакет** (`internal/engine`), работающий поверх интерфейса `Store`.
Он не сетевой сервис и не глобальный синглтон (без глобального состояния). Это позволяет встраивать
один и тот же движок в разные процессы ОС:

| Сценарий запуска | `Store` | Кто двигает инстанс |
|---|---|---|
| `ladix run file.ladix` | `MemoryStore` | один процесс: программа исполняется сверху вниз, `запустить процесс` синхронно доводит инстанс до первого ожидания/терминала и возвращает управление (SPEC §11 — неблокирующе). Незавершённые задачи видны в выводе по завершении `run`. |
| `ladix complete <task-id>` | `SQLiteStore` | короткоживущий процесс: грузит инстанс, помечает задачу готовой, **сам** прогоняет движок до следующего ожидания/терминала, персистит, выходит. |
| `ladix serve` | `SQLiteStore` | демон: планировщик триггеров (EM-17) запускает процессы; каждый синхронно доходит до первого ожидания внутри демона. Человеческие шаги завершаются отдельными процессами `ladix complete`. |
| `ladix emit <E> [json]` | `SQLiteStore` | короткоживущий процесс: пишет внешнее событие (имя + JSON-payload) в очередь `events` и выходит; демон `serve` разбирает на тике (EM-17.3). Источник для `когда событие`. |

**Ключевая идея:** «продвинуть процесс» — это синхронный вызов движка в том процессе ОС, который
инициировал событие (CLI-команда или тик демона). Сетевого слоя и обязательного демона для потока
«человек-в-цикле» нет. Демон (`serve`) нужен только под триггеры по времени/метрикам.

> Команды CLI (`run`/`serve`/`complete`/`tasks`/`emit`/`metric`/`repl`) и их флаги — **README,
> раздел CLI**. Команда `start` в v1 **выкинута**: процесс запускается триггером (`serve`) или
> вызовом `запустить процесс` внутри программы (`run`).

## EM-2. `ProcessInstance`

```go
type Status string

const (
    StatusCreated   Status = "создан"      // персистирован, первый шаг ещё не активирован (транзиентно)
    StatusRunning   Status = "выполняется" // активный шаг исполняет тело
    StatusWaiting   Status = "ожидает"     // активный шаг создал Task, инстанс спит
    StatusDone      Status = "выполнен"     // все шаги готовы (терминал)
    StatusFailed    Status = "провален"     // сбой вызвать / runtime-ошибка шага (терминал)
    StatusCancelled Status = "отменён"      // зарезервирован; в v1 недостижим (SPEC §12)
)

type ProcessInstance struct {
    ID          string           // "p-…", уникален в рамках Store (SPEC §11)
    ProcessName string           // имя ProcessDecl
    Status      Status
    CurrentStep string           // имя активного шага; при терминале — последний обработанный
    Variables   map[string]Value // переменные процесса (SPEC §6); Value — интерфейс значений Ladix
    CreatedAt   time.Time
    UpdatedAt   time.Time
}
```

Статусы инстанса по-русски: `создан` / `выполняется` / `ожидает` / `выполнен` / `провален`;
`отменён` зарезервирован и в v1 недостижим (SPEC §12). Go-идентификаторы (`StatusCreated` и т.д.)
оставлены как есть.

- **`CurrentStep` — один указатель.** Параллельности нет (SPEC §11), активен ровно один шаг,
  исполнение строго по исходнику ⇒ «завершённые шаги» = все объявленные до `CurrentStep`.
  Множество-completed и DAG из `после` в исполнении v1 не нужны (`после` — только валидатор,
  SPEC §11). Движок резолвит имя→позицию по определению процесса.
- **`Variables`** — карта имя→значение. Параметры процесса кладутся сюда при создании как
  начальные переменные (SPEC §6, SPEC §11). `пусть`-локальные шага сюда **не** попадают (живут
  только в кадре исполнения шага).
- **`Value`** — Go-интерфейс, представляющий любое из 10 значений Ladix (SPEC §4). Движок и `Store`
  оперируют `Value`, не зная о формате хранения (см. EM-4).

## EM-3. `Task`

```go
type TaskStatus string

const (
    TaskPending   TaskStatus = "открыта"
    TaskCompleted TaskStatus = "завершена"
)

type Task struct {
    ID          string     // "t-…", уникален в рамках Store
    InstanceID  string     // → ProcessInstance.ID
    StepName    string     // шаг, породивший задачу
    Assignee    string     // значение «исполнитель» (Строка, SPEC §11)
    Deadline    *time.Time // абсолютный дедлайн = момент создания + «срок»; nil, если «срок» не задан
    Status      TaskStatus
    CreatedAt   time.Time
    CompletedAt *time.Time // nil, пока открыта
}
```

- **Нет входного payload (v1).** Завершая задачу, человек не передаёт данные в процесс (SPEC §12).
  Канал данных между шагами — только переменные процесса.
- **`Deadline` — `time.Time` (полная точность), внутренний.** «Срок» (`Длительность`) прибавляется
  к моменту создания. **Просрочка вычисляется движком** (`time.Now().After(*Deadline)`), не
  Ladix-кодом: `сейчас()`/`ДатаВремя` в v1 нет (SPEC §12). Наружу (в Ladix) дедлайн как значение
  **не** экспонируется; экспонируется производное `просрочена: Булево` (см. EM-13). Точный дедлайн
  печатает только CLI `ladix tasks` (Go-форматирование).
- **`TaskStatus`** — строки `открыта`/`завершена` (внутренние для `Task`, не путать со статусами
  инстанса EM-2).

## EM-4. Значения процесса и сериализация

Переменные процесса динамические (10 типов SPEC §4). Для `SQLiteStore` нужен формат хранения; выбран
**type-tagged JSON** — человекочитаемый (БД демона можно инспектировать), языконезависимый,
кругооборотит все типы.

| Тип Ladix | JSON-кодировка |
|---|---|
| Целое | `{"т":"Целое","зн":42}` |
| Дробное | `{"т":"Дробное","зн":3.14}` |
| Строка | `{"т":"Строка","зн":"привет"}` |
| Булево | `{"т":"Булево","зн":true}` |
| Пусто | `{"т":"Пусто","зн":null}` |
| Длительность | `{"т":"Длительность","зн":{"значение":5,"единица":"мин"}}` (пара значение+единица; единица обязательна — `1час ≠ 60мин`, а `мес` к секундам не сводится, SPEC §4) |
| Период | `{"т":"Период","зн":"ежемесячно"}` |
| Дата | `{"т":"Дата","зн":"2026-05-31"}` (ISO `YYYY-MM-DD`) |
| Список | `{"т":"Список","зн":[ <рекурсивно>, … ]}` |
| Запись | `{"т":"Запись","зн":{"поле": <рекурсивно>, …}}` |

**Граница абстракции:** type-tagged JSON — это **внутреннее дело `SQLiteStore`**. Интерфейс `Store`
(EM-5) принимает и отдаёт Go-структуры с `map[string]Value`; `MemoryStore` хранит `Value` нативно,
без всякого JSON. Движок про JSON/SQL не знает вообще — поэтому встроенный бэкенд позже заменяется на
Camunda/Kestra без правки движка.

## EM-5. Интерфейс `Store`

```go
type Store interface {
    SaveInstance(inst *ProcessInstance) error   // upsert: создание и обновление
    LoadInstance(id string) (*ProcessInstance, error)

    SaveTask(t *Task) error
    LoadTask(id string) (*Task, error)
    ListPendingTasks(assignee string) ([]*Task, error) // assignee=="" → все открытые

    NextInstanceID() (string, error)
    NextTaskID() (string, error)

    // Триггеры и события (EM-17)
    LoadTriggerState(triggerID string) (*TriggerState, error)  // ErrTriggerStateNotFound → прайм (EM-17.2)
    SaveTriggerState(ts *TriggerState) error
    NextEventID() (string, error)
    EnqueueEvent(e *Event) error                               // ladix emit (EM-17.3)
    ListUnprocessedEvents() ([]*Event, error)                  // FIFO по CreatedAt
    MarkEventProcessed(id string) error
}

var (
    ErrInstanceNotFound     = errors.New("process instance not found")
    ErrTaskNotFound         = errors.New("task not found")
    ErrTriggerStateNotFound = errors.New("trigger state not found") // → прайм (EM-17.2)
)
```

Методы триггеров/событий добавлены в тот же контракт; их структуры `TriggerState`/`Event` определены
в EM-17.2/EM-17.3. `MemoryStore` хранит их эфемерно (живут в рамках одного `run`, EM-17.8),
`SQLiteStore` — в таблицах `trigger_state`/`events`.

- **Почему интерфейс, а не структура** — движок зависит только от контракта; `MemoryStore`
  (тесты/`run`, миллисекунды) и `SQLiteStore` (`serve`) взаимозаменяемы; путь к Camunda/Kestra
  открыт.
- **`SaveInstance` — upsert.** Один метод на создание и обновление: движок не различает
  «вставить/обновить», это забота реализации (`INSERT … ON CONFLICT` в SQLite, перезапись в карте
  в Memory).
- **Сентинел-ошибки под `errors.Is`:** `LoadInstance` несуществующего id → `ErrInstanceNotFound`;
  вызывающий проверяет `errors.Is(err, ErrInstanceNotFound)`, а не сравнивает строки.
  `состояние_процесса(id)`/`статус_процесса(id)` так отличают «не найдено» от прочих ошибок и дают
  Ladix-ошибку `процесс 'id' не найден` (см. EM-13, docs/stdlib.md).
- **Id mint в Store** — `NextInstanceID`/`NextTaskID`: уникальность «в рамках Store» (SPEC §11)
  живёт в одном месте. SQLite — последовательность/таблица-счётчик; Memory — атомарный счётчик.
- **Минимализм.** Транзакционного метода «завершить задачу + продвинуть инстанс атомарно» в
  интерфейсе нет намеренно — корректность при сбое между `SaveTask` и `SaveInstance` обеспечивается
  идемпотентным восстановлением (EM-12), а не усложнением контракта. `SQLiteStore` волен внутри
  обернуть связанные записи в транзакцию.

## EM-6. `MemoryStore`

`internal/store/memory.go`. Карты `map[string]*ProcessInstance` и `map[string]*Task` под
`sync.Mutex` (на случай конкурентного доступа из горутин в `serve`-подобных тестах). Счётчики id —
атомарные. Никакой сериализации: `Value` лежат как есть. Назначение — `ladix run` (одна программа от
старта до конца) и быстрые тесты lifecycle.

## EM-7. `SQLiteStore`

`internal/store/sqlite.go`, через `modernc.org/sqlite` (чистый Go, без CGO — кросс-компиляция одной
командой). Эскиз схемы:

```sql
CREATE TABLE instances (
    id           TEXT PRIMARY KEY,
    process_name TEXT NOT NULL,
    status       TEXT NOT NULL,
    current_step TEXT NOT NULL,
    variables    TEXT NOT NULL,   -- type-tagged JSON (EM-4)
    created_at   TEXT NOT NULL,   -- RFC3339
    updated_at   TEXT NOT NULL
);
CREATE TABLE tasks (
    id           TEXT PRIMARY KEY,
    instance_id  TEXT NOT NULL REFERENCES instances(id),
    step_name    TEXT NOT NULL,
    assignee     TEXT NOT NULL,
    deadline     TEXT,            -- RFC3339 или NULL
    status       TEXT NOT NULL,
    created_at   TEXT NOT NULL,
    completed_at TEXT
);
CREATE INDEX idx_tasks_pending ON tasks(assignee, status);
```

**WAL + busy_timeout (ключевое).** Несколько процессов ОС (демон `serve` + короткоживущие
`ladix complete`/`tasks`) пишут в один файл. Стандартная Go-практика без CGO:

```
PRAGMA journal_mode = WAL;     -- читатели не блокируют писателя, один писатель за раз
PRAGMA busy_timeout = 5000;    -- при занятой БД ждать до 5с, а не падать с SQLITE_BUSY
PRAGMA foreign_keys = ON;
```

WAL даёт «много читателей + один писатель»; `busy_timeout` сериализует редкие конкурентные записи без
явных блокировок в коде. В v1 этого достаточно (коллизии демона и ручного `complete` редки). Без CGO
всё это — обычные `Exec`-вызовы при открытии соединения.

Путь к файлу БД — флаг `--db` CLI (дефолт `ladix.db` в текущем каталоге); см. README, раздел CLI.

## EM-8. Идентификаторы

- **Mint в `Store`**, непрозрачная строка, префикс типа: `p-…` (инстанс), `t-…` (задача).
  Пользователь формат не парсит (SPEC §11).
- **Схема:** префикс + монотонный счётчик Store (нуль-паддинг) + короткий случайный суффикс из
  `crypto/rand` (stdlib, без CGO) против угадывания: например `p-000123-a3f7`. Чистый счётчик без
  суффикса тоже допустим (уникальность в рамках Store обеспечена счётчиком); суффикс — гигиена, не
  требование.

## EM-9. Жизненный цикл: машина состояний и точки персиста

Формализация переходов SPEC §11 с отметками `SaveInstance` (▼ = персист):

```
запустить процесс P(args):
    id ← Store.NextInstanceID()
    inst ← {id, P, статус=создан, vars=bind(params,args), current_step=первый_шаг}
    ▼ SaveInstance(inst)                       # «создан» (транзиентно)
    advance(inst)                              # синхронный прогон
    return id

advance(inst):                                 # крутит шаги, пока не ожидание/терминал
    loop:
        шаг ← lookup(inst.ProcessName, inst.CurrentStep)
        inst.статус = выполняется
        ▼ SaveInstance(inst)
        err ← runStepBody(inst, шаг)           # SPEC §11 тело-вперёд; каждое «присвоить» ▼ персистит
        если err:
            inst.статус = провален
            ▼ SaveInstance(inst); return       # терминал (SPEC §11)
        если у шага есть «исполнитель»:         # человеческий шаг → заснуть
            t ← {NextTaskID(), inst.id, шаг.имя, исполнитель, дедлайн(шаг.срок)}
            ▼ SaveTask(t)
            inst.статус = ожидает
            ▼ SaveInstance(inst); return        # засыпание (SPEC §11)
        next ← следующий_по_исходнику(inst.CurrentStep)
        если next == ∅:
            inst.статус = выполнен
            ▼ SaveInstance(inst); return        # терминал (SPEC §11)
        inst.CurrentStep = next                 # авто-шаг готов → следующий

complete(taskID):                              # SPEC §11, синхронно
    t ← Store.LoadTask(taskID)                 # нет → ErrTaskNotFound → ошибка CLI (exit 2)
    если t.статус == завершена: error «уже завершена»   # → ошибка CLI (exit 2)
    inst ← Store.LoadInstance(t.InstanceID)
    t.статус = завершена; t.completed_at = now
    ▼ SaveTask(t)
    next ← следующий_по_исходнику(inst.CurrentStep)
    если next == ∅:
        inst.статус = выполнен; ▼ SaveInstance(inst)
    иначе:
        inst.CurrentStep = next
        advance(inst)                           # активировать следующий шаг (может снова заснуть)
```

`ladix complete` на неизвестном или уже завершённом task-id завершается с **кодом возврата 2**
(usage-ошибка); тексты диагностик — EM-16. Коды возврата CLI см. README, раздел CLI.

**Гранулярность персиста.** `SaveInstance` зовётся на: создание, каждое `присвоить` (SPEC §6), каждую
смену статуса/продвижение шага, терминал. Для SQLite каждая — мелкая запись (WAL это тянет).
`присвоить` в цикле `пока` ⇒ много записей: в v1 принимаем ради корректности «значение всегда в
Store»; батчинг/дебаунс — оптимизация v2.

## EM-10. Драйвер исполнения и пробуждение

- **Засыпание** — это `return` из `advance` в статусе `ожидает` с персистированным инстансом.
  Никаких висящих горутин/таймеров на время ожидания человека: всё состояние в `Store`. Инстанс
  переживает рестарт демона.
- **Пробуждение** — внешнее событие `ladix complete <task-id>` в отдельном процессе ОС: грузит
  инстанс из `Store`, помечает задачу, синхронно зовёт `advance` от следующего шага, персистит,
  выходит. Демону ничего сообщать не нужно — истина в SQLite; на своём следующем тике он видит
  актуальное состояние.
- **Встраиваемость.** `advance`/`complete`/`start` — методы пакета `engine`, переиспользуемые и в
  CLI-командах, и в `serve`. Это прямое следствие «движок — библиотека, не сервис».

## EM-11. Конкурентность

- **`ladix run`** — один процесс, `MemoryStore`, всё синхронно: гонок нет.
- **`serve` + `ladix complete`** — разные процессы ОС над одним SQLite-файлом. Сериализацию записей
  обеспечивает WAL+`busy_timeout` (EM-7), а не блокировки в коде Ladix.
- **Внутри демона** планировщик (EM-17) — горутина с `time.Ticker`; её работа (переоценить триггеры,
  запустить процессы) и любые встроенные вызовы движка сериализуются `sync.Mutex` вокруг прогона
  движка, чтобы два тика не лезли в один инстанс. Грациозная остановка демона — `context.Context`:
  тикер слушает `ctx.Done()` и выходит, не оставляя утечки горутины (детали тикера — EM-17.1).

## EM-12. Восстановление после сбоя

- **Персист на границах шага.** `присвоить` коммитит переменную процесса сразу (SPEC §6); локальные
  `пусть` шага не персистируются — при падении посреди шага теряется только незакоммиченный кадр
  шага, переменные процесса целы.
- **Рестарт демона.** Инстансы в `ожидает` корректны (проснутся по `complete`). Инстанс, застрявший
  в `выполняется`/`создан` (падение посреди шага), на старте демона **переактивируется** с его
  `CurrentStep` — `advance` прогоняет шаг заново.
- **At-least-once, честно.** Повторный прогон шага может повторить побочные эффекты. В v1
  `вызвать`/`уведомить` — стабы-логи, повтор безвреден. Для реальных систем (v2) это
  **at-least-once**; exactly-once (журнал эффектов / транзакционные outbox) — v2. Документируем явно,
  а не прячем.
- **Сбой между `SaveTask(завершена)` и продвижением инстанса** (EM-9 `complete`): на рестарте
  обнаруживается «задача завершена, а инстанс всё ещё `ожидает` на её шаге» → движок до-продвигает
  идемпотентно. Поэтому транзакционный комбо-метод в `Store` не обязателен (EM-5).

## EM-13. Отображение в стандартную библиотеку

Сигнатуры и полное описание функций домена — **docs/stdlib.md**. Реализация через `Store`:

| Функция Ladix | Реализация через `Store` |
|---|---|
| `статус_процесса(id) → Строка` | `LoadInstance(id).Status`; `ErrInstanceNotFound` → Ladix-ошибка `процесс 'id' не найден`. |
| `состояние_процесса(id) → Запись` | `LoadInstance(id).Variables` → `Запись` (имя→значение). Не найдено → та же ошибка. |
| `задачи_пользователя(исполнитель) → Список` | `ListPendingTasks(исполнитель)` → `[]*Task` → `Список` из `Запись` (ниже). |

**`Task` → `Запись`** (поверхность, видимая Ladix-коду):

```
{
  ид:         Строка,   # Task.ID
  процесс:    Строка,   # Task.InstanceID
  шаг:        Строка,   # Task.StepName
  исполнитель: Строка,  # Task.Assignee
  статус:     Строка,   # "открыта" / "завершена"
  просрочена: Булево     # движок: time.Now().After(Deadline); при nil-дедлайне — ложь
}
```

Сырой `Deadline` в `Запись` **не** входит (нет `ДатаВремя`, SPEC §12); точный дедлайн показывает
только CLI `ladix tasks`. `просрочена` — производное от Go-времени, единственный наблюдаемый
Ladix-коду признак просрочки (вместо несуществующего `сейчас()`).

## EM-14. Go-идиомы (зачем именно так)

- **`Store` — интерфейс, движок — пакет без глобалов.** Тестируемость (Memory за миллисекунды),
  заменяемость бэкенда, отсутствие глобального состояния.
- **`errors.Is` + сентинелы** вместо сравнения строк ошибок — стандарт Go для «различить вид ошибки»
  (`ErrInstanceNotFound`/`ErrTaskNotFound`/`ErrTriggerStateNotFound`).
- **`time.Time`/`time.Duration`** для моментов/дедлайнов: полная точность внутри, day-усечение только
  там, где Ladix реально не имеет `ДатаВремя`.
- **WAL + `busy_timeout`** — канонический способ дать `modernc.org/sqlite` многопроцессный доступ без
  CGO и без ручных блокировок.
- **`context.Context` + `ctx.Done()`** для остановки демона без утечки горутин (тикер — EM-17.1).
- **`*time.Time` (указатель) для nullable-полей** (`Deadline`, `CompletedAt`): `nil` = «не задано»,
  идиоматичнее «нулевого времени».

## EM-15. Границы: что не покрыто (→ v2)

- **Сетевой/IPC-слой** — не в v1.
- **Батчинг персиста, инкрементальность, exactly-once эффектов, отзыв осиротевших задач,
  транзакционный outbox** → v2.
- **Точные поля для миграций схемы SQLite, версии БД** → деталь имплементации.

## EM-16. Диагностики lifecycle

Заголовок рантайм-ошибки домена — по канону SPEC §13: «Ошибка в строке N, колонка M:» (где есть
позиция вызова в исходнике, например встроенная функция `статус_процесса`). CLI-ошибки команд
(`complete`) — отдельная диагностика процесса, без позиции в исходнике.

| Случай | Уровень | Сообщение |
|---|---|---|
| `статус_процесса`/`состояние_процесса` неизвестного id | Runtime (заголовок «Ошибка в строке N, колонка M:») | `процесс '<id>' не найден` |
| `ladix complete` неизвестного task-id | CLI Error (exit 2) | `задача '<id>' не найдена` |
| `ladix complete` уже завершённой задачи | CLI Error (exit 2) | `задача '<id>' уже завершена` |
| Открытие битой/несовместимой SQLite-БД | Fatal (старт) | `не удалось открыть хранилище '<путь>': <причина>` |
| Сбой записи в `Store` (диск/блокировка > timeout) | Runtime | оборачивается через `fmt.Errorf("...: %w", err)`, всплывает с контекстом |

## EM-17. Планировщик триггеров

Планировщик — часть демона `serve` (EM-1). Он реализует семантику триггеров **SPEC §11**: переход
метрик `ложь→истина`, доставку событий, расписание.

### EM-17.1. Обзор: что делает тик

Тикер (EM-11) на каждом тике вызывает `d.tick()`. Один тик — **последовательный** проход в
детерминированном порядке:

```
tick():
  1. drainEvents()       # разобрать накопленную очередь events (EM-17.3)
  2. evalMetrics()       # переоценить все метрика-триггеры, детект перехода (EM-17.2)
  3. checkSchedules()    # проверить все расписание-триггеры (EM-17.4)
```

Каждый сработавший триггер исполняет своё тело (EM-17.5). Триггеры одного вида обрабатываются в
**порядке объявления в исходнике** (детерминизм, SPEC §11). Сбой одного триггера изолирован
(EM-17.6) и не мешает остальным.

Базовый интервал тикера — флаг CLI `--interval` (дефолт `1m`, формат `time.ParseDuration`); см.
README, раздел CLI. Разрешение тика ≥ разрешения `в "ЧЧ:ММ"` (минуты) достаточно: `расписание в
"14:30"` сработает в пределах одного интервала. Грациозная остановка — `ctx.Done()` (EM-11).

### EM-17.2. Состояние перехода (`trigger_state`)

Чтобы поймать переход `ложь→истина` (метрика) и каденс (расписание), демон помнит состояние **между
тиками и между рестартами**: оно персистится в `Store`, симметрично остальному durable-состоянию.

```go
type TriggerState struct {
    TriggerID     string     // стабильный ключ триггера (EM-17.2.1)
    Kind          string     // "metric" | "schedule_every" | "schedule_at"
    LastBool      *bool      // metric: базовая линия; nil = ещё не праймлен
    LastFire      *time.Time // schedule_every: момент последнего срабатывания
    LastFiredDate *string    // schedule_at: дата "YYYY-MM-DD" последнего срабатывания
}
```

**Прайм без срабатывания.** Для метрика-триггера: если `LoadTriggerState` вернул
`ErrTriggerStateNotFound` (первая оценка), демон вычисляет условие и **молча** записывает базовую
линию (`LastBool`), не исполняя тело — даже если условие уже истинно. Срабатывание возможно только со
следующей оценки, на фактическом переходе `ложь→истина`. Персист базовой линии означает, что после
рестарта прайм не повторяется (SPEC §11).

**Заморозка базы при невычислимом условии.** Если на оценке метрика `пусто` / сравнение не-`Булево`
(SPEC §10) — `LastBool` не перезаписывается (`SaveTriggerState` пропускается), тело не исполняется
(SPEC §11).

#### EM-17.2.1. Идентификатор триггера

Триггеры анонимны (нет имени в грамматике). Стабильный ключ — **порядковый индекс объявления** в
исходнике: `TriggerID = "trg-<N>"` (N — 0-based порядок среди всех `TriggerDecl`). Прост и стабилен,
пока исходник не редактируется между рестартами.

Граница (фиксируется в SPEC §12): правка исходника, сдвигающая порядок триггеров, «съезжает»
сохранённое состояние (старое `trg-2` теперь относится к другому триггеру). Для v1 приемлемо (рестарт
с тем же файлом — норма). Альтернатива «ключ = хеш текста условия» (устойчива к переупорядочиванию,
сбрасывает базу при правке условия) — v2.

### EM-17.3. Очередь событий (`events`)

`ladix emit <E> [json]` — короткоживущий процесс (как `complete`): пишет событие в очередь `events`
общего `Store` (`EnqueueEvent`) и выходит. Демон разбирает очередь на тике (`drainEvents`).

```go
type Event struct {
    ID          string    // opaque, "e-…"
    Name        string    // имя события
    PayloadJSON string    // сырой JSON payload (маппинг → Запись при обработке)
    CreatedAt   time.Time
    Processed   bool
}
```

`drainEvents`:

1. `ListUnprocessedEvents()` → события в порядке поступления (FIFO по `CreatedAt`/rowid).
2. Для каждого: найти событие-триггеры с `EventTrigger.Name == E`.
3. Распарсить `PayloadJSON` в `Запись` (маппинг JSON→типы как у источников, SPEC §9; доступ к полю
   толерантный, SPEC §6), привязать к предопределённой `событие`.
4. Исполнить тело каждого совпавшего триггера (EM-17.5).
5. `MarkEventProcessed(id)`.

Событие без обработчиков — помечается processed (отбрасывается), лог «событие E без триггеров».
**At-least-once** (симметрично EM-12): сбой демона между исполнением тела и `MarkEventProcessed` →
событие переобработается при следующем старте (повтор `запустить процесс` безвреден —
fire-and-forget). Exactly-once — v2.

Эскиз схемы SQLite (в дополнение к EM-7):

```sql
CREATE TABLE trigger_state (
    trigger_id      TEXT PRIMARY KEY,
    kind            TEXT NOT NULL,
    last_bool       INTEGER,        -- 0/1/NULL (NULL = не праймлен)
    last_fire       TEXT,           -- RFC3339 или NULL
    last_fired_date TEXT            -- "YYYY-MM-DD" или NULL
);
CREATE TABLE events (
    id           TEXT PRIMARY KEY,
    name         TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    created_at   TEXT NOT NULL,
    processed    INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_events_pending ON events(processed, created_at);
```

### EM-17.4. Расписание

Демон смотрит на Go-wall-clock **внутри** (деталь имплементации, наружу как значение Ladix не течёт —
SPEC §12).

**`каждые D`** (`schedule_every`):
- Якорь: при первой регистрации (`ErrTriggerStateNotFound`) `LastFire ← now` (момент старта), без
  срабатывания.
- На тике: если `now >= LastFire + D` → сработать, `LastFire ← now` (факт срабатывания, дрейф не
  копим: `next = факт + D`).
- `LastFire` персистится — после рестарта каденс продолжается с сохранённого якоря (не сбрасывается
  на старт).

**`в "ЧЧ:ММ"`** (`schedule_at`):
- На тике: пусть `today = now.date`, `target = now.date в ЧЧ:ММ`. Если `LastFiredDate != today` И
  `now >= target` → сработать, `LastFiredDate ← today`.
- Раз в сутки. Если демон стартовал после `ЧЧ:ММ` — сработает в день старта (условие выполнено, дата
  ещё не отмечена); далее — на следующих сутках.

### EM-17.5. Исполнение тела и `advance`

Сработавший триггер исполняет тело (`Block`) интерпретатором в scope тела триггера (SPEC §11):
предопределённые `значение`/`событие`, read-only глобалы/метрики, локальные `пусть`. `запустить
процесс P(...)` внутри → EM-9 (`NextInstanceID`, создать `ProcessInstance`, `advance` до
ожидания/терминала), fire-and-forget. Несколько `запустить процесс` в одном теле — последовательно.

### EM-17.6. Изоляция сбоев (`recover`)

Каждый триггер на тике обёрнут `recover` (см. EM-12): runtime-ошибка или паника в одном триггере
**логируется и не роняет демон** — остальные триггеры этого тика и последующие тики продолжают
работать. Базовая линия метрики уже обновлена до тела (SPEC §11), поэтому сбойный триггер не
зацикливается на повторном `ложь→истина`.

### EM-17.7. Конкурентность

- Тик **последовательный** — один поток исполнения движка в демоне (EM-11). Метрика-триггеры,
  расписание, события на одном тике не пересекаются по времени.
- `ladix emit` пишет в `events` из **другого** процесса ОС; демон читает на тике. Кросс-процессная
  синхронизация — WAL + `busy_timeout` (EM-7), как для `complete`. Гонок нет: SQLite сериализует
  запись.
- `trigger_state` читается/пишется **только** демоном (на тике) — внешние процессы его не трогают.

### EM-17.8. Режим `run`

`ladix run` (MemoryStore, без тикера) делает **один** оценочный проход метрика-триггеров после
загрузки источников: базовая линия = `ложь` ⇒ истинное условие срабатывает один раз
(`fire-if-true`). `trigger_state` — в памяти, эфемерно. Расписание/событие в `run` — **no-op** с
логом «требует serve». Это даёт демо «метрика < порог → запустить процесс» прямо в `run` (SPEC §11).

### EM-17.9. Стоимость переоценки

Каждый тик пересчитывает все метрика-триггеры → пересчитывает их метрики (SPEC §10 — чистый пересчёт
на чтение; источник кешируется на запуск, SPEC §9). В v1 приемлемо. Кеш/инвалидация значений метрик
между тиками — v2 (EM-17.10).

### EM-17.10. Что планировщик НЕ покрывает (→ v2)

- **Cron-выражения** и сложное расписание (`каждые`/`в` — единственные формы, SPEC §12).
- **Приём событий по сети** (HTTP-эндпоинт): источник событий в v1 — только `ladix emit` через общий
  SQLite (Design Y отвергнут, SPEC §12).
- **Exactly-once** доставки событий и эффектов триггеров (at-least-once, EM-17.3).
- **Кеш значений метрик** между тиками / инкрементальный пересчёт (EM-17.9).
- **Стабильный ключ триггера при правке исходника** (хеш условия вместо индекса, EM-17.2.1).
