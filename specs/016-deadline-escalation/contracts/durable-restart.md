# Contract: durable-эскалация × рестарт (B4b)

Источник §AU-6.3 / §AU-12.B. Группа: **B4b-бэкенд**. ОБЯЗАТЕЛЬНЫЙ инвариант DoD (INV-2).

## Гарантия

Эскалация — ровно раз на задачу, переживает рестарт демона БЕЗ дублирования. Состояние НЕ в
`TriggerState` (D-AU-5), а в `Task.Escalated`, персистнутом в SQLite. После рестарта
`RunRestartScan` (`restart.go:28`) реактивирует инстансы; `checkDeadlines` читает
`ListPendingTasks` из той же `--db`, видит `Escalated==true` → `continue` → повтор невозможен.

## Порядок с B5 (осознанная последовательность, НЕ дефект)

§AU-12.B канон стартует инстанс `ladix start эскалация_плана 2500000 --db demo.db`, но
`ladix start` — это **B5**, идёт ПОСЛЕ B4. Поэтому durable тестируется на уровне **Go-API**:

```text
1. SQLiteStore(demo.db); engine.Start("эскалация_плана", [2500000])
   → p-000001, факт=2500000, шаг связаться_с_клиентом, t-000001 (срок = created+2дн)
2. Daemon{clock: FixedClock(created), st: SQLiteStore}; d.tick()
   → checkDeadlines: t-000001 НЕ просрочена → тишина
3. clock.Advance(3дн); d.tick()
   → t-000001 просрочена, !Escalated, шаг/процесс совпали
   → fireDeadlineBody: "[уведомление] руководитель: 2500000" — РОВНО ОДИН раз
   → t-000001.Escalated=true; SaveTask (UPSERT, точка 3 кодека)
4. d.tick() ещё раз (без рестарта)
   → Escalated==true → continue → НЕТ повтора
5. РЕСТАРТ: новый SQLiteStore(demo.db); RunRestartScan(); d.tick()
   → ListPendingTasks читает Escalated=true (точка 4 кодека) → continue → НЕТ повтора
6. assert: уведомление руководителю напечатано РОВНО ОДИН раз за все тики/прогоны
```

Полная CLI-сборка §AU-12.B (через `ladix start`/`serve`) и end-to-end §AU-12.C — на **M2-гейте
ПОСЛЕ B5/B6** (терминальный гейт M2, не критерий приёмки B4b).

## Граничные случаи (§AU-6.3)

| Случай | Поведение |
|--------|-----------|
| Задача завершена `complete` ДО просрочки | не в `ListPendingTasks` → эскалации нет |
| Задача эскалирована, затем завершена | `Escalated` уже стоит; завершение штатно |
| `--db` отсутствует (MemoryStore) | durable НЕ держится (эфемерно); демо ОБЯЗАНО с `--db` (§AU-9) |

## Замки §AU-12.B (B4b-группа)

- **(а) единичность**: уведомление РОВНО один раз за оба прогона (счётчик в стабе/буфере).
- **(б) персист**: `Escalated` персистнут в SQLite между прогонами (перечитать из новой
  `SQLiteStore` на той же `--db` → `Escalated==true`).
- **(в) аддитивность**: 4-я фаза не ломает первые три (живой daemon-тест, см.
  `tick-phase-checkdeadlines.md`).
- **(г) МУТПРОБА (несущая)**: снять durable-фильтр `if t.Escalated { continue }` →
  шаги 4 и 5 эскалируют повторно → durable-golden КРАСНЕЕТ (двойная эскалация после рестарта).
  Это главный замок INV-2.

## Дополнительные мутпробы (4 точки кодека → durable)

- Пропуск точки 3 (ON CONFLICT escalated) → шаг 3 пишет `SaveTask`, но upsert не сохраняет →
  на рестарте (шаг 5) `Escalated=false` → повтор → красный.
- Пропуск точки 4 (SELECT/scanTask escalated) → `ListPendingTasks` всегда `false` → уже шаг 4
  (без рестарта) эскалирует повторно → красный.

Тем самым durable-golden — интегральный замок целостности всех 4 точек кодека.
