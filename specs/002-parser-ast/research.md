# Phase 0 — Research & Decisions: Парсер + AST Ladix

**Feature**: 002-parser-ast | **Date**: 2026-06-02 | **Plan**: [plan.md](./plan.md)

Спека предельно детальна (FR-001..FR-029, A1–A6, D1–D6), и бриф зафиксировал решения D1–D6 плюс явно
поручил сформулировать неканонические тексты ошибок и перечислить синхро-токены, поэтому **открытых
`NEEDS CLARIFICATION` нет**. Этот документ фиксирует ключевые проектные решения в формате
*Decision / Rationale / Alternatives*, чтобы код и задачи (`/speckit-tasks`) не дрейфовали. Каждое
решение опирается на размещённые источники истины (конституция IX).

---

## D-R1. `Position` — ast-local; **D1 РЕШЁН ЗДЕСЬ** (A2)

- **Decision**: узлы пакета `ast` несут СВОЙ тип `Position{Line, Col int}` (1-based, руны) и НЕ
  импортируют `internal/errors`. Helper-конвертер `errors.Position → ast.Position` живёт в пакете
  `parser` (`pos.go`), не в `ast`. Тип **дублируется, не разделяется**. Лексер не затронут — `Token.Pos`
  остаётся `errors.Position`.
- **Rationale**: ARCHITECTURE §4.1/§2.1 и конституция IV/VII требуют, чтобы `ast` был **листовым**
  (на него опираются, он ни на кого выше не опирается). Импорт `errors` в `ast` создал бы ребро
  `ast → errors` и лишил бы `ast` листовости. 001 оставлял D1 ОТЛОЖЕННЫМ именно до шага AST/parser —
  этот шаг и есть точка решения; конституция (уже ратифицированная, принцип IV) фиксирует выбор
  ast-local. Конвертер в `parser` уместен: парсер — единственное место, где видны обе стороны
  (читает `Token.Pos`, строит узлы `ast`).
- **Alternatives considered**:
  - Общая `Position` в `errors`, импортируемая из `ast` (как у лексера на шаге 001) — отвергнута:
    нарушает листовость `ast` (конституция VII, ARCHITECTURE §2.1).
  - Конвертер в `ast` — отвергнут: затащил бы `errors` в `ast`.
- **Статус**: **D1 — РЕШЁН** (ast-local). Guardrail 1.

## D-R2. Диапазон int64 у `IntLit` проверяет парсер (D2)

- **Decision**: при сборке `IntLit` парсер берёт нормализованную цифровую строку токена `INT`
  (`Token.Lexeme`, без `_` — гарантия лексера C-3) и конвертирует через `strconv.ParseInt(lexeme, 10,
  64)`. Ошибка диапазона (`ErrRange`) → синтаксическая **статическая накапливаемая** ошибка
  `целочисленный литерал вне диапазона типа Целое '<лексема>'` (дословно §13.4). Узел `IntLit` всё равно
  создаётся (со значением 0 / sentinel), чтобы разбор продолжился и накопил прочие ошибки. Знак НЕ
  сворачивается в литерал: `-X` остаётся `UnaryExpr(-, IntLit(X))`, поэтому точный `MinInt64`
  (`9223372036854775808` как беззнаковый литерал > MaxInt64) даёт ту же ошибку — невыразимость ожидаема
  (`SPEC §4/§12`).
- **Rationale**: §13.1/§13.4 классифицируют «целый литерал вне диапазона» как **Синтаксическую**
  (парсер), не лексическую и не рантайм; 001 (D-R2) уже переложил конверсию на парсер, неся `INT`
  строкой. Единое место диапазон-проверки.
- **Alternatives considered**:
  - Свёртка знака (`-X` → `IntLit(-X)`), чтобы выразить `MinInt64` — отвергнута брифом (НЕ сворачивать
    знак); усложняет грамматику и ломает конвенцию «унарный минус — отдельный узел».
  - Проверка в лексере — отвергнута на шаге 001 (D2, вариант B).
- **Статус**: **D2 — РЕШЁН** (парсер). Guardrail 2.

## D-R3. `DurationLit` — диапазон НЕ проверяется в 002 (FR-021)

- **Decision**: `DurationLit` берёт единицу и числовую лексему из `Token.Value`/`Token.Lexeme`
  (`DurationValue{Amount, Unit}` лексера) и строит узел БЕЗ проверки диапазона. Переполнение величины
  длительности — backlog `float-overflow-spec-gap`, вне фичи 002.
- **Rationale**: бриф явно исключил проверку `DurationLit`; вырожденный edge, отдельного текста §13.4
  нет. Согласованность с тем, что лексер тоже не проверял (001 D-R3).
- **Alternatives considered**: проверять величину как у `IntLit` — отвергнуто (вне scope, нет канон-текста).
- **Статус**: вне scope 002. Guardrail 2.

## D-R4. Единый `BinOp`, `CompOp` = подмножество (D3)

- **Decision**: `BinOp` — единый enum всех 14 бинарных операторов (`или` `и` `+` `-` `*` `/` `//` `%`
  `==` `!=` `<` `<=` `>` `>=`). `CompOp` — именованное подмножество из 6 сравнений, **отбираемое из
  `BinOp`** (например `type CompOp = BinOp` с набором валидных значений, или предикат `BinOp.IsComparison()`),
  без дублирования констант. `UnOp` — отдельный enum (`не`, унарный `-`). У всех — `String()` для
  диагностики/тестов.
- **Rationale**: ARCHITECTURE §4.7 (стр. ~233) — один источник истины операторов; `CompOp` не дублирует
  константы, а отбирает их; на `CompOp` сошлётся будущий `MetricTrigger.Op` (§4.5). Снимает расхождение
  §4.5↔§4.7 (правка ARCHITECTURE, коммит 5350930).
- **Alternatives considered**: два независимых enum (`BinOp` + отдельный `CompOp`) — отвергнут: дублирует
  6 констант, риск рассинхронизации.
- **Статус**: **D3 — РЕШЁН**. Guardrail 3.

## D-R5. Конвенция `Pos()` узла (D4)

- **Decision**: `BinaryExpr.Pos`/`UnaryExpr.Pos` = позиция токена **оператора** (не левого операнда);
  `CallExpr.Pos` = позиция `Callee`; `IndexExpr.Pos`/`FieldExpr.Pos` = позиция `Target`; литералы и
  `Ident` — свой токен; statements (`LetStmt`/`IfStmt`/…) — ведущий ключевой токен; `FunctionDecl` —
  токен `функция`; `Block` — позиция `INDENT`/первого оператора; `Program` хранит `EOFPos` отдельно.
- **Rationale**: load-bearing для будущей runtime-диагностики eval — деление на ноль должно
  рапортоваться на колонке `/` (ARCHITECTURE §4.1, `examples/ошибка.ladix` стр. 5 кол. 14). Позиция
  оператора у бинарных/унарных — единственный способ это обеспечить.
- **Alternatives considered**: `Pos` = левый операнд — отвергнут: ломает диагностику оператора (eval).
- **Статус**: **D4 — РЕШЁН**. Guardrail 4.

## D-R6. `GroupExpr` сворачивается (D5)

- **Decision**: при разборе `"(" Expression ")"` парсер возвращает обёрнутое выражение как есть;
  отдельный узел `GroupExpr` НЕ материализуется. Приоритет, заданный скобками, уже отражён структурой
  дерева (`(2 + 3) * 4` → `BinaryExpr(*, BinaryExpr(+, 2, 3), 4)`).
- **Rationale**: ARCHITECTURE §4.7 — «`GroupExpr` обычно сворачивается». Узел-обёртка не несёт
  семантики и усложнил бы обход дерева в eval.
- **Alternatives considered**: материализовать `GroupExpr` (для точного round-trip исходника) —
  отвергнуто: round-trip/форматер не в scope v1; узел был бы мёртвым весом.
- **Статус**: **D5 — РЕШЁН**. Guardrail 5.

## D-R7. Парсер работает безусловно на best-effort потоке; без стадийного гейтирования (FR-025)

- **Decision**: парсер — чистая функция `[]Token → (*Program, *ErrorList)`; он НЕ знает о лексических
  ошибках и НЕ гейтит разбор по их наличию. Лексер при ошибке пропускает проблемную лексему (токен не
  эмитится — 001 C-1.6), поэтому поток может иметь «дыры»; парсер разбирает то, что есть, и регистрирует
  свои синтаксические ошибки в общий `ErrorList`. Любой каскад от «дыр» ограничен общим бюджетом (≈20) и
  panic-mode-синхронизацией.
- **Rationale**: §13.2 — panic-mode единый для лексера+парсера, накопление ≈20. Разделение
  ответственности: «гейтить ли парсер при лексических ошибках» — решение сборки пайплайна (CLI, будущая
  фича), не самого парсера. Чистая функция тестируема и переиспользуема (конституция V).
- **Alternatives considered**:
  - Fail-fast на границе (если есть лексические ошибки — не парсить) — отвергнуто: §13.2 требует
    накопления через обе фазы; решение всё равно за пайплайном, не за парсером.
- **Статус**: дефолт зафиксирован (не молчаливый). Guardrail 11.

## D-R8. Множество синхро-токенов panic-mode — явный список (FR-026, D6)

- **Decision**: при ошибке парсер регистрирует её, затем отбрасывает токены до ближайшего токена из
  **явного** набора (перечислен в spec.md «Множество синхро-токенов» / contracts/syntax-errors.md):
  структурные `NEWLINE`/`DEDENT`/`EOF`; ведущие ключевые слова statements (`пусть`/`если`/`пока`/`для`/
  `вернуть`/`прервать`/`продолжить`); декларация B (`функция`); зарезервированные step-action
  (`присвоить`/`вызвать`/`уведомить`); отложенные top-level декларации (`источник`/`метрика`/`процесс`/
  `когда`). Семантика потребления: структурные `NEWLINE`/`DEDENT` при синхронизации **потребляются**
  (разбор продолжается после них); ведущие ключевые слова **не** потребляются (разбор начинается с них).
  До точки синхронизации регистрация НОВЫХ ошибок подавлена (без фантомов).
- **Rationale**: бриф требует ПЕРЕЧИСЛИТЬ синхро-токены явно, а не качественно. §13.2 называет безопасные
  точки: `NEWLINE`/`DEDENT`/начало top-level-элемента — набор их кодирует. Отложенные декларации включены
  как безопасные точки ре-синхронизации (сами дают SE-UNEXPECTED, но не порождают каскад).
- **Alternatives considered**:
  - Синхронизация только по `NEWLINE` — отвергнута: внутри блока на `DEDENT` нужно закрыться, а
    ведущие ключевые слова дают более точное восстановление.
  - Качественное описание «до безопасной точки» — отвергнуто брифом.
- **Статус**: зафиксировано. Guardrail 10.

## D-R9. Ручной recursive descent, каскад по приоритетам (конституция II)

- **Decision**: разбор выражений — каскад из ОДНОЙ функции на уровень приоритета
  (`parseLogicOr → parseLogicAnd → parseLogicNot → parseComparison → parseAdditive → parseMultiplicative
  → parseUnary → parsePostfix → parsePrimary`); лево-ассоциативность — циклом `for` внутри уровня
  (`left = BinaryExpr(op, left, right)`); унарные `не`/`-` — рекурсией (право-ассоциативно); постфикс —
  циклом навешивания `CallExpr`/`IndexExpr`/`FieldExpr`. Один токен предпросмотра (`peek`), без
  бэктрекинга. `Comparison` допускает не более одного `CompOp` (после первого — если снова `CompOp` →
  SE-CHAIN).
- **Rationale**: конституция II ЗАПРЕЩАЕТ генераторы/комбинаторы/regex; каскад «одна функция на уровень»
  буквально отражает грамматику §9 и даёт полный контроль над позициями (конституция IV). Прозрачнее
  Pratt-парсинга для фиксированной грамматики.
- **Alternatives considered**:
  - Pratt / precedence-climbing — допустим конституцией (ручной), но менее буквально отражает EBNF §9;
    отвергнут ради читаемости и прямого соответствия grammar.md.
  - Генераторы/комбинаторы — ЗАПРЕЩЕНЫ конституцией II.
- **Статус**: Guardrail 9.

## D-R10. `ParseError` — добавление к `errors` без правок агрегата (FR-023)

- **Decision**: новый файл `internal/errors/parserror.go` с типом
  `ParseError struct { Pos Position; Msg string }` и методом `Error()`, дающим тот же двухстрочный канон,
  что у `LexError` (`Ошибка в строке N, колонка M:\n<Msg>`). `ParseError` складывается в **тот же**
  `errors.ErrorList` (агрегат уже принимает `Add(err error)` и разворачивается `Unwrap() []error` —
  `aggregate.go` НЕ меняется). Развёртка через `errors.As(&ParseError{})`. Пакет `errors` не растёт сверх
  этого файла (+тест).
- **Rationale**: §13 — единый формат для всех категорий; §13.2 — общий накопитель лексика+синтаксис.
  Существующий `ErrorList.Add(error)`/`Unwrap()[]error` (001) уже полиморфен по `error` — `ParseError`
  встаёт без изменений агрегата. Бриф: «не трогать `errors` сверх добавления типа синтаксической ошибки».
- **Alternatives considered**:
  - Отдельный список синтаксических ошибок — отвергнут: §13.2 требует ОДИН накопитель (общий бюджет).
  - Богатый `ParseError` (с полями expected/got) — отвергнут: `Msg`-строка достаточна для golden-тестов
    и канона §13; шаблонизация текста — в `parser/errors.go`.
- **Статус**: Guardrail 8.

## D-R11. Разбор statement: присваивание vs выражение; голый `вернуть` (FR-009/FR-012)

- **Decision**: statement, не начинающийся с ведущего ключевого слова, разбирается так: разобрать
  выражение; если следующий токен `ASSIGN` (`=`) — это присваивание, и разобранное слева ОБЯЗАНО быть
  `*ast.Ident`, иначе → SE-ASSIGN-TARGET (`неверная цель присваивания: слева от '=' допустима только
  переменная`); иначе — `ExpressionStmt`, завершаемый `NEWLINE`. `ReturnStmt`: после `вернуть` — если
  следующий токен НЕ начинает выражение (т.е. `NEWLINE`) → `Value = nil` (голый возврат); иначе разобрать
  выражение. Различение «начинает ли токен выражение» — по множеству FIRST(Expression) (литералы,
  `IDENT`, унарные `не`/`-`, `(`, `[`, `запустить`).
- **Rationale**: grammar §3 — `AssignStmt ::= Ident "=" …`, lvalue только `Ident`; `x.f = …`/`x[i] = …`
  не допускаются (US2). Разбор «expr, затем проверка `=`» — стандартная техника для леворекурсивно
  неоднозначного начала (IDENT может начать и присваивание, и выражение). Голый `вернуть` — `ReturnStmt`
  с `nil` (ARCHITECTURE §4.3: «nil → голый `вернуть` → `пусто`»).
- **Alternatives considered**:
  - Спекулятивный lookahead `IDENT =` для выбора ветки до разбора — отвергнут: ломается на
    `x.f =`/`x[i] =` (нужно разобрать постфикс, чтобы понять, что lvalue не `Ident`); «expr-then-`=`»
    обрабатывает оба случая единообразно и даёт точный SE-ASSIGN-TARGET.
- **Статус**: Guardrail 7 (часть «парсер не делает семантику»: объявленность `x` НЕ проверяется).

## D-R12. Блок на виртуальных токенах; пустой блок; вложенная функция (FR-013/FR-014)

- **Decision**: `Block` после `:` разбирается как `NEWLINE` → `INDENT` → `Statement`+ → `DEDENT`.
  Если после `:`+`NEWLINE` нет `INDENT` (следующий — `DEDENT` или statement того же уровня) → пустой блок
  → SE-EMPTY-BLOCK. `FunctionDecl` разбирается ТОЛЬКО функцией верхнего уровня (`parseTopLevelItem`); при
  встрече `функция` внутри любого `Block` (в `parseStatement`) → SE-NESTED-FN (`вложенные функции не
  поддерживаются в v1`) — это **синтаксическая** проверка (grammar §4: `FunctionDecl` не входит в
  `Statement`), не семантическая.
- **Rationale**: grammar §10 — `Block ::= Newline Indent Statement Statement* Dedent`, пустые блоки
  запрещены; §4 — вложенные функции синтаксически запрещены. Лексер гарантирует баланс `INDENT`/`DEDENT`
  (001 C-1.3), поэтому парсер опирается на них напрямую.
- **Alternatives considered**:
  - Трактовать вложенную `функция` как семантику (eval-later) — отвергнуто: grammar §4 относит её к
    синтаксису, и для неё есть канон-текст §13.4.
- **Статус**: Guardrail 7/12.

## Решения по текстам синтаксических ошибок

- **Три канонических текста** воспроизводятся ДОСЛОВНО из `SPEC §13.4` (конституция VIII, FR-024):
  `сравнения нельзя сцеплять, используйте 'и': 1 < x и x < 10`; `вложенные функции не поддерживаются в
  v1`; `целочисленный литерал вне диапазона типа Целое '<лексема>'`.
- **Четыре эталона** (SE-EXPECTED, SE-UNEXPECTED, SE-EMPTY-BLOCK, SE-ASSIGN-TARGET) сформулированы по
  стилю §13.4 и зафиксированы spec.md / contracts/syntax-errors.md. Бриф ЯВНО поручил их сформулировать —
  это санкционированное доопределение (конституция IX), не молчаливое. Псевдо-лексемы виртуальных токенов
  в текстах (`NEWLINE`→`конец строки`, `INDENT`→`увеличение отступа`, `DEDENT`→`конец блока`, `EOF`→
  `конец файла`) — конвенциональный дефолт для читаемости сообщений (виртуальные токены пустой лексемы
  не имеют). Любое уточнение формулировок — через `/speckit-clarify` до реализации.

## Структурные решения

- **S1 — Корень Go-модуля = `src/`** (унаследовано из 001; module `github.com/denis-kosyakov/ladix`).
- **S2 — Тесты co-located** (`*_test.go` рядом с пакетами), идиома Go + конституция VI.
- **S3 — Два новых листовых/полулистовых пакета**: `internal/ast` (листовой — импортирует только себя) и
  `internal/parser` (`parser → {ast, errors, lexer}`). Граф без циклов (ARCHITECTURE §2.1). `errors`
  дополняется одним файлом `parserror.go`.
