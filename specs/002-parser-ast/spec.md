# Feature Specification: Парсер + AST Ladix (ручной recursive descent, подмножество B)

**Feature Branch**: `002-parser-ast`

**Created**: 2026-06-02

**Status**: Draft

**Input**: User description: «Реализовать второй слой компилятора Ladix: парсер (ручной recursive descent) и пакет `ast`. Парсер потребляет поток токенов лексера (фича 001) и строит AST императивного ядра языка (подмножество B: выражения, statements, `FunctionDecl`, блоки). НЕ интерпретатор — eval будет фичей 003. Плюс понятные синтаксические ошибки со строкой и колонкой, накопление и panic-mode восстановление.»

**Источники истины**: `SPEC.md` §3 (грамматика), §4 (диапазон `Целое`), §5 (выражения, приоритеты, ассоциативность), §13 (ошибки: §13.1 категории, §13.2 накопление, §13.4 тексты); `docs/grammar.md` §3/§4/§9/§10 (EBNF подмножества); `ARCHITECTURE.md` §4 (эскиз AST: §4.1 `Position`/`Pos()`, §4.3 statements, §4.4 `FunctionDecl`, §4.6 step actions, §4.7 выражения/`BinOp`/`CompOp`, §4.8 `Block`); `specs/001-lexer-tokens/contracts/token-stream.md` + `data-model.md` (поток токенов — стабильный вход).

## User Scenarios & Testing *(mandatory)*

«Пользователи» парсера — два класса: **(A) автор программы на Ladix**, который видит позиционные синтаксические диагностики при нарушении грамматики, и **(B) eval-потребитель** (будущая фича 003), которому парсер отдаёт AST как стабильный контракт. Сценарии описывают наблюдаемое поведение для обоих, без деталей реализации.

### User Story 1 — Выражения с приоритетами строятся в корректное дерево (Priority: P1)

Автор пишет любое выражение Ladix; парсер строит AST, точно отражающее каскад приоритетов и лево-ассоциативность из `SPEC §5`. Покрыты все литералы, унарные/бинарные операторы, постфикс-цепочка (вызов/индекс/`.поле`), список, группировка; при сборке целого литерала проверяется диапазон int64; цепочечные сравнения запрещены.

**Why this priority**: выражения — ядро, на которое опираются все statements (условия, присваивания, аргументы, возвраты). Без корректного дерева приоритетов невозможен ни один следующий слой. Это фундамент и самостоятельный MVP: разбор выражений.

**Independent Test**: подать таблицу выражений, сверить построенный AST с эталоном; контрольный инвариант `2 + 3 * 4` → `BinaryExpr(+, IntLit(2), BinaryExpr(*, IntLit(3), IntLit(4)))`; лево-ассоциативность `a - b - c` → `BinaryExpr(-, BinaryExpr(-, a, b), c)`.

**Acceptance Scenarios**:

1. **Given** `2 + 3 * 4`, **When** разбор выражения, **Then** дерево `BinaryExpr(+, 2, BinaryExpr(*, 3, 4))` (умножение глубже сложения).
2. **Given** `(2 + 3) * 4`, **When** разбор, **Then** `BinaryExpr(*, BinaryExpr(+, 2, 3), 4)` — группировка свёрнута в обёрнутое выражение, отдельного `GroupExpr` в дереве НЕТ.
3. **Given** `a - b - c` и `10 / 2 / 5`, **When** разбор, **Then** оба лево-ассоциативны: `((a - b) - c)`, `((10 / 2) / 5)`.
4. **Given** `не x > -10 и x < 0`, **When** разбор, **Then** приоритеты `не` > сравнение > `и` дают `BinaryExpr(и, UnaryExpr(не, BinaryExpr(>, x, UnaryExpr(-, 10))), BinaryExpr(<, x, 0))`; унарный `-` НЕ сворачивается в литерал (`-10` = `UnaryExpr(-, IntLit(10))`).
5. **Given** `данные[i].поле(1, 2,)`, **When** разбор, **Then** левоассоциативная постфикс-цепочка `CallExpr(FieldExpr(IndexExpr(Ident(данные), Ident(i)), поле), [1, 2])`; висящая запятая в списке аргументов допустима.
6. **Given** `[1, "две", истина,]` и `[]`, **When** разбор, **Then** `ListLit` с гетерогенными элементами и висящей запятой; пустой список — `ListLit{}`.
7. **Given** целый литерал на 30 девяток, **When** сборка `IntLit`, **Then** синтаксическая ошибка `целочисленный литерал вне диапазона типа Целое '<лексема>'`; **And** `-9223372036854775808` даёт ту же ошибку на литерале `9223372036854775808` (точный `MinInt64` целым литералом невыразим — ожидаемо).
8. **Given** `1 < x < 10`, **When** разбор, **Then** синтаксическая ошибка `сравнения нельзя сцеплять, используйте 'и': 1 < x и x < 10` (в `Comparison` не более одного `CompOp`).

### User Story 2 — Переменные, присваивание, печать, каркас программы (Priority: P1)

Автор пишет программу из объявлений, присваиваний и вызовов; парсер строит `Program` — список top-level-элементов, завершающийся ровно на `EOF`. `печать(...)` — обычный вызов, без отдельного узла. Lvalue присваивания — только `Ident`; присваивание в поле/индекс — синтаксическая ошибка.

**Why this priority**: каркас программы и базовые statements — минимальный самостоятельный срез: разобрать `examples/hello.ladix` и `examples/арифметика.ladix`. Без него выражения некуда встроить.

**Independent Test**: подать программу из `пусть`/присваивания/`печать(...)` и выражений-statements, сверить `Program.Items` с эталоном; убедиться, что разбор завершается ровно на `EOF` (`Program.EOFPos` зафиксирован).

**Acceptance Scenarios**:

1. **Given** `печать("Привет, Уклад!")`, **When** разбор, **Then** `Program` из одного `ExpressionStmt(CallExpr(Ident(печать), [StringLit]))`; отдельного print-узла нет.
2. **Given** `пусть a = 2 + 3 * 4`, **When** разбор, **Then** `LetStmt{Name: Ident(a), Value: BinaryExpr(+, …)}`.
3. **Given** `x = x + 1` (где `x` ранее объявлен), **When** разбор, **Then** `AssignStmt{Name: Ident(x), Value: …}`; lvalue — `Ident`. (Объявлено ли `x` — НЕ проверяется, это eval-later.)
4. **Given** `x.поле = 5` или `x[i] = 5`, **When** разбор, **Then** синтаксическая ошибка `неверная цель присваивания: слева от '=' допустима только переменная`.
5. **Given** `печать(a, b)` (несколько аргументов), **When** разбор, **Then** `CallExpr` с двумя аргументами.
6. **Given** полная программа `examples/арифметика.ladix`, **When** разбор, **Then** `Program` без синтаксических ошибок, завершение ровно на `EOF`.

### User Story 3 — Условия, циклы, блоки на INDENT/DEDENT (Priority: P2)

Автор пишет `если`/`иначе если`/`иначе`, `пока`, `для` с телами-блоками; парсер строит блоки на виртуальных токенах лексера (`NEWLINE`→`INDENT`→`Statement`+→`DEDENT`). Пустой блок — синтаксическая ошибка. `прервать`/`продолжить` разбираются синтаксически (без проверки «внутри цикла»).

**Why this priority**: управляющие конструкции расширяют ядро до `examples/условие.ladix` и `examples/цикл.ladix`. Зависят от US1 (условия — выражения) и US2 (тело — statements), поэтому P2.

**Independent Test**: подать вложенные `если`/`пока`/`для`, сверить структуру `Block`/`ElseClause`; подать `иначеесли` слитно и пустой блок — получить ожидаемые ошибки.

**Acceptance Scenarios**:

1. **Given** `если C: <блок> иначе если D: <блок> иначе: <блок>`, **When** разбор, **Then** `IfStmt{Cond, Then *Block, Else: ElseClause(иначе если → вложенный)}`; финальный `иначе` — `ElseClause{Body *Block}`.
2. **Given** вложенные блоки (тело `если` внутри тела `для`), **When** разбор, **Then** корректная вложенность `Block`, число уровней соответствует `INDENT`/`DEDENT`.
3. **Given** `для i в диапазон(1, 11):` с телом, **When** разбор, **Then** `ForStmt{Var: Ident(i), Iterable: CallExpr(…), Body *Block}`.
4. **Given** `пока истина:` с телом, содержащим `прервать`, **When** разбор, **Then** `WhileStmt`, в теле `BreakStmt` (легальность вне/внутри цикла НЕ проверяется).
5. **Given** заголовок блока с `:` и переводом строки, но без увеличения отступа (пустой блок), **When** разбор, **Then** синтаксическая ошибка `пустой блок не допускается, добавьте хотя бы один оператор`.
6. **Given** `иначеесли C:` (слитно — один `IDENT`), **When** разбор, **Then** синтаксическая ошибка по стилю §13.4 (`иначеесли` — не ключевое слово, грамматика не допускает два операнда подряд → `ожидалось 'конец строки', получено '<лексема>'`).

### User Story 4 — Функции: объявление, параметры, возврат, рекурсия (Priority: P2)

Автор объявляет функции с позиционными параметрами и телом-блоком; внутри — `вернуть` (с выражением или голый) и рекурсивные вызовы. `FunctionDecl` — только на верхнем уровне; вложенная функция — синтаксическая ошибка с дословным текстом.

**Why this priority**: функции замыкают функциональный чеклист (`examples/функция.ladix`, `examples/факториал.ladix`). Зависят от US1–US3, поэтому P2.

**Independent Test**: разобрать `examples/функция.ladix` и `examples/факториал.ladix` без ошибок; подать вложенную `функция` — получить дословный текст.

**Acceptance Scenarios**:

1. **Given** `функция факториал(n): <тело>`, **When** разбор, **Then** `FunctionDecl{Name: Ident(факториал), Params: [Ident(n)], Body *Block}`.
2. **Given** `функция f(a, b, c,):` (висящая запятая в параметрах), **When** разбор, **Then** три позиционных параметра; висящая запятая допустима.
3. **Given** `вернуть n * факториал(n - 1)`, **When** разбор, **Then** `ReturnStmt{Value: BinaryExpr(…)}`; рекурсивный вызов — обычный `CallExpr`.
4. **Given** голый `вернуть`, **When** разбор, **Then** `ReturnStmt{Value: nil}` (голый возврат; значение `пусто` — eval-later).
5. **Given** `функция` внутри тела другой `функция`, **When** разбор, **Then** синтаксическая ошибка `вложенные функции не поддерживаются в v1`.

---

### User Story 5 — Понятные синтаксические ошибки + восстановление (Priority: P2, пронизывающая)

Автор допускает синтаксические ошибки; парсер регистрирует каждую с точной позицией `(строка, колонка)` 1-based в рунах и дословным текстом в двухстрочном формате `Ошибка в строке N, колонка M:` + описание. Несколько ошибок за прогон собираются в общий `ErrorList` (бюджет ≈20, общий с лексером); panic-mode восстановление синхронизируется по явному множеству токенов, без фантомного каскада и без Go stack trace.

**Why this priority**: понятные позиционные ошибки — ключевая ценность языка (конституция IV/VIII). Пронизывает US1–US4 (каждая даёт свои ошибки), но самостоятельно тестируется набором ошибочных входов, поэтому P2.

**Independent Test**: по одному входу на каждый канонический/репрезентативный текст синтаксической ошибки; сверить категорию, позицию (строка и колонка в рунах) и дословный текст. Отдельно: одна программа с ≥2 ошибками на разных строках → несколько диагностик (по одной на проблему, без фантомов), накопитель не превышает бюджет, без stack trace.

**Acceptance Scenarios**:

1. **Given** вход с ≥2 независимыми синтаксическими ошибками на разных строках, **When** разбор, **Then** возвращено столько же диагностик с верными позициями; после каждой ошибки парсер синхронизируется до безопасной точки и продолжает (нет каскада фантомов).
2. **Given** незакрытый вызов `печать(1, 2` до `EOF`, **When** разбор, **Then** ошибка `ожидалось ')', получено 'конец файла'` (отсутствующий закрыватель — частный случай «ожидался токен»).
3. **Given** `если x` без `:` и тела, **When** разбор, **Then** ошибка `ожидалось ':', получено '<лексема>'`.
4. **Given** ведущее ключевое слово отложенной декларации (`источник`/`метрика`/`процесс`/`когда`) или `значение` на верхнем уровне, **When** разбор, **Then** ошибка `неожиданный токен '<лексема>'` (декларации `источник`/`метрика`/`процесс`/`триггер` — вне scope B).
5. **Given** вход, порождающий больше бюджета ошибок, **When** разбор, **Then** накопитель ограничен ≈20 сообщениями (общий с лексером), без stack trace.

### Edge Cases

- **Завершение на `EOF`**: разбор top-level-цикла останавливается ровно на `EOF`; `Program.EOFPos` берёт позицию токена `EOF`. Любой непотреблённый токен до `EOF` (кроме корректных разделителей) — синтаксическая ошибка.
- **`{`/`}` (LBRACE/RBRACE)**: грамматика подмножества B (и полная грамматика v1) фигурных скобок не использует — лексер эмитит их лишь для баланса при подавлении `NEWLINE`. Встреча `{` в позиции выражения/statement → `неожиданный токен '{'`.
- **Голый `вернуть` против `вернуть E`**: после `вернуть` сразу `NEWLINE` → `ReturnStmt{Value: nil}`; иначе разбирается выражение. (Различение по тому, начинается ли следующий токен с выражения.)
- **`печать` / `длина` / `диапазон` / `добавить` / `сумма`**: обычные `Ident` в позиции `Callee`; встроенность — eval-later (парсер не резолвит).
- **Имена периодов `ежедневно`…`ежегодно`**: обычные `Ident` (резолв — eval).
- **Постфикс по результату вызова**: `f()[0].g` — корректная левоассоциативная цепочка; `IndexExpr`/`FieldExpr` навешиваются на результат предыдущего постфикса.
- **`-X` на границе int64**: знак не сворачивается; `UnaryExpr(-, IntLit("X"))`. Диапазон int64 проверяется на самом `IntLit`, поэтому `MinInt64` литералом невыразим (ожидаемо, `SPEC §4/§12`).
- **`DurationLit` вне диапазона**: в фиче 002 НЕ проверяется (backlog `float-overflow-spec-gap`); `DurationLit` несёт величину как лексему, парсер на ней не падает.
- **Декларативные примеры `examples/выручка.ladix`, `examples/онбординг.ladix`**: содержат top-level декларации (`источник`/`метрика`/`процесс`/`когда`) вне scope B → ожидаемо дают `неожиданный токен`; в набор parse-clean фичи 002 НЕ входят.
- **`examples/ошибка.ladix`**: парсится БЕЗ синтаксических ошибок — его единственный дефект (деление на ноль) — **runtime**, не синтаксис.

## Requirements *(mandatory)*

### Functional Requirements — пакет `ast`

- **FR-001**: Пакет `ast` ОБЯЗАН определить локальный тип `Position{Line, Col int}` (оба 1-based, в рунах), НЕ импортируя `errors` (сохранение листовости `ast`, D1, ARCH §4.1, конституция IV/VII). ОБЯЗАН предоставить корневой интерфейс `Node` с `Pos() Position`, встраиваемую базу для `Pos()` и маркер-подынтерфейсы `Statement`/`Expression`/`Decl`/`TopLevelItem` (sum-type через интерфейсы).
- **FR-002**: Пакет `ast` ОБЯЗАН определить все узлы подмножества B (ARCH §4.2–§4.8): `Program{Items []TopLevelItem; EOFPos Position}`; statements `LetStmt`, `AssignStmt`, `ExpressionStmt`, `IfStmt`(+`ElseClause`-union), `WhileStmt`, `ForStmt`, `ReturnStmt`, `BreakStmt`, `ContinueStmt`; декларация `FunctionDecl{Name Ident; Params []Ident; Body *Block}`; выражения `BinaryExpr`, `UnaryExpr`, `CallExpr`, `IndexExpr`, `FieldExpr`; литералы/Primary `IntLit`, `FloatLit`, `StringLit`, `BoolLit`, `NoneLit`, `DurationLit`, `ListLit`, `Ident`; структурный `Block{Stmts []Statement}`.
- **FR-003**: `ast` ОБЯЗАН зарезервировать узлы шага процесса и запуска процесса (ARCH §4.6/§4.7): варианты `StepAction` — `AssignAction{Name Ident; Value Expression}`, `CallAction{Name Ident; Args []Expression}`, `NotifyAction{Name Ident; Args []Expression}` (реализуют `Statement`); `RunProcessExpr{Process Ident; Args []Expression}` (реализует `Expression`/Primary). Семантика «только в шаге процесса» — eval-later (узлы только определены и строятся, не валидируются).
- **FR-004**: `BinOp` ОБЯЗАН быть единым enum всех бинарных операторов (`или` `и` `+` `-` `*` `/` `//` `%` `==` `!=` `<` `<=` `>` `>=`); `CompOp` ОБЯЗАН быть именованным подмножеством `BinOp` из шести сравнений (`==` `!=` `<` `<=` `>` `>=`), отбираемым из `BinOp` без дублирования констант (D3, ARCH §4.7, единый источник истины операторов). `UnOp` — enum унарных (`не`, унарный `-`).
- **FR-005**: Конвенция `Pos()` узла ОБЯЗАНА быть (D4, ARCH §4.1): `BinaryExpr.Pos`/`UnaryExpr.Pos` = токен **оператора**; `CallExpr.Pos` = позиция `Callee`; `IndexExpr.Pos`/`FieldExpr.Pos` = позиция `Target`; литералы и `Ident` — свой токен; `LetStmt`/`IfStmt`/`WhileStmt`/`ForStmt`/`ReturnStmt`/… — ведущий ключевой токен; `FunctionDecl` — токен `функция`; `Block` — позиция `INDENT`/первого оператора. Два statement без ведущего ключевого слова — явные исключения: `AssignStmt.Pos` = позиция lvalue (токен `Name`), `ExpressionStmt.Pos` = `Expr.Pos()`.
- **FR-006**: `GroupExpr` отдельным узлом НЕ материализуется: `( Expression )` сворачивается в обёрнутое выражение (D5, ARCH §4.7). Приоритет, заданный скобками, отражён структурой дерева, а не отдельным узлом.

### Functional Requirements — парсер: программа и statements

- **FR-007**: Парсер ОБЯЗАН потреблять поток токенов лексера (контракт `token-stream.md`) и строить `Program` из `TopLevelItem` до токена `EOF` включительно; цикл верхнего уровня завершается ровно на `EOF`, `EOFPos` фиксируется. В scope B `TopLevelItem` = `Statement | FunctionDecl`.
- **FR-008**: `LetStmt` ОБЯЗАН разбираться как `пусть Ident "=" Expression NEWLINE`; отсутствие `Ident`, `=` или `NEWLINE` на ожидаемом месте → `ожидалось '<X>', получено '<лексема>'`.
- **FR-009**: Statement, начинающийся с выражения, ОБЯЗАН разбираться так: разобрать выражение; если следующий токен `=` — это `AssignStmt`, причём lvalue ОБЯЗАН быть `Ident`, иначе ошибка `неверная цель присваивания: слева от '=' допустима только переменная`; иначе — `ExpressionStmt`, завершаемый `NEWLINE`.
- **FR-010**: `печать(...)` ОБЯЗАН разбираться как обычный `CallExpr` (`Callee = Ident(печать)`); отдельного print-узла НЕТ.
- **FR-011**: ОБЯЗАНЫ разбираться `IfStmt` (`если Expression ":" Block ElseClause?`), `ElseClause` (`иначе ":" Block` | `иначе если Expression ":" Block ElseClause?`), `WhileStmt` (`пока Expression ":" Block`), `ForStmt` (`для Ident "в" Expression ":" Block`).
- **FR-012**: ОБЯЗАНЫ разбираться `ReturnStmt` (`вернуть Expression? NEWLINE`; без выражения → `Value = nil`), `BreakStmt` (`прервать NEWLINE`), `ContinueStmt` (`продолжить NEWLINE`) — синтаксически, БЕЗ проверки контекста (legality `вернуть`/`прервать`/`продолжить` — eval-later).
- **FR-013**: `Block` ОБЯЗАН строиться на виртуальных токенах лексера: `NEWLINE` → `INDENT` → `Statement`+ → `DEDENT` (минимум один statement). Отсутствие `INDENT` после `:`+`NEWLINE` (пустой блок) → `пустой блок не допускается, добавьте хотя бы один оператор`.
- **FR-014**: `FunctionDecl` (`функция Ident "(" ParamList? ")" ":" Block`) ОБЯЗАН разбираться ТОЛЬКО на верхнем уровне; позиционные параметры (`ParamList` с висящей запятой); вложенная `функция` (в теле функции, шага, любого `Block`) → `вложенные функции не поддерживаются в v1`.
- **FR-015**: `StepAction` (`присвоить`/`вызвать`/`уведомить`, ARCH §4.6, grammar §7) ОБЯЗАН разбираться и резервироваться как `Statement` (доступен и внутри `если`/`пока`/`для`); семантический гард «только в шаге процесса» — eval-later, парсер его НЕ проверяет.
- **FR-016**: `RunProcessExpr` (`запустить процесс Ident ("(" ArgList? ")")?`, ARCH §4.7, grammar §9) ОБЯЗАН разбираться и резервироваться как Primary; скобки — часть самого узла, НЕ постфикс-вызов по результату (при ведущем `запустить` альтернатива выбирается сразу, неоднозначности с Postfix нет).
- **FR-017**: Ведущие ключевые слова отложенных деклараций на верхнем уровне (`источник`/`метрика`/`процесс`/`когда`) и `значение` ОБЯЗАНЫ давать `неожиданный токен '<лексема>'` (декларации `источник`/`метрика`/`процесс`/`триггер` — вне scope B, отдельный будущий top-level-диспетчер; декларация-триггер вводится ключевым словом `когда`, отдельного слова `триггер` в языке нет — это лишь название категории).

### Functional Requirements — парсер: выражения

- **FR-018**: Парсер ОБЯЗАН реализовать полный каскад приоритетов `SPEC §5` / grammar §9 (низший→высший): `LogicOr → LogicAnd → LogicNot → Comparison → Additive → Multiplicative → Unary → Postfix → Primary`. Все бинарные операторы — **лево-ассоциативны**; унарные `не`/`-` — префиксные, право-ассоциативные. Контрольные инварианты: `2 + 3 * 4` → `BinaryExpr(+, 2, BinaryExpr(*, 3, 4))`; `a - b - c` → `BinaryExpr(-, BinaryExpr(-, a, b), c)`.
- **FR-019**: `Comparison` ОБЯЗАН допускать НЕ БОЛЕЕ одного `CompOp` (`Additive (CompOp Additive)?`); второй подряд `CompOp` → `сравнения нельзя сцеплять, используйте 'и': 1 < x и x < 10` (цепочечные сравнения запрещены).
- **FR-020**: Постфикс-цепочка ОБЯЗАНА разбираться лево-ассоциативно: вызов `"(" ArgList? ")"` → `CallExpr`, индекс `"[" Expression "]"` → `IndexExpr`, доступ `"." Ident` → `FieldExpr`; навешиваются на результат предыдущего звена. `ArgList` допускает висящую запятую.
- **FR-021**: ОБЯЗАНЫ разбираться все литералы/Primary: `IntLit` (см. FR-022), `FloatLit` (предразобранный float64 из токена), `StringLit` (развёрнутая строка из токена), `BoolLit` (`истина`/`ложь`), `NoneLit` (`пусто`), `DurationLit` (величина-лексема + единица из токена; диапазон НЕ проверяется), `ListLit` (`"[" (Expression ("," Expression)* ","?)? "]"` — висящая запятая, гетерогенность, `[]`), `Ident`.
- **FR-022**: При сборке `IntLit` парсер ОБЯЗАН проверить диапазон int64 по нормализованной цифровой строке токена `INT` (D2): значение вне диапазона → синтаксическая (статическая, **накапливаемая**) ошибка `целочисленный литерал вне диапазона типа Целое '<лексема>'`. Знак НЕ сворачивается в литерал (`-X` остаётся `UnaryExpr(-, IntLit(X))`), поэтому точный `MinInt64` целым литералом невыразим — это ожидаемо, не баг.

### Functional Requirements — контракт ошибок и восстановление

- **FR-023**: ОБЯЗАНА вводиться категория **Синтаксическая** (`SPEC §13.1`): тип `ParseError` в пакете `errors` с встраиваемой `errors.Position` и русским описанием БЕЗ заголовка; текстовое представление ОБЯЗАНО давать канонический двухстрочный вид `Ошибка в строке N, колонка M:` + перевод строки + описание (`N`, `M` 1-based, колонка в рунах). `ParseError` ОБЯЗАН разворачиваться через `errors.As` и складываться в тот же агрегат/`ErrorList`, что и лексические ошибки. Пакет `errors` НЕ изменяется сверх добавления типа синтаксической ошибки.
- **FR-024**: Три канонических текста ОБЯЗАНЫ воспроизводиться ДОСЛОВНО из `SPEC §13.4`: `сравнения нельзя сцеплять, используйте 'и': 1 < x и x < 10`; `вложенные функции не поддерживаются в v1`; `целочисленный литерал вне диапазона типа Целое '<лексема>'`. Прочие синтаксические тексты сформулированы по стилю §13.4 и зафиксированы этой спекой как эталоны для golden-тестов (см. «Контракт синтаксических ошибок» ниже).
- **FR-025**: Обнаружив синтаксическую ошибку, парсер ОБЯЗАН зарегистрировать её в общий `ErrorList` и перейти в panic-mode: подавлять регистрацию НОВЫХ ошибок и отбрасывать токены до ближайшего токена из явного **множества синхро-токенов** (см. ниже), затем продолжить разбор. Накопитель ограничен ≈20 сообщениями (мягкий предел, **общий с лексером**, `SPEC §13.2`). Каскад фантомных ошибок ЗАПРЕЩЁН; Go stack trace в выводе ЗАПРЕЩЁН.
- **FR-026**: Множество синхро-токенов panic-mode ОБЯЗАНО быть явным (перечислено ниже в «Множество синхро-токенов»), а не описано качественно.

### Quality / Constitution Gates

- **FR-027**: Код ОБЯЗАН проходить `go build ./...` и `go vet ./...` без замечаний и быть отформатирован `gofmt` без диффа (конституция I).
- **FR-028**: Парсер и пакет `ast` разрабатываются **tests-first**: табличные тесты «вход → ожидаемый AST» (включая инвариант приоритетов) и golden-тесты синтаксических ошибок «вход → строка/колонка/текст» — часть каждой задачи (конституция VI).
- **FR-029**: Без изменяемого пакет-уровневого состояния: парсер — явно создаваемое значение, получающее поток токенов через параметры; helper-конвертер `errors.Position → ast.Position` живёт в пакете `parser` (НЕ в `ast` — иначе теряется листовость; обратное направление парсеру не требуется), `ast` пакет `errors` не импортирует (конституция V, D1).

### Out of Scope (границы)

- **НЕ** интерпретация/исполнение (eval), **НЕ** вычисление выражений, **НЕ** резолв имён/типов — фича 003.
- **НЕ** декларации верхнего уровня `источник`/`метрика`/`процесс`/`триггер` (`когда`) — отдельная будущая фича парсера ПОСЛЕ eval (отдельный top-level-диспетчер, не трогает ядро `parsePrimary`/`parseStatement`). Встреча их ведущих ключевых слов (и `значение`) на верхнем уровне → `неожиданный токен`.
- **НЕ** семантический анализ: области видимости, типы, «`вернуть` только в функции», «`присвоить`/`вызвать`/`уведомить` только в шаге», легальность `прервать`/`продолжить` вне цикла, дубли объявлений, арность — eval-later.
- **НЕ** проверка диапазона `DurationLit` (backlog `float-overflow-spec-gap`); **НЕ** свёртка знака на целом литерале.
- **НЕ** изменение лексера (фича 001) и пакета `errors` сверх добавления типа синтаксической ошибки.

### Key Entities

- **`ast.Position`**: позиция узла — строка и колонка, 1-based, в рунах; локальна для `ast` (дублирует, не разделяет, `errors.Position`).
- **`ast.Node` и подынтерфейсы**: `Node` (`Pos()`), `Statement`/`Expression`/`Decl`/`TopLevelItem` — sum-type через маркер-методы.
- **Узлы AST подмножества B**: `Program`, statements, `FunctionDecl`, выражения, литералы, `Block`, плюс зарезервированные `StepAction`/`RunProcessExpr`.
- **`BinOp`/`CompOp`/`UnOp`**: enum операторов; `CompOp` — подмножество `BinOp`.
- **`Parser`**: разборщик; принимает поток токенов, выдаёт `Program` (best-effort даже при ошибках) и собранные ошибки.
- **`ParseError`**: синтаксическая ошибка — `Position` + русское описание; даёт канонический двухстрочный текст; пригодна к `errors.As`.
- **`ErrorList` / агрегат**: общий накопитель лексических и синтаксических ошибок (бюджет ≈20), обходимый стандартной развёрткой.
- **Множество синхро-токенов**: явный набор токенов-точек синхронизации panic-mode.

## Контракт синтаксических ошибок (эталоны для golden-тестов)

Тексты — после строки заголовка `Ошибка в строке N, колонка M:`; русские, по стилю `SPEC §13.4`; `<лексема>` подставляется реальной лексемой токена; `<X>` — ожидаемой лексемой/именем. Виртуальные токены в текстах отображаются псевдо-лексемами: `NEWLINE` → `конец строки`, `INDENT` → `увеличение отступа`, `DEDENT` → `конец блока`, `EOF` → `конец файла`.

| Код | Текст описания | Триггер |
|---|---|---|
| **SE-CHAIN** (канон) | `сравнения нельзя сцеплять, используйте 'и': 1 < x и x < 10` | второй `CompOp` в `Comparison` (FR-019) |
| **SE-NESTED-FN** (канон) | `вложенные функции не поддерживаются в v1` | `функция` не на верхнем уровне (FR-014) |
| **SE-INT-RANGE** (канон) | `целочисленный литерал вне диапазона типа Целое '<лексема>'` | `IntLit` вне int64 (FR-022) |
| **SE-EXPECTED** | `ожидалось '<X>', получено '<лексема>'` | на месте обязательного токена другой: нет `:`/`)`/`]`/`=`/`в`, нет имени после `.`, нет `NEWLINE`-завершения, незакрытая скобка на `EOF` |
| **SE-UNEXPECTED** | `неожиданный токен '<лексема>'` | ведущий токен не начинает допустимый элемент/выражение (вкл. `источник`/`метрика`/`процесс`/`когда`/`значение`/`{` на верхнем уровне, FR-017) |
| **SE-EMPTY-BLOCK** | `пустой блок не допускается, добавьте хотя бы один оператор` | после `:`+`NEWLINE` нет `INDENT` с ≥1 оператором (FR-013) |
| **SE-ASSIGN-TARGET** | `неверная цель присваивания: слева от '=' допустима только переменная` | lvalue не `Ident` (`x.f = …`, `x[i] = …`, FR-009) |

> Эталонные тексты SE-EXPECTED/SE-UNEXPECTED/SE-EMPTY-BLOCK/SE-ASSIGN-TARGET фиксируются этой спецификацией (бриф явно поручил сформулировать их по стилю §13.4 — это не молчаливое доопределение, см. конституция IX). Любое уточнение формулировок — через `/speckit-clarify` до реализации.

## Множество синхро-токенов panic-mode (явный список)

При восстановлении парсер отбрасывает токены до ближайшего токена из набора, затем возобновляет разбор. Имена видов токенов — в контракте потока токенов 001 (`specs/001-lexer-tokens/contracts/token-stream.md`).

| Группа | Токены | При синхронизации |
|---|---|---|
| Структурные | `NEWLINE`, `DEDENT`, `EOF` | `NEWLINE`/`DEDENT` **потребляются**; на `EOF` разбор завершается |
| Ведущие ключевые слова statements | `пусть`, `если`, `пока`, `для`, `вернуть`, `прервать`, `продолжить` | НЕ потребляются (разбор начинается с них) |
| Декларация scope B | `функция` | НЕ потребляется |
| Зарезервированные step-action | `присвоить`, `вызвать`, `уведомить` | НЕ потребляются |
| Отложенные top-level декларации | `источник`, `метрика`, `процесс`, `когда` | НЕ потребляются (сами дают SE-UNEXPECTED) |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Примеры императивного ядра языка — `examples/{hello,арифметика,условие,цикл,функция,факториал}.ladix` — парсятся с **нулём** синтаксических ошибок; `examples/ошибка.ladix` парсится с **нулём** синтаксических ошибок (его дефект — runtime). Декларативные примеры (`выручка`, `онбординг`) в набор не входят.
- **SC-002**: Инвариант приоритетов `2 + 3 * 4` → `BinaryExpr(+, 2, BinaryExpr(*, 3, 4))` и лево-ассоциативность `a - b - c` → `((a - b) - c)` подтверждены табличными тестами; вся таблица выражений (литералы, унарные/бинарные, постфикс, список, группировка) строит ожидаемое дерево.
- **SC-003**: Каждый из 7 кодов синтаксических ошибок (SE-CHAIN, SE-NESTED-FN, SE-INT-RANGE, SE-EXPECTED, SE-UNEXPECTED, SE-EMPTY-BLOCK, SE-ASSIGN-TARGET) воспроизводится ДОСЛОВНО в двухстрочном формате с корректной позицией `(строка, колонка)` 1-based в рунах — по одному проверенному golden-кейсу на код (три канонических — байт-в-байт по `SPEC §13.4`).
- **SC-004**: Каждый узел AST несёт корректную `Position` по конвенции `Pos()` (FR-005): `BinaryExpr` — на колонке оператора, `CallExpr` — на `Callee`, `IndexExpr`/`FieldExpr` — на `Target`, листья — на своём токене.
- **SC-005**: Программа с ≥2 синтаксическими ошибками на разных строках даёт несколько собранных диагностик (по одной на проблему, без фантомного каскада); накопитель не превышает ≈20 (общий бюджет с лексером); в выводе нет Go stack trace.
- **SC-006**: Разбор завершается ровно на `EOF` для валидных программ; `Program.EOFPos` соответствует позиции токена `EOF`; непотреблённый «хвост» до `EOF` диагностируется.
- **SC-007**: Сборка и статанализ чистые: `go build ./...` и `go vet ./...` без замечаний, код `gofmt`-форматирован; все табличные и golden-тесты парсера и `ast` зелёные.

## Assumptions

- **A1 — Вход стабилен**: парсер опирается на контракт потока токенов `001-lexer-tokens/contracts/token-stream.md` (ровно один `EOF`; внутри незакрытых `(`/`[`/`{` нет `NEWLINE`/`INDENT`/`DEDENT`; число `DEDENT` = числу снятых уровней; каждый токен несёт `Type`/`Lexeme`/`Pos`; `INT` несёт цифровую строку, диапазон — у парсера). Best-effort поток лексера при лексических ошибках парсер принимает как есть.
- **A2 — Размещение `Position`**: `ast` несёт локальную `Position` (D1, ARCH §4.1, конституция IV), `errors`/токены — свою; конвертер `errors.Position → ast.Position` — в пакете `parser` (обратное направление не требуется). Тип дублируется, не разделяется.
- **A3 — Имена типов**: публичные Go-имена английские и идиоматичные (`ParseError`, `Parser`, узлы `IntLit`/`BinaryExpr`/…) по конституции III; тексты пользовательских сообщений — русские (конституция VIII).
- **A4 — Бюджет накопителя**: «≈20» — мягкий верхний предел общей (лексика+синтаксис) доли; точное число — деталь реализации (как в фиче 001).
- **A5 — Предразобранные значения литералов**: `FloatLit`/`StringLit`/`BoolLit`/`DurationLit` берут готовое значение/единицу из `Token.Value` (контракт C-3 фичи 001); `IntLit` собирает int64 сам из `Token.Lexeme` (цифровая строка) с проверкой диапазона.
- **A6 — Go 1.22+**, единый модуль, без CGO; новые пакеты `internal/ast` и `internal/parser`; пакет `errors` дополняется лишь типом `ParseError` (и его интеграцией в существующий агрегат).

## Зафиксированные решения (НЕ переоткрывать)

> Перенесены из брифа как контекст реализации; ни одно не блокирует разбор.

- **D1 — `Position` ast-local**: узлы `ast` держат свой `Position`, не импортируют `errors`; конвертер — в `parser` (FR-001/FR-029, A2).
- **D2 — Диапазон `Целое` проверяет парсер**: лексер несёт `INT` цифровой строкой; парсер при сборке `IntLit` проверяет int64 и выдаёт синтаксическую накапливаемую ошибку; `MinInt64` литералом невыразим — ожидаемо (FR-022).
- **D3 — Единый `BinOp`, `CompOp` = подмножество**: один enum операторов; шесть сравнений — отбор из `BinOp`, без дублирования; на `CompOp` сошлётся будущий `MetricTrigger` (FR-004).
- **D4 — Конвенция `Pos()` узла**: оператор для `BinaryExpr`/`UnaryExpr`, `Callee` для `CallExpr`, `Target` для `IndexExpr`/`FieldExpr`, свой токен для листьев (FR-005).
- **D5 — `GroupExpr` сворачивается**: `(...)` не материализуется отдельным узлом (FR-006).
- **D6 — panic-mode лексера уже есть** (фича 001); парсер добавляет СВОЁ восстановление поверх потока токенов (FR-025/FR-026).
