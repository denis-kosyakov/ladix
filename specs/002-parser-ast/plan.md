# Implementation Plan: Парсер + AST Ladix (ручной recursive descent, подмножество B)

**Branch**: `002-parser-ast` | **Date**: 2026-06-02 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/002-parser-ast/spec.md`

## Summary

Реализовать **второй слой** компилятора Ladix: пакет `internal/ast` (узлы дерева) и пакет
`internal/parser` (ручной recursive-descent разборщик). Парсер потребляет поток токенов лексера
(фича 001, контракт `token-stream.md`) и строит AST императивного ядра языка — **подмножество B**:
выражения с полным каскадом приоритетов, statements (`пусть`/присваивание/выражение/`если`/`пока`/`для`/
`вернуть`/`прервать`/`продолжить`), `FunctionDecl`, блоки на `INDENT`/`DEDENT`, плюс зарезервированные
узлы `StepAction`/`RunProcessExpr`. Это **НЕ** интерпретатор — eval будет фичей 003. Дополнительно:
новая категория ошибки **Синтаксическая** (`ParseError` в `internal/errors`), накопление в общий
`ErrorList` (бюджет ≈20) и panic-mode восстановление с явным множеством синхро-токенов.

**Технический подход**: ручной recursive descent (без генераторов парсеров и комбинаторов —
конституция II), каскад из одной функции на уровень приоритета (`LogicOr → … → Primary`) с
лево-ассоциативностью через цикл; постфикс-цепочка (вызов/индекс/`.поле`) — отдельным уровнем;
блоки строятся на виртуальных токенах лексера. Диапазон int64 проверяется **парсером** при сборке
`IntLit` (D2, `strconv.ParseInt`). Узлы `ast` несут **локальную** `Position` (D1 решён здесь — в пользу
ast-local; конвертер `errors.Position → ast.Position` живёт в `parser`). Граф зависимостей:
`parser → {ast, errors, lexer}`; `ast` — листовой (импортирует только себя). `ParseError` интегрируется
в существующий `errors.ErrorList` без правок агрегата (`Add(error)` уже принимает любой `error`).

Структура поставки следует приоритетам user stories: **P1** выражения (US1) + каркас/statements (US2) →
**P2** условия/циклы/блоки (US3) + функции (US4) + диагностика/восстановление (US5, пронизывающая).

## Technical Context

**Language/Version**: Go **1.22+**, единый модуль `github.com/denis-kosyakov/ladix` (корень — `src/`),
без CGO (конституция I).

**Primary Dependencies**: только стандартная библиотека Go (`strconv` для `ParseInt` диапазона int64,
`fmt`, `errors`, при необходимости `strings`). Внешних зависимостей парсер **не вводит**. Генераторы
парсеров/комбинаторы (participle, goyacc, ANTLR) и regex для разбора — **ЗАПРЕЩЕНЫ** (конституция II).

**Storage**: N/A (парсер — чистая трансформация `[]lexer.Token` → `*ast.Program` + `*errors.ErrorList`).

**Testing**: `go test` с **табличными** тестами «вход → ожидаемый AST» и **golden**-тестами
синтаксических ошибок «вход → (строка, колонка, текст)», co-located `_test.go` рядом с пакетами
(`internal/ast`, `internal/parser`); `testify/require` ДОПУСКАЕТСЯ точечно (конституция VI). Tests-first:
тест на каждое правило грамматики подмножества B и на каждый из 7 кодов синтаксических ошибок.

**Target Platform**: кросс-платформенный статический бинарник (Windows/macOS/Linux одной командой
`go build`); парсер платформонезависим.

**Project Type**: компонент компилятора/интерпретатора (библиотечные пакеты внутри `internal/`).

**Performance Goals**: явных числовых целей нет; ориентир — линейный однопроходный разбор по слайсу
токенов без бэктрекинга (recursive descent с одним токеном предпросмотра; постфикс/каскад — без
переразбора). Масштаб входов адекватен DSL.

**Constraints**:
- Позиции `(строка, колонка)` 1-based, в **рунах**; `ast.Position` — **локальный** тип `ast`, не
  импортирующий `errors` (D1, конституция IV/VII).
- Без изменяемого пакет-уровневого состояния; `Parser` создаётся явно (конституция V, FR-029).
- Все пользовательские тексты — **на русском**; три канонических текста — дословно из `SPEC §13.4`
  (конституция VIII).
- В штатных путях паника ЗАПРЕЩЕНА; синтаксические ошибки — накапливаемые значения (конституция III).
- Разбор валидной программы завершается ровно на `EOF` (FR-007).

**Scale/Scope**: два новых пакета — `internal/ast` (узлы + `BinOp`/`CompOp`/`UnOp`) и `internal/parser`
(каскад + statements + восстановление) — плюс одно дополнение к `internal/errors` (`ParseError`).
~30 типов узлов AST, 14 бинарных операторов (`CompOp` = подмножество из 6), 7 кодов синтаксических
ошибок, множество синхро-токенов из 18 видов (3 структурных + 7 ведущих statement + 1 `функция`
+ 3 step-action + 4 отложенных декларации).

## Guardrails — контракт реализации (нормативно для tasks/implement)

План фиксирует инварианты как **контракт**, чтобы код не дрейфовал. Каждый нормативен (нарушение =
регресс, ловится тестом и/или ревью):

1. **`ast` — листовой** (D1, решён здесь): пакет `ast` определяет СВОЙ `Position{Line, Col int}` и НЕ
   импортирует `errors`. Helper-конвертер `errors.Position → ast.Position` живёт в пакете `parser`
   (НЕ в `ast`). Тип дублируется, не разделяется. (FR-001/FR-029)
2. **Диапазон int64 проверяет парсер** (D2): при сборке `IntLit` парсер конвертирует нормализованную
   цифровую строку токена `INT` (`strconv.ParseInt(lexeme, 10, 64)`); при выходе → синтаксическая
   **накапливаемая** ошибка `целочисленный литерал вне диапазона типа Целое '<лексема>'`. Знак НЕ
   сворачивается (`-X` = `UnaryExpr(-, IntLit(X))`), поэтому `MinInt64` литералом невыразим — ожидаемо.
   `DurationLit` на диапазон **НЕ** проверяется (backlog `float-overflow-spec-gap`). (FR-022)
3. **Единый `BinOp`, `CompOp` = подмножество** (D3): один enum всех 14 бинарных операторов; `CompOp` —
   именованное подмножество из 6 сравнений, отбираемое из `BinOp` БЕЗ дублирования констант; `UnOp` —
   отдельный enum (`не`, унарный `-`). На `CompOp` сошлётся будущий `MetricTrigger`. (FR-004)
4. **Конвенция `Pos()` узла** (D4): `BinaryExpr.Pos`/`UnaryExpr.Pos` = токен **оператора**; `CallExpr.Pos`
   = `Callee`; `IndexExpr.Pos`/`FieldExpr.Pos` = `Target`; листья/`Ident` — свой токен; statements/
   `FunctionDecl` — ведущий ключевой токен; `Block` — `INDENT`/первый оператор. (FR-005)
5. **`GroupExpr` сворачивается** (D5): `( E )` возвращает обёрнутое выражение; отдельного узла в дереве
   НЕТ. Приоритет скобок отражён структурой. (FR-006)
6. **Зарезервированные узлы парсятся, но НЕ валидируются**: `StepAction` (`AssignAction`/`CallAction`/
   `NotifyAction`) как `Statement` и `RunProcessExpr` как Primary СТРОЯТСЯ парсером; семантика «только в
   шаге процесса» — eval-later (парсер её НЕ проверяет). Причина включить сейчас — они вшиты в
   центральные `parseStatement`/`parsePrimary`; зарезервировав их, будущая фича деклараций не правит
   оттестированное ядро. (FR-003/FR-015/FR-016)
7. **Парсер НЕ делает семантику**: НЕ проверяет области видимости, типы, объявленность/дубли,
   арность, «`вернуть` только в функции», «`присвоить`/`вызвать`/`уведомить` только в шаге»,
   легальность `прервать`/`продолжить` вне цикла. ЕДИНСТВЕННАЯ структурная проверка, которую парсер
   делает, — **вложенная `функция`** (это синтаксис по grammar §4 → `вложенные функции не
   поддерживаются в v1`). Всё прочее — eval-later. (FR-012/FR-014, Out of Scope)
8. **`ParseError` — только добавление к `errors`**: тип `ParseError{Pos errors.Position; Msg string}` с
   `Error()` → тот же двухстрочный канон, что у `LexError`; складывается в **тот же** `errors.ErrorList`
   (агрегат `Add(error)`/`Unwrap()[]error` уже это поддерживают — правок `aggregate.go` НЕ требуется).
   Пакет `errors` НЕ меняется сверх нового файла `parserror.go` (+ тест). (FR-023)
9. **`Parser` — чистое значение**: `[]lexer.Token → (*ast.Program, *errors.ErrorList)`; конструктор
   явный, токены и (опц.) общий `*ErrorList` через параметры; без пакет-уровневого состояния; ручной
   recursive descent (конституция II/V, FR-029).
10. **Panic-mode восстановление** (D6, поверх лексерного): обнаружив ошибку, парсер регистрирует её в
    `ErrorList` и синхронизируется — отбрасывает токены до ближайшего токена из **явного множества
    синхро-токенов** (см. spec.md «Множество синхро-токенов»), подавляя регистрацию НОВЫХ ошибок до
    точки синхронизации. Структурные `NEWLINE`/`DEDENT` при синхронизации потребляются; ведущие
    ключевые слова — нет. Бюджет ≈20 (общий с лексером). Каскад фантомов и Go stack trace — ЗАПРЕЩЕНЫ.
    (FR-025/FR-026)
11. **Парсер работает БЕЗУСЛОВНО на best-effort потоке** лексера: он не знает о лексических ошибках и не
    гейтит разбор по ним (стадийное гейтирование лексика→синтаксис — забота будущего CLI-пайплайна, не
    парсера 002). Любой каскад от лексических «дыр» в потоке ограничен общим бюджетом и panic-mode. (D-R7)
12. **Границы**: ТОЛЬКО `internal/ast` + `internal/parser` + `ParseError`. **НЕ** eval/исполнение, **НЕ**
    резолв имён/типов, **НЕ** декларации `источник`/`метрика`/`процесс`/`триггер` (их ведущие ключевые
    слова и `значение` на верхнем уровне → `неожиданный токен`), **НЕ** изменение лексера. (Out of Scope)
13. **Набор parse-clean** (SC-001): `examples/{hello,арифметика,условие,цикл,функция,факториал}.ladix`
    и `examples/ошибка.ladix` парсятся с НУЛЁМ синтаксических ошибок. Декларативные `выручка`/`онбординг`
    в набор НЕ входят (ожидаемо дают `неожиданный токен`).

**Structure Decision**:
- **Два новых пакета** `internal/ast` (листовой) и `internal/parser`; `ast` НЕ импортирует `errors`
  (листовость, D1/S3). Граф: `parser → ast`, `parser → errors`, `parser → lexer`; циклов нет.
- **`errors` дополняется одним файлом** `parserror.go` — агрегат `ErrorList` уже полиморфен по `error`,
  правок не требует (guardrail 8).
- **Тесты co-located** (`*_test.go` рядом с кодом), идиома Go + конституция VI (S2, унаследовано).
- **Разбиение файлов** по зонам ответственности — рекомендательное (навигация); фактическое число
  файлов — деталь реализации, лишь бы пакеты оставались без пакет-уровневого изменяемого состояния.

## Phasing — порядок поставки по приоритетам User Stories

Фазы упорядочены по приоритетам US (spec.md). Каждая — самостоятельно тестируема (tests-first). US5
(диагностика+восстановление) — **пронизывающая**: каждая фаза эмитит свои ошибки, финальная фаза
закрывает полный golden-каталог и многоошибочное накопление.

- **Фаза 0 (каркас, до US)**: пакет `ast` — `Position`, интерфейсы `Node`/`Statement`/`Expression`/
  `Decl`/`TopLevelItem`, `base`, enum'ы `BinOp`/`CompOp`/`UnOp` (+`String()`); пакет `parser` — `Parser`
  (курсор по `[]Token`, `peek`/`advance`/`expect`, регистрация в `ErrorList`, конвертер `pos.go`);
  `errors.ParseError` (+тест двухстрочного формата). Гейт: пустой ввод → `Program{Items:[], EOFPos}`;
  `ParseError.Error()` даёт канон.
- **Фаза P1 — выражения + каркас/statements (US1+US2, MVP)**: каскад приоритетов (`parse_expr.go`),
  все литералы (`IntLit` с диапазон-проверкой), постфикс-цепочка, список, свёртка группировки; цепочечные
  сравнения → SE-CHAIN; `Program`/`LetStmt`/`AssignStmt`(lvalue=Ident)/`ExpressionStmt`; `печать(...)` —
  обычный `CallExpr`. Гейт: инвариант `2 + 3 * 4` (SC-002), `examples/{hello,арифметика}.ladix` parse-clean,
  завершение на `EOF` (SC-006), SE-INT-RANGE/SE-ASSIGN-TARGET (SC-003).
- **Фаза P2a — условия/циклы/блоки (US3)**: `Block` на `NEWLINE`/`INDENT`/`Statement`+/`DEDENT`; пустой
  блок → SE-EMPTY-BLOCK; `IfStmt`/`ElseClause`/`WhileStmt`/`ForStmt`; `ReturnStmt`/`BreakStmt`/
  `ContinueStmt` синтаксически. Гейт: `examples/{условие,цикл}.ladix` parse-clean; вложенные блоки;
  `иначеесли` слитно → ошибка (SC-001/SC-003).
- **Фаза P2b — функции + зарезервированные узлы (US4)**: `FunctionDecl` (top-level; вложенная → SE-NESTED-FN);
  позиционные параметры; зарезервированные `StepAction`/`RunProcessExpr` парсятся. Гейт:
  `examples/{функция,факториал}.ladix` parse-clean (SC-001); SE-NESTED-FN дословно (SC-003).
- **Фаза P2c — диагностика+восстановление (US5, финализация)**: полный golden-каталог 7 кодов с
  позициями в рунах; явное множество синхро-токенов в `recover.go`; многоошибочное накопление без
  фантомов; отложенные декларации/`значение`/`{` на верхнем уровне → SE-UNEXPECTED; без stack trace.
  Гейт: SC-003 (все 7 дословно), SC-005 (≥2 ошибки, бюджет ≤≈20).

Зависимости фаз: P1 опирается на Фазу 0; P2a/P2b опираются на P1 (нужны выражения и каркас); P2c
финализирует восстановление поверх P1/P2 (нужны источники ошибок). Внутри каждой фазы — tests-first.

## Открытые вопросы и отложенные расхождения

- **D1 (РЕШЁН ЗДЕСЬ)**: размещение `Position` — на шаге AST выбран **ast-local** (узлы `ast` несут свою
  `Position`, не импортируют `errors`; конвертер — в `parser`). Согласовано с ARCHITECTURE §4.1 и
  конституцией IV/VII; 001 оставлял D1 отложенным до этого шага. Лексер не затронут (`Token.Pos`
  остаётся `errors.Position`). (D-R1)
- **Слияние бюджета лексер↔парсер** (форвард-нота из 001, частично закрыта): `ParseError` складывается в
  тот же тип `errors.ErrorList`; в собранном пайплайне один и тот же `*ErrorList` протаскивается
  лексер→парсер, поэтому ≈20 — действительно общий предел. Фактическая проводка — забота будущего
  CLI-пайплайна; парсер 002 принимает `*ErrorList` через параметр (или создаёт свой в изоляции). (D-R7/D-R10)
- **Каскад от лексических «дыр»**: парсер работает безусловно на best-effort потоке (guardrail 11);
  стадийное гейтирование не вводится в 002 — это решение-дефолт, зафиксированное в D-R7, а не молчаливое.
