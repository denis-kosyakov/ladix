# Research: Стабильные контентные ключи триггеров

Все вопросы проектирования закрыты зафиксированными решениями (D-1..D-8). Здесь —
консолидация с обоснованием, отвергнутыми альтернативами и **мутпробами** (каждый замок обязан
КРАСНЕТЬ при инверсии фикса). Открытых **NEEDS CLARIFICATION** нет.

Источник истины — код (карта проверена): минт ключа `daemon/tick.go:43-45`; call-sites
`metrics.go:38` / `schedule.go:47`; реестр `eval/interpreter.go:141-143`; миграции
`store/sqlite.go:81-122,374-412`; `checkAt` `daemon/schedule.go:105-133`.

## Решение 1 (D-1): где живёт канонизатор условия

- **Decision**: новый файл `src/internal/ast/canon.go` (пакет `ast`): экспортируемые
  `CanonicalTriggerCondition(spec TriggerSpec) string` и приватный тотальный `canonExpr(e Expression) string`.
- **Rationale**: канонизация — чистая функция от AST, без зависимостей от рантайма/Store/eval. Её
  естественное место — **листовой** пакет `ast`, где живут сами узлы (Конституция VII). Тестируется
  изолированно (T1) без поднятия демона/БД. Импортирует только `fmt`/`strconv` — листовость `ast`
  не нарушается (не тянет `errors`).
- **Alternatives rejected**:
  - *В `internal/daemon`*: тянул бы AST-знание (19 типов) в слой оркестрации; канонизатор стал бы
    нетестируемым в отрыве от демона; нарушил бы разделение «чистое преобразование vs. побочные эффекты».
  - *В `internal/eval`*: `eval` не листовой; канонизатор там обрастал бы соблазном звать
    вычислитель; чистота преобразования размывается.

## Решение 2 (D-2): тотальность `canonExpr` и поведение на неизвестной форме

- **Decision**: `switch e.(type)` по **всем 19** конкретным `Expression` (`IntLit`, `FloatLit`,
  `StringLit`, `BoolLit`, `NoneLit`, `DurationLit`, `WindowPeriodLit`, `LastCompletedPeriodLit`,
  `ListLit`, `Ident`, `BinaryExpr`, `UnaryExpr`, `CallExpr`, `IndexExpr`, `FieldExpr`,
  `RunProcessExpr`, `CallExternalExpr`, `ValueExpr`, `EventExpr`); `default` →
  `panic(fmt.Sprintf("canonExpr: незнакомый тип выражения %T", e))`.
- **Rationale**: FR-003/SC-007 — нет молчащего схлопывания разных форм в одну строку. Громкий
  `panic` — санкционированный Принципом III инвариант «не должно случиться» (фронтенд гарантирует
  валидность условия до демона; все реализации `Expression` — в `internal/ast`, внешних нет).
  Исчерпываемость защищена тестом (T1: stub-тип, реализующий `exprNode()`, → `default`-panic;
  recover-assert). **Мутпроба**: убрать любую ветку из switch → её тип уходит в `default` → паника
  на валидном входе → T1 (и T2) краснеют.
- **Alternatives rejected**:
  - *Молчащий default → `""`*: два разных выражения дали бы одинаковый ключ → порча baseline (тот
    самый класс дефекта, что устраняем). Запрещено FR-003.
  - *Default → `fmt.Sprintf("%v", e)`*: недетерминированно/непрозрачно; форма зависит от деталей
    типа, не от смысла; ломает каноническое равенство.

## Решение 3 (D-3): нормализация числовых/строковых/булевых литералов (каноническое равенство)

- **Decision**:
  - `IntLit.Value (int64)` → `strconv.FormatInt(v, 10)`.
  - `FloatLit.Value (float64)` → `strconv.FormatFloat(v, 'g', -1, 64)` — **детерминированная
    кратчайшая round-trip форма**; ЗАФИКСИРОВАНА как канон дробных.
  - `StringLit.Value` → `strconv.Quote(v)` — экранированная закавыченная форма (служебные символы
    не коллизируют).
  - `BoolLit.Value` → `strconv.FormatBool(v)`; `NoneLit` → фиксированная строка `"пусто"`.
- **Rationale**: канонизация идёт от **разобранного** значения, а не от текста. `10_000_000` и
  `10000000` лексер уже разобрал в один `int64` → одна строка → один ключ (SC-002/FR-003). `'g'`
  с precision `-1` — стандартная Go-форма кратчайшего round-trip представления (детерминирована для
  фиксированной версии Go). **Мутпроба**: заменить `FormatInt` на исходный текст токена — `10_000_000`
  ≠ `10000000` → T2 краснеет.
- **Alternatives rejected**:
  - *Канон по тексту токена*: вернул бы зависимость от форматирования (разделители/пробелы) — прямо
    противоречит SC-002.
  - *`FormatFloat('f', …)`*: фиксированная точность теряет/добавляет нули, не round-trip; разные
    дробные могли бы совпасть или одно — разойтись между прогонами.

## Решение 4 (D-4): форма ключа и хеш

- **Decision**: `key = "trg-" + fmt.Sprintf("%016x", fnv.New64a()⟶Sum64(canonical + "#" + ord))`,
  где `ord := strconv.Itoa(порядковый_номер)`; хеш — `hash/fnv` (FNV-1a-64, stdlib). 16 hex-цифр =
  `%016x` от 64-битного значения.
- **Rationale**: FR-001. FNV-1a-64 — stdlib, без CGO, без новых зависимостей (Конституция I);
  детерминирован, дёшев, достаточен для не-криптографической идентичности. Префикс `"trg-"`
  сохранён для узнаваемости в БД/логах (символьно, не как `trg-<N>`). `"#" + ord` в **хешируемой**
  строке (а не в открытом виде) — дубликаты разводятся внутри хеша.
- **Alternatives rejected**:
  - *Криптохеш (SHA-256)*: избыточен для durable-идентичности; длиннее; та же детерминированность
    при большей цене.
  - *Внешняя hash-библиотека*: нарушает Конституцию I (новая зависимость) без выгоды над stdlib.
  - *Класть `canonical` в ключ как есть*: длинные/неэкранируемые строки в PRIMARY KEY; хеш даёт
    фиксированную короткую форму.

## Решение 5 (D-5): дизамбигуация дубликатов (порядковый номер)

- **Decision**: 0-based номер триггера **внутри группы** с одинаковым `canonical(условие)`, в
  порядке объявления. Алгоритм билдера: `ordinals := map[string]int{}`; для каждого триггера
  `ord := ordinals[c]; ordinals[c]++`. Уникальное условие → группа из одного → `ord=0` →
  ключ **не зависит от соседей**.
- **Rationale**: FR-004. Уникальный (типичный) случай: `ord=0` всегда, ключ стабилен под любыми
  перестановками несвязанных триггеров (ядро фичи). Дубликаты (вырожденный случай US3): `ord` 0,1,…
  разводит их в разные строки `trigger_state` (SC-004). **Мутпроба**: убрать `#ord` из хешируемой
  строки → два идентичных условия дают один ключ → T4 краснеет.
- **Alternatives rejected**:
  - *Глобальный `idx` объявления в ключе*: ровно текущий баг (позиционность) — отвергнут целиком.
  - *Падать на дубликатах*: вырожденный, но легальный случай; падение — недружелюбно и не требуется.

## Решение 6 (D-6): когда и где считаются ключи (один раз, поле демона)

- **Decision**: новый билдер `buildTriggerKeys(trig []*ast.TriggerDecl) []string` (в `internal/daemon`,
  файл `keys.go` или рядом с удалённым `triggerID` в `tick.go`); вычисляется **один раз в
  конструкторе `New` (daemon.go:37-49)** из `interp.Triggers()`; результат — поле
  `triggerKeys []string` структуры `Daemon` (daemon.go:25-33). На каждом тике `metrics.go:38` и
  `schedule.go:47` читают `d.triggerKeys[idx]` (массив выровнен по индексам списка триггеров).
  Событие-/дедлайн-слоты пусты (`""`) и не читаются (events.go/checkdeadlines.go не зовут ключ).
- **Rationale**: FR-005 + Конституция V (без глобалов — состояние в поле экземпляра, не пакетный
  `var`). Один проход группировки на инициализации; тик — O(1) чтение. **Конструктор уже принимает
  `interp`** (находка плана) → заполнение внутри `New` без правки сигнатуры/call-sites
  (`serve.go:326` и 4 теста не трогаются). Старый `triggerID` удаляется (FR-005, SC-008 — нет
  захардкоженного `trg-%d`).
- **Alternatives rejected**:
  - *Считать ключ per-tick*: лишняя работа; FR-005 требует один проход.
  - *Пакетная `var keys`*: запрещено Конституцией V.
  - *Менять сигнатуру `New` (новый параметр keys)*: не нужно — `interp` уже в `New`; правка
    сигнатуры задела бы 5 call-sites без выгоды (рецепт предполагал иначе; код опроверг — см. план).

## Решение 7 (D-7): миграция схемы 2→3

- **Decision**: добавить 3-й элемент в `schemaMigrations` (`sqlite.go:106-122`) — строку
  `DELETE FROM trigger_state;` (комментарий «2 → 3: ре-кей триггеров на контентные ключи (§FR-009),
  сброс позиционного состояния»); забампить `currentSchemaVersion` 2→3 (`sqlite.go:82-84`). DDL
  `trigger_state` и тип `TriggerState` **не трогать**. Инвариант INV-R1 (`init()` :91-97):
  `currentSchemaVersion (3) == baselineVersion (1) + len(schemaMigrations) (2)` — двойной
  compile/runtime-замок.
- **Rationale**: FR-009. Миграция видит только базу, не AST → старые `trg-<N>` переиздать нельзя
  → переход = **сброс + ленивый ре-прайминг** на последующих тиках. Forward-only (соответствует
  модели миграций). `migrate()` (:374-412) применяет элемент в одной транзакции с
  `PRAGMA user_version`. **Мутпроба**: не забампить версию (оставить 2) при добавленном элементе →
  `init()` INV-R1 паникует на старте (1+2≠2) → пакет не компилируется/падает → T7 и любой тест
  store краснеют.
- **Alternatives rejected**:
  - *Не чистить, домигрировать ключи*: невозможно без AST (см. выше).
  - *Удалить DDL и пересоздать таблицу*: избыточно; `DELETE` достаточно, схема не меняется (FR-007).

## Решение 8 (D-8): FR-010 — прайм-без-срабатывания schedule_at на первом промахе

- **Decision**: в `checkAt` (`schedule.go:105-133`) добавить miss-ветку ДО fire. Точно:
  `miss := stderrors.Is(loadErr, store.ErrTriggerStateNotFound)`; если `miss && !now.Before(target)`
  (промах И `сейчас >= цель`) → `SaveTriggerState({TriggerID:id, Kind:atKind, LastFiredDate:&today})`
  + `return` (прайм, тело НЕ исполняется). Случай `miss && now.Before(target)` — без изменений
  (падает в существующий `now.Before(target)`→return, штатно сработает в target). Минимальная
  дельта: Save идентичен прежнему, разница — **не запускать тело**.
- **Rationale**: FR-010 + Complexity Tracking. После `DELETE FROM trigger_state` все триггеры на
  первом тике видят промах; метрика (metrics.go:59-67) и `каждые` (schedule.go:66-74) уже
  праймят-без-срабатывания; schedule_at сейчас **догоняет** (catch-up `:121` `now.Before(target)`
  ложно → Save+fire) → ложный плановый запуск при апгрейде. Приведение убирает этот класс.
  **Мутпроба**: не добавить miss-ветку → schedule_at с `сейчас>=цель` на первом промахе срабатывает
  → T8 краснеет (инверсионный 🔁).
- **Alternatives rejected**:
  - *Оставить catch-up*: воспроизводит дефект; отвергнут спекой.
  - *Трогать `сейчас<цель`*: сломал бы штатное срабатывание в назначенное время (регресс); вне
    scope FR-010.
