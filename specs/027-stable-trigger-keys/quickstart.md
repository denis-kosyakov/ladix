## 9 замков

### T1 — исчерпываемость `canonExpr` (`ast/canon_test.go`)

- **Что**: table из **РОВНО 19** типов выражений с ожидаемыми каноническими строками →
  `canonExpr(input) == expected` для каждого. Плюс: локальный stub-тип, реализующий `Expression`
  (`exprNode()`), → `canonExpr(stub)` **паникует** (`recover` + assert текста/факта паники).
- **FR/SC**: FR-003, SC-007.
- **🔁**: убрать любую ветку из switch → её тип уходит в `default`-panic → строка-кейс или stub
  краснеет. Доказывает «нет молчащего схлопывания».

### T2 — каноническое равенство (parse→canon)

- **Что**: распарсить **через parser** ДВА (три) исходных текста триггера, отличающихся только
  форматированием числа/пробелами: `выручка_30д < 10_000_000` vs `< 10000000` vs `<  10000000` →
  `CanonicalTriggerCondition` (а лучше и ключ `buildTriggerKeys`) **совпадают**.
- **FR/SC**: FR-002/003, SC-002. Через parser — доказать независимость от текста.
- **🔁**: канон по тексту токена вместо `FormatInt` → `10_000_000 ≠ 10000000` → краснеет.

### T3 — каноническое различие

- **Что**: разные имя метрики / оператор сравнения / значение порога → **разные** канонические
  строки/ключи.
- **FR/SC**: FR-002, SC-003.
- **🔁**: схлопнуть оператор/имя в канон (потерять компонент) → совпадение → краснеет.

### T4 — дизамбигуация дубликатов

- **Что**: два триггера с **идентичным** условием → `buildTriggerKeys` даёт **разные** ключи
  (`ord` 0 и 1).
- **FR/SC**: FR-004, SC-004.
- **🔁**: убрать `#ord` из хешируемой строки → один ключ на оба → краснеет.

### T5 — стабильность под перестановкой (`daemon`, 🔁 ЯДРО БАГА)

- **Что**: построить ключи `buildTriggerKeys` для `[метрика-триггер]` и для
  `[событие-триггер, тот же метрика-триггер]` (несвязанный вставлен **ПЕРЕД**) → ключ
  метрика-триггера **ИДЕНТИЧЕН** в обоих случаях.
- **FR/SC**: FR-001/004/005, SC-001. **Замок, который ревьюер лично проверит на мутпробе.**
- **🔁**: вернуть позиционный `triggerID(idx)` → idx метрики сдвинулся (0→1) → ключи разные →
  краснеет. Это ядро устраняемого дефекта.

### T6 — ре-прайминг при правке условия (`daemon`)

- **Что**: правка условия триггера → **новый** ключ → нет ложного фронта (читается чистый baseline,
  лениво праймится). Старая строка под старым ключом не подхватывается.
- **FR/SC**: FR-002/008, SC-003.
- **🔁**: сделать ключ нечувствительным к порогу → старый baseline подхватился → ложный фронт →
  краснеет.

### T7 — миграция 2→3 (`store`, SQLite-специфика)

- **Что**: собрать v2-БД со строками `trigger_state` (`trg-0`, `trg-1`, …) и `user_version=2` →
  `NewSQLiteStore(path)` → `trigger_state` **ПУСТА**, `PRAGMA user_version == 3`; Close+reopen
  сохраняет новые (контентные) ключи и версию 3. Паттерн — `store/migrate_test.go`.
- **FR/SC**: FR-009, SC-005. (`user_version` — SQLite-специфика; миграция только SQLite.)
- **🔁**: не забампить версию / убрать `DELETE`-ступень → INV-R1 паника ИЛИ строки остаются →
  краснеет.

### T8 — поведенческая нейтральность первого тика (`daemon`, 🔁)

- **Что**: первый тик после апгрейда:
  - метрика истинная на апгрейде → miss → **прайм, НЕ срабатывает**;
  - `schedule_every` наступившее → **прайм, НЕ срабатывает**;
  - `schedule_at` с `сейчас >= цель` → **прайм** (`LastFiredDate=today`), **НЕ срабатывает**;
  - следующий день/тик — срабатывает штатно.
- **FR/SC**: FR-008/010, SC-006.
- **🔁**: не привести `checkAt` к прайму → `schedule_at` срабатывает на первом промахе → краснеет.

### T9 — паритет durable Memory/SQLite (`eachStore`)

- **Что**: durable-замки (ключ-минт детерминирован, состояние одинаково) прогоняются в **обеих**
  impl через `eachStore` там, где применимо (миграционный T7 — только SQLite).
- **FR/SC**: FR-007, SC-001/004.
- **🔁**: расхождение Load/Save между impl → один сабтест краснеет.

**0 новых** KW / builtins / eval-кодов. Старый `triggerID(idx)` **удалён**.
