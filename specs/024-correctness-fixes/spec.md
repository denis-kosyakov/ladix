## User Scenarios & Testing *(mandatory)*

Эта фича — **починка корректности без новой языковой функциональности**. Ценность для пользователя:
шесть логических багов value-пространства (молчаливая потеря/искажение значений, недетерминированный
порядок при NaN, дубль задачи при рестарте демона, ложное переполнение) устранены точечными правками,
а каждый фикс закреплён co-land тест-замком, который доказуемо краснеет при откате фикса (mutation-probe).
Только **Фикс C** добавляет наблюдаемое поведение (две новые ошибки + golden-дельта `28 → 30`);
остальные пять переиспользуют существующие сообщения / не вводят ошибок.

### User Story 1 - Фикс C: `дробное()`/`число()` отвергают NaN/Inf/hex-float (Priority: P1)

Пользователь конвертирует строку в число встроенными `дробное(x)` / `число(x)`. Сейчас `"nan"`,
`"+inf"`, hex-float `"0x1p4"` молча уходят в `Дробное` (Go `ParseFloat` принимает их без ошибки),
загрязняя value-пространство нечисловыми/непредставимыми величинами. После фикса такие строки громко
отвергаются — единственный фикс, добавляющий наблюдаемое поведение и новые сообщения.

**Why this priority**: Единственный фикс с пользовательски-видимым контрактом (2 новых сообщения +
golden-дельта), и он замыкает источник, из которого NaN мог попасть в систему через конверсию строк.
Строгость согласована со строгим CSV-фильтром источников (`source_loader.go`).

**Independent Test**: Прогнать `дробное("nan")`, `дробное("+inf")`, `дробное("0x1p4")`, `число("inf")`
— каждый даёт `ОшибкаВыполнения`, не `Дробное`. Валидные `дробное("3.5")` / `число("42")` — по-прежнему
успешны. Прогнать golden-замок реестра ошибок — `len(seen)` равен `30`, в таблице присутствуют оба новых
кейса.

**Acceptance Scenarios**:

1. **Given** строка `"nan"`, **When** вызывается `дробное("nan")`, **Then** возвращается
   `ОшибкаВыполнения` с сообщением `дробное: «nan» не является конечным числом`, а НЕ значение `Дробное`.
2. **Given** строка `"inf"`, **When** вызывается `число("inf")`, **Then** возвращается
   `ОшибкаВыполнения` с сообщением `число: «inf» не является конечным числом`.
3. **Given** Go-hex-float `"0x1p4"`, **When** вызывается `дробное("0x1p4")`, **Then** возвращается
   `ОшибкаВыполнения` (форма отвергнута), а НЕ `Дробное{16.0}`.
4. **Given** валидная десятичная строка `"3.5"`, **When** вызывается `дробное("3.5")`, **Then**
   возвращается `Дробное{3.5}` (поведение не регрессировало); `целое()` (ParseInt) не затронут.
5. **Given** golden-замок реестра ошибок `errors_golden_test.go`, **When** он прогоняется, **Then**
   `len(seen) == 30` (было `28`), и оба новых сообщения присутствуют в exact-match таблице с категорией
   `ОшибкаВыполнения`.

### User Story 2 - Фикс A: идемпотентность создания задачи при рестарте serve (Priority: P1)

Демон `serve` перезапускается и реактивирует «залипший» процесс-инстанс в статусе «выполняется»,
стоящий на человеческом шаге. Сейчас `advance` безусловно минтит новый `Task` и сохраняет его — на
рестарте создаётся **дубль** задачи на том же (instance, step). После фикса повторная реактивация
идемпотентна: уже открытая задача обнаруживается, новый id не минтится, счётчик не жжётся.

**Why this priority**: Дубль задачи на рестарте — наблюдаемая порча данных в durable-пути демона
(`daemon/restart.go` → `ReactivateInstance` → `advance`). Подход — лёгкий query-guard; тяжёлый
partial-unique-индекс (миграция + бамп схемы) отвергнут анкером.

**Independent Test**: Предзалить `StatusRunning`-инстанс, уже стоящий на человеческом шаге `согласовать`
с уже сохранённой `TaskPending` на этом шаге; вызвать `ReactivateInstance`; проверить, что
`len(st.ListPendingTasks("")) == 1` (не `2`) и id существующей задачи не изменился.

**Acceptance Scenarios**:

1. **Given** `StatusRunning`-инстанс с уже существующей `TaskPending` на текущем человеческом шаге,
   **When** вызывается `ReactivateInstance` (через `advance`), **Then** новая задача НЕ создаётся
   (счётчик `NextTaskID` не жжётся), статус инстанса = `StatusWaiting`, инстанс сохранён,
   `printTaskCreated` не повторяется.
2. **Given** инстанс на человеческом шаге БЕЗ существующей открытой задачи, **When** вызывается
   `advance`, **Then** задача минтится и сохраняется как прежде (поведение happy-path не регрессировало).
3. **Given** после реактивации, **When** считаются открытые задачи, **Then** их ровно одна, а id
   совпадает с предзалитой задачей.

### User Story 3 - Фикс B: `Compare` трактует NaN как несравнимый (IEEE-754) (Priority: P2)

Сравнение значений (`<`, `мин`, `макс`, `сортировать`) над `Дробное{NaN}` сейчас возвращает «равны/
упорядочены» (`cmpFloat` — голый `switch a<b/a>b/default→0`, при NaN все ветки ложны → `0`), нарушая
IEEE-754 и давая молчаливо-неверный порядок. После фикса NaN объявляется несравнимым (`bool=false`), что
поднимает существующую typeErr «несравнимы» — громкая ошибка вместо тихой порчи порядка.

**Why this priority**: Defense-in-depth: после фиксов C+D NaN из конструкции недостижим, но фикс B
страхует против будущего `Inf−Inf` (арифметика→Inf — отдельный backlog). Чуть ниже приоритетом, так как
прямой источник NaN закрывает C.

**Independent Test**: `Compare(Дробное{NaN}, Дробное{5})` → `(_, false)` (несравнимы; NaN через
`math.NaN()`). Eval-уровень: `сортировать`/`мин` списка с NaN → ошибка «несравнимы».

**Acceptance Scenarios**:

1. **Given** два значения, одно из которых `Дробное{NaN}`, **When** вызывается `value.Compare`, **Then**
   возвращается `(0, false)` — взаимно неупорядочиваемы (а НЕ «равны/упорядочены»).
2. **Given** список с элементом-NaN, **When** вызывается `сортировать`/`мин`/`макс`, **Then**
   поднимается существующая typeErr «несравнимы» (через `ok==false`).
3. **Given** значения с `Inf` (не NaN), **When** вызывается `Compare`, **Then** они упорядочиваются
   корректно (`Inf` НЕ затронут фиксом).
4. **Given** `==` / `!=` над NaN, **When** они вычисляются, **Then** поведение прежнее (идут через
   `value.Equal`, не `Compare`) — фикс их НЕ трогает.

### User Story 4 - Фикс D: jsonval сохраняет число вне float64 как `Дробное{±Inf}` (Priority: P2)

Payload события / `--данные` / вебхук содержит число вне диапазона float64 (`1e400`). Сейчас
`numberToValue` на `Float64()`-ErrRange возвращает `value.None` — **молчаливая** потеря (как JSON null).
После фикса, по толерантному контракту payload (деградация лучше сбоя доставки), такое число сохраняется
как `Дробное{±Inf}`.

**Why this priority**: Молчаливое превращение большого числа в `None` искажает payload-данные авто-шагов
и эффектов. Толерантный подход зафиксирован контрактом `decode.go` и `SPEC.md` («Дробное держит ±Inf»);
store-codec round-trip ±Inf/NaN уже держит, ничего не ломается.

**Independent Test**: Декодировать `1e400` → `Дробное{+Inf}`, `-1e400` → `Дробное{-Inf}`. (Существующий
`99999999999999999999` ≈1e20 дыру не ловил — в пределах float64.)

**Acceptance Scenarios**:

1. **Given** JSON-число `1e400` (вне float64), **When** оно декодируется через `numberToValue`, **Then**
   возвращается `Дробное{+Inf}`, а НЕ `value.None`.
2. **Given** JSON-число `-1e400`, **When** оно декодируется, **Then** возвращается `Дробное{-Inf}`.
3. **Given** число в пределах float64, **When** оно декодируется, **Then** возвращается обычное
   `Целое`/`Дробное` (поведение не регрессировало); для чисел ветка `None` становится недостижима.

### User Story 5 - Фикс E: `сумма()` промоутится в Дробное вместо ложного overflow (Priority: P2)

Пользователь суммирует список, где есть и большие целые, и дробные (`[MaxInt64, …, 2.0]`). Сейчас
overflow-гард целого аккумулятора срабатывает на каждом Целом **до** проверки наличия дробных, и сумма
ложно падает с «переполнение целого числа», хотя должна промоутиться в `Дробное`. После фикса overflow-
гард гейтится за наличием `Дробное`.

**Why this priority**: Ложная ошибка на корректном смешанном входе — наблюдаемый дефект агрегата. Чисто-
целый путь (где overflow реален) сохраняет существующую ошибку RT-OVERFLOW.

**Independent Test**: `сумма([9223372036854775807, 9223372036854775807, 1.5])` → `Дробное` (≈1.8e19), не
ошибка. Регресс: `сумма([9223372036854775807, 1])` (all-int) → по-прежнему «переполнение целого числа».

**Acceptance Scenarios**:

1. **Given** список с `Дробное` и большими `Целое` (`[MaxInt64, MaxInt64, 1.5]`), **When** вызывается
   `сумма`, **Then** результат — `Дробное` (≈1.8e19), а НЕ ошибка переполнения.
2. **Given** чисто-целый список с реальным переполнением (`[MaxInt64, 1]`), **When** вызывается `сумма`,
   **Then** поднимается существующая ошибка «переполнение целого числа» (RT-OVERFLOW; поведение не
   регрессировало).

### User Story 6 - Фикс F: `MinInt64 // -1` поднимает overflow вместо wraparound (Priority: P3)

Целочисленное floor-деление `MinInt64 // -1` сейчас — голый `a/b` без ловушки, молча заворачивается
(wraparound). После фикса этот единственный overflow-случай поднимает ту же ошибку «переполнение целого
числа» (RT-OVERFLOW), что и умножение `*` — симметрия принципа «нигде нет молчаливого wraparound».

**Why this priority**: Узкий, редко достижимый край (один вход), но молчаливый wraparound нарушает
инвариант корректности целочисленной арифметики. Решение владельца — чинить, по симметрии с `*`.

**Independent Test**: Выражение, дающее `MinInt64 // -1` (`MinInt64` через `(0 - 9223372036854775807 -
1)`) → «переполнение целого числа». Happy-path `7 // 2 → 3` не ломается; деление-на-ноль остаётся как
есть.

**Acceptance Scenarios**:

1. **Given** выражение `MinInt64 // -1`, **When** оно вычисляется, **Then** поднимается
   `ОшибкаВыполнения` «переполнение целого числа» (RT-OVERFLOW), а НЕ молчаливый wraparound.
2. **Given** обычное floor-деление `7 // 2`, **When** оно вычисляется, **Then** результат `3` (поведение
   не регрессировало).
3. **Given** деление на ноль, **When** оно вычисляется, **Then** поведение прежнее (отдельная ошибка
   деления-на-ноль, фиксом не тронута).

### Edge Cases

- **Линейность v1-процессов (Фикс A):** v1-процессы линейны (нет возврата на тот же шаг), поэтому
  `Pending`-задача на (inst, CurrentStep) однозначна — это та, что догоняем; query-guard корректен.
- **NaN недостижим после C+D (Фикс B):** прямой источник NaN из конверсии строк (C) и payload (D)
  закрыт, поэтому B — defense-in-depth против будущей арифметики `Inf−Inf` (вне скоупа, backlog).
- **`Inf` остаётся упорядочиваемым (Фикс B):** правка трогает только NaN; `Inf` сравнивается корректно
  и НЕ затрагивается.
- **Толерантность vs строгость (Фиксы C↔D):** строгий отказ конверсии строк (C) сознательно
  контрастирует с толерантным payload (D, `Дробное{±Inf}`) — это зафиксированный сплит контрактов.
- **Чисто-целый путь сохраняет overflow (Фикс E):** гейт за `hasFloat` не отключает overflow-гард для
  all-int сумм — RT-OVERFLOW там по-прежнему срабатывает.
- **Round-trip ±Inf (Фикс D):** store-codec держит ±Inf/NaN — `Дробное{±Inf}` из payload durable.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (Фикс A)**: Создание человеческой задачи в `engine.advance` MUST стать идемпотентным через
  query-guard: перед минтом `NextTaskID`/`SaveTask` искать существующую открытую задачу на текущем
  (instance, step) — `t.Status == store.TaskPending && t.StepName == step.Name.Name`. Найдена → НЕ минтить
  новый id, НЕ `SaveTask`, НЕ повторять `printTaskCreated`; выставить `inst.Status = store.StatusWaiting`,
  сохранить инстанс, вернуть `nil`. Не найдена → текущее поведение (mint + SaveTask + печать + save).
  Partial-unique-индекс ОТВЕРГНУТ (миграция/бамп схемы — тяжело).
- **FR-002 (Фикс A)**: MUST появиться новый тест-замок (`engine/reactivate_test.go`): предзалить
  `StatusRunning`-инстанс с уже сохранённой `TaskPending` на человеческом шаге; вызвать
  `ReactivateInstance`; ассертить `len(st.ListPendingTasks("")) == 1` (не `2`) и неизменность id
  существующей задачи. Фикс A НЕ вводит новых сообщений и НЕ меняет golden-счётчик.
- **FR-003 (Фикс B)**: `value.Compare` на float-ветках MUST перед `cmpFloat` проверять
  `if math.IsNaN(af) || math.IsNaN(bf) { return 0, false }` (несравнимы). `Inf` НЕ трогать. Следствие
  (намеренно): сравнение/`мин`/`макс`/`сортировать` со значением-NaN поднимает существующую typeErr
  «несравнимы» через `ok==false`. `==`/`!=` (через `value.Equal`) НЕ трогать.
- **FR-004 (Фикс B)**: MUST появиться тест-замок в `value/equal_test.go` (`TestCompare`):
  `Compare(Дробное{NaN}, Дробное{5}) → (_, false)`; плюс eval-уровень — `сортировать`/`мин` списка с NaN
  (через `math.NaN()`) → ошибка «несравнимы». Фикс B НЕ вводит новых сообщений и НЕ меняет
  golden-счётчик.
- **FR-005 (Фикс C)**: `builtinDrobnoe` и `builtinChislo` (строка-ветки) MUST отвергать нечисловые/
  непредставимые формы: после `ParseFloat(strings.TrimSpace(x.V), 64)` отказывать, если
  `strings.ContainsAny(s, "xXpP")` (hex-float) ИЛИ `math.IsInf(f, 0) || math.IsNaN(f)`. Общий хелпер
  `parseFiniteFloat(s string) (float64, bool)` MUST быть вынесен и использован в обоих. Отказ →
  `runtimeErr(<pos>, <msg>)` (тип `ОшибкаВыполнения`), позиция — как у прочих ошибок этих builtins.
- **FR-006 (Фикс C, НОВЫЕ сообщения дословно)**: Фикс C MUST добавить ровно ДВА новых сообщения об
  ошибке, дословно (где `%s` = исходная строка-аргумент после `TrimSpace`):
  - `дробное: «%s» не является конечным числом`
  - `число: «%s» не является конечным числом`
- **FR-007 (Фикс C, golden 28→30)**: Golden-замок `eval/errors_golden_test.go` MUST быть обновлён в той
  же правке: добавить 2 кейса (категория `ОшибкаВыполнения`/RT-*) в exact-match таблицу и изменить
  count-замок `TestErrorsRegistryExactMatch` с `len(seen) != 28` на `len(seen) != 30` (правка
  `:205-207`). Это ЕДИНСТВЕННЫЙ фикс, меняющий golden-счётчик (`28 → 30`); реестр
  `specs/003-interpreter-eval/contracts/runtime-errors.md` MUST быть синхронизирован с двумя новыми
  сообщениями.
- **FR-008 (Фикс C)**: MUST появиться тест-замок в `eval/builtins_test.go`: `дробное("nan")`,
  `дробное("+inf")`, `дробное("0x1p4")`, `число("inf")` → ошибка (не `Дробное`); валидные
  `дробное("3.5")`, `число("42")` — по-прежнему ок. `целое()` (ParseInt) НЕ трогать.
- **FR-009 (Фикс D)**: `jsonval.numberToValue` MUST сохранять число вне float64 (`1e400`) как
  `Дробное{±Inf}` вместо `value.None`: на `Float64()`-ErrRange `f` уже = `±Inf` → вернуть
  `value.Дробное{V: f}` (`f, _ := n.Float64(); return value.Дробное{V: f}`). Для чисел ветка `None`
  становится недостижима. Толерантный подход — по контракту `decode.go`/`SPEC.md`; store-codec round-trip
  ±Inf/NaN уже держит.
- **FR-010 (Фикс D)**: MUST появиться тест-замок в `jsonval/decode_test.go`: `1e400` → `Дробное{+Inf}`,
  `-1e400` → `Дробное{-Inf}`. Фикс D НЕ вводит новых сообщений (толерантно, без ошибок) и НЕ меняет
  golden-счётчик.
- **FR-011 (Фикс E)**: `builtinSumma` MUST отложить/гейтить overflow-гард целого аккумулятора за
  наличием `Дробное` (`hasFloat`): предсканировать список (или копить параллельно), при наличии `Дробное`
  суммировать во `fSum` БЕЗ int-гарда → `Дробное`; все Целые → текущий int-путь с overflow-гардом
  (RT-OVERFLOW).
- **FR-012 (Фикс E)**: MUST появиться тест-замок в `eval/builtins_test.go`:
  `сумма([9223372036854775807, 9223372036854775807, 1.5])` → `Дробное` (≈1.8e19), не ошибка; регресс
  `сумма([9223372036854775807, 1])` (all-int) → по-прежнему «переполнение целого числа». Фикс E НЕ вводит
  новых сообщений (overflow только на all-int пути) и НЕ меняет golden-счётчик.
- **FR-013 (Фикс F)**: `floorDivInt64` MUST получить сигнатуру `(int64, bool)` (bool=overflow), зеркально
