# Feature Specification: B3 — payload задачи через `complete --данные`

**Feature Branch**: `015-complete-payload`

**Created**: 2026-06-17

**Status**: Draft

**Input**: Якорь — `docs/automation-model.md` §AU-5 (B3), решение §AU-1 D-AU-3,
CLI-ошибка §AU-10.C. Веха M2 автоматизации; фронтенд языка НЕ меняется.

## Контекст и граница

B3 даёт оператору передать **payload** при завершении человеческой задачи:
`ladix complete <файл> <task-id> [--данные '{…}']`. JSON-объект декодируется в
**read-only эфемерную** `value.Запись` и инжектится под именем `данные` в среду
**первого шага догона** того же `complete`. Без флага → ПУСТАЯ `Запись` (НЕ ошибка).
Эфемерность (D-AU-3): `данные` живёт ТОЛЬКО сквозь догон одного `complete`, НЕ
персистится в инстанс/задачу/SQLite (персист — путь отступления M3).

**Слои затронуты:** CLI (`completeMain`/`completeTask` в `cmd/ladix/main.go`),
engine (4 функции протяжки в `internal/engine/engine.go`), eval-инжект (точка
`stepEnv.Define("данные", data)` внутри `advance`). Независим, параллелен B4a.

**НЕ затронуты (пустой дифф):** `internal/eval` (импорт-граф без store/engine; `данные`
приходит уже как `value.Запись`), `internal/store` (нет новых полей/колонок),
`internal/value`, frontend (lexer/parser/ast/analyze), `ProcessRuntime` (остаётся
8 методов — НЕ шов; протяжка `data` — ВНУТРЕННИЙ API движка).

**jsonval — ПОТРЕБЛЯЕТСЯ, не создаётся.** Пакет `internal/jsonval` уже существует
(создан в B2/014, merge `aebac92`); `jsonval.PayloadToRecord(payload string)
(value.Запись, error)` экспортирован. B3 ВЫЗЫВАЕТ его из `cmd/ladix` для декода
`--данные`; второго JSON-декодера B3 НЕ добавляет, пакет НЕ лифтит и НЕ дублирует.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Payload виден первому шагу догона (Priority: P1)

Оператор завершает задачу с данными (`--данные '{"итог":"ок","сумма":100}'`).
Шаг(и), которые догоняет этот `complete` (продвижение после завершения), ВИДЯТ
переменную `данные` как `value.Запись` и могут читать её поля (`данные.итог`,
`данные.сумма`). Прочитанное оператор сохраняет в переменную процесса своим
`присвоить факт = данные.итог` — она персистится в инстанс штатным `AssignProcessVar`.

**Why this priority**: Ядро фичи — без инжекта `данные` payload бесполезен. MVP
B3 = именно это. Без US1 фича не существует.

**Independent Test**: процесс, где первый шаг после завершаемого читает `данные.поле`
и присваивает его в переменную процесса; `complete … --данные '{"поле":V}'`;
проверить, что переменная инстанса = V (через `inspect`/Store), и что без `--данные`
поле читается как Пусто. Полностью независимо от US2/US3.

**Acceptance Scenarios**:

1. **Given** инстанс ожидает на задаче `t1`, следующий шаг читает `данные.итог` и
   делает `присвоить факт = данные.итог`, **When** `ladix complete f t1 --данные
   '{"итог":"готово"}'`, **Then** exit 0, переменная инстанса `факт = "готово"`.
2. **Given** payload с числом `{"сумма":2500000}`, **When** complete с этим payload,
   **Then** шаг видит `данные.сумма` как `Целое 2500000` (число без `.eE` → Целое).
3. **Given** payload-объект с вложенностью `{"клиент":{"имя":"А"}}`, **When**
   complete, **Then** `данные.клиент.имя` → `Строка "А"` (вложенный объект → Запись).

---

### User Story 2 — Эфемерность payload (Priority: P1)

`данные` существует ТОЛЬКО на первом шаге догона текущего `complete`. Второй и
последующие шаги того же догона видят ПУСТУЮ `Запись`. `данные` НЕ персистится:
после `complete` ни задача, ни инстанс, ни SQLite не содержат payload; следующий
`complete` без `--данные` видит пустую `Запись` (а не воскресший payload).

**Why this priority**: D-AU-3 лочит «эфемерный = живёт только сквозь догон одного
complete». Нарушение (инжект в `processEnv` или персист в Task) ломает несущий
инвариант 2 и открывает утечку payload в M3. Равноприоритетно ядру.

**Independent Test**: процесс с ≥2 авто-шагами в одном догоне; первый читает
`данные.x`, второй читает `данные.x`; complete с `--данные '{"x":1}'`; проверить,
что первый увидел 1, второй увидел Пусто (пустая Запись). Рестарт-проба: после
complete перечитать инстанс/задачи из Store — payload отсутствует.

**Acceptance Scenarios**:

1. **Given** догон с двумя авто-шагами, оба читают `данные.метка`, **When**
   `complete … --данные '{"метка":"X"}'`, **Then** первый шаг сохранил "X", второй
   шаг сохранил Пусто (после первой итерации `cur = value.NewRecord(nil,nil)`).
2. **Given** успешный `complete … --данные '{"итог":"да"}'`, **When** перечитать
   инстанс и его задачи из Store (новый процесс/новый запуск CLI), **Then** ни одно
   поле инстанса/задачи не содержит "да"; нет нового столбца/поля payload.
3. **Given** инстанс после payload-complete снова ожидает на следующей задаче,
   **When** второй `ladix complete f t2` БЕЗ `--данные`, **Then** шаг видит `данные`
   как пустую `Запись` (`данные.итог` → Пусто, открытая-запись семантика), exit 0.

---

### User Story 3 — Без флага → пусто; плохой JSON → дословная ошибка (Priority: P2)

Без `--данные` complete работает ровно как сегодня (пустая `Запись`, регресс не
ломается). Невалидный JSON в `--данные` → дословная CLI-ошибка, exit 2, инстанс не
тронут.

**Why this priority**: Граничные случаи и совместимость. P2 — после ядра и
эфемерности, но обязательны для DoD (дословность ошибки + регресс-зелень).

**Independent Test**: (а) существующий complete-golden (007b run-golden) без
`--данные` остаётся байт-точным; (б) `complete … --данные '{не json'` → stderr
`ladix: неверный JSON в --данные: <деталь>`, exit 2, Store не изменён.

**Acceptance Scenarios**:

1. **Given** валидный complete без `--данные`, **When** запуск, **Then** вывод и
   exit-код идентичны поведению до B3 (пустая `Запись` на старых вызовах движка).
2. **Given** `--данные '{"итог": '` (обрыв), **When** complete, **Then** stderr =
   `ladix: неверный JSON в --данные: <деталь>` (префикс дословен), exit 2, инстанс
   и задача в Store без изменений (валидация ДО `eng.Complete`).
3. **Given** `--данные` без значения (`--данные` последний аргумент), **When**
   complete, **Then** stderr `ladix: флаг --данные требует значение`, exit 2
   (зеркально существующему `--вебхук`).
4. **Given** `--данные '[1,2]'` (JSON-массив, не объект), **When** complete, **Then**
   ошибка декода объекта → `ladix: неверный JSON в --данные: <деталь>`, exit 2
   (payload — JSON-ОБЪЕКТ; `PayloadToRecord` отвергает не-объект).

---

### Edge Cases

- `--данные '{}'` (пустой объект) → пустая `Запись`, НЕ ошибка; эквивалентно
  отсутствию флага по наблюдаемому поведению шага.
- Догон, у которого первый шаг — снова человеческий (создаёт задачу, засыпает) →
  `данные` видит этот первый шаг; повторного шага в этом догоне нет (цикл вышел).
- Терминальный догон (следующего шага нет, инстанс сразу `выполнен`) → `данные`
  фактически не используется ни одним телом; это нормально, не ошибка.
- Путь `catchUp` (`caughtUp=true`, хвост сбойного окна D-4): `данные` тоже
  прокидывается через `catchUp` (§AU-5.3 — «на догоне человеческий ввод актуален»).
- Read-only барьер: тело шага читает `данные.поле`, но `присвоить данные = …`
  запрещён (как тело триггера); попытка переприсвоить `данные` — ошибка/барьер.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: CLI `complete` MUST принимать опциональный флаг `--данные '<json-объект>'`
  (формы `--данные V` и `--данные=V`), зеркально существующему `--вебхук`. Грамматика:
  `ladix complete <файл> <id> [--db путь] [--данные '{…}'] [--вебхук URL] [--max-depth N]`.
- **FR-002**: При наличии `--данные` CLI (`completeTask`) MUST декодировать значение
  через `jsonval.PayloadToRecord` в `value.Запись` ПЕРЕД `eng.Complete`. Декод/валидация
  — на CLI; движок получает уже готовую `value.Запись` (не строку).
- **FR-003**: Без `--данные` payload MUST быть ПУСТОЙ `value.Запись` (`value.NewRecord(nil,nil)`),
  НЕ ошибка; поведение complete идентично доB3.
- **FR-004**: Невалидный JSON в `--данные` (или не-объект) MUST давать stderr
  `ladix: неверный JSON в --данные: <деталь>` и exit 2, ДО любой мутации Store.
- **FR-005**: `--данные` без значения MUST давать stderr `ladix: флаг --данные требует
  значение`, exit 2 (зеркально `--вебхук`).
- **FR-006**: Движок MUST протягивать payload `data value.Запись` через ЧЕТЫРЕ функции:
  `Complete(taskID, data)` → [`catchUp(inst, data, t)`] → `advanceAfterComplete(inst,
  data, caughtUp)` → `advance(inst, data)`. Все четыре — ВНУТРЕННИЙ API движка.
- **FR-007**: `advance` MUST инжектить `данные` в **per-step** `stepEnv` через
  `stepEnv.Define("данные", data)` (НЕ в `processEnv`) перед `ExecStepBody`.
- **FR-008**: ТОЛЬКО первый шаг догона MUST видеть `данные`; после первой итерации
  цикла шагов инжектируемое значение MUST становиться пустой `Запись`
  (`cur = value.NewRecord(nil,nil)`), т.е. второй+ шаг видит пустую `Запись`.
- **FR-009**: `данные` MUST НЕ персистироваться: НЕ добавляются поля в `store.Task`,
  `store.ProcessInstance`, схему SQLite; после `complete` payload не воскрешается ни
  рестартом, ни перечтением Store.
- **FR-010**: `данные` MUST быть read-only внутри тела шага (как тело триггера):
  чтение полей разрешено, переприсвоение `присвоить данные = …` запрещено.
- **FR-011**: `ProcessRuntime` MUST остаться 8 методов (НЕ шов); `internal/eval` MUST
  НЕ импортировать `store`/`engine`/`jsonval` (`данные` входит как `value.Запись`).
- **FR-012**: Существующие вызовы 4 функций (без `--данные`) MUST передавать пустую
  `Запись` по умолчанию; регресс-поведение complete (golden 007b) — без изменений.
- **FR-013**: B3 MUST переиспользовать `jsonval.PayloadToRecord` — НИКАКОГО второго
  JSON→`Запись` декодера; пакет `jsonval` НЕ создаётся и НЕ лифтится повторно.

### Key Entities

- **payload `данные`**: транзиентная read-only `value.Запись`, декод из `--данные`
  JSON-объекта; область жизни — первый шаг догона одного `complete`; вне догона
  отсутствует (НЕ хранится нигде).
- **протяжка `data`**: внутренний параметр движка, проходящий 4 функции от CLI-входа
  до точки `stepEnv.Define`; на старых путях — пустая `Запись`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `complete … --данные '{"итог":V}'` делает `данные.итог == V` читаемым
  первым шагом догона; присвоение в переменную процесса персистится (наблюдаемо
  через `inspect`/Store). Мутация «не Define данные» → замок красный.
- **SC-002**: Второй шаг того же догона видит `данные` как пустую `Запись`; payload
  отсутствует в Store после complete. Мутация «Define на processEnv» ИЛИ «персист в
  Task» → замок красный.
- **SC-003**: Без `--данные` complete-вывод и exit-код байт-точно совпадают с
  доB3-поведением (регресс-замок зелёный).
- **SC-004**: Плохой JSON → stderr ровно `ladix: неверный JSON в --данные: <деталь>`,
  exit 2, Store не изменён.
- **SC-005**: Дифф `internal/eval`/`internal/store`/`internal/value`/frontend — пуст
  по существу (ни новых полей хранилища, ни импортов eval→store/engine); `ProcessRuntime`
  = 8 методов; 0 новых зависимостей модуля; детерминизм (FixedClock в тестах).

## Assumptions

- `jsonval.PayloadToRecord(payload string) (value.Запись, error)` существует и
  экспортирован (проверено живьём на `aebac92`: `src/internal/jsonval/decode.go:31`).
- Сигнатуры и строки 4 функций — по эмпирике `engine.go` на `aebac92`
  (`Complete`:108, `catchUp`:177, `advanceAfterComplete`:189, `advance`:242; step-loop
  `stepEnv := eval.NewEnvironment(processEnv)`:262, `ExecStepBody`:275). Импл сверяет.
- Read-only барьер `данные` реализуется тем же механизмом, что для тела триггера B4 /
  read-only env (env-`boundary`); B3 опирается на существующий барьер, нового не вводит.
- Семантика декода чисел/null/вложенности — как у `jsonval.PayloadToRecord` (число без
  `.eE` → Целое, int64-overflow → Дробное, `null` → Пусто, объект→Запись, массив→Список).
- Тесты детерминированы FixedClock; БД тестовая (D-AU-9 допускает сброс схемы).
