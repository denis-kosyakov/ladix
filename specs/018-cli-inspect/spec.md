# Feature Specification: B6 — `ladix inspect <id>` (снимок инстанса + лёгкая история задач)

**Feature Branch**: `018-cli-inspect`

**Created**: 2026-06-17

**Status**: Draft

**Input**: B6 вехи M2 автоматизации Ladix — ПОСЛЕДНЯЯ фича вехи. Источник истины:
`docs/automation-model.md` §AU-8 (B6), §AU-2 (контракт Store 15→16, аддитивный инвариант),
§AU-9 (серверная модель, единая `--db`, хелпер `openStore`), §AU-10.C (CLI-ошибки),
§AU-10.D (stdout канон inspect), D-AU-8, D-AU-10. Решения залочены владельцем.

## Резюме

Новая read-only CLI-подкоманда `ladix inspect <id> [--db <path>]` печатает человекочитаемый снимок
одного инстанса процесса (имя процесса, статус, текущий шаг, переменные) и лёгкую историю его задач
(открытые + завершённые). Подкоманда `inspectMain` читает Store НАПРЯМУЮ — `LoadInstance(id)` +
НОВЫЙ read-only метод `ListTasksByInstance(id)` — БЕЗ движка и БЕЗ eval (как `tasksMain`). Метод
`ListTasksByInstance(instanceID string) ([]*Task, error)` (порядок ID ASC) добавляется в контракт
`Store` (15→16, аддитивно по §AU-2) и реализуется в ОБОИХ бэкендах — `MemoryStore` и `SQLiteStore`.
Дефолт хранилища — SQLite `ladix.db` через хелпер `openStore` (введён в B5; семья
`complete`/`tasks`/`emit`/`start`). Слой — только CLI + один метод Store; новой языковой функциональности
нет. После B5→B6 демо-пара исполнима: `ladix start …` создаёт инстанс, `ladix inspect <id>` его
показывает. `--json` и `explain` ОТЛОЖЕНЫ в M3-C5 (D-AU-8).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Снимок инстанса + история задач (Priority: P1)

Оператор смотрит состояние конкретного инстанса по его id из терминала. На выходе — человекочитаемый
снимок (имя процесса, статус, текущий шаг), список переменных инстанса (`имя = значение`) и список
задач инстанса (открытые + завершённые) в порядке ID, с пометкой `, эскалирована` для уже
эскалированных задач.

**Why this priority**: Это ядро B6 и наблюдаемость оператора (хартия §3). Замыкает демо-пару B5→B6:
после `ladix start` инстанс должен быть виден через `inspect` в той же БД. MVP — одна эта история
уже даёт исполнимый `ladix inspect`.

**Independent Test**: `ladix start <файл> эскалация_плана 2500000 --db <tmp>` создаёт `p-000001`; затем
`ladix inspect p-000001 --db <tmp>` → stdout (golden маскирует `<время>`):
```
инстанс p-000001: процесс эскалация_плана, статус ожидает, шаг 'связаться_с_клиентом'
переменные:
  факт = 2500000
задачи:
  t-000001 шаг 'связаться_с_клиентом' → менеджер, срок до <время>, открыта
```
exit 0.

**Acceptance Scenarios**:

1. **Given** инстанс `p-000001` процесса `эскалация_плана`, статус `ожидает`, шаг
   `'связаться_с_клиентом'`, переменная `факт = 2500000`, одна открытая НЕ эскалированная задача
   `t-000001` с дедлайном, **When** `ladix inspect p-000001 --db <db>`, **Then** stdout =
   ```
   инстанс p-000001: процесс эскалация_плана, статус ожидает, шаг 'связаться_с_клиентом'
   переменные:
     факт = 2500000
   задачи:
     t-000001 шаг 'связаться_с_клиентом' → менеджер, срок до <время>, открыта
   ```
   exit 0.
2. **Given** та же задача, но `t.Escalated == true` (эскалирована демоном `serve`, B4), **When**
   `ladix inspect p-000001 --db <db>`, **Then** строка задачи оканчивается `, открыта, эскалирована`
   (суффикс `, эскалирована` после статуса).
3. **Given** задача завершена (`MarkTaskCompleted`, статус `завершена`), **When** inspect, **Then**
   строка задачи содержит `, завершена` (а НЕ `, открыта`); порядок задач — ID ASC независимо от
   статуса (открытые и завершённые в одном списке).
4. **Given** переменные инстанса `{факт: 2500000}`, **When** inspect, **Then** строка переменной =
   `  факт = 2500000` (значение через `value.String`); порядок переменных — порядок `inst.Variables`.
5. **Given** отсутствие `--db`, **When** `ladix inspect p-000001`, **Then** используется SQLite
   `ladix.db` (семья complete/tasks/emit/start), НЕ MemoryStore (без `--db` инстанса бы не было).

### User Story 2 — Неизвестный инстанс (Priority: P1)

Оператор просит снимок инстанса, которого нет в БД. CLI отвергает запрос дословной CLI-ошибкой и
ненулевым кодом выхода.

**Why this priority**: Защита от тихого пустого/мусорного вывода на опечатку id. Дословность ошибки —
exact-match замок §AU-10.C; код выхода 2 — паритет семьи CLI-команд (§EN-8.B).

**Independent Test**: `ladix inspect p-999999 --db <db>` над БД без `p-999999` → stderr =
`ladix: инстанс 'p-999999' не найден`, exit 2.

**Acceptance Scenarios**:

1. **Given** БД без инстанса `p-999999`, **When** `ladix inspect p-999999 --db <db>`, **Then** stderr =
   `ladix: инстанс 'p-999999' не найден`, exit 2, stdout пуст.
2. **Given** `LoadInstance` вернул `ErrInstanceNotFound`, **Then** CLI транслирует сентинел в дословный
   русский текст §AU-10.C (не печатает английский сентинел).

### User Story 3 — Read-only метод Store `ListTasksByInstance` в обоих бэкендах (Priority: P1)

Контракт `Store` получает РОВНО один новый read-only метод
`ListTasksByInstance(instanceID string) ([]*Task, error)`, возвращающий ВСЕ задачи инстанса (открытые
И завершённые) в порядке ID ASC. Реализован в `MemoryStore` и `SQLiteStore` идентично по контракту.
Существующие 15 методов и их сигнатуры не трогаются; число методов 15→16.

**Why this priority**: Метод — единственное несущее изменение бэкенда (§AU-2). Аддитивность и паритет
двух бэкендов — несущий инвариант M2-гейта (drift-watch). Без него inspect не покажет завершённые
задачи (`ListPendingTasks` даёт только открытые).

**Independent Test**: на каждом бэкенде сохранить задачи `t-000003`, `t-000001`, `t-000002` инстанса
`p-000001` (вперемешку) + задачу `t-000010` другого инстанса `p-000002` → `ListTasksByInstance("p-000001")`
возвращает РОВНО `[t-000001, t-000002, t-000003]` в порядке ID ASC, без `t-000010`. Параллельно
проверить, что число методов интерфейса `Store` = 16 (15 старых не тронуты).

**Acceptance Scenarios**:

1. **Given** инстанс с тремя задачами, сохранёнными вперемешку, **When** `ListTasksByInstance(id)`,
   **Then** результат отсортирован по ID ASC (замок порядка) в обоих бэкендах.
2. **Given** задачи двух инстансов, **When** `ListTasksByInstance(id1)`, **Then** возвращены только
   задачи `id1` (фильтрация по `InstanceID`).
3. **Given** инстанс со смешанными статусами (открытые + завершённые), **When** `ListTasksByInstance(id)`,
   **Then** возвращены ОБЕ группы (в отличие от `ListPendingTasks` — только открытые).
4. **Given** инстанс без задач, **When** `ListTasksByInstance(id)`, **Then** результат пуст (`nil`/`[]`),
   ошибки нет.
5. **Given** задача с `Escalated == true`, **When** `ListTasksByInstance(id)`, **Then** поле `Escalated`
   сохранено в возвращённой задаче (SQLite-кодек читает колонку `escalated`).

### Edge Cases

- **Инстанс без задач**: блок `задачи:` печатается, но без строк-задач под ним (форма блока при пустом
  списке закрепляется в contracts/inspect-cli.md по §AU-10.D). Переменные печатаются как обычно.
- **Инстанс без переменных** (пустой `Variables`): блок `переменные:` без строк-переменных.
- **Завершённый/терминальный инстанс** (статус `выполнен`): снимок печатает терминальный статус и
  последний обработанный шаг (`CurrentStep`); задачи показываются как `завершена`.
- **Дедлайн отсутствует** (`Deadline == nil`): хвост `срок до <время>` НЕ печатается у строки задачи
  (паритет `FormatTaskLine`); строка задачи — `t-… шаг '…' → исполнитель, открыта[, эскалирована]`.
  Точная форма строки без дедлайна — закрепить в contracts по §AU-10.D.
- **Read-only гарантия**: `inspect` не пишет в Store (ни `SaveInstance`, ни `SaveTask`); чисто чтение.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять подкоманду `ladix inspect <id> [--db <path>]`; диспетчеризация
  `cmd/ladix/main.go` switch `case "inspect": return inspectMain(args[1:], stdout, stderr)`.
- **FR-002**: `inspectMain` ДОЛЖНА разбирать один позиционный `<id>` и флаг `--db <path>` (форма
  `--db путь` и `--db=путь`), дефолт `defaultDBPath="ladix.db"` (D-AU-10).
- **FR-003**: При отсутствии позиционного `<id>` система ДОЛЖНА печатать usage и завершаться с кодом 2.
- **FR-004**: `inspectMain` ДОЛЖНА открывать Store через хелпер `openStore(dbPath)` (§AU-9): непустой
  путь → `SQLiteStore` (defer Close), пустой → `MemoryStore`; дефолт-путь непуст → SQLite.
- **FR-005**: `inspectMain` ДОЛЖНА читать состояние НАПРЯМУЮ через `st.LoadInstance(id)` и
  `st.ListTasksByInstance(id)` — БЕЗ движка (`engine`) и БЕЗ eval/интерпретатора.
- **FR-006**: Если `LoadInstance(id)` вернул `ErrInstanceNotFound`, система ДОЛЖНА печатать на stderr
  ДОСЛОВНО `ladix: инстанс '<id>' не найден` и завершаться с кодом 2; stdout пуст.
- **FR-007**: При успехе система ДОЛЖНА печатать на stdout снимок инстанса первой строкой ДОСЛОВНО:
  `инстанс <id>: процесс <имя_процесса>, статус <статус>, шаг '<текущий_шаг>'`, где `<статус>` —
  русское строковое значение `inst.Status` (напр. `ожидает`), `<текущий_шаг>` — `inst.CurrentStep`.
- **FR-008**: Система ДОЛЖНА печатать блок `переменные:` и под ним по строке на переменную в формате
  `  <имя> = <значение>`, где `<значение>` = `value.String(v)`, в порядке итерации `inst.Variables`.
- **FR-009**: Система ДОЛЖНА печатать блок `задачи:` и под ним по строке на задачу из
  `ListTasksByInstance(id)` (порядок ID ASC) в формате
  `  <t-id> шаг '<шаг>' → <исполнитель>[, срок до <время>], <статус>[, эскалирована]`, где `<статус>` —
  `открыта`/`завершена`; хвост `, срок до <время>` — только при `Deadline != nil`; суффикс
  `, эскалирована` — ТОЛЬКО при `t.Escalated == true`. Точные разделители/позиции — §AU-10.D.
- **FR-010**: Метка `, эскалирована` ДОЛЖНА присутствовать тогда и только тогда, когда поле
  `t.Escalated` истинно (поле введено в B4/016, D-AU-5).
- **FR-011**: Контракт `Store` ДОЛЖЕН получить РОВНО один новый метод
  `ListTasksByInstance(instanceID string) ([]*Task, error)` (read-only), доводя число методов до 16;
  существующие 15 методов и сигнатуры (`store.go:12-34`) НЕ меняются (аддитивный инвариант §AU-2).
- **FR-012**: `ListTasksByInstance` ДОЛЖЕН возвращать ВСЕ задачи указанного инстанса (открытые И
  завершённые), отфильтрованные по `InstanceID`, отсортированные по ID ASC; для инстанса без задач —
  пустой результат (`nil`/`[]`), без ошибки.
- **FR-013**: `ListTasksByInstance` ДОЛЖЕН быть реализован в `MemoryStore` (сортировка `out[i].ID < out[j].ID`)
  И в `SQLiteStore` (`SELECT … FROM tasks WHERE instance_id = ? ORDER BY id ASC`); SQLite-вариант ДОЛЖЕН
  читать колонку `escalated` (как `ListPendingTasks`) через общий `buildTask`/`scanTask`, чтобы поле
  `Escalated` не терялось.
- **FR-014**: `inspect` ДОЛЖЕН быть read-only: НЕ вызывать `SaveInstance`/`SaveTask`/`MarkTaskCompleted`
  или иные пишущие методы Store.
- **FR-015**: Все stdout-форматы (FR-007..FR-009) — exact-match golden; golden маскирует `<время>`
  дедлайна. Тексты — дословно из §AU-10.D (Принцип VIII: канон якоря).
- **FR-016**: CLI-ошибки stderr (FR-006) — exact-match; дословно из §AU-10.C.
- **FR-017**: Изменения НЕ затрагивают каталог диагностик `L=11`/`SE=14`/`eval=28` (CLI-ошибки — stderr
  cmd-слоя, не каталог). `ProcessRuntime`=8 НЕ трогается; eval без store/engine.
- **FR-018**: Единая `--db`/`openStore` НЕ ломает существующие команды (`start`/`complete`/`tasks`/
  `emit`/`serve`/`run`/`metric`); их golden и поведение целы (§EN-7/007b/durable B4).

### Key Entities *(include if feature involves data)*

- **ProcessInstance** (существ., `store/types.go`): `ID`, `ProcessName`, `Status`, `CurrentStep`,
  `Variables map[string]value.Value`. Источник снимка (FR-007/FR-008). Не меняется.
- **Task** (существ., `store/types.go`, 9 полей вкл. `Escalated bool` из B4): `ID`, `InstanceID`,
  `StepName`, `Assignee`, `Deadline *time.Time`, `Status`, `Escalated`. Источник строк задач
  (FR-009/FR-010). Не меняется.
- **Store** (контракт, `store/store.go`): получает `ListTasksByInstance` (16-й метод, read-only).

## Success Criteria *(mandatory)*

- **SC-001**: `ladix inspect <id> --db <db>` над существующим инстансом печатает снимок + историю
  exact-match по §AU-10.D (golden маскирует `<время>`), exit 0.
- **SC-002**: Эскалированная задача показывает суффикс `, эскалирована`; не-эскалированная — НЕ
  показывает (инверсия-замок суффикса).
- **SC-003**: Неизвестный инстанс → `ladix: инстанс '<id>' не найден`, exit 2, stdout пуст.
- **SC-004**: `ListTasksByInstance` возвращает задачи инстанса в порядке ID ASC (открытые +
  завершённые), отфильтрованные по инстансу, в ОБОИХ бэкендах; пустой инстанс → пусто/без ошибки.
- **SC-005**: Контракт `Store` = 16 методов; 15 старых сигнатур не тронуты (компиляция + счётный замок).
- **SC-006**: Единая `--db`/`openStore` без регресса: существующие golden команд зелёные; каталог
  L=11/SE=14/eval=28 цел.
- **SC-007**: 0 новых зависимостей; детерминизм (id/время) для golden; `inspect` read-only (Store не
  пишется).

## Out of Scope (M3+)

- `--json` вывод и `explain` (почему сработал триггер / trace метрики) — ОТЛОЖЕНЫ в M3-C5 (D-AU-8).
- Полная трассировка истории / фильтры по статусу задач / пагинация.
- Любая новая языковая/синтаксическая функциональность; изменения eval/engine/ProcessRuntime.
- Реальные миграции схемы Store (D-AU-9: сброс схемы; M3-C2).

## Assumptions

- Сигнатура метода — `[]*Task` (slice указателей), дословно по §AU-2 (`store.go` зеркалит
  `ListPendingTasks`/`ListInstancesByStatus`). (Бриф упоминал `[]Task` — расходится с якорем; следуем
  якорю §AU-2.)
- Статус инстанса печатается как русское значение `inst.Status` (`ожидает`/`выполнен`/…) без перевода.
- Формат `<время>` дедлайна — `2006-01-02 15:04` (как `FormatTaskLine`/`deadlineLayout`), маскируется в
  golden.
- Точные разделители строк задач/переменных и форма блоков при пустых списках — закрепляются в
  contracts/inspect-cli.md строго по §AU-10.D.
