# Quickstart: Лексер Ladix (001-lexer-tokens)

**Feature**: 001-lexer-tokens | **Plan**: [plan.md](./plan.md)

Как разработчику начать реализацию и проверять лексер. На этом шаге создаются только пакеты
`internal/errors` и `internal/lexer` (+ каркас Go-модуля). Корень модуля — `src/`.

## 0. Каркас модуля (Фаза 0)

```bash
cd src
go mod init github.com/denis-kosyakov/ladix   # go 1.22
# структура (создаётся по мере фаз):
#   src/internal/errors/{position,lexerror,aggregate,warning}.go (+ _test.go)
#   src/internal/lexer/{token,lexer,indent,scan_*,keywords,panic_mode}.go (+ _test.go)
```

## 1. Цикл tests-first (конституция VI, FR-028)

Для КАЖДОЙ категории токенов и КАЖДОГО канонического текста ошибки — табличный тест **до/вместе** с
кодом:

```bash
cd src
go test ./internal/errors/...      # формат двухстрочной ошибки, развёртка errors.As, агрегат
go test ./internal/lexer/...       # таблицы токенов по категориям + 11 канонических ошибок
go test ./...                      # всё вместе
```

Табличный тест токенов сверяет последовательность `(Type, Lexeme, Pos)` с эталоном; тест ошибок
сверяет `(категория, Pos, Msg)` через двухстрочное представление. Источники эталонов:
- токены и разграничения → [contracts/token-stream.md](./contracts/token-stream.md) §C-4;
- тексты ошибок (дословно) → [contracts/lexical-errors.md](./contracts/lexical-errors.md).

## 2. Гейты качества (конституция I, FR-027, SC-006)

```bash
cd src
gofmt -l .            # пусто = отформатировано
go vet ./...          # без замечаний
go build ./...        # собирается чисто
```

Все три ОБЯЗАНЫ быть чистыми до завершения каждой задачи.

## 3. Чек-лист приёмки по фазам (по приоритетам US)

- **P1 (US1, MVP)** — поток токенов валидной программы:
  - [ ] `пусть x = 5_000` → `KW(пусть)·IDENT(x)·ASSIGN·INT("5000")·NEWLINE·EOF` (SC-001)
  - [ ] `5.поле` → `INT("5")·DOT·IDENT(поле)`; `1.5дн` → `FLOAT(1.5)·IDENT(дн)`
  - [ ] вложенные блоки → `INDENT`/`DEDENT` по уровням; внутри `[ … ]` переводы прозрачны
  - [ ] пустой ввод → один `EOF`; поток ВСЕГДА завершается `EOF` (SC-003)
- **P2 (US2)** — диагностика:
  - [ ] каждый из 11 текстов воспроизводится ДОСЛОВНО, по одному кейсу (SC-004)
  - [ ] колонка считается в рунах на кириллическом префиксе (SC-002)
- **P3 (US3)** — panic-mode:
  - [ ] ≥2 ошибки на разных строках → несколько ошибок без фантомов; накопитель ≤ ≈20; поток → `EOF` (SC-005)
  - [ ] после ошибочной лексемы валидные токены остатка строки продолжают эмититься (best-effort, вариант a — C-1.6)

## 4. Границы (НЕ делать на этом шаге)

- НЕ парсер/AST/eval/движок/CLI/Store; лексер НЕ диагностирует незакрытые скобки/блоки.
- НЕ проверять диапазон int64 у `INT` и величины `DURATION` — несём цифровую лексему строкой
  (диапазон у парсера, guardrail 1).
- НЕ резолвить семантику (периоды, встроенные функции, поля записи — `IDENT`).
- НЕ печатать сводку «Найдено K ошибок.» и не форматировать вывод CLI.
