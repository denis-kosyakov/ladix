## Формат: `[ID] [P?] [Story?] Описание + путь к файлу`

- **[P]**: можно выполнять параллельно (разные файлы, нет зависимостей от незавершённых задач)
- **[Story]**: к какой user story относится задача (US1, US2, US3); фазы Setup/Foundational/Polish — без метки
- Каждая задача указывает точный путь к файлу

## Фаза 5: User Story 3 — несколько ошибок за прогон, panic-mode (Priority: P3)

**Goal**: лексер не останавливается на первой ошибке — собирает несколько ошибок в `ErrorList` (бюджет ≈20) без фантомного каскада; проблемная лексема пропускается, валидные токены остатка строки всё равно эмитятся (вариант **a**); поток всегда завершается `EOF`.

**Independent Test**: вход с ≥2 ошибками на разных строках → собрано несколько ошибок (по одной на проблему, без фантомов), накопитель ≤ ≈20, поток завершается ровно одним `EOF`; после ошибочной лексемы валидные токены остатка продолжают эмититься (C-1.6). Гейт: SC-005.

**Зависимость от US2**: нужны зарегистрированные ошибки (US2), чтобы их накапливать и синхронизировать.

### Тесты US3 (пишутся ПЕРВЫМИ, обязаны падать) ⚠️

- [ ] T033 [US3] Табличный тест panic-mode в `src/internal/lexer/panic_mode_test.go`: US3.1 (2 независимые ошибки на строках N и N+2 → ровно две ошибки с верными позициями, поток → `EOF`); US3.2 (`пусть x = @ + 5` → поток `KW·IDENT·ASSIGN·PLUS·INT·NEWLINE·EOF`, ровно одна ошибка «неожиданный символ '@'», токен `@` не создаётся — вариант a, C-1.6); US3.3 (>лимита → накопитель ≤ ≈20, поток → `EOF`) (SC-005)

### Реализация US3

- [ ] T034 [US3] Контроллер panic-mode в `src/internal/lexer/panic_mode.go`: при ошибке — регистрация в `ErrorList`; до точки синхронизации (следующий нормализованный `\n`; внутри незакрытых скобок — физический перевод, A4) подавлять регистрацию ТОЛЬКО НОВЫХ ошибок (без фантомов); проблемная лексема пропускается (токен не эмитится — как L-11), остаток строки токенизируется штатно; мягкий предел ≈20 (A3); поток всегда → `EOF` (FR-025/FR-026, guardrail 6)

## Зависимости и порядок выполнения

### Зависимости фаз

- **Setup (Фаза 1)**: без зависимостей — старт немедленно.
- **Foundational (Фаза 2)**: после Setup — БЛОКИРУЕТ все user stories.
- **US1 (Фаза 3)**: после Foundational. MVP.
- **US2 (Фаза 4)**: после US1 (наслаивает error-детекцию на сканеры US1). Тестируется отдельным гейтом.
- **US3 (Фаза 5)**: после US2 (накапливает зарегистрированные ошибки).
- **Polish (Фаза 6)**: после всех желаемых US.

> Примечание: в отличие от типового speckit-параллелизма, здесь US1→US2→US3 **последовательны** (P2/P3 модифицируют те же файлы сканеров и опираются на поток US1) — это зафиксировано планом («P2 опирается на P1; P3 — на P2»). Каждая US при этом остаётся НЕЗАВИСИМО ТЕСТИРУЕМОЙ через свой набор `*_test.go` и гейт SC.

- T001 → T002 → (Фаза 2).

## Заметки

- `[P]` = разные файлы, нет зависимостей от незавершённых задач.
- `[Story]` (US1/US2/US3) связывает задачу с user story для трассируемости.
- Тесты пишутся и **падают** до реализации (конституция VI, FR-028).
- Все пользовательские тексты — русские, дословно по contracts/lexical-errors.md (FR-024); переформулировать ЗАПРЕЩЕНО.
- `INT` и числовая величина `DURATION` несутся СТРОКОЙ; диапазон int64 проверяет парсер (guardrail 1) — лексер на величине НЕ падает.
- Коммит после каждой задачи или логической группы; останавливаться на любом checkpoint для независимой валидации US.
- Избегать: расплывчатых задач, конфликтов по одному файлу в `[P]`, кросс-сторовых зависимостей, ломающих независимую тестируемость.
