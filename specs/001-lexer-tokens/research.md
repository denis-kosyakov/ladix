# Phase 0 — Research & Decisions: Лексер Ladix

**Feature**: 001-lexer-tokens | **Date**: 2026-06-01 | **Plan**: [plan.md](./plan.md)

Спека предельно детальна (FR-001..FR-029, A1–A5, D1–D4), поэтому **открытых
`NEEDS CLARIFICATION` нет**. Этот документ фиксирует ключевые проектные решения лексера в формате
*Decision / Rationale / Alternatives*, чтобы код и задачи (`/speckit-tasks`) не дрейфовали.
Каждое решение опирается на размещённые источники истины (конституция IX).

---

## D-R1. `Position` — в `internal/errors`, тип `errors.Position` (A1)

- **Decision**: на этом шаге `Position{Line, Col int}` (1-based, руны) живёт в `internal/errors`;
  `Token.Pos` имеет тип `errors.Position`. Граф: `lexer → errors`; лексер **не** импортирует `ast`.
- **Rationale**: SPEC §13 говорит об «общей `Position`» в `internal/errors`; конституция III/IV
  требует общую встраиваемую `Position{Line, Col}`. Для лексера это естественно и не создаёт цикла
  (`lexer` и так зависит от `errors` ради `LexError`).
- **Alternatives considered**:
  - Локальная `Position` в `ast` (ARCHITECTURE §4.1, ради листовости `ast`) — отвергнута **для этого
    шага**: лексер не зависит от `ast`, тащить её сюда нельзя. Противоречие реально только на шаге AST.
- **Статус**: **D1 — ОТЛОЖЕН** до шага AST/parser; здесь НЕ решается (guardrail 3).

## D-R2. `INT`: цифровая строка, без int64-конверсии и диапазон-проверки (D2/B2)

- **Decision**: корректный по форме целый прогон цифр (с допустимыми `_`) лексер эмитит как `INT`,
  неся **нормализованную цифровую строку** (цифры без `_`) КАК СТРОКУ. Преобразование в `int64` и
  проверку диапазона выполняет **парсер** при сборке числового литерала. `MinInt64`
  (`-9_223_372_036_854_775_808`) невыразим целым литералом (свёртка знака — у парсера, беззнаковая
  проверка). Лексер на величине НЕ падает; битую ФОРМУ (`1__000`, `_5`, `5_`) по-прежнему ловит как
  лексическую ошибку «неверный числовой литерал».
- **Rationale**: SPEC §4 (строка про `Целое`) и §13.1/§13.4 классифицируют «целый литерал вне
  диапазона» как **статическую ошибку парсера**, не лексическую и не рантайм. Прецеденты: Go
  (type-check), Rust (lint), Monkey (parser). Несение строки делает лексер устойчивым к 30-значным
  числам и сохраняет одно место диапазон-проверки.
- **Alternatives considered**:
  - Диапазон-проверка в лексере с новым текстом «числовой литерал вне диапазона Целое» — отвергнута
    владельцем спеки (D2, вариант B): диапазон — забота парсера.
  - Рантайм-категория (как у арифметического переполнения) — отвергнута: литерал известен статически.
- **Статус**: **D2 — РЕШЁН** (вариант B/B2). Guardrail 1.

## D-R3. `DURATION`: числовая величина тоже несётся как лексема, без диапазон-проверки (FR-017)

- **Decision**: после ЦЕЛОГО числа слитный буквенный run читается жадно и сверяется с
  {`сек`,`мин`,`час`,`дн`,`нед`,`мес`}; точное совпадение → `DURATION` (единица + числовая лексема).
  Числовую **величину** длительности лексер в int64 НЕ конвертирует и на диапазон НЕ проверяет —
  несёт как лексему; конверсию/диапазон делает парсер (единое правило с `INT`, D-R2).
- **Rationale**: единое место диапазон-проверки и согласованность с FR-007. Переполнение величины
  длительности (>9.2e18) — вырожденный edge; отдельный диагностический текст НЕ вводится —
  переиспользуется формулировка целого литерала (§13.4), чтобы не раздувать канон.
- **Alternatives considered**:
  - Отдельный спец-текст «длительность вне диапазона» в §13.4 — отвергнут (раздувание вырожденного
    edge). Если он когда-нибудь понадобится — это открытый микровопрос к владельцу спеки, не молчаливая
    вставка.
- **Статус**: согласовано (хвост ревью D2). Guardrail 1/2.

## D-R4. Контракт значения токена (FR-007)

- **Decision**: `FLOAT` несёт предразобранное `float64`; `STRING` — развёрнутую строку (escape
  раскрыты); `DURATION` — единицу (`сек`…`мес`) + числовую лексему-строку; `INT` — нормализованную
  цифровую строку (без int64); `BOOL` (`истина`/`ложь`) — готовое булево; `NONE` (`пусто`) — без
  значения; прочие токены несут лексему как есть. Каждый токен несёт позицию **первой руны** лексемы.
- **Rationale**: предразбор того, что лексер умеет разобрать однозначно и без потери (float, string),
  упрощает парсер; то, что требует диапазон-семантики (`INT`/величина `DURATION`), оставляется строкой.
- **Alternatives considered**: предразбор `INT` в `int64` — отвергнут (D-R2). Хранить `STRING` сырой
  (без раскрытия escape) — отвергнуто: FR-018 требует развёрнутого значения.
- **Статус**: Guardrail 2.

## D-R5. Английские публичные имена, русские сообщения (A2/D4)

- **Decision**: публичные Go-имена — английские идиоматичные: `Lexer`, `Token`, `TokenType`,
  `Position`, `LexError`, агрегат `ErrorList`, `Warning`. Тексты сообщений — русские, дословно по SPEC §13.
- **Rationale**: конституция III («явные типы», английские идентификаторы кода) и VIII («сообщения —
  русские, дословно») вместе; конституция имеет приоритет над русскими именами типов ARCHITECTURE §8.2
  (`ЛексическаяОшибка`). Имя агрегата — `ErrorList` (идиоматичный «список ошибок»): обращение
  `errors.ErrorList` читается без заикания-повтора в квалификаторе пакета.
- **Alternatives considered**: русские имена типов (`ЛексическаяОшибка`) из ARCHITECTURE §8.2 —
  отвергнуты: конституция III приоритетна, английские имена идиоматичны для Go.
- **Статус**: **D4 — РЕШЁН**. Guardrail 4.

## D-R6. Объём `internal/errors` на этом шаге (A5)

- **Decision**: реализуются только `Position`, `LexError` (Pos + Msg, двухстрочный `Error()`,
  `errors.As`-дружба), агрегат нескольких ошибок (накопление + развёртка `Unwrap() []error`), и
  зарезервированный тип `Warning` (структура есть, лексер его НЕ порождает). Прочие категории
  (`ParseError`, `СемантическаяОшибка`, …) — будущие шаги.
- **Rationale**: пакет `errors` — листовой (ARCHITECTURE §2.1) и общий для всех; но раздувать его до
  всех шести категорий сейчас не нужно — лексеру хватает указанного объёма. Заголовок предупреждения
  зарезервирован (FR-004) ради стабильности контракта формата.
- **Alternatives considered**: сразу все категории ошибок — отвергнуто (вне границ, YAGNI на шаге).
- **Статус**: Guardrail 5.

## D-R7. Panic-mode: синхронизация и бюджет (A3/A4, FR-025/FR-026)

- **Decision** (вариант **a**, решён владельцем): обнаружив лексическую ошибку, лексер регистрирует её
  в агрегат и **до конца текущей логической строки** (следующий нормализованный `\n`; внутри незакрытых
  скобок логическая строка не завершается — синхронизация идёт до физического перевода) НЕ регистрирует
  НОВЫЕ ошибки (без каскада фантомов). Токенизация при этом продолжается штатно: проблемная лексема
  пропускается (токен не эмитится — как у L-11), а остаток строки разбивается на токены и попадает в
  поток — подавляются ТОЛЬКО ошибки, токены остатка эмитятся. Накопитель ограничен **≈20** лексическими
  сообщениями (мягкий предел, бюджет общий с парсером). Поток токенов всё равно завершается одним `EOF`.
  Лексер **не** печатает «Найдено K ошибок.» (это слой CLI/агрегат-потребитель).
- **Rationale**: SPEC §13.2 (panic-mode для лексера+парсера, ≈20), FR-025/FR-026. «≈20» трактуется как
  деталь реализации (A3); точка синхронизации — `\n` (A4).
- **Alternatives considered**: fail-fast (стоп на первой ошибке) — отвергнут: US3 требует пакетной
  диагностики. Синхронизация по токену, а не по строке — отвергнута: §13.2/A4 фиксируют конец строки.
- **Открытая форвард-нота (не новое расхождение)**: фактическая механика *слияния* бюджета лексера и
  парсера — забота сборки пайплайна на шаге парсера; лексер ограничивает только собственное накопление.
  Помечено для шага парсера, здесь не доопределяется.
- **Статус**: Guardrail 6.

## D-R8. Ручной посимвольный сканер, без regex (конституция II)

- **Decision**: токенизация — посимвольный скан по рунам; операторы — жадным максимальным совпадением
  (`==`,`!=`,`<=`,`>=`,`//` — по одному токену; `!` валиден только как часть `!=`, одиночный `!` →
  «неожиданный символ '!'»). Идентификатор читается жадно до первого не-словарного символа, затем
  сверяется с таблицами по полной строке.
- **Rationale**: конституция II ЗАПРЕЩАЕТ regex и генераторы для токенизации; ручной скан даёт полный
  контроль над позициями (конституция IV) и диагностикой.
- **Alternatives considered**: regexp/участники-комбинаторы — ЗАПРЕЩЕНЫ конституцией.
- **Статус**: Guardrail (II).

## D-R9. Нормализация ввода и прозрачность (FR-011/FR-014/FR-022)

- **Decision**: до токенизации ридер отбрасывает ведущий BOM и нормализует `\r\n` и одиночный `\r` в
  `\n` (дальше `\r` не встречается). `#` вне строки — комментарий до конца строки (прозрачен); `#`
  внутри строки — обычный символ. Пустые строки и строки только с комментарием прозрачны для отступов
  (NEWLINE не эмитится, отступ не пересчитывается). Регистр значим.
- **Rationale**: FR-011/FR-014/FR-022, SPEC §2. Нормализация до скана упрощает позиционный учёт и
  правила отступов.
- **Alternatives considered**: обработка `\r` в основном цикле — отвергнута (усложняет позиции);
  нормализация на входе чище.
- **Статус**: Guardrail (правила сканирования).

## D-R10. «Табы запрещены» — два текста (D3) и прочие канонические тексты

- **Decision**: таб в ведущих пробелах → «табы в отступах запрещены, используйте пробелы» (§13.4
  дословно); таб между токенами/в строке → «табы запрещены, используйте пробелы» (D3 — доопределение
  брифа, согласовано со SPEC §2 «табы запрещены везде»). Полный каталог из 11 текстов — в
  [contracts/lexical-errors.md](./contracts/lexical-errors.md), воспроизводится ДОСЛОВНО (FR-024).
- **Rationale**: §13.4 дословно содержит только текст для отступа; второй текст — осознанное
  доопределение, согласованное со SPEC §2.
- **Статус**: **D3 — РЕШЁН** (доопределение).

## D-R11. Позиция токена `EOF` (вскрыто верификацией плана, решено владельцем)

- **Decision**: `EOF` несёт позицию **сразу после последней обработанной руны ввода** (куда встал бы
  следующий символ): на пустом вводе — `(1, 1)`; после финального (физически последнего) перевода
  строки — следующая логическая строка, колонка 1. **Уточнение 1 (синтетические NEWLINE/DEDENT на
  EOF)**: NEWLINE (завершение последней логической строки) и серия DEDENT (закрытие уровней),
  эмитируемые на EOF (FR-023), несут ТУ ЖЕ позицию, что и EOF — у этих маркеров конца нет собственной
  диагностической нагрузки. **Уточнение 2 (хвостовые пустые строки)**: FR-022 делает хвостовые пустые
  строки прозрачными для эмиссии NEWLINE и подсчёта отступов, но руны `\n` всё равно поглощаются,
  поэтому EOF встаёт после ФИЗИЧЕСКИ последней руны (`"abc\n\n\n"` → `(4, 1)`); «финальный `\n`» в
  правиле = физически последний перевод строки. Зафиксировано как РЕШЁННОЕ правило в FR-009/FR-023,
  contracts/token-stream.md C-5 и data-model.md §5.6.
- **Rationale**: FR-009 ранее задавал позицию `EOF` прозой «в конце ввода», тогда как у
  NEWLINE/INDENT/DEDENT колонка определена точно. Конституция IV требует `Position` на КАЖДОМ токене.
  Выбран конвенциональный для лексеров дефолт (позиция «следующего символа»), согласованный с
  существующим инвариантом 1-based (`Line ≥ 1, Col ≥ 1`, data-model §1) для пустого ввода.
- **Alternatives considered**:
  - Позиция последней руны (а не «после неё») — отвергнута: «после последней руны» естественнее для
    маркера конца и единообразна с тем, куда указывал бы курсор парсера.
  - Оставить отложенным микровопросом — отвергнуто владельцем (правило фиксируется сейчас).
- **Замечание**: точная `(Line, Col)` у `EOF` не несёт нагрузки ни для одной диагностики лексера
  (C-6: незакрытые скобки на `EOF` диагностирует парсер), поэтому риск низкий; правило закрывает пробел
  ради единообразия и конституции IV. ARCHITECTURE §4.2 резервирует поле `EOFPos` — согласуется.
  Уточнения 1–2 закрывают вскрытые ревью пробелы по позициям синтетических NEWLINE/DEDENT на `EOF` и по
  хвостовым пустым строкам.
- **Статус**: **РЕШЁН** (владелец, конвенциональный дефолт).

## Структурные решения

- **S1 — Корень Go-модуля = `src/`** (module `github.com/denis-kosyakov/ladix`). Учебный шаблон
  (`src/AGENTS.md`) размещает реализацию в `src/`; ARCHITECTURE §2 разрешает корень «в `src/` либо в
  корне». Внутри — стандартная Go-раскладка (`internal/...`, `cmd/ladix/`). Решение обратимо.
- **S2 — Тесты co-located** (`*_test.go` рядом с пакетами), идиома Go + конституция I/VI. Верхнеуровневый
  `tests/` шаблона остаётся для будущих кросс-срезовых тестов.

**Все `NEEDS CLARIFICATION` разрешены.** Adversarial-верификация плана вскрыла две неоднозначности, обе
закрыты владельцем: недоопределённую позицию `EOF` — **решена** (D-R11); и эмиссию токенов остатка
строки в panic-mode — **разрешена** владельцем по варианту **a** (после ошибки подавляется только
регистрация новых ошибок, токены остатка эмитятся; D-R7, FR-025). Ложной по итогу осталась только одна
громкая находка верификации — счёт «37 vs 34 ключевых слов»: артефакт здесь корректен (34 вида токенов;
`истина`/`ложь`/`пусто` идут BOOL/NONE) и правок не требует.
