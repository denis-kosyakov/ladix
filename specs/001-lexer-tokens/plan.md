# Implementation Plan: Лексер Ladix (поток токенов + лексические ошибки)

**Branch**: `001-lexer-tokens` | **Date**: 2026-06-01 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-lexer-tokens/spec.md`

## Summary

Реализовать **лексер** Ladix: пакет `internal/lexer`, превращающий UTF-8-исходник `.ladix`
в плоский поток токенов с позициями (включая виртуальные `NEWLINE`/`INDENT`/`DEDENT`/`EOF`),
и пакет `internal/errors` в объёме, нужном лексеру (`Position`, `LexError`, агрегат ошибок,
зарезервированный `Warning`). Только токены и лексическая диагностика — **НЕ** парсер, **НЕ** AST.

**Технический подход**: ручной посимвольный сканер (recursive-descent-совместимый, без regex и
кодогенерации — конституция II), стек уровней отступа → виртуальные токены, panic-mode-накопление
лексических ошибок с синхронизацией до конца логической строки. Числовые лексемы (INT и числовая
величина DURATION) несутся **как строки** — диапазон int64 проверяет парсер на следующем шаге
(D2/B2). Граф зависимостей: `lexer → errors`; `lexer` НЕ зависит от `ast` (A1).

Структура поставки следует приоритетам user stories: **P1** поток токенов валидной программы (MVP) →
**P2** позиционная лексическая диагностика → **P3** panic-mode (несколько ошибок за прогон).

## Technical Context

**Language/Version**: Go **1.22+**, единый модуль, без CGO (конституция I).

**Primary Dependencies**: только стандартная библиотека Go (`unicode`, `unicode/utf8`, `strings`,
`errors`, `fmt`). Внешних зависимостей лексер **не вводит**; `modernc.org/sqlite` к этому шагу
не относится. Генераторы лексеров/парсеров и regex для токенизации — ЗАПРЕЩЕНЫ (конституция II).

**Storage**: N/A (лексер — чистая трансформация `[]byte`/`string` → `[]Token` + `[]LexError`).

**Testing**: `go test` с **табличными** (table-driven) тестами, co-located `_test.go` рядом с
пакетами (`internal/lexer`, `internal/errors`); `testify/require` ДОПУСКАЕТСЯ точечно (конституция VI).
Tests-first: тест на каждую категорию токенов и на каждый канонический текст ошибки.

**Target Platform**: кросс-платформенный статический бинарник (Windows/macOS/Linux одной командой
`go build`); лексер платформонезависим.

**Project Type**: компонент компилятора/интерпретатора (библиотечный пакет внутри `internal/`).

**Performance Goals**: явных числовых целей нет; ориентир — линейный однопроходный скан O(n) по рунам
без переразбора. Аллокации не критичны на этом шаге (учебный масштаб входов).

**Constraints**:
- Позиции `(строка, колонка)` 1-based, считаются **в рунах** (Unicode code points), не в байтах
  (конституция IV).
- Без изменяемого пакет-уровневого состояния; экземпляр `Lexer` создаётся явно (конституция V, FR-029).
- Все пользовательские тексты — **на русском**, дословно по канону SPEC §13 (конституция VIII).
- Поток токенов **всегда** завершается ровно одним `EOF` (FR-008/FR-023).

**Scale/Scope**: ровно два пакета — `internal/lexer` (+ co-located тесты) и `internal/errors`
(в объёме A5). 67 видов токенов, 11 канонических лексических ошибок, 12 зарезервированных слов,
6 единиц длительности, 4 escape-последовательности.

## Guardrails — контракт реализации (нормативно для tasks/implement)

План фиксирует следующие инварианты как **контракт**, чтобы код не дрейфовал. Каждый — нормативен
(нарушение = регресс, ловится тестом и/или ревью):

1. **Лексер НЕ проверяет диапазон int64** — ни у `INT`, ни у числовой величины `DURATION`. Корректный
   по форме прогон цифр эмитится с **нормализованной цифровой строкой** как лексемой; преобразование в
   `int64` и проверку диапазона выполняет **парсер** (D2/B2). `MinInt64` невыразим целым литералом
   (свёртка знака — у парсера). Лексер на величине НЕ падает. (FR-016, FR-017)
2. **Контракт значения токена** (FR-007): `FLOAT`/`STRING` — предразобранное значение (float64 /
   развёрнутая строка); `DURATION` — единица + числовая лексема; `INT` — нормализованная цифровая
   строка (без предразбора в int64); прочие токены — лексема как есть.
3. **`Position` живёт в `internal/errors`**; `Token.Pos` имеет тип `errors.Position`; граф зависимостей
   `lexer → errors`, лексер **НЕ** зависит от `ast` (A1). **D1 здесь НЕ решается** (отложен до AST-шага).
4. **Публичные Go-имена — английские и идиоматичные**: `Lexer`, `Token`, `TokenType`, `Position`,
   `LexError`, агрегат ошибок. Тексты пользовательских сообщений — **русские** (A2/D4).
5. **`internal/errors` на этом шаге — только объём, нужный лексеру**: `Position`, `LexError`, агрегат
   нескольких ошибок, зарезервированный тип `Warning` (лексер предупреждений **не** порождает). Прочие
   категории ошибок (`ParseError`, …) — на будущих шагах (A5).
6. **Panic-mode** (вариант **a**): накопление лексических ошибок (бюджет ≈20, общий с парсером —
   мягкий предел); до точки синхронизации (конец текущей логической строки: следующий нормализованный
   `\n`; внутри скобок — до физического перевода) подавляется ТОЛЬКО регистрация НОВЫХ ошибок, без
   каскада фантомов. Токенизация остатка строки при этом продолжается штатно: проблемная лексема
   пропускается (токен не эмитится — как у L-11), а валидные токены остатка попадают в поток. Поток
   **всегда** завершается одним `EOF` (FR-025, A3, A4). Лексер **не** печатает сводку
   «Найдено K ошибок.» (FR-026).
7. **Tests-first**: табличные тесты на каждую категорию токенов и каждую каноническую ошибку (FR-028);
   без изменяемого пакет-уровневого состояния (FR-029); `go build ./...` и `go vet ./...` чисто,
   `gofmt`-форматирование (FR-027, SC-006).
8. **Границы**: ТОЛЬКО `internal/lexer` + `internal/errors`. **НЕ** парсер/AST/eval/движок/CLI/Store.
   Лексер **НЕ** диагностирует незакрытые скобки/блоки (это парсер) и **НЕ** резолвит семантику
   (периоды, встроенные функции, поля записи — обычные `IDENT`).

## Phasing — порядок поставки по приоритетам User Stories

Фазы упорядочены по приоритетам US (spec.md). Каждая фаза — самостоятельно тестируема (tests-first).

- **Фаза 0 (каркас, до US)**: `go.mod`, скелет пакетов `errors` (Position, LexError, агрегат, Warning)
  и `lexer` (Token, TokenType, конструктор, ридер с BOM/CRLF-нормализацией). Табличные тесты формата
  ошибки и пустого ввода (`пустой ввод → один EOF`).
- **Фаза P1 — поток токенов (US1, MVP)**: сканеры IDENT/ключевые слова, INT/FLOAT/DURATION, STRING,
  операторы (жадное совпадение), разделители; стек отступов → NEWLINE/INDENT/DEDENT/EOF; прозрачность
  переводов внутри скобок и пустых/комментарных строк. Гейт: SC-001/SC-003 (все категории, поток
  завершается EOF; `5.`→INT+DOT, `1.5дн`→FLOAT+IDENT, `<`/`<=`, `/`/`//`, `=`/`==`).
- **Фаза P2 — лексическая диагностика (US2)**: 11 канонических `LexError` с точной позицией в рунах
  (табы, отступ не кратен 4, рваный DEDENT, незакрытая строка, перевод строки в строке, неизвестный
  escape, неверный числовой литерал, неизвестный суффикс, неожиданный символ, зарезервированное слово).
  Гейт: SC-002/SC-004 (позиции в рунах; каждый текст дословно, по одному кейсу).
- **Фаза P3 — panic-mode (US3)**: накопление в агрегат; до конца логической строки подавляется только
  регистрация новых ошибок (без фантомов), а остаток строки токенизируется штатно — проблемная лексема
  пропускается, валидные токены остатка эмитятся (вариант **a**); бюджет ≈20, поток всё равно
  завершается EOF. Гейт: SC-005.

Зависимости фаз: P1 опирается на Фазу 0; P2 опирается на P1 (нужен поток); P3 опирается на P2 (нужны
ошибки для накопления). Внутри каждой фазы — tests-first.

## Открытые вопросы и отложенные расхождения

- **D1 (отложен)**: размещение `Position` — `internal/errors` (этот шаг, A1) против локальной в `ast`
  (ARCHITECTURE §4.1). Для лексера противоречия нет. **Решение — на шаге AST/parser, не здесь.**
- **Передача общего бюджета ошибок лексер↔парсер** (не новое расхождение, форвард-нота): «≈20» —
  мягкий предел лексической доли (A3). Механика фактического слияния бюджета с парсером — деталь
  сборки пайплайна на шаге парсера; лексер просто ограничивает собственное накопление. Помечено для
  шага парсера, не выдумывается здесь.

- **Позиция `EOF` (вскрыто adversarial-верификацией плана, РЕШЕНО)**: FR-009 задавал её прозой «в конце
  ввода» без детерминированного правила. Решено владельцем — конвенциональный дефолт: позиция сразу
  после последней обработанной руны; пустой ввод → `(1, 1)`; после финального `\n` → следующая строка,
  колонка 1. Зафиксировано в FR-009, contracts/token-stream.md C-5, data-model.md §5.6, research.md D-R11.

_D2/D3/D4 и позиция `EOF` — решены (см. spec.md и research.md); D1 — отложен явно. Adversarial-
верификация плана: 2 значимые находки, обе устранены владельцем — позиция `EOF` (D-R11) и семантика
panic-mode (вариант **a**: остаток строки токенизируется, подавляется только регистрация новых ошибок —
FR-025, guardrail 6); ложной осталась одна громкая находка — счёт «37 vs 34 ключевых слов» (артефакт
корректен)._
