# Phase 1 — Data Model: Декларативный слой v1 — источники + метрики

**Feature**: 004-source-metric | **Date**: 2026-06-07 | **Plan**: [plan.md](./plan.md)

Описывает сущности фичи 004: новые AST-узлы (`SourceDecl`/`MetricDecl`/`MetricAttrPos`),
доведение конструируемых типов `value` (`Дата.Compare`, предопределённые `Период`, формат `Дробное`),
реестры на `Interpreter` (источники/метрики/кеш/стек/`clock`), активацию встроенных `дата`/`сегодня`
и отображение реестра сообщений §SM-9 на типы `errors`. Поля описаны **концептуально** (контракт)
плюс дословные Go-сигнатуры там, где их фиксирует якорь; точную реализацию конкретизирует
`/speckit-tasks`. Публичные Go-имена английские, тексты сообщений русские, имена типов канонические
(`Целое`/`Дробное`/`Дата`/`Период`/`Запись`). **Источник истины — `docs/source-metric-model.md` §SM-0…§SM-12,
D-1…D-9; при любом расхождении побеждает он.** Семантический фон — `SPEC.md §9/§10`,
`docs/grammar.md §5–6`, `docs/eval-model.md §7/§8.3/§9/§10`.

## 1. AST-узлы (пакет `internal/ast`) — §SM-2

Конвенции 002 (см. `specs/002-parser-ast/data-model.md`): встраиваемая база `declBase{base{Position}}`
даёт `Pos()` **и** маркеры `declNode()`/`topLevelItem()` через embedding — **отдельные методы НЕ
писать**. `Pos()` = ведущий ключевой токен. `Ident`/`StringLit` хранятся **по значению** (как
`FunctionDecl.Name Ident`); опциональное подвыражение — поле типа `Expression` со значением `nil`
(как `ReturnStmt.Value`); обязательное подвыражение — не-nil после успешного парса. Эталон для
копирования — `ast.FunctionDecl` (`internal/ast/decl.go`).

Оба новых узла встраивают `declBase` первым полем → автоматически реализуют `Decl` и `TopLevelItem`,
пополняя union `Decl` (в scope B была одна `FunctionDecl`; теперь `FunctionDecl | SourceDecl | MetricDecl`).
`MetricAttrPos` — **вспомогательная структура, не `Node`** (без `Pos()`, без маркеров): носитель
позиций ключевых слов атрибутов для точечной диагностики (D-2).

### Узлы (реализуют `Decl`)

| Узел | Поля | `Pos()` |
|---|---|---|
| `SourceDecl` | `declBase`; `Name Ident`; `File StringLit`; `FilePos Position` | токен `источник` |
| `MetricDecl` | `declBase`; `Name Ident`; `Source Ident`; `Where Expression`; `Aggregate Expression`; `Period Expression`; `ByDate Expression`; `Attrs MetricAttrPos` | токен `метрика` |

### Вспомогательная структура (не `Node`)

| Узел | Поля | Назначение |
|---|---|---|
| `MetricAttrPos` | `SourcePos, WherePos, AggregatePos, PeriodPos, ByDatePos Position` | позиция ключевого слова каждого **присутствующего** атрибута (нулевая `Position{}` для отсутствующего); для точной диагностики §SM-9.A pairing/обязательности |

**Семантика полей:**

- `SourceDecl.File StringLit` — строковый литерал пути (атрибут `файл:`), **не** `Expression`;
  путь интерпретируется относительно cwd процесса (§SM-8.1). `FilePos` — позиция самого литерала пути.
- `MetricDecl.Source Ident` — **не** `Expression` (D-1): парсер в позиции `источник:` читает ровно
  один `IDENT` (`parseSourceRef`); имя не резолвится в парсере (guardrail 7 соблюдён).
- `MetricDecl.Aggregate` — **обязателен** (не-nil после успешного парса).
- `MetricDecl.Where`, `.Period`, `.ByDate` — `nil`, если соответствующий атрибут отсутствует.
  Все три и `Aggregate` парсятся обычным `parseExpression` (приоритеты 002); их типы и поля записи
  парсер/семпроход не резолвят (D-5/D-6 — eval-time).

### Конструкторы (дословно по §SM-2)

```go
func NewSourceDecl(pos Position, name Ident, file StringLit, filePos Position) *SourceDecl

func NewMetricDecl(pos Position, name Ident, source Ident,
                   where Expression, aggregate Expression,
                   period Expression, byDate Expression,
                   attrs MetricAttrPos) *MetricDecl
```

Оба возвращают **указатель** (как `NewFunctionDecl`); инициализируют базу композитным литералом
`declBase{base{pos}}`. По образцу `decl_test.go`: тест `Test<Узел>Pos` проверяет `Pos()` через `!=`,
поля прямым доступом (`md.Name.Name`, `md.Source.Name`), и две компайл-тайм строки
`var _ Decl = sd` / `var _ TopLevelItem = sd`.

> **Граница 002/004.** `ProcessDecl`/`StepDecl`/`TriggerDecl` в 004 **не вводятся** — `KW_PROCESS`/
> `KW_WHEN`/`KW_VALUE` остаются отвергаемыми парсером (§SM-0, R7). Их AST добавится тем же способом в 005+.

## 2. Типы значений (`internal/value`) — конструируемые типы (§SM-5)

Go-структуры всех 10 типов уже заданы (`scalar.go`/`deferred.go`/`record.go`); `Equal`/`String(repr)`
реализованы. 004 добавляет **только** недостающее для `Дата`/`Период`/`Дробное`.

| Тип | Go-представление | Что добавляет 004 | Что готово |
|---|---|---|---|
| `Дата` | `struct{ Year, Month, Day int }` (поля `int`, **не** `int64`) | ветвь `Дата↔Дата` в `value.Compare` (§2.1) | `TypeName()="Дата"`, `repr` ISO `YYYY-MM-DD` (`isoDate`) |
| `Период` | `struct{ Name string }` | **5 предопределённых значений** регистрируются в глобальной области (§2.2) | `TypeName()="Период"`, `repr`=`Name`, `Equal` по `Name`; `Compare` **не определён** (несравним → `0,false`) |
| `Запись` | `struct{ keys []string; fields map[string]Value }` | — (порождается загрузчиком источника, §SM-8.1, через `value.NewRecord`) | `NewRecord`/`Get`(→`None` на отсутствующем)/`Keys`/`repr` — готовы |
| `Дробное` | `struct{ V float64 }` | **исправить `formatFloat`** (R1, §2.3) | `TypeName()`, `Equal`, `Compare` — готовы |
| `Длительность` | `struct{ Amount int64; Unit string }` | **ничего** (нет конструктора в 004; остаётся смоделированной) | — |

### 2.1. `Дата.Compare` — порядок (встройка в `value.Compare`, `equal.go`)

`value.Compare(a, b Value) (int, bool)` — знак `-1/0/+1` + `ok bool` (упорядочиваемость). Добавить
ветвь `case Дата:` с вложенным `case Дата:`: лексикографическое сравнение тройки `(Year, Month, Day)`.
Поля — `int`, поэтому `cmpInt64` напрямую не подходит → **добавить хелпер `cmpInt(a, b int) int`** (по
образцу `cmpInt64`/`cmpFloat`). Период остаётся несравнимым (падает в финальный `return 0, false`).

| Пара | Результат |
|---|---|
| `Дата ↔ Дата` | `cmpInt(Year)` → при равенстве `cmpInt(Month)` → при равенстве `cmpInt(Day)`; `true` |
| `Дата ↔ не-Дата` | `0, false` → вызывающий `evalOrder` даёт `ОшибкаТипа «'<оп>' нельзя применить к Дата и <тип>»` |
| `Период ↔ что-либо` | `0, false` (периоды не упорядочены) |

**Назначение:** проверка попадания записи в календарное окно `начало ≤ d ≤ конец` (§SM-8.2) — обе
границы суть `Дата`, граница **включительна** с обеих сторон. (`Дата.Equal` параллельно не требуется
для 004 — окно проверяется через знак `Compare`, `==` над датами в метриках не возникает.)

### 2.2. Предопределённые `Период` — новое в глобальной области (§SM-5, D-9)

5 значений `Период{Name}` регистрируются в **глобальной области интерпретатора** при инициализации
как **read-only иденты** (не ключевые слова, `grammar §6`): `ежедневно`, `еженедельно`, `ежемесячно`,
`ежеквартально`, `ежегодно`.

| Аспект | Решение |
|---|---|
| Где | `Interpreter.global` (`*Environment`); резолвятся обычным `env.Lookup` в `evalIdent`/`период:` |
| Чем | `value.Период{Name: "<имя>"}` (готовый тип) |
| Как | **новое:** до 004 предопределённых идентов в `global` не было (встроенные/функции жили в `funcs`/`builtins`, не в `vars`). 004 заводит 5 привязок в `global` при конструировании интерпретатора — через `global.Define("ежемесячно", value.Период{Name:"ежемесячно"})` и т.д. (либо эквивалент). Это **единственные** значения-иденты, предобъявленные в global |
| Read-only | повторное `пусть ежемесячно` — затенение (как у встроенных, не ошибка); затенять не рекомендуется, но не запрещено |

### 2.3. Формат `Дробное` (R1, одобрено владельцем — Вариант A) — `value/repr.go`

Текущий `formatFloat` использует `'g'` → `1000000.0` печатается как `"1e+06"` (баг для бизнес-диапазона).
**Чиним:** фиксированная запись для `|f| ∈ [1e-4, 1e16)`; sci (`'g'`) для очень больших/малых;
integer-looking → добавить `.0`.

| Вход | Выход | Примечание |
|---|---|---|
| `2175.0` | `2175.0` | integer-looking + `.0` (golden `функция.ladix` сохраняется) |
| `3.4` | `3.4` | дробная часть как есть |
| `1000000.0` | `1000000.0` | **новое:** фиксированная запись (было `1e+06`) |
| `1000000.5` | `1000000.5` | **новое:** фиксированная запись |
| `1e20` | `1e+20` | вне `[1e-4, 1e16)` → sci (repr-кейс `repr_test.go:20` сохраняется) |

**Синхронные правки:** `docs/eval-model.md §7` (политика формата `Дробное`), `docs/source-metric-model.md §SM-5`
(снять «repr не трогаем»), добавить repr-кейсы `1000000.0`/`1000000.5`. Этот формат — единый для
`строка(x)` и `печать` (golden-метрика `среднее → 1000000.0`, §SM-10).

## 3. Реестры на `Interpreter` (`internal/eval`) — §SM-4/§SM-7/§SM-8

Текущая структура `Interpreter` — поля `global/funcs/builtins/maxDepth/depth/out/iterating/analyzed`.
004 добавляет реестры декларативного слоя и `clock`. **Никакого пакета `internal/store` (§SM-12, R2):**
ветвь `metric` не заводит store, нет персиста, нет `--db`.

| Поле (новое) | Тип | Назначение |
|---|---|---|
| `sources` | `map[string]*ast.SourceDecl` | реестр источников (заполняется на Шаге 1 `Analyze`); резолв `MetricDecl.Source`, загрузчик §SM-8.1 |
| `metrics` | `map[string]*ast.MetricDecl` | реестр метрик (Шаг 1 `Analyze`); резолв имени-метрики как значения (D-8), CLI `metric` |
| `recordCache` | `map[string][]value.Запись` (ключ = имя источника) | **лень + кеш на запуск** (§9.6): JSON читается при первом обращении любой метрики, кешируется до конца запуска |
| `metricStack` | `[]string` (или `map[string]bool` + срез для порядка) | стек активных метрик для детекта цикла (D-8): `цикл зависимостей метрик: a → … → a` (§SM-9.B) |
| `clock` | `Clock` | инъекция времени (§SM-7, R4); `сегодня()` и окна периодов читают **только** его |

**`Clock` (контракт, §SM-7):**

```go
// пакет eval (или общий internal/clock)
type Clock interface{ Now() value.Дата }   // усечено до Y/M/D
```

- `SystemClock{}` — прод: `time.Now()` в `time.Local`, усечённый до даты (таймзоны — v2). Фиксируется
  **один раз на запуск** (`run`/`metric`): снять `Now()` в начале, переиспользовать (§10.6).
- `FixedClock{Дата{2026, 5, 31}}` — тесты/golden (§SM-10): все метрик-тесты инъектируют эту дату.
- **Запрет:** ни один путь `eval`/движка метрики не вызывает `time.Now()` напрямую — только через
  `i.clock` (аналогично тому, как вывод идёт только через `i.out`, не `os.Stdout`).

**`NewInterpreter` — расширение сигнатуры (R4):** текущая `NewInterpreter(out io.Writer, maxDepth int)`
→ **третий параметр** `clock Clock`. Поле `i.clock`. Обновить **всех вызывающих**: `cmd/ladix` (`run`/`metric`)
и все eval-тесты — добавить clock-аргумент (`FixedClock` в тестах, `SystemClock` в проде). Билтины
получают `*Interpreter` первым аргументом (`b.Fn(i, args, pos)`), поэтому `i.clock` доступен
встроенной `сегодня()` без отдельного протаскивания.

> **Где `Период` живут vs реестры.** Предопределённые `Период` — значения-иденты в `global` (§2.2,
> через `vars`). Источники/метрики — **не** значения (§9.1: источник не первоклассен): они в отдельных
> map `sources`/`metrics`, не в `global.vars`. Имя источника/метрики делит **глобальное пространство
> имён** с функциями (§SM-9.A повтор, R5).

## 4. Встроенные `дата`/`сегодня` (`internal/eval/builtins`) — §SM-6

Активировать из `deferredNames` **ровно две** функции; прочие 7 дата/время и 3 процессные остаются
deferred. Сигнатура реализации — стандартная `BuiltinFn`:

```go
type BuiltinFn func(i *Interpreter, args []value.Value, pos ast.Position) (value.Value, error)
```

### Активация (механизм)

| Шаг | Действие |
|---|---|
| Удалить из `deferredNames` | убрать `"дата"`, `"сегодня"` из среза (`builtins.go`) |
| Зарегистрировать | в `registerBuiltins()`: `add(fixed("сегодня", 0, builtinSegodnya))`, `add(overloaded("дата", builtinData))` |
| Написать реализации | `builtinSegodnya`/`builtinData` (новые функции с сигнатурой `BuiltinFn`) |
| Обновить инварианты | `TestBuiltinRegistryClosed`: активных **23→25**, deferred **12→10**, всего **35** (без изменений). `TestBuiltinDeferredAll`: итерирует по `deferredNames` (10 имён) |

### `сегодня() → Дата` (фикс. арность 0)

- `ArityFixed`, `N=0`. Лишние аргументы → семпроход `«'сегодня' принимает 0 аргументов, передано M»`.
- Возвращает `i.clock.Now()` (§SM-7), **не** `time.Now()` напрямую. В пределах запуска фиксирована.

### `дата(...) → Дата | Пусто` (перегруженная, `ArityOverloaded`)

Диспетчеризация в теле `builtinData` по `len(args)` и типу (как `диапазон`/`длина`):

| Форма | Поведение |
|---|---|
| `дата(s: Строка)` | разобрать `s` как `YYYY-MM-DD` (ровно 10 символов, `\d{4}-\d{2}-\d{2}`, валидный календарь с високосным). Успех → `Дата{Y,M,D}`. Невалидно (формат/несуществующая дата/наличие `T…`) → §SM-9.C `«дата: «<значение>» не является датой»` |
| `дата(п: Пусто)` | → `Пусто` (ключ к §10.4: запись без поля даты даёт `по_дате: дата(поле) → Пусто` → запись вне окна, **без ошибки**) |
| `дата(г: Целое, м: Целое, д: Целое)` | собрать дату; невалидный календарь (`м∉1..12`, `д` вне числа дней месяца с учётом високосного) → §SM-9.C `«дата: некорректные год/месяц/день»` |
| 1 арг не `Строка`/`Пусто` | §SM-9.C `«дата: ожидается Строка или Пусто, получено <тип>»` |
| иная арность (2, ≥4) / 3 арг не `Целое` | `«'дата': неверное число аргументов»` (арность) либо §SM-9.C (тип) |

> **`stdlib.md` синк:** `дата/сегодня` пометить «доступны»; `длительность/в_*/вчера/завтра` — «v2 (deferred)»;
> тексты ошибок `дата` — привести к §SM-9.C дословно.

## 5. Реестр ошибок §SM-9 → типы `errors`

Четыре листовых типа `errors` (по `{Pos Position, Msg string}` + `Error()` по значению) уже есть:
`ParseError`/`СемантическаяОшибка`/`ОшибкаВыполнения`/`ОшибкаТипа`. **Новых типов не вводится** —
004 добавляет только новые `Msg`. Конструкторы из `eval` (`interpreter.go`): `semErr`/`typeErr`/`runtimeErr`
+ `toErrPos`; для парсера — литерал `errors.ParseError{Pos:…, Msg:…}` в `*ErrorList`. Соглашения §8.3:
payload **без** завершающей точки; `'…'` — идентификаторы/ключевые слова/имена атрибутов; `«…»` —
дословное строковое значение (путь/формат/значение даты); `<тип>` = `value.TypeName()`; `N` с 1.

### §SM-9.A — декларации (`ParseError` — парсер; `СемантическаяОшибка` — семпроход)

| Текст (вербатим) | Категория | Где конструируется | Позиция |
|---|---|---|---|
| `неизвестный атрибут '<имя>'` | ParseError | парсер (`parseMetricDecl`/`parseSourceDecl`) | имя атрибута |
| `атрибут '<имя>' уже задан` | ParseError | парсер | повторный атрибут |
| `ожидается имя источника` | ParseError | парсер (`parseSourceRef`, не IDENT, D-1) | токен после `источник:` |
| `'<имя>' уже объявлено в строке N` | СемантическаяОшибка | семпроход (Шаг 1, повтор источник/метрика, R5) | имя декларации |
| `метрика '<имя>': отсутствует обязательный атрибут 'источник'` | СемантическаяОшибка | семпроход (Шаг 1b) | токен `метрика` |
| `метрика '<имя>': отсутствует обязательный атрибут 'агрегат'` | СемантическаяОшибка | семпроход (Шаг 1b) | токен `метрика` |
| `метрика '<имя>': 'период' требует 'по_дате'` | СемантическаяОшибка | семпроход (Шаг 1b) | `Attrs.PeriodPos` |
| `метрика '<имя>': 'по_дате' без 'период' не имеет смысла` | СемантическаяОшибка | семпроход (Шаг 1b) | `Attrs.ByDatePos` |
| `метрика '<имя>': источник '<ист>' не объявлен` | СемантическаяОшибка | семпроход (Шаг 1b) | `Attrs.SourcePos` |
| `метрика '<имя>': '<ист>' — не источник` | СемантическаяОшибка | семпроход (Шаг 1b, имя занято функцией/метрикой) | `Attrs.SourcePos` |

> **Повтор функция↔функция (R5):** существующий текст `функция '<имя>' уже объявлена в строке N`
> (регресс 003) сохраняется. Коллизии с участием источника/метрики — общий §SM-9.A текст
> `'<имя>' уже объявлено в строке N`. Шаг 1 `Analyze` объединить в один упорядоченный проход по
> `FunctionDecl`+`SourceDecl`+`MetricDecl`.

### §SM-9.B — загрузка источника и имя-как-значение (`ОшибкаВыполнения`)

| Текст (вербатим) | Где конструируется | Позиция |
|---|---|---|
| `источник '<имя>': файл «<путь>» не найден` | загрузчик §SM-8.1 | объявление `источник` |
| `источник '<имя>': не удалось прочитать файл «<путь>»` | загрузчик | объявление `источник` |
| `источник '<имя>': ожидался JSON-массив объектов в «<путь>»` | загрузчик | объявление `источник` |
| `источник '<имя>': запись N не является объектом` | загрузчик (N с 1) | объявление `источник` |
| `источник '<имя>': некорректный JSON в «<путь>» (<деталь>)` | загрузчик | объявление `источник` |

## 6. Схема источника и разрешение голого имени (§SM-8.1)

**Схема (§9.5):** объединение ключей по **всем** записям источника. Разрешение голого имени `x` в
`где`/`агрегат`/`по_дате` (per-record, в scope полей записи) — строго по порядку:

| Приоритет | Условие | Результат |
|---|---|---|
| 1 | `x` найдено в `global`/`Environment` (глобаль, предопр. `Период`) | значение переменной/периода |
| 2 | `x` — имя функции (`funcs`) или встроенной (`builtins`) | как обычно (вызов/функция-как-значение по контексту) |
| 3 | `x` ∈ схема источника (известное поле) | значение поля текущей записи; **нет в данной записи → `Пусто`** (`Запись.Get`) |
| 4 | иначе | `ОшибкаВыполнения «неизвестное поле '<имя>' (известные: <отсортировано по возрастанию>)»` |

**Границы:**

- Доступ `запись.поле` (`FieldExpr`) — **толерантный**: нет поля → `Пусто`, **без** проверки схемы
  (отличается от голого имени, где промах схемы → ошибка).
- На **пустом** источнике (0 записей) схема пуста → опечатку поля поймать нельзя (§9.7) — осознанная
  цена; но пустой источник короткозамыкается на пустой результат (§10.5) до вычисления выражений.
- Список «известных» в сообщении — **отсортирован по возрастанию** (детерминизм golden); пример
  §SM-10: `«неизвестное поле 'статус_опечатка' (известные: дата_заказа, клиент, статус, сумма_заказа)»`.
- Контексты вычисления (D-9): `период:` — **один раз** в глобальной области (`Период`); `где`/`по_дате`/
  проекции агрегата — **per-record** в scope полей. Голое поле вне агрегатной функции / вложенный
  агрегат — §SM-9.C (eval-time, движок метрики, не парсер/семпроход).
