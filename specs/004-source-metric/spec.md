# Feature Specification: Декларативный слой v1 — источники и метрики

**Feature Branch**: `004-source-metric`

**Created**: 2026-06-07

**Status**: Draft

**Input**: User description: "Декларативный слой v1: источники данных и метрики — парсер, AST, семантика, движок метрики, встроенные дата/сегодня, CLI ladix metric"

> **Связывающий якорь.** Источник истины поведения, контрактов и текстов — `docs/source-metric-model.md`
> (§SM-0…§SM-12). Эта спецификация описывает **что** и **зачем** на уровне пользователя; решения по
> открытым вопросам (D-1…D-9), формы AST, реестр сообщений и golden-таблица закреплены в якоре и при
> любом расхождении побеждает он. Семантический фон — `SPEC.md §9` (источники) и `§10` (метрики).

## User Scenarios & Testing *(mandatory)*

Ladix — декларативно-императивный язык бизнес-автоматизации. До этой фичи язык умеет лексировать (001),
разбирать и строить AST (002) и исполнять чистое императивное ядро B (003): функции, рекурсию,
управляющий поток, 23 встроенных. Фича 004 открывает **декларативный слой**: пользователь описывает
*откуда* брать данные (`источник`) и *что считать* по ним (`метрика`), а не пишет цикл вручную.

Пользователи:
- **Автор модели** — бизнес-аналитик/разработчик, пишущий `.ladix`-файл с декларациями источников и метрик.
- **Оператор CLI** — тот, кто запускает `ladix metric <файл> <имя>` и получает посчитанное значение.

### User Story 1 — Объявить источник и метрику и статически их проверить (Priority: P1)

Автор модели в `.ladix`-файле объявляет источник данных (имя + путь к JSON-файлу) и метрику над ним
(имя источника, фильтр `где`, агрегат, опционально календарный период и поле даты). Программа с
такими декларациями **разбирается без ошибок**, а структурные и статически разрешимые нарушения
(дубликат атрибута, неизвестный атрибут, отсутствие обязательного атрибута, ссылка на необъявленный
источник, период без поля даты) дают **точную диагностику с позицией** ещё до загрузки данных.

**Why this priority**: Без корректного синтаксиса и статической валидации деклараций никакое
вычисление невозможно. Это фундамент, который сам по себе ценен — он делает декларации
первоклассной частью языка и ловит ошибки автора как можно раньше.

**Independent Test**: Подать метрик-онли фикстуру (источник + метрика без `процесс`/`когда`) на
разбор и семантический проход → ноль ошибок. Подать варианты с дубликатом атрибута / неизвестным
атрибутом / `период` без `по_дате` / необъявленным источником → ожидаемые точные сообщения об ошибках.

**Acceptance Scenarios**:

1. **Given** файл с `источник продажи: файл: "data/sales.json"` и корректной метрикой над ним,
   **When** файл разбирается и проходит семантическую проверку, **Then** ошибок нет.
2. **Given** метрика с `период: ежемесячно`, но без `по_дате:`, **When** идёт семантическая проверка,
   **Then** ошибка `метрика '<имя>': 'период' требует 'по_дате'` с позицией строки атрибута `период`.
3. **Given** метрика с `источник: несуществующий` (нет такой декларации источника), **When** идёт
   семантическая проверка, **Then** ошибка `метрика '<имя>': источник 'несуществующий' не объявлен`.
4. **Given** блок метрики с двумя атрибутами `где:`, **When** идёт разбор, **Then** ошибка разбора
   `атрибут 'где' уже задан` с позицией повторного атрибута.
5. **Given** блок метрики с атрибутом `тип:` (не из фиксированного набора), **When** идёт разбор,
   **Then** ошибка разбора `неизвестный атрибут 'тип'`.

### User Story 2 — Посчитать метрику и получить значение (Priority: P1)

Оператор CLI запускает `ladix metric <файл> <имя_метрики>` и получает в stdout одно посчитанное
значение (число или `пусто`). Движок лениво загружает JSON-источник, строит календарное окно по
текущей дате (для метрик с `период:`), фильтрует записи (`по_дате` в окне И `где` истинно),
применяет агрегат (`сумма/количество/среднее/мин/макс`) и печатает результат. Пустое окно даёт `0`
для суммы/количества и `пусто` для прочих — **без** ошибки «список пуст».

**Why this priority**: Это основная ценность фичи — превратить декларацию в число. Без неё
декларации мертвы. Вместе с US1 образует сквозной вертикальный срез (объявил → посчитал).

**Independent Test**: При фиксированной дате `2026-05-31` и `data/sales.json` (3 записи мая 2026)
прогнать golden-таблицу §SM-10: `выручка_месяца` (сумма оплаченных за месяц) = `2000000`;
`количество` = `2`; `среднее` = `1000000.0`; `мин` = `800000`; `макс` = `1200000`; недельное/дневное
окно (пустое) = `0`; среднее на пустом окне = `пусто`. CLI: `ladix metric <фикстура> выручка_месяца`
печатает `2000000` и завершается с кодом 0.

**Acceptance Scenarios**:

1. **Given** `выручка_месяца` (сумма `сумма_заказа` где `статус == "оплачен"`, период `ежемесячно`,
   по дате `дата(дата_заказа)`) и `D = 2026-05-31`, **When** считается метрика, **Then** результат
   `2000000` (две майские оплаченные записи: 1 200 000 + 800 000).
2. **Given** та же метрика с периодом `еженедельно` (окно `[05-25, 05-31]`, ни одна запись не
   попадает), **When** считается метрика, **Then** результат `0` (а не ошибка «список пуст»).
3. **Given** метрика со `среднее(сумма_заказа)` на пустом дневном окне, **When** считается,
   **Then** результат `пусто`.
4. **Given** метрика без атрибута `где` за `ежемесячно`, **When** считается, **Then** в сумму входят
   все три майские записи → `2500000`.
5. **Given** `ladix metric <файл> неизвестная_метрика`, **When** запуск, **Then** stderr содержит
   `неизвестная метрика 'неизвестная_метрика'`, код выхода 1.
6. **Given** метрика над источником с несуществующим путём `файл: "нет.json"`, **When** считается,
   **Then** ошибка `источник '<имя>': файл «нет.json» не найден`, код выхода 1.

### User Story 3 — Работать с датами в выражениях (Priority: P2)

Автор модели использует встроенные `дата(...)` и `сегодня()` в выражениях метрик (и в императиве):
собрать дату из строки `"YYYY-MM-DD"`, из тройки `год, месяц, день`, получить `пусто` из `пусто`
(запись без поля даты), и узнать текущую дату. Результат детерминирован в пределах одного запуска.

**Why this priority**: Оси времени метрик (`по_дате`, окна `период`) опираются на даты. Без
конструктора `дата` и `сегодня` нельзя сопоставить запись с календарным окном. Это поддерживающая
US2, но имеет самостоятельную ценность (даты доступны и в обычных выражениях).

**Independent Test**: `дата("2026-05-03")` → дата, печатается `2026-05-03`; `дата(пусто)` → `пусто`;
`дата(2026, 5, 3)` → та же дата; `дата("2026-13-40")` → ошибка `дата: «2026-13-40» не является датой`;
`сегодня()` при фиксированной дате `2026-05-31` → `2026-05-31`.

**Acceptance Scenarios**:

1. **Given** запись без поля `дата_заказа`, **When** вычисляется `дата(дата_заказа)`, **Then**
   результат `пусто`, и запись **исключается** из окна метрики без ошибки.
2. **Given** строка `"2026-02-29"` (2026 — не високосный), **When** вычисляется `дата(...)`,
   **Then** ошибка `дата: «2026-02-29» не является датой`.
3. **Given** тройка `дата(2026, 13, 1)`, **When** вычисляется, **Then** ошибка
   `дата: некорректные год/месяц/день`.

### User Story 4 — Получать понятную диагностику вычисления (Priority: P3)

При вычислении метрики автор модели получает точные сообщения о нарушениях, разрешимых только во
время исполнения (когда известна схема источника): опечатка в имени поля (со списком известных
полей), `где`, давшее не-`Булево`, голое поле вне агрегатной функции, вложенный агрегат, цикл
зависимостей между метриками.

**Why this priority**: Улучшает опыт автора, но не блокирует основной поток (метрики без ошибок
считаются и без этой диагностики). Поэтому ниже приоритетом, чем счёт.

**Independent Test**: exact-match тесты для §SM-9.C: `где: статус_опечатка == "x"` →
`неизвестное поле 'статус_опечатка' (известные: дата_заказа, клиент, статус, сумма_заказа)`;
`где: статус` (строка) → `'где' должно давать Булево, получено Строка`;
`агрегат: сумма_заказа` (голое поле) → `поле 'сумма_заказа' использовано вне агрегатной функции`.

**Acceptance Scenarios**:

1. **Given** `где`, ссылающееся на несуществующее поле, **When** считается метрика, **Then** ошибка
   `неизвестное поле '<имя>' (известные: …)` со списком полей схемы по возрастанию.
2. **Given** две метрики, ссылающиеся друг на друга как на значение, **When** одна считается,
   **Then** ошибка `цикл зависимостей метрик: <имя> → … → <имя>`.

---

### Edge Cases

- **Пустой источник** (JSON `[]`): схема пуста, опечатку поля поймать нельзя (осознанная цена,
  §9.7); метрика возвращает пустой результат по §10.5.
- **Запись без поля даты**: `дата(поле) → пусто` → запись вне окна, без ошибки (§10.4).
- **Запись — не объект** в JSON-массиве: ошибка `источник '<имя>': запись N не является объектом`
  (N с 1).
- **Целое вне int64** в JSON: ошибка `источник '<имя>': запись N, поле '<поле>': целое число вне диапазона`.
- **Различение целого и дробного** в JSON по форме токена: `1200000` → Целое, `1200000.0`/`1.2e6` → Дробное.
- **Граница окна включительна** с обеих сторон (`начало ≤ d ≤ конец`).
- **Файл `examples/выручка.ladix`** в 004 целиком **не** парсится: он содержит `процесс`/`когда`,
  чьи ведущие токены остаются отвергаемыми → ошибка `неожиданный токен 'процесс'` (ожидаемо, это 006+).
- **Имя источника как значение** в императиве → ошибка `'<имя>' — источник, его нельзя использовать
  как значение`.
- **`период:`, давшее не-`Период`** → ошибка `'период' должно давать Период, получено <тип>`.

## Requirements *(mandatory)*

### Functional Requirements

**Синтаксис и AST (стадия 2)**

- **FR-001**: Язык MUST разбирать декларацию источника верхнего уровня: `источник <имя>:` с
  единственным атрибутом `файл: "<путь>"` (строковый литерал).
- **FR-002**: Язык MUST разбирать декларацию метрики верхнего уровня: `метрика <имя>:` с блоком
  атрибутов из фиксированного набора `{источник, где, агрегат, период, по_дате}`.
- **FR-003**: В позиции `источник:` метрики парсер MUST читать ровно один идентификатор (имя
  источника), не общее выражение; иной токен → ошибка разбора `ожидается имя источника` (D-1).
- **FR-004**: В позициях `где/агрегат/период/по_дате` парсер MUST читать полное выражение с теми же
  приоритетами, что в 002.
- **FR-005**: Парсер MUST отвергать неизвестное имя атрибута (`неизвестный атрибут '<имя>'`) и
  повтор атрибута (`атрибут '<имя>' уже задан`) как ошибки разбора, с позицией соответствующего
  атрибута (D-3).
- **FR-006**: Декларации источника/метрики допустимы MUST только на верхнем уровне; ведущий
  `источник`/`метрика` внутри блока/функции → ошибка разбора.
- **FR-007**: Токены `процесс`/`когда`/`значение` (`KW_PROCESS`/`KW_WHEN`/`KW_VALUE`) MUST
  оставаться отвергаемыми парсером (вне границы 004).

**Семантический проход (стадия 3)**

- **FR-008**: Семантический проход MUST регистрировать источники и метрики в общем глобальном
  пространстве имён (вместе с функциями); повтор имени → `'<имя>' уже объявлено в строке N`.
- **FR-009**: Для метрики семпроход MUST требовать наличие `источник` и `агрегат`; отсутствие →
  `метрика '<имя>': отсутствует обязательный атрибут '<имя_атрибута>'`.
- **FR-010**: Атрибут `период` MUST присутствовать тогда и только тогда, когда присутствует
  `по_дате`; нарушение → `'период' требует 'по_дате'` либо `'по_дате' без 'период' не имеет смысла`.
- **FR-011**: Имя в `источник:` метрики MUST ссылаться на зарегистрированный источник; не найдено →
  `источник '<ист>' не объявлен`; найдено, но это функция/метрика → `'<ист>' — не источник`.
- **FR-012**: Семпроход MUST NOT резолвить имена полей записи, проверять типы выражений
  `где/по_дате/агрегат`, голое поле или вложенный агрегат — это оставлено времени исполнения.

**Типы и встроенные**

- **FR-013**: Тип `Дата` MUST поддерживать сравнение порядка (`<,<=,>,>=,==,!=`) лексикографически
  по `(год, месяц, день)`; сравнение `Дата` с не-`Дата` → ошибка типа.
- **FR-014**: Пять предопределённых значений `Период` (`ежедневно, еженедельно, ежемесячно,
  ежеквартально, ежегодно`) MUST быть доступны как иденты в глобальной области (read-only).
- **FR-015**: Встроенная `сегодня()` MUST возвращать текущую дату (арность 0).
- **FR-016**: Встроенная `дата(...)` MUST быть перегруженной: `дата(Строка)` парсит ISO `YYYY-MM-DD`;
  `дата(Пусто)` → `Пусто`; `дата(Целое, Целое, Целое)` собирает дату с валидацией календаря.
- **FR-017**: `дата(Строка)` с форматом ≠ `YYYY-MM-DD` или несуществующей датой → `дата: «<значение>»
  не является датой`; `дата(Целое×3)` с невалидным календарём → `дата: некорректные год/месяц/день`;
  валидация високосного года для февраля обязательна.
- **FR-018**: Прочие 10 встроенных дата/время и процессных (`длительность`, `в_секундах`…`в_днях`,
  `вчера`, `завтра`, процессные) MUST оставаться недоступными (deferred).

**Детерминизм времени**

- **FR-019**: Текущая дата MUST читаться только через инъектируемый источник времени (Clock); прямой
  системный вызов времени в слое вычисления/движка запрещён.
- **FR-020**: В пределах одного запуска `сегодня()` MUST быть зафиксирована (одно и то же значение).

**Движок метрики**

- **FR-021**: Источник MUST загружаться лениво (при первом обращении) и кешироваться до конца
  запуска; путь — относительно текущего рабочего каталога процесса.
- **FR-022**: Загрузчик MUST разбирать JSON-массив объектов и маппить: `null→Пусто`, `bool→Булево`,
  строка→`Строка` (даты не распознаются), число без `.`/`e`/`E`→`Целое` (вне int64 → ошибка),
  число с `.`/экспонентой→`Дробное`, массив→`Список`, объект→`Запись`.
- **FR-023**: Не-массив на верхнем уровне / элемент не объект / битый JSON MUST давать ошибку
  выполнения с именем источника и путём (§SM-9.B), номер записи с 1.
- **FR-024**: Схема источника MUST вычисляться как объединение ключей всех записей; в сообщении об
  опечатке поля список известных полей — отсортирован по возрастанию.
- **FR-025**: Для метрики с `период:` движок MUST вычислить `Период` один раз (глобально) и
  построить полное календарное окно `[начало, конец]` (включительно), содержащее текущую дату, по
  правилам §10.4 (дневное/недельное ISO/месячное/квартальное/годовое, с учётом високосного года).
- **FR-026**: Запись MUST включаться в агрегат, если `по_дате` даёт `Дата` в окне (при наличии
  `период:`) И `где` истинно (при наличии `где`); `по_дате = Пусто` → запись исключается без
  проверки `где` и без ошибки.
- **FR-027**: `где`, давшее не-`Булево`, и `по_дате`, давшее не-`Дата`/не-`Пусто`, MUST давать
  ошибку выполнения (§SM-9.C).
- **FR-028**: Агрегат MUST переиспользовать существующие `сумма/количество/среднее/мин/макс`;
  проекция каждого агрегата вычисляется на каждой выжившей записи и пропускает записи, где даёт `Пусто`.
- **FR-029**: Голое поле вне агрегатной функции и вложенный агрегат MUST давать ошибку выполнения
  (`поле '<имя>' использовано вне агрегатной функции`, `вложенный агрегат недопустим`).
- **FR-030**: Пустой результат (нет выживших записей) MUST давать `Целое 0` для корневого
  единичного `сумма`/`количество`, иначе `Пусто`; в контексте метрики пустая проекция MUST NOT
  давать ошибку «список пуст» (§10.5 перекрывает поведение общих функций).
- **FR-031**: Имя метрики, использованное как значение (идент, не найденный среди
  переменных/функций/встроенных), MUST резолвиться в реестр метрик и запускать пересчёт; цикл
  зависимостей → `цикл зависимостей метрик: <имя> → … → <имя>` (D-8).
- **FR-032**: Имя источника, использованное как значение, MUST давать `'<имя>' — источник, его
  нельзя использовать как значение`.

**CLI**

- **FR-033**: `ladix metric <файл> <имя> [--max-depth N]` MUST лексировать → разбирать → семантически

### Key Entities *(include if feature involves data)*

- **Источник (Source)**: именованная декларация, связывающая имя с путём к JSON-файлу-массиву
  объектов. Не первоклассен (нельзя использовать как значение). Лениво загружается и кешируется.
- **Метрика (Metric)**: именованная декларация вычисления над источником: обязательны имя источника и
  агрегат; опциональны фильтр `где`, календарный `период` и поле даты `по_дате` (последние два —
  парой). Может ссылаться на другую метрику как на значение.
- **Запись (Record)**: один объект из загруженного источника — набор именованных полей. Доступ к
  отсутствующему полю даёт `Пусто`.
- **Дата (Date)**: значение `(год, месяц, день)` с порядком сравнения; печатается как `YYYY-MM-DD`.
- **Период (Period)**: одно из пяти предопределённых календарных значений, задающее размер окна.
- **Окно (Window)**: пара `[начало, конец]` дат (включительно), полный календарный период,
  содержащий текущую дату.
- **Схема (Schema)**: множество известных полей источника = объединение ключей всех его записей.

## Assumptions

- Семантика источников (`SPEC §9`) и метрик (`SPEC §10`) уже зафиксирована и **не пересматривается**;
  фича закрывает реализационные дыры по якорю `docs/source-metric-model.md`.
- Грамматика деклараций (`docs/grammar.md §5–6`) готова и используется как есть.
- Решения по открытым вопросам D-1…D-9 (§SM-1) приняты архитектором и не переоткрываются.
- Тип `Запись` и его конструктор/доступ в слое значений уже готовы; 004 добавляет лишь вызывающий
  код (движок) и `Дата.Compare`.
- Агрегаты `сумма/количество/среднее/мин/макс` уже реализованы в 003 и переиспользуются.
- Golden-метрика берётся из метрик-онли фикстуры (не из `examples/выручка.ladix`, чья исполнимость —
  цель 006+); вывод фикстуры дата-зависим, поэтому она хранится как тест-фикстура, не в `examples/`.
- `ladix metric` в проде использует системное время (зафиксированное на запуск); тесты инъектируют
  фиксированную дату `2026-05-31`.

## Out of Scope *(boundaries §SM-0/§SM-12)*

- `процесс`/`шаг`/`когда` (парсинг и исполнение), пакеты жизненного цикла процессов/хранилища — 005/006/007.
- Встроенные `длительность`, `в_секундах`…`в_днях`, `вчера`, `завтра`; арифметика `Дата ± Длительность`,
  `Дата − Дата` (окна считаются календарной арифметикой над полями даты, без типа `Длительность`).
- Авто-распознавание дат-строк, NDJSON/CSV, `тип:`-атрибуты источника, live-reload, таймзоны/`ДатаВремя`,
  скользящие/«последний завершённый» окна, кеш значения метрики, второй источник на метрику — v2 (`SPEC §12`).
- Персист инстансов и реальное хранилище — `ladix metric` использует заглушку в памяти.
