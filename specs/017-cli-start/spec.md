# Feature Specification: B5 — `ladix start <процесс> [аргументы]` (CLI-запуск инстанса)

**Feature Branch**: `017-cli-start`

**Created**: 2026-06-17

**Status**: Draft

**Input**: B5 вехи M2 автоматизации Ladix. Источник истины: `docs/automation-model.md` §AU-7 (B5),
§AU-9 (серверная модель, единая `--db`, хелпер `openStore`), §AU-10 (CLI-ошибки + stdout канон),
§AU-4.5 (проводка `--вебхук`), D-AU-7, D-AU-10. Решения залочены владельцем.

## Резюме

Новая CLI-подкоманда `ladix start <файл> <процесс> [аргументы...] [--db <path>] [--вебхук <url>] [--max-depth N]`
создаёт инстанс объявленного процесса в SQLite через существующий движок (`engine.Start`). Позиционные
аргументы парсятся в **типизированные литералы** `value.Value` (Целое/Дробное/Булево/Пусто/Дата/Строка).
Число аргументов **сверяется с арностью** процесса на CLI ДО запуска. Печатает созданные задачи (строки
движка `[задача] …`) и ID инстанса (`запущен инстанс <id>`). Слой — только CLI; новой языковой
функциональности нет. После B5 канон §AU-12.B (`ladix start эскалация_плана 2500000 --db demo.db`)
становится исполним на CLI; полная end-to-end сборка §AU-12.B/§AU-12.C идёт на M2-гейте, НЕ здесь.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Запуск процесса с типизированными аргументами (Priority: P1)

Оператор запускает объявленный процесс вручную из терминала, передавая значения параметров позиционно.
Каждый аргумент превращается в типизированный литерал; инстанс создаётся в общей БД (`ladix.db` по
умолчанию или указанной `--db`), видимой `serve`/`complete`/`inspect`. На выходе — созданные задачи и ID
инстанса.

**Why this priority**: Это ядро B5 и предусловие демо-пары B5→B6 и golden §AU-12.B (детерминированный
старт инстанса вместо edge-метрики). Без него §AU-12.B недостижим. MVP — одна эта история уже даёт
исполнимый `ladix start`.

**Independent Test**: `ladix start <файл> эскалация_плана 2500000 --db <tmp>` над фикстурой с процессом
`эскалация_плана(факт)` → stdout содержит `[задача] t-000001 → … срок до <DT>` и `запущен инстанс p-000001`,
exit 0; инстанс читается из той же БД.

**Acceptance Scenarios**:

1. **Given** файл с процессом `эскалация_плана(факт)`, имеющим человеческий первый шаг со `срок:`,
   **When** `ladix start <файл> эскалация_плана 2500000 --db demo.db`,
   **Then** stdout =
   ```
   [задача] t-000001 → менеджер, шаг 'связаться_с_клиентом', срок до <время>
   запущен инстанс p-000001
   ```
   exit 0, инстанс `p-000001` персистнут в `demo.db`.
2. **Given** процесс с одним параметром, **When** аргумент `2500000`, **Then** параметр связан
   значением `value.Целое{2500000}`.
3. **Given** терминальный процесс без человеческих задач (сразу завершается), **When** `ladix start <файл> P …`,
   **Then** stdout = ровно `запущен инстанс p-000001` (движок тих, `[задача]`-строк нет).
4. **Given** отсутствие `--db`, **When** `ladix start <файл> P …`, **Then** используется SQLite `ladix.db`
   (семья complete/tasks/emit), НЕ MemoryStore.

### User Story 2 — Типизация позиционных литералов argv (Priority: P1)

Каждый позиционный аргумент распознаётся как типизированный литерал по форме строки: целое, дробное,
булево, пусто, дата (ISO), иначе — строка. Невалидное целое (вне Int64) даёт дословную CLI-ошибку.

**Why this priority**: Корректная типизация — предусловие связывания параметров; ошибочный тип молча
исказил бы исполнение. Замки на каждый тип + плохой литерал предотвращают дрейф §AU-7.2.

**Independent Test**: Таблица argv→тип: `2500000`→Целое, `3.14`→Дробное, `истина`→Булево, `ложь`→Булево,
`пусто`→Пусто, `2026-01-01`→Дата, `перезвонит`→Строка; `99999999999999999999`→CLI-ошибка вне диапазона.

**Acceptance Scenarios**:

1. **Given** argv `2500000`, **Then** `value.Целое{2500000}`.
2. **Given** argv `-42`, **Then** `value.Целое{-42}` (ведущий минус допустим).
3. **Given** argv `3.14`, **Then** `value.Дробное{3.14}`; `-0.5`→`value.Дробное{-0.5}`.
4. **Given** argv `истина` / `ложь`, **Then** `value.Булево{true}` / `value.Булево{false}`.
5. **Given** argv `пусто`, **Then** `value.None` (Пусто).
6. **Given** argv `2026-01-01`, **Then** `value.Дата{Year:2026, Month:1, Day:1}`.
7. **Given** argv `перезвонит` (или `2 500 000` одним токеном из шелла), **Then** `value.Строка`.
8. **Given** argv `99999999999999999999` (вне Int64), **Then** stderr =
   `ladix: не удалось разобрать аргумент '99999999999999999999': целое вне диапазона типа Целое`, exit 2.

### User Story 3 — Сверка арности и неизвестный процесс (Priority: P1)

CLI сверяет число переданных аргументов с числом параметров процесса ДО запуска движка и отвергает
неизвестный процесс дословной CLI-ошибкой.

**Why this priority**: Защищает от молчаливого мисматча и от другого (худшего) текста движка
(`процесс '%s' не найден в определении`, engine.go:69). Дословность ошибок — exact-match замок §AU-10.C.

**Independent Test**: процесс `P(a)` (1 параметр): `ladix start <файл> P` (0 арг) и `ladix start <файл> P x y`
(2 арг) → exit 2 дословно; `ladix start <файл> НЕТ x` → `процесс 'НЕТ' не объявлен` exit 2.

**Acceptance Scenarios**:

1. **Given** процесс `эскалация_плана(факт)` (1 параметр), **When** `ladix start <файл> эскалация_плана` (0 арг),
   **Then** stderr = `ladix: процесс 'эскалация_плана' ожидает 1 аргументов, получено 0`, exit 2.
2. **Given** тот же процесс, **When** `ladix start <файл> эскалация_плана 100 200` (2 арг),
   **Then** stderr = `ladix: процесс 'эскалация_плана' ожидает 1 аргументов, получено 2`, exit 2.
3. **Given** файл без процесса `неизвестный`, **When** `ladix start <файл> неизвестный 5`,
   **Then** stderr = `ladix: процесс 'неизвестный' не объявлен`, exit 2 (НЕ текст движка).
4. **Given** процесс с 0 параметров, **When** `ladix start <файл> P` (0 арг), **Then** запуск проходит (арность 0=0).

### User Story 4 — Единая `--db` и хелпер `openStore` (Priority: P2)

`start` следует семье `complete`/`tasks`/`emit` (дефолт `ladix.db` → SQLite). Конструкция Store,
инлайн-продублированная в 5 местах, выделяется в хелпер `openStore(dbPath)`, переиспользуемый `start` без
регресса существующих команд.

**Why this priority**: Единая `--db` — предусловие демо (start→serve→complete→inspect одна БД). Хелпер
устраняет дубли (§AU-9), но не должен менять поведение complete/tasks/emit (замок-регресс).

**Independent Test**: `start` без `--db` пишет в `ladix.db`; complete/tasks/emit golden остаются зелёными
после введения `openStore`.

**Acceptance Scenarios**:

1. **Given** `start <файл> P …` без `--db`, **Then** Store = SQLite `ladix.db` (не Memory).
2. **Given** `start <файл> P … --db x.db`, **Then** Store = SQLite `x.db`.
3. **Given** введён `openStore`, **When** прогон существующих golden complete/tasks/emit, **Then** все
   зелёные (нет регресса; `dbPath != "" → SQLite` defer Close, иначе Memory — узкий снимок логики runFile).

### Edge Cases

- **Аргументы при 0-параметрическом процессе с лишними argv** → арность-мисматч exit 2.
- **`--вебхук` в `start`**: см. FR-013 (решение). Невалидный URL вебхука → `ladix: неверный URL вебхука '<URL>'`
  exit 2 (§AU-4.5/§EN-8.B).
- **Отсутствие позиционного `<процесс>`** → usage-ошибка stderr, exit 2 (нет имени процесса).
- **Нет файла / ошибка компиляции файла** → диагностика + exit 1 (как существующие команды, FR-004).
- **`2026-13-45`** (форма ISO, но невалидная дата) → решение парсера дат (валидировать как M1 Дата-поле)
  — см. FR-007; зафиксировано в data-model.
- **`пусто` как имя процесса vs литерал**: распознавание литерала касается ТОЛЬКО ПОЗИЦИОННЫХ аргументов
  ПОСЛЕ имени процесса; имя процесса — всегда строка-идентификатор.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА добавить подкоманду `start` в switch `cmd/ladix/main.go` →
  `startMain(args[1:], stdout, stderr) int`.
- **FR-002**: `startMain` ДОЛЖНА разбирать грамматику вызова
  `ladix start <файл> <процесс> [аргументы...] [--db путь] [--вебхук URL] [--max-depth N]`.
  Файл с определениями — первый позиционный (как `run`/`complete`), `<процесс>` — второй позиционный,
  остальные позиционные — аргументы. (Сверено с §AU-7.1: `start` конструирует Store/интерпретатор/движок
  и зовёт `engine.Start`; источник процессов — компилируемый файл, как у всех CLI-команд.)
- **FR-003**: Каждый позиционный аргумент ДОЛЖЕН парситься в `value.Value` парсером argv-литералов
  (FR-005..FR-009) ДО `engine.Start`.
- **FR-004**: Система ДОЛЖНА компилировать файл (lex→parse→Analyze) и при ошибке компиляции вести себя
  как существующие команды (диагностика + exit 1); top-level `interp.Run` НЕ исполняется (как complete).
- **FR-005**: Аргумент формы `^-?\d+$` ДОЛЖЕН давать `value.Целое{V}` (диапазон Int64). Вне диапазона →
  CLI-ошибка FR-016.
- **FR-006**: Аргумент формы `^-?\d+\.\d+$` (или с экспонентой `eE`) ДОЛЖЕН давать `value.Дробное{V}`.
- **FR-007**: Аргумент формы `^\d{4}-\d{2}-\d{2}$` (ISO) ДОЛЖЕН давать `value.Дата{Year,Month,Day}`
  (парс как M1 Дата-поле). Валидация календарной корректности — по образцу M1 Дата (зафиксировать в
  data-model: невалидная дата формы ISO → ошибка парса литерала, единообразно с M1).
- **FR-008**: Аргументы `истина` / `ложь` ДОЛЖНЫ давать `value.Булево{true}` / `value.Булево{false}`
  (маппинг BOOL-литералов лексера, `scan_ident.go:26-31`). Аргумент `пусто` ДОЛЖЕН давать `value.None`.
- **FR-009**: Любой иной аргумент ДОЛЖЕН давать `value.Строка{V}` (весь argv-токен как строка, без снятия
  кавычек — их снимает шелл). Запись/Список/Длительность/Период в argv НЕ поддерживаются (M3, §AU-13).
- **FR-010**: Перед запуском система ДОЛЖНА получить `pd, ok := interp.Process(name)`
  (`(*ast.ProcessDecl, bool)`, exports.go:19). `!ok` → CLI-ошибка FR-015 exit 2 (CLI формирует САМ,
  НЕ полагается на текст движка `процесс '%s' не найден в определении`).
- **FR-011**: При `ok` система ДОЛЖНА сравнить `len(pd.Params)` (ast/process.go:10) с числом argv;
  несовпадение → CLI-ошибка FR-014 exit 2 ДО `engine.Start`.
- **FR-012**: При совпадении арности система ДОЛЖНА вызвать `engine.Start(процесс, args)`, который
  возвращает `(instanceID string, error)`; печать `[задача]`-строк делает движок через `printTaskCreated`
  (`Start→advance`, НЕ `advanceAfterComplete` → строки статуса нет), а строку `запущен инстанс <id>`
  печатает САМ `startMain`.
- **FR-013** (РЕШЕНИЕ по `--вебхук`): `start` ДОЛЖЕН принимать флаг `--вебхук <URL>` / env `LADIX_WEBHOOK`
  и проводить его в движок тем же хелпером `withExternalCallerOpt`/`WithExternalCaller`, как `run`/`serve`/
  `complete` (§AU-4.5 явно перечисляет `start` среди команд, принимающих `--вебхук`). ОБОСНОВАНИЕ
  применимости к start-исполнению: `engine.Start` синхронно прогоняет `advance` от первого шага; если
  процесс не упирается в первый человеческий шаг (терминальный/автоматические шаги с `вызвать`/`уведомить`),
  эффекты сработают НА СТАРТЕ → драйвер должен быть проведён, иначе тихий стаб вместо доставки. Поэтому
  `--вебхук` в `start` нужен (паритет с complete-догоном §AU-4.5). Невалидный URL → CLI-ошибка FR-017.
- **FR-014** (ДОСЛОВНО): `ladix: процесс '<имя>' ожидает <N> аргументов, получено <M>` (stderr, exit 2),
  где N=`len(pd.Params)`, M=число argv.
- **FR-015** (ДОСЛОВНО): `ladix: процесс '<имя>' не объявлен` (stderr, exit 2).
- **FR-016** (ДОСЛОВНО): `ladix: не удалось разобрать аргумент '<argv>': целое вне диапазона типа Целое`
  (stderr, exit 2). Аналоги для иных типов формируются по образцу, если применимо (напр. дробное вне
  диапазона) — зафиксировать инвентарь в data-model; ядро замка — целое вне диапазона.
- **FR-017** (ДОСЛОВНО, §AU-4.5): `ladix: неверный URL вебхука '<URL>'` (stderr, exit 2).
- **FR-018** (stdout канон ДОСЛОВНО, §AU-10.D, golden маскирует `<время>` дедлайна как `<DT>`,
  id детерминирован при засеве):
  ```
  [задача] t-000001 → менеджер, шаг 'связаться_с_клиентом', срок до <время>
  запущен инстанс p-000001
  ```
  Терминальный процесс без задач → ТОЛЬКО `запущен инстанс <id>`.
- **FR-019**: `start` ДОЛЖЕН дефолтить в SQLite `ladix.db` (семья complete/tasks/emit, D-AU-10), НЕ в
  MemoryStore (семья run/serve). С `--db путь` → SQLite по пути.
- **FR-020**: Система ДОЛЖНА выделить хелпер `openStore(dbPath string)` (или эквивалент с defer-Close),
  инкапсулирующий узкий снимок логики runFile (main.go:235-244: `dbPath != "" → SQLiteStore`, defer Close;
  иначе MemoryStore), и переиспользовать его в `start`. Хелпер НЕ ДОЛЖЕН менять поведение существующих
  команд (опционально рефакторит их под себя без регресса golden).
- **FR-021**: Новые CLI-ошибки B5 — stderr команды (`ladix: …`, exit 2, §EN-8.B), НЕ программные
  диагностики. Счётчики каталога диагностик (L=11, SE=14, eval=28) НЕ меняются.

### Несущие инварианты (нацелены в plan/tasks)

- **INV-1 (CLI-only)**: НЕ менять шов `ProcessRuntime` (8 методов после B1), НЕ добавлять метод `Store`
  (16 после B6). `start` потребляет существующий `engine.Start`/`interp.Process`. eval — без store/engine.
- **INV-2 (единая `--db`)**: start/complete/tasks/emit/inspect → SQLite `ladix.db`; run/serve → Memory;
  metric → всегда Memory. `openStore` без регресса существующих команд.
- **INV-3 (golden целы)**: §EN-7/007b/durable(B4) golden целы; счётчики L=11/SE=14/eval=28 целы (новые
  CLI-ошибки — stderr cmd, не каталог).
- **INV-4 (M2-гейт)**: после B5 `ladix start эскалация_плана 2500000 --db demo.db` исполним; полная
  сборка §AU-12.B/§AU-12.C — на M2-гейте, НЕ в этой фиче.

### Key Entities

- **argv-литерал**: результат парсинга одного позиционного аргумента → `value.Value` одного из типов
  Целое/Дробное/Булево/Пусто/Дата/Строка (§AU-7.2).
- **startMain**: подкоманда CLI (`cmd/ladix`), сигнатура `startMain(rest []string, stdout, stderr io.Writer) int`.
- **openStore**: хелпер конструкции Store по `dbPath` (§AU-9), переиспользуемый `start` (и, опционально,
  существующими командами без регресса).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `ladix start <файл> эскалация_плана 2500000 --db demo.db` создаёт инстанс, печатает канон
  §AU-10.D (FR-018) и завершается exit 0; инстанс читается из `demo.db`.
- **SC-002**: Каждый из 6 типов литерала (Целое/Дробное/Булево/Пусто/Дата/Строка) парсится из argv в
  корректный `value.Value` (таблица US2); целое вне Int64 → FR-016 дословно exit 2.
- **SC-003**: Арность-мисматч (N≠M) → FR-014 дословно exit 2; неизвестный процесс → FR-015 дословно exit 2.
- **SC-004**: stdout канон `start` — exact-match (golden маскирует время `<DT>`); сдвиг строки/формата
  ломает замок.
- **SC-005**: `start` без `--db` пишет в SQLite `ladix.db`; введение `openStore` не даёт регресса golden
  complete/tasks/emit.
- **SC-006**: Счётчики каталога диагностик L=11/SE=14/eval=28 не изменены; B5 не трогает ProcessRuntime
  (=8) и Store (=16 после B6).
- **SC-007**: 0 новых зависимостей; детерминизм (FixedClock/засев id) для golden.

## Assumptions

- A1: `engine.Start(name, args)` существует и возвращает `(instanceID string, error)` (engine.go:65),
  печатает `[задача]`-строки через `printTaskCreated`; НЕ печатает строку статуса инстанса (то делает
  `advanceAfterComplete`, не `Start→advance`). Подтверждено эмпирикой.
- A2: `interp.Process(name)` — метод интерпретатора `(*Interpreter) Process(string) (*ast.ProcessDecl, bool)`
  (exports.go:19). `ProcessDecl.Params []Ident` (ast/process.go:10).
- A3: Дефолт `start` = SQLite `ladix.db` (D-AU-10), а НЕ Memory; иначе рассинхрон с complete/inspect.
- A4: `--вебхук` применим к `start` (FR-013): эффекты могут сработать на синхронном `advance` старта.
- A5: golden-маскирование времени — существующий приём (`срок до <DT>`, trigger_golden_test.go:70
  `idMaskRE`); id детерминированы при свежей БД (p-000001/t-000001).
- A6: Полный end-to-end §AU-12.B/§AU-12.C (serve→эскалация→рестарт→inspect) собирается на M2-гейте, НЕ в B5.

## Dependencies

- B1 (ProcessRuntime 7→8) уже влит (master @a1ad856). B5 НЕ трогает ProcessRuntime.
- B6 (`inspect`, Store 15→16) — параллелен/после; B5 не зависит, но образует демо-пару B5→B6.
- Источник истины: `docs/automation-model.md` §AU-7/§AU-9/§AU-10/§AU-4.5, D-AU-7, D-AU-10.
