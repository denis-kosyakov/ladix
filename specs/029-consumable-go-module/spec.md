# Feature Specification: Потребляемый Go-модуль LADIX

**Feature Branch**: `029-consumable-go-module`

**Created**: 2026-06-28

**Status**: Draft

**Input**: User description: "Превратить LADIX в чисто потребляемый Go-модуль `github.com/denis-kosyakov/ladix`: фронтенд (лексер/парсер/AST/значения/ошибки + новый IR + корневой фасад) импортируется внешними проектами как публичная библиотека; standalone (движок процессов, CLI, SQLite-стор, демон) сохраняется как reference-implementation. Потребитель — платформа «Уклад» (вариант B: исполняет определения нативно, движок LADIX не переносит, подключает версии через semver-пин Go-модуля). БЕЗ изменения семантики/синтаксиса языка — только перемещение, экспорт и упаковка."

## Почему (контекст и проблема) *(mandatory)*

LADIX задумывался как DSL, чей фронтенд (разбор и валидация бизнес-определений: метрики,
процессы, триггеры) встраивается во внешние системы. Сегодня этого сделать **нельзя** по
четырём упаковочным причинам, ни одна из которых не связана с самим языком:

1. **`go.mod` лежит в `src/`, а не в корне репозитория.** Команда
   `go get github.com/denis-kosyakov/ladix` НЕ работает: Go ищет модуль по корню репозитория,
   а там его нет. Внешний потребитель физически не может подключить модуль по его имени.
2. **Весь код — под `internal/`.** Пакеты `lexer`, `parser`, `ast`, `value`, `errors`
   лежат в `src/internal/*` и по правилам Go недоступны для импорта из других модулей.
   Внешний потребитель не может вызвать ни одну функцию фронтенда.
3. **Нет узкой точки входа и версионируемого контракта вывода.** Чтобы получить разобранную
   программу, потребителю пришлось бы знать внутреннее устройство AST. Нет стабильного,
   сериализуемого промежуточного представления (IR) с номером схемы, на который можно
   опереться через границу модуля и версий.
4. **Риск затащить тяжёлый backend.** Если граница между фронтендом и backend размыта,
   внешний потребитель, импортируя фронтенд, рискует транзитивно затянуть `modernc.org/sqlite`,
   движок процессов и демон — то есть всю исполняющую машинерию, которая ему не нужна и
   которую он (вариант B) реализует нативно сам.

**Боль платформы «Уклад» (потребитель).** Уклад принял архитектурное решение «вариант B»:
исполнять бизнес-определения нативно на своём backend, **не** перенося движок LADIX, и
подключать LADIX только как парсер/валидатор/нормализатор определений с пином версии через
semver. Сейчас это технически невозможно: модуль не подключается, фронтенд не импортируется,
нет IR-контракта.

**Боль мейнтейнера LADIX.** Без чистой границы любая эволюция backend рискует протечь в
публичную поверхность; нет автоматической гарантии, что фронтенд остаётся «лёгким».

Эта фича — **чистая переупаковка**: переезд `go.mod` в корень, добавление узкого ПУБЛИЧНОГО
фасада `ladix.Compile` и версионируемого пакета `ir` ПОВЕРХ фронтенд-пакетов, которые ОСТАЮТСЯ
под `internal/` (см. Clarifications 2026-06-29: публичная поверхность = только `ladix`+`ir`),
страж границы фронтенд↔backend и приведение go-директивы к согласованной версии. Семантика
и синтаксис языка, тексты диагностик и числовая модель — **байт-в-байт неизменны**; standalone
(CLI, движок, SQLite, демон) сохраняется целиком как reference-implementation и исполняемая
спецификация для ~25000 LOC существующих тестов.

## Clarifications

### Session 2026-06-28

- Q: Объём валидации `ladix.Compile` — только синтаксис (lexer+parser) или синтаксис+семантика? → A: B — `Compile` выполняет лексику + синтаксис + семантический проход `eval.Analyze` (без исполнения). Фасад транзитивно зависит от `internal/eval` (но НЕ от `store`/`engine`/`daemon`/`sqlite`); страж границы запрещает только `internal/{store,engine,daemon}` и `modernc.org/sqlite` (`internal/eval` РАЗРЕШЁН).

### Session 2026-06-29

- Q: Публичная поверхность модуля — какие пакеты публичны? → A: ТОЛЬКО `ladix` (фасад `Compile`) + `ir`. `lexer`/`parser`/`ast`/`value`/`errors`/`eval`/`engine`/`store`/`daemon` ОСТАЮТСЯ под `internal/` (наружу НЕ выносятся; фасад импортирует их как `internal/*` своего же модуля). Массовой правки импортов нет. Расширение поверхности позже — аддитивно (`internal`→public не ломает совместимость); из-за этого конституционная правка понижена с MAJOR (`2.0.0`) до MINOR.
- Q: Словарь `ir.Diagnostic.Severity` в v1? → A: эмитится ТОЛЬКО `error` (отражает текущую эмиссию фронтенда). `warning` специфицирован в SPEC §13, но фронтендом НЕ эмитится (отложен). Потребитель ОБЯЗАН толерантно обрабатывать неизвестные значения `Severity` (не падать, трактовать ≥информативно); появление `warning` позже — аддитивно и НЕ требует bump `SchemaVersion`.
- Q: Словарь `ir.Diagnostic.Stage` для фасада `Compile`? → A: ограничен `{lexical, syntax, semantic}` — компиляция статическая; ошибки «Типа»/«Выполнения» (SPEC §13.1) — runtime (типизация в LADIX динамическая, SPEC §4), фронтендом НЕ производятся. Потребитель толерантен к неизвестным `Stage` (forward-compat).
- Q: Представление выражений в IR v1 — строки или структура? → A: канонические строки достаточны для round-trip и reference-движка. Для варианта B (Уклад транслирует метрики в SQL на ClickHouse) строк НЕ хватит, а парсер по Q1 остаётся `internal/` → осознанный ОТЛОЖЕННЫЙ gap: структурное представление выражений появится в `ir` на Phase 4 (bump `SchemaVersion` → v2, предусмотрен политикой), а НЕ через вынос парсера/AST в публичную поверхность.
- Q: JSON round-trip `ir` — гарантия v1 или forward-looking? → A: ТЕСТИРУЕМЫЙ контракт v1 — golden-тест сериализации `ir.Program` + декодер, толерантный к неизвестным полям/`severity`/`stage`. Весь semver-риск стянут в `ir` (Q1), потому его форму защищаем golden-замком; JSON — мост к будущему proto/BSR для не-Go потребителей.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Уклад импортирует фасад и компилирует определение в IR (Priority: P1)

Платформа «Уклад» добавляет `github.com/denis-kosyakov/ladix` в свои зависимости, импортирует
корневой пакет `ladix` и вызывает `ladix.Compile(source)`. На валидном исходнике она получает
`*ir.Program` (со стабильным `schema_version`) и пустой/некритичный список диагностик; на
невалидном — `program == nil` и `[]ir.Diagnostic` с дословными русскими сообщениями. При этом
сборка Уклада **не затягивает** `modernc.org/sqlite` и backend-пакеты LADIX.

**Why this priority**: это ключевая ценность фичи и единственная причина, по которой Уклад
вообще может потреблять LADIX. Без узкого импортируемого фасада и версионируемого IR фича
бессмысленна. Без US1 нет продукта.

**Independent Test**: из внешнего тест-модуля (или теста корневого пакета) импортировать
`ladix` и `ir`, скомпилировать валидный и невалидный исходники, проверить тип/`schema_version`
результата и дословность диагностик; отдельно — страж границы доказывает, что публичное
замыкание `ladix`+`ir` не содержит `modernc.org/sqlite` и `internal/{store,engine,daemon}`.

**Acceptance Scenarios**:

1. **Given** валидный исходник LADIX, **When** вызывается `ladix.Compile(source)`,
   **Then** возвращается `*ir.Program` с `SchemaVersion == 1`, `err == nil` и без диагностик
   уровня `error` (`program != nil`). (A1)
2. **Given** исходник с синтаксической/семантической ошибкой, **When** вызывается
   `ladix.Compile(source)`, **Then** `program == nil`, `err == nil`, а `diags` содержит хотя бы
   одну `Diagnostic` уровня `error` с дословным русским сообщением из SPEC §13 и позицией
   (`Line`/`Col`). (A2)
3. **Given** путь к файлу `.ladix`, **When** вызывается `ladix.CompileFile(path)`,
   **Then** результат эквивалентен `Compile` над содержимым файла; при ошибке чтения файла
   возвращается `err != nil` (внутренний сбой, а не диагностика). (A3)
4. **Given** внешний модуль, импортирующий только `ladix` и `ir`, **When** разрешаются его
   зависимости, **Then** в транзитивном замыкании НЕТ `modernc.org/sqlite` и пакетов
   `internal/{store,engine,daemon}` (потребитель не тянет SQLite). (A4)

### User Story 2 — `go get` работает с корня, module-path стабилен (Priority: P1)

Внешний разработчик выполняет `go get github.com/denis-kosyakov/ladix@v0.1.0` и получает
рабочий модуль: `go.mod` лежит в корне репозитория, module-path неизменен
(`github.com/denis-kosyakov/ladix`, без сегмента `/src`), go-директива — согласованная версия
(`1.23`), модуль собирается.

**Why this priority**: без рабочего `go get` US1 недостижима физически — это инфраструктурное
предусловие потребления. P1 наравне с US1.

**Independent Test**: убедиться, что `go.mod` в корне; что module-path равен
`github.com/denis-kosyakov/ladix`; что внутренние импорты `internal/*` и `cmd/*` НЕ сломаны
переездом модуля (путь не содержал `/src`, поэтому импорт-пути стабильны); что go-директива
== `1.23`; что `go build ./...` из корня зелёный.

**Acceptance Scenarios**:

1. **Given** репозиторий после переезда, **When** проверяется расположение `go.mod`,
   **Then** он находится в корне репозитория, а не в `src/`. (A5)
2. **Given** корневой `go.mod`, **When** читается директива `module`, **Then** она равна
   `github.com/denis-kosyakov/ladix` (без `/src`), и существующие импорты `internal/*` / `cmd/*`
   продолжают резолвиться без правок. (A6)
3. **Given** корневой `go.mod`, **When** читается директива `go`, **Then** она равна `1.23`
   (согласована с README и конституцией; расхождение `1.25.0` устранено). (A7)

### User Story 3 — Standalone reference-implementation сохранён и зелён (Priority: P2)

Мейнтейнер LADIX продолжает использовать CLI, движок процессов, SQLite-стор и демон как
эталонную реализацию и исполняемую спецификацию. После переупаковки `go build`, `go vet` и
`go test ./...` из **корня** зелёные; ~25000 LOC существующих тестов не удалены и проходят;
backend остаётся под `internal/`.

**Why this priority**: сохранность reference-impl и тестового корпуса — гарантия, что
переупаковка ничего не сломала. Это не новая ценность для потребителя (P2), но обязательное
условие безопасности рефактора.

**Independent Test**: из корня прогнать `go build ./...`, `go vet ./...`, `go test ./...`;
убедиться, что ни один тест не удалён, тест-хелперы путей (`cmd/ladix`, использовавшие
`../../../`) починены под новую раскладку, а `examples/`/`testdata` резолвятся.

**Acceptance Scenarios**:

1. **Given** репозиторий после переупаковки, **When** из корня выполняется
   `go build ./... && go vet ./... && go test ./...`, **Then** все три команды зелёные. (A8)
2. **Given** тест-хелперы `cmd/ladix`, ранее адресовавшие корень через `../../../`,
   **When** структура `src/`→корень изменилась, **Then** хелперы починены и тесты находят
   `examples/`/`testdata`; ни один тест не удалён. (A9)
3. **Given** пакеты `lexer`, `parser`, `ast`, `value`, `errors`, `eval`, `engine`, `store`,
   `daemon`, `jsonval`, **When** проверяется их расположение, **Then** они остаются под
   `internal/` (наружу НЕ вынесены; публичны только `ladix`+`ir`), CLI остаётся в `cmd/ladix`. (A10)

### User Story 4 — Версионирование и первый релиз (Priority: P3)

Мейнтейнер публикует модуль и тегирует версии по semver (`vX.Y.Z`). Первый тег — `v0.1.0`.
Версии языка аддитивны (новые возможности не ломают существующий синтаксис); breaking-изменение
формата IR сопровождается bump `ir.SchemaVersion`.

**Why this priority**: версионирование важно для устойчивого потребления, но не блокирует
первый импорт и компиляцию. P3.

**Independent Test**: убедиться, что определён `ir.SchemaVersion == 1`; что задокументирована
политика semver и аддитивности; что репозиторий готов к тегу `v0.1.0` (публикация = `git remote`
+ `push` + тег, вне диффа кода).

**Acceptance Scenarios**:

1. **Given** пакет `ir`, **When** читается `SchemaVersion`, **Then** он равен `1` и сериализуется
   в JSON-поле `schema_version`. (A11)
2. **Given** будущее breaking-изменение формата IR, **When** оно вносится, **Then** правило
   требует bump `ir.SchemaVersion`; аддитивные изменения языка версию схемы НЕ меняют. (A12)
3. **Given** готовый к публикации репозиторий, **When** выполняется релиз, **Then** первый тег
   — `v0.1.0` по semver. (A13)

### Edge Cases

- **Переезд `go.mod` ломает тест-хелперы путей.** Хелперы в `cmd/ladix`, адресовавшие корень
  репозитория относительными `../../../`, после схлопывания `src/`→корень указывают не туда;
  это В скоупе починки (US3/A9). `examples/data/*` резолвятся file-relative (фича 026) и
  безопасны.
- **Импорт-пути НЕ переписываются массово.** По решению Clarifications 2026-06-29 фронтенд-
  пакеты НЕ выносятся из `internal/`, поэтому массовой правки импортов нет: единственное
  перемещение — `go.mod` в корень (схлопывание `src/`→корень при неизменном module-path без
  `/src`), оно импорт-стабильно. Публичная поверхность пополняется ТОЛЬКО двумя новыми пакетами
  (`ir`, `ladix`); их добавление чужие импорты не трогает.
- **Страж границы краснеет при протечке SQLite.** Если кто-то в публичном замыкании
  (`ladix`, `ir`) транзитивно подтянет `internal/{store,engine,daemon}` или
  `modernc.org/sqlite`, тест-страж `boundary_test.go` (через `go list -deps`) обязан упасть.
  `internal/eval` в замыкании допустим (см. FR-009).
- **Что считается breaking-изменением IR.** Удаление/переименование поля, смена типа, смена
  семантики существующего поля — breaking, требует bump `SchemaVersion`. Добавление нового
  опционального поля при сохранении совместимости чтения — аддитивно (как и появление нового
  значения `Severity`/`Stage` — потребитель обязан их толерантно игнорировать). Переход выражений
  из канонических строк в структурное представление — breaking (будущий bump → v2); это
  осознанный отложенный gap для варианта B (Уклад транслирует метрики в SQL на ClickHouse и со
  строк не сможет — Phase 4), закрываемый структурой в `ir`, а НЕ выносом парсера/AST наружу.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ОБЯЗАНА перенести `go.mod` из `src/` в **корень репозитория**, сохранив
  module-path неизменным `github.com/denis-kosyakov/ladix` (без сегмента `/src`), так чтобы
  внутренние импорты `internal/*` и `cmd/*` НЕ ломались переездом модуля. (A5, A6)
- **FR-002**: Система ОБЯЗАНА обеспечить работоспособность `go get github.com/denis-kosyakov/ladix`
  с корня репозитория. (A5, A6)
- **FR-003**: Система ОБЯЗАНА сделать публичной поверхностью модуля РОВНО два пакета: корневой
  пакет-фасад `ladix` и новый версионируемый пакет `ir`. Фронтенд-пакеты `lexer`, `parser`,
  `ast`, `value`, `errors` ОСТАЮТСЯ под `internal/` (наружу НЕ выносятся; фасад `ladix`
  импортирует их как `internal/*` своего же модуля). Массовой правки импорт-путей нет. Расширение
  публичной поверхности позже — аддитивно (`internal`→public не ломает совместимость). (A1, A2)
- **FR-004**: Система ОБЯЗАНА оставить backend-пакеты `eval`, `engine`, `store`, `daemon`,
  `jsonval` под `internal/`, а CLI — в `cmd/ladix`; backend наружу НЕ выносится. (A10)
- **FR-005**: Система ОБЯЗАНА предоставить узкий фасад `ladix.Compile(source string) (program *ir.Program, diags []ir.Diagnostic, err error)`
  и `ladix.CompileFile(path string) (*ir.Program, []ir.Diagnostic, error)` с инвариантом:
  `program != nil` ⟺ среди `diags` нет элемента с `Severity == error`; `err != nil` только при
  внутреннем сбое (например, ошибка чтения файла), НЕ при ошибке компиляции. `Compile` выполняет
  ТРИ стадии валидации: лексику (lexer) + синтаксис (parser) + семантический проход `eval.Analyze`
  (лёгкий fail-fast обход AST БЕЗ исполнения); семантические ошибки попадают в `diags` наравне с
  лексическими/синтаксическими. Фасад строит одноразовый `eval.Interpreter` (вывод в `io.Discard`)
  только ради `Analyze`. (A1, A2, A3)
- **FR-006**: Система ОБЯЗАНА определить пакет `ir` с: `const SchemaVersion = 1`; типом
  `Program{ SchemaVersion int (json:"schema_version"); Metrics; Processes; Triggers }`; типом
  `Position{ Line; Col }`; типом `Diagnostic{ Severity; Stage; Message; Pos }`. Все JSON-теги —
  `snake_case`. Словарь `Severity` в v1 — `error` (фронтенд эмитит только ошибки; `warning`
  специфицирован SPEC §13, но НЕ эмитится — отложен). Словарь `Stage` — `{lexical, syntax,
  semantic}` (компиляция статическая; ошибки «Типа»/«Выполнения» SPEC §13.1 — runtime, динамическая
  типизация SPEC §4, фронтендом НЕ производятся). (A1, A11)
- **FR-007**: Система ОБЯЗАНА брать `Diagnostic.Message` **дословно** из текстов диагностик
  SPEC §13 (русские формулировки); переформулирование ЗАПРЕЩЕНО (Принцип VIII). (A2)
- **FR-008**: Система ОБЯЗАНА представлять выражения в IR `SchemaVersion == 1` **каноническими
  строками** (как `ast.CanonicalTriggerCondition`). Этого достаточно для round-trip и reference-
  движка. Структурное представление выражений — ОСОЗНАННЫЙ отложенный gap: для варианта B (Уклад
  транслирует метрики в SQL на ClickHouse) строк не хватит, но т.к. парсер по FR-003 остаётся
  `internal/`, структура появится в `ir` на Phase 4 через bump `SchemaVersion` (→ v2), а НЕ через
  вынос парсера/AST в публичную поверхность. (A12)
- **FR-009**: Система ОБЯЗАНА удерживать жёсткую границу: публичное замыкание (`ladix`, `ir` —
  единственные публичные пакеты, FR-003) НЕ ИМЕЕТ ПРАВА импортировать `internal/{store,engine,
  daemon}` или `modernc.org/sqlite` — ни прямо, ни транзитивно. `internal/eval` (как и
  `internal/{lexer,parser,ast,value,errors,jsonval}`) из запретного списка ЯВНО ИСКЛЮЧЁН: фасад
  `ladix` импортирует `eval` ради семантического прохода `Analyze` (FR-005), а `eval` сам НЕ тянет
  `store`/`engine`/`daemon`/`sqlite` (проверено), поэтому граница остаётся «лёгкой». (A4)
- **FR-010**: Система ОБЯЗАНА проверять границу FR-009 тестом-стражем `boundary_test.go`,
  опирающимся на `go list -deps` над публичным замыканием (`ladix`, `ir`); запретный набор стража
  = `internal/{store,engine,daemon}` и `modernc.org/sqlite` (НО НЕ `internal/eval`); страж ОБЯЗАН
  краснеть при протечке любого запрещённого пакета в публичное замыкание. (A4)
- **FR-011**: Система ОБЯЗАНА привести go-директиву `go.mod` к `1.23` и устранить расхождение
  версий между `go.mod` (`1.25.0`), README и конституцией, приведя их к единому `1.23`. (A7)
- **FR-012**: Система ОБЯЗАНА сохранить standalone reference-implementation: CLI, движок
  процессов, SQLite-стор и демон НЕ удаляются. (A10)
- **FR-013**: Система ОБЯЗАНА сохранить весь существующий тестовый корпус (~25000 LOC): ни один
  тест не удаляется; `go build ./...`, `go vet ./...`, `go test ./...` из **корня** зелёные. (A8)
- **FR-014**: Система ОБЯЗАНА починить тест-хелперы путей, сломанные схлопыванием `src/`→корень
  (в частности `cmd/ladix`, использовавшие `../../../`), чтобы тесты находили `examples/`/`testdata`. (A9)
- **FR-015**: Система ОБЯЗАНА НЕ менять семантику и синтаксис языка, тексты диагностик, числовую
  модель, wire-форматы и контракт Store; фича — только перемещение/экспорт/упаковка.
- **FR-016**: Система ОБЯЗАНА определить политику версионирования: semver `vX.Y.Z`; аддитивность
  версий языка; первый тег `v0.1.0`; bump `ir.SchemaVersion` при breaking-изменении формата IR.
  Аддитивные изменения (новое опциональное поле, новое значение `Severity`/`Stage`) версию схемы
  НЕ меняют. (A11, A12, A13)
- **FR-017**: Правка конституции ОБЯЗАНА быть выполнена отдельным артефактом как **предусловие
  Constitution Check** этапа плана; в данной спецификации она фиксируется как требование процесса.
  Правка — **MINOR-bump (НЕ MAJOR `2.0.0`)**: т.к. по FR-003 НИЧЕГО не покидает `internal/`
  (`errors`/`value`/`ast` остаются внутренними), Принцип III НЕ меняется и Принцип VII НЕ
  переопределяется — конституция лишь ДОПОЛНЯЕТСЯ разрешением двух новых публичных пакетов
  (`ladix`, `ir`) и публичного типа `ir.Position` (Принцип IV). Точный номер MINOR-версии
  выбирается в артефакте конституции.
- **FR-018**: Система ОБЯЗАНА зафиксировать в чеклисте «контракта апстрима», что контракт с
  платформой «Уклад» принят со слов владельца (вариант B) и рекомендуется закрепить документом

  wire-ключей и НЕ добавляет внешних зависимостей фронтенда (потребитель не тянет SQLite).
- **FR-020**: Система ОБЯЗАНА зафиксировать контракт forward-compat для потребителя: потребитель
  IR ОБЯЗАН толерантно обрабатывать неизвестные значения `Severity`/`Stage` и неизвестные
  JSON-поля (не падать; неизвестный `Severity` трактовать как ≥информативный). Благодаря этому
  появление `warning`, новой стадии или нового опционального поля — аддитивно и НЕ требует bump
  `SchemaVersion`. (A2)
- **FR-021**: Система ОБЯЗАНА сделать JSON round-trip пакета `ir` **тестируемым контрактом v1**:
  golden-тест сериализации `ir.Program` (фиксирует форму `snake_case`) + декодер, толерантный к
  неизвестным полям/`severity`/`stage`. Обоснование: по FR-003 весь semver-риск стянут в `ir`,
  потому его форму защищаем golden-замком; JSON — мост к будущему proto/BSR для не-Go потребителей.
  (A11)

### Key Entities *(include if feature involves data)*

- **`ir.Program`**: корень IR; поле `SchemaVersion` (`schema_version`, == 1 в v1) плюс коллекции
  `Metrics`, `Processes`, `Triggers`. Сериализуем в JSON (`snake_case`).
- **`ir.Metric` / `ir.Process` / `ir.Trigger`**: нормализованные определения; выражения — как
  канонические строки (v1). Структурное представление — будущий bump схемы.
- **`ir.Diagnostic`**: одна проблема компиляции; поля `Severity` (v1 — только `error`; `warning`
  отложен), `Stage` (`{lexical, syntax, semantic}`), `Message` (дословно SPEC §13), `Pos`
  (`ir.Position`). Потребитель толерантен к неизвестным `Severity`/`Stage`.
- **`ir.Position`**: позиция в исходнике; поля `Line`, `Col`.
- **JSON-форма `ir`**: `snake_case`; round-trip — golden-locked контракт v1 (FR-021); декодер
  игнорирует неизвестные поля/`severity`/`stage`.
- **Фасад `ladix.Compile` / `ladix.CompileFile`**: узкая точка входа (ЕДИНСТВЕННЫЙ публичный
  способ получить `ir`); контракт `program != nil ⟺ нет diags уровня error`, `err != nil` только
  при внутреннем сбое.
- **Страж границы `boundary_test.go`**: тест, через `go list -deps` доказывающий, что публичное
  замыкание (`ladix`, `ir`) не содержит `internal/{store,engine,daemon}` и `modernc.org/sqlite`.

## Assumptions

- **Контракт апстрима принят со слов владельца, документа на стороне Уклада пока НЕТ.** В
  репозитории платформы «Уклад» (`/Users/denis/dev/uklad`, go `1.23`, модули
  `github.com/uklad/uklad/backend/*`) на момент написания **отсутствует** какой-либо контракт на
  LADIX: нет `docs/ladix/integration_v4.md`, нет тикетов `BL-LADIX-*`, ноль упоминаний «ladix».
  «Контракт апстрима» = устное решение «вариант B» (исполнять определения нативно, движок не
  переносить, пинить версии semver) от владельца. Это ЯВНОЕ допущение (Принцип IX — молча
  додумывать запрещено); рекомендуется закрепить документом на стороне Уклада
  (`docs/ladix/integration_v4.md`) — вне диффа данной фичи.
- Существующее поведение языка (синтаксис, семантика, тексты диагностик SPEC §13, числовая
  модель) считается **корректным эталоном**; задача — переупаковать, а не изменить.
- SpecKit используется нативно (артефакты `specs/029-*`); процесс планирования и реализации
  идёт через `/speckit-*`.
- Репозиторий остаётся in-place внутри `scalingclub_practice/ladix`; публикация = `git remote`
  + `push` + тег (вне диффа кода).
- go-директива `1.23` допустима конституцией (требует `1.22+`); блокеров для понижения с
  `1.25.0` нет.
- **Структурное представление выражений в IR — отложено до Phase 4 (вариант B).** v1 несёт
  выражения каноническими строками; их хватает для round-trip и reference-движка, но НЕ для
  трансляции метрик в SQL на ClickHouse в Укладе. Это осознанный gap, закрываемый структурой в
  `ir` (bump `SchemaVersion` → v2), а НЕ выносом парсера/AST наружу (FR-008, FR-003).
- **Потребитель IR толерантен к неизвестным `Severity`/`Stage`/полям** — предусловие аддитивной
  эволюции схемы без bump (FR-020).

## Out of Scope

- НЕ менять семантику и синтаксис языка.
- НЕ удалять движок процессов, CLI, SQLite-стор и демон (standalone reference-impl сохраняется).
- НЕ переформулировать тексты диагностик (Принцип VIII — дословно SPEC §13).
- НЕ раскалывать пакет `eval` (~4.5k LOC): наружу выносится IR-контракт, а исполнитель остаётся
  под `internal/`.
- НЕ выносить `lexer`/`parser`/`ast`/`value`/`errors` из `internal/` (Clarifications 2026-06-29:
  публичны ТОЛЬКО `ladix`+`ir`; расширение поверхности — позже, аддитивно).
- НЕ ломать существующие тесты и пути `testdata`/`examples` (`examples/data/*` file-relative
  безопасны; починка тест-хелперов `cmd/ladix` `../../../` — В скоупе, см. FR-014).
- НЕ переводить выражения IR в структурное представление (v1 — канонические строки; структурное
  — будущий bump `SchemaVersion`).
- НЕ создавать документ контракта на стороне Уклада (`docs/ladix/integration_v4.md`) — вне диффа.
