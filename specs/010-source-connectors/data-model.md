# Phase 1 — Data Model: коннекторы источника (010-A1)

**Назначение.** A1 — чистый фронтенд + загрузчик. Эта модель фиксирует
**структуры данных**, которые A1 вводит или расширяет: узлы AST, множество
аннотаций полей и их отображение в `value`-типы, матрицу коэрсии, жизненный цикл
записи и каталог ошибок. Источник истины — `docs/source-connectors-model.md`
§SC-2..§SC-9; любой пробел закрывается ТАМ.

Нормативные термины: **ИНВАРИАНТ** — должно выполняться всегда; **АДДИТИВНО** —
существующая структура расширяется без изменения старых полей/сигнатур.
**Несущее свойство (§SC-0):** все программы v1 валидны — источник без `тип:`/`поля:`
ведёт себя ровно как v1 (JSON schemaless).

## 1. SourceDecl — расширение (§SC-2)

`SourceDecl` (`ast/decl.go:21`) сегодня несёт только `Name`/`File`/`FilePos`.
A1 расширяет его **аддитивно** (дословно из §SC-2):

```go
type SourceDecl struct {
    declBase
    Name    Ident
    File    StringLit
    FilePos Position
    Type    Ident       // НОВОЕ: значение тип: (json|csv|ndjson); zero-value Name=="" → json (A1-2)
    TypePos Position     // НОВОЕ: позиция атрибута тип: (presence: Line!=0)
    Fields  []FieldDef   // НОВОЕ: объявленная схема поля:; nil/пусто → schemaless (A1-3)
    FieldsPos Position    // НОВОЕ: позиция атрибута поля: (presence: Line!=0)
}
```

**Поля.**
- `Type Ident` — голое значение `тип:` (`json`/`csv`/`ndjson`); нулевое `Name==""` ⇒ `json` (§SC-D-PARSE-2, A1-2).
- `TypePos Position` — позиция атрибута `тип:`; **наличие = `Line != 0`** (presence-конвенция, как `MetricAttrPos`).
- `Fields []FieldDef` — объявленная схема; `nil`/пусто ⇒ schemaless.
- `FieldsPos Position` — позиция атрибута `поля:`; наличие = `Line != 0`.

**Инварианты.**
- ИНВАРИАНТ (§SC-D-1, presence): наличие `тип:`/`поля:` отслеживается `Pos.Line != 0`, не nil-указателем.
- ИНВАРИАНТ (§SC-D-3, конструктор): `NewSourceDecl` сохраняет текущую сигнатуру; `Type`/`Fields` заполняются парсером сеттер-присваиванием (`sd.Type = …`), как `MetricDecl.Attrs` — иные вызовы конструктора не трогаются.
- ИНВАРИАНТ: v1-форма (без `тип:`/`поля:`) даёт нулевые `Type`/`Fields` ⇒ путь JSON schemaless (§SC-6).

## 2. FieldDef — новый листовой узел (§SC-2)

Новый узел AST в `ast/decl.go`, рядом с `SourceDecl` (дословно из §SC-2):

```go
// FieldDef — одно объявление поля в блоке поля: (имя: ТипПоля)
type FieldDef struct {
    Name     Ident     // имя поля (произвольный идентификатор)
    TypeName Ident     // имя типа (Целое|Дробное|Строка|Логическое|Дата) — резолвится семантически
    Pos      Position  // позиция строки объявления поля
}
```

**Поля.**
- `Name Ident` — имя поля; произвольный идентификатор (НЕ keyword; `поля` остаётся `IDENT`, §SC-D-RESERVE).
- `TypeName Ident` — имя типа-аннотации; принадлежность множеству проверяется **семантически** (§SC-4-sem п.3), не парсером.
- `Pos Position` — позиция строки объявления поля; используется как позиция семантической ошибки «неизвестный тип поля».

**Инварианты.**
- ИНВАРИАНТ (§SC-D-2, листовость): `FieldDef` несёт **локальную** `ast.Position`, не импортирует `errors`; пакет `ast` остаётся листовым (конституция IV/VII).
- ИНВАРИАНТ: имена полей уникальны в пределах источника — дубликат ловит парсер (§SC-D-PARSE-3, `msgDuplicateAttr`), семантика не дублирует (§SC-4-sem п.4).

## 3. Множество аннотаций `поля:` → `value`-типы (§SC-5)

Аннотация в `поля:` отображается в значение `value` так (дословно из §SC-5):

| Аннотация в `поля:` | Значение `value` | Печать `TypeName()` |
|---|---|---|
| `Целое` | `value.Целое{V int64}` | `Целое` |
| `Дробное` | `value.Дробное{V float64}` | `Дробное` |
| `Строка` | `value.Строка{V string}` | `Строка` |
| `Логическое` | `value.Булево{V bool}` | `Булево` |
| `Дата` | `value.Дата{Year,Month,Day}` | `Дата` |

**Инварианты.**
- ИНВАРИАНТ (§SC-D-BOOL): аннотация `Логическое` отображается в значение `Булево` (историческое имя-тип). A1 принимает **ровно эти пять** имён (A1-4); прочее ⇒ `semErr` «неизвестный тип поля».
- ИНВАРИАНТ (§SC-D-BOOL, диагностика): в «ожидался `<Тип>`» печатается **аннотация** (`Логическое`); в «получено `<тип>`» — фактический `TypeName()` значения (`Булево`).
- ИНВАРИАНТ (§SC-D-DATE): `value.Дата` строится строгим `parseISODate(s)` (`eval/builtins_date.go:61`, 10-байт `ГГГГ-ММ-ДД`, валидация календаря/високосного) — **тот же** парсер, что у builtin `дата(...)`, единый канон формата.

## 4. Матрица коэрсии `applySchema` (§SC-D-COERCE)

Применяется при `len(decl.Fields) > 0`. Для каждой записи N (с 1) и каждого
объявленного `FieldDef{name, T}` (дословно из §SC-D-COERCE):

1. **Отсутствие** (A1-5): поля `name` нет в записи (членство в `Keys()`) ⇒ `runtimeErr` «отсутствует объявленное поле». (Лишние поля — ок, A1-6.)
2. **Коэрсия значения `v` в тип `T`** — различается по источнику:

| `T` \ источник | CSV (всё `Строка`) | JSON/NDJSON (типизировано) |
|---|---|---|
| `Строка` | оставить как есть | требуется `Строка`; иначе A1-10 |
| `Целое` | `strconv` строки→int; ошибка→A1-10 | `Целое` ок; `Дробное`→A1-10 (демоушена нет) |
| `Дробное` | `strconv` строки→float; ошибка→A1-10 | `Дробное` ок; `Целое`→промоушен в `Дробное` (A1-10) |
| `Логическое` | `истина`/`ложь`→`Булево`; иначе A1-10 | `Булево` ок; иначе A1-10 |
| `Дата` | `parseISODate`; ошибка→A1-7 | `Строка`→`parseISODate` (A1-7); иначе A1-10 |

3. **Запись с коэрснутыми значениями** заменяет исходную (порядок ключей сохранён; лишние поля остаются).

**Правила (§SC-D-COERCE-*).**
- ИНВАРИАНТ `INT` (§SC-D-COERCE-INT): CSV-`Целое` — без `.`/`e`/`E`; десятичная точка ⇒ ошибка «не является целым» (а не молчаливое `Дробное`); инвариант формы числа §9.3 SPEC.
- ИНВАРИАНТ `FLOAT` (§SC-D-COERCE-FLOAT): CSV-`Дробное` принимает и `1200000`, и `1200000.5` (обе → `Дробное`).
- ИНВАРИАНТ `PROMO` (§SC-D-COERCE-PROMO): **единственный** кросс-тип промоушен — `Целое→Дробное` (A1-10), как `arith.go:233`; прочее несовпадение ⇒ `runtimeErr` (A1-10).

## 5. Жизненный цикл записи (§SC-6, §SC-D-RECORD)

**Поток (§SC-6).** `loadSource` — диспетчер по `decl.Type.Name`:

```
name := decl.Name.Name; if cache hit → return
switch decl.Type.Name {                 // "" → json (A1-2)
  case "", "json":  recs = loadJSON(...)
  case "csv":       recs = loadCSV(...)   // НОВОЕ
  case "ndjson":    recs = loadNDJSON(...)// НОВОЕ
}
if len(decl.Fields) > 0 { recs = applySchema(decl, recs) }  // §SC-D-COERCE
i.recordCache[name] = recs
```

Жизненный цикл одной записи: **load** (по формату) → **dispatch по `Type`** →
**applySchema** (если есть схема) → **пересборка через `NewRecord`**.

**Пересборка (§SC-D-RECORD, верифицировано).** `value.Запись` (`record.go`) имеет
приватные `keys`/`fields`; **Set-метода НЕТ**, `fields` неэкспортируем. Поэтому
`applySchema` НЕ мутирует на месте, а **пересобирает**:
- `keys := r.Keys()`; `newFields := {}`; для каждого `k`: `newFields[k] = r.Get(k)` (лишние поля как есть);
- для каждого `FieldDef{name,T}`: **присутствие = членство `name` в `keys`** (отличает «отсутствует» A1-5 от «есть, но `Пусто`/null» — последнее → A1-10); коэрснуть `r.Get(name)`, записать в `newFields[name]`;
- вернуть `NewRecord(keys, newFields)`.

**Публичная поверхность `value.Запись` — БЕЗ ИЗМЕНЕНИЙ.** `Keys() []string`,
`Get(name) Value`, `NewRecord(keys, fields)` — используются как есть; пакет `value`
**не трогается** (остаётся листовым, конституция VII).

**Edge (null/пустая ячейка, §SC-D-RECORD).** Объявленное поле со значением `Пусто`
(JSON null) или пустой CSV-ячейкой (`""`) — НЕ «отсутствует» (ключ есть), а
несовпадение/непарс: `Пусто`→A1-10 «ожидался `<Тип>`, получено Пусто»; `""`→
A1-7/A1-10 непарс. Зафиксировать golden-кейсом.

**Инварианты.**
- ИНВАРИАНТ (§SC-D-CACHE): новые загрузчики ТОЖЕ пишут `i.recordCache[name]` — кеш по имени источника, per-run; путь — `os.Open(path)` от CWD (§12, НЕ менять).
- ИНВАРИАНТ (§SC-D-EMPTY): источник из нуля записей со схемой — `applySchema` ничего не валидирует (нечего); метрика даёт пустой результат (§SM-10), совместимо с §9.7 SPEC.
- ИНВАРИАНТ (§SC-D-NDJSON): пустые строки NDJSON пропускаются (A1-9); не-объект на строке ⇒ load-ошибка.

## 6. Сущности ошибок (§SC-9)

Конвенция §SM-9: **без точки в конце**; `'…'` — идентификаторы/имена; `«…»` —
строковые литералы (пути/значения/форматы); `<тип>` — из закрытого множества; **N с
1**; тексты — **дословный канон** (конституция VIII), реализация берёт byte-identical.

**§SC-9.A — Семантика (Analyze), `СемантическаяОшибка`; позиция = `TypePos` / `FieldDef.Pos`:**
```
источник '<имя>': неизвестный тип источника '<знач>' (допустимо: json, csv, ndjson)
источник '<имя>': тип '<csv|ndjson>' требует объявления полей (поля:)
источник '<имя>': неизвестный тип поля '<знач>' (допустимо: Целое, Дробное, Строка, Логическое, Дата)
```
(Парсерные «неизвестный атрибут '<имя>'» / «атрибут '<имя>' уже задан» / «поле
'<имя>' уже объявлено» — переиспользуют §SM-9.A `msgUnknownAttr`/`msgDuplicateAttr`.)

**§SC-9.B — Загрузка/коэрсия (рантайм), `ОшибкаВыполнения`; позиция = decl:**
```
источник '<имя>': запись N: отсутствует объявленное поле '<поле>'
источник '<имя>': запись N, поле '<поле>': ожидался <Тип>, получено <тип>
источник '<имя>': запись N, поле '<поле>': «<знач>» не является датой (ожидался формат ГГГГ-ММ-ДД)
источник '<имя>': запись N, поле '<поле>': «<знач>» не является целым
источник '<имя>': запись N, поле '<поле>': «<знач>» не является дробным
источник '<имя>': запись N, поле '<поле>': «<знач>» не является логическим (ожидалось истина/ложь)
источник '<имя>': в заголовке CSV «<путь>» отсутствует поле '<поле>'
источник '<имя>': некорректный CSV в «<путь>» (<деталь>)
источник '<имя>': запись N: некорректный JSON (<деталь>)
```
(`<Тип>` в «ожидался» — аннотация `поля:`, `Логическое` не `Булево`; `<тип>` в
«получено» — `TypeName()` значения. Существующие JSON-сообщения §SM-9.B — без
изменений.)

**Инварианты.**
- ИНВАРИАНТ: семантика (§SC-9.A) — статическая (без чтения файла), на этапе Analyze; рантайм (§SC-9.B) — при load/coerce.
- ИНВАРИАНТ: каждая ошибка несёт имя источника, имя поля (где применимо), номер записи N (с 1).

## 7. Инварианты состояния (§SC-2, §SC-D-CACHE)

- ИНВАРИАНТ (кеш): записи кешируются `i.recordCache[name]` по имени источника, per-run; повторный `loadSource` того же имени возвращает кеш.
- ИНВАРИАНТ (позиции): семантические ошибки несут позицию декларации — `TypePos` (тип/обязательность полей) либо `FieldDef.Pos` (тип поля); load/coerce-ошибки несут позицию токена `источник` (decl).
- ИНВАРИАНТ (presence): нулевые `TypePos`/`FieldsPos` (`Line==0`) ≡ v1-форма ⇒ JSON schemaless путь.
- ИНВАРИАНТ (изоляция, §SC-8/§SC-11): `Store`/`ProcessRuntime`/экспорт `eval`/условие триггера/фронтенд `где`/`агрегат`/`период`/`по_дате` — НЕ трогаются; `ast` листовой; 0 новых зависимостей.
