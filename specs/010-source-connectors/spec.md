# Feature Specification: Коннекторы источника (тип: + схема поля:)

**Feature Branch**: `010-source-connectors`

**Created**: 2026-06-15

**Status**: Draft

**Input**: Снять три ограничения §12 SPEC для источников БЕЗ поломки v1: атрибут `тип:` источника (`json` | `csv` | `ndjson`, по умолчанию `json`); блок схемы `поля:` (типизированное объявление полей записи `Целое`/`Дробное`/`Строка`/`Логическое`/`Дата`); распознавание дат — поле, объявленное `Дата`, парсится из строки ISO `ГГГГ-ММ-ДД`. Это срез M1-A1 хартии v2: реальный CSV-источник кормит существующую метрику.

> **Источник истины** — `docs/source-connectors-model.md` (§SC-0…§SC-13 + предрешённые развилки A1-1…A1-10). Спецификация выведена из якоря и не вводит требований сверх него и НЕ содержит NEEDS CLARIFICATION; при любом расхождении источников побеждает якорь. **Несущее свойство (инвариант 3 хартии §5):** изменение — чистый фронтенд + загрузчик; все программы v1 остаются валидными (источник без `тип:`/`поля:` ведёт себя ровно как v1 — JSON schemaless). Фронтенд `где`/`агрегат`/`период`/`по_дате`, контракт `Store`, движок процессов и условие триггера — НЕ трогаются.

## User Scenarios & Testing *(mandatory)*

Действующие лица: **бизнес-автор** (пишет источник + метрику на реальной выгрузке Уклада — CSV/NDJSON/JSON со схемой), **аналитик** (сверяет результат метрики на CSV с эталоном), **оператор** (прогоняет `ladix run`/`serve` поверх типизированного источника). Система — **фронтенд + загрузчик источников Ladix**: декларации `источник`/`метрика`, загрузка и коэрсия записей по объявленной схеме, диагностика ошибок данных с позицией.

### User Story 1 — Реальный CSV-источник кормит метрику (Priority: P1)

Бизнес-автор берёт реальную CSV-выгрузку заказов (первая строка — заголовок столбцов, разделитель `,`, кодировка UTF-8) и подключает её как источник, объявив `тип: csv` и схему `поля:` с типами столбцов. Существующая метрика v1 (фильтр `где` + агрегат, например `сумма(сумма_заказа)`, с уже доступным периодом v1 `ежемесячно` либо вовсе без `период:`) считается поверх этого CSV-источника и даёт тот же скаляр, что и на эквивалентном JSON-источнике. Сегодня это невозможно: слово `тип` зарезервировано лексером (lex-ошибка), а источник умеет только JSON-массив без схемы.

**Why this priority**: Это срез Definition of Done вехи M1 (хартия §2/§4): «метрика считается на реальном CSV-источнике; срез сценария до триггера зелёный». Без него M1 не сдвигается, реальные выгрузки Уклада не подключаются — поэтому P1 и MVP фичи.

**Independent Test**: Положить одинаковый набор записей в `testdata/` тремя формами (json со схемой / csv / ndjson), объявить эквивалентные источники и одну метрику, прогнать на фикс-`Clock`. Метрика на CSV-источнике даёт байт-точно тот же скаляр, что на JSON-источнике; exit 0. Реализуется и проверяется только декларациями `источник`/`метрика` и загрузчиком, без участия движка процессов/Store.

**Acceptance Scenarios**:

1. **Given** источник с `тип: csv`, корректным заголовком и схемой `поля:`, и метрика над ним (A1-1, A1-8), **When** выполняется прогон метрики, **Then** результат равен результату той же метрики над эквивалентным JSON-источником со схемой, exit 0.
2. **Given** источник без `тип:` и без `поля:` (v1-форма, A1-2), **When** он грузится, **Then** он трактуется ровно как v1 JSON schemaless — поведение и вывод не меняются.
3. **Given** источник `тип: csv` БЕЗ блока `поля:` (A1-3), **When** программа анализируется, **Then** выдаётся семантическая ошибка «тип 'csv' требует объявления полей (поля:)» с позицией атрибута `тип:`, exit 1.
4. **Given** источник с `тип:` неизвестного значения (например `тип: xml`, A1-1), **When** программа анализируется, **Then** выдаётся семантическая ошибка «неизвестный тип источника 'xml' (допустимо: json, csv, ndjson)» с позицией, exit 1.
5. **Given** CSV-заголовок, в котором отсутствует объявленный в `поля:` столбец (A1-8), **When** источник грузится, **Then** выдаётся ошибка выполнения «в заголовке CSV «<путь>» отсутствует поле '<поле>'» с позицией декларации, exit 1.

### User Story 2 — Схема поля: валидирует записи и распознаёт даты (Priority: P2)

Бизнес-автор объявляет схему `поля:` (имя поля → тип из `Целое`/`Дробное`/`Строка`/`Логическое`/`Дата`) и полагается на загрузчик: каждое объявленное поле обязано присутствовать в записи; значение коэрсится в объявленный тип; поле, объявленное `Дата`, читается из строки ISO `ГГГГ-ММ-ДД` без явного вызова `дата(...)` — и сразу доступно метрике по оси `по_дате`. Лишние (необъявленные) поля разрешены и игнорируются. Несовпадение типа, отсутствие поля и невалидная дата дают чистую ошибку данных с именем источника, именем поля и номером записи.

**Why this priority**: Схема и распознавание дат — ценность авторинга поверх P1 (P1 уже даёт работающий CSV→метрику), но без них типобезопасность и дата-ось на сырых данных недостижимы. Логически вторая по важности, поэтому P2.

**Independent Test**: Источник со схемой, включающей поле `Дата` со строкой ISO; метрика с `по_дате: дата(<поле>)` видит `Дата` без явного `дата(...)`. Отдельно — фикстуры с отсутствующим полем, несовпадением типа и невалидной датой дают точные сообщения §13-канона с номером записи. Проверяется загрузчиком/коэрсией, без движка.

**Acceptance Scenarios**:

1. **Given** запись, в которой отсутствует объявленное в `поля:` поле (A1-5), **When** источник грузится, **Then** ошибка выполнения «источник '<имя>': запись N: отсутствует объявленное поле '<поле>'» (N с 1), exit 1.
2. **Given** запись с лишним необъявленным полем (A1-6), **When** источник грузится, **Then** лишнее поле игнорируется, ошибки нет, остальные поля коэрсятся штатно.
3. **Given** поле, объявленное `Дата`, со строкой `«2026-05-31»` (A1-7), **When** источник грузится, **Then** поле становится значением `Дата` и доступно метрике по `по_дате` без явного `дата(...)`.
4. **Given** поле, объявленное `Дата`, со строкой `«2026-13-40»` или `«31.05.2026»` (A1-7), **When** источник грузится, **Then** ошибка выполнения «… «<знач>» не является датой (ожидался формат ГГГГ-ММ-ДД)» с именем источника, поля и номером записи, exit 1.
5. **Given** поле, объявленное типом вне множества (например `Деньги`, A1-4), **When** программа анализируется, **Then** семантическая ошибка «неизвестный тип поля '<знач>' (допустимо: Целое, Дробное, Строка, Логическое, Дата)» с позицией строки поля, exit 1.

---

### User Story 3 — NDJSON-источник и JSON со схемой (Priority: P3)

Бизнес-автор подключает поток NDJSON (один JSON-объект на строку, пустые строки пропускаются) с объявленной схемой, а также может объявить схему поверх классического JSON-массива для типизации/валидации записей. Несовпадение типа значения и схемы даёт ошибку, кроме единственного разрешённого промоушена `Целое→Дробное`. Все три формата (json/csv/ndjson) с эквивалентным набором записей дают одинаковый результат метрики.

**Why this priority**: NDJSON и JSON-со-схемой расширяют охват форматов и закрывают §12, но реальный срез DoD M1 уже обеспечен CSV (P1); NDJSON — дополнительная форма, поэтому P3.

**Independent Test**: Источник `тип: ndjson` со схемой и фикстурой, где есть пустые строки между объектами; метрика даёт тот же скаляр, что эквивалентные json/csv. Отдельно — фикстура с `Целое`-значением в `Дробное`-поле проходит (промоушен), а `Дробное` в `Целое`-поле даёт ошибку. Проверяется загрузчиком, без движка.

**Acceptance Scenarios**:

1. **Given** NDJSON-файл с пустыми строками между объектами (A1-9), **When** источник грузится, **Then** пустые строки пропускаются, каждая непустая строка — независимый объект-запись, нумерация записей сквозная с 1.
2. **Given** строка NDJSON, не являющаяся JSON-объектом (A1-9), **When** источник грузится, **Then** ошибка выполнения «источник '<имя>': запись N: некорректный JSON (<деталь>)» (или «не является объектом»), exit 1.
3. **Given** `Целое`-значение в поле, объявленном `Дробное` (A1-10), **When** источник грузится, **Then** значение промоутится в `Дробное`, ошибки нет.
4. **Given** `Дробное`-значение в поле, объявленном `Целое` (A1-10, демоушена нет), **When** источник грузится, **Then** ошибка выполнения «… ожидался Целое, получено Дробное» с позицией, exit 1.
5. **Given** эквивалентный набор записей в формах json (со схемой) / csv / ndjson, **When** одна и та же метрика считается над каждым, **Then** результат идентичен (равные скаляры).

---

### Edge Cases

- Источник `тип: csv`/`ndjson` без блока `поля:` — семантическая ошибка (схема обязательна, A1-3); JSON без `поля:` валиден (schemaless, A1-2/A1-3).
- Пустой блок `поля:` (двоеточие, INDENT сразу DEDENT) — ошибка пустого блока на этапе парсера.
- Дубликат атрибута источника (`тип:` дважды) или дубликат имени поля в `поля:` — ошибка «атрибут … уже задан» / «поле … уже объявлено» (переиспользуют §SM-9 канон).
- Источник из нуля записей со схемой — коэрсия не валидирует (нечего), метрика даёт пустой результат (совместимо с §9.7 SPEC); ошибки нет.
- CSV-`Целое` из ячейки с десятичной точкой/`e` (например `«12.5»` в `Целое`-поле) — ошибка «не является целым» (молчаливого превращения в Дробное нет, инвариант формы числа §9.3 SPEC).
- `Логическое`-поле из CSV-ячейки вне `истина`/`ложь` — ошибка «не является логическим (ожидалось истина/ложь)».
- `тип(x)` после освобождения слова `тип` — не lex-ошибка, а семантическая «неизвестная функция 'тип'»; интроспекция типа остаётся вне v2 (хартия §3/§9); меняется лишь категория диагностики (требует обновления 009-замка).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Источник ДОЛЖЕН поддерживать атрибут `тип:` со значением из множества `json`, `csv`, `ndjson` (A1-1). Значение `тип:` — голый идентификатор.
- **FR-002**: При опущенном `тип:` источник ДОЛЖЕН трактоваться как `json` — полная обратная совместимость с v1 (A1-2).
- **FR-003**: Источник ДОЛЖЕН поддерживать блок схемы `поля:` — вложенный список объявлений «имя_поля: ТипПоля». Для `json` блок `поля:` опционален; для `csv` и `ndjson` — обязателен (A1-3).
- **FR-004**: Тип поля в `поля:` ДОЛЖЕН принадлежать множеству `Целое`, `Дробное`, `Строка`, `Логическое`, `Дата` (A1-4); иное значение даёт семантическую ошибку «неизвестный тип поля» с позицией строки поля.
- **FR-005**: Если объявленное в `поля:` поле отсутствует в записи источника, система ДОЛЖНА выдать ошибку данных с именем источника, именем поля и номером записи (N с 1) (A1-5).
- **FR-006**: Лишние (необъявленные в `поля:`) поля записи ДОЛЖНЫ разрешаться и игнорироваться без ошибки (A1-6).
- **FR-007**: Поле, объявленное `Дата`, ДОЛЖНО парситься из строки ISO `ГГГГ-ММ-ДД` в значение `Дата` (тем же строгим парсером формата, что и builtin `дата(...)`) и быть доступным метрике по оси `по_дате` без явного `дата(...)`; невалидная дата даёт ошибку данных с позицией (A1-7).
- **FR-008**: Загрузчик CSV ДОЛЖЕН трактовать первую строку как заголовок (имена столбцов), использовать разделитель `,` и кодировку UTF-8; заголовок обязан содержать все объявленные поля (иначе ошибка «в заголовке CSV … отсутствует поле …»), лишние столбцы игнорируются (A1-8).
- **FR-009**: Загрузчик NDJSON ДОЛЖЕН читать один JSON-объект на строку и пропускать пустые строки; строка-не-объект даёт ошибку данных с номером записи (A1-9).
- **FR-010**: При коэрсии значения в объявленный тип единственный разрешённый кросс-тип промоушен — `Целое→Дробное`; любое иное несовпадение типа значения и схемы ДОЛЖНО давать ошибку данных «ожидался <Тип>, получено <тип>» с позицией (A1-10).
- **FR-011**: Все программы v1 ДОЛЖНЫ оставаться валидными: источник без `тип:` и без `поля:` ведёт себя побайтно как v1 JSON schemaless (инвариант 3 хартии §5); существующие `examples/*.ladix` и golden-тесты проходят без изменения вывода.
- **FR-012**: Каждая ошибка загрузки/коэрсии ДОЛЖНА нести позицию: имя источника, имя поля (где применимо) и номер записи (N с 1); тексты сообщений — дословный русский канон §13/§SC-9 (без точки в конце; `'…'` — идентификаторы; `«…»` — строковые литералы/пути/значения).
- **FR-013**: В «ожидался <Тип>» ДОЛЖНА печататься аннотация из `поля:` (например `Логическое`), а в «получено <тип>» — фактическое имя типа значения; имена закрытого множества — из §SC-5.
- **FR-014**: Фича ДОЛЖНА добавить 0 новых зависимостей (CSV/JSON — средствами стандартной библиотеки; это форматы данных, не грамматика языка).
- **FR-015**: Изоляция фронтенда ДОЛЖНА быть сохранена: лексер/парсер/AST/семантика расширяются только аддитивно и не зависят от движка/Store; контракт `Store`, `ProcessRuntime`, экспорт интерпретатора, фронтенд `где`/`агрегат`/`период`/`по_дате` и условие триггера — НЕ изменяются.
- **FR-016**: Активация `тип:` как атрибута источника НЕ должна вводить интроспекцию типа: вызов `тип(x)` ОБЯЗАН оставаться недоступным (ошибка, exit 1, БЕЗ вывода имени типа «Целое» — встроенная функция `тип` остаётся неактивированной, как требует хартия §3/§9). 009-тест-замок, ранее проверявший конкретную категорию диагностики `тип`, обновляется под новую реальность (сохраняя защиту «exit 1 + нет вывода типа») и обязан кусаться при любой активации интроспекции.
- **FR-017**: Семантические проверки источника (`тип:` ∈ множества; `поля:` обязателен для csv/ndjson; тип каждого поля ∈ множества; дубликаты имён полей) ДОЛЖНЫ выполняться статически на этапе анализа (без чтения файла), с точной позицией.
- **FR-018**: Метрика над типизированным/CSV/NDJSON-источником ДОЛЖНА давать тот же скаляр, что над эквивалентным JSON-источником, и без изменений течь в `ladix run`/`serve`/триггер (границы не меняются).

### Key Entities *(include if feature involves data)*

- **Источник**: декларация поставщика записей. Атрибуты: `файл:` (путь, v1), `тип:` (`json`/`csv`/`ndjson`, по умолчанию `json`), `поля:` (опциональная схема; обязательна для csv/ndjson). Наличие `тип:`/`поля:` отслеживается по позиции, нулевое значение ≡ v1-форма.
- **Поле схемы**: одно объявление внутри `поля:` — имя поля (произвольный идентификатор) + имя типа (`Целое`/`Дробное`/`Строка`/`Логическое`/`Дата`), с позицией строки объявления. Имена полей уникальны в пределах источника.
- **Запись**: одна загруженная единица данных источника (объект JSON/NDJSON или строка CSV после заголовка), нумеруется с 1. После применения схемы каждое объявленное поле коэрснуто в свой тип; лишние поля сохраняются; порядок ключей не меняется.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Метрика на CSV-источнике даёт байт-точно тот же результат, что та же метрика на эквивалентном JSON-источнике (равные скаляры на фикс-`Clock`).
- **SC-002**: Эквивалентный набор записей в трёх формах (json со схемой / csv / ndjson) даёт идентичный результат одной метрики (три равных скаляра).
- **SC-003**: Срез M1 DoD: метрика по образцу `выручка_30д` (фильтр `где статус == "оплачен"` + `сумма(сумма_заказа)`, период v1 `ежемесячно` или без `период:`, ось `по_дате`) считается на реальном CSV-источнике `orders.csv` со схемой `поля:` (`дата_заказа: Дата`, `сумма_заказа: Дробное`, `статус: Строка`) и даёт ожидаемый скаляр, exit 0.
- **SC-004**: Невалидная дата в `Дата`-поле даёт ошибку с именем источника, именем поля и номером записи источника (N с 1), exit 1, stderr — §13-канон.
- **SC-005**: Отсутствие объявленного поля (A1-5), несовпадение типа без разрешённого промоушена (A1-10) и `csv`/`ndjson` без `поля:` (A1-3) — каждое даёт точную диагностику с позицией, exit 1.
- **SC-006**: Промоушен `Целое→Дробное` проходит без ошибки; `Дробное→Целое` и прочие кросс-типы дают ошибку (A1-10).
- **SC-007**: Все существующие `examples/*.ladix` и golden-тесты проходят без изменения вывода; источник без `тип:`/`поля:` грузится как v1 JSON schemaless (0 регрессов).
- **SC-008**: Фича добавляет 0 новых зависимостей; контракт `Store`, `ProcessRuntime`, фронтенд метрик и условие триггера остаются неизменными (изоляция фронтенда сохранена).
- **SC-009**: `печать(тип(5))` завершается exit 1 и НЕ выводит «Целое» (интроспекция типа недоступна — встроенная `тип` не активирована); 009-замок инверсии зелёный и кусается на мутпробе.

## Assumptions

- **A1-1 (типы коннекторов) РЕШЕНО**: ровно `json`, `csv`, `ndjson`; БД/API/HTTP — вне M1.
- **A1-2 (`тип:` опущен) РЕШЕНО**: → `json`, полная обратная совместимость.
- **A1-3 (обязательность `поля:`) РЕШЕНО**: опционально для `json`, обязательно для `csv`/`ndjson`.
- **A1-4 (типы полей) РЕШЕНО**: ровно `Целое`, `Дробное`, `Строка`, `Логическое`, `Дата`; аннотация `Логическое` отображается в значение `Булево`.
- **A1-5 (поле отсутствует) РЕШЕНО**: ошибка данных (источник/поле/запись N).
- **A1-6 (лишние поля) РЕШЕНО**: разрешены, игнорируются.
- **A1-7 (`Дата`-поле) РЕШЕНО**: ISO `ГГГГ-ММ-ДД` → `Дата` тем же строгим парсером, что `дата(...)`; невалидная → ошибка с позицией. Авто-распознавание дат для НЕобъявленных полей НЕ делается — только поля `Дата` в `поля:`.
- **A1-8 (CSV) РЕШЕНО**: 1-я строка — заголовок; разделитель `,`; UTF-8. `разделитель:`/`кодировка:` — вне M1.
- **A1-9 (NDJSON) РЕШЕНО**: один JSON-объект на строку; пустые строки пропускаются.
- **A1-10 (несовпадение типа) РЕШЕНО**: промоушен `Целое→Дробное` ок; прочее — ошибка с позицией.
- **Окна и ряды метрик вне A1**: `метрика-как-ряд`, период `последние N <ед>` и «последний завершённый период» — это A2 (фича 011), НЕ эта фича. Срез DoD M1 в A1 использует существующий период v1 (`ежемесячно`) или вовсе без `период:`.
- **Время не трогается**: `Clock` не меняется; `parseISODate` — чистая функция формата, не зависит от «сегодня»; детерминизм окон — забота A2.
- **Путь к файлу** — `os.Open(path)` от CWD (как §12 v1), не меняется.

## Out of Scope

Согласно §SC-12 якоря, A1 осознанно НЕ делает:

- **Окна метрик** `последние N <ед>` / «последний завершённый период», ряды значений — это **A2 (фича 011)**.
- **БД/API/HTTP-коннекторы**, live-reload, базовый каталог-конфиг — **M3+**.
- **Атрибуты `адрес:`/`разделитель:`/`кодировка:`** — вне M1 (CSV фиксирован: `,` + UTF-8).
- **Операторная арифметика дат/длительностей** (`Дата ± Длит`, `Дата − Дата`) — backlog (хартия §9).
- **Мультиисточник на метрику**, дополнительные агрегаты, ось не-дата — вне M1.
- **Авто-распознавание дат для необъявленных полей** — нет; голые строки остаются `Строка`.
- **Интроспекция `тип(x)`** — вне v2 (хартия §3/§9); A1 делает `тип` ключевым словом-атрибутом источника, но вызов `тип(x)` остаётся недоступным (встроенная функция dormant).
