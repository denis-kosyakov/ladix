## D-1. Коллизия резерва `тип`: keyword `KW_TYPE`, а не голый `IDENT`

**Контекст.** Слово `тип` сегодня в `reservedWords` (`lexer/keywords.go:31`
`"тип": true`) → даёт лексическую ошибку и НЕ порождает токен. Ловушка
(верифицировано): builtin с именем `тип` ЗАРЕГИСТРИРОВАН и реализован
(`builtins.go:75` `add(fixed("тип", 1, builtinTip))`); единственное, что держит
`тип(x)` недостижимым, — лексер-резерв. Атрибут источника `тип:` требует, чтобы
слово порождало токен. Якорь: §SC-D-RESERVE, §SC-D-LEX-MIN.

**Decision.** `тип` делается **ключевым словом `KW_TYPE`** (новый `TokenType`), а
НЕ обычным `IDENT`: убирается из `reservedWords` (счётчик-комментарий 12→11),
добавляется `"тип": KW_TYPE` в `keywords` (счётчик keyword +1). `KW_TYPE` НЕ
добавляется в `startsExpression`/`parsePrimary`. Парсер `parseSourceDecl` матчит
атрибут по сырой лексеме (`attrTok.Lexeme == "тип"`), как уже делает для
`файл`=`KW_FILE`. Слово `поля` ОБЯЗАНО остаться `IDENT` (не keyword): v1-программа
вправе использовать `поля` как имя переменной; keyword-изация сломала бы её
(нарушение инварианта обратной совместимости). Асимметрия принципиальна: `тип` уже
зарезервирован (ни одна валидная v1-программа его не использует), `поля` —
свободный идентификатор.

**Rationale.** После A1 `тип(5)` = `KW_TYPE` `(` `5` `)`; `KW_TYPE` не начинает
выражение → парс-ошибка → `тип(x)` ПО-ПРЕЖНЕМУ недостижим, `builtinTip` остаётся
dormant, достижимость 34 builtin'ов сохраняется. Меняется только КАТЕГОРИЯ
диагностики (lex→parse), не факт блокировки — хартия §3/§9 запрещает активацию
`тип(x)` в v2.

**Alternatives.**
- *Разрезервировать `тип` в голый `IDENT`* — ОТКЛОНЁН: `тип(5)` распарсится как
  вызов зарегистрированного builtin `тип` → **СЛУЧАЙНО активирует интроспекцию
  `тип(x)`**, явно запрещённую хартией §3/§9.
- *Context-sensitive лексинг* (`тип` — keyword только перед `:`) — ОТКЛОНЁН:
  непропорционально сложно, нарушает простоту ручного лексера (конституция I/II),
  не нужно при keyword-подходе.
- *Оставить `тип` зарезервированным* — ОТКЛОНЁН: атрибут `тип:` тогда не лексится
  (токена нет) — фича невозможна.

## D-2. Вложенный блок `поля:`: `openAttrBlock` + прецедент `parseStepDecl`

**Контекст.** `parseSourceDecl` (`parse_decl.go:41`) сегодня допускает только
однострочный атрибут `файл:` и делает `break` на первом плохом атрибуте. Блок
`поля:` — многострочный (`поля:` `NEWLINE` `INDENT` { `имя` `:` `тип` `NEWLINE` }+
`DEDENT`), требует сбора нескольких `FieldDef` и восстановления внутри блока.
Якорь: §SC-D-PARSE-3, §SC-2.

**Decision.** Открытие блока — существующий `openAttrBlock()` (`parse_decl.go`, уже
эмитит и проверяет `INDENT`). Внутренний цикл `for !p.check(DEDENT) && !p.check(EOF)`
с собственным `seen map` на имена полей (дубль → `msgDuplicateAttr`/доменная),
**восстановление через `continue`** (стиль `parseStepDecl`, чтобы собрать несколько
`FieldDef`, а не падать на первой строке). Пустой `поля:` (INDENT сразу DEDENT) →
`msgEmptyBlock`. Каждая строка → `FieldDef{Name, TypeName, Pos}`. Внешний цикл
источника сохраняет `break` на плохом атрибуте (источник — короткий блок);
многострочное восстановление нужно ТОЛЬКО во внутреннем `поля:`-цикле. Цикл
атрибутов переводится на `switch attrTok.Lexeme` с валидатором
`sourceAttrName(lexeme) ∈ {файл, тип, поля}` (зеркало `metricAttrName`,
`parse_decl.go:95`); дубликат атрибута → `msgDuplicateAttr` через `seen map`.

**Rationale.** `openAttrBlock`/INDENT-DEDENT/`continue`-восстановление —
существующие проверенные механизмы парсера (метрика, шаг процесса). A1
переиспользует их аддитивно: ноль нового синтаксического каркаса, INDENT кратен 4
(как везде). Парсер принимает любой `IDENT` для значения `тип:`/типа поля —
доменная валидация множеств переносится в Analyze (см. D-5), чтобы дать чистую
семантическую диагностику, а не парсерное «ожидался json».

**Alternatives.**
- *Однострочный `поля:` (через запятую)* — ОТКЛОНЁН: ломает визуальный стиль
  блоков Ladix (метрика/процесс/шаг — все INDENT-блоки), не масштабируется.
- *Падать на первой плохой строке поля* — ОТКЛОНЁН: §SC-D-PARSE-3 требует собрать
  несколько `FieldDef`; `continue`-восстановление даёт полную картину ошибок схемы.

## D-3. Коэрсия записи: пересборка через `NewRecord`, а не мутация

**Контекст.** `value.Запись` (`record.go`) имеет приватные `keys []string` /
`fields map[string]Value`, публичные `Keys() []string`, `Get(name) Value`,
`NewRecord(keys, fields)` — **Set-метода НЕТ, `fields` неэкспортируем**
(верифицировано). Коэрсия по схеме обязана преобразовать значения, не нарушив
листовость пакета `value` (конституция VII). Якорь: §SC-D-RECORD, §SC-6.

**Decision.** `applySchema(decl, recs)` НЕ мутирует на месте, а **пересобирает**
запись: `keys := r.Keys()`; для каждого `k` копирует `r.Get(k)` в `newFields`
(сохраняя лишние поля как есть, A1-6); затем для каждого `FieldDef{name, T}`
коэрсит `r.Get(name)` в `T` и пишет в `newFields[name]`; возвращает
`NewRecord(keys, newFields)`. Пакет `value` НЕ трогается. **Присутствие поля
определяется членством `name` в `keys`** — это отличает «поле отсутствует»
(A1-5 → «отсутствует объявленное поле») от «поле есть, но значение `Пусто`/null»
(A1-10 → несовпадение типа «ожидался `<Тип>`, получено `Пусто`»). Edge null/пустая
ячейка фиксируется golden-кейсом.

**Rationale.** Immutable публичный API `Запись` (нет `Set`) — это контракт, а не
ограничение: пересборка через `NewRecord` сохраняет порядок ключей, не вводит
мутаторов в листовой `value`, не нарушает изоляцию. Членство в `keys` —
единственный надёжный различитель «absent vs present-but-null», иначе A1-5 и A1-10
схлопнулись бы в одну неточную диагностику.

**Alternatives.**
- *Добавить `Запись.Set(name, v)`* — ОТКЛОНЁН: вводит мутатор в листовой `value`,
  расширяет публичную поверхность ради внутренней нужды загрузчика; пересборка
  достигает того же без churn пакета.
- *Различать absent/null по `Get()==None`* — ОТКЛОНЁН: `Get` отсутствующего поля и
  поля со значением `Пусто` неразличимы по возврату; членство в `keys` —
  единственный корректный признак присутствия.

## D-4. CSV через `encoding/csv`; даты через `parseISODate`

**Контекст.** `loadCSV`/`loadNDJSON` — новые загрузчики поверх диспетчера
`loadSource` по `decl.Type` (`source_loader.go:24` — текущий JSON-путь).
Конституция I требует 0 новых зависимостей; конституция II — ручной парсер
ЯЗЫКА. Формат даты должен совпадать с builtin `дата(...)`. Якорь: §SC-D-CSV,
§SC-D-NDJSON, §SC-D-DATE.

**Decision.** `loadCSV` использует stdlib `encoding/csv` (аналог `encoding/json`
для JSON-источника): 1-я строка — заголовок, разделитель `,`, UTF-8; заголовок
обязан содержать все объявленные поля (иначе load-ошибка «в заголовке CSV «<путь>»
отсутствует поле '<поле>'»); лишние столбцы игнорируются (A1-6); каждая ячейка —
`Строка`, затем коэрсия. `loadNDJSON` читает построчно, пустые строки пропускаются
(A1-9), каждая непустая — независимый JSON-объект через переиспользование
JSON-декодера на один объект; не-объект → load-ошибка. Поле `Дата` строится
строгим `parseISODate(s)` (`builtins_date.go:61`, ровно 10 байт `ГГГГ-ММ-ДД`,
валидация календаря/високосного) — **тот же парсер, что у builtin `дата(...)`**,
единый канон формата. Новые загрузчики тоже пишут `i.recordCache[name]`; путь —
`os.Open(path)` от CWD (§12, не менять).

**Rationale.** `encoding/csv` — формат данных, не грамматика языка → конституция II
(ручной парсер) НЕ нарушена; это прямой аналог `encoding/json`, уже используемого
JSON-источником. 0 новых зависимостей (конституция I). Переиспользование
`parseISODate` гарантирует, что `Дата`-поле и `дата(...)` принимают/отвергают
ровно одни строки (`«2026-13-40»`/`«31.05.2026»`/`«…T10:00»` отвергаются), без
второй реализации формата.

**Alternatives.**
- *Ручной CSV-сплиттер* — ОТКЛОНЁН: переизобретает экранирование/кавычки, риск
  багов; конституция II запрещает ручной парсер только для ГРАММАТИКИ, не для
  форматов данных.
- *`time.Parse(layout)` для дат* — ОТКЛОНЁН: толерантен к лишним символам/времени,
  разойдётся с строгим каноном `дата(...)`; `parseISODate` уже строг и единственен.
- *Внешняя CSV-библиотека* — ОТКЛОНЁН: нарушает 0-deps (конституция I).

## D-5. Матрица коэрсии: CSV(текст)→тип vs JSON/NDJSON(типизировано)→валидация

**Контекст.** CSV даёт все ячейки как `Строка`; JSON/NDJSON дают уже
типизированные значения (`Целое`/`Дробное`/`Булево`/`Строка`/`Пусто`). Коэрсия в
объявленный тип `T` различается по источнику. Единственный разрешённый кросс-тип
промоушен — `Целое→Дробное` (A1-10), как в числовых помощниках `arith.go`
(`toFloat`: `Целое.V`→`float64`). Якорь: §SC-D-COERCE, §SC-4-sem.

**Decision.** Матрица `applySchema` по `T` и форме источника:
**CSV (всё `Строка`)** — `Строка`: как есть; `Целое`: `strconv` без `.`/`e`/`E`
(§SC-D-COERCE-INT — десятичная точка → «не является целым», инвариант формы числа
§9.3 SPEC); `Дробное`: `strconv` float, принимает и `1200000`, и `1200000.5`;
`Логическое`: `истина`/`ложь`→`Булево`, иначе ошибка; `Дата`: `parseISODate`.
**JSON/NDJSON (типизировано)** — `Строка`: требуется `Строка`; `Целое`: `Целое` ок,
`Дробное`→ошибка (демоушена нет); `Дробное`: `Дробное` ок, **`Целое`→промоушен в
`Дробное`** (единственный кросс-тип, A1-10); `Логическое`: `Булево` ок; `Дата`:
`Строка`→`parseISODate`, иначе несовпадение. Прочее несовпадение → `runtimeErr`
«ожидался `<Тип>`, получено `<тип>`» («ожидался» печатает АННОТАЦИЮ `поля:` —
`Логическое`, не `Булево`; «получено» — `TypeName()` значения). Валидация множеств
(`тип:` ∈ {json,csv,ndjson}; `поля:` обязателен для csv/ndjson; тип поля ∈ 5 имён)
— статическая, в Analyze (§SC-4-sem), без чтения файла.

**Rationale.** Разделение CSV/типизировано отражает физику форматов: CSV не несёт
типов (всё текст → parse), JSON/NDJSON несут (→ validate). Единственный промоушен
`Целое→Дробное` копирует уже существующую числовую семантику `arith.go` — не новое
правило, а перенос инварианта. Доменные проверки множеств в Analyze (а не в
парсере/загрузчике) дают точную семантическую диагностику с позицией БЕЗ чтения
файла, как существующие проверки 004.

**Alternatives.**
- *Молчаливый CSV-`Целое` с точкой → `Дробное`* — ОТКЛОНЁН: ломает инвариант формы
  числа §9.3 SPEC; CSV-`Целое` обязано быть ровно `Целое` (§SC-D-COERCE-INT).
- *Двусторонний промоушен `Дробное↔Целое`* — ОТКЛОНЁН: демоушен `Дробное→Целое`
  теряет точность; A1-10 разрешает ровно один — `Целое→Дробное`.
- *Валидация множеств в парсере* — ОТКЛОНЁН: дала бы синтаксическую «ожидался
  json» вместо чистой доменной «неизвестный тип источника … (допустимо: …)»;
  Analyze точнее.

## D-6. Детерминизм и обратная совместимость: A1 не трогает `Clock`, `Type=="" → json`

**Контекст.** Несущее свойство A1 (инвариант 3 хартии §5) — чистый фронтенд +
загрузчик; все программы v1 остаются валидными. Источник без `тип:`/`поля:` обязан
вести себя побайтно как v1 JSON schemaless. Якорь: §SC-7, §SC-8, §SC-11, §SC-0.

**Decision.** A1 НЕ трогает `Clock`: `parseISODate` — чистая функция формата, не
зависит от «сегодня» (детерминизм окон — забота A2/011). Диспетчер `loadSource`
по `decl.Type.Name`: нулевое значение (`Type.Name == ""`, presence по
`TypePos.Line != 0`) → текущий JSON-путь (lines 42–78) БЕЗ изменений (A1-2);
`applySchema` вызывается только при `len(decl.Fields) > 0` — источник без схемы
проходит мимо коэрсии. Контракт `Store` (15 методов), `ProcessRuntime` (7 методов),
экспорт `eval`, фронтенд `где`/`агрегат`/`период`/`по_дате`, условие триггера — НЕ
трогаются. Метрика над типизированным/CSV-источником даёт тот же скаляр и течёт в
`run`/`serve`/триггер без изменений границ. Все `examples/*.ladix` и golden v1
(`метрики.ladix`/`выручка.ladix`) — зелёные без изменения вывода.

**Rationale.** `Type==""`-ветка диспетчера сохраняет старый код-путь как есть →
нулевой регресс v1 (замок на регресс диспетчера, §SC-10 #3). Несвязанность с
`Clock` держит A1 детерминированным в любой день и оставляет временную семантику
окон чистой границей A2. Изоляция фронтенда (лексер/парсер/AST/семантика не зависят
от `engine`/`Store`; `ast` листовой) — соблюдена аддитивностью узлов/атрибутов.

**Alternatives.**
- *Прогонять `applySchema` всегда* — ОТКЛОНЁН: схема опциональна для json (A1-3);
  безусловная коэрсия изменила бы поведение schemaless-источника → регресс v1.
- *Ввести зависимость дата-окна от `Clock` в A1* — ОТКЛОНЁН: окна — A2 (011); A1
  только распознаёт `Дата` как формат, не трогая «сегодня»/планировщик.
