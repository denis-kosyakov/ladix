## D-R1. Хранилище состояния — нарезанный контракт из 8 методов, две реализации (Q-нет / D-3 / §EN-2)

- **Decision**: ввести `internal/store` с интерфейсом `Store` из **ровно 8 методов** (D-3) и **двумя**
  реализациями за одним контрактом:
  - **`MemoryStore`** (`memory.go`, `func NewMemoryStore() *MemoryStore`) — эфемерное хранилище в
    памяти (`run` без `--db`, `metric`, тесты): карты `map[string]*ProcessInstance`/`map[string]*Task`
    + счётчики id под одним `sync.Mutex`, **без сериализации** (`value.Value` лежат как есть), **без
    алиасинга указателей** (`Save`/`Load` копируют инстанс, карту `Variables` и задачу — значения
    разделяются, ссылочность Список/Запись сохраняется).
  - **`SQLiteStore`** (`sqlite.go`, `func NewSQLiteStore(path string) (*SQLiteStore, error)` +
    `func (s *SQLiteStore) Close() error`) — персистентное файл-хранилище на `modernc.org/sqlite`
    (чистый Go, **без CGO**): конструктор **явно** исполняет PRAGMA (WAL, busy_timeout=5000,
    foreign_keys=ON — EM-7) + DDL (`instances`/`tasks`/`counters` с сидом `INSERT OR IGNORE`,
    `CREATE TABLE IF NOT EXISTS`), первая ошибка открытия/инициализации возвращается наружу.
  - 8 методов (дословно §EN-2): `SaveInstance` (upsert) / `LoadInstance` (→ `ErrInstanceNotFound`);
    `SaveTask` / `LoadTask` (→ `ErrTaskNotFound`); `ListPendingTasks(assignee)` (`""`=все, порядок
    **по возрастанию id**, D-15); `MarkTaskCompleted(id, completedAt)` (атомарно открыта→завершена,
    повтор → `ErrTaskAlreadyCompleted`, D-12); `NextInstanceID` / `NextTaskID` (mint, D-10).
  - сентинелы (английские, наружу не печатаются — транслируются в §EN-8): `ErrInstanceNotFound`,
    `ErrTaskNotFound`, `ErrTaskAlreadyCompleted`.
- **Rationale**: контракт «нарезан» намеренно — только то, что нужно движку 006 (§EN-2). Две
  реализации за интерфейсом дают тестируемость (`MemoryStore` без файла/IO для lifecycle-юнитов) и
  персист (`SQLiteStore` для человека-в-цикле, который ждёт дольше, чем живёт процесс ОС). Явный
  `Exec` DDL/PRAGMA в конструкторе нужен потому, что `database/sql` ленив — без него ошибка открытия
  не всплыла бы (и не стала бы источником CLI-текста `не удалось открыть хранилище`). `Close()` —
  метод конкретного типа, НЕ интерфейса (CLI делает `defer Close()` после успешного открытия).
- **Alternatives considered**:
  - **CGO-sqlite** (`mattn/go-sqlite3`) — **отвергнут**: конституция I прямо запрещает CGO и называет
    `modernc.org/sqlite` единственной разрешённой зависимостью; CGO сломал бы кросс-компиляцию одной
    командой и потребовал C-toolchain.
  - **Полный контракт с листингами инстансов и триггерными методами** — **отвергнут** (D-3/D-4):
    листинги инстансов в 006 не нужны (рестарт-скан — носитель демон 007); 6 триггерных методов
    (`LoadTriggerState`/`EnqueueEvent`/…) и `ErrTriggerStateNotFound` 007 добавит **аддитивно**, не
    меняя 8 существующих методов и DDL (путь отступления §EN-10).
  - **Транзакционный комбо-метод «завершить + продвинуть»** — **отвергнут** (§EN-2): корректность
    сбойного окна обеспечивает идемпотентный гард-догон D-4 (см. D-R6), отдельный метод избыточен.
- **Статус**: РЕШЁН (§EN-2, D-3/D-4). FR-001…007.

## D-R2. Кодек значений — type-tagged JSON (D-5 / D-6 / D-21 / §EN-2)

- **Decision**: внутри `SQLiteStore` значения переменных процесса кодируются **type-tagged JSON**
  (`codec.go`) — каждое значение несёт метку типа `{"т":"<Тип>","зн":<…>}`:
  - Целое/Строка/Булево/Пусто/Период/Дата — скаляр в `зн`; Дробное — число, **но спецзначения
    `NaN`/`+Inf`/`-Inf` — строками** (D-5; round-trip честный);
  - Длительность — `{"значение":N,"единица":"мин"}`; Список — массив рекурсивно;
  - **Запись — массивом пар** `[["ключ", <значение>], …]` с сохранением порядка `value.Запись.Keys()`
    (D-6; плоский JSON-объект EM-4 отменён);
  - **верхний уровень карты переменных** — JSON-объект с ключами **по возрастанию** (D-21; Go-map
    порядок теряет, кодек детерминизирует);
  - временные поля (`created_at`/`updated_at`/`deadline`/`completed_at`) — `time.RFC3339`
    **секундной** точности (НЕ Nano: секунд достаточно, строки детерминированы).
  - Round-trip MUST быть честным для всех **10 типов** значений (FR-006).
- **Rationale**: метка типа нужна, чтобы при чтении восстановить точный Ladix-тип (JSON сам по себе не
  различает Целое/Дробное/Дату). Строки для NaN/Inf — потому что JSON не имеет их числового
  представления (round-trip иначе бы врал). Массив пар для Записи — потому что порядок ключей значим
  (`Keys()`), а JSON-объект порядок не гарантирует. Ключи верхнего уровня по возрастанию — детерминизм
  golden и `состояние_процесса` (D-21). RFC3339 секунд — простота и детерминизм.
- **Alternatives considered**: плоский JSON-объект для Записи (EM-4) — **отвергнут** (D-6): теряет
  порядок ключей; `RFC3339Nano` — **отвергнут**: лишняя точность, недетерминированные хвосты;
  числовой `NaN`/`Inf` — **отвергнут** (D-5): невыразим в JSON. Кодек — внутреннее дело `SQLiteStore`;
  `MemoryStore` JSON не трогает, движок про JSON/SQL не знает (путь замены бэкенда открыт, EM-4).
- **Статус**: РЕШЁН (§EN-2, D-5/D-6/D-21). FR-006.

## D-R3. Граница eval↔engine — интерфейс `ProcessRuntime` в eval + сеттер-инъекция (D-1 / §EN-4)

- **Decision**: цикл `eval↔engine` разрывается **интерфейсом `ProcessRuntime`, объявленным в
  `internal/eval`** и инжектируемым сеттером; **`engine` его реализует**. `eval` **НЕ** импортирует ни
  `store`, ни `engine`; `engine → eval, store, ast, value, errors`.
  - `ProcessRuntime` (8 методов): `StartProcess`, `AssignProcessVar` (хук персиста `присвоить`),
    `CallExternal`/`Notify` (стабы действий), `InstanceStatus`/`InstanceVariables`/`UserTasks`
    (process-builtins).
  - экспорт `eval` (новые методы): `SetProcessRuntime(rt ProcessRuntime)` (инъекция до Run; результата
    Analyze не меняет); `Process(name)` (реестр процессов `i.processes`); `GlobalEnv()`; `EvalExpr`
    (вычисление атрибутов шага движком, D-9); `ExecStepBody` (исполнение тела шага в `stepEnv`,
    `body []ast.Statement` — НЕ `*ast.Block`); `Locals()` на `Environment` (снапшот только для
    тестов/сверки).
  - кадр шага `global → processEnv → stepEnv` (= SPEC §6.4): `processEnv` строится при **каждом**
    входе в `advance` из персистированных `Variables` (один на весь прогон); `stepEnv` — свой на шаг.
- **Rationale**: прямой импорт `eval → engine` (или наоборот) создал бы цикл, запрещённый
  конституцией VII. Интерфейс **в eval** (а не в engine) — потому что зовущая сторона (рантайм
  активированных конструкций) живёт в `eval`, а реализация — в `engine`; сеттер-инъекция (а не
  конструктор) нужна, чтобы интерпретатор собирался до движка, а движок — над интерпретатором
  (`NewEngine(st, interp, …)`). При `nil`-runtime активированные конструкции дают защитную
  ОшибкуВыполнения `внутренняя ошибка: движок процессов не подключён` (§EN-8.A) — но в CLI 006 ветка
  недостижима: `run`/`complete`/`metric` собирают единый стек (§EN-6).
- **Alternatives considered**:
  - прямой импорт `eval → engine` — **отвергнут** (D-1): цикл (engine уже зависит от eval), нарушение
    конституции VII;
  - интерфейс в `engine`, реализуемый `eval` — **отвергнут**: перевернул бы направление зависимости
    (eval стал бы зависеть от engine);
  - конструкторная инъекция движка в интерпретатор — **отвергнут**: порядок сборки (`metric` и
    `run`/`complete` строят interp до store/engine) делает сеттер естественнее.
- **Статус**: РЕШЁН (§EN-4, D-1). FR-019…023.

## D-R4. Часы движка — отдельный `engine.Clock` (D-2 / §EN-3)

- **Decision**: время движка идёт от **собственных** подменяемых часов `engine.Clock`
  (`type Clock interface { Now() time.Time }`, дефолт `SystemClock{}` — единственное легальное
  `time.Now()` движка; инъекция `WithClock`). Используется для `CreatedAt`/`UpdatedAt`/`CompletedAt`,
  абсолютизации дедлайна, признака `просрочена`. **Дневные часы интерпретатора** (`eval.Clock`,
  `value.Дата` для метрик 004, golden 2026-05-31) **не трогаются**. Инвариант D-2 переформулируется:
  «прямой `time.Now()` запрещён всюду, кроме реализаций Clock-интерфейсов — **два** легальных места:
  eval (дневной) и engine (lifecycle)».
- **Rationale**: метрики 004 живут в «дне» (дата без времени, golden 2026-05-31); lifecycle движка
  живёт в `time.Time` с секундной точностью (метки, дедлайны). Слить часы — значило бы либо сдвинуть
  golden 004 (нарушив SC-007/FR-043), либо потерять точность lifecycle. Отдельный `engine.Clock`
  изолирует и даёт `WithClock(фикс. 2026-05-31 00:00:00)` для байт-точного golden движка (сценарий А),
  не задевая дневные часы. `SystemClock{}` экспортируется — `tasks` берёт `now` из него (D-22).
- **Alternatives considered**: единый общий Clock для eval и engine — **отвергнут** (D-2): риск сдвига
  golden 004 и потери секундной точности lifecycle; глобальный `time.Now()` — **отвергнут**:
  конституция V (без глобального состояния) и недетерминизм golden.
- **Статус**: РЕШЁН (§EN-3, D-2). FR-017, SC-009.

## D-R5. Mint id — персистентный счётчик (D-10 / §EN-2)

- **Decision**: id выдаются **персистентным монотонным счётчиком** в формате `p-NNNNNN`/`t-NNNNNN`
  (нуль-паддинг 6): SQLite — таблица `counters(name TEXT PRIMARY KEY, value INTEGER NOT NULL)`,
  инкремент и выдача в **одной транзакции** (сид `INSERT OR IGNORE … VALUES ('instance',0),('task',0)`
  гарантирует строку); Memory — счётчик под mutex. Свежее хранилище всегда начинает с
  `p-000001`/`t-000001` (детерминизм golden); в SQLite счётчик **переживает перезапуски** — повторный
  `run --db` продолжает нумерацию (`p-000002`/`t-000003`, норма v1). `SaveInstance` остаётся upsert —
  коллизии исключены конструктивно.
- **Rationale**: детерминированные id критичны для golden (CLI-тесты не маскируют id — только
  `<время>`); атомарность инкремента+выдачи гарантирует уникальность без случайных суффиксов.
  Персистентность счётчика — следствие Q2 (повторный `run --db` создаёт новые инстансы): без неё
  второй прогон выдал бы те же id и столкнулся бы со старыми инстансами в БД.
- **Alternatives considered**: **случайный суффикс EM-8** — **отвергнут** (D-10): недетерминирован
  (golden пришлось бы маскировать id), уникальность вероятностная, а не конструктивная; UUID —
  **отвергнут**: длинные id ломают читаемый формат `p-NNNNNN` и golden.
- **Статус**: РЕШЁН (§EN-2, D-10). FR-002.

## D-R6. Атомарное завершение задачи + гард-догон — идемпотентность вместо комбо-метода (D-4 / D-12 / §EN-3)

- **Decision**: завершение задачи — атомарный переход `открыта`→`завершена` методом
  `MarkTaskCompleted(id, completedAt)` (SQLite: условный `UPDATE … WHERE status='открыта'` + проверка
  rows affected; Memory: под mutex), уже завершена → `ErrTaskAlreadyCompleted` (D-12). Сбойное окно
  «`MarkTaskCompleted` прошёл, advance не успел» (kill процесса ОС между завершением и продвижением)
  закрывает **гард-догон в `complete`** (D-4): повторный `complete` уже-завершённой задачи проверяет
  инстанс — если `ожидает` И `CurrentStep == task.StepName` (хвост сбоя), → **идемпотентное
  до-продвижение без повторного `MarkTaskCompleted`**, строка 8 §EN-7 (вместо 7), **exit 0**; иначе →
  `ladix: задача '<id>' уже завершена`, exit 2. Проигравший остаточную гонку двойного `complete`
  (D-12) маршрутизируется в ту же ветку догона.
- **Rationale**: транзакционный комбо-метод «завершить + продвинуть» потребовал бы держать
  Ladix-исполнение (тело следующего шага) внутри транзакции БД — это смешало бы слои (Store не знает о
  движке/eval) и заблокировало бы БД на время исполнения. **Идемпотентный догон** дешевле и
  корректнее: завершение задачи и продвижение разделены, а повторный `complete` безопасно добивает
  застрявшее окно. Догон детектируется по статусу задачи `завершена` **до** любых мутаций (§EN-3,
  порядок гардов). Инстанс, упавший в `выполняется` (kill посреди шага), остаётся залипшим до 007
  (рестарт-скан — носитель демон, D-4) — граница §EN-10.
- **Alternatives considered**: транзакционный комбо-метод — **отвергнут** (§EN-2, см. выше);
  «повторный complete всегда exit 2» (ARCH-канон) — **отвергнут** (D-4): не закрывал бы сбойное окно,
  инстанс залипал бы навсегда без 007.
- **Статус**: РЕШЁН (§EN-3, D-4/D-12). FR-003, FR-015/016.

## D-R7. Фаза атрибутов до тела, тип-гарды атрибутов движком, абсолютизация срока (D-9 / D-18 / D-19 / §EN-3)

- **Decision**:
  - **Фаза атрибутов — до тела** (D-9, правка EM-9 под SPEC §11.3): порядок шага = (1)
    `исполнитель`/`срок` вычисляются в кадре шага (`EvalExpr`), (2) тело (`ExecStepBody`), (3) развилка
    задача/продвижение. Ошибка вычисления атрибута = runtime-ошибка шага → инстанс `провален` (как
    ошибка тела, D-14).
  - **Тип-гарды атрибутов — движком** на фазе атрибутов (D-18; семантика 005 их **не** обходит):
    `исполнитель` обязан быть `Строка`, `срок` — `Длительность`; нарушение → ОшибкаТипа байт-точным
    текстом §EN-8.A (`шаг '<имя>': исполнитель должен быть Строка, получено <тип>` /
    `… срок должен быть Длительность …`) с позицией выражения атрибута, инстанс `провален`.
  - **Абсолютизация срока** (D-19): `Deadline = Task.CreatedAt + срок`; единицы → Go-время:
    `сек`/`мин`/`час`/`дн`/`нед` — фиксированные множители `time.Duration` (дн=24h, нед=168h);
    `мес` — календарный `AddDate(0, n, 0)`. Это **внутренняя Go-механика дедлайна**, НЕ
    Ladix-арифметика (clamp-семантика SPEC §4 на неё не распространяется). Шаг без `срок` →
    задача без дедлайна (`Deadline == nil`).
- **Rationale**: атрибуты до тела — потому что развилка (создавать ли задачу) зависит от `исполнитель`,
  а дедлайн — от `срок`; их значения нужны на фазе 3. Тип-гарды движком (а не семпроходом) — потому что
  семпроход 005 атрибуты выражениями не обходит (паритет с `checkMetricDecl`, §PM-1/D-11), значит
  движок — единственное место, где `исполнитель: 42` ловится. Абсолютизация при создании задачи (а не
  лениво) — дедлайн фиксируется моментом входа в шаг; множители — Go-механика, не подпадающая под
  clamp SPEC §4 (та — для Ladix-арифметики дат, которая в 006 не активируется).
- **Alternatives considered**: тело до атрибутов (старый EM-9) — **отвергнут** (D-9): развилка
  потребовала бы атрибуты раньше; тип-гарды в семпроходе — **отвергнут** (D-18): семпроход атрибуты не
  обходит; ленивый дедлайн (вычислять при чтении) — **отвергнут** (D-19): недетерминирован относительно
  момента создания задачи.
- **Статус**: РЕШЁН (§EN-3, D-9/D-18/D-19). FR-010/011/012, FR-013/014.

## D-R8. Активация deferred-веток 005 — литерал длительности и минимум сравнений (D-7 / D-16 / D-17 / §EN-5)

- **Decision**: граница deferred сдвигается **ровно** на карту §EN-5 (точечную и исчерпывающую):
  - **`DurationLit`** активируется полностью (D-7): рантайм даёт `value.Длительность{Amount, Unit}`;
    **семантический deferred снимается** (`analyze.go` case удаляется) — литерал валиден в любой
    позиции. AST несёт нормализованную лексему-строку (`Amount string`, D-16): активация —
    `strconv.ParseInt(Amount, 10, 64)`; вне диапазона int64 → ОшибкаВыполнения `литерал длительности
    вне диапазона типа Целое` с позицией литерала (D-16).
  - **Сравнения Длительностей** — **минимум** D-17: `==`/`!=` — по паре единица+значение
    (`1час != 60мин`, **нормализации нет**) — новый case в `value.Equal`; `<`/`<=`/`>`/`>=` — только в
    **одной** единице (новый case в `value.Compare`); разные единицы → `ok==false` → существующий текст
    ОшибкиТипа `'<оп>' нельзя применить к Длительность и Длительность`.
  - **3 процессные встроенные** активируются (D-15) через `ProcessRuntime`: `статус_процесса(id)` →
    статус-строка; `состояние_процесса(id)` → Запись переменных (ключи по возрастанию, D-21);
    `задачи_пользователя(имя)` → открытые задачи (`""`=все, по возрастанию id, поля «Task → Запись»
    EM-13 вкл. `просрочена`). Аргумент не-Строка → ОшибкаТипа `<имя>: ожидается Строка, получено
    <тип>`; неизвестный id → `процесс '<id>' не найден`.
  - реестр встроенных: **25 + 10 → 28 + 7** (инвариант суммы 35 сохраняется); 7 дата-имён
    (`вчера`/`завтра`/`длительность`/`в_секундах`/`в_минутах`/`в_часах`/`в_днях`) остаются deferred с
    прежним текстом. Мёртвая после активации рантайм-заглушка `deferredConstruct` (без вызовов) —
    **удаляется** вместе с активацией (staticcheck U1000).
- **Rationale**: активируется **минимум, без которого значение врёт** — литерал должен давать
  значение-носитель (иначе `срок: 3дн` пуст), а сравнения — корректный результат (без case Длительности
  `2дн == 2дн` дало бы ложь). **Арифметика** Длительностей/дат **НЕ** активируется (D-17): SPEC §4
  описывает целевую семантику v1+, но в 006 она остаётся ОшибкойТипа — это «обвязка», не ядро движка.
  Сравнения без нормализации (`1час != 60мин`) — потому что нормализация требует множителей единиц,
  что уже половина арифметики; минимализм держит границу §EN-10 чёткой.
- **Alternatives considered**: полная активация арифметики Длительности — **отвергнут** (D-17): за
  пределами «обвязки движка», бэклог 007+/v2; нормализация в сравнениях — **отвергнут** (D-17): тянет
  множители (= арифметика); активация 7 дата-встроенных — **отвергнут** (D-17): зависят от
  арифметики/конструктора `длительность(…)`, остаются deferred.
- **Статус**: РЕШЁН (§EN-5, D-7/D-15/D-16/D-17). FR-024…028.

## D-R9. CLI-разрез — run --db, complete <file> <task-id>, tasks (Q1 / Q2 / Q3 / §EN-6)

- **Decision**: новый CLI-разрез (Q1=006=движок+человек-в-цикле; триггеры/демон → 007):
  - **`ladix run <файл> [--db путь] [--max-depth N]`** (Q2): без `--db` — `MemoryStore` (эфемерно,
    как сейчас); с `--db` — `SQLiteStore` (мост в файл). После последнего top-level — сводка открытых
    задач (строки 5–6 §EN-7) **только при N≥1**; висящие задачи — не ошибка, exit 0. **Повторный
    `run --db` того же файла создаёт НОВЫЕ инстансы** (счётчик персистентен, старые остаются в БД) —
    норма v1.
  - **`ladix complete <file.ladix> <task-id> [--db путь] [--max-depth N]`** (Q3): ровно два
    позиционных аргумента (меньше/больше → usage, exit 2); **истина — в исходнике**, БД хранит только
    состояние. Файл MUST чисто пройти компиляцию (лексер→парсер→семантика; иначе обычный барьер канон
    §13, exit 1), но **top-level НЕ исполняется** (иначе каждый `complete` плодил бы новые инстансы);
    БД — SQLite, дефолт `ladix.db`. Дрейф исходника против БД → CLI-ошибка §EN-8.B, exit 2, инстанс не
    тронут. Успех (вкл. догон) → stdout строки 7–10, exit 0; runtime-ошибка продвижения → `провален`,
    канон §13, exit 1.
  - **`ladix tasks [исполнитель] [--db путь]`**: файл **НЕ** принимает (всё из БД; ни движок, ни
    интерпретатор не строятся); по строке `FormatTaskLine` на каждую открытую (строка 6 §EN-7,
    **единый** формат с run-сводкой, D-22); пусто → `открытых задач нет`. Exit 0.
  - usage — 4 команды; коды **0/1/2** (FR-033); `metric` — Store всегда `MemoryStore` (флага `--db`
    нет): формула может дёрнуть `запустить процесс`/process-builtin, поэтому собирает исполняемый стек.
- **Rationale**: Q1 разрезает 006/007 по «движок vs триггеры». Q2 (`run --db` вместо `serve`) даёт
  мост в персист без демона — человек-в-цикле работает командами, не сервисом. Q3 (`complete` берёт
  файл + task-id, истина в исходнике) — потому что БД хранит только состояние, а определения процессов
  живут в `.ladix`; дрейф (переименованный шаг) ловится гардами Q3 по именам. Top-level не исполняется
  в `complete` — иначе повторное исполнение плодило бы инстансы. `tasks` файла не требует — всё в БД.
  Единый `FormatTaskLine` (D-22) — один источник формата строки задачи для `run`-сводки и `tasks`.
- **Alternatives considered**: `serve`/`emit`/`--interval` демон — **отвергнут** (Q1/§EN-0): EM-17 →
  007; `complete <task-id>` без файла (определения в БД) — **отвергнут** (Q3): БД хранит только
  состояние, истина в исходнике; `tasks` с файлом — **отвергнут** (Q3): листинг — чисто из БД,
  движок/файл не нужны; исполнять top-level в `complete` — **отвергнут** (§EN-6): плодило бы инстансы.
- **Статус**: РЕШЁН (§EN-6, Q1/Q2/Q3). FR-029…034, FR-029 (сводка), D-22.

## D-R10. Маршрутизация сбоев Store и провал инстанса (D-14 / D-20 / §EN-3 / §EN-8)

- **Decision**:
  - **Сбои Store маршрутизируются по инициатору** (§EN-3): пути, инициированные Ladix-узлом
    (`запустить процесс`, `присвоить`, process-builtins — включая весь `advance` внутри `Start`) →
    ОшибкаВыполнения `сбой хранилища: <причина>` с позицией узла-инициатора (§EN-8.A, exit 1);
    CLI-пути `complete`/`tasks` (загрузки, завершение, листинг, декод битой БД, персисты продвижения)
    → `ladix: сбой хранилища: <причина>`, exit 2 (§EN-8.B — Ladix-позиции нет).
  - **Провал инстанса** (D-14): необработанная runtime-ошибка тела/атрибута персистирует инстанс как
    `провален` и всплывает как обычная ошибка программы (канон §13, fail-fast, exit 1; `run` и
    `complete` одинаково). Дополнительной CLI/stdout-строки о провале **нет**.
  - **CLI-ошибки 006** (D-20): одна строка `ladix: <текст>` в stderr, exit 2 (тексты §EN-8.B).
  - категория **`ОшибкаПроцесса` НЕ вводится** (D-14): `вызвать` в v1 всегда успешен (стаб) — ей
    нечего нести; строка «Процесса» SPEC §13.1 остаётся зарезервированной прозой.
- **Rationale**: двойная маршрутизация — потому что у Ladix-инициированного сбоя есть позиция узла
  (канон §13 применим), а у CLI-операции (`tasks`, `LoadTask`) Ladix-позиции нет (exit 2, формат
  `ladix:`). Провал без новой категории — `вызвать` недостижимо проваливается (всегда успешен),
  значит `ОшибкаПроцесса` пуста; провал виден как статус в Store и через `статус_процесса`, диагностика
  — исходная ошибка тела/атрибута.
- **Alternatives considered**: единый формат сбоя Store — **отвергнут** (§EN-3): теряет позицию для
  Ladix-путей или навешивает фальшивую позицию на CLI-пути; категория `ОшибкаПроцесса` — **отвергнут**
  (D-14): нечем наполнить в v1.
- **Статус**: РЕШЁН (§EN-3/§EN-8, D-14/D-20). FR-014, FR-018, FR-037/038.

## D-R11. Байт-точные реестры stdout (§EN-7) и диагностик (§EN-8) — exact-match канон (D-13 / §EN-7 / §EN-8)

- **Decision**: все системные строки и диагностики 006 — **exact-match канон**, тесты сверяют
  байт-в-байт:
  - **stdout — 11 форматов §EN-7** (каждая `\n`): 1/1а стаб `уведомить` (аргументы через пробел / без
    аргументов — без двоеточия и хвостовых пробелов); 2 стаб `вызвать` (через `", "`); 3/4 создание
    задачи (со сроком / без); 5 заголовок сводки `открытых задач: <N>`; 6 строка задачи
    (`FormatTaskLine`, D-22: поля через **два** пробела, хвост `срок до <время>` только при дедлайне,
    `ПРОСРОЧЕНА` только при `Overdue`); 7 `задача <t-id> завершена`; 8 `задача <t-id> уже была
    завершена, инстанс до-продвинут` (догон); 9/10 итог `complete`; 11 `открытых задач нет`. Запуск —
    **тихий** (D-13: системной строки нет, `запущен …, id:` печатает ПРОГРАММА). Время дедлайна —
    `Deadline.Format("2006-01-02 15:04")` локальной зоны.
  - **§EN-8.A — 9 текстов** (канон §13, позиция, stderr, exit 1): `процесс '<id>' не найден`;
    `статус_процесса`/`состояние_процесса`/`задачи_пользователя`: `ожидается Строка, получено <тип>`;
    `шаг '<имя>': исполнитель должен быть Строка …` / `… срок должен быть Длительность …`; `литерал
    длительности вне диапазона типа Целое`; `сбой хранилища: <причина>`; `внутренняя ошибка: движок
    процессов не подключён`.
  - **§EN-8.B — 10 текстов** (одна строка `ladix: <текст>`, stderr, exit 2): `задача '<id>' не
    найдена` / `уже завершена`; `инстанс '<id>' не найден`; `инстанс '<p-id>' не ожидает (статус
    '<статус>')`; `задача … не соответствует текущему шагу …`; `процесс … не найден в определении`;
    `шаг … не найден в определении процесса …`; `не удалось открыть хранилище '<путь>': <причина>`;
    `сбой хранилища: <причина>`; `флаг --db требует значение`.
  - **Чего в stdout НЕТ** (осознанно, D-13/D-14): запуск процесса, терминал внутри `run`, строки о
    провале, заголовок у `tasks` при непустом списке.
- **Rationale**: байт-точность — конституция VIII (тексты дословно, переформулировать запрещено) и
  основа golden-тестов (сценарии А/Б, SC-005/006). Тихий запуск (D-13) — потому что демо печатает
  `запущен …, id:` сама (`печать`), движок не должен дублировать. Два пробела в строке задачи и
  условные хвосты — фиксированный формат `FormatTaskLine` (единый для `run`/`tasks`, D-22).
- **Alternatives considered**: системная строка о запуске — **отвергнут** (D-13): дублировала бы
  печать программы; единый формат сбоя без разделения A/B — см. D-R10.
- **Статус**: РЕШЁН (§EN-7/§EN-8, D-13/D-22). FR-035/036, FR-037/038/039, SC-005/006.
