## User Scenarios & Testing *(mandatory)*

Ladix — декларативно-императивный язык бизнес-автоматизации. До этой фичи язык лексирует (001),
строит AST (002), исполняет императивное ядро (003), считает метрики по источникам (004) и полностью
**парсит и семантически проверяет** процессы (005) — но не исполняет их: `запустить процесс` упирается
в рантайм-границу «не поддерживается в этой версии». Фича 006 включает **движок исполнения**: процесс
реально запускается, шаги исполняются в порядке исходника, на человеческом шаге (с `исполнитель:`)
создаётся **задача** и инстанс засыпает, человек завершает задачу командой `ladix complete`, инстанс
просыпается и идёт дальше — до терминала. Состояние переживает завершение процесса ОС: между запусками
оно живёт в SQLite-файле (`run --db` / `tasks` / `complete`).

Пользователи:

- **Автор процесса** — пишет `.ladix`-файл с `процесс`/`шаг`/действиями; теперь его программа
  исполняется: действия печатают эффекты, переменные процесса персистируются, процессные встроенные
  (`статус_процесса`/`состояние_процесса`/`задачи_пользователя`) и литералы длительности (`3дн`)
  становятся живыми значениями.
- **Оператор CLI** — запускает `ladix run [--db]`, смотрит открытые задачи `ladix tasks`, завершает
  их `ladix complete`; получает байт-точные системные строки в stdout и понятные ошибки с кодами
  возврата 0/1/2.
- **Исполнитель задачи (человек-в-цикле)** — видит свои открытые задачи (исполнитель, шаг, срок,
  просрочка) и завершением задачи продвигает бизнес-процесс.

### User Story 1 — Запустить процесс и довести его до точки ожидания человека (Priority: P1)

Оператор запускает `ladix run examples/онбординг.ladix` (без `--db` — эфемерное хранилище в памяти).
Top-level программа исполняется сверху вниз; `запустить процесс онбординг("Петров")` создаёт инстанс
и **синхронно** прогоняет шаги: автоматический шаг исполняет тело (`присвоить` + `уведомить`-стаб),
человеческий шаг (`исполнитель: "руководитель"`, `срок: 3дн`) создаёт задачу с абсолютизированным
дедлайном — инстанс засыпает в статусе `ожидает`. Сам запуск **тихий** (D-13): строку
`запущен онбординг, id: p-000001` печатает программа (`печать`), а не движок. После top-level CLI
печатает сводку висящих задач. Висящие задачи — не ошибка: exit 0.

**Why this priority**: Это сердце фичи — без запуска и продвижения инстанса не существует ни
человек-в-цикле, ни персистентности. Сценарий А (§EN-9) — флагман-демо и golden всей фичи: он
проверяет одновременно lifecycle, фазу атрибутов, стабы действий, создание задачи и сводку.

**Independent Test**: Прогнать `ladix run examples/онбординг.ladix` (файл как есть, 005-редакция)
с фиксированными часами движка → байт-точный stdout из 5 строк, exit 0; состояние хранилища на
выходе: инстанс `p-000001` `ожидает` на шаге `провести_встречу`, переменные
`{имя: "Петров", сотрудник: "Петров"}`, задача `t-000001` `открыта`.

**Acceptance Scenarios**:

1. **Given** `examples/онбординг.ladix` и фиксированные часы движка (2026-05-31 00:00:00), **When**
   `ladix run examples/онбординг.ladix`, **Then** exit 0 и stdout дословно (5 строк, §EN-9 сценарий А):

   ```
   [уведомление] ИТ: создать учётку для Петров
   [задача] t-000001 → руководитель, шаг 'провести_встречу', срок до 2026-06-03 00:00
   запущен онбординг, id: p-000001
   открытых задач: 1
   t-000001  p-000001  'провести_встречу'  руководитель  срок до 2026-06-03 00:00
   ```

2. **Given** тот же запуск, **When** исполнение завершилось, **Then** в хранилище: инстанс `p-000001`
   в статусе `ожидает`, текущий шаг `провести_встречу`, переменные `{имя: "Петров", сотрудник: "Петров"}`
   (пусть-локали шага в переменные процесса не попадают); задача `t-000001` `открыта`.
3. **Given** программа, где все шаги процесса автоматические (без `исполнитель`), **When** `ladix run`,
   **Then** инстанс синхронно доходит до статуса `выполнен`, терминал **тихий** (системной строки нет),
   сводка задач не печатается (`N == 0`), exit 0.
4. **Given** шаг с `исполнитель: 42` (не Строка), **When** `ladix run`, **Then** канон §13 в stderr с
   текстом `шаг '<имя>': исполнитель должен быть Строка, получено Целое`, exit 1, инстанс персистирован
   как `провален` (D-18/D-9/D-14); дополнительной CLI-строки о провале нет.
5. **Given** шаг с телом `присвоить x = 1/0`, **When** `ladix run`, **Then** `деление на ноль`
   (канон §13), exit 1, инстанс `провален` (D-14).

### User Story 2 — Человек-в-цикле: персистентная цепочка run --db → tasks → complete (Priority: P1)

Оператор запускает процесс с мостом в SQLite: `ladix run онбординг.ladix --db test.db`. Инстанс
засыпает в файле БД и переживает завершение процесса ОС. Отдельными командами оператор смотрит
открытые задачи (`ladix tasks --db test.db`, с фильтром по исполнителю и без), а исполнитель
завершает их: `ladix complete онбординг.ladix t-000001 --db test.db` — истина в исходнике, БД хранит
только состояние (Q3). Завершение будит инстанс: следующий человеческий шаг создаёт новую задачу,
последний — переводит инстанс в `выполнен`. Повторный `run --db` того же файла создаёт **новые**
инстансы (id-счётчик персистентен, D-10) — норма v1.

**Why this priority**: Человек-в-цикле — заявленная ценность фичи (Q1): процесс, который ждёт
человека дольше, чем живёт процесс ОС. Без SQLite-моста и `complete` фича 006 неотличима от
синхронного скрипта. Сценарий Б (§EN-9) — golden-цепочка этой ценности.

**Independent Test**: Прогнать на свежей БД цепочку из 6 команд сценария Б (§EN-9) → каждый шаг даёт
ожидаемый stdout (маскируется только `<время>` дедлайнов — id детерминированы) и exit 0; состояние
между командами живёт только в файле БД.

**Acceptance Scenarios**:

1. **Given** свежая БД `test.db`, **When** `ladix run онбординг.ladix --db test.db`, **Then** stdout
   как в сценарии А (5 строк), exit 0; состояние — в `test.db`.
2. **Given** БД после шага 1, **When** `ladix tasks --db test.db`, **Then** одна строка
   `t-000001  p-000001  'провести_встречу'  руководитель  срок до <DT>`, exit 0 (заголовка при
   непустом списке нет).
3. **Given** та же БД, **When** `ladix tasks Петров --db test.db` (у «Петров» открытых задач нет),
   **Then** `открытых задач нет`, exit 0.
4. **Given** та же БД, **When** `ladix complete онбординг.ladix t-000001 --db test.db`, **Then**
   exit 0 и три строки: `задача t-000001 завершена` ⏎
   `[задача] t-000002 → HR, шаг 'закрыть_адаптацию', срок до <DT>` ⏎
   `инстанс p-000001: ожидает, шаг 'закрыть_адаптацию'` (инстанс снова заснул на следующем
   человеческом шаге).
5. **Given** та же БД, **When** `ladix complete онбординг.ladix t-000002 --db test.db`, **Then**
   exit 0 и две строки: `задача t-000002 завершена` ⏎ `инстанс p-000001: выполнен` (терминал).
6. **Given** та же БД после шага 5, **When** повторный `ladix run онбординг.ladix --db test.db`,
   **Then** как шаг 1, но id `p-000002`/`t-000003` (Q2/D-10: счётчик персистентен, старые инстансы
   остаются в БД), exit 0.

### User Story 3 — Гарды завершения: некорректный complete не ломает состояние (Priority: P2)

Исполнитель ошибается: завершает несуществующую задачу, завершает задачу повторно, подсовывает
`complete` файл без нужного процесса или файл, где текущий шаг инстанса переименован (дрейф исходника
против БД), указывает неоткрываемый путь БД или файл с ошибкой компиляции. Каждый такой случай даёт
**одну строку** `ladix: <текст>` в stderr и exit 2 (D-20), а ошибка компиляции — обычный барьер
канона §13 и exit 1; **инстанс при отказе гарда не тронут**. Особый случай — гард-догон (D-4):
повторный `complete` уже-завершённой задачи при инстансе, всё ещё ожидающем на том же шаге (хвост
сбоя «задача закрыта, продвижение не успело»), идемпотентно до-продвигает инстанс и завершается
**успехом** (exit 0) с пометкой в выводе.

**Why this priority**: БД — разделяемое состояние, и `complete` — единственная команда, которая его
мутирует извне. Гарды D-8/Q3/D-4 — вся защита целостности v1; их тексты и exit-коды — часть
пользовательской поверхности и приёмки §EN-9. Без US1/US2 проверять нечего, поэтому P2.

**Independent Test**: На БД после шага 5 сценария Б прогнать шесть негативов §EN-9 → байт-точные
stderr-тексты и коды 2/1; отдельно (на уровне движка, с фабрикованным состоянием хранилища) — два
кейса гардов D-8, недостижимых через CLI-цепочку.

**Acceptance Scenarios**:

1. **Given** БД после сценария Б, **When** `complete онбординг.ladix t-999999 --db test.db`, **Then**
   stderr `ladix: задача 't-999999' не найдена`, exit 2.
2. **Given** та же БД (инстанс `выполнен` — догон неприменим), **When** повторный
   `complete онбординг.ladix t-000001 --db test.db`, **Then** stderr
   `ladix: задача 't-000001' уже завершена`, exit 2.
3. **Given** существующий чисто компилируемый файл без процесса `онбординг`
   (`examples/hello.ladix`), **When** `complete examples/hello.ladix t-000001 --db test.db`, **Then**
   stderr `ladix: процесс 'онбординг' не найден в определении`, exit 2 (дрейф Q3).
4. **Given** testdata-фикстура `онбординг-дрейф.ladix` (процесс есть, шаг `закрыть_адаптацию`
   переименован; текущий шаг инстанса == `закрыть_адаптацию`), **When**
   `complete онбординг-дрейф.ladix t-000001 --db test.db`, **Then** stderr
   `ladix: шаг 'закрыть_адаптацию' не найден в определении процесса 'онбординг'`, exit 2 —
   дрейф-гарды идут **до** гарда «уже завершена» (§EN-3).
5. **Given** неоткрываемый путь БД, **When** `complete онбординг.ladix t-000001 --db нет/такого/каталога.db`,
   **Then** stderr `ladix: не удалось открыть хранилище 'нет/такого/каталога.db': <причина>`, exit 2.
6. **Given** testdata-фикстура `сломанный.ladix` с парс-ошибкой, **When**
   `complete сломанный.ladix t-000001 --db test.db`, **Then** канон §13 в stderr (двухстрочный/
   накопленный), exit 1 — компиляция файла обязана пройти чисто до любой работы с БД.
7. **Given** фабрикованное состояние: открытая задача при инстансе в статусе `выполняется`, **When**
   движок завершает задачу, **Then** отказ гарда D-8 с CLI-текстом
   `ladix: инстанс '<p-id>' не ожидает (статус 'выполняется')`, инстанс не тронут (через CLI-цепочку
   кейс практически недостижим — один активный шаг = одна открытая задача; уровень движка, §EN-9).
8. **Given** фабрикованное состояние: открытая задача с шагом ≠ текущему шагу ожидающего инстанса,
   **When** движок завершает задачу, **Then** отказ гарда D-8 с текстом
   `ladix: задача '<t-id>' не соответствует текущему шагу инстанса '<p-id>'`, инстанс не тронут.
9. **Given** задача завершена, но инстанс остался `ожидает` на том же шаге (хвост сбоя), **When**
   повторный `complete` этой задачи, **Then** stdout
   `задача <t-id> уже была завершена, инстанс до-продвинут` (строка 8 §EN-7 вместо строки 7), инстанс
   до-продвинут, exit 0 (гард-догон D-4).

### User Story 4 — Длительности и процессные встроенные как живые значения (Priority: P2)

Автор процесса пользуется активированными конструкциями языка: литерал длительности (`2дн`) —
полноценное значение в любой позиции (печать `2дн`, сравнения `==`/`!=` и порядковые в одной
единице); процессные встроенные опрашивают состояние движка из программы: `статус_процесса(id)` →
статус-строка, `состояние_процесса(id)` → Запись переменных, `задачи_пользователя(имя)` →
список открытых задач (пустая строка = все). Граница deferred сдвигается ровно на карту §EN-5:
7 дата-встроенных (`вчера`, `завтра`, `длительность`, `в_секундах`, `в_минутах`, `в_часах`, `в_днях`)
и арифметика длительностей/дат остаются за бортом (D-17).

**Why this priority**: Это «обвязка» движка в самом языке — без неё процессы исполняются, но программа
не может наблюдать их состояние, а `срок: 3дн` не имеет значения-носителя. Зависит от US1 (движок
должен существовать), поэтому P2.

**Independent Test**: Прогнать точечные приёмки §EN-9 (таблица слоя): литерал, сравнения, диапазон,
встроенные на живом/неизвестном id, deferred-граница `вчера()`.

**Acceptance Scenarios**:

1. **Given** `пусть d = 2дн` ⏎ `печать(d)`, **When** `ladix run`, **Then** stdout `2дн`, exit 0
   (D-7/D-16; семантический deferred литерала снят — валиден в любой позиции).
2. **Given** `печать(2дн == 2дн)` / `печать(1час == 60мин)`, **When** `ladix run`, **Then** `истина` /
   `ложь` (D-17: единица+значение, без нормализации).
3. **Given** `печать(2дн < 5мин)` (разные единицы), **When** `ladix run`, **Then** канон §13 с
   существующим текстом `'<' нельзя применить к Длительность и Длительность`, exit 1; а
   `печать(2дн < 5дн)` → `истина` (D-17: порядок только в одной единице).
4. **Given** `пусть x = 9999999999999999999дн`, **When** `ladix run`, **Then**
   `литерал длительности вне диапазона типа Целое`, exit 1 (D-16).
5. **Given** `печать(статус_процесса(id))` после `пусть id = запустить процесс …` (инстанс заснул),
   **When** `ladix run`, **Then** `ожидает`; **Given** `статус_процесса("p-999999")`, **Then**
   `процесс 'p-999999' не найден`, exit 1 (D-15); **Given** `статус_процесса(1)`, **Then**
   `статус_процесса: ожидается Строка, получено Целое`, exit 1.
6. **Given** `печать(длина(задачи_пользователя("")))` после запуска онбординга, **When** `ladix run`,
   **Then** `1` (D-15: пустая строка = все открытые, порядок по возрастанию id).
7. **Given** `вчера()`, **When** `ladix run`, **Then** прежний текст
   `функция 'вчера' не поддерживается в этой версии` — deferred-граница 7 дата-имён не сдвинулась.

### Edge Cases

- **Гард-догон против «уже завершена»**: догон срабатывает **только** при паре «задача `завершена` И
  инстанс `ожидает` на том же шаге»; любое другое состояние повторного `complete` → exit 2. Проигравший
  остаточную гонку двух одновременных `complete` одной задачи попадает в ту же ветку догона (D-12;
  сама гонка — документированная граница §EN-10).
- **Дрейф-гарды раньше гарда повторности** (§EN-3): `complete` сперва проверяет, что процесс и текущий
  шаг инстанса находятся в поданном файле, и только потом — статус задачи (негатив 4 §EN-9 это ловит).
- **`complete` не исполняет top-level**: повторное исполнение программы создавало бы новые инстансы
  на каждый `complete`. Следствие: шаг, читающий top-level `пусть`-глобаль, при пробуждении даёт
  `'<имя>' не объявлено` → инстанс `провален`, exit 1 (граница §EN-10; в `run` тот же шаг работает);
  источники/метрики работают в обоих режимах (ленивая загрузка).
- **`--db` на несуществующий файл** по валидному пути создаёт пустую БД со схемой: `complete` тогда
  даёт `ladix: задача '<id>' не найдена`, `tasks` — `открытых задач нет`; отдельной диагностики
  «базы нет» в v1 нет (§EN-6).
- **`x = E` на переменной процесса** (не `присвоить`) мутирует слой процесса **без персиста** — мутация
  живёт до конца текущего прогона и теряется при следующем пробуждении; канонический канал мутации —
  `присвоить`; диагностика «используйте `присвоить`» в v1 не вводится (§EN-10).
- **Повторная активация шага может повторить `присвоить`** (at-least-once, D-11): идемпотентность по
  переменным — ответственность автора программы (граница §EN-10).
- **Вложенный `запустить процесс` из тела шага** синхронно доводит вложенный инстанс до его
  ожидания/терминала и возвращает id; печать программы и движка перемешивается в порядке исполнения
  (всё синхронно, один поток).
- **`вызвать` в v1 всегда успешен** (стаб): путь «сбой `вызвать` → `провален`» описан контрактом, но
  недостижим; категория `ОшибкаПроцесса` не вводится — ей нечего нести (D-14).
- **Инстанс, убитый посреди шага** (kill процесса ОС в `выполняется`), остаётся залипшим до 007
  (рестарт-скан — носитель демон, D-4); закрыто только окно «задача завершена, advance не успел» —
  гард-догоном.
- **`уведомить` без аргументов** печатает строку без двоеточия и хвостовых пробелов (строка 1а §EN-7);
  `вызвать` без аргументов — `[вызов] <имя>()`.
- **`присвоить` в цикле `пока`** ⇒ много мелких персист-записей — принято в v1 (батчинг — v2).
- **`metric` и движок**: формула метрики может через функцию дёрнуть `запустить процесс`/процессную
  встроенную — поэтому `metric` тоже собирает исполняемый стек (хранилище всегда эфемерное, флага
  `--db` у неё нет); защитная ошибка «движок процессов не подключён» в CLI 006 недостижима.

## Requirements *(mandatory)*

### Functional Requirements

**Хранилище состояния (§EN-2)**

- **FR-001**: Система MUST предоставлять хранилище состояния процессов с двумя реализациями за одним
  контрактом: **эфемерное в памяти** (для `run` без `--db`, `metric` и тестов) и **персистентное
  SQLite-файловое** (`modernc.org/sqlite`, чистый Go без CGO — **первая внешняя зависимость
  проекта**). Контракт — ровно 8 операций (D-3): сохранить (upsert) / загрузить инстанс; сохранить /
  загрузить задачу; список открытых задач с фильтром по исполнителю (пустой фильтр = все открытые,
  порядок **по возрастанию id**, D-15); атомарно завершить задачу; выдать очередной id инстанса /
  задачи. Операции листинга инстансов и триггерные операции MUST NOT вводиться (D-3/D-4; триггерные
  операции 007 добавит аддитивно, листинги инстансов — вне контракта v006, срок носителя якорь не
  назначает).
- **FR-002**: Id MUST выдаваться персистентным счётчиком (D-10) в формате `p-NNNNNN` / `t-NNNNNN`
  (нуль-паддинг до 6): свежее хранилище всегда начинает с `p-000001`/`t-000001` (детерминизм golden);
  в SQLite счётчик переживает перезапуски (инкремент и выдача атомарны), уникальность гарантируется
  конструктивно (случайный суффикс EM-8 отменён).
- **FR-003**: Завершение задачи MUST быть атомарным переходом `открыта` → `завершена` с фиксацией
  момента завершения (D-12); повторное завершение MUST быть различимо для движка — этим проигравший
  гонку одновременного завершения (D-12) маршрутизируется в ветку гард-догона D-4; сам догон
  детектируется по статусу задачи `завершена` до любых мутаций (§EN-3).
- **FR-004**: Отказы «инстанс не найден», «задача не найдена», «задача уже завершена» MUST быть
  различимы движком и транслироваться в русские тексты §EN-8 (SPEC §13, конвенция проекта);
  внутренние ошибки наружу не печатаются.
- **FR-005**: Открытие SQLite-хранилища MUST явно и идемпотентно инициализировать схему (таблицы
  инстансов, задач и счётчиков с сидом; повторное открытие безвредно) и включать режимы
  конкурентности EM-7 (WAL, busy-timeout, внешние ключи); первая же ошибка открытия/инициализации
  MUST всплывать как CLI-ошибка `ladix: не удалось открыть хранилище '<путь>': <причина>`, exit 2.
- **FR-006**: Значения переменных процесса в SQLite MUST кодироваться type-tagged JSON (§EN-2):
  каждое значение несёт метку типа; спецзначения Дробного `NaN`/`+Inf`/`-Inf` — **строками** (D-5);
  Запись — **массивом пар** с сохранением порядка ключей (D-6); верхний уровень карты переменных —
  объект с ключами **по возрастанию** (D-21); временные поля — RFC3339 секундной точности.
  Round-trip MUST быть честным (что записано — то и читается) для всех 10 типов значений.
- **FR-007**: Реализация в памяти MUST исключать алиасинг: сохранение/загрузка копируют инстанс,
  карту переменных И задачу (значения разделяются — ссылочность Список/Запись сохраняется); мутации
  снаружи не видны в хранилище до следующего сохранения.

**Движок: запуск, продвижение, машина состояний (§EN-3)**

- **FR-008**: Запуск процесса MUST создавать инстанс в статусе `создан` с переменными из позиционной
  связки параметров и аргументов и **синхронно** продвигать его до первой точки ожидания или
  терминала; запуск **тихий** — системной stdout-строки нет (D-13). Имя процесса гарантированно
  разрешено семантикой 005 (§PM-4).
- **FR-009**: Машина статусов MUST соответствовать SPEC §11.1: `создан` → `выполняется` →
  (человеческий шаг) `ожидает` ↔ (complete) `выполняется` → `выполнен`; сбой → `провален`; `отменён`
  зарезервирован и недостижим. Финальное завершение задачи переводит инстанс из `ожидает` в
  `выполнен` **напрямую** (§EN-3, завершение при отсутствии следующего шага); через `выполняется`
  инстанс проходит только при наличии следующего шага (продвижение). Шаги исполняются **строго в
  порядке исходника** (§11.2), активен ровно один. Инстанс MUST персистироваться на создание,
  каждую смену статуса/шага, каждое `присвоить` и
  терминал (гранулярность EM-9), с обновлением метки изменения перед каждой записью.
- **FR-010**: Атрибуты шага MUST вычисляться **до тела** (D-9, правка EM-9 под SPEC §11.3): (1)
  `исполнитель`/`срок` в кадре шага, (2) тело, (3) развилка задача/продвижение. Ошибка вычисления
  атрибута = runtime-ошибка шага (инстанс `провален`, как ошибка тела).
- **FR-011**: Типы атрибутов MUST проверяться движком на фазе атрибутов (D-18; семантика 005 их не
  обходит): `исполнитель` обязан быть Строкой, `срок` — Длительностью; нарушение → ОшибкаТипа
  байт-точным текстом §EN-8.A с позицией выражения атрибута, инстанс `провален`.
- **FR-012**: Дедлайн задачи MUST абсолютизироваться при её создании: момент создания + `срок` (D-19);
  единицы `сек`/`мин`/`час`/`дн`/`нед` — фиксированные множители (дн = 24 ч, нед = 168 ч), `мес` —
  календарное смещение. Это внутренняя механика дедлайна, не Ladix-арифметика (clamp-семантика SPEC §4
  на неё не распространяется). Шаг без `срок` → задача без дедлайна.
- **FR-013**: Развилка после тела (SPEC §11.3): задан `исполнитель` → создать задачу (stdout-строка
  3/4 §EN-7: со сроком/без), перевести инстанс в `ожидает` и заснуть (EM-10); не задан → следующий шаг
  по исходнику; шагов больше нет → `выполнен`, **тихо** (печати нет).
- **FR-014**: Провал (D-14): необработанная runtime-ошибка тела или атрибута MUST персистировать
  инстанс как `провален` и всплывать как обычная ошибка программы — канон SPEC §13 в stderr,
  fail-fast, exit 1 (`run` и `complete` одинаково). Дополнительной CLI/stdout-строки о провале нет;
  категория `ОшибкаПроцесса` MUST NOT вводиться (строка «Процесса» SPEC §13.1 остаётся
  зарезервированной прозой).
- **FR-015**: Завершение задачи MUST проходить гарды строго в порядке §EN-3: задача существует →
  инстанс существует → **дрейф-гарды Q3** (процесс инстанса и его текущий шаг найдены в поданном
  файле) → гард-догон D-4 → гарды D-8 (инстанс в `ожидает` И текущий шаг == шаг задачи) → атомарное
  завершение → печать → продвижение. Любое нарушение гарда → CLI-ошибка §EN-8.B, exit 2, **инстанс не
  тронут**.
- **FR-016**: Гард-догон (D-4): повторное завершение уже-завершённой задачи при инстансе в `ожидает`
  на том же шаге MUST идемпотентно до-продвинуть инстанс (без повторного завершения задачи), напечатав
  строку 8 §EN-7 вместо строки 7, exit 0; во всех прочих случаях повторного завершения →
  `ladix: задача '<id>' уже завершена`, exit 2. Проигравший гонку одновременного завершения (D-12)
  MUST уходить в ту же ветку догона.
- **FR-017**: Время движка (D-2) MUST идти от собственных подменяемых часов (дефолт — системные;
  подмена — тесты/golden): временные метки инстансов/задач, абсолютизация дедлайна, признак
  «просрочена» (текущий момент позже дедлайна; без дедлайна — не просрочена, EM-13). Дневные часы
  интерпретатора (метрики 004, golden 2026-05-31) MUST NOT затрагиваться; инвариант «прямое обращение
  к системному времени запрещено всюду, кроме реализаций часов» переформулируется под два легальных
  места (интерпретатор и движок).
- **FR-018**: Сбои хранилища MUST маршрутизироваться по инициатору (§EN-3): пути, инициированные
  Ladix-узлом (`запустить процесс`, `присвоить`, процессные встроенные — включая весь прогон внутри
  запуска), → ОшибкаВыполнения `сбой хранилища: <причина>` с позицией узла-инициатора (§EN-8.A,
  exit 1); CLI-пути `complete`/`tasks` (загрузки, завершение, листинг, декод битой БД, персисты
  продвижения из `complete`) → `ladix: сбой хранилища: <причина>`, exit 2 (§EN-8.B — Ladix-позиции у
  такой ошибки нет).

**Интеграция движка с интерпретатором (§EN-4)**

- **FR-019**: Тело шага MUST исполняться в трёхслойном кадре SPEC §6.4: глобальная область →
  переменные процесса → локали шага; чтение имени идёт вверх по цепочке, затем
  функции/источники/метрики (существующий резолв — без изменений). Слой переменных процесса MUST
  строиться заново при каждом продвижении из персистированных переменных (один слой на весь прогон;
  слой шага — свой на каждый шаг). Граница интерпретатор↔движок закрыта решением D-1 и не
  переоткрывается (механизм границы — уровень плана реализации).
- **FR-020**: `присвоить x = E` MUST вычислять `E` в текущем кадре, создавать/обновлять переменную
  **слоя процесса** (мимо тени `пусть`-локали шага — §6.4) и **немедленно персистировать** изменение —
  это единственный персистирующий канал мутации переменных процесса. Обычное `x = E`, достигнув слоя
  процесса, мутирует его **без** персиста (документированная граница §EN-10; диагностика — v2).
  Снапшот слоя при засыпании MUST NOT сниматься (иначе неперсистируемые мутации утекали бы в БД).
- **FR-021**: `вызвать Имя(args)` / `уведомить Имя(args)` MUST вычислять аргументы слева направо и
  исполняться стабами (D-13): одна stdout-строка форматов 2 / 1–1а §EN-7 (имя цели — идентификатор,
  не резолвится как переменная); `вызвать` в v1 всегда успешен, `уведомить` — best-effort без сбоя.
- **FR-022**: `запустить процесс P(args)` MUST вычислять аргументы, запускать процесс (FR-008) и
  возвращать Строку-id; конструкция работает на верхнем уровне, в функции и в теле шага; вложенный
  запуск синхронно доводит вложенный инстанс до его ожидания/терминала и возвращает управление
  внешнему шагу.
- **FR-023**: При неподключённом движке активированные конструкции MUST давать защитную
  ОшибкуВыполнения `внутренняя ошибка: движок процессов не подключён` (§EN-8.A); в CLI 006 ветка
  недостижима — все команды, исполняющие Ladix-код (`run`/`complete`/`metric`), собирают единый
  исполняемый стек (§EN-6; у `metric` хранилище всегда эфемерное, флага `--db` нет).

**Активация deferred-веток 005 (карта §EN-5 — точечная и исчерпывающая)**

- **FR-024**: Литерал длительности MUST активироваться полностью (D-7): рантайм даёт значение
  Длительность (число + единица); **семантический deferred снимается** — литерал валиден в любой
  позиции выражения; нормализованная лексема вне диапазона Целого → ОшибкаВыполнения
  `литерал длительности вне диапазона типа Целое` с позицией литерала (D-16). Сверх снятия этого
  case семантический проход 005 MUST NOT меняться (контекст-гард действий, арность запуска — уже
  корректны для 006).
- **FR-025**: Сравнения Длительностей MUST активироваться минимумом D-17: `==`/`!=` — по паре
  единица+значение (`1час != 60мин`, нормализации нет); `<`/`<=`/`>`/`>=` — только в **одной**
  единице; порядковое сравнение разных единиц → существующая ОшибкаТипа
  `'<оп>' нельзя применить к Длительность и Длительность`. Арифметика Длительностей и дат MUST NOT
  активироваться (граница §EN-10).
- **FR-026**: Три процессные встроенные MUST активироваться (D-15) с реализацией через движок:
  `статус_процесса(id)` → статус-строка; `состояние_процесса(id)` → Запись переменных инстанса с
  ключами **по возрастанию** (D-21); `задачи_пользователя(имя)` → открытые задачи исполнителя
  (пустая строка = все) списком Записей **по возрастанию id**, поля — таблица «Task → Запись» EM-13
  (включая `просрочена`). Аргумент не-Строка → ОшибкаТипа `<имя>: ожидается Строка, получено <тип>`
  (позиция вызова); неизвестный id → ОшибкаВыполнения `процесс '<id>' не найден` (позиция вызова).
- **FR-027**: Реестр встроенных MUST стать **28 активных + 7 deferred = 35** (инвариант суммы
  сохраняется); 7 дата-имён (`вчера`, `завтра`, `длительность`, `в_секундах`, `в_минутах`, `в_часах`,
  `в_днях`) остаются deferred с прежним текстом `функция '<имя>' не поддерживается в этой версии`.
- **FR-028**: Все замки инвентаря §EN-0 MUST быть перевёрнуты: deferred-тест CLI-онбординга (код 1 →
  код 0 + golden сценария А, включая стейл-докстринг); тест семантической границы (литерал
  длительности и `статус_процесса(1)` — семантика чиста, проверка переезжает в рантайм); тест
  deferred-встроенных (итерирует 7 оставшихся имён; счёт-комментарии «10» → «7»); стейл-комментарии
  счёта реестра («25 активных + 10», «23 активных + 12» → «28 + 7»); шапка deferred-значений
  («Длительность не конструируется» → конструируется); строка онбординга в `examples/MANIFEST.md`
  (код 0, golden сценария А, id детерминированы, маска только `<время>`); стейл-формулировка
  «единственный легальный вызов системного времени» (теперь два легальных места — интерпретатор и
  движок, D-2). Мёртвая после активации рантайм-заглушка deferred MUST быть удалена вместе с
  активацией (§EN-5).

**CLI (§EN-6)**

- **FR-029**: `ladix run <файл> [--db путь] [--max-depth N]`: без `--db` — эфемерное хранилище (как
  сейчас); с `--db` — SQLite (Q2). После последнего top-level MUST печататься сводка открытых задач
  (строки 5–6 §EN-7) **только при N ≥ 1**; висящие задачи — не ошибка, exit 0. Повторный `run --db`
  того же файла создаёт **новые** инстансы (счётчик персистентен; старые остаются в БД и видны в
  `tasks`) — документированная норма v1.
- **FR-030**: `ladix complete <file.ladix> <task-id> [--db путь] [--max-depth N]` (Q3): ровно два
  позиционных аргумента (меньше/больше → usage, exit 2); истина — в исходнике: файл MUST чисто пройти
  компиляцию (лексика → синтаксис → семантика; иначе обычный барьер, stderr канон §13, exit 1), но
  top-level MUST NOT исполняться (исключает создание новых инстансов на каждый `complete`). БД —
  SQLite, путь из `--db`, дефолт `ladix.db`. Успех (включая догон) → stdout строки 7–10 §EN-7,
  exit 0; runtime-ошибка продвижения → инстанс `провален`, канон §13, exit 1, итоговой строки нет.
- **FR-031**: `ladix tasks [исполнитель] [--db путь]`: файл MUST NOT приниматься (всё из БД; ни движок,
  ни интерпретатор не строятся); БД — SQLite, дефолт `ladix.db`; один опциональный позиционный —
  фильтр-исполнитель. Вывод — по строке формата задачи на каждую открытую (строка 6 §EN-7; формат
  един с run-сводкой — один источник формата, D-22); пустой список → `открытых задач нет` (строка 11).
  Exit 0 в обоих случаях.
- **FR-032**: Usage-строка MUST обновиться до четырёх команд (`run`/`metric`/`complete`/`tasks` с их
  флагами); разбор флагов — в существующем стиле (`--флаг значение` и `--флаг=значение`); неизвестный
  флаг → `ladix: неизвестный флаг <а>`, exit 2; `--db` без значения →
  `ladix: флаг --db требует значение`, exit 2. Существующие CLI-тексты (`не удалось прочитать файл`,
  `неверное значение --max-depth`, `лишний аргумент`, usage) — без изменений.
- **FR-033**: Коды возврата MUST сохранять канон README: **0** — успех (включая `run` с висящими
  задачами и гард-догон); **1** — ошибка программы Ladix (компиляция, рантайм, провал инстанса) и
  внутренняя паника; **2** — ошибка использования/окружения (аргументы, файл, хранилище, гарды
  `complete`, дрейф Q3).
- **FR-034**: Несуществующий файл БД по валидному пути MUST создавать пустую БД со схемой (поведение
  любой команды, открывающей хранилище); следствия для `complete`/`tasks` — штатные «не найдена» /
  «открытых задач нет»; отдельной диагностики «базы нет» в v1 нет.

**Байт-точный stdout (§EN-7)**

- **FR-035**: Все системные строки MUST печататься в stdout байт-точно по реестру §EN-7 (11 форматов,
  каждая строка завершается `\n`): 1/1а — стаб `уведомить` (аргументы через одиночный пробел / без
  аргументов — без двоеточия и хвостовых пробелов); 2 — стаб `вызвать` (аргументы через `", "`);
  3/4 — создание задачи (со сроком / без); 5 — заголовок сводки `открытых задач: <N>`; 6 — строка
  задачи (поля через **два** пробела, хвост `срок до <время>` только при дедлайне, хвост `ПРОСРОЧЕНА`
  только при просрочке); 7 — `задача <t-id> завершена` (до продвижения); 8 — `задача <t-id> уже была
  завершена, инстанс до-продвинут`; 9/10 — итог `complete` (`инстанс <p-id>: ожидает, шаг '<имя>'` /
  `инстанс <p-id>: выполнен`); 11 — `открытых задач нет`. Аргументы — каноническим строковым
  представлением значений (Длительность — `3дн`); время дедлайна — формат `ГГГГ-ММ-ДД ЧЧ:ММ`
  локальной зоны (байт-точный канон формата — §EN-7).
- **FR-036**: В stdout MUST NOT появляться (осознанно, D-13/D-14): сообщение о запуске процесса
  (печать `запущен …, id: …` в демо делает программа), сообщение о терминале внутри `run`, строки о
  провале (провал — диагностика stderr), заголовок у `tasks` при непустом списке.

**Байт-точные диагностики (§EN-8)**

- **FR-037**: Новый слой ошибок программы §EN-8.A MUST воспроизводиться байт-точно в каноне §13
  (двухстрочный формат, позиция обязательна, stderr, exit 1): `процесс '<id>' не найден`;
  `статус_процесса: ожидается Строка, получено <тип>`; `состояние_процесса: ожидается Строка,
  получено <тип>`; `задачи_пользователя: ожидается Строка, получено <тип>`;
  `шаг '<имя>': исполнитель должен быть Строка, получено <тип>`;
  `шаг '<имя>': срок должен быть Длительность, получено <тип>`;
  `литерал длительности вне диапазона типа Целое`; `сбой хранилища: <причина>`;
  `внутренняя ошибка: движок процессов не подключён`.
- **FR-038**: CLI-ошибки §EN-8.B MUST воспроизводиться байт-точно одной строкой `ladix: <текст>` в
  stderr, exit 2 (D-20): `задача '<id>' не найдена`; `задача '<id>' уже завершена`;
  `инстанс '<id>' не найден`; `инстанс '<p-id>' не ожидает (статус '<статус>')`;
  `задача '<t-id>' не соответствует текущему шагу инстанса '<p-id>'`;
  `процесс '<имя>' не найден в определении`; `шаг '<имя>' не найден в определении процесса '<имя>'`;
  `не удалось открыть хранилище '<путь>': <причина>`; `сбой хранилища: <причина>`;
  `флаг --db требует значение`.
- **FR-039**: Существующие реестры диагностик (eval-model §8.3, source-metric-model §SM-9,
  process-model §PM-6) MUST действовать без изменений — runtime-ошибки тела шага это они и есть.

### Key Entities *(include if feature involves data)*

- **Экземпляр процесса (ProcessInstance)**: конкретный запуск процесса. Несёт **id** (`p-NNNNNN`),
  **имя процесса**, **статус** (`создан` — транзиентный, `выполняется`, `ожидает`, `выполнен`,
  `провален`; `отменён` — резерв, в v1 недостижим), **текущий шаг** (при терминале — последний
  обработанный), **переменные процесса** (персистирует только канал `присвоить`; пусть-локали шага
  сюда не попадают) и **временные метки** создания/обновления (часы движка). Персистируется на каждую
  смену статуса/шага и каждое `присвоить`.
- **Задача (Task)**: точка ожидания человека, создаётся при входе в человеческий шаг. Несёт **id**
  (`t-NNNNNN`), **ссылку на инстанс**, **имя шага**, **исполнителя** (Строка; в v1 — совещательная
  метка, реестра ролей нет), **дедлайн** (абсолютизированный момент или отсутствует), **статус**
  (`открыта` / `завершена`), **метки** создания/завершения. «Просрочена» — вычислимый признак
  (текущий момент позже дедлайна), не статус.
- **Хранилище (Store)**: контракт из 8 операций над инстансами и задачами (D-3) с двумя реализациями —
  эфемерной (память) и персистентной (SQLite-файл). Внутри SQLite значения кодируются type-tagged
  JSON (D-5/D-6/D-21), времена — RFC3339; движок о формате хранения не знает (путь замены бэкенда
  открыт, EM-4).
- **Счётчики id**: персистентные монотонные счётчики инстансов и задач (D-10); свежее хранилище —
  `p-000001`/`t-000001`; в SQLite переживают перезапуски — повторный `run --db` продолжает нумерацию.
- **Длительность (значение)**: число + единица (`сек`/`мин`/`час`/`дн`/`нед`/`мес`); конструируется
  литералом (`3дн`); сравнима на равенство (единица+значение) и порядково в одной единице (D-17);
  арифметики в 006 нет.
- **Часы движка**: источник реального времени lifecycle (метки, дедлайны, просрочка); подменяемы в
  тестах (фиксированный момент → байт-точный golden); отдельны от дневных часов интерпретатора (D-2).

  `complete <file.ladix> <task-id>`) и архитектора **D-1…D-22** (граница интерпретатор↔движок, часы
  движка, нарезанный контракт хранилища, гард-догон, кодеки NaN/Записи, фаза атрибутов, персистентный
  mint id, at-least-once, атомарное завершение, тихий запуск, провал без новой категории, процессные
  встроенные, лексема-строка литерала, минимум сравнений Длительности, тип-гарды атрибутов,

  гарантирует валидность определений процессов в скомпилированном файле; синтаксис и AST в 006 не
  меняются вовсе (§EN-10, путь отступления).
- `modernc.org/sqlite` — чистый Go (без CGO), первая внешняя зависимость проекта; go.mod + go.sum

- `examples/онбординг.ladix` используется приёмкой **как есть** (005-редакция); правки примеров не
  требуются, синкается только `MANIFEST.md`.
- Граница эксплуатации v1: исходник между `run --db` и `complete` не меняют (дрейф ловится гардами Q3

- Функциональный чеклист от 006 ничего не требует — фича целиком продуктовая (§EN-0).

## Out of Scope *(границы §EN-0/§EN-10)*

- **Триггеры и демон** — EM-17 целиком: `serve`, `emit`, флаг `--interval`, тик планировщика,
  состояние триггеров (`TriggerState`), очередь событий, fire-if-true-проход в `run`, триггерные
  операции хранилища и его таблицы, фронтенд `когда` (парсер/AST/семантика, предопределённые
  `значение`/`событие`) → **фича 007**. `repl` — вне 006 (дополнительная возможность, фича не назначена).
- **Рестарт-скан залипших инстансов** (упавших в `выполняется`/`создан` посреди шага) → **007**
  (носитель — демон, D-4); в 006 такой инстанс остаётся залипшим; закрыто только окно «задача
  завершена, продвижение не успело» — гард-догоном D-4.
- **Листинги инстансов** в контракте хранилища отсутствуют (D-4; срок носителя якорь не назначает);
  **версионирование определений** (смена тела шага между `run` и `complete` не детектится — дрейф
  ловится только по именам; хеш определения в инстансе) → v2.
- **Арифметика Длительности и дат** (`Длит ± Длит`, `Длит * X`, `Дата ± Длит`, `Дата - Дата` —
  SPEC §4) не активируется (D-17), остаётся ОшибкаТипа; **7 дата-встроенных** (`вчера`, `завтра`,
  `длительность`, `в_секундах`, `в_минутах`, `в_часах`, `в_днях`) остаются deferred. Бэклог 007+/v2.
- **Категория `ОшибкаПроцесса`** не вводится (D-14: ей нечего нести — `вызвать` в v1 всегда успешен);
  строка «Процесса» SPEC §13.1 остаётся зарезервированной прозой.
- **At-least-once `присвоить`** (D-11): повтор шага может повторить мутации; идемпотентность по
  переменным — ответственность автора. **Остаточная гонка двойного `complete`** (D-12): проигравший
  уходит в догон D-4; последствия ограничены гардами D-8. Транзакционный комбо-метод хранилища
  «завершить + продвинуть» не вводится намеренно (§EN-2) — корректность окна обеспечивает
  идемпотентный гард-догон D-4.
- **Правило «`'x'` — переменная процесса, используйте `присвоить`»**: рантайм 006 не различает запись
  `x = E` в слой процесса (мутация без персиста, живёт до конца прогона) — диагностика v2.
- **Top-level `пусть`-глобали при `complete`**: top-level не исполняется — шаг, читающий глобаль, при
  пробуждении даёт `'<имя>' не объявлено` → `провален`, exit 1 (в `run` тот же шаг работает); канал
  данных между шагами — переменные процесса; источники/метрики доступны в обоих режимах.
- **Exactly-once эффектов, батчинг персиста, транзакционный outbox, отзыв осиротевших задач при
  `провален`, payload задачи (`complete` не передаёт данные), реестр ролей/прав** → v2 (EM-12/EM-15,
  SPEC §12).
- **Машинно-читаемый вывод, миграции схемы БД** → 007/v2.
