# Quickstart: Движок исполнения процессов + человек-в-цикле (006-process-engine)

**Feature**: 006-process-engine | **Plan**: [plan.md](./plan.md) | **Якорь**: [../../docs/engine-model.md](../../docs/engine-model.md) | **Спека**: [spec.md](./spec.md)

Как разработчику собрать, запустить и проверить фичу 006 руками. Фича 006 **включает движок исполнения** процессов: `запустить процесс` реально создаёт инстанс и **синхронно** прогоняет шаги в порядке исходника; на человеческом шаге (`исполнитель:`) создаётся **задача** и инстанс засыпает; человек завершает задачу командой `ladix complete`, инстанс просыпается и идёт дальше — до терминала. Состояние переживает завершение процесса ОС: между запусками оно живёт в **SQLite-файле** (`run --db` / `tasks` / `complete`). Активируются рантайм-deferred-ветки 005 — действия шага (`присвоить`/`вызвать`/`уведомить`), литерал длительности (`3дн`), три процессные встроенные.

Это **продуктовая** фича (функциональный чеклист от 006 ничего не требует, [§EN-0](../../docs/engine-model.md)). Три новых наблюдаемых поверхности: **байт-точный stdout** ([§EN-7](../../docs/engine-model.md), 11 форматов), **байт-точные диагностики** ([§EN-8](../../docs/engine-model.md), §EN-8.A program-ошибки exit 1 / §EN-8.B CLI-ошибки exit 2), **CLI** ([§EN-6](../../docs/engine-model.md): `run --db`/`complete`/`tasks`).

Все команды `go` — от корня Go-модуля `src/` (там `go.mod`, модуль `github.com/denis-kosyakov/ladix`, go 1.22). **Новая внешняя зависимость** — `modernc.org/sqlite` (чистый Go, без CGO; первая зависимость проекта, go.mod + go.sum — отдельным коммитом, FR-041). Пути `.ladix`-примеров — от **корня репозитория**.

> **Прежде чем читать дальше:** при любом расхождении этого файла с якорем побеждает якорь. Здесь — сборка/запуск/ручная проверка; контракт `Store`, машина состояний, кадр шага, гарды `complete` и **байт-точные** тексты — в `docs/engine-model.md §EN-2…§EN-9`.

## 0. Где лежит go.mod и как собирать

```bash
cd src                       # все команды go — отсюда; go.mod здесь
ls go.mod                    # github.com/denis-kosyakov/ladix, go 1.22
go mod download              # подтянуть modernc.org/sqlite (FR-041, первая внешняя зависимость)
go build -o /tmp/ladix ./cmd/ladix
```

Новые пакеты ([§EN-0](../../docs/engine-model.md)): `internal/store` (типы `ProcessInstance`/`Task`/статусы, интерфейс `Store` v006 из 8 методов, `MemoryStore`, `SQLiteStore`, кодек type-tagged JSON, mint id) и `internal/engine` (lifecycle `Start`/`advance`/`Complete`, engine-Clock, реализация `eval.ProcessRuntime`). Граф: `engine → eval, store, ast, value, errors`; **eval НЕ импортирует ни store, ни engine** — цикл разорван интерфейсом `ProcessRuntime`, объявленным в eval (D-1).

## 2. Канонический вход — `examples/онбординг.ladix` (как есть, 005-редакция)

Приёмка использует файл **без правок** (FR-005 spec: только `MANIFEST.md` синкается). Содержимое:

```ladix
# Процесс адаптации нового сотрудника: автоматический шаг + два человеческих
процесс онбординг(сотрудник):
    шаг завести_доступы:
        присвоить имя = сотрудник                 # переменная процесса
        уведомить ИТ("создать учётку для " + сотрудник)   # авто-эффект (стаб-лог)
    шаг провести_встречу после завести_доступы:
        исполнитель: "руководитель"
        срок:        3дн
    шаг закрыть_адаптацию после провести_встречу:
        исполнитель: "HR"
        срок:        5дн

# Запуск из императивного кода: захватываем ID инстанса
пусть id = запустить процесс онбординг("Петров")
печать("запущен онбординг, id:", id)
```

Поток исполнения: `завести_доступы` (авто) исполняет тело — `присвоить имя = сотрудник` (переменная процесса персистится) + `уведомить ИТ(...)` (стаб-строка) → продвижение; `провести_встречу` (человеческий: `"руководитель"`, `3дн`) создаёт задачу `t-000001` и инстанс **засыпает** в `ожидает`; top-level `печать` выводит «запущен онбординг, id: p-000001» (печатает **программа**, не движок — запуск тихий, D-13). После top-level CLI печатает сводку висящих задач. `закрыть_адаптацию` будет активирован при `complete`.

## 3. Сценарий А (US1, [§EN-9](../../docs/engine-model.md)) — `ladix run` без `--db` (MemoryStore)

```bash
cd src
go build -o /tmp/ladix ./cmd/ladix
cd ..                                   # из корня репозитория
/tmp/ladix run examples/онбординг.ladix
```

**Ожидаемый stdout (байт-точно, 5 строк, с фиксированными часами движка 2026-05-31 00:00:00):**

```
[уведомление] ИТ: создать учётку для Петров
[задача] t-000001 → руководитель, шаг 'провести_встречу', срок до 2026-06-03 00:00
запущен онбординг, id: p-000001
открытых задач: 1
t-000001  p-000001  'провести_встречу'  руководитель  срок до 2026-06-03 00:00
```

**exit 0** (висящие задачи — не ошибка, FR-029). Разбор строк по реестру [§EN-7](../../docs/engine-model.md):
- строка 1 — стаб `уведомить` (формат 1: получатель + двоеточие + аргументы через **один** пробел);
- строка 2 — создание Task со сроком (формат 3); дедлайн абсолютизирован `CreatedAt + 3дн` = 2026-06-03 00:00 (D-19, дн = 24 ч);
- строка 3 — печать **программы** (`печать(...)`, разделитель аргументов — один пробел);
- строка 4 — заголовок сводки `run` (формат 5; печатается **только при N ≥ 1**);
- строка 5 — строка задачи (формат 6, `FormatTaskLine`; разделитель полей — **два** пробела; хвост «срок до» только при дедлайне; «ПРОСРОЧЕНА» — нет, 2026-05-31 < 2026-06-03).

**Состояние Store на выходе** (наблюдаемо через `статус_процесса`/`состояние_процесса` или БД): инстанс `p-000001` — статус `ожидает`, текущий шаг `провести_встречу`, переменные `{имя: "Петров", сотрудник: "Петров"}` (пусть-локали шага в переменные процесса не попадают); задача `t-000001` — статус `открыта`. **(SC-001)**

> **Чего в stdout НЕТ** (осознанно, D-13/D-14): системной строки о запуске (запуск тихий — «запущен …» делает программа); строки о терминале внутри `run`; строк о провале (провал — stderr); заголовка у `tasks` при непустом списке (FR-036, SC-005).

### Вариации сценария А (acceptance US1)

- **Все шаги автоматические** (без `исполнитель`): инстанс синхронно доходит до `выполнен`, терминал **тихий** (системной строки нет), сводка не печатается (`N == 0`), exit 0.
- **`исполнитель: 42`** (не Строка): stderr канон §13 `шаг '<имя>': исполнитель должен быть Строка, получено Целое`, exit 1; инстанс персистирован как `провален` (D-18/D-14); дополнительной CLI-строки о провале нет.
- **Тело `присвоить x = 1/0`**: stderr `деление на ноль` (канон §13), exit 1, инстанс `провален` (D-14).

## 4. Сценарий Б (US2, [§EN-9](../../docs/engine-model.md)) — персистентная цепочка `run --db` → `tasks` → `complete` (SQLiteStore)

Свежая БД; состояние между командами живёт **только** в файле `test.db` (персистентность между процессами ОС). `<DT>` — маска времени дедлайна на CLI-уровне (id детерминированы). Все команды — из корня репозитория, бинарь в `/tmp/ladix`.

```bash
rm -f test.db                                        # свежая БД (или иной несуществующий путь — создастся со схемой)
```

**Шаг 1 — запуск с мостом в SQLite:**

```bash
/tmp/ladix run examples/онбординг.ladix --db test.db
```
stdout — **как сценарий А (5 строк)**; exit 0; состояние теперь в `test.db`.

**Шаг 2 — открытые задачи (без фильтра):**

```bash
/tmp/ladix tasks --db test.db
```
```
t-000001  p-000001  'провести_встречу'  руководитель  срок до <DT>
```
exit 0. Заголовка при **непустом** списке нет (формат един с run-сводкой, D-22). `tasks` файл НЕ принимает — всё из БД; ни движок, ни интерпретатор не строятся.

**Шаг 3 — фильтр по исполнителю «Петров» (открытых задач у него нет):**

```bash
/tmp/ladix tasks Петров --db test.db
```
```
открытых задач нет
```
exit 0 (формат 11).

**Шаг 4 — завершить первую задачу (будит инстанс → новая задача):**

```bash
/tmp/ladix complete examples/онбординг.ladix t-000001 --db test.db
```
```
задача t-000001 завершена
[задача] t-000002 → HR, шаг 'закрыть_адаптацию', срок до <DT>
инстанс p-000001: ожидает, шаг 'закрыть_адаптацию'
```
exit 0. Завершение (формат 7) → продвижение → следующий человеческий шаг `закрыть_адаптацию` создаёт `t-000002` (формат 3) → инстанс снова заснул (формат 9). Истина — в исходнике (Q3): файл компилируется чисто, top-level НЕ исполняется.

**Шаг 5 — завершить последнюю задачу (терминал):**

```bash
/tmp/ladix complete examples/онбординг.ladix t-000002 --db test.db
```
```
задача t-000002 завершена
инстанс p-000001: выполнен
```
exit 0. Следующего шага нет → инстанс из `ожидает` напрямую в `выполнен` (формат 10, итог терминала).

**Шаг 6 — повторный `run --db` той же БД (Q2/D-10: счётчик персистентен):**

```bash
/tmp/ladix run examples/онбординг.ladix --db test.db
```
stdout — **как шаг 1**, но id `p-000002` / `t-000003` (старые инстансы остаются в БД и видны в `tasks`); exit 0. Норма v1. **(SC-002)**

> **`--db` на несуществующий путь** (валидный каталог) создаёт пустую БД со схемой (`CREATE TABLE IF NOT EXISTS`); тогда `complete` даёт `задача '<id>' не найдена`, `tasks` — `открытых задач нет`; отдельной диагностики «базы нет» в v1 нет (FR-034).

## 5. Негативы (US3, [§EN-9](../../docs/engine-model.md)) — гарды `complete`, инстанс не тронут

Прогон **после шага 5 сценария Б** (`test.db`: инстанс `p-000001` `выполнен`, задачи `t-000001`/`t-000002` `завершены`). CLI-ошибки — одна строка `ladix: <текст>` в stderr, exit 2 (D-20); парс-ошибка — канон §13, exit 1.

### 5.1. Несуществующая задача (`ErrTaskNotFound`)

```bash
/tmp/ladix complete examples/онбординг.ladix t-999999 --db test.db
# stderr: ladix: задача 't-999999' не найдена
# exit 2
```

### 5.2. Повторное завершение при инстансе `выполнен` (догон D-4 неприменим)

```bash
/tmp/ladix complete examples/онбординг.ladix t-000001 --db test.db
# stderr: ladix: задача 't-000001' уже завершена
# exit 2
```
Догон срабатывает **только** при паре «задача `завершена` И инстанс `ожидает` на том же шаге»; здесь инстанс `выполнен` → exit 2.

### 5.3. Файл без процесса `онбординг` (дрейф Q3)

```bash
/tmp/ladix complete examples/hello.ladix t-000001 --db test.db
# stderr: ladix: процесс 'онбординг' не найден в определении
# exit 2
```
`examples/hello.ladix` компилируется чисто, но процесса `онбординг` (имя из инстанса БД) в нём нет → дрейф-гард.

### 5.4. Дрейф шага (testdata-фикстура: шаг переименован)

Фикстура импл-чата `онбординг-дрейф.ladix` — процесс `онбординг` есть, шаг `закрыть_адаптацию` переименован; после шага 5 текущий шаг инстанса `== 'закрыть_адаптацию'`:

```bash
/tmp/ladix complete онбординг-дрейф.ladix t-000001 --db test.db
# stderr: ladix: шаг 'закрыть_адаптацию' не найден в определении процесса 'онбординг'
# exit 2
```
Дрейф-гарды идут **до** гарда «уже завершена» ([§EN-3](../../docs/engine-model.md)): сперва проверяется наличие процесса и текущего шага в поданном файле, и только потом — статус задачи.

### 5.5. Неоткрываемый путь БД

```bash
/tmp/ladix complete examples/онбординг.ladix t-000001 --db нет/такого/каталога.db
# stderr: ladix: не удалось открыть хранилище 'нет/такого/каталога.db': <причина>
# exit 2
```
Открытие/инициализация SQLite не удались (`NewSQLiteStore` явно исполняет PRAGMA + DDL — `database/sql` ленив, без явного `Exec` ошибка не всплыла бы).

### 5.6. Файл с парс-ошибкой (компиляция обязана пройти до работы с БД)

Фикстура импл-чата `сломанный.ladix` с **парс**-ошибкой (НЕ `examples/ошибка.ladix` — та падает в рантайме, а `complete` файл не исполняет, её компиляция чиста):

```bash
/tmp/ladix complete сломанный.ladix t-000001 --db test.db
# stderr: канон §13 (двухстрочный/накопленный):
#         Ошибка в строке N, колонка M:
#         <текст парс-ошибки>
# exit 1
```
Компиляция файла (лексер → синтаксис → семантика) обязана пройти чисто **до** любой работы с БД; ошибка → обычный барьер канона §13, exit 1. **(SC-003)**

> **Фабрикованные гарды D-8** (acceptance US3 п.7-8) — недостижимы через CLI-цепочку (один активный шаг = одна открытая задача), проверяются на уровне движка с фабрикованным Store-состоянием: открытая задача при инстансе `выполняется` → `ladix: инстанс '<p-id>' не ожидает (статус 'выполняется')`; открытая задача с шагом ≠ текущему шагу `ожидающего` инстанса → `ladix: задача '<t-id>' не соответствует текущему шагу инстанса '<p-id>'`; инстанс в обоих случаях **не тронут**.
>
> **Гард-догон D-4** (acceptance US3 п.9): задача `завершена`, но инстанс остался `ожидает` на том же шаге (хвост сбоя) → повторный `complete` печатает строку 8 `задача <t-id> уже была завершена, инстанс до-продвинут` **вместо** строки 7, идемпотентно до-продвигает инстанс, exit 0.

## 6. Точечные приёмки слоя (US4, [§EN-9](../../docs/engine-model.md)) — длительности и процессные встроенные

Короткие `.ladix`-сниппеты через `printf`; все — `ladix run` (MemoryStore). Граница deferred сдвинута **ровно** на карту [§EN-5](../../docs/engine-model.md): арифметика длительностей/дат и 7 дата-встроенных остаются за бортом (D-17).

### 6.1. Литерал длительности — живое значение (D-7/D-16)

```bash
printf 'пусть d = 2дн\nпечать(d)\n' > /tmp/d.ladix
/tmp/ladix run /tmp/d.ladix
# stdout: 2дн
# exit 0
```
Семантический deferred литерала **снят** — `2дн` валиден в любой позиции; рантайм даёт `value.Длительность{Amount:2, Unit:"дн"}`, печать — каноническим repr `2дн`.

### 6.2. Сравнения длительностей (D-17: единица + значение, без нормализации)

```bash
printf 'печать(2дн == 2дн)\n' > /tmp/eq1.ladix; /tmp/ladix run /tmp/eq1.ladix    # stdout: истина
printf 'печать(1час == 60мин)\n' > /tmp/eq2.ladix; /tmp/ladix run /tmp/eq2.ladix  # stdout: ложь  (разные единицы, нормализации нет)
printf 'печать(2дн < 5дн)\n' > /tmp/lt1.ladix; /tmp/ladix run /tmp/lt1.ladix      # stdout: истина  (порядок в одной единице)
```

### 6.4. Литерал вне диапазона типа Целое (D-16)

### 6.6. `вчера()` остаётся deferred (граница 7 дата-имён НЕ сдвинулась, FR-027)

```bash
printf 'печать(вчера())\n' > /tmp/y.ladix
/tmp/ladix run /tmp/y.ladix
# stderr: Ошибка в строке 1, колонка ...:
#         функция 'вчера' не поддерживается в этой версии

```
7 дата-встроенных (`вчера`, `завтра`, `длительность`, `в_секундах`, `в_минутах`, `в_часах`, `в_днях`) остаются в `deferredNames` с прежним текстом. Реестр: **28 активных + 7 deferred = 35**. **(SC-004)**

## 7. Чек-лист приёмки по user stories

- **US1 (P1, запуск до точки ожидания)** — сценарий А (§3): `ladix run examples/онбординг.ladix` → байт-точный stdout из 5 строк, exit 0; состояние Store: `p-000001` `ожидает`/`провести_встречу`, переменные `{имя, сотрудник}`, `t-000001` `открыта` **(SC-001)**. Вариации: все-авто → `выполнен` тихо; `исполнитель: 42` → ОшибкаТипа exit 1 `провален`; `1/0` → `деление на ноль` exit 1 `провален`.
- **US2 (P1, человек-в-цикле / SQLite)** — сценарий Б (§4): цепочка из 6 команд на свежей БД → ожидаемый stdout каждого шага и exit 0; повтор создаёт `p-000002`/`t-000003`; состояние между командами — только в файле БД **(SC-002)**.
- **US3 (P2, гарды `complete`)** — негативы (§5): 6 кейсов → дословные stderr и коды (несуществующая задача 2, повтор при `выполнен` 2, файл без процесса 2, дрейф шага 2, неоткрываемая БД 2, парс-ошибка 1) **(SC-003)**; фабрикованные гарды D-8 и догон D-4 — на уровне движка/acceptance.
- **US4 (P2, длительности и встроенные)** — точечные приёмки (§6): литерал `2дн`; сравнения `==`/`!=`/порядок; вне диапазона; `статус_процесса` на живом/неизвестном/не-Строка; `задачи_пользователя("")`; `вчера()` deferred **(SC-004)**.
- **stdout/диагностики** — 11 форматов §EN-7 exact-match **(SC-005)**; тексты §EN-8.A (9) + §EN-8.B (10) байт-точно, реестры 003/004/005 не изменились **(SC-006)**.
- **Гейты** — `go build`/`go vet`/`gofmt -l`/`go test ./...`/`-race` зелёные, регрессы 001–005, golden 004 неизменен **(SC-007)**; замки инвентаря перевёрнуты, реестр 28+7 **(SC-008)**; D-2 grep-инвариант — два легальных `time.Now()` **(SC-009)**.

## 8. Границы (НЕ делать на этом шаге, [§EN-0](../../docs/engine-model.md)/[§EN-10](../../docs/engine-model.md))

- **НЕ трогать триггеры/демон** — весь EM-17: `serve`, `emit`, `--interval`, тик планировщика, `TriggerState`, очередь `events`, fire-if-true в `run`, триггерные методы Store + таблицы, фронтенд `когда` → **007**. `repl` — вне 006.
- **НЕ вводить** рестарт-скан залипших инстансов (носитель — демон 007, D-4); закрыто только окно «задача завершена, advance не успел» — гард-догоном.
- **НЕ вводить** методы листинга инстансов в контракт Store (D-3/D-4); **НЕ вводить** транзакционный комбо-метод «завершить + продвинуть» (корректность — идемпотентный догон).
- **НЕ активировать** арифметику Длительности и дат (`Длит ± Длит`, `Длит * X`, `Дата ± Длит`, `Дата - Дата` — D-17, остаётся ОшибкаТипа); **НЕ снимать** deferred с 7 дата-встроенных.
- **НЕ вводить** категорию `ОшибкаПроцесса` (D-14: `вызвать` в v1 всегда успешен — нечего нести); строка «Процесса» SPEC §13.1 остаётся зарезервированной прозой.
- **НЕ снимать** снапшот слоя при засыпании (иначе мутации `x = E` мимо хука `присвоить` утекали бы в БД — единственный персистирующий канал — `присвоить`, FR-020); **НЕ вводить** диагностику «используйте `присвоить`» (v2).
- **НЕ исполнять** top-level при `complete` (создавало бы новые инстансы на каждый `complete`); следствие — top-level `пусть`-глобаль при пробуждении даёт `'<имя>' не объявлено` → `провален` (граница §EN-10).
- **НЕ менять** синтаксис/AST 005 (формы §PM-2 движок читает как есть); **НЕ переоткрывать** Q1–Q3 / D-1…D-22.
