# Data Model: золотой сквозной пример §2 (цепочка сущностей)

**Фича**: `023-v2-finalization` | **Якорь**: `docs/v2-finalization-model.md §F-1` + spec.md «Key
Entities». Сущности существуют **уже** (фичи 010–022); эта финализация лишь **сводит их в один
пример** и закрепляет наблюдаемую цепочку замками. Новых типов/полей язык не получает (FR-015).

§2-цепочка DoD (поток данных слева направо):

```
источник заказы  ──►  метрика выручка_30д  ──►  метрика-триггер (связка)  ──►  процесс эскалация_плана
   (CSV)              (окно последние 30дн)      когда < 3_000_000              │
                                                  передаёт снимок (значение)    ├─ задача t-000001 (человек)
                                                                                ├─ payload {"итог":"перезвонит"}
                                                                                └─ реальный эффект → инстанс p-000001
```

---

## E1. Источник `заказы`
- **Тип**: CSV-коннектор поверх `data/orders.csv` (`тип: csv`). Общая фикстура с `выручка_30д.ladix`
  (НЕ менять данные).
- **Схема (`поля:`)**: `дата_заказа: Дата`, `сумма_заказа: Дробное`, `статус: Строка`.
- **Инвариант**: `data/orders.csv` переиспользуется → консистентные golden между примерами.
- **Валидация (приёмка)**: входит в чистый набор `TestExamplesParseCleanSet` (парсится без диагностик).

## E2. Метрика `выручка_30д`
- **Поля декларации**: `источник: заказы`; `где: статус == "оплачен"`; `агрегат: сумма(сумма_заказа)`;
  `период: последние 30дн`; `по_дате: дата_заказа`.
- **Семантика**: скользящее окно `(d−30, d]` по `дата_заказа`; агрегат суммы при фильтре статуса.
- **Снимок (детерминированный)**: под `FixedClock{2026,6,15}` окно `(2026-05-16, 2026-06-15]`
  оставляет оплаченный заказ `2026-05-27` (300000) → **скаляр `300000.0`**.
- **Дата-зависимость**: под реальными часами снимок плывёт (после 2026-06-26 → `0.0`) → golden
  обязан идти на FixedClock (research.md R1).
- **Валидация (приёмка)**: `runMetric` под FixedClock из repo-root печатает `300000.0\n`.

## E3. Метрика-триггер (связка)
- **Форма**: `когда метрика выручка_30д < 3_000_000: запустить процесс эскалация_плана(значение)`.
- **Передача данных**: снимок метрики передаётся как аргумент `значение` → параметр процесса `факт`.
- **Условие срабатывания**: `300000.0 < 3_000_000` → истина → fire (под `run` — fire-if-true, без
  ребра).
- **Наблюдаемость**: при срабатывании под `run` печатает explain-строку «почему» (§C-5.3 run-форма,
  см. contracts/t-gold-metric.md).
- **Семантика serve (edge)**: на boot демона метрика — ребро `ложь→истина`; первый тик праймит без
  срабатывания → постоянно-истинное `< план` инстанс на boot НЕ порождает (метрика-driven старт
  демонстрируется отдельным RUN-прогоном, не serve-boot).

## E4. Процесс `эскалация_плана(факт)`
- **Шаг 1 `связаться_с_клиентом`** (человеческий): `исполнитель: "менеджер"`, `срок: 3дн` → порождает
  задачу `t-000001`.
- **Шаг 2 `зафиксировать_итог` после `связаться_с_клиентом`** (авто, durable-захват):
  `присвоить итог = данные.итог` (читает payload).
- **Шаг 3 `уведомить_crm` после `зафиксировать_итог`** (авто, реальный эффект):
  `уведомить crm("итог звонка: " + итог)`.
- **Эскалация дедлайна**: `когда задача просрочена в эскалация_плана.связаться_с_клиентом: уведомить
  руководитель(факт)` (исполняет демон serve; под `run` — заглушка `… требует serve (фича 007b)`).
- **Инвариант контракта payload (edge)**: доступ `данные.итог` к открытой записи без поля даёт `Пусто`
  (не падает); ошибка возникает шагом позже на конкатенации `"итог звонка: " + итог`, если `итог` пуст
  → `--данные` с полем `итог`-строкой обязателен для осмысленного догона.

## E5. Задача `t-000001`
- **Происхождение**: человеческий шаг `связаться_с_клиентом`.
- **Состояние**: открыта → завершается пользователем (`complete … --данные`).
- **Под run** (тихий старт, D-13): печатается `[задача] t-000001 → менеджер, шаг
  'связаться_с_клиентом', срок до <DT>` (дедлайн маскируется).

## E6. Payload
- **Форма**: `--данные '{"итог":"перезвонит"}'` при завершении задачи.
- **Поле**: `итог` (Строка) → читается шагом `зафиксировать_итог`, конкатенируется в текст эффекта.

## E7. Реальный эффект
- **Форма**: `уведомить crm("итог звонка: " + итог)`.
- **Наблюдаемая строка**: `[уведомление] crm: итог звонка: перезвонит`.
- **Exactly-once**: через рестарт демона доставляется ровно 1 раз (outbox) —
  `TestStepEffectExactlyOnceRestart` (терминальный гейт, не переписывать).

## E8. Инстанс процесса `p-000001`
- **Происхождение**: метрика-триггер (US2, RUN-путь) ИЛИ ручной старт (US3, `ladix start`).
- **Терминальный статус**: «выполнен» (`инстанс p-000001: выполнен`).

## Удаляемое (W1)
- **Хардкод-литеральный старт**: `пусть id = запустить процесс эскалация_плана(2500000)` +
  `печать("запущен контроль плана, id:", id)` — УДАЛИТЬ из примера; старт становится метрика-driven
  (E3) либо ручным внешним (`ladix start`). После удаления литерального числа `2500000` и `печать` в
  файле быть не должно (SC-002).
