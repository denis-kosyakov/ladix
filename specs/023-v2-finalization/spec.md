## User Scenarios & Testing *(mandatory)*

Эта фича — финализация v2 **без новой языковой функциональности**. Ценность для пользователя:
весь золотой сквозной сценарий §2 хартии (от CSV-источника до exactly-once эффекта) можно увидеть
и запустить **в одном файле-примере** вместо склейки из обрывков двух примеров и Go-тестов;
поведение этого примера закреплено детерминированными тест-замками, которые не дают регрессу
протечь незамеченным.

### User Story 1 - Один запускаемый пример всей §2-цепочки (Priority: P1)

Пользователь (изучающий язык / интегратор / грейдер) открывает `examples/контроль_плана.ladix` и
видит **полную** §2-цепочку DoD одним файлом: CSV-источник со схемой полей → метрика как
скользящее окно «последние 30дн» → связка «когда метрика < план запустить процесс, передав снимок» →
процесс с человеческим шагом и сроком → эскалация дедлайна → авто-шаги, читающие payload → реальный
эффект (`уведомить`) в теле шага. Раньше аналитическая половина жила в `выручка_30д.ladix`,
процессная — в `контроль_плана.ladix` со стартом-литералом, а связка — только в Go-тесте; теперь они
сведены воедино, а хардкод-литеральный старт убран (старт стал метрика-driven).

**Why this priority**: Это сердце фичи и центральный артефакт §2-DoD (D-1=a: расширяем существующий
файл, не плодим новый). Без него остальные замки нечего пинить. MVP = этот файл существует, парсится
чисто и прогоняется.

**Independent Test**: Открыть `examples/контроль_плана.ladix`; убедиться, что он содержит источник
`заказы` (CSV `data/orders.csv`, схема `поля:`), метрику `выручка_30д` (окно `последние 30дн`),
триггер `когда метрика выручка_30д < 3_000_000: запустить процесс эскалация_плана(значение)`,
3-шаговый процесс `эскалация_плана` (человеческий шаг + срок, авто-шаги с `данные.итог` и
`уведомить crm`) и триггер эскалации `когда задача просрочена`; убедиться, что хардкод-литеральный
старт (`пусть id = запустить процесс ...` + `печать`) удалён. Прогнать набор парсинга примеров —
файл парсится без диагностик.

**Acceptance Scenarios**:

1. **Given** репозиторий на ветке этой фичи, **When** запускается набор «все примеры парсятся чисто»,
   **Then** `examples/контроль_плана.ladix` входит в чистый набор и не даёт ни одной диагностики.
2. **Given** расширенный `контроль_плана.ladix`, **When** разработчик просматривает файл, **Then** в нём
   присутствуют все семь фасетов §2-цепочки (источник, окно-метрика, метрика-триггер, человеческий
   шаг+срок, эскалация, payload-чтение, реальный эффект), а литерального старта-числа и `печать` в нём
   больше нет.
3. **Given** существующие M1-обучающие примеры, **When** фича завершена, **Then**
   `examples/выручка_30д.ladix` и `examples/выручка.ladix` остаются без изменений, реестр примеров
   растёт (не уменьшается), а `data/orders.csv` переиспользуется как общая фикстура.

### User Story 2 - Детерминированный golden-замок аналитической половины (Priority: P1)

Поскольку метрика §2 — оконная (`последние 30дн`), её снимок дата-зависим: под реальными часами
значение поплывёт по календарю. Пользователь-сопровождающий должен иметь **детерминированный** замок,
который под фиксированными часами пинит три наблюдаемых фасета сквозного прохода: (i) скалярное
значение метрики, (ii) человеко-читаемую строку explain метрика-триггера, (iii) метрика-driven старт
инстанса процесса. Замок заменяет прежний дата-наивный golden эскалации дедлайна, который ломается от
добавления источника.

**Why this priority**: Без детерминированного замка золотой пример не имеет страховки от регресса, а
дата-зависимость делает наивный golden ложно-зелёным/ложно-красным по календарю. Это анти-ловушка из
анкора (§F-1 design-note): голый прогон под реальными часами сегодня даёт совпадающее значение, но
окно скоро исключит единственный оплаченный заказ — фиксированные часы обязательны.

**Independent Test**: Прогнать новый golden под фиксированными часами `{2026,6,15}` из корня
репозитория (чтобы резолвился `data/orders.csv`); проверить, что (i) скаляр метрики равен `300000.0`,
(ii) печатается строка explain срабатывания триггера в каноническом формате, (iii) стартует инстанс
`p-000001` процесса `эскалация_плана`. Инвертировать ожидание (сорвать снимок или строку) — замок
должен покраснеть.

**Acceptance Scenarios**:

1. **Given** фиксированные часы `{2026,6,15}` и данные `data/orders.csv`, **When** вычисляется метрика
   `выручка_30д`, **Then** наблюдаемый скаляр строго равен `300000.0` (< `3_000_000` → порог пробит).
2. **Given** те же фиксированные часы, **When** прогоняется путь, вычисляющий и проверяющий метрика-триггер,
   **Then** печатается одна человеко-читаемая строка explain срабатывания (снимок ↔ порог) в
   каноническом формате наблюдаемости и стартует инстанс `p-000001` процесса `эскалация_плана`.
3. **Given** golden-замок зафиксирован, **When** в реализации портят снимок метрики или строку
   срабатывания, **Then** замок падает (кусается при инверсии).
4. **Given** прежний дата-наивный golden эскалации дедлайна, **When** фича завершена, **Then** он
   заменён детерминированной формой под фиксированными часами (старый замок более не существует в
   прежнем виде).

### User Story 3 - Герметичный замок жизненного цикла «старт → задача → complete → эффект» (Priority: P2)

Пользователь должен иметь **дата-независимый** замок ручного жизненного цикла, который проходит
процессную половину §2 от старта до завершённого инстанса: ручной старт процесса → появляется задача
исполнителя → завершение задачи с payload `{"итог":"перезвонит"}` → исполняются авто-шаги догона →
печатается строка реального эффекта `[уведомление] crm: итог звонка: перезвонит` → инстанс переходит в
«выполнен». Дедлайн в выводе маскируется (дат в наблюдаемом эффекте нет → замок не плывёт по
календарю).

**Why this priority**: Закрывает процессную половину §2 (человек-в-цикле, payload, реальный эффект)
герметично и без зависимости от часов — дополняет дата-зависимый golden из US2. Чуть ниже приоритетом,
так как опирается на тот же расширенный пример, но проверяет ручной путь (`start`/`complete`),
а не метрика-driven.

**Independent Test**: Из корня репозитория во временной БД выполнить: старт процесса `эскалация_плана`
с аргументом → дождаться задачи `t-000001` → завершить её с `--данные '{"итог":"перезвонит"}'` →
проверить, что в выводе есть строка `[уведомление] crm: итог звонка: перезвонит` и `инстанс p-000001:
выполнен`; дедлайн в выводе замаскирован, дат нет. Сменить ключ payload или текст эффекта — замок
должен покраснеть.

**Acceptance Scenarios**:

1. **Given** временная БД и расширенный пример, **When** пользователь стартует процесс `эскалация_плана`
   с аргументом, **Then** создаётся человеческая задача `t-000001` для исполнителя шага
   `связаться_с_клиентом`.
2. **Given** открытая задача `t-000001`, **When** пользователь завершает её с payload
   `{"итог":"перезвонит"}`, **Then** исполняются авто-шаги (`зафиксировать_итог` читает `данные.итог`,
   `уведомить_crm` шлёт эффект), печатается строка `[уведомление] crm: итог звонка: перезвонит`, и
   инстанс `p-000001` переходит в статус «выполнен».
3. **Given** герметичный замок зафиксирован, **When** дедлайн маскируется во выводе, **Then** в
   наблюдаемой строке эффекта нет дат → замок дата-независим и детерминирован.

### User Story 4 - Терминальные гейты и сборка остаются зелёными (Priority: P1)

Сопровождающий должен быть уверен, что расширение примера и новые замки **не сломали** уже
существующие терминальные гейты сквозного сценария (end-to-end эскалация с реальным эффектом;
exactly-once доставка эффекта через рестарт демона) и не задели соседние golden'ы (старт/инспекция/
часы), и что весь набор сборки/проверок/форматирования/тестов из исходников проходит.

**Why this priority**: Регресс-страховка. Финализация без новой функциональности обязана сохранить
все ранее закреплённые инварианты; «зелёные гейты» — формальный критерий завершения.

**Independent Test**: Прогнать терминальные гейты (end-to-end эскалация + exactly-once на рестарте) и
golden'ы старта/инспекции/часов — все зелёные без правок. Прогнать полный набор сборки/анализа/
форматирования/тестов из исходников — exit 0.

**Acceptance Scenarios**:

1. **Given** расширенный пример и новые замки, **When** прогоняются терминальные гейты сквозного
   сценария (end-to-end эскалация с webhook-эффектом; exactly-once: реальный эффект доставлен ровно
   один раз через рестарт демона), **Then** оба зелёные и не переписаны.
2. **Given** добавленный источник/метрика в примере, **When** прогоняются golden'ы старта, инспекции
   и единых часов CLI, **Then** все зелёные без правок (они инстанцируют процесс по имени, минуя
   top-level метрику).
3. **Given** вся фича собрана, **When** прогоняется полный набор сборки, статического анализа,
   проверки форматирования и тестов из каталога исходников, **Then** все шаги завершаются успешно
   (exit 0), а сборочный бинарь и файлы БД не закоммичены.

---

### Edge Cases

- **Дата-зависимость окна:** под реальными часами снимок `выручка_30д` плывёт (окно `(d−30, d]`
  начиная с `2026-06-26` исключает единственный оплаченный заказ `2026-05-27` → значение уходит к
  `0.0`). Поэтому дата-зависимый golden обязан идти под фиксированными часами `{2026,6,15}`, а не под
  реальными — наивный прогон даёт сиюминутно-совпадающее значение, что является ложной страховкой.
- **Резолв пути к данным:** прежний golden эскалации ломается дважды от добавления источника —
  `data/orders.csv` не резолвится из рабочего каталога теста, и снимок дата-зависим; новый замок
  прогоняется из корня репозитория (или с абсолютным путём к данным во временном каталоге).
- **Серверная метрика на старте демона не порождает инстанс:** семантика серверного метрика-триггера —
  ребро «ложь→истина» (первый тик праймит без срабатывания), поэтому постоянно-истинное `< план`
  после прайма не стартует инстанс на boot; метрика-driven старт демонстрируется отдельным
  fire-if-true прогоном (US2), не серверным boot.
- **Payload-контракт авто-шага:** доступ к `данные.итог` сам по себе не падает (отсутствующее поле
  открытой записи даёт пустое значение), но шагом позже конкатенация `"итог звонка: " + итог` падает,
  если `итог` пуст → payload `--данные` с полем `итог`-строкой обязателен для осмысленного прохода
  догона.
- **Соседний clock-golden, прогоняющий догон:** один из golden'ов часов реально исполняет новые
  авто-шаги догона (несёт тот же payload); при смене имён шагов или ключа payload его необходимо
  перепроверить — иначе он покраснеет.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (W1)**: Пример `examples/контроль_плана.ladix` MUST быть расширен до полной §2-цепочки:
  CSV-источник `заказы` (`data/orders.csv`, тип `csv`, схема `поля:` с `дата_заказа`/`сумма_заказа`/
  `статус`) + окно-метрика `выручка_30д` (агрегат суммы по `сумма_заказа`, фильтр `статус == "оплачен"`,
  период `последние 30дн`, по дате `дата_заказа`). Целевое содержимое — копи-реди блок анкора §F-1.
- **FR-002 (W1)**: Файл MUST содержать связку-триггер `когда метрика выручка_30д < 3_000_000:
  запустить процесс эскалация_плана(значение)`, передающий снимок метрики как аргумент процесса.
- **FR-003 (W1)**: 3-шаговый процесс `эскалация_плана` MUST быть сохранён: человеческий шаг
  `связаться_с_клиентом` (исполнитель + срок), авто-шаг `зафиксировать_итог` (читает `данные.итог`),
  авто-шаг `уведомить_crm` (реальный эффект `уведомить crm`), плюс триггер эскалации дедлайна `когда
  задача просрочена`.
- **FR-004 (W1)**: Хардкод-литеральный старт (`пусть id = запустить процесс ...` со значением
  `2500000` + последующая `печать`) MUST быть удалён из примера; старт инстанса становится
  метрика-driven (через триггер FR-002) либо ручным внешним путём (`ladix start`).
- **FR-005 (W1)**: Расширенный `examples/контроль_плана.ladix` MUST парситься чисто (входит в набор
  «все примеры парсятся без диагностик»).
- **FR-006 (W2)**: MUST появиться новый детерминированный golden-замок **T-GOLD-METRIC** под
  фиксированными часами `{2026,6,15}`, прогоняемый из корня репозитория, который пинит три фасета
  **разными путями**: (i) скаляр метрики `выручка_30д = 300000.0` (метрика-путь); (ii) человеко-читаемую
  строку explain срабатывания метрика-триггера и (iii) метрика-driven старт инстанса `p-000001`
  процесса `эскалация_плана` (run-путь, вычисляющий и проверяющий триггеры). Один метрика-путь все три
  фасета НЕ закрывает — требуются оба пути.
- **FR-007 (W2)**: Строка explain MUST соответствовать каноническому формату наблюдаемости «почему
  сработал триггер» (снимок ↔ порог, оператор сравнения); точные байты снимаются с живого бинаря на
  этапе реализации.
- **FR-008 (W2)**: T-GOLD-METRIC MUST **заменить** существующий дата-наивный golden эскалации дедлайна
  (`TestCLIGoldenDeadlineEscalation`), который ломается от добавления источника (нерезолвимый путь
  данных + дата-зависимый снимок); прежний замок не должен сохраняться в исходной форме.
- **FR-009 (W3)**: MUST появиться новый герметичный, дата-независимый замок жизненного цикла
  **T-LIFECYCLE** в `src/cmd/ladix/quickstart_smoke_test.go`, который из корня репозитория во временной
  БД проходит: ручной старт `эскалация_плана` → задача `t-000001` → завершение с
  `--данные '{"итог":"перезвонит"}'` → исполнение авто-шагов → строка эффекта `[уведомление] crm:
  итог звонка: перезвонит` → `инстанс p-000001: выполнен`. Дедлайн в выводе MUST маскироваться (дат в
  наблюдаемом эффекте нет).
- **FR-010 (W2/W3)**: Оба новых замка (T-GOLD-METRIC, T-LIFECYCLE) MUST «кусаться» при инверсии:
  срыв снимка метрики, строки explain или строки эффекта приводит к падению соответствующего замка
  (доказуемо мутпробой).
- **FR-011 (W4)**: Терминальные гейты `TestM2GoldenEndToEnd` (end-to-end эскалация + webhook POST) и
  `TestStepEffectExactlyOnceRestart` (реальный эффект доставлен ровно один раз через рестарт демона)
  MUST оставаться зелёными и НЕ переписываться.
- **FR-012 (W4)**: Golden'ы старта (`start_golden_test.go`), инспекции (`inspect_golden_test.go`) и
  единых часов CLI (`clock_unify_test.go`) MUST оставаться зелёными без правок; при этом замок часов,
  реально прогоняющий авто-шаги догона, MUST быть перепроверен на согласованность имён шагов и ключа
  payload.
- **FR-013 (W5)**: Полный набор `go build/vet ./...`, `gofmt -l .`, `go test ./...` из каталога `src/`
  MUST проходить успешно (exit 0); сборочный бинарь и файлы БД не должны быть закоммичены.
- **FR-014 (детерминизм)**: Все новые golden MUST быть детерминированы — на фиксированных часах и
  фиксированных данных (`data/orders.csv`); дата-зависимые проверки пинятся фиксированными часами, а не
  текущей датой; дедлайны маскируются.
- **FR-015 (граница)**: Эта фича MUST НЕ вводить новую языковую функциональность, новые ключевые слова,
  коды ошибок, встроенные функции или зависимости; продакшн-логика движка/хранилища/интерпретатора не
  меняется (правки — только пример, заменяемый/новые тест-замки). Сохранность несущих швов

### Key Entities *(include if feature involves data)*

- **Источник `заказы`**: CSV-коннектор поверх `data/orders.csv` со схемой полей `дата_заказа` (Дата),
  `сумма_заказа` (Дробное), `статус` (Строка); общая фикстура с `выручка_30д.ladix`.
- **Метрика `выручка_30д`**: скользящее окно `последние 30дн` по дате `дата_заказа`; агрегат — сумма
  `сумма_заказа` при `статус == "оплачен"`; под фиксированными часами `{2026,6,15}` снимок = `300000.0`.
- **Метрика-триггер (связка)**: `когда метрика выручка_30д < 3_000_000` → запускает процесс
  `эскалация_плана`, передавая снимок (`значение`) как аргумент; при срабатывании печатает строку
  explain «почему».
- **Процесс `эскалация_плана`**: человеческий шаг `связаться_с_клиентом` (исполнитель + срок) → авто-шаг
  `зафиксировать_итог` (читает payload `данные.итог`) → авто-шаг `уведомить_crm` (реальный эффект); плюс

- **Задача**: человеческая единица работы `t-000001`, порождаемая человеческим шагом; завершается
  пользователем с payload.
- **Payload**: объект `--данные '{"итог":"перезвонит"}'`, передаваемый при завершении задачи; поле
  `итог` (строка) читается авто-шагом и конкатенируется в текст эффекта.
- **Реальный эффект**: `уведомить crm("итог звонка: " + итог)` → наблюдаемая строка `[уведомление] crm:
  итог звонка: перезвонит`; через рестарт демона доставляется exactly-once (outbox).
- **Инстанс процесса**: `p-000001`, порождаемый метрика-триггером (US2) или ручным стартом (US3);
  терминальный статус — «выполнен».
