# Contract — Диагностики (007b): новая семош формата `"ЧЧ:ММ"`

**Anchor**: §TR-11 п.3 (формат `"ЧЧ:ММ"` отложен в 007b, ложится аддитивно), FR-014, SC-005.
Единственная новая диагностика 007b. Реестр диагностик 007a **НЕ меняется** (FR-026).

> Тексты 007a (TR-VAL-CTX/TR-EVT-CTX/TR-MET-UNDECL/TR-MET-NOTMETRIC/SE-TRIGGER-KIND/SE-EXPECT-COMPOP/
> SE-SCHEDULE-SPEC) — **неизменны**. 007b добавляет **ровно одну** семантическую диагностику.

## SE-TIME-FORMAT (новая, 007b) — невалидный формат строки `в "ЧЧ:ММ"`

- **Стадия**: семантическая (`СемантическаяОшибка`/`semErr`, errors.СемантическаяОшибка).
- **Место**: `eval/analyze.go`, `checkTrigger`, ветка `*ast.AtSchedule` — **точно та точка**, где 007a
  явно отложил проверку (analyze.go:223 «содержимое строки "ЧЧ:ММ" НЕ анализируется … → 007b»).
- **Позиция** (Принцип IV, руны, с 1): токен строкового литерала `AtSchedule.At` (его `Pos()` уже в
  AST 007a, ast/trigger.go:96–101). Печатает строку И колонку.
- **Двухстрочный канон** (Принцип VIII, §13): `Ошибка в строке N, колонка M:\n<текст>`.

### Правила валидации (FR-014, SC-005)

Строка `s := AtSchedule.At.Value` валидна ⟺ **все**:
1. ровно 5 рун, форма `ЧЧ:ММ` (руна[2] == `:`);
2. руны [0],[1],[3],[4] — десятичные цифры (обязательные ведущие нули);
3. часы `ЧЧ` ∈ 00–23;
4. минуты `ММ` ∈ 00–59.

Проверка **посимвольная (руны)**, **без regex** (Принцип II). Нарушение любого пункта → SE-TIME-FORMAT.

| Вход | Результат |
|---|---|
| `"09:05"`, `"00:00"`, `"14:30"`, `"23:59"` | валидно (тело валидируется штатно) |
| `"25:99"` | SE-TIME-FORMAT (часы>23, минуты>59) |
| `"9:05"` | SE-TIME-FORMAT (нет ведущего нуля часов / длина≠5) |
| `"09:5"` | SE-TIME-FORMAT (нет ведущего нуля минут / длина≠5) |
| `"9:5"`, `"24:00"`, `"12:60"`, `"ab:cd"`, `"12-30"`, `"012:30"`, `""` | SE-TIME-FORMAT |

### Текст диагностики (импл-факт — фиксируется дословно при реализации)

§TR-11 оставляет точный текст импл-проходу (как §TR-6.4 в 007a оставлял строку-заглушку). Текст
ОБЯЗАН быть русским, по канону §13, и закрепляется exact-match golden-тестом в момент написания кода.
Рекомендуемая форма (стиль зеркалит существующие semErr-тексты analyze.go, напр. «'%s' — не метрика»):

```
расписание 'в': неверный формат времени '<строка>', ожидается "ЧЧ:ММ" (часы 00–23, минуты 00–59)
```

(Финальная формулировка утверждается при реализации; этот контракт фиксирует ПРАВИЛА и МЕСТО, не
обязывает к точной строке — она становится каноном через golden-тест.)

### Когда срабатывает

При **подъёме демона** `serve` — на семпроходе `interp.Analyze(prog)` ДО старта тикера (serve-command.md
шаг 3). exit 1. Демон не стартует. В `run` эта диагностика тоже сработает, **только** если файл
содержит `когда расписание в "...":` — но 007a уже валидирует всё тело триггера на семпроходе, а
формат строки был отложен; добавление SE-TIME-FORMAT в `analyze.go` означает, что и `run`, и `serve`
теперь отвергают невалидный формат. Это **аддитивно** (§TR-11 п.3) и не меняет прочее поведение `run`
(FR-026): программа 007a без `в "невалидно"` остаётся валидной.

> Тонкость регресса: если в существующих 007a-тестах/примерах есть `в "невалидная строка"` с
> ожиданием parse-clean/semantic-clean — такой замок инвертируется (теперь это SE-TIME-FORMAT). Аудит
> примеров/тестов на наличие невалидных `"ЧЧ:ММ"` — задача фазы E (см. plan.md / quickstart.md).

## Инвариант границы (FR-026, §TR-11)

- Синтаксис трёх форм триггера — НЕ меняется (узел `AtSchedule` синтаксически принимает любую строку).
- AST-узлы 007a — НЕ меняются.
- Реестр диагностик 007a — НЕ меняется (7 текстов 007a дословно те же).
- Добавляется РОВНО одна семош (SE-TIME-FORMAT). Программа, валидная в 007a и не содержащая
  невалидного `"ЧЧ:ММ"`, остаётся валидной в 007b без правок.
