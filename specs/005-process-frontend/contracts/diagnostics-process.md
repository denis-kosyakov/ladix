# Contract: Реестр диагностик слоя процессов (§PM-6)

**Feature**: 005-process-frontend | **Источники**: docs/process-model.md §PM-6 (байт-точный реестр),
§PM-2 (формы узлов), §PM-3 (переход парсера), §PM-4 (семпроход `Analyze`), §PM-5 (граница deferred);
spec.md FR-006/FR-007/FR-010..FR-015/FR-018/FR-019/FR-024/FR-025, SC-001/SC-002/SC-003. Решения
**D-3** (категория `СемантическаяОшибка`, **не** `errors.ОшибкаПроцесса`), **D-5** (общий namespace +
шаги локальны), **D-8** (дубль атрибута — парсер, `p.error`+`break`), **D-9** (процессные builtins
остаются deferred-builtins), **D-10** (запуск: семпроход резолвит арность, исполнение — рантайм),
**D-11** (атрибуты шага не обходятся семпроходом), **D-13** (дубль параметра процесса не проверяется).

**Это главный контракт фичи 005.** Тексты — exact-match канон для слоя процессов (тесты
семпрохода/парсера сверяют **байт-в-байт**, SC-001/002/003). Соглашения `eval-model §8.3`/`§SM-9`:
payload **без** завершающей точки; одинарные `'…'` — для идентификаторов/ключевых слов/имён; `N`
нумеруется **с 1**; позиция = строка/колонка (в рунах, с 1; конституция IV). Все сообщения слоя
процессов оборачиваются в канонический **двухстрочный** формат вывода (§DP-0). При расхождении с
`SPEC §13.4`/`§7.4` для текстов нового слоя побеждает §PM-6 (репрезентативность `SPEC` — §PM-6 нота).

## DP-0. Двухстрочный формат вывода (конституция VIII, §8.1)

Каждое сообщение ниже — это **payload** (полезная нагрузка, вторая строка). Вывод на пользователя —
ровно две строки, как у всех ошибок 001–004:

```
Ошибка в строке N, колонка M:
<payload>
```

- Строка 1 — `Ошибка в строке N, колонка M:` (заголовок с позицией `Pos()` соответствующего узла/
  токена; формируется типом ошибки `Error()`, **не** входит в реестр payload'ов §PM-6).
- Строка 2 — payload **дословно** из таблиц §DP-1..§DP-4 (без завершающей точки).
- Категория ошибки определяет тип Go и стадию: `ОшибкаРазбора` (парсер, стадия 2),
  `СемантическаяОшибка` (`semErr`, стадия 3). **Новый тип ошибки в 005 не вводится** (D-3): процессные
  диагностики переиспользуют существующие `errors.ОшибкаРазбора` / `errors.СемантическаяОшибка`.
  `errors.ОшибкаПроцесса` — категория **исполнения** (движок 006), фронтенд её **не** порождает.

> **Граница payload vs позиция.** Реестр фиксирует **только** payload (вторую строку). Привязка
> позиции (`Pos()`) указана в колонке «позиция» каждой таблицы — её сверяют отдельным полем теста
> (`got.Pos == want.Pos`), не байт-сравнением строки.

## DP-1. §PM-6.A — Структура объявления (`ОшибкаРазбора`, парсер, стадия 2)

Эмитятся парсером `parseProcessDecl`/`parseStepDecl` (§PM-3) при разборе блоков процесса/шага и
атрибутов. **Все три текста — переиспользование** уже существующих хелперов (`parser/errors.go`),
ничего нового не вводится (FR-006/FR-007).

| Payload (дословно) | Условие-триггер | Хелпер | Позиция (`Pos()`) | Решение |
|---|---|---|---|---|
| `атрибут '<имя>' уже задан` | повтор `исполнитель:`/`срок:` в одном шаге; `<имя>` = лексема ключевого слова (`исполнитель`/`срок`) | `msgDuplicateAttr` (`errors.go:29`, переиспользуется из 004 §SM-9.A) | токен **повторного** атрибута (`attrTok.Pos`) | **D-8** (парсер `p.error`+`break`, строго как `parseMetricDecl` `parse_decl.go:129-134`) |
| `пустой блок не допускается, добавьте хотя бы один оператор` | блок процесса (`процесс P:` без шагов) **или** блок шага (`шаг A:` без строк) — нет `INDENT` после `:`/NEWLINE | `msgEmptyBlock` (`errors.go:17`, переиспользуется) | позиция, где ожидался `INDENT` (как `openAttrBlock`) | FR-007 |
| `неожиданный токен '<лексема>'` | не-`шаг` строка в блоке процесса (`процесс P:`⏎`  печать(1)`); также `когда` на top-level (триггер 007); `<лексема>` = текст ведущего токена строки | `msgUnexpected` (`errors.go:45`, переиспользуется) | ведущий токен строки (`peek().Pos`, до `advance`) | §PM-3 шаг 6 (backstop), §PM-0 (007-граница для `когда`) |

**Тонкости (§PM-3):**
- **«Неизвестного атрибута» в шаге НЕТ** (в отличие от `metric`): любая не-`исполнитель`/`срок`
  строка трактуется как `Statement`. Например `foo: bar` → `foo` разбирается как выражение-оператор,
  затем `:` — неожиданный токен в `parseExprStatement`/`parsePrimary` (общий `SE-UNEXPECTED`, **не**
  входит в реестр процессов).
- `после` без имени (`шаг A после :`) → парсер даёт **`SE-EXPECTED`** от `expect(IDENT, "имя шага")`
  (общий текст `msgExpected`, реестр 002 — **не** новый текст слоя процессов); `After` остаётся пуст,
  восстановление — штатный `synchronize`. См. §PM-7 негатив.
- Дубль **параметра** процесса (`процесс P(x, x):`) — **не** диагностируется (D-13, позиционное
  связывание как `FunctionDecl`); новый текст не вводится.

## DP-2. §PM-6.B — Семантика процесса/шага (`СемантическаяОшибка`, семпроход, стадия 3)

Эмитятся `Analyze` (Шаг 1 регистрация + Шаг 1c `checkProcessDecl`, §PM-4). Категория — `semErr`
(`СемантическаяОшибка`, D-3). Первые три текста — **переиспользование** общих диагностик
регистрации/резерва (как источник/метрика, D-5); остальные шесть — **новые** тексты слоя.

| Payload (дословно) | Условие-триггер | Позиция (`Pos()`) | Источник текста |
|---|---|---|---|
| `'<имя>' уже объявлено в строке N` | повтор имени процесса в общем глобальном namespace (делит с функцией/источником/метрикой); `N` — строка первого объявления | `d.Name.Pos()` процесса-дубля | переиспользование (общий, как источник/метрика) — D-5, FR-010 |
| `имя '<имя>' зарезервировано встроенной функцией` | имя процесса = имя встроенной (`checkReservedDeclName`) | `d.Pos()` процесса | переиспользование (`checkReservedDeclName`, как источник/метрика) — D-5 |
| `имя '<имя>' зарезервировано предопределённым периодом` | имя процесса = предопределённый период (`value.PeriodNames`) | `d.Pos()` процесса | переиспользование (`checkReservedDeclName`) — D-5 |
| `шаг '<имя>' уже объявлен в строке N` | дубль имени шага внутри процесса (свой namespace, D-5); `N` — строка первого шага с этим именем | `step.Name.Pos()` шага-дубля | **новый** — FR-011 |
| `шаг '<S>' после '<X>', но шаг '<X>' не объявлен` | имя `X` из `после` шага `S` не среди имён шагов этого процесса | `Xident.Pos()` (имя X в `After`) | **новый** — FR-012, D-4 |
| `шаг '<S>' после '<X>', но '<X>' объявлен позже` | `X` найден на индексе `j >= i` (forward-ссылка или self-ссылка) — нарушение «ссылка строго назад» | `Xident.Pos()` (имя X в `After`) | **новый** — FR-012, D-4 |
| `шаг '<имя>': срок без исполнитель не имеет эффекта` | `Attrs.DeadlinePos.Line != 0` И `Attrs.AssigneePos.Line == 0` | `step.Attrs.DeadlinePos` (строка `срок:`) | **новый** — FR-013, §11.4 |
| `действие '<имя>' допустимо только в шаге процесса` | `присвоить`/`вызвать`/`уведомить` вне тела шага (`inStep == false`); `<имя>` = `присвоить`/`вызвать`/`уведомить` (`constructName(st)`) | `st.Pos()` (ведущий токен действия) | **новый** — FR-014, контекст-гард |
| `'вернуть' допустимо только внутри функции; в шаге процесса используйте 'присвоить'` | `вернуть` в теле шага (`!inFunction && inStep`); базовый текст 003 + уточнение для шага | `st.Pos()` (токен `вернуть`) | **новый** (двухконтекстный) — FR-015, §7.3 |

**Тонкости (§PM-4):**
- `действие '<имя>' допустимо только в шаге процесса` — `<имя>` берётся из существующего
  `constructName(st)` (`interpreter.go:146-163`), который уже отображает `AssignAction`→`присвоить`,
  `CallAction`→`вызвать`, `NotifyAction`→`уведомить`. **В шаге** (`inStep == true`) действие валидно
  → `return nil`; payload (`Args`/`Value`) **не** обходится (D-11), исполнение — рантайм-deferred
  (`stmt.go:64`, **недостижимо в 005**, §PM-5).
- `'вернуть' …` — единственный **двухконтекстный** текст: вне функции и вне шага даёт **только**
  базовую часть `'вернуть' допустимо только внутри функции` (текст 003, **не** в реестре слоя
  процессов); в шаге (`inStep == true`) к ней дописывается `; в шаге процесса используйте 'присвоить'`.
  Реестр §PM-6.B фиксирует **полную** форму (шаговый контекст).
- `прервать`/`продолжить` в шаге — работают по `loopDepth` (внутри `пока`/`для` шага валидны;
  вне цикла — общий текст 003, **не** слой процессов).
- **Дубль шаг-локальных `пусть`/`для`** в теле шага → общий текст регистрации переменных
  `'<имя>' уже объявлено в строке N` (через `collectVars`, как тело функции, D-12) — **не** новый
  текст слоя. `пусть x` с именем **параметра** процесса в шаге — **разрешён** (теняет, §6.4;
  `letLine` параметрами не засевается, D-12) → диагностики нет.

## DP-3. §PM-6.C — Запуск процесса (`СемантическаяОшибка`, семпроход §7.4, стадия 3)

Эмитятся `checkRunProcess(r, vars)` (§PM-4, заменяет безусловный `deferredConstruct` на
`analyze.go:330-331`). Имя резолвится **только** против реестра процессов `i.processes` (синтаксис
`запустить процесс Ident`, **не** против переменных, в отличие от `CallExpr` — D-10). Все четыре
текста — **новые** тексты слоя. Категория — `semErr`. **Исполнение** `запустить процесс` остаётся
рантайм-deferred (D-10, §DP-4) — семпроход проверяет **только** существование процесса и **арность**.

| Payload (дословно) | Условие-триггер | Позиция (`Pos()`) | Решение |
|---|---|---|---|
| `'<P>' принимает N аргументов, передано M` | `P ∈ i.processes`, но `len(Args) != len(Params)`; `N` = арность процесса, `M` = число переданных | `r.Pos()` (токен `запустить`) | D-10, FR-018 (формат как у функций, §8.3) |
| `'<P>' — функция, не процесс` | `P ∈ i.funcs` (пользовательская функция, не процесс) | `r.Pos()` (токен `запустить`) | D-10, FR-018 |
| `'<P>' — не процесс` | `P ∈ i.metrics` **или** `P ∈ i.sources` (метрика/источник, не процесс) | `r.Pos()` (токен `запустить`) | D-10, FR-018 |
| `процесс '<P>' не объявлен` | `P` нигде не объявлен как процесс (включая имя **встроенной** — ветка builtins НЕ проверяется) | `r.Pos()` (токен `запустить`) | D-10, FR-018, §PM-4 |

**Порядок проверок в `checkRunProcess` (fail-fast, §PM-4):**
1. Аргументы — `checkExpr(a, vars)` для каждого `a ∈ r.Args` (args-first, как `checkCall`); ошибка
   аргумента возвращается **до** проверки имени/арности.
2. `P ∈ i.processes` → проверка арности (`'<P>' принимает N аргументов, передано M`) или `nil` (ок).
3. Иначе `P ∈ i.funcs` → `'<P>' — функция, не процесс`.
4. Иначе `P ∈ i.metrics` → `'<P>' — не процесс`.
5. Иначе `P ∈ i.sources` → `'<P>' — не процесс`.
6. Иначе → `процесс '<P>' не объявлен`.

**Тонкость (§PM-4):** имя встроенной после `запустить процесс` (`запустить процесс печать(...)`) —
`i.builtins` в `checkRunProcess` **НЕ** проверяется (в отличие от `checkCall`); падает в общий
`процесс '<P>' не объявлен`. Осознанно (редкий ввод; имя не зарезервировано под запуск) — ветку
builtins **не** добавлять.

## DP-4. §PM-6.D — Deferred-тексты eval-слоя (`eval-model §8.3`) — рантайм И семантика

**Не новые тексты 005** — это существующий `eval-model §8.3` (`конструкция <X> …`,
`функция '<имя>' …`), перечислены здесь **для полноты границы deferred** (§PM-5). Механизм
`i.deferredConstruct(node)` (`interpreter.go:146`) даёт `СемантическаяОшибку`
`конструкция <X> не поддерживается в этой версии` и вызывается из ДВУХ мест: семпроход
(`analyze.go`) и рантайм (`stmt.go:64`, `expr.go:49-51`). Deferred-builtin даёт
`функция '<имя>' не поддерживается в этой версии` из `checkCall` (семантика).

| Payload (дословно) | Конструкция | Стадия (где deferred в 005) | Решение |
|---|---|---|---|
| `конструкция присвоить не поддерживается в этой версии` | `присвоить` **в шаге** при исполнении | **рантайм** (`stmt.go:64`) — **недостижимо в 005** (тело шага не исполняется, §PM-5; ветка активируется движком 006) | §PM-5, D-1 |
| `конструкция вызвать не поддерживается в этой версии` | `вызвать` **в шаге** при исполнении | **рантайм** (`stmt.go:64`) — недостижимо в 005 | §PM-5 |
| `конструкция уведомить не поддерживается в этой версии` | `уведомить` **в шаге** при исполнении | **рантайм** (`stmt.go:64`) — недостижимо в 005 | §PM-5 |
| `конструкция запустить процесс не поддерживается в этой версии` | `запустить процесс P(...)` при исполнении (после чистого семпроха) | **рантайм** (`expr.go:49`) — **наблюдаемая** граница 005 (top-level запуск) | D-10, §PM-5, FR-025 |
| `конструкция литерал длительности не поддерживается в этой версии` | `DurationLit` (`2дн`) в **обходимой** семпроходом позиции (`присвоить x = 2дн`, тело функции, глобаль) | **семантика** (`analyze.go:332-333`, без изменений) — в `срок:` **недостижимо** (атрибут не обходится, D-11) | D-11, §PM-0 (известное ограничение) |
| `функция '<имя>' не поддерживается в этой версии` | deferred-builtin `статус_процесса`/`состояние_процесса`/`задачи_пользователя` | **семантика** (`checkCall`, без изменений) | D-9, FR-024 |

**Что НЕ меняется в eval (рантайм-deferred остаётся до 006):** `stmt.go:64`
(`AssignAction`/`CallAction`/`NotifyAction` → `deferredConstruct`), `expr.go:49-51`
(`RunProcessExpr`/`DurationLit` → `deferredConstruct`). Эти строки уже верны для 005 — **НЕ трогать**
(границы scope, §PM-5/§PM-8). `constructName` (`interpreter.go:146-163`) уже отображает все типы
действий и `запустить процесс`/`литерал длительности` — **изменения не требуются**.

> **Почему `статус_процесса` остаётся семантическим (D-9), а `запустить процесс` уходит в рантайм
> (D-10).** `функция '<имя>' не поддерживается` — установленный контракт §8.3 для deferred-builtins
> (003); перенос в рантайм потребовал бы менять механизм builtin и ломать регресс-тесты
> (`TestBuiltinDeferredAll`) — вне scope 005. `запустить процесс` — reserved-узел (не builtin), его
> deferred уже двусторонний; убрать семантическую сторону дёшево и даёт «парс+сем чисто» (Q2=A).

## DP-6. Синк-каноны документов (моя зона, §PM-6 нота)

- `SPEC §13.4` (Семантическая-строка) пополняется текстами §DP-2/§DP-3 (§PM-6.B/C).
- `SPEC §7.4` — заменяется текстами §DP-3 (§PM-6.C) **вместо** текущих `…параметров… в строке L` /
  `…не найдено.` (репрезентативные → байт-точные).
- `SPEC §13.4`/`§7.4` — **репрезентативны** (не exact-match); при расхождении побеждает §PM-6 / этот
  контракт. `eval-model §8.3` — exact-match источник §DP-4 (не дублируется, не переписывается).
