# Feature Specification: Фронтенд триггеров и метрика-fire-if-true в `run` (007a)

**Feature Branch**: `007a-trigger-frontend`

**Created**: 2026-06-12

**Status**: Draft

**Input**: Реализовать фронтенд всех трёх форм триггера `когда …` (метрика / событие / расписание) — парсинг и семантику — плюс одну точку исполнения: метрика-триггер срабатывает разово в команде `run` по принципу fire-if-true. Демон `serve`, события/`emit`/очередь, edge-детект, персист состояния триггеров, исполнение расписания и рестарт-скан — вне scope (фича 007b).

> **Источник истины** — `docs/trigger-model.md` (§TR-0…§TR-11). Спецификация выведена из якоря и не вводит требований сверх него; при любом расхождении источников для слоя 007a побеждает якорь.

## User Scenarios & Testing *(mandatory)*

Пользователь — **автор `.ladix`-файла** (описывает метрики, процессы и триггеры) и **оператор CLI** (запускает `ladix run`). Система — **тулчейн Ladix** (лексер → парсер → семантический проход → исполнение команды `run`).

### User Story 1 — Объявить триггер в трёх формах и статически его проверить (Priority: P1)

Автор `.ladix` объявляет на верхнем уровне триггер `когда <спец>:` с индентным телом в одной из трёх форм:

- `когда метрика <имя> <сравнение> <выражение>:` — метрика-триггер с **ровно одним** сравнением;
- `когда событие <имя>:` — событие-триггер;
- `когда расписание (каждые <длительность> | в "<строка>"):` — расписание-триггер.

Тулчейн принимает все три формы лексером, парсером и семантическим проходом единообразно. В теле метрика-триггера доступно предопределённое имя `значение`, в теле событие-триггера — `событие` (и доступ `событие.поле`). Тело переиспользует императивное ядро языка (`пусть`/`если`/`пока`/`для`/`печать`/выражения/`запустить процесс`). Семантический проход резолвит метрику в условии, проверяет контекст `значение`/`событие`, арность `запустить процесс` и запрещает действия-шага. Автор получает раннюю диагностику ещё до исполнения.

**Why this priority**: Это фундамент фичи — без распознавания и валидации трёх форм нечего исполнять и не на что вешать fire-if-true. Синтаксис и диагностики фиксируются здесь **навсегда**: программа, валидная в 007a, остаётся валидной в 007b без правок. Поэтому P1.

**Independent Test**: Прогнать `examples/выручка.ladix` (метрика-триггер с условием `< 3_000_000` и телом `запустить процесс разбор_падения(значение)`) → exit 0, ноль диагностик (раньше падал на `неожиданный токен 'когда'`). Дописать `когда событие заявка_создана:` и `когда расписание каждые 1дн:` → по-прежнему exit 0. Заменить единицу на `каждые 1нед` / `каждые 1мес` → всё ещё exit 0. Поставить `значение` на верхнем уровне вне триггера → `неожиданный токен 'значение'`, exit 1.

**Acceptance Scenarios**:

1. **Given** файл с `когда метрика просрочка > 5:` и телом из одной строки `запустить процесс разбор(значение)`, где `просрочка` — объявленная метрика, `разбор` — процесс с одним параметром, **When** файл разбирается и проходит семантическую проверку, **Then** ошибок нет, exit 0.
2. **Given** файл с `когда событие заявка_создана:` и телом `запустить процесс обработать(событие.клиент)`, где `обработать` — процесс с одним параметром, **When** файл разбирается и проходит семантическую проверку, **Then** ошибок нет, exit 0 (выражение `событие` и доступ `событие.поле` принимаются в теле событие-триггера).
3. **Given** файл с `когда расписание каждые 1дн:` и телом `запустить процесс ежедневный_отчёт()`, **When** файл разбирается и проходит семантическую проверку, **Then** ошибок нет, exit 0; та же программа с `каждые 1нед`, `каждые 1мес`, `каждые 5мин`, `каждые 1час`, `каждые 30сек` тоже даёт exit 0 (все 6 единиц длительности приняты без ограничений).
4. **Given** файл с `когда расписание в "25:99":` и непустым телом, **When** файл разбирается и проходит семантическую проверку, **Then** ошибок нет, exit 0 — содержимое строки времени в 007a не валидируется (любая строка принимается).
5. **Given** файл с `когда метрика просрочка > 5:` без тела (после `:` нет ни одного оператора), **When** идёт разбор, **Then** синтаксическая ошибка `пустой блок не допускается, добавьте хотя бы один оператор`, exit 1.

### User Story 2 — Запустить процесс из метрики через fire-if-true в `run` (Priority: P1)

Оператор CLI запускает `ladix run <файл>`. После исполнения всех конструкций верхнего уровня и до печати сводки висящих задач тулчейн делает **одноразовый** проход по метрика-триггерам в порядке их объявления в файле. Для каждого вычисляется значение метрики и порог (правая часть), применяется сравнение. Если условие истинно — в среду тела инжектируется `значение` (= вычисленное число метрики), исполняется тело, и `запустить процесс …` создаёт инстанс процесса, который штатно продвигается до первой человеческой задачи и попадает в сводку открытых задач того же прогона. База триггера считается **ЛОЖЬ эфемерно** (только в памяти прогона); durable-состояние триггеров не читается и не пишется даже под `--db`, поэтому повторный `run` того же файла на той же БД снова срабатывает с тем же результатом.

**Why this priority**: Это единственное наблюдаемое снаружи исполнение триггера в 007a и единственный мост «декларатив → процесс» без демона — именно он даёт демонстрируемость фичи. Зависит от US1 (формы должны парситься и валидироваться), но является ядром ценности, поэтому P1.

**Independent Test**: Прогнать `ladix run` на детерминированной фикстуре, где метрика без окна = 2 000 000, а триггер `когда метрика выручка_всего < 3_000_000:` запускает `разбор_падения(значение)`. Условие истинно при любой дате → процесс стартует, `значение` = 2 000 000 передаётся в процесс, в сводке открытых задач видна задача первого шага. Повторный `run --db <та же БД>` даёт тот же результат.

**Acceptance Scenarios**:

1. **Given** детерминированная фикстура: метрика без `период:`/`по_дате:` со значением 2 000 000 и триггер `когда метрика выручка_всего < 3_000_000:` с телом `запустить процесс разбор_падения(значение)`, **When** запускается `ladix run <файл>`, **Then** exit 0; условие `2 000 000 < 3 000 000` истинно → процесс `разбор_падения` запущен с аргументом 2 000 000, инстанс получает id формата `p-NNNNNN`, в сводке открытых задач видна задача первого шага; вывод детерминирован и не зависит от `сегодня()`.
2. **Given** тот же файл, но порог изменён на `< 1_000_000`, **When** запускается `ladix run <файл>`, **Then** exit 0; условие `2 000 000 < 1 000 000` ложно → тело не исполняется, `значение` не инжектируется, процесс не запускается, сводка задач пуста (базовый контракт — молчание).
3. **Given** файл с метрика-триггером, истинным условием и запуском процесса, исполняемый дважды подряд с `--db <файл.db>`, **When** `ladix run --db <файл.db> <файл>` запускается повторно, **Then** оба прогона срабатывают одинаково — инстанс/задачи персистятся в SQLite штатно (как в 006), но состояние самих триггеров не пишется/не читается, поэтому второй прогон снова видит «база = ЛОЖЬ» и снова создаёт инстанс.
4. **Given** файл с тремя триггерами в порядке: метрика-триггер (истинный), событие-триггер `когда событие X:`, расписание-триггер `когда расписание каждые 1дн:`, **When** запускается `ladix run <файл>`, **Then** метрика-триггер исполняется и печатает вывод тела + запуск процесса; для событие- и расписание-триггеров печатается ровно одна строка-заглушка со смыслом «требует serve (фича 007b)»; всё в порядке объявления; сводка открытых задач — последней.

### User Story 3 — Получать точные диагностики и негативы фронтенда триггеров (Priority: P2)

Автор `.ladix`, нарушивший правила триггеров, получает **байт-точную** диагностику с позицией (строка/колонка) и кодом выхода 1. Семантический проход ловит: `значение` вне тела метрика-триггера; `событие` вне тела событие-триггера; неизвестную метрику в условии; неверную арность `запустить процесс` и резолв имени не-в-процесс; действия-шага (`присвоить`/`вызвать`/`уведомить`) в теле триггера; `вернуть` в теле триггера (оно не функция). Парсер ловит отсутствие вида триггера после `когда`, отсутствие оператора сравнения после `метрика <имя>`, отсутствие `каждые`/`в` после `расписание`, а также `{`/`}` и `значение` на верхнем уровне.

**Why this priority**: Это гарды и негативы — обвязка фундамента US1/US2. Без US1/US2 проверять нечего, поэтому P2. Тексты диагностик становятся критериями приёмки и должны воспроизводиться байт-точно.

**Independent Test**: `значение` в тело событие-триггера → `выражение 'значение' допустимо только в теле триггера метрики`, exit 1. `событие` в тело метрика-триггера → `выражение 'событие' допустимо только в теле триггера события`, exit 1. `когда метрика неведомая > 5:` для необъявленного имени → `метрика 'неведомая' не объявлена`, exit 1. Запуск процесса с неверной арностью → `'<P>' принимает N аргументов, передано M`, exit 1. `присвоить x = 1` в теле триггера → `действие 'присвоить' допустимо только в шаге процесса`, exit 1.

**Acceptance Scenarios**:

1. **Given** тело событие-триггера или расписание-триггера, содержащее выражение `значение`, **When** идёт семантическая проверка, **Then** ошибка `выражение 'значение' допустимо только в теле триггера метрики` с позицией токена `значение`, exit 1.
2. **Given** тело метрика-триггера или расписание-триггера, содержащее выражение `событие` (или `событие.поле`), **When** идёт семантическая проверка, **Then** ошибка `выражение 'событие' допустимо только в теле триггера события` с позицией токена `событие`, exit 1.
3. **Given** `когда метрика неизвестное_имя > 5:`, где `неизвестное_имя` нигде не объявлено как метрика, **When** идёт семантическая проверка, **Then** ошибка `метрика 'неизвестное_имя' не объявлена` с позицией имени, exit 1.
4. **Given** `запустить процесс P(a, b)` в теле триггера, где процесс `P` объявлен с одним параметром, **When** идёт семантическая проверка, **Then** ошибка `'P' принимает 1 аргументов, передано 2`, exit 1; для необъявленного `P` → `процесс 'P' не объявлен`; для функции `P` → `'P' — функция, не процесс`; для метрики/источника `P` → `'P' — не процесс`.
5. **Given** тело любого триггера, содержащее действие-шага `присвоить`/`вызвать`/`уведомить`, **When** идёт семантическая проверка, **Then** ошибка `действие '<имя>' допустимо только в шаге процесса` (`<имя>` = конкретное действие), exit 1.
6. **Given** `когда` без вида триггера (например `когда нечто:`), либо `метрика M` без оператора сравнения, либо `расписание` без `каждые`/`в`, **When** идёт разбор, **Then** соответственно `ожидалось 'метрика, событие или расписание', получено '<лексема>'` / `ожидалось 'оператор сравнения', получено '<лексема>'` / `ожидалось 'каждые или в', получено '<лексема>'`, exit 1.

### User Story 4 — Осознанный отказ на составном условии и невалидный токен на верхнем уровне (Priority: P3)

Автор `.ladix`, попытавшийся написать составное условие метрика-триггера (`когда метрика X < Y и Z > W:`), упирается в ограничение версии: условие — ровно одно сравнение, грамматика не собирает логические операторы в условии. Отказ наблюдается как синтаксическая ошибка про ожидаемое `:` (а не семантическая), потому что после правой части ожидается двоеточие. Аналогично `{`/`}` на верхнем уровне и `значение` вне триггера остаются невалидными.

**Why this priority**: Краевые случаи и осознанное ограничение v1, расширяемое аддитивно в v2 без слома синтаксиса. Не блокирует ядро, поэтому P3.

**Independent Test**: `когда метрика просрочка > 5 и долг > 100:` → разбор упирается в ожидание `:` после `5`, синтаксическая ошибка, exit 1. `{` на верхнем уровне → `неожиданный токен '{'`, exit 1.

**Acceptance Scenarios**:

1. **Given** `когда метрика просрочка > 5 и долг > 100:` — попытка составного условия, **When** идёт разбор, **Then** синтаксическая ошибка про ожидаемое двоеточие (составное условие невыразимо в v1, диагностики «составное условие» не существует), exit 1.
2. **Given** `{` или `}` в позиции верхнего уровня, **When** идёт разбор, **Then** ошибка `неожиданный токен '{'` (или `'}'`), exit 1 (фигурных скобок в языке нет).
3. **Given** `значение` как ведущий токен на верхнем уровне вне любого триггера, **When** идёт разбор, **Then** ошибка `неожиданный токен 'значение'`, exit 1; при этом ведущий `когда` на верхнем уровне больше **НЕ** даёт ошибку — это валидная декларация триггера.

---

### Edge Cases

- **`нед`/`мес` валидны и ошибки не дают**: правило «нед/мес → ошибка» сознательно не вводилось (исполнение расписания в 007b будет календарным). Все 6 единиц `каждые` (сек/мин/час/дн/нед/мес) принимаются синтаксически без ограничений.
- **Формат `в "ЧЧ:ММ"` в 007a не валидируется**: содержимое строки времени принимается как есть (любая строка); диагностики формата времени в реестре 007a НЕТ вовсе. Валидация `ЧЧ:ММ` (ведущий ноль `"9:05"` vs `"09:05"`, диапазон 00–23 : 00–59) отложена в 007b.
- **`{`/`}` на верхнем уровне → `неожиданный токен`**: тело триггера — индентный блок (ровно 4 пробела на ступень, табы запрещены), а не `{}`-скобки; фигурных скобок в языке нет.
- **Ведущий `когда` на верхнем уровне больше НЕ отвергается**: раньше давал `неожиданный токен 'когда'`, теперь диспетчеризуется в декларацию триггера. `значение` и `событие` остаются невалидными ведущими токенами на верхнем уровне (`неожиданный токен 'значение'` / `неожиданный токен 'событие'`) — оба отвергаются предикатом `isUnexpectedTopLevel` симметрично. `значение` уже было в предикате; `событие` исходно не значилось, но шов B добавил его в `parsePrimary` как первичное выражение, поэтому `KW_EVENT` добавлен в `isUnexpectedTopLevel` как компенсация шва B (иначе ведущий `событие` разобрался бы как голое выражение-оператор).
- **`'<имя>' — не метрика` достижима**: LHS условия `метрика <имя>` принимает ЛЮБОЙ идентификатор (грамматика не требует именно объявленную метрику); если имя резолвится в не-метрику (функция/источник/процесс), семпроход даёт `'<имя>' — не метрика` (exit 1). Негативный сценарий построим и покрыт `src/internal/eval/analyze_trigger_test.go`.
- **Действия-шага отвергаются на компиляции, не в рантайме**: `присвоить`/`вызвать`/`уведомить` в теле триггера дают семантическую ошибку до исполнения; тело триггера анализируется как контекст вне шага.
- **`вернуть` в теле триггера — семантическая ошибка**: тело триггера не функция, поэтому голый `вернуть` даёт существующую диагностику `'вернуть' допустимо только внутри функции`; `прервать`/`продолжить` — только внутри `пока`/`для`.
- **`значение`/`событие` — жёсткие ключевые слова**: их нельзя использовать как имена переменных нигде в программе; коллизия с глобальным `пусть` того же имени невозможна на уровне лексера.
- **Ложное метрика-условие → молчание**: тело не исполняется, `значение` не инжектируется, процесс не запускается; базовый контракт — отсутствие вывода (опциональная строка-пропуск demo — по решению реализации).
- **Тело триггера не мутирует глобалы**: глобальные `пусть` и метрики видны read-only; локальные `пусть` тела пишутся в локальную среду и исчезают по завершении прохода (триггер эфемерен). `значение` инжектируется read-only и не протекает наружу.
- **Несколько метрика-триггеров → строго порядок объявления**: stdout и порядок создаваемых процессов определяются лексическим порядком исходника; приоритизации/сортировки по имени метрики нет.
- **Эфемерность относится только к состоянию триггеров**: процессы и задачи, порождённые триггером, персистятся в SQLite под `--db` штатно (как в 006); ЛОЖЬ-база касается только самих триггеров.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Парсер MUST разбирать триггер как верхнеуровневую декларацию `когда <спец>:` с индентным телом (минимум один оператор) в одной из трёх форм; пустой блок после `:` MUST давать синтаксическую ошибку `пустой блок не допускается, добавьте хотя бы один оператор`.
- **FR-002**: Парсер MUST принимать метрика-форму `когда метрика <имя> <сравнение> <выражение>:`, где `<сравнение>` — один из шести операторов (`==` `!=` `<` `<=` `>` `>=`), а `<выражение>` — произвольное выражение; условие — РОВНО одно сравнение.
- **FR-003**: Парсер MUST принимать событие-форму `когда событие <имя>:` (без оператора и выражения) и расписание-форму `когда расписание (каждые <длительность> | в "<строка>"):`.
- **FR-004**: Система MUST принимать все 6 единиц длительности в `каждые <длительность>` (сек/мин/час/дн/нед/мес) без ограничений; `нед` и `мес` MUST NOT давать ошибку в 007a.
- **FR-005**: Семантический проход MUST NOT анализировать содержимое строкового литерала в `расписание в "<строка>"`; реестр диагностик 007a MUST NOT содержать диагностику формата времени `ЧЧ:ММ` (валидация отложена в 007b).
- **FR-006**: Парсер MUST принимать выражения `значение` и `событие` (и `событие.поле`) синтаксически в ЛЮБОЙ позиции выражения (контекстно-свободно: тело метрики, тело шага, глобальный `пусть`, аргумент вызова), а не только в теле триггера; единственное исключение — верхний уровень (FR-020). Контекстное ограничение накладывает семантический проход (FR-007), а не парсер.
- **FR-007**: Семантический проход MUST давать ошибку `выражение 'значение' допустимо только в теле триггера метрики` (exit 1) при встрече `значение` вне тела метрика-триггера, и `выражение 'событие' допустимо только в теле триггера события` (exit 1) при встрече `событие` вне тела событие-триггера; в теле расписание-триггера недопустимы оба.
- **FR-008**: Семантический проход MUST резолвить имя в условии метрика-триггера против реестра метрик: незарегистрированное имя → `метрика '<имя>' не объявлена`; имя объявлено, но не метрика → `'<имя>' — не метрика`; обе — семантические, exit 1. Семпроход MUST также валидировать выражение-порога (правую часть сравнения) тем же `checkExpr` (резолв имён, арность вызовов); тип-чек «число vs число» остаётся рантайму (зеркало FR-022).
- **FR-009**: Семантический проход MUST разрешать в теле триггера императивное ядро (`пусть`, присваивание переменных, `если`/`иначе`, `пока`, `для`, `печать`, выражения-операторы, `запустить процесс`; `вернуть`/`прервать`/`продолжить` — в их обычных контекстных рамках) и MUST NOT разрешать действия-шага.
- **FR-010**: Семантический проход MUST отвергать действия-шага (`присвоить`/`вызвать`/`уведомить`) в теле триггера той же диагностикой `действие '<имя>' допустимо только в шаге процесса` (exit 1), что и для действий-шага вне процесса (текст не меняется); тело триггера трактуется как контекст вне шага.
- **FR-011**: Семантический проход MUST проверять `запустить процесс P(args)` в теле триггера тем же путём, что и в остальных контекстах языка (сначала аргументы, затем резолв `P` против реестра процессов и сверка арности); диагностики `'<P>' принимает N аргументов, передано M` / `процесс '<P>' не объявлен` / `'<P>' — функция, не процесс` / `'<P>' — не процесс` MUST воспроизводиться байт-точно без изменений (exit 1).
- **FR-012**: Команда `run` MUST выполнять одноразовый проход по метрика-триггерам строго после исполнения всех конструкций верхнего уровня и до печати сводки висящих задач; при нескольких метрика-триггерах порядок обработки — текстовый порядок объявления в файле, без приоритизации.
- **FR-013**: Команда `run` MUST оценивать условие каждого метрика-триггера ровно один раз: вычислить значение метрики, вычислить порог в среде верхнего уровня (глобальные `пусть` доступны), применить сравнение; при истинном результате — исполнить тело.
- **FR-014**: Команда `run` MUST трактовать предыдущее состояние каждого триггера как ЛОЖЬ эфемерно (только в памяти прогона) и MUST NOT читать или писать durable-состояние триггеров даже под `--db`; следствие — повторный `run` того же файла на той же БД снова срабатывает идентично.
- **FR-015**: При истинном условии метрика-триггера `run` MUST инжектировать в среду тела предопределённое имя `значение` = вычисленное числовое значение метрики (read-only); так `запустить процесс P(значение)` MUST передавать в процесс это значение.
- **FR-016**: Команда `run` MUST исполнять `запустить процесс P(...)` из тела штатным путём движка исполнения (006): создание инстанса с id формата `p-NNNNNN`, продвижение до первого ожидания, персист инстанса/задач (под `--db` — в SQLite); порождённые процессы/задачи MUST попадать в сводку открытых задач того же прогона.
- **FR-017**: При ложном условии метрика-триггера `run` MUST NOT исполнять тело, инжектировать `значение` или запускать процесс; базовый контракт вывода — молчание.
- **FR-018**: Команда `run` MUST NOT исполнять событие- и расписание-триггеры: для каждого MUST печататься ровно одна строка-заглушка со смыслом «<вид> триггер '<имя>' требует serve (фича 007b)», в порядке объявления; точный текст строки и форма `<имя>` фиксируются по факту реализации (§TR-6).
- **FR-019**: Парсер MUST давать `ожидалось 'метрика, событие или расписание', получено '<лексема>'` при отсутствии вида триггера после `когда`; `ожидалось 'оператор сравнения', получено '<лексема>'` при отсутствии оператора после `метрика <имя>`; `ожидалось 'каждые или в', получено '<лексема>'` при отсутствии `каждые`/`в` после `расписание`; все — exit 1.
- **FR-020**: Парсер MUST NOT отвергать ведущий `когда` на верхнем уровне (это валидная декларация триггера) и MUST продолжать отвергать `значение`, `событие`, `{`, `}` на верхнем уровне диагностикой `неожиданный токен '<лексема>'` (exit 1). И `значение`, и `событие` отвергаются через `isUnexpectedTopLevel` симметрично; `KW_EVENT` добавлен в этот предикат как компенсация шва B (исходно не значился, но шов B сделал `событие` первичным выражением в `parsePrimary`).
- **FR-021**: Грамматика MUST делать составное условие метрика-триггера (`X < Y и Z > W`) невыразимым (нет рекурсии в логические операторы); попытка дописать логику после правой части MUST приводить к синтаксической ошибке про ожидаемое `:`, а не к семантической диагностике (диагностики «составное условие» не существует).
- **FR-022**: Семантический проход MUST NOT форсировать типовое соответствие в условии метрика-триггера (число vs число) — это рантайм, зеркало того, что `если`/`пока` не статизируют тип условия; и MUST полностью валидировать тело событие-триггера (контекст-гард `событие`, запрет действий-шага, арность процессов), хотя оно не исполняется в `run`.
- **FR-023**: Документация-якорь (`docs/trigger-model.md §TR-0…§TR-11`), SPEC §1/§11.6/§12, README и манифест примеров MUST быть синхронизированы: `examples/выручка.ladix` переведён из parse-error в parse-clean пример; добавлен run-demo пример с детерминированной фикстурой (метрика без окна). *(Чисто-доковые синки SPEC/README/execution-model — за архитектор-чатом; синки кода/тестов/манифеста/фикстур — за импл-чатом.)*
- **FR-024**: Все тесты 001–006 MUST оставаться зелёными; `examples/выручка.ladix` MUST переходить в parse-clean набор (exit 0). Negative-набор examples-теста, ранее ожидавший `неожиданный токен 'когда'` на `выручка.ladix`, MUST быть согласован с якорем §TR-10.5: набор из единственного кейса пустеет → его удаляют либо заполняют новым негативом (напр. `значение` на верхнем уровне).
- **FR-025**: Тело триггера MUST видеть глобальные `пусть`, метрики и предопределённое имя (`значение` в метрика-теле / `событие` в событие-теле) **только для чтения** (read-only); локальные `пусть`, объявленные в теле, MUST писаться в локальную среду прохода и быть эфемерными (исчезать по завершении прохода триггера), не мутируя глобальное состояние (§TR-5).

### Key Entities

- **Декларация триггера (`когда …`)**: верхнеуровневая декларация с индентным телом. Несёт **вид** (метрика / событие / расписание), **спецификацию срабатывания** (условие / имя события / расписание) и **тело** (блок минимум из одного оператора, переиспользующий императивное ядро минус действия-шага). Регистрируется глобально; в момент объявления не исполняется.
- **Метрика-триггер**: форма с условием `метрика <имя> <сравнение> <выражение>` — ровно одно сравнение. Несёт **имя метрики** (должно резолвиться в объявленную метрику), **оператор сравнения** (один из шести) и **порог-выражение** (правая часть, вычисляется в среде верхнего уровня). Единственная форма, исполняемая в `run` (fire-if-true).
- **Событие-триггер**: форма `событие <имя>`. Несёт **имя события**. В теле доступно предопределённое имя `событие` (запись из payload, доступ через `.`). В 007a парсится и валидируется полностью, но в `run` не исполняется (no-op + строка-заглушка).
- **Расписание-триггер**: форма `расписание (каждые <длительность> | в "<строка>")`. Несёт **подформу** (периодическая `каждые` с одной из 6 единиц длительности, либо суточная `в "строка"`). Содержимое строки времени в 007a не валидируется. В теле нет предопределённых имён. В `run` не исполняется (no-op + строка-заглушка).
- **`значение`** (предопределённое имя метрика-тела): read-only имя, видимое только в теле метрика-триггера. В `run` при истинном условии инжектируется = вычисленное числовое значение метрики; не протекает наружу. Вне метрика-тела — семантическая ошибка контекст-гарда.
- **`событие`** (предопределённое имя событие-тела): read-only имя (и доступ `событие.поле`), видимое только в теле событие-триггера. В 007a фактической инжекции в `run` нет (событие-триггеры не исполняются), но семантический проход полностью валидирует контекст. Вне событие-тела — семантическая ошибка контекст-гарда.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Все три формы триггера (`когда метрика … :`, `когда событие … :`, `когда расписание … :`) парсятся и проходят семантический проход без ошибок; `examples/выручка.ladix` даёт exit 0 и ноль диагностик (parse-clean), включая тело с выражением `значение`.
- **SC-002**: Все 6 единиц длительности (`сек`/`мин`/`час`/`дн`/`нед`/`мес`) в `каждые` принимаются без ошибок; строка времени в `в "…"` принимается без проверки формата (в реестре 007a нет диагностики формата `ЧЧ:ММ`).
- **SC-003**: При истинном условии метрика-триггер в `run` запускает процесс ровно один раз с детерминированным stdout: на детерминированной фикстуре (метрика без окна = 2 000 000, порог `< 3_000_000`) процесс создаётся с `значение` = 2 000 000, задача первого шага видна в сводке открытых задач; вывод не зависит от `сегодня()`.
- **SC-004**: Повторный `run` того же файла на той же БД (включая `--db`) даёт тот же результат — триггер снова срабатывает (база = ЛОЖЬ, durable-состояние триггеров не читается/не пишется); при ложном условии (`< 1_000_000`) — молчание и пустая сводка задач.
- **SC-005**: Каждая семантическая диагностика 007a воспроизводится **байт-точно** (двухстрочный канон с позицией, без завершающей точки, имена в одинарных кавычках), exit 1: `выражение 'значение' допустимо только в теле триггера метрики`; `выражение 'событие' допустимо только в теле триггера события`; `метрика '<имя>' не объявлена`; `'<имя>' — не метрика`.
- **SC-006**: Переиспользуемые диагностики в теле триггера воспроизводятся **байт-точно** без изменений текста, exit 1: `действие '<имя>' допустимо только в шаге процесса`; `'<P>' принимает N аргументов, передано M`; `процесс '<P>' не объявлен`; `'<P>' — функция, не процесс`; `'<P>' — не процесс`; `'вернуть' допустимо только внутри функции`.
- **SC-007**: Синтаксические диагностики диспетчера форм воспроизводятся **байт-точно**, exit 1: `ожидалось 'метрика, событие или расписание', получено '<лексема>'`; `ожидалось 'оператор сравнения', получено '<лексема>'`; `ожидалось 'каждые или в', получено '<лексема>'`; `неожиданный токен 'значение'` (на верхнем уровне); `неожиданный токен 'событие'` (на верхнем уровне); ведущий `когда` на верхнем уровне ошибки не даёт.
- **SC-008**: `go build ./...`, `go vet ./...` — чисто; `gofmt` — без правок; `go test ./...` — зелёное, включая все регресс-тесты 001/002/003/004/005/006 (тест на `когда` в `examples/выручка.ladix` инвертирован на parse-clean).

## Assumptions

- Спецификация **выведена из** `docs/trigger-model.md` (§TR-0…§TR-11) и не вводит требований сверх якоря; при любом расхождении источников побеждает якорь. В частности, упоминания валидации формата `"ЧЧ:ММ"` в SPEC — и в §11.6 (проза «формат `"ЧЧ:ММ"` валидируется на семантике (00:00–23:59)»), и в §13.4 (диагностика `расписание: ожидался формат "ЧЧ:ММ" …`) — относятся к 007b; в 007a (§TR-7.E) такой диагностики НЕТ. Приведение этих мест SPEC к границе 007a/007b — за архитектор-чатом (доковый синк).
- Решения владельца и архитектора (разрез B: чистый фронтенд трёх форм + метрика-fire-if-true в `run`; нед/мес валидны без ошибки; формат `ЧЧ:ММ` отложен; FixedClock-флаг в v1 не вводится) приняты и **не переоткрываются**.
- Фронтенд процессов 005 и движок исполнения 006 готовы и не меняются: тело триггера переиспользует существующее императивное ядро, `запустить процесс` идёт штатным путём движка 006, проверка арности процесса и контекст-гард действий-шага переиспользуются без правок текстов.
- Интерпретатор (eval) не трогается по существу: сравнение в условии идёт через существующий оператор сравнения 003; forever-cache интерпретатора безвреден, так как проход одноразовый (сброс между триггерами не нужен).
- Golden run-demo дата-независим: эталонный пример исполнения использует метрику без `период:`/`по_дате:` (окна нет), результат стабилен при любой дате.
- Точный текст строки-заглушки событие/расписание-триггера и форма `<имя>` в ней, а также точный формат строки-нотификации о срабатывании в stdout закрепляются **по факту при реализации** (§TR-6) — это импл-факты, закрываемые кодом, не пробелы спецификации.
- Имя нового run-demo файла и контр-демо (ветка «условие ложно», порог `< 1_000_000`) — предложение/опционально по решению реализации.

## Out of Scope (→ фича 007b / v2)

- **Демон `serve`** — длинноживущий цикл планировщика триггеров → **007b**.
- **События / `emit` / очередь событий** — доставка событие-триггерам; сам синтаксис `когда событие …` и выражение `событие` в 007a парсятся и валидируются, но НЕ исполняются → **007b**.
- **Edge-детект «был-ложь → стал-истина» + персист durable-состояния триггеров** — подавление повторных срабатываний; в 007a проход одноразовый, база всегда ЛОЖЬ → **007b**.
- **Исполнение расписания**, включая **календарный сдвиг для `нед`/`мес`** и периодический опрос → **007b**.
- **Валидация формата строки `"ЧЧ:ММ"`** (ведущий ноль, диапазон 00–23 : 00–59) — в 007a строка принимается как есть; диагностика — новая в 007b → **007b**.
- **Рестарт-скан** активных/осиротевших инстансов при подъёме демона → **007b**.
- **Источник событий `ladix emit`** и любой внешний канал доставки событий → **007b**.
- **Составное условие метрика-триггера** (`X < Y и Z > W`, предикаты по нескольким метрикам) — невыразимо в v1, расширяемо аддитивно → **v2**.
- **Решение блокера forever-cache интерпретатора** — в 007a безвредно (один проход за `run`), системно решается в **007b**.

## Dependencies

- **Лексер 001** — токены `когда`/`метрика`/`событие`/`расписание`/`каждые`/`в`/`значение`/`запустить` как жёсткие ключевые слова.
- **Парсер+AST 002** — индентные блоки, выражения, операторы сравнения, литералы длительности.
- **Интерпретатор 003** — императивное ядро тела (`пусть`/`если`/`пока`/`для`/`печать`), оператор сравнения для условия.
