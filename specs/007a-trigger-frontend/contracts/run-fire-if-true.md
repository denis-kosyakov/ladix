# Контракт: проход fire-if-true в `run`

**Фаза**: 1 (design) | **Якорь**: `docs/trigger-model.md §TR-6, §TR-8` | **Решения**: D-25, D-26, D-27 | **FR**: FR-012…018

> Единственная точка **исполнения** триггеров в 007a: после `interp.Run(prog)`, до сводки задач, один проход по метрика-триггерам в порядке объявления. База триггера = ЛОЖЬ эфемерно (не читает/не пишет `trigger_state` даже под `--db`); событие/расписание → одна строка-заглушка.

## Назначение

Экспортный метод интерпретатора, исполняющий метрика-триггеры по принципу fire-if-true, и точка его вызова из `cmd/ladix/main.go`. Метод живёт в `eval` (сохраняет инкапсуляцию env/метрик и принцип V — нет глобального состояния), вызывается из `runFile`. Событие/расписание-триггеры — no-op + лог.

**Размещение**: `src/internal/eval/trigger_run.go` — НОВЫЙ (проход fire-if-true); `src/cmd/ladix/main.go` — ИЗМЕНЯЕТСЯ (точка вызова в `runFile`).

## Экспортный API

```go
// RunTriggers исполняет одноразовый проход fire-if-true по зарегистрированным
// триггерам (реестр i.triggers, заполнен Analyze Шаг 1d) в порядке объявления.
// Для метрика-триггера: вычислить метрику, вычислить порог, сравнить; при истине —
// инжектировать read-only «значение» и исполнить тело (StartProcess штатным путём).
// Для событие/расписание — одна строка-заглушка в w. База ЛОЖЬ эфемерно: не читает/
// не пишет trigger_state даже под --db. Ошибка тела/метрики всплывает как error
// (обрабатывается зеркалом interp.Run: двухстрочный Error() → stderr, exit 1).
func (i *Interpreter) RunTriggers(w io.Writer) error
```

(Имя метода/сигнатура `w io.Writer` — концептуальные; точное имя за импл-проходом. `w` = тот же `stdout`, что у `interp` и `engine`.)

## Точка интеграции (§TR-8.1, main.go)

Вызов **строго после** `interp.Run(prog)` (main.go:196) и **до** `st.ListPendingTasks("")` (main.go:202), внутри замыкания `guard`. Координаты — между строкой 196 и 202:

```go
if err := interp.Run(prog); err != nil {        // main.go:196 — шаг 8 (top-level + семпроход)
	fmt.Fprintln(stderr, err.Error())
	return 1
}
// ◀── ТОЧКА ВСТАВКИ (§TR-8.1 шаг 9) ──▶
if err := interp.RunTriggers(stdout); err != nil {
	fmt.Fprintln(stderr, err.Error())            // зеркало обработки ошибки interp.Run
	return 1
}
pending, perr := st.ListPendingTasks("")        // main.go:202 — шаг 10 (сводка задач)
```

**Почему именно здесь** (директива архитектора, §TR-6.1): глобальные `пусть` связываются исполнением top-level в `interp.Run` (шаг 8) — тело/порог триггера могут на них ссылаться, значит проход обязан идти ПОСЛЕ. Процессы, которые триггер запустит, ещё успевают попасть в сводку висящих задач (шаг 10). Запускать раньше — читать несвязанные имена.

## Алгоритм (§TR-6.3)

Итерация по `i.triggers` **в порядке `prog.Items`** (FR-012, детерминизм stdout и порядка процессов; без приоритизации/сортировки). Для каждого:

```
RunTriggers(w):
    for _, td := range i.triggers:                 // порядок объявления
        switch spec := td.Spec.(type):
          case *ast.MetricTrigger:
              // 1. вычислить значение метрики (числовое value.Value)
              metricVal, err := i.evalMetricByName(spec.Metric.Name, spec.Metric.Pos())
              if err != nil: return err
              // 2. вычислить порог в среде верхнего уровня (глобалы доступны)
              threshVal, err := i.evalExpr(i.global, spec.Threshold)
              if err != nil: return err
              // 3. применить CompOp существующим оператором сравнения 003 → Булево
              fired, err := i.compare(ast.BinOp(spec.Op), metricVal, threshVal)
              if err != nil: return err
              // 4. база ЛОЖЬ ⇒ «переход ложь→истина» ≡ «истинно сейчас»
              if fired:
                  env := NewEnvironment(i.global)        // локальный env тела
                  env.Define("значение", metricVal)      // read-only обеспечено тем, что «значение» — ключевое слово KW_VALUE (не присваиваемое), §TR-5
                  if err := i.evalBlockInTrigger(env, td.Body); err != nil:
                      return err
                  // тело: «запустить процесс» → evalRunProcess → i.runtime.StartProcess
                  //   → Engine.StartProcess (id p-NNNNNN); под --db инстанс/задачи в SQLite
              // ложь → молчание (тело не исполнено, значение не инжектировано)
          case *ast.EventTrigger:
              fmt.Fprintf(w, "событие триггер '%s' требует serve (фича 007b)\n", spec.Event.Name)
          case *ast.ScheduleTrigger:
              fmt.Fprintf(w, "расписание триггер '<имя>' требует serve (фича 007b)\n")
    return nil
```

- **Шаг 3** — сравнение через **существующий eval сравнения** (тот же путь, что бинарные сравнения выражений; никакой новой арифметики, переиспользуется оператор 003). `value.Value` метрики числовой; `CompOp` — defined type над `BinOp`, кастится к `BinOp` для оператора.
- **Шаг 4 — база ЛОЖЬ.** Предыдущее состояние каждого триггера считается ЛОЖЬ (только в памяти `run`), поэтому «переход ложь→истина» ≡ «условие истинно сейчас». Фактическое правило: оценить условие один раз; если истинно — исполнить тело.
- **`значение`** инжектируется обычным `env.Define("значение", metricVal)` = то самое число, что сравнивали (снимок метрики на момент прохода, §TR-6.3/D-27). Read-only гарантируется не отдельным API окружения (`DefineReadOnly` в `Environment` нет), а тем, что `значение` — ключевое слово `KW_VALUE`, не присваиваемое в синтаксисе (присвоить ему нельзя — парсер не примет). Тело исполняется как императивный блок в контексте `inStep=false`: доступны `пусть`/`если`/`пока`/`печать`/выражения/`запустить процесс`; действия-шага уже отвергнуты семпроходом (analyze-trigger.md), сюда не доходят.
- **`запустить процесс P(...)`** внутри тела исполняется штатным путём eval: `evalRunProcess` вычисляет аргументы → `i.runtime.StartProcess(name, args)` → `Engine.StartProcess` → `Engine.Start`. Движок минтит id `p-NNNNNN`, персистит статус `created`, синхронно продвигает до первого ожидания. Эфемерность §TR-6.2 относится **только** к состоянию триггеров, не к процессам, которые триггер породил.
- **Ложное условие** → тело не исполняется, `значение` не инжектируется, процесс не запускается; триггер пропускается без вывода (базовый контракт — молчание; опциональная строка-пропуск demo — по решению реализации).

> **forever-cache eval безвреден.** Интерпретатор 003 кэширует вычисленные сущности без `Reset`. В 007a безопасно: проход одноразовый, метрика в условии вычисляется один раз за `run`, повторного обращения с ожиданием иного результата нет. Отдельный `Reset` между триггерами не нужен (системно решается в 007b).

## Событие / расписание — строка-заглушка (§TR-6.4)

Событие- и расписание-триггеры в `run` **не исполняются**. Они полноценно проходят лексер/парсер/семпроход (включая контекст-гард `событие`), но на стадии исполнения для каждого печатается **одна строка** в порядке объявления:

```
<вид> триггер '<имя>' требует serve (фича 007b)
```

где `<вид>` ∈ {`событие`, `расписание`}, `<имя>` — имя события/целевой метрики/триггера.

Формат выше — модель.

## Поведение под `--db` (§TR-8.3)

Точка вставки и логика прохода **те же**. Различие только в Store движка: процессы/задачи, запущенные триггером, персистятся в SQLite штатно (как в 006). **Состояние самих триггеров** (edge-детект `trigger_state`) НЕ трогается ни при чтении, ни при записи — **даже под `--db`** (канон §TR-6.2). Следствие — demo детерминированно и повторяемо: повторный `run --db` того же файла на той же БД снова видит «база триггера = ЛОЖЬ», снова оценивает условие с нуля и (если истинно) снова создаёт инстанс. Durable-дедупликация срабатываний — 007b. Эфемерность относится исключительно к триггер-состоянию.
