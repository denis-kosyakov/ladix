# Quickstart: Фронтенд триггеров и метрика-fire-if-true в `run` (007a)

**Feature**: 007a-trigger-frontend | **Plan**: [plan.md](./plan.md) | **Якорь**: [../../docs/trigger-model.md](../../docs/trigger-model.md) | **Спека**: [spec.md](./spec.md)

Как разработчику собрать, запустить и проверить фичу 007a руками. Фича добавляет **фронтенд
триггеров** `когда …:` — единообразный парсинг и семантическую валидацию всех трёх форм
(`метрика` / `событие` / `расписание`) — плюс **одну** точку исполнения: метрика-триггер
срабатывает разово в команде `run` по принципу **fire-if-true** (условие истинно сейчас →
исполнить тело один раз; база триггера = ЛОЖЬ эфемерно, см. [§TR-6](../../docs/trigger-model.md)).

Три новые наблюдаемые поверхности:

- **stdout команды `run`** — нотификация о срабатывании метрика-триггера + штатный вывод
  движка 006 (создание инстанса/задачи) + сводка висящих задач; для событие/расписание-триггеров
  — строка-заглушка «требует serve» ([§TR-6.4/6.5](../../docs/trigger-model.md));
- **семантические диагностики** — контекст-гарды `значение`/`событие`, резолв метрики,
  переиспользуемые гарды действий-шага и арности процесса ([§TR-7.A…D](../../docs/trigger-model.md));
- **синтаксические диагностики** — диспетчер форм `когда` (вид триггера / оператор сравнения /
  `каждые`-`в`), переворот замка top-level `когда` ([§TR-7.F](../../docs/trigger-model.md)).

Все команды `go` — от корня Go-модуля `src/` (там `go.mod`, модуль
`github.com/denis-kosyakov/ladix`). Пути `.ladix`-примеров — от **корня репозитория**.
007a **не добавляет пакетов и зависимостей** — расширяет `ast`/`parser`/`eval` + одна точка
врезки в `cmd/ladix`.

> **Прежде чем читать дальше:** при любом расхождении этого файла с якорем побеждает якорь.
> Здесь — сборка/запуск/ручная проверка; грамматика форм, AST-узлы, алгоритм fire-if-true и
> **байт-точные** тексты диагностик — в `docs/trigger-model.md §TR-1…§TR-9`.

## 0. Где лежит go.mod и как собирать

```bash
cd src                              # все команды go — отсюда; go.mod здесь
ls go.mod                           # github.com/denis-kosyakov/ladix
go build -o /tmp/ladix ./cmd/ladix  # бинарник ladix
```

Лексер уже несёт все нужные ключевые слова (`когда`/`метрика`/`событие`/`расписание`/`каждые`/
`в`/`значение`/`запустить`) и 6 единиц длительности — правок не требует
([§TR-2](../../docs/trigger-model.md)). Расширяются: `ast` (узлы `TriggerDecl`, формы-спеки,
`ValueExpr`/`EventExpr`), `parser` (два шва — top-level диспетчер `когда` + Primary
`значение`/`событие`), `eval` (регистрация триггеров, контекст-гарды, проход fire-if-true).
Граф зависимостей ацикличен; `ast` остаётся листовым.

## 1. Гейты качества (SC-008) — обязаны быть чистыми

```bash
cd src
go build ./...     # собирается
go vet ./...       # без замечаний
gofmt -l .         # пусто = ок (любой вывод = нужен gofmt -w; правок не вносим)
go test ./...      # зелёное, ВКЛЮЧАЯ все регрессы 001–006
```

**Критерий готовности (SC-008):** `go build ./...` и `go vet ./...` — чисто; `gofmt -l .` — без
правок; `go test ./...` — зелёное, включая **все** регресс-тесты 001/002/003/004/005/006. Тест
на `когда` в `examples/выручка.ladix` инвертирован с parse-error на parse-clean (см. §7).
Run-golden детерминирован: фикстура без `период:`/`по_дате:`, вывод не зависит от `сегодня()`.

## 2. Канонический вход — `examples/выручка.ladix` (parse-clean канон синтаксиса)

Канон **синтаксиса** US1: лексер + парсер + семпроход проходят без ошибок, диагностик ноль,
AST строится. Парсинг и семпроход не зависят от даты запуска ([§TR-9](../../docs/trigger-model.md)).
Файл целиком:

```ladix
# Источник данных: заказы из JSON (лениво загружается при первом обращении метрики)
источник продажи:
    файл: "data/sales.json"
# записи: { клиент, дата_заказа, сумма_заказа, статус }

# Метрика: выручка за текущий месяц по оплаченным заказам
метрика выручка_месяца:
    источник: продажи
    где:      статус == "оплачен"
    агрегат:  сумма(сумма_заказа)
    период:   ежемесячно
    по_дате:  дата(дата_заказа)

# Процесс реакции: человек-в-цикле (аналитик готовит отчёт, директор смотрит)
процесс разбор_падения(текущая_выручка):
    шаг подготовка_отчёта:
        исполнитель: "аналитик"
        срок:        2дн
        присвоить выручка = текущая_выручка     # переменная процесса для следующих шагов
    шаг встреча после подготовка_отчёта:
        исполнитель: "директор"
        срок:        1дн

# Триггер: связываем декларатив и процесс
когда метрика выручка_месяца < 3_000_000:
    запустить процесс разбор_падения(значение)
```

Раньше файл падал на токене `когда` с `неожиданный токен 'когда'`. После 007a — `когда`
маршрутизируется в декларацию триггера; тело-выражение `значение` (узел `ValueExpr`) принимается
парсером в любой позиции, а семпроход проверяет лишь контекст (`значение` в теле метрика-триггера)
и арность `разбор_падения` (один параметр — один аргумент). Окно метрики `сегодня()` в parse/sem
не вычисляется → канон стабилен без привязки к Clock.

## 3. Сценарий А (US1) — три формы parse-clean

Канон синтаксиса (§2) проходит чисто:

```bash
cd src && go build -o /tmp/ladix ./cmd/ladix && cd ..
/tmp/ladix run examples/выручка.ladix
# exit 0, ноль диагностик (раньше падал на «неожиданный токен 'когда'»)
```

Дописать в конец файла событие-форму и расписание-форму — по-прежнему **exit 0**. Все три формы
в одном сниппете:

```ladix
когда метрика выручка_месяца < 3_000_000:
    запустить процесс разбор_падения(значение)

когда событие заявка_создана:
    запустить процесс обработать(событие.клиент)

когда расписание каждые 1дн:
    запустить процесс ежедневный_отчёт()
```

(где `обработать`/`ежедневный_отчёт` — объявленные процессы соответствующей арности; в теле
событие-триггера доступно выражение `событие` и доступ `событие.поле`.)

Все 6 единиц длительности в `каждые` принимаются без ограничений — заменить единицу и убедиться,
что **exit 0** в каждом случае:

```bash
# каждый вариант парсится и проходит семпроход → exit 0
#   каждые 30сек   каждые 5мин   каждые 1час   каждые 1дн   каждые 1нед   каждые 1мес
```

`нед`/`мес` **НЕ** дают ошибку в 007a (исполнение расписания в 007b будет календарным).
Строка времени в `когда расписание в "25:99":` тоже принимается без проверки формата — в реестре
007a диагностики формата `ЧЧ:ММ` НЕТ вовсе ([§TR-9](../../docs/trigger-model.md), FR-005).

## 4. Сценарий Б (US2) — метрика-fire-if-true в `run`

Детерминированная run-проверка собирается **инлайн** golden-тестом
`src/cmd/ladix/trigger_golden_test.go` в `t.TempDir()` (отдельной testdata-фикстуры нет;
[§TR-9](../../docs/trigger-model.md) D-26): метрика **без окна** (`период:`/`по_дате:` нет) →
агрегат по всем оплаченным строкам → **2 000 000** при любой дате. Порог `< 3_000_000` → условие
истинно. Программа-пример целиком:

```ladix
# Demo fire-if-true: метрика без окна → детерминированно при любой дате
источник продажи:
    файл: "data/sales.json"

# Без период: и по_дате: → агрегат по ВСЕМ оплаченным строкам (не зависит от сегодня())
метрика выручка_всего:
    источник: продажи
    где:      статус == "оплачен"
    агрегат:  сумма(сумма_заказа)

процесс разбор_падения(текущая_выручка):
    шаг подготовка_отчёта:
        исполнитель: "аналитик"
        срок:        2дн
        присвоить выручка = текущая_выручка
    шаг встреча после подготовка_отчёта:
        исполнитель: "директор"
        срок:        1дн

когда метрика выручка_всего < 3_000_000:
    запустить процесс разбор_падения(значение)
```

Источник `data/sales.json` — две оплаченные строки 1 200 000 + 800 000 (отменённая отбрасывается
фильтром `статус == "оплачен"`) → метрика `выручка_всего` = **2 000 000** при любой дате.

**Прогон (условие истинно):** сохранить программу-пример выше в файл (напр. `/tmp/демо.ladix`) и
прогнать — то же, что делает `trigger_golden_test.go` инлайн в `t.TempDir()`:

```bash
/tmp/ladix run /tmp/демо.ladix
```

Условие `2 000 000 < 3 000 000` истинно → в среду тела инжектируется `значение` = 2 000 000
(read-only) → `запустить процесс разбор_падения(значение)` создаёт инстанс, продвигает его до
первой человеческой задачи (`подготовка_отчёта`, исполнитель «аналитик»), задача попадает в
сводку открытых задач того же прогона. **exit 0.**

**Ожидаемый stdout (маски — ИМПЛ-ФАКТ, точные тексты по факту реализации §TR-6):**

```
<строка-нотификации о срабатывании / запуске процесса — §TR-6.5, ИМПЛ-ФАКТ; содержит инстанс p-NNNNNN>
[задача] t-NNNNNN → аналитик, шаг 'подготовка_отчёта', срок до <время>
открытых задач: 1
t-NNNNNN  p-NNNNNN  'подготовка_отчёта'  аналитик  срок до <время>
```

- `p-NNNNNN`/`t-NNNNNN` — минтятся движком 006 (свежий Store → `p-000001`/`t-000001`); маска
  по [§EN-7](../../docs/engine-model.md);
- **точный формат строки-нотификации о срабатывании триггера** ([§TR-6.5](../../docs/trigger-model.md)
  TODO-FACT) — логирует ли проход факт срабатывания отдельной строкой или виден только эффект
  (задача первого шага) — **ИМПЛ-ФАКТ**, закрывается кодом, не выдумывается дословно здесь;
- строки задачи/сводки — штатный вывод движка 006, формат [§EN-7](../../docs/engine-model.md);
- `значение` = 2 000 000 передаётся в процесс → переменная процесса `выручка` = 2 000 000
  ([§TR-9](../../docs/trigger-model.md) D-27); вывод детерминирован, не зависит от `сегодня()`.

**Контр-демо (условие ложно):** тот же файл с порогом `< 1_000_000`:

```bash
# триггер: когда метрика выручка_всего < 1_000_000:
/tmp/ladix run <фикстура-с-порогом-1_000_000>
```

```
открытых задач нет
```

Условие `2 000 000 < 1 000 000` ложно → тело **не** исполняется, `значение` не инжектируется,
процесс не запускается; базовый контракт — молчание, пустая сводка задач. **exit 0.**

**Повторный прогон на той же БД (база триггера = ЛОЖЬ эфемерно):**

```bash
rm -f /tmp/демо.db
/tmp/ladix run /tmp/демо.ladix --db /tmp/демо.db   # 1-й прогон
/tmp/ladix run /tmp/демо.ladix --db /tmp/демо.db   # 2-й прогон — ТОТ ЖЕ результат
```

Оба прогона срабатывают идентично. Durable-состояние **самих триггеров** не читается и не
пишется даже под `--db` ([§TR-6.2](../../docs/trigger-model.md), FR-014), поэтому второй прогон
снова видит «база = ЛОЖЬ» и снова создаёт инстанс. Эфемерность относится **только** к состоянию
триггеров: процессы и задачи, порождённые триггером, персистятся в SQLite штатно (как в 006),
поэтому id во втором прогоне сдвигаются (`p-000002`/`t-000002`, …). **exit 0** в обоих.

> **Порядок и состав вывода** ([§TR-6.1/6.5](../../docs/trigger-model.md)): проход fire-if-true
> идёт **строго после** исполнения всех top-level statements и **до** печати сводки задач; при
> нескольких метрика-триггерах — в порядке текстового объявления (без сортировки). Событие- и
> расписание-триггеры в `run` **не исполняются** — для каждого печатается ровно одна
> строка-заглушка вида `<вид> триггер '<имя>' требует serve (фича 007b)` (точный текст и форма
> `<имя>` — **ИМПЛ-ФАКТ** [§TR-6.4](../../docs/trigger-model.md), `<вид>` ∈ {событие, расписание}).

## 5. Негативы (US3/US4) — точные диагностики, exit 1

Каждая семантическая диагностика — двухстрочный канон с позицией (строка/колонка), без
завершающей точки, имена в одинарных кавычках; тире `—` (U+2014). Тексты дословны
([§TR-7](../../docs/trigger-model.md)).

### 5.1. `значение` вне тела метрика-триггера (контекст-гард, US3)

`значение` в теле событие- или расписание-триггера:

```
выражение 'значение' допустимо только в теле триггера метрики
```
exit 1. Позиция — токен `значение`.

### 5.2. `событие` вне тела событие-триггера (контекст-гард, US3)

`событие` (или `событие.поле`) в теле метрика- или расписание-триггера:

```
выражение 'событие' допустимо только в теле триггера события
```
exit 1. Позиция — токен `событие`.

### 5.3. Неизвестная метрика в условии (US3)

`когда метрика неведомая > 5:` — имя не объявлено как метрика:

```
метрика 'неведомая' не объявлена
```
exit 1. Если имя объявлено, но не метрика → `'<имя>' — не метрика` (может быть недостижим:
грамматика фиксирует левую часть как жёсткий `метрика <имя>` — диагностика остаётся в реестре
до подтверждения на импл-проходе).

### 5.4. Неверная арность `запустить процесс` (переиспользуемая, US3)

`запустить процесс P(a, b)`, где процесс `P` объявлен с одним параметром:

```
'P' принимает 1 аргументов, передано 2
```
exit 1. Соседние тексты того же семейства (байт-точно, без изменений): для необъявленного `P` →
`процесс 'P' не объявлен`; для функции `P` → `'P' — функция, не процесс`; для метрики/источника
`P` → `'P' — не процесс`.

### 5.5. Действие-шага в теле триггера (переиспользуемая, US3)

`присвоить x = 1` (или `вызвать`/`уведомить`) в теле любого триггера:

```
действие 'присвоить' допустимо только в шаге процесса
```
exit 1. `<имя>` = конкретное действие. Тело триггера трактуется как контекст вне шага
(`inStep=false`); отвергается на компиляции, не в рантайме. Голый `вернуть` в теле триггера даёт
существующую `'вернуть' допустимо только внутри функции` (тело — не функция).

### 5.6. Нет вида триггера после `когда` (синтаксис, US3)

`когда нечто:`:

```
ожидалось 'метрика, событие или расписание', получено 'нечто'
```
exit 1. Сёстры по диспетчеру форм: `метрика M` без оператора сравнения →
`ожидалось 'оператор сравнения', получено '<лексема>'`; `расписание` без `каждые`/`в` →
`ожидалось 'каждые или в', получено '<лексема>'`.

### 5.7. Составное условие метрика-триггера (US4)

`когда метрика просрочка > 5 и долг > 100:` — попытка составного условия. Грамматика не собирает
логические операторы в условии (ровно одно сравнение), поэтому после правой части `5` ожидается
`:` — **синтаксическая** ошибка про ожидаемое двоеточие (не семантическая; диагностики
«составное условие» не существует), exit 1.

### 5.8. Невалидный токен на верхнем уровне (US4)

`значение` или `{`/`}` как ведущий токен на верхнем уровне вне триггера:

```
неожиданный токен 'значение'
```
exit 1 (аналогично `неожиданный токен '{'` / `'}'` / `неожиданный токен 'событие'`; фигурных
скобок в языке нет — тело триггера индентное). При этом ведущий `когда` на верхнем уровне
**НЕ** даёт ошибку — это валидная декларация триггера. И `значение`, и `событие` отвергаются
симметрично через `isUnexpectedTopLevel` (`KW_EVENT` добавлен в предикат как компенсация
шва B, который сделал `событие` первичным выражением в `parsePrimary`).

### 5.9. Пустой блок триггера (синтаксис)

`когда метрика просрочка > 5:` без тела (после `:` нет ни одного оператора):

```
пустой блок не допускается, добавьте хотя бы один оператор
```
exit 1.

## 6. Чек-лист приёмки по user stories

- **US1 (P1, три формы parse-clean)** — §3: `выручка.ladix` → exit 0, ноль диагностик; три формы
  парсятся и проходят семпроход; все 6 единиц `каждые` и `в "строка"` приняты без проверки
  формата **(SC-001/002)**.
- **US2 (P1, fire-if-true в `run`)** — §4: на демо-программе из §4 (собирается инлайн golden-тестом
  в `t.TempDir()`; метрика 2 000 000, порог `< 3_000_000`) процесс создаётся с `значение` =
  2 000 000, задача первого шага в сводке;
  контр-демо (`< 1_000_000`) → молчание; повтор `run --db` идентичен (база = ЛОЖЬ) **(SC-003/004)**.
- **US3 (P2, диагностики)** — §5.1…5.6: контекст-гарды `значение`/`событие`, резолв метрики,
  арность процесса, действия-шага, диспетчер форм — байт-точно exit 1 **(SC-005/006/007)**.
- **US4 (P3, краевые)** — §5.7/5.8: составное условие → ожидание `:`; `значение`/`{` на top-level
  → `неожиданный токен`; ведущий `когда` на top-level ошибки не даёт **(SC-007)**.
- **Гейты** — §1: `go build`/`go vet`/`gofmt -l`/`go test ./...` зелёные, регрессы 001–006 **(SC-008)**.

## 7. Замки, которые фича переворачивает

[§TR-10](../../docs/trigger-model.md) — каждый синк вносится явно, иначе тесты/доки разойдутся с
кодом. Порядок: сначала код+тесты в одном коммите с поведенческим сдвигом, затем доки отдельным
синк-коммитом.

- **`examples/выручка.ladix`: parse-error (код 1) → parse-clean.** Центральный поведенческий
  сдвиг: файл больше не падает на `неожиданный токен 'когда'`, парсится чисто, exit 0
  ([§TR-10.4](../../docs/trigger-model.md)).
- **`src/internal/parser/examples_test.go` — переворот замка.** `TestDeclarativeExamplesUnexpected`
  держит запись `{"выручка.ladix", "неожиданный токен 'когда'"}` (единственный кейс набора).
  Действие: удалить запись `выручка.ladix` — набор пустеет → либо удалить таблицу-кейс/тест, либо
  наполнить новым негативом, который реально остаётся parse-error в v1 (напр. `значение` на
  верхнем уровне — единственный «отложенный» ведущий токен из бывшего списка) ([§TR-10.5](../../docs/trigger-model.md)).
- **Новые parse/sem-тесты триггеров.** Позитивы (три формы, все 6 единиц, `в "строка"`,
  `событие.поле`) + негативы (`значение`/`событие` вне контекста, неизвестная метрика, арность
  `запустить процесс`, действия-шага, диспетчер форм, пустой блок) — точные тексты из
  [§TR-7](../../docs/trigger-model.md).
- **Golden run-demo в `src/cmd/ladix/trigger_golden_test.go`.** Добавить golden на демо-программу,
  собираемую инлайн в `t.TempDir()` (без testdata-фикстуры): истина → процесс + задача в сводке;
  опционально контр-демо `< 1_000_000` → молчание; повтор `run --db` идентичен
  ([§TR-9](../../docs/trigger-model.md) D-26).
- **`examples/MANIFEST.md` синк.** Перевести `выручка.ladix` из категории parse-error/«отложенный
  синтаксис» в **parse-clean пример** (синтаксис v1, триггеры поддержаны); снять пометку
  «содержит отложенные `процесс`/`когда`». Добавить новый run-demo пример с пометкой
  «детерминированная фикстура, метрика без окна» ([§TR-10.7](../../docs/trigger-model.md)).
