# Phase 0 — Research & Decisions: Фронтенд триггеров + метрика-fire-if-true в `run`

**Feature**: 007a-trigger-frontend | **Date**: 2026-06-12 | **Plan**: [plan.md](./plan.md)

Открытых `[NEEDS CLARIFICATION]` **нет**: все развилки, которые мог бы поднять фронтенд триггеров
(размещение AST-узлов, два шва парсера, механизм контекст-гарда `значение`/`событие`, новизна текста
резолва метрики, точка врезки fire-if-true, эфемерность ЛОЖЬ-базы, golden-стратегия), закрыты в

поведения, контрактов и текстов слоя 007a (как `docs/engine-model.md` §EN для 006,
`docs/process-model.md` §PM для 005); при любом расхождении источников (SPEC §11.6/§13.4, README,

Документ фиксирует принятые решения в формате *Decision / Rationale / Alternatives*, чтобы код и

**D-TR-1** и **D-25…D-27** зафиксированы как **принятые** и **не переоткрываются** (spec.md
Assumptions прямо это требует: разрез B — чистый фронтенд трёх форм + метрика-fire-if-true в `run`;
нед/мес валидны без ошибки; формат `"ЧЧ:ММ"` отложен; FixedClock-флаг не вводится). Каждое решение
несёт ссылку на номер якоря (§TR-N / D-TR-1 / D-25…).

> **Граница 007a (§TR-0/§TR-11).** Фронтенд всех трёх форм + одна точка исполнения (метрика-fire-if-true

## D-R1. Размещение AST-узлов триггера: declBase + маркер-интерфейсы, type-switch без тегов (якорь: §TR-2, FR: FR-001…006)

- **Decision**: новые узлы AST для триггеров аддитивно, `ast` остаётся листовым:
  - **`TriggerDecl`** встраивает `declBase` (как `ProcessDecl`/`FunctionDecl`) → реализует
    `Decl` (`declNode()`+`topLevelItem()`), встаёт в `parseTopLevelItem`; поля `Spec TriggerSpec`
    и `Body *Block` (тело — штатный `*ast.Block` из `parseBlock`); `Pos()` = токен `когда`.
  - **`TriggerSpec`** — маркер-интерфейс (`Node` + пустой `triggerSpec()`), реализуемый тремя
    вспомогательными узлами `MetricTrigger`/`EventTrigger`/`ScheduleTrigger` (встраивают `specBase` →
    `base`, как `ElseClause`, **не** `declBase`).
  - **`ScheduleSpec`** — второй маркер-интерфейс с двумя подформами `EverySchedule` (`каждые
    DurationLiteral`) / `AtSchedule` (`в StringLiteral`).
  - **`ValueExpr`/`EventExpr`** — первичные выражения (встраивают `exprBase` → `exprNode()`),
    беспараметрические (как `NoneLit`), `Pos()` = токен `значение`/`событие`.
  - Дискриминация форм/подформ — **Go type-switch по конкретному типу**, без tag-полей.
  - `MetricTrigger.Op` имеет тип `ast.CompOp` (defined type над `BinOp`, op.go:55-68) —
    наземная правда, не выбор: комментарий op.go прямо фиксирует «на CompOp сошлётся будущий
    `MetricTrigger.Op`».
- **Rationale**: зеркало уже принятых конвенций кодовой базы — `declBase` для top-level деклараций,
  `exprBase` для выражений, `base` для вспомогательных узлов; конструкторы `New…(pos, …)`
  встраивают `base{pos}`. Маркер-интерфейс с type-switch идиоматичнее tag-поля: семпроход и парсер
  уже разбирают узлы свичем по конкретному типу (`parsePrimary`, `checkStmt`), новый код встаёт в
  тот же паттерн. Тело триггера — `*Block` (как `FunctionDecl.Body`), потому что парсится штатным
  `parseBlock()` без атрибутов, который возвращает именно `*ast.Block`.
- **Alternatives considered**:
  - **Один тип `TriggerSpec struct` с тегом-видом + nil-полями форм** — **отвергнут**: расходится с
    маркер-интерфейсной дискриминацией кодовой базы, плодит nil-проверки вместо type-switch.
  - **Один тип `ScheduleSpec struct{ Every *DurationLit; At *StringLit }` с одним ненулевым полем**
    — **отвергнут** (§TR-2): единообразие с `TriggerSpec` и явная дискриминация перевешивают.
  - **Хранить постфикс `событие.поле` внутри `EventExpr`** — **отвергнут** (см. D-R-FIELD ниже,
    §TR-2): дублировало бы логику доступа к полям.
  - **`MetricTrigger`/прочие как `declBase`** — **отвергнут**: это не самостоятельные top-level
    декларации, а разновидности спеки внутри `TriggerDecl` (зеркало `StepDecl` внутри `ProcessDecl`).
- **Статус**: РЕШЁН (§TR-2). FR-001…006.

## D-R2. Доступ `событие.поле` переиспользует FieldExpr — без расширения EventExpr (якорь: §TR-2, §TR-3 шов B, FR: FR-006)

- **Decision**: постфиксный доступ `событие.клиент` **не хранится** внутри `EventExpr`:
  - `parsePrimary` возвращает беспараметрический `EventExpr`;
  - существующий постфиксный слой выражений навешивает `FieldExpr{Target, Field}` без правок
    постфикс-парсера: `событие.клиент` → `FieldExpr{Target: *EventExpr, Field: Ident("клиент")}`;
  - `EventExpr` остаётся «голым» Primary (как `RunProcessExpr` не тащит постфикс-вызов внутрь).
- **Rationale**: `событие.поле` структурно идентичен любому `target.field`; переиспользование
  существующего `FieldExpr` убирает дублирование логики доступа к полям и держит `EventExpr`
  беспараметрическим. Это «собирается даром» — постфикс-парсер уже умеет навешивать `.поле` на любое
  Primary.
- **Alternatives considered**:
  - **Поле `Path []Ident` внутри `EventExpr`** — **отвергнут**: дублирует постфикс-логику доступа,
    которую `FieldExpr` уже реализует для всех целей.
  - **Контекстный лексер, выдающий `событие.поле` как единый токен** — **отвергнут**: ломает
    посимвольный сканер и принцип «парсер строит дерево, лексер не знает структуры».
- **Статус**: РЕШЁН (§TR-2, §TR-3 шов B). FR-006.

## D-R3. Два независимых шва парсера: top-level `когда` и Primary `значение`/`событие` (якорь: D-TR-1, §TR-3, FR: FR-006/020)

- **Decision**: триггеры подключаются **двумя независимыми швами**, которые нельзя сваливать в один:
  - **Шов A (top-level).** Удалить `KW_WHEN` из `isUnexpectedTopLevel`; добавить в каскад
    `parseTopLevelItem` ветку `if p.check(lexer.KW_WHEN) { return p.parseTriggerDecl() }` перед
    `isUnexpectedTopLevel`. Прецедент — **`KW_PROCESS`** (top-level декларация 005,
    `parse_stmt.go:22`).
  - **Шов B (Primary).** Добавить в `parsePrimary` ветки `case lexer.KW_VALUE → parseValueExpr` и
    `case lexer.KW_EVENT → parseEventExpr` (после `KW_RUN`, перед `default`); добавить `KW_VALUE`/
    `KW_EVENT` в предикат `startsExpression` (FIRST(Expression), рядом с `KW_RUN`). Прецедент —
    **`KW_RUN`** (первичное выражение, `parse_expr.go:196`).
  - **`KW_VALUE` остаётся недопустимым на top-level** через `isUnexpectedTopLevel` (`неожиданный
    токен 'значение'`); **`KW_EVENT` недопустим на top-level через default-путь** `parsePrimary`
    (в `isUnexpectedTopLevel` исходно не значился, результат тот же — `неожиданный токен 'событие'`).
- **Rationale**: якорь process-model описал `когда`/`значение` как пару «отложенных top-level-токенов»
  в одном списке `isUnexpectedTopLevel` — это было верно для 005 (оба отвергались), но в 007a они
  **расходятся**: `когда` становится объявлением верхнего уровня (шов A), а `значение`/`событие` —
  первичными выражениями (шов B) и остаются недопустимыми на top-level. Их нельзя обрабатывать одной
  правкой: `KW_WHEN` уходит из `isUnexpectedTopLevel` в `parseTopLevelItem`, а `KW_VALUE` уходит в
  `parsePrimary`. `значение`/`событие` обязаны работать как Primary внутри тел триггеров (`запустить
  процесс P(значение)`, `событие.клиент`) — если бы остались только top-level-отказом, тело триггера
  не могло бы на них ссылаться. Оба шва имеют прямые прецеденты в коде — мы их зеркалим, не изобретая
  механизм.
- **Alternatives considered**:
  - **Один общий шов «снять оба токена из `isUnexpectedTopLevel`»** — **отвергнут** (D-TR-1): `когда`
    и `значение` идут в разные места парсера (top-level vs Primary), общая правка их смешала бы.
  - **Контекстный лексер `значение`/`событие` как Ident в теле триггера** — **отвергнут** (§TR-3 шов
    B): нарушает «парсер строит дерево контекстно-свободно, контекст-гард — на семпроходе».
  - **Парсить условие метрики через общий `parseExpression` с top-level** — **отвергнут** (см. D-R5,
    §TR-3): тогда составное условие стало бы выразимым, ломая осознанное ограничение v1.
- **Статус**: РЕШЁН (D-TR-1, §TR-3). FR-006, FR-020.

## D-R4. Диспетчер форм по второму токену + плоский разбор спеки (якорь: §TR-3, FR: FR-001…003/019)

- **Decision**: `parseTriggerDecl` (новая функция в `parse_decl.go` рядом с `parseProcessDecl`)
  распознаёт вид триггера по **второму токену** (после `когда`), плоским switch:
  - `KW_METRIC` → `метрика` Ident `expectCompOp()` `parseExpression()` `:` `parseBlock()` →
    `MetricTrigger{Metric, Op, Threshold}`;
  - `KW_EVENT` → `событие` Ident `:` `parseBlock()` → `EventTrigger{Event}`;
  - `KW_SCHEDULE` → `расписание` `parseScheduleSpec()` `:` `parseBlock()` → `ScheduleTrigger{Spec}`;
  - `default` → `SE-TRIGGER-KIND` через `msgExpected("метрика, событие или расписание", peek())`,
    `synchronize()`, `return nil`.
  - `parseScheduleSpec`: `KW_EVERY` → `каждые` `expect(DURATION)` → `EverySchedule`; `KW_IN` →
    `в` `expect(STRING)` → `AtSchedule`; `default` → `SE-SCHEDULE-SPEC` через
    `msgExpected("каждые или в", peek())`.
  - `expectCompOp`: exact-match шести токенов `EQ/NEQ/LT/LE/GT/GE`; иначе `SE-EXPECT-COMPOP` через
    `msgExpected("оператор сравнения", got)`.
  - `parseBlock` **не меняется** — тело триггера разбирается тем же `parseBlock()`, что тела функции/
    шага (`NEWLINE INDENT Statement+ DEDENT`); пустой блок → `msgEmptyBlock`.
- **Rationale**: точный паттерн `KW_PROCESS` 005 — новая ветка в каскаде top-level. Все три новые
  синтаксические диагностики выражаются через **существующий** `msgExpected(expected, got)`
  (errors.go:40, формат `ожидалось '%s', получено '%s'`) подстановкой `expected` — отдельные
  const/функции это деталь оформления импл-чата, текст канонизирован якорем (§TR-7.F «наземная
  правда»). Переиспользование `parseBlock` даёт пустой-блок-диагностику и индентный контракт даром.
- **Alternatives considered**:
  - **Распознавать вид по lookahead глубже второго токена** — **отвергнут**: вид однозначно задаётся
    вторым токеном (`метрика`/`событие`/`расписание`), глубже смотреть незачем.
  - **Заводить новые const `msgTriggerKind`/`msgScheduleSpec`** — **отвергнут как обязательное**: текст
    фиксирован через `msgExpected`; именование хелпера — свобода импл-чата, но не текста (§TR-7.F).
- **Статус**: РЕШЁН (§TR-3). FR-001…003, FR-019.

## D-R5. Грамматика условия — ровно одно сравнение, плоский разбор (якорь: §TR-1, §TR-4 проверка 6, FR: FR-021)

- **Decision**: условие метрика-триггера — структурно **ровно одно сравнение** `метрика Ident
  CompOp Expression`:
  - разбирается плоско (имя → оператор → правая часть), **не** через общий `parseExpression` с
    рекурсией в логические операторы;
  - составное `X < Y и Z > W` **структурно невыразимо**: после правой части ожидается `:`, и
    попытка дописать `и Z > W` упирается в `expect(COLON)` → синтаксическая ошибка про ожидаемое `:`;
  - **семантической диагностики «составное условие» НЕТ** — это не семантическая проверка, а
    отсутствие грамматической продукции.
- **Rationale**: ограничение «одно сравнение» — **структурное, а не приоритетное** решение: грамматика
  физически не собирает логику в условии, поэтому отказ наблюдается как синтаксическая ошибка
  ожидания `:`, а не как отдельная семантическая диагностика. Это осознанное ограничение v1 (SPEC
  §12, решение владельца), расширяемое аддитивно в v2 (заменить плоский разбор на `parseExpression`
  с булевым результатом / правую рекурсию по `и`/`или` в `MetricTrigger`) без слома существующего
  синтаксиса.
- **Alternatives considered**:
  - **Парсить условие общим `parseExpression` + семантически отвергать составное** — **отвергнут**
    (§TR-4 проверка 6): ввёл бы лишнюю диагностику и сделал бы составное синтаксически выразимым, что
    усложнило бы аддитивное расширение в v2.
  - **Ввести диагностику «составное условие не поддерживается»** — **отвергнут**: конструкция просто
    не собирается грамматикой; спека прямо требует, чтобы такой диагностики не существовало (FR-021).
- **Статус**: РЕШЁН (§TR-1, §TR-4 проверка 6). FR-021.

## D-R6. Контекст-гарды значение/событие — флаги inMetricTrigger/inEventTrigger в обходе (якорь: §TR-4 проверка 3, FR: FR-007)

- **Decision**: контекст «значение» / «событие» проверяется новыми флагами обхода, зеркало
  существующего `inStep`:
  - в сигнатуру `checkStmt`/`checkExpr` (и связанных `checkStmts`/`checkElse`) добавляются два
    взаимоисключающих флага `inMetricTrigger`/`inEventTrigger` (оба false на top-level/в функции/в
    шаге; не меняются при нисходе в `если`/`пока`/`для`, как `inStep`);
  - новые case-ветки: `case *ast.ValueExpr` → если `!inMetricTrigger` → `semErr(e.Pos(), msgValueCtx)`
    (`TR-VAL-CTX`); `case *ast.EventExpr` → если `!inEventTrigger` → `semErr(e.Pos(), msgEventCtx)`
    (`TR-EVT-CTX`);
  - `analyzeTrigger` выставляет `inMetricTrigger=true` для метрика-тела, `inEventTrigger=true` для
    событие-тела, оба false для расписание-тела (там недопустимы оба имени).
  - Тексты дословно: `выражение 'значение' допустимо только в теле триггера метрики` (TR-VAL-CTX);
    `выражение 'событие' допустимо только в теле триггера события` (TR-EVT-CTX).
- **Rationale**: `inStep`-флага недостаточно — он один на «вне шага», а нужен **вид** окружающего
  триггера (метрика vs событие vs расписание). Минимальное расширение — два булевых флага, пробрасываемых
  ровно как `inStep`. Этим же даром закрывается изоляция видов (§TR-5): в событие-теле `значение` →
  `TR-VAL-CTX`, в метрика-теле `событие` → `TR-EVT-CTX`, в расписание-теле любое из них →
  соответствующая `TR-*-CTX`. Точное место добавления (отдельные параметры vs маленький `ctx`-struct)
  — импл-факт по факту существующей сигнатуры обхода (§TR-4 TODO-FACT); архитектурно — два флага.
- **Alternatives considered**:
  - **Один enum-параметр `triggerKind` (none/metric/event/schedule)** — **отвергнут как обязательное**:
    два булевых флага точнее зеркалят `inStep` и проще читаются в case-ветках; enum — допустимая
    импл-деталь, но не предписан.
  - **Контекстный лексер/резолв `значение` как Ident в скоупе** — **отвергнут** (§TR-3): нарушает
    контекстно-свободный парсинг; гард обязан жить на семпроходе.
- **Статус**: РЕШЁН (§TR-4 проверка 3). FR-007.

## D-R7. Новый текст `метрика '<имя>' не объявлена` ≠ CLI-текст `неизвестная метрика '%s'` (якорь: §TR-4 проверка 1, §TR-7.B, FR: FR-008)

- **Decision**: резолв имени в условии метрика-триггера против реестра `i.metrics`:
  - незарегистрированное имя → **новый текст** `метрика '<имя>' не объявлена` (`TR-MET-UNDECL`);
  - имя объявлено, но не метрика (источник/процесс/функция) → `'<имя>' — не метрика`
    (`TR-MET-NOTMETRIC`) — **существующий** текст из `metric.go`/`checkMetricDecl`, переиспользуется;
  - правая часть сравнения валидируется тем же `checkExpr` (резолв имён, арность вызовов); тип-чек
    «число vs число» остаётся рантайму (зеркало FR-022 — `если`/`пока` тип условия не статизируют).
- **Rationale**: текст `метрика '<имя>' не объявлена` — **новый** для семпрохода условия триггера и
  **отличается** от существующего CLI-текста `неизвестная метрика '%s'` (eval/metric.go, точка
  `metric`-подкоманды). Это два разных контекста резолва: CLI-текст возникает, когда оператор просит
  вычислить метрику по имени из командной строки (`ladix metric <имя>`), а новый — когда семпроход
  резолвит имя метрики **внутри декларативного условия триггера** на стадии компиляции. Объединять их
  нельзя: один — рантайм-CLI-диагностика подкоманды, другой — семантическая ошибка валидации AST;
  стиль нового текста — прямое зеркало `функция 'f' не объявлена` / `процесс '<P>' не объявлен`.
  Различающий `'<имя>' — не метрика` уже существует в `metric.go` и зеркалит каскад `checkRunProcess`
  (`'<P>' — функция, не процесс` / `'<P>' — не процесс`), поэтому переиспользуется без нового текста.
- **Alternatives considered**:
  - **Переиспользовать CLI-текст `неизвестная метрика '%s'` для условия триггера** — **отвергнут**:
    разные контексты (рантайм-CLI vs семпроход-валидация); сообщение «неизвестная метрика» подходит
    подкоманде, но в условии триггера семантически точнее «не объявлена» (в один ряд с `функция/процесс
    не объявлен`).
  - **Завести и новый текст для «не метрика»** — **отвергнут**: `'<имя>' — не метрика` уже есть в
    `metric.go`, дублировать незачем; YAGNI и единство реестра.
- **Статус**: РЕШЁН (§TR-4 проверка 1, §TR-7.B). FR-008.

## D-R8. Переиспользование гардов действий-шага / запуска процесса / `вернуть` (якорь: §TR-4 проверки 4–5, §TR-7.C/D, FR: FR-009…011)

- **Decision**: тело триггера трактуется как **контекст вне шага** (`inStep=false`), что даёт
  бесплатно три переиспользования без нового кода и текстов:
  - **действия-шага** (`присвоить`/`вызвать`/`уведомить` — узлы `AssignAction`/`CallAction`/
    `NotifyAction`) → существующий гард `inStep=false` (analyze.go:365-375), текст `действие '<имя>'
    допустимо только в шаге процесса` (§PM-6.B), `<имя>` через `constructName`;
  - **`запустить процесс P(args)`** → существующий `checkRunProcess` (analyze.go:471-494) без правок:
    args-first fail-fast, резолв только против реестра процессов `i.processes`, сверка арности; четыре
    текста §PM-6.C байт-точно (`'<P>' принимает N аргументов, передано M` / `процесс '<P>' не
    объявлен` / `'<P>' — функция, не процесс` / `'<P>' — не процесс`);
  - **`вернуть`** → существующая диагностика `'вернуть' допустимо только внутри функции` (тело
    триггера не функция); `прервать`/`продолжить` — только внутри `пока`/`для`.
- **Rationale**: тело триггера семантически тождественно top-level по набору разрешённых конструкций
  (императивное ядро минус действия-шага). Разрешённое множество определяется **отрицательно**: всё,
  что валидно на top-level/в функции, валидно и здесь; всё, что гардируется `inStep`, запрещено.
  Поскольку тело обходится той же цепочкой `checkStmt → checkExpr`, `RunProcessExpr` и действия
  попадают в существующие проверки автоматически. Никакого нового списка «разрешённых в триггере
  операторов» не заводится; единственное расширение поверх top-level — `значение`/`событие` (D-R6).
- **Alternatives considered**:
  - **Новый текст «действие недопустимо в теле триггера»** — **отвергнут** (§TR-7.C): действие
    недопустимо вне шага в принципе, и «шаг процесса» в существующем тексте корректно описывает
    единственное место, где оно разрешено.
  - **Отдельный путь резолва процесса для триггера** — **отвергнут**: `checkRunProcess` уже
    args-first и резолвит только против реестра процессов; дублировать нечего.
- **Статус**: РЕШЁН (§TR-4 проверки 4–5, §TR-7.C/D). FR-009…011.

## D-R9. Полная валидация тела событие-триггера, хотя в `run` оно no-op (якорь: §TR-5, §TR-8.4, FR: FR-022)

- **Decision**: событие-триггер в 007a **полностью валидируется** семпроходом, несмотря на то что в
  `run` он не исполняется:
  - контекст-гард `событие` через `inEventTrigger=true` (доступ `событие` и `событие.поле` приняты);
  - запрет действий-шага тем же `inStep=false`;
  - арность `запустить процесс` тем же `checkRunProcess`;
  - в `run` тело событие-триггера — **no-op** (исполнения нет), вместо него печатается строка-заглушка
    (D-R12).
- **Rationale**: фронтенд фиксируется навсегда (§TR-0): программа, валидная в 007a, остаётся валидной
  в 007b. Поэтому контекст-гарды, запрет действий и арность процессов должны ловиться уже сейчас —
  иначе невалидное событие-тело прошло бы 007a и упало бы только при подъёме `serve` в 007b. Расхождение
  «компилируется vs исполняется» локализовано **в одной точке** — проходе §TR-6 (no-op для событие/
  расписание), и нигде больше в конвейере (§TR-8.4). Контракт инжекции `событие` зафиксирован для 007b
  (`env.Define("событие", eventRecord)`), но в 007a фактической инжекции нет.
- **Alternatives considered**:
  - **Не валидировать событие-тело в 007a (отложить вместе с исполнением)** — **отвергнут** (FR-022):
    сломало бы инвариант границы — невалидный фронтенд протёк бы в 007b.
  - **Валидировать частично (только синтаксис, без контекст-гарда)** — **отвергнут**: гард `событие` и
    запрет действий — часть синтаксис-фиксируется-навсегда контракта.
- **Статус**: РЕШЁН (§TR-5, §TR-8.4). FR-022.

## D-R10. Fire-if-true — экспортный метод интерпретатора, вызов из main после interp.Run (якорь: §TR-6, §TR-8, FR: FR-008/012…018)

- **Decision**: точка исполнения метрика-fire-if-true живёт в `eval` как **экспортный метод
  интерпретатора** (напр. `RunTriggers(w io.Writer)`), вызываемый из `cmd/ladix/main.go`:
  - **место врезки** — строго между шагом 8 (`interp.Run(prog)`, main.go:196) и шагом 10
    (`ListPendingTasks`, main.go:202), внутри замыкания `guard`; единственное корректное место
    (§TR-8.1);
  - **алгоритм §TR-6.3** на каждый метрика-триггер в порядке объявления (`prog.Items`): (1) вычислить
    значение метрики через существующий конвейер метрик → числовое `value.Value`; (2) вычислить порог
    (правую часть) в среде верхнего уровня (глобальные `пусть` доступны); (3) применить `CompOp`
    через **существующий оператор сравнения 003** (никакой новой арифметики) → `Булево`; (4) при
    истине — инжектировать read-only `значение` = вычисленное число метрики и исполнить тело-`Block`;
  - `запустить процесс` внутри тела идёт штатным путём движка 006 (`i.runtime.StartProcess` →
    `Engine.StartProcess` → `Engine.Start`): минт id `p-NNNNNN`, продвижение до первого ожидания,
    персист под `--db`; порождённые задачи попадают в сводку того же прогона;
  - при ложном условии — тело не исполняется, `значение` не инжектируется, процесс не запускается
    (молчание, базовый контракт).
- **Rationale**: размещение в `eval` сохраняет **инкапсуляцию** env/реестра метрик/реестра триггеров
  (внешний код не лезет в приватные карты интерпретатора) и принцип **V** (нет глобального состояния —
  проход это метод значения-интерпретатора, реестр триггеров — поле `Interpreter`, `ProcessRuntime`
  инжектируется как в 006). Порядок «после `interp.Run`, до сводки» обязателен: глобальные `пусть`
  связываются именно исполнением top-level (шаг 8), тело/условие триггера на них ссылаются, а
  запущенные процессы должны успеть в сводку висящих задач (шаг 10). Запускать проход раньше — читать
  несвязанные имена. Ошибка исполнения тела всплывает как `error` и обрабатывается как ошибка
  `interp.Run` (двухстрочный канон, exit 1, под `guard`).
- **Alternatives considered**:
  - **Исполнять триггеры внутри `interp.Run` (как часть top-level прохода)** — **отвергнут** (§TR-8.1):
    тогда триггеры оценивались бы до полного связывания глобалов и до того, как процессы успели бы
    попасть в сводку; порядок «после Run» нарушен.
  - **Реализовать проход в `cmd/ladix` поверх публичного API** — **отвергнут**: вытолкнул бы наружу
    приватные env/метрики, сломав инкапсуляцию и принцип V.
  - **Новый оператор сравнения для условия** — **отвергнут** (§TR-6.3): переиспользуется готовый
    оператор сравнения 003; интерпретатор по существу не трогается.
- **Статус**: РЕШЁН (§TR-6, §TR-8). FR-008, FR-012…018.

## D-R11. Эфемерная ЛОЖЬ-база: trigger_state не читается/не пишется даже под --db (якорь: §TR-6.2, §TR-8.3, FR: FR-014, SC-004)

- **Decision**: предыдущее состояние каждого триггера считается **ЛОЖЬ эфемерно** (только в памяти
  текущего `run`):
  - durable `trigger_state` **не читается и не пишется** — даже под `--db`; таблицы состояния
    триггеров в 007a нет вовсе;
  - SQLite под `--db` используется движком процессов для инстансов/задач (как в 006), но состояния
    триггеров не касается;
  - следствие: «переход ложь→истина» эквивалентен «условие истинно сейчас» → фактическое правило
    «оценить условие один раз; если истинно — исполнить тело»; повторный `run --db` того же файла на
    той же БД снова видит «база = ЛОЖЬ» и снова срабатывает идентично;
  - **контраст**: процессы и задачи, порождённые триггером, персистятся в SQLite штатно (006) —
    эфемерность относится **исключительно** к состоянию триггеров.
- **Rationale**: edge-детект и подавление повторных срабатываний — носитель демона `serve` (007b,
  §TR-11 п.2). В 007a проход одноразовый, поэтому моделировать durable-состояние незачем, а его
  отсутствие делает demo детерминированным и повторяемым (директива владельца/архитектора): второй
  прогон не зависит от истории первого. Это сознательный контраст с at-most-once семантикой метрики в
  007b (сдвиг состояния до тела), которая ляжет аддитивно.
- **Alternatives considered**:
  - **Писать `trigger_state` уже в 007a (подготовить таблицу)** — **отвергнут** (§TR-6.2): edge-детект
    — функция 007b; преждевременная таблица усложнила бы demo и сделала бы повторный `run`
    неповторяемым.
  - **Эфемерность распространить и на процессы/задачи** — **отвергнут**: процессы человека-в-цикле
    обязаны персиститься под `--db` (контракт 006); ЛОЖЬ-база касается только триггеров.
- **Статус**: РЕШЁН (§TR-6.2, §TR-8.3). FR-014, SC-004.

## D-R12. Строки-заглушки событие/расписание в `run` — импл-факт, закрывается кодом (якорь: §TR-6.4, FR: FR-018)

- **Decision**: для каждого событие- и расписание-триггера `run` печатает **ровно одну** строку-заглушку
  со смыслом «требует serve (фича 007b)»:
  - одна строка на триггер, в порядке объявления (как §TR-6.1); исполнение — no-op;
  - модельная форма (§TR-6.4): `<вид> триггер '<имя>' требует serve (фича 007b)`, где `<вид>` ∈
    {`событие`, `расписание`};
  - **точная форма `<имя>` и дословный текст** — **импл-факт** (§TR-6 TODO-FACT): закрывается кодом по
    факту полей идентификации триггера в AST (у расписания собственного имени нет — кандидат текст/
    индекс), **не пробел спеки**.
- **Rationale**: это честный сигнал пользователю, что декларация валидна, но исполнение живёт в демоне
  `serve` (007b). Точная лексика строки и форма `<имя>` — деталь оформления, не поведенческое решение;
  якорь помечает её TODO-FACT, закрываемым на импл-проходе по фактическим полям AST, а не догадкой в
  спеке (конституция IX — импл-факты помечены и закрываются кодом).
- **Alternatives considered**:
  - **Молчать на событие/расписание-триггерах** — **отвергнут** (FR-018): пользователь не отличил бы
    «не поддержано в run» от «проигнорировано»; строка-заглушка — явный сигнал.
  - **Зафиксировать дословный текст в спеке сейчас** — **отвергнут** (§TR-6 TODO-FACT): форма `<имя>`
    зависит от фактических полей идентификации в AST; преждевременная фиксация рисковала бы дрейфом.
- **Статус**: РЕШЁН (§TR-6.4). FR-018.

## D-R13. Инжекция `значение` через env.Define — read-only, прецедент параметров функций (якорь: §TR-5, FR: FR-015/025)

- **Decision**: предопределённое имя `значение` инжектируется в **локальный** env тела триггера:
  - перед исполнением метрика-тела движок делает `env.Define("значение", <численное значение
    метрики>)` — read-only, тип числовой (Целое/Дробное, как вернула метрика);
  - прецедент — параметры функций / предопределённые Периоды, связываемые через `env.Define`
    (read-only);
  - **порядок Define** (§TR-5): (1) глобалы уже связаны (проход идёт после `interp.Run`); (2) инжекция
    `значение` — первое и единственное предопределённое связывание в локальном env; (3) локальные
    `пусть` тела связываются по ходу исполнения стандартной семантикой блока;
  - имя инжектируется в **локальный** env (не глобальный) → не протекает наружу; коллизия с
    глобальным `пусть` того же имени невозможна (`значение`/`событие` — жёсткие KW, не Ident);
  - тело видит глобальные `пусть` и метрики **read-only**; локальные `пусть` тела пишутся в локальный
    env и эфемерны (исчезают по завершении прохода).
- **Rationale**: инжекция предопределённого имени через `env.Define` в производный локальный env —
  ровно тот механизм, которым уже связываются параметры функций и предопределённые Периоды; новый код
  не требуется, только новая точка вызова. Локальность гарантирует, что fire-if-true проход
  одноразовый и без побочных эффектов на глобалы (эфемерность триггера, §TR-6). `значение` = то же
  число метрики, что сравнивалось в условии (шаг 1 §TR-6.3), поэтому `запустить процесс P(значение)`
  передаёт текущий снимок метрики.
- **Alternatives considered**:
  - **Инжектировать `значение` в глобальный env** — **отвергнут** (§TR-5): протекло бы наружу и
    нарушило бы read-only-видимость глобалов из тела.
  - **Хранить `значение` как спец-поле интерпретатора, минуя env** — **отвергнут**: `ValueExpr`
    резолвится через стандартный lookup env (как Ident параметра); спец-канал дублировал бы механизм.
- **Статус**: РЕШЁН (§TR-5). FR-015, FR-025.

## D-R14. Безвредность forever-cache при одноразовом проходе (якорь: §TR-0, §TR-6.3, §TR-11 п.2)

- **Decision**: forever-cache интерпретатора 003 (нет `Reset` между обращениями) в 007a **безвреден**
  и **сброс не нужен**:
  - проход fire-if-true одноразовый — метрика в условии вычисляется ровно один раз за `run`;
  - повторного обращения к кешу с ожиданием иного результата нет → отдельный `Reset` между триггерами
    не требуется;
  - блокер кеша системно решается в **007b** (§TR-11 п.2): при многократной переоценке метрик на
    тиках демона нужен честный шов (`ResetRunState()` либо свежий `Interpreter` per-tick) — оба
    варианта аддитивны, синтаксис не затрагивают; РЕШЕНИЕ за владельцем на kickoff 007b.
- **Rationale**: это фундамент обоснования разреза 007a/007b (§TR-0): forever-cache мешает только
  повторной переоценке (демон), а в `run` условие оценивается один раз — поэтому отсутствие `Reset`
  ни на что не влияет, и demo без демона корректно. Зафиксировано как Assumption спеки, чтобы код не
  городил преждевременный сброс кеша, который понадобится лишь в 007b.
- **Alternatives considered**:
  - **Ввести `ResetRunState()` уже в 007a** — **отвергнут** (§TR-11 п.2): преждевременно — при
    одноразовом проходе сбрасывать нечего; решение по форме сброса — за kickoff 007b.
  - **Создавать свежий `Interpreter` под проход триггеров** — **отвергнут**: проход обязан видеть тот
    же env с уже связанными глобалами (D-R10/D-R13); новый интерпретатор потерял бы их.
- **Статус**: РЕШЁН (§TR-0, §TR-6.3, §TR-11 п.2).

## D-R15. Разведение golden-артефактов: parse-канон vs run-фикстура без окна (якорь: D-25…D-27, §TR-9)

- **Decision**: два **разных** эталона, которые нельзя путать:
  - **Канон синтаксиса** — `examples/выручка.ladix`: метрика с окном (`период: ежемесячно` +
    `по_дате:`), но parse/sem **не вычисляют окно** → артефакт **дата-независим**; роль —
    parse-clean golden (лексер+парсер+семпроход чисто, ноль диагностик, тело с `значение`);
  - **Demo исполнения** — детерминированная run-проверка живёт в
    `src/cmd/ladix/trigger_golden_test.go`; программа-пример строится **инлайн** в `t.TempDir()`
    (без отдельной testdata-фикстуры) с метрикой **БЕЗ окна** (`выручка_всего` =
    `сумма(сумма_заказа)` по оплаченным = **2 000 000** при любой дате) → run-golden stdout
    детерминирован; триггер `когда метрика выручка_всего < 3_000_000` всегда истинен стабильно;
  - `значение` в run-golden = снимок метрики `выручка_всего` = 2 000 000 во всех прогонах (D-27);
  - контр-демо (опционально, порог `< 1_000_000`) → ложно → пустая сводка, детерминированный golden
    ветки «условие ложно»;
  - имя run-фикстуры/контр-демо — предложение, финал за импл-чатом.
- **Rationale**: `выручка.ladix` **не годится** для run-golden — её метрика с `период: ежемесячно`
  строит окно от `сегодня()`, а данные `sales.json` за май 2026, поэтому stdout «плывёт по дате
  запуска» (2 000 000 в мае vs 0 вне мая, §SM-10): зафиксировать такой snapshot в testdata = заложить
  мину, протухающую при смене системной даты. FixedClock-флаг в v1 не вводим (директива владельца) —
  вместо контроля времени убираем **зависимость** от времени: метрика без `период:`/`по_дате:` (§SM-8
  — окна нет, все записи проходят фильтр тривиально) даёт стабильный агрегат. При этом parse/sem
  `выручка.ladix` детерминированы (окно в этих фазах не вычисляется), поэтому она остаётся годным
  parse-clean каноном синтаксиса.
- **Alternatives considered**:
  - **Один артефакт `выручка.ladix` и для parse, и для run** — **отвергнут** (D-25): run-stdout
    зависел бы от даты, golden протух бы.
  - **Ввести FixedClock-флаг для стабилизации run-golden** — **отвергнут** (D-26, директива владельца):
    в v1 не вводится; устраняется зависимость от времени, а не время.
- **Статус**: РЕШЁН (D-25…D-27, §TR-9). FR-016/023, SC-001/003.

## D-R16. Граница 007a/007b и аддитивность: что отложено и почему (якорь: §TR-11, FR: FR-004/005)

- **Decision**: зафиксировать, что синтаксис/AST/диагностики 007a **фиксируются навсегда**, а отложенное
  ляжет в 007b **аддитивно**:
  - **«нед/мес → ошибка» сознательно НЕ вводилось**: исполнение расписания календарное (нед/мес —
    календарный сдвиг, консистентно с `срок`/D-19, а не фиксированный множитель), поэтому в 007a все
    6 единиц `каждые` валидны без ограничений (FR-004); исполнение добавится в 007b (§TR-11 п.3);
  - **формат `"ЧЧ:ММ"` отложен**: язык не валидирует содержимое строковых литералов на семпроходе, а
    значение расписания в `run` это no-op → в реестре 007a диагностики формата времени **нет вовсе**
    (FR-005, §TR-7.E); валидация (ведущий ноль, диапазон 00–23 : 00–59) — новый код 007b (§TR-11 п.3);
  - узел `AtSchedule` (007a) принимает строку как есть; диагностика формата ляжет аддитивно, синтаксис
    007a не трогается;
  - **инвариант границы**: программа на `.ladix`, валидная в 007a, остаётся валидной в 007b без правок
    — все три формы, узлы `TriggerDecl`/`ValueExpr`/`EventExpr`, контекст-гарды и реестр диагностик в
    007b только **дополняются исполнением** (демон, состояние, доставка).
- **Rationale**: разрез B (владелец) разводит «фронтенд фиксируется» и «исполнение откладывается».
  Вводить «нед/мес → ошибка» было бы вредно: эти единицы синтаксически валидны и в 007b будут исполняться
  календарно, поэтому отвергать их сейчас сломало бы аддитивность (валидная-в-007a программа стала бы
  невалидной?). То же с форматом `"ЧЧ:ММ"`: преждевременная валидация без исполнения расписания не
  имеет применения и потребовала бы канонического текста семош, который определяется в 007b вместе со
  всеми деталями.
- **Alternatives considered**:
  - **Отвергать `нед`/`мес` в 007a (раз исполнение отложено)** — **отвергнут** (§TR-11 п.3): сломало бы
    инвариант границы; единицы валидны, исполнение календарное добавится позже.
  - **Валидировать `"ЧЧ:ММ"` уже в 007a** — **отвергнут** (§TR-4 проверка 2, §TR-7.E): нет прецедента
    проверки содержимого строк на семпроходе; значение расписания в `run` не используется; текст и
    детали — за 007b.
- **Статус**: РЕШЁН (§TR-11). FR-004, FR-005.
