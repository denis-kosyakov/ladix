# Phase 1 — Data Model: Фронтенд триггеров и метрика-fire-if-true в `run` (007a)

**Feature**: 007a-trigger-frontend | **Date**: 2026-06-12 | **Plan**: [plan.md](./plan.md)

Описывает сущности **AST** фичи 007a и контракт предопределённых имён `значение`/`событие`. Все узлы —
аддитивное расширение пакета `internal/ast`; новых пакетов нет, `ast` остаётся **листовым** (узлы не
импортируют `errors`, несут только локальную `ast.Position`). 007a добавляет одну top-level декларацию
(`TriggerDecl`), маркер-интерфейс формы `TriggerSpec` с тремя реализациями, маркер-интерфейс подформы
расписания `ScheduleSpec` с двумя реализациями и два первичных выражения (`ValueExpr`/`EventExpr`).
Доступ `событие.поле` **не** вводит нового узла — переиспользуется существующий `FieldExpr`.

**Источник истины — `docs/trigger-model.md` §TR-2 (формы узлов) и §TR-5 (контракт scope тела триггера);
при любом расхождении побеждает якорь.** Поля, конструкторы и инварианты ниже выведены из §TR-2/§TR-5 и
сверены с реальным кодом (`ast/node.go` — `base`/`declBase`/`exprBase`/`Node`/`TopLevelItem`; `ast/op.go`
— `CompOp` как defined type над `BinOp`; `ast/expr.go` — `FieldExpr`/`RunProcessExpr`; `ast/literal.go` —
`Ident`/`DurationLit`/`StringLit`; `ast/block.go` — `Block`; `ast/position.go` — локальная `Position`).
Эталон стиля/глубины — `specs/006-process-engine/data-model.md`.

> **Конвенции AST (наземная правда).** `declBase` даёт `Pos()` + маркеры `declNode()`/`topLevelItem()`
> (узел встаёт в union `Decl`/`TopLevelItem`); `exprBase` даёт `Pos()` + `exprNode()` (узел встаёт в
> `Expression`); `base` даёт только `Pos()` (вспомогательные узлы). Конструкторы `New…(pos Position, …)`
> встраивают `base{pos}`. `Position` — 1-based, колонка в **рунах** (конституция IV). Дискриминация форм —
> Go type-switch по конкретному типу, **без tag-полей** (зеркало того, как `parsePrimary`/семпроход уже
> разбирают узлы свичем по типу).
>
> **007a НЕ моделирует durable-состояние.** Таблицы `trigger_state`, edge-детект «ложь→истина» и любые
> Store-сущности триггеров **отсутствуют** — база триггера в `run` считается ЛОЖЬ эфемерно, только в
> памяти прогона (§TR-6.2). Это отложено в 007b и здесь не описывается.

## 1. `TriggerDecl` — top-level декларация триггера (§TR-2, FR-001)

Верхнеуровневая декларация `когда <Spec>: <Body>`. Зеркало `ProcessDecl`/`FunctionDecl`: встраивает
`declBase` (→ реализует `Decl` и `TopLevelItem`), поэтому встаёт в каскад `parseTopLevelItem` рядом с
`процесс` (шов A, §TR-3). Регистрируется глобально на Шаге 1 `Analyze`, но **в момент объявления не
исполняется** — исполнение (только метрика-форма) происходит отдельным проходом fire-if-true в `run`
(§TR-6). Форма вынесена в поле-интерфейс `Spec`; тело — `*Block` (как `FunctionDecl.Body`), потому что
парсится штатным `parseBlock()` без атрибутов.

```go
// TriggerDecl — объявление триггера верхнего уровня: «когда <Spec>: <Body>».
// Pos() = токен «когда». Spec — одна из трёх форм (MetricTrigger/EventTrigger/
// ScheduleTrigger). Body — индентный блок (тело триггера, императивное ядро).
type TriggerDecl struct {
	declBase
	Spec TriggerSpec // форма триггера (метрика/событие/расписание)
	Body *Block      // тело: NEWLINE INDENT Statement+ DEDENT
}

func NewTriggerDecl(pos Position, spec TriggerSpec, body *Block) *TriggerDecl {
	return &TriggerDecl{declBase: declBase{base{pos}}, Spec: spec, Body: body}
}
```

### Поля

| Поле | Тип | Семантика | FR |
|---|---|---|---|
| `declBase` | встраивание | `Pos()` + маркеры `declNode()`/`topLevelItem()` — `TriggerDecl` встаёт в union `Decl`/`TopLevelItem` | FR-001/FR-020 |
| `Spec` | `TriggerSpec` | форма-маркер: `*MetricTrigger` ИЛИ `*EventTrigger` ИЛИ `*ScheduleTrigger` (type-switch) | FR-002/FR-003 |
| `Body` | `*Block` | тело триггера: непустой индентный блок; то же `parseBlock`, что у функции/шага | FR-001/FR-009 |

### Инварианты

- **Локальная позиция.** `Pos()` = `ast.Position` токена `когда` (1-based, руны); узел НЕ импортирует
  `errors` (листовость пакета `ast`).
- **Тело непустое.** `Body.Stmts` содержит ≥1 оператор; пустой блок после `:` ловит **парсер**
  (`parseBlock` → `msgEmptyBlock`, FR-001), а не семпроход и не инвариант узла.
- **Регистрируется глобально, не исполняется при объявлении.** Семпроход регистрирует декларацию (Шаг 1
  `Analyze`); исполнение — только для метрика-формы и только в `run` (§TR-6), для событие/расписание в
  `run` — no-op + строка-заглушка (FR-018).
- **Союз форм закрыт.** `Spec` принимает ровно одну из трёх реализаций `TriggerSpec`; иной вид триггера
  невыразим грамматически (диспетчер форм → `SE-TRIGGER-KIND`, §TR-3/FR-019).

## 2. `TriggerSpec` — маркер-интерфейс трёх форм (§TR-2, FR-002/003)

Спецификация формы триггера. Вспомогательные узлы (встраивают `base` через `specBase`, как `ElseClause`),
несут только данные формы и позицию. Дискриминация — Go type-switch по конкретному типу, **без tag-полей**.

```go
// TriggerSpec — форма триггера. Реализуется MetricTrigger, EventTrigger,
// ScheduleTrigger. Маркер triggerSpec() — пустой метод (как stmtNode/exprNode).
type TriggerSpec interface {
	Node
	triggerSpec()
}

type specBase struct{ base }

func (specBase) triggerSpec() {}
```

### 2.1. `MetricTrigger` — «метрика Metric Op Threshold» (FR-002/008)

Единственная форма, исполняемая в `run` (fire-if-true, §TR-6). Условие — **ровно одно сравнение**
(грамматика плоская: имя → оператор → выражение, без рекурсии в логические операторы; §TR-3 шов A).

```go
// MetricTrigger — «метрика Metric Op Threshold». Pos() = токен «метрика».
// Условие — ОДНО сравнение (ограничение v1, §TR-4 проверка 6).
type MetricTrigger struct {
	specBase
	Metric    Ident      // имя метрики (резолвится семпроходом против i.metrics)
	Op        CompOp     // оператор сравнения (==,!=,<,<=,>,>=)
	Threshold Expression // правая часть сравнения (любое выражение)
}

func NewMetricTrigger(pos Position, metric Ident, op CompOp, threshold Expression) *MetricTrigger {
	return &MetricTrigger{specBase: specBase{base{pos}}, Metric: metric, Op: op, Threshold: threshold}
}
```

| Поле | Тип | Семантика | FR |
|---|---|---|---|
| `specBase` | встраивание | `Pos()` (= токен `метрика`) + маркер `triggerSpec()` | FR-002 |
| `Metric` | `ast.Ident` | имя метрики; семпроход резолвит против реестра `i.metrics` | FR-008 |
| `Op` | `CompOp` | оператор сравнения — одна из `CompEq/CompNeq/CompLt/CompLe/CompGt/CompGe` | FR-002 |
| `Threshold` | `ast.Expression` | порог (правая часть); вычисляется в среде верхнего уровня в `run` | FR-002/FR-013 |

- **`Op` — defined type `CompOp` над `BinOp`** (`ast/op.go:56`, НЕ type-alias): шесть констант
  `CompEq/CompNeq/CompLt/CompLe/CompGt/CompGe` (значения `OpEq/OpNeq/OpLt/OpLe/OpGt/OpGe`), отображают
  `== != < <= > >=`; `CompOp.String()` переиспользует `BinOp.String()`. Это канон (`op.go:55` прямо
  фиксирует ссылку `MetricTrigger.Op`), не выбор.
- **Инвариант «одно сравнение».** Структурное ограничение грамматики, не поле и не семпроверка: составное
  условие (`X < Y и Z > W`) невыразимо — попытка дописать логику упирается в `expect(COLON)` →
  синтаксическая ошибка про ожидаемое `:` (FR-021, §TR-4 проверка 6).
- **Тип «число vs число» не статизируется** — остаётся рантайму (зеркало того, что `если`/`пока` не
  форсируют тип условия, FR-022). Семпроход валидирует `Threshold` тем же `checkExpr` (резолв имён,
  арность вызовов; FR-008).

### 2.2. `EventTrigger` — «событие Event» (FR-003)

Парсится и **полностью валидируется** семпроходом (контекст-гард `событие`, запрет действий-шага, арность
процессов; FR-022), но в `run` **не исполняется** — no-op + строка-заглушка (FR-018). В теле доступно
предопределённое имя `событие` (§6).

```go
// EventTrigger — «событие Event». Pos() = токен «событие».
type EventTrigger struct {
	specBase
	Event Ident // имя события
}

func NewEventTrigger(pos Position, event Ident) *EventTrigger {
	return &EventTrigger{specBase: specBase{base{pos}}, Event: event}
}
```

| Поле | Тип | Семантика | FR |
|---|---|---|---|
| `specBase` | встраивание | `Pos()` (= токен `событие`) + маркер `triggerSpec()` | FR-003 |
| `Event` | `ast.Ident` | имя события; в 007a имя события против реестра не резолвится (событий нет до 007b) | FR-003/FR-018 |

### 2.3. `ScheduleTrigger` — «расписание ScheduleSpec» (FR-003/004)

Парсится и валидируется структурно, в `run` **не исполняется** — no-op + строка-заглушка (FR-018). В теле
**нет** предопределённых имён: и `значение`, и `событие` дают контекст-ошибку (§6, FR-007).

```go
// ScheduleTrigger — «расписание ScheduleSpec». Pos() = токен «расписание».
type ScheduleTrigger struct {
	specBase
	Spec ScheduleSpec // «каждые DurationLiteral» ИЛИ «в StringLiteral»
}

func NewScheduleTrigger(pos Position, spec ScheduleSpec) *ScheduleTrigger {
	return &ScheduleTrigger{specBase: specBase{base{pos}}, Spec: spec}
}
```

| Поле | Тип | Семантика | FR |
|---|---|---|---|
| `specBase` | встраивание | `Pos()` (= токен `расписание`) + маркер `triggerSpec()` | FR-003 |
| `Spec` | `ScheduleSpec` | подформа-маркер: `*EverySchedule` ИЛИ `*AtSchedule` (type-switch, §3) | FR-003/FR-004 |

### Инварианты §2

- Каждая реализация несёт `Pos()` своего ведущего токена (`метрика`/`событие`/`расписание`).
- `TriggerSpec` — закрытый союз ровно из трёх типов; четвёртой формы нет (диспетчер форм →
  `SE-TRIGGER-KIND`, FR-019).
- Все три — вспомогательные узлы (`base`, не `declBase`); top-level декларацией является **только**
  `TriggerDecl` (§1).

## 3. `ScheduleSpec` — подформа расписания (§TR-2, FR-003/004/005)

Два взаимоисключающих варианта расписания, моделируемые **двумя конкретными типами под общим маркером**
(не одним типом с тегом и двумя nil-полями) — единообразно с `TriggerSpec` и проще для type-switch.

```go
// ScheduleSpec — спецификация расписания: интервал ИЛИ время суток.
// Реализуется EverySchedule («каждые») и AtSchedule («в»).
type ScheduleSpec interface {
	Node
	scheduleSpec()
}

type schedBase struct{ base }

func (schedBase) scheduleSpec() {}
```

### 3.1. `EverySchedule` — «каждые DurationLiteral» (FR-004)

```go
// EverySchedule — «каждые DurationLiteral». Pos() = токен «каждые».
// Every — литерал длительности; ВСЕ 6 единиц принимаются в 007a (§TR-1).
type EverySchedule struct {
	schedBase
	Every *DurationLit // 3дн/5мин/2нед/1мес/30сек/1час
}

func NewEverySchedule(pos Position, every *DurationLit) *EverySchedule {
	return &EverySchedule{schedBase: schedBase{base{pos}}, Every: every}
}
```

| Поле | Тип | Семантика | FR |
|---|---|---|---|
| `schedBase` | встраивание | `Pos()` (= токен `каждые`) + маркер `scheduleSpec()` | FR-003 |
| `Every` | `*ast.DurationLit` | интервал; принимаются все 6 единиц (`сек/мин/час/дн/нед/мес`) | FR-004 |

- **Все 6 единиц без ограничений.** `DurationLit` несёт `Amount`/`Unit` (`ast/literal.go`); 007a принимает
  любую единицу, **`нед`/`мес` НЕ дают ошибки** (правило «нед/мес → ошибка» сознательно не вводилось —
  исполнение расписания в 007b будет календарным, FR-004, §TR-1).

### 3.2. `AtSchedule` — «в StringLiteral» (FR-005)

```go
// AtSchedule — «в StringLiteral». Pos() = токен «в». At — строковый литерал
// "ЧЧ:ММ"; формат содержимого в 007a НЕ проверяется (валидация → 007b, §TR-11 п.3).
type AtSchedule struct {
	schedBase
	At StringLit // "ЧЧ:ММ" (любая строка)
}

func NewAtSchedule(pos Position, at StringLit) *AtSchedule {
	return &AtSchedule{schedBase: schedBase{base{pos}}, At: at}
}
```

| Поле | Тип | Семантика | FR |
|---|---|---|---|
| `schedBase` | встраивание | `Pos()` (= токен `в`) + маркер `scheduleSpec()` | FR-003 |
| `At` | `ast.StringLit` | время суток; содержимое строки в 007a **не валидируется** (любая строка) | FR-005 |

- **Содержимое «ЧЧ:ММ» не анализируется.** Реестр диагностик 007a НЕ содержит диагностики формата
  времени; `"25:99"` принимается как есть (FR-005, §TR-4 проверка 2). Валидация (`00:00–23:59`, ведущий
  ноль) отложена в 007b.
- **`At` хранится по значению** (`StringLit`, не указатель) — зеркало `SourceDecl.File StringLit`
  (`ast/decl.go:24`). Передача значение-vs-указатель подтверждается импл-проходом по факту узла (§TR-2
  TODO-FACT).

### Инварианты §3

- `ScheduleSpec` — закрытый союз ровно из двух типов; отсутствие `каждые`/`в` после `расписание` →
  `SE-SCHEDULE-SPEC` (FR-019).
- Оба — вспомогательные узлы (`base`), несут позицию своего ведущего токена.

## 4. `ValueExpr` — выражение «значение» (§TR-2, FR-006/007/015)

Первичное выражение (Primary) без внутренней структуры — зеркало `NoneLit`/`RunProcessExpr`: встраивает
`exprBase` (→ реализует `Expression`), параметров нет, `Pos()` = токен `значение`.

```go
// ValueExpr — выражение «значение» (предопределённое имя метрика-триггера).
// Pos() = токен «значение». Допустимо только в теле метрика-триггера (гард §TR-4).
type ValueExpr struct {
	exprBase
}

func NewValueExpr(pos Position) *ValueExpr {
	return &ValueExpr{exprBase: exprBase{base{pos}}}
}
```

| Поле | Тип | Семантика | FR |
|---|---|---|---|
| `exprBase` | встраивание | `Pos()` (= токен `значение`) + маркер `exprNode()` — `ValueExpr` встаёт в `Expression` | FR-006 |

### Инварианты

- **Синтаксически принимается ВЕЗДЕ.** `parsePrimary` контекста не знает — `значение` парсится в любой
  позиции выражения (тело метрики, тело шага, глобальный `пусть`, аргумент вызова; FR-006). Единственное
  исключение — верхний уровень как ведущий токен: `неожиданный токен 'значение'` через `isUnexpectedTopLevel`
  (FR-020).
- **Контекст накладывает семпроход**, не парсер: `значение` вне тела метрика-триггера →
  `выражение 'значение' допустимо только в теле триггера метрики` (`TR-VAL-CTX`, exit 1; FR-007).
- **Доступ через инжекцию read-only в `run`.** При истинном условии движок делает
  `env.Define("значение", <численное значение метрики>)` в локальный env тела (read-only, не протекает
  наружу; FR-015, §6).
- `значение` — жёсткое ключевое слово (KW), не `Ident`: коллизия с глобальным `пусть` того же имени
  невозможна на уровне лексера.

## 5. `EventExpr` — выражение «событие» (§TR-2, FR-006/007)

Первичное выражение (Primary), зеркало `ValueExpr`: встраивает `exprBase`, без параметров, `Pos()` = токен
`событие`.

```go
// EventExpr — выражение «событие» (предопределённое имя событие-триггера).
// Pos() = токен «событие». Допустимо только в теле событие-триггера (гард §TR-4).
type EventExpr struct {
	exprBase
}

func NewEventExpr(pos Position) *EventExpr {
	return &EventExpr{exprBase: exprBase{base{pos}}}
}
```

| Поле | Тип | Семантика | FR |
|---|---|---|---|
| `exprBase` | встраивание | `Pos()` (= токен `событие`) + маркер `exprNode()` — `EventExpr` встаёт в `Expression` | FR-006 |

### Инварианты

- **Доступ `событие.поле` НЕ расширяет `EventExpr`.** Постфиксный `.поле` навешивает существующий
  `FieldExpr` (`ast/expr.go:55`): `событие.клиент` → `FieldExpr{Target: *EventExpr, Field: Ident("клиент")}`,
  как любой `target.field`. `EventExpr` остаётся беспараметрическим (как `RunProcessExpr` не тащит
  постфикс-вызов внутрь). Нового узла доступа к полю не вводится (FR-006).
- **Синтаксически принимается ВЕЗДЕ** (как `ValueExpr`); на верхнем уровне как ведущий токен —
  `неожиданный токен 'событие'` через default-путь верхнего уровня (`событие` в `isUnexpectedTopLevel`
  исходно не значится, результат тот же; FR-020).
- **Контекст накладывает семпроход**: `событие` (или `событие.поле`) вне тела событие-триггера →
  `выражение 'событие' допустимо только в теле триггера события` (`TR-EVT-CTX`, exit 1; FR-007).
- **Фактической инжекции `событие` в 007a нет** — событие-триггеры в `run` не исполняются (no-op).
  Контракт инжекции (`env.Define("событие", <запись payload>)`) зафиксирован для 007b; семпроход 007a при
  этом полностью валидирует событие-тело (FR-022, §6).
- `событие` — жёсткое ключевое слово (KW), не `Ident`.

## 6. Предопределённые имена `значение`/`событие` — контракт scope (§TR-5, FR-025)

Тело триггера исполняется (в 007a — только тело метрика-триггера, в `run`) в собственном `Environment`,
производном от глобального. Контракт ниже задаёт, что тело **видит**, мутируемость каждой категории и
порядок связывания имён. Это зеркало контракта scope шага (§PM), адаптированное под триггеры.

### Что видит тело (видимость и мутируемость)

| Категория имён | Видимость | Мутируемость | Источник |
|---|---|---|---|
| Предопределённое `значение` (метрика-тело) | видно | **read-only** | инжектируется в `run` при срабатывании: `env.Define("значение", <число метрики>)` |
| Предопределённое `событие` (событие-тело) | видно | **read-only** | инжекция при доставке события (007b); в 007a фактической инжекции нет (no-op) |
| Глобальные `пусть` | видно | **read-only** из тела | связаны на top-level до прохода триггеров (`interp.Run` отработал, §TR-6) |
| Метрики (по имени) | видно (имена реестра) | **read-only** | резолв через `i.metrics`; вычисляются лениво |
| Функции, процессы (по имени) | видно | вызов / запуск | реестры `i.funcs`/`i.processes` |
| Локальные `пусть` тела | видно | **read/write локально** | объявляются в теле, живут в env тела, **эфемерны** |

### Порядок Define

1. **Глобалы уже связаны.** Проход триггеров идёт ПОСЛЕ `interp.Run(prog)` — глобальный env заполнен,
   тело ссылается на top-level `пусть`/метрики/функции/процессы read-only.
2. **Инжекция предопределённого имени.** Перед исполнением тела — `env.Define("значение", metricValue)`
   для метрика-тела (или `env.Define("событие", record)` для событие-тела в 007b). Первое и единственное
   предопределённое связывание в локальном env.
3. **Локальные `пусть`** связываются по ходу исполнения тела стандартной семантикой блока (как в теле
   функции/шага).

### Инварианты scope (FR-025)

- **Тело не мутирует глобалы.** Глобальные `пусть`, метрики и предопределённое имя видны **read-only**;
  локальные `пусть` пишутся в локальный env и **исчезают по завершении прохода** (триггер эфемерен).
  `значение` инжектируется read-only и не протекает наружу.
- **Изоляция видов триггеров** (взаимоисключающие флаги `inMetricTrigger`/`inEventTrigger`, §TR-4): в
  событие-теле `значение` → `TR-VAL-CTX`; в метрика-теле `событие` → `TR-EVT-CTX`; в расписание-теле
  недопустимы **оба** (оба флага false).
- **Изоляция инжекции от глобалов.** Предопределённое имя инжектируется в **локальный** env тела, не
  глобальный — не конфликтует с одноимённым глобальным `пусть` (что невозможно и так: `значение`/`событие`
  — KW, не `Ident`).

### Жёсткие ключевые слова

`значение` и `событие` — **жёсткие ключевые слова** (KW_VALUE/KW_EVENT), их **нельзя** использовать как
имена переменных **нигде** в программе. Лексер выделяет их в отдельные токены, поэтому коллизия с
переменной/полем/именем функции невозможна на уровне лексера (а не отлавливается семпроходом). На верхнем
уровне как ведущий токен оба отвергаются (`неожиданный токен 'значение'` / `неожиданный токен 'событие'`,
FR-020), внутри тела чужого вида триггера — контекст-ошибкой (FR-007).
