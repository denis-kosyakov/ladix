# Быстрый старт: окна метрик — «последние N дней» и «прошлый месяц» за 5 минут

Это пошаговое руководство для бизнес-автора «Уклада». За пять минут вы объявите метрику
со **скользящим окном** `последние 30дн`, посчитаете её над реальной CSV-выгрузкой, затем
переключите ту же метрику на **последний завершённый период** `прошлый месяц` и увидите,
как выглядит ошибка в недопустимом окне.

Окна метрик (фича 011, A2) снимают ограничение v1, где метрика умела считать только текущий
календарный период (`ежемесячно`…`ежегодно`). Теперь у `период:` три формы:

| Форма | Что считает |
|---|---|
| `ежемесячно` (и 4 других адверба v1) | текущий календарный период — **как раньше, без изменений** |
| `последние N <ед>` (`дн`/`нед`/`мес`) | скользящее окно `(сегодня − N, сегодня]` |
| `прошлый <период>` (`день`/`неделя`/`месяц`/`квартал`/`год`) | весь предыдущий завершённый календарный период |

Метрика по-прежнему даёт **одно число (скаляр)** по окну. Ряд значений (временной ряд) —
пока не поддержан, отложен (см. §MW-12 якоря).

Всё ниже воспроизводимо из свежего клона. Сборку и базовые команды см. в
[общем быстром старте](../../../docs/quickstart.md); здесь команды запускаются из **корня
репозитория**, бинарник — `./ladix`.

> **Об окне и дате.** Окно всегда строится от даты запуска (`сегодня()`, замороженной на
> один прогон). Поэтому значение оконной метрики зависит от дня запуска и от данных — это
> нормально и детерминированно в пределах одного прогона. В примерах ниже выгрузка
> `data/orders.csv` содержит заказы за май 2026; конкретный скаляр вы увидите свой —
> в зависимости от того, попадают ли майские даты в окно от сегодняшнего дня.

## Шаг 1. Скользящее окно «последние 30 дней» над CSV (A1)

Возьмём реальную CSV-выгрузку заказов `data/orders.csv` (колонки `дата_заказа`,
`сумма_заказа`, `статус`) и объявим метрику `выручка_30д` — выручку по оплаченным заказам
за **последние 30 дней**. Создайте файл `выручка_30д.ladix`:

```ladix
источник заказы:
    файл: "data/orders.csv"
    тип: csv
    поля:
        дата_заказа: Дата
        сумма_заказа: Дробное
        статус: Строка

# Скользящее окно: оплаченные заказы за последние 30 дней от сегодня.
метрика выручка_30д:
    источник: заказы
    где:      статус == "оплачен"
    агрегат:  сумма(сумма_заказа)
    период:   последние 30дн         # окно (сегодня − 30, сегодня]
    по_дате:  дата(дата_заказа)      # ось окна — обязательна
```

Посчитайте метрику:

```sh
./ladix metric выручка_30д.ladix выручка_30д
```

В окно `(сегодня − 30, сегодня]` попадут только оплаченные заказы, чья `дата_заказа` лежит
в последних 30 днях; метрика просуммирует их `сумма_заказа` и выдаст один скаляр. Запись
ровно на нижней границе (`сегодня − 30`) в окно **не входит** — окно полуоткрытое слева;
запись на сегодняшнюю дату — входит (§MW-D-WINDOW-SLIDE, §MW-10).

> **Заметка про единицы.** `дн`, `нед`, `мес` взаимозаменяемы по длительности:
> `последние 7дн` и `последние 1нед` дают одинаковую выборку записей и равный скаляр.
> Форма пишется слитно — `30дн` (один токен). С пробелом `последние 30 дн` — не
> поддержано (§MW-12).

## Шаг 2. Последний завершённый период «прошлый месяц»

Часто нужен не «30 дней от сегодня», а **весь прошлый календарный месяц целиком**. Замените
строку `период:` на `прошлый месяц`:

```ladix
    период:   прошлый месяц        # весь предыдущий календарный месяц
    по_дате:  дата(дата_заказа)
```

```sh
./ladix metric выручка_30д.ladix выручка_30д
```

Теперь окно — это полный предыдущий календарный месяц относительно сегодня (например, если
запуск в июне, окно равно `[1 мая, 31 мая]`), а не «месяц назад от текущего числа». Записи
текущего месяца в окно не попадут (§MW-D-WINDOW-COMPLETED, §MW-10).

Аналогично работают `прошлая неделя`, `прошлый квартал`, `прошлый год`, `прошлый день` —
каждый берёт полный предыдущий календарный период. На фиксированную дату 2026-06-15 форма
`прошлый месяц` даёт ровно окно `[2026-05-01, 2026-05-31]` — именно сюда попадают все
четыре майских заказа из `data/orders.csv`.

> **Об аддитивности.** Старые формы никуда не делись. В одной программе можно соседствовать
> `период: ежемесячно` (текущий месяц), `период: последние 30дн` (скользящее) и
> `период: прошлый месяц` (завершённый) — `период:` принимает любую из трёх форм (§MW-D-PARSE).

## Шаг 3. Как выглядит ошибка

Окна оси-даты считаются в днях, неделях и месяцах — почасовых единиц нет. Если указать
`час` (или `сек`/`мин`), анализ остановится с ошибкой ещё до счёта:

```ladix
    период:   последние 5час       # ← недопустимая единица для окна
```

```sh
./ladix metric выручка_30д.ladix выручка_30д
```

```
метрика 'выручка_30д': единица 'час' недопустима для окна (допустимо: дн, нед, мес)
```

Код возврата — `1`; сообщение указывает позицию атрибута `период:`. Так же отвергаются
неположительный размер окна и неизвестный период:

```
последние 0дн   → метрика 'выручка_30д': размер окна должен быть положительным
прошлый век     → метрика 'выручка_30д': неизвестный период 'век' (допустимо: день, неделя, месяц, квартал, год)
```

Ещё одна частая ошибка — **окно без оси `по_дате`**. Период (любой формы) требует, чтобы у
метрики была ось даты. Уберите строку `по_дате:` — и получите существующее сообщение v1:

```
метрика 'выручка_30д': период требует по_дате
```

Это та же проверка, что и для календарных периодов v1 (A2-4); новой ошибки окна тут нет.

## Что дальше

- Пять календарных периодов v1 (`ежедневно`, `еженедельно`, `ежемесячно`, `ежеквартально`,
  `ежегодно`) работают **без изменений** — они считают текущий календарный период, как и
  раньше; примеры — в `examples/выручка.ladix` и `examples/метрики.ladix`.
- **Метрика-как-ряд** (временной ряд значений по окнам, а не один скаляр) — пока не
  поддержана, отложена на следующую веху (A2-1, §MW-12).
- Полная модель окон и границ — в [`docs/metric-windows-model.md`](../../../docs/metric-windows-model.md)
  (§MW-0…§MW-13); спецификация фичи — в [`spec.md`](spec.md).
