## D-1. Парс `период:` — спец-парс ветки, а не keyword-изация / generic-выражение

**Контекст.** `parseMetricDecl` (`parse_decl.go:185`), ветка `case "период":`
(строка 226) сегодня зовёт generic `p.parseExpression()`. Форма
`последние 30дн` = два соседних primary: `IDENT("последние")` + `DURATION("30дн")`
(литерал длительности — ОДИН токен `DURATION` с `DurationValue{Amount, Unit}`,
`scan_number.go`; лексер НЕ трогается, §MW-2). Generic `parseExpression` вернёт
ОДИН узел (`Ident("последние")`) и оставит висящий `DURATION` → парс-ошибка. Слова
`последние`/`прошлый`/`прошлая`/nouns лексятся как `IDENT` (`scan_ident.go:33`).
Якорь: §MW-D-PARSE, §MW-D-PARSE-1, §MW-2.

**Decision.** Ветку `период:` перевести с `parseExpression()` на новый
`parsePeriodValue()`, который КОНТЕКСТНО матчит по сырой лексеме (как A1 матчит
`тип`/`поля`, как метрика-атрибуты матчатся по `attrTok.Lexeme`,
`parse_decl.go:175`):
- `IDENT("последние")` → `advance`, `expect(DURATION, …)` → `ast.WindowPeriodLit{Amount, Unit, Pos}`;
- `IDENT("прошлый"|"прошлая")` → `advance`, `expect(IDENT, …)` → `ast.LastCompletedPeriodLit{Noun, Pos}`;
- иначе → `parseExpression()` (адверб-константа v1 — путь БЕЗ изменений).

Слова `последние`/`прошлый`/`прошлая`/nouns ОСТАЮТСЯ `IDENT`, ключевыми словами НЕ
становятся.

**Rationale.** Контекстный матч в ветке `период:` безопасен для v1: программа
вправе звать переменную `последние`/`прошлый` в общем выражении — keyword-изация
сломала бы её (нарушение инварианта обратной совместимости 5 хартии §5). Спец-парс
именно ветки `период:` (а не общего выражения) держит скользящие/завершённые формы
недостижимыми вне атрибута, что критично для D-2 (кодек-скип). Путь
`parseExpression` для адверб-констант не меняется → `период: ежемесячно` валиден как
раньше (§MW-D-PARSE-4).

**Alternatives.**
- *Сделать `последние`/`прошлый` ключевыми словами* — ОТКЛОНЁН: ломает v1-программы,
  использующие эти слова как имена переменных; нарушает обратную совместимость
  (инвариант 5 хартии §5).
- *Оставить generic `parseExpression`* — ОТКЛОНЁН: не умеет совместить два соседних
  primary (`IDENT` + `DURATION`) в один период-узел; падает на висящем `DURATION`
  (§MW-2). Спец-парс — единственный способ собрать `последние N<ед>` без новой
  грамматики выражений.
- *Спейсовая форма `последние 30 дн`* — ОТКЛОНЁНА как поддерживаемая (§MW-D-PARSE-2):
  `30` лексится `INT`, `expect(DURATION)` найдёт `INT` → парс-ошибка «ожидался
  период вида N<ед>, например 30дн». Поддержана только контигуальная `30дн`
  (документированный edge).

## D-2. `value.Период` — аддитивное расширение {Amount,Unit,Offset}, а не новый тип

**Контекст.** `value.Период` (`deferred.go:28-29`) сегодня — `struct{ Name string }`.
Окно строит `periodWindow(p value.Период, d value.Дата)` (`window.go:17`) — уже
принимает `Период`. Пять календарных констант (`value.PeriodNames`) регистрируются
read-only глобалами в `interpreter.go` (нулевые поля). Пакет `value` — листовой
(конституция VII). Якорь: §MW-3, §MW-D-VALUE, §MW-D-VALUE-EQ.

**Decision.** Расширить `Период` **аддитивно** — `{Name string, Amount int64,
Unit string, Offset int}`: календарные константы → нулевые новые поля; скользящее →
`{Name:"последние", Amount:N, Unit:ед}`; завершённое → `{Name:<адверб>, Offset:-1}`.
Затрагиваются ровно 3 файла пакета `value` (верифицировано по строкам):
- `deferred.go:28` — расширить структуру;
- `equal.go:71-73` — `case Период` сравнивает только `Name`; обновить на ВСЕ поля
  (`Name && Amount && Unit && Offset`);
- `repr.go:49` — `case Период` печатает `Name`; обновить: `Name=="последние"` →
  `«последние N<ед>»`; `Offset!=0` → `«прошлый <noun>»`; иначе `Name` (v1).

`store/codec.go:92-93` (кодирует `Период` по `Name`) **НЕ трогать**. Новый тип
значения `Окно` НЕ вводится.

**Rationale.** `periodWindow` уже берёт `Период` — аддитивное расширение проще, чем
новый тип `Окно` (потребовал бы новую сигнатуру окна, новый eval-путь, новую
сериализацию). `Период` буквально моделирует период всех трёх форм. **Кодек-скип
обоснован:** скользящие/завершённые `Период` **недостижимы как first-class
значения** — парсер спец-парсит `последние`/`прошлый` ТОЛЬКО в ветке `период:`
(D-1); в общем выражении (`присвоить x = последние 30дн`) `последние` — обычный
IDENT (undefined → ошибка), `DURATION` остаётся → скользящий `Период` не родится.
Персистятся лишь 5 календарных адвербов с нулевыми `Amount/Unit/Offset` → `Name`-only
round-trip корректен; контракт Store и сериализация не меняются (инвариант 3 хартии
§5). Расширение `equal`/`repr` обязательно для структурного равенства/печати всех
полей (FR-017).

**Alternatives.**
- *Новый тип значения `Окно`* — ОТКЛОНЁН: `periodWindow` уже принимает `Период`;
  новый тип потянул бы за собой новую сигнатуру окна, eval-кейс и кодек — больше
  churn без выигрыша (§MW-3).
- *Тронуть `store/codec.go` под новые поля* — ОТКЛОНЁН: скользящие/завершённые
  `Период` недостижимы как значения (D-1) → персистятся лишь 5 `Name`-only констант;
  правка кодека была бы мёртвым кодом и расширила бы контракт сериализации без
  нужды. (Если будущая фича сделает `Период` first-class — кодек тогда.)

## D-3. Скользящее окно — инклюзивно-эквивалентные границы поверх `recordSurvives` без его изменения

**Контекст.** Фильтр записей `recordSurvives` (`metric_engine.go:108-153`) при
`hasPeriod` отвергает запись, если её дата `< winStart` или `> winEnd`, → окно
ИНКЛЮЗИВНО `[winStart, winEnd]`. Скользящее окно семантически — полуинтервал
`(сегодня − N, сегодня]` (нижняя граница ИСКЛЮЧЕНА, A2-3). Якорь: §MW-6,
§MW-D-WINDOW-SLIDE, §MW-10.

**Decision.** В `periodWindow` добавить ветку `case p.Name=="последние"`,
возвращающую полуинтервал ИНКЛЮЗИВНО-ЭКВИВАЛЕНТНО, чтобы переиспользовать
инклюзивный `recordSurvives` БЕЗ его изменения:
- `конец = d` (инклюзивно);
- `нижняя_искл = d − N ед`: `дн`→`AddDate(0,0,-N)`, `нед`→`AddDate(0,0,-7*N)`,
  `мес`→`AddDate(0,-N,0)`;
- `начало = нижняя_искл.AddDate(0,0,+1)` — инклюзивная нижняя граница ≡ полуинтервал
  `(нижняя_искл, d]`.

Через `dateToTime`/`timeToDate` (UTC-полночь, как существующие 5 ветвей).

**Rationale.** Сдвиг `начало` на `+1` день делает инклюзивный диапазон
`[нижняя_искл+1, d]` точным эквивалентом полуинтервала `(нижняя_искл, d]` — это
позволяет НЕ трогать `recordSurvives` (инвариант изоляции бэкенда), а лишь вернуть
правильную пару дат. Формулы `AddDate` per unit верифицированы против golden-таблицы
§MW-10 на `FixedClock{2026,6,15}`: `последние 30дн` → `[2026-05-17, 2026-06-15]`
(запись на `2026-05-16`=нижняя_искл ИСКЛ, на `2026-05-17` вкл); `последние 2нед`
(14дн) → `[2026-06-02, 2026-06-15]`; `последние 1мес` → `[2026-05-16, 2026-06-15]`.
Эквивалентность единиц (`последние 7дн` ≡ `последние 1нед`) выводится из идентичной
длительности (SC-001).

**Alternatives.**
- *Сделать `recordSurvives` полуинтервальным (строгое `>` на нижней границе)* —
  ОТКЛОНЁН: меняет общий фильтр записей, ломает 5 календарных периодов (инклюзивных),
  нарушает изоляцию (инвариант 3 хартии §5). Сдвиг `+1` в окне локален и
  обратно-совместим.
- *Возвращать полуинтервал и развилкой выбирать инклюзивность в фильтре* — ОТКЛОНЁН:
  вводит флаг-режим в `recordSurvives`, усложняет горячий путь; инклюзивный
  эквивалент достигает того же без условной логики в фильтре.

## D-4. «Последний завершённый» — сдвиг якорной даты + переиспользование календарного `periodWindow`

**Контекст.** Существующие 5 ветвей `periodWindow` вычисляют ТЕКУЩИЙ календарный
период от даты `d` (`window.go:18-50`). «Последний завершённый» (`прошлый месяц`) —
тот же календарный период, но ПРЕДЫДУЩИЙ. Якорь: §MW-6, §MW-D-WINDOW-COMPLETED,
§MW-5.

**Decision.** Завершённый период несёт `Offset:-1` при календарном `Name` (D-2). В
`periodWindow` для `p.Offset != 0`: сдвинуть якорную дату `d` назад на `|Offset|`
периодов базовой единицы (`ежедневно`→`AddDate(0,0,Offset)`;
`еженедельно`→`AddDate(0,0,7*Offset)`; `ежемесячно`→`AddDate(0,Offset,0)`;
`ежеквартально`→`AddDate(0,3*Offset,0)`; `ежегодно`→`AddDate(Offset,0,0)`), затем
вычислить КАЛЕНДАРНОЕ окно сдвинутой даты существующими 5 ветвями
(`periodWindow({Name, Offset:0}, сдвинутая_d)`). Eval `LastCompletedPeriodLit`
маппит noun→адверб (`nounToAdverb`: день→ежедневно … год→ежегодно) и ставит
`Offset:-1` (§MW-5).

**Rationale.** Полный предыдущий период = текущий период СДВИНУТОЙ даты —
переиспользование существующей календарной логики (нулевой риск рассинхрона с
текущим периодом). На `FixedClock{2026,6,15}` `прошлый месяц`: `d.AddDate(0,-1,0)`
= `2026-05-15`, текущий месяц которого = `[2026-05-01, 2026-05-31]` (SC-002,
§MW-10). Маппинг noun→адверб переиспользует те же 5 календарных имён → ни одного
нового кода окна сверх сдвига.

**Alternatives.**
- *Отдельная формула диапазона для каждого завершённого периода* — ОТКЛОНЁН:
  дублирует календарную логику 5 ветвей (риск расхождения «прошлый» vs «текущий»);
  сдвиг-якоря переиспользует один источник истины.
- *Хранить готовый диапазон в `Период`* — ОТКЛОНЁН: окно зависит от `d=i.now()`
  (детерминизм, D-6); диапазон не может быть статическим полем значения.

## D-5. Синтаксис завершённого — `прошлый|прошлая <noun>`, а не адверб-квалификатор

**Контекст.** Свобода синтаксиса для «последнего завершённого» (A2-6). Пример
хендоффа — `прошлый месяц` (натуральный русский). Якорь: §MW-1 (A2-6),
§MW-D-PARSE, §MW-8.

**Decision.** Форма — `период: прошлый|прошлая <день|неделя|месяц|квартал|год>`:
прилагательное `прошлый`/`прошлая` + существительное-период. Парсер принимает оба
рода (`прошлый месяц`, `прошлая неделя`) без согласования — род валидируется лишь
неявно множеством nouns; noun ∈ {день,неделя,месяц,квартал,год} (иначе сем-ошибка
«неизвестный период», D-4/§MW-SEM-3).

**Rationale.** `прошлый <noun>` грамматичен и совпадает с примером хендоффа
(`прошлый месяц`); существительные-периоды (`месяц`/`неделя`/…) естественнее для
бизнес-автора, чем адверб-форма. Допуск обоих родов (`прошлый`/`прошлая`) без
строгого согласования упрощает парсер и не вредит (множество nouns — единственный
валидатор), сохраняя натуральность («прошлая неделя», «прошлый месяц»).

**Alternatives.**
- *Адверб-квалификатор `ежемесячно прошлый` / `прошлый ежемесячно`* — ОТКЛОНЁН:
  неграмматичен по-русски, не совпадает с примером хендоффа; noun-форма читается как
  естественный бизнес-вопрос.
- *Строгое согласование рода (`прошлый` только с муж., `прошлая` только с жен.)* —
  ОТКЛОНЁН: лишняя проверка без семантической пользы (noun уже однозначен);
  усложняет диагностику ради грамматического педантизма.

## D-6. Арифметика месяцев — принять нормализацию Go `AddDate`, зафиксировать честным golden

**Контекст.** Go `time.AddDate` нормализует переполнение дня:
`2026-05-31.AddDate(0,-1,0)` = `2026-05-01` (апрель 30 дней → «31 апреля» → 1 мая).
Для `последние N мес` и `прошлый месяц/квартал/год` на датах конца месяца это даёт
неинтуитивные границы. Якорь: §MW-6, §MW-D-WINDOW-EDGE, §MW-9 #4, §MW-12.

**Decision.** Принять нормализацию Go `AddDate` как есть (FR-015: 0 новых
зависимостей, окно — чистая функция от даты), задокументировать как edge. Golden DoD
пиннить на дате-НЕ-конце-месяца (`FixedClock{2026,6,15}`), плюс ОДИН явный
golden-кейс конца месяца (`FixedClock{2026,5,31}`, `последние 1мес` / `прошлый
месяц`) с зафиксированным НОРМАЛИЗОВАННЫМ результатом — честная фиксация, не
«округлённая красиво» (§MW-9 #4, SC-008). «Снап на последний день месяца» (обход
нормализации) — backlog вне A2.

**Rationale.** `AddDate` — stdlib, детерминирован, 0 deps; собственная
«снап-логика» добавила бы ветвление и риск рассинхрона с календарными ветвями.
Честный golden конца месяца защищает от тихого регресса арифметики и документирует
реальное поведение (стиль §VF: фиксировать факт, не идеал). Основной DoD-срез
(`выручка_30д`) использует середину месяца — нормализация не задевает витрину.

**Alternatives.**
- *Снап-на-последний-день-месяца* — ОТКЛОНЁН (в A2): доп. ветвление и обход
  стандартной арифметики; вынесен в backlog (§MW-12) — не нужен DoD-срезу.
- *Пиннить golden «красивым» (ненормализованным) ожиданием* — ОТКЛОНЁН: тест
  разошёлся бы с реальным `AddDate` → красный/ложный; честная фиксация
  нормализованного значения корректна и стабильна.

## D-7. Метрика-как-РЯД — ОТЛОЖЕНА (A2-1): меняет Value-модель и сравнение триггера

**Контекст.** Альтернатива оконной метрике-скаляру — метрика как ВРЕМЕННОЙ РЯД
значений (значение на каждый под-период окна). Якорь: §MW-0, §MW-1 (A2-1), §MW-12,
§MW-7.

**Decision.** Ряд ОТЛОЖЕН (вне A2). Метрика остаётся **СКАЛЯРОМ по окну**
(агрегат → одно значение; пустое окно → `emptyWindowResult`: сумма/количество→0,
иначе Пусто). Зафиксировано в якоре И спеке (FR-010), backlog M-next.

**Rationale.** Ряд изменил бы Value-модель (новый тип «ряд»/коллекция значений) И
сравнение в условии триггера (`когда метрика X < N` сейчас сравнивает скаляр —
`trigger_run.go:64` `evalMetricByName`). Это нарушило бы несущий инвариант A2:
`Store`/`ProcessRuntime`/экспорт `eval`/условие+тело триггера НЕ трогаются (A2-7,
инвариант 3 хартии §5, §MW-7). Золотому сценарию M1 (`выручка_30д` — скаляр) ряд не
нужен. Скаляр-окно даёт DoD-срез БЕЗ касания бэкенда — ряд не оправдывает поломку
изоляции в A2.

**Alternatives.**
- *Ввести ряд сразу в A2* — ОТКЛОНЁН: ломает изоляцию (Value-модель + сравнение
  триггера, A2-7), не нужен DoD; меняет контракт, который A2 обязан сохранить.
- *Скаляр + опциональный ряд-флаг* — ОТКЛОНЁН: всё равно тянет тип-ряд в Value и
  ветку сравнения в триггере; половинчатость без выигрыша для M1.
