# Implementation Plan: Каркас миграций схемы Store (forward-only)

**Branch**: `019-store-schema-migrations` | **Date**: 2026-06-18 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/019-store-schema-migrations/spec.md`

## Summary

Вводится forward-only механизм версионирования схемы SQLite внутри постоянного хранилища
(`SQLiteStore`), основанный на встроенной отметке версии `PRAGMA user_version`. Базовая версия
`baselineVersion = 1` («схема 006/007/018»), актуальная `currentSchemaVersion = 2`. Новая функция
`migrate(db)` вызывается в `NewSQLiteStore` ПОСЛЕ применения базовой `db.Exec(ddl)` и ДО возврата
готового хранилища; она прогоняет упорядоченный реестр `schemaMigrations`, где единственная ступень
1→2 создаёт таблицу `outbox` и индекс `idx_outbox_instance` (DDL — дословно из §C-2a.3). Каждый шаг
миграции и поднятие `user_version` атомарны в одной транзакции (шаблон по образцу существующего
`nextCounter`). `MemoryStore` миграций не имеет. Технический подход полностью продиктован якорем
`docs/reliability-model.md` §C-2a: точные константы, точка встройки, DDL и шаблон раннера зафиксированы
там и в on-disk дайджесте `.m3-ledger/digest-anchor.md` (секция C2a) + `digest-seams.md`.

ГРАНИЦЫ: создаётся только таблица `outbox` через миграцию. Go-методы `LoadOutbox`/`SaveOutbox`,
тип `OutboxRecord`, sentinel `ErrOutboxNotFound` и расширение контракта `Store` 16→18 — НЕ входят
(это последующая фича C2b). Контракт `Store` остаётся 16 методов; двойной compile-time замок не
меняется. Дифф строго в `src/internal/store/`; пакеты `eval`/`engine`/`cmd`/`daemon` имеют ПУСТОЙ дифф.

## Technical Context

**Language/Version**: Go 1.22+ (модуль под `src/`; сборка `cd src && go build ./...`).

**Primary Dependencies**: `modernc.org/sqlite` (CGO-free, единственная разрешённая внешняя зависимость
по Принципу I). 0 НОВЫХ зависимостей в данной фиче. Из stdlib используются `database/sql` и `fmt`
(оба уже импортированы в `src/internal/store/sqlite.go`).

**Storage**: SQLite, файл базы (`--db <path>`). Версионирование схемы — через встроенный
`PRAGMA user_version` (метка в самой базе, не отдельная таблица). Один процесс — одно соединение
(`db.SetMaxOpenConns(1)`).

**Testing**: `go test ./...`; табличные тесты пакета `store` (`src/internal/store/*_test.go`).
Замки §C-2a.4: fresh / legacy-v0 / idempotent + инверсионная мутпроба.

**Target Platform**: один статический бинарь (Linux/macOS), CGO запрещён (Принцип I).

**Project Type**: single project — интерпретатор/CLI на Go (`src/cmd/ladix` + `src/internal/...`).
Фича затрагивает ровно один внутренний пакет: `src/internal/store/`.

**Performance Goals**: миграция выполняется один раз при открытии хранилища; единственная ступень —
лёгкий `CREATE TABLE/INDEX IF NOT EXISTS`. Накладные расходы при повторном открытии = одно чтение
`PRAGMA user_version` (без шагов). Жёстких числовых целей нет; критерий — отсутствие регресса
времени открытия (порядок наносекунд на сравнение версии).

**Constraints**: полный детерминизм (без недетерминированного поведения миграции); атомарность
шаг+бамп в одной транзакции; forward-only (нет понижающих миграций); сохранность данных базовых
таблиц; пустой дифф вне пакета store; CGO запрещён.

**Scale/Scope**: точечная фича размера S. Затрагиваемые объекты: `sqlite.go` (вставка вызова
`migrate(db)` + новый блок констант/реестра/функции миграции, ~30–40 строк) + новый тестовый файл.
Реестр миграций на момент фичи — ровно 1 ступень (1→2).

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

Конституция `.specify/memory/constitution.md` v1.0.0, 9 принципов I–IX. Проверка по каждому:

- **I. Язык и сборка** — PASS. Чистый Go, CGO не вводится, бинарь остаётся статическим. 0 новых
  зависимостей (`database/sql` + `fmt` уже в импортах `sqlite.go`); `modernc.org/sqlite` — уже
  единственная разрешённая внешняя зависимость. `gofmt`/`go vet` чисты.
- **II. Парсинг — ручной** — PASS (N/A). Лексер/парсер не затрагиваются; никаких генераторов/regex.
- **III. Ошибки — явные типы** — PASS. `migrate` возвращает `error` по идиоме Go; ошибка миграции
  оборачивает `db.Close()` + возврат ошибки из `NewSQLiteStore` (как существующие ветки `db.Exec`).
  Нет panic в нормальном пути. `Position`-типизированные ошибки релевантны фронтенду (лексер/парсер),
  не инфраструктуре хранилища — здесь применяется обычный `error` хранилища, как у соседних методов
  (`nextCounter`, `SaveTask`). Барьер recover на уровне CLI-подкоманды не затрагивается.
- **IV. Позиции — сквозные** — PASS (N/A). Нет токенов/AST-узлов; `Position` неприменим к слою БД.
- **V. Без глобального состояния** — PASS. `schemaMigrations` — пакетная неизменяемая константа-срез
  строк DDL (read-only данные, не мутабельное состояние; аналог существующего неизменяемого `const ddl`
  и `const pragmas`). `migrate(db)` получает `*sql.DB` параметром (DI). `Store` остаётся интерфейсом.
  Никакого изменяемого package-level состояния не вводится.
- **VI. Тесты — вперёд** — PASS. Тесты пишутся вместе с реализацией миграции; табличные и с
  инверсионной мутпробой (§C-2a.4). Принцип VI прямо требует tests-first для лексера/парсера; для
  данной инфраструктурной фичи тесты сопровождают код и предоставляют красный-при-снятии-гарантии
  замок (SC-004), что соответствует духу принципа.
- **VII. Раскладка проекта** — PASS. Изменения строго в существующем пакете `internal/store`
  (под `src/`). Ацикличность не нарушается; новых пакетов нет; `store` остаётся листом контракта.
- **VIII. Язык сообщений** — PASS. Фича не вводит сообщений, видимых пользователю (миграция —
  безмолвная инфраструктура; при ошибке возвращается стандартная ошибка хранилища, как у соседей).
  Нет новых строк §13-канона; v1-программы валидны.
- **IX. Спека — источник истины** — PASS. Поведение целиком выведено из `docs/reliability-model.md`
  §C-2a (+ §C-0/§C-6/§C-7) и сверено с живым кодом через `.m3-ledger/digest-seams.md`. Пробелов/
  конфликтов, требующих STOP-and-ASK, не обнаружено.

**Итог: Constitution 9/9 PASS.** Нарушений нет.

**Замечание о Принципе простоты (Governance).** Конституция не выделяет отдельного нумерованного
«принципа простоты»; в §C-0 якоря и в Governance конституции простота трактуется как «минимальный
механизм под задачу». Forward-only миграционный каркас — минимально достаточный механизм для отзыва
паллиатива D-AU-9 (см. Complexity Tracking ниже): он строго проще, чем внешняя миграционная
библиотека или таблица истории миграций, и не нарушает ни одного из 9 принципов. Поэтому формального
нарушения нет, но обоснование выбора зафиксировано в Complexity Tracking для прозрачности (по
требованию якоря/брифа).

## Complexity Tracking

> Заполнено для прозрачности выбора механизма (по требованию брифа/якоря §C-0). Формального нарушения
> ни одного из 9 принципов конституции НЕТ — таблица фиксирует, почему forward-only-каркас выбран
> поверх более простых паллиативов, а не нарушение.

| Решение (потенциально «лишняя» сложность) | Почему необходимо | Более простая альтернатива отвергнута, потому что |
|---|---|---|
| Введение миграционного каркаса (`user_version` + `schemaMigrations` + `migrate`) вместо «как было» | Отзыв D-AU-9: паллиатив «пересоздавать/сбрасывать БД при изменении схемы» УНИЧТОЖАЛ пользовательские данные при каждом апгрейде; forward-only сохраняет данные между версиями продукта (надёжность долгоживущего хранилища) | Паллиатив (сброс БД) проще, но теряет данные — недопустимо для постоянного хранилища; `IF NOT EXISTS`-only не умеет ALTER существующих таблиц (латентный гэп, который сброс маскировал) |
| Транзакция вокруг каждого шага+бампа версии (а не «просто Exec») | Атомарность: при сбое между DDL-шагом и поднятием `user_version` схема и отметка версии не должны разойтись (полупримененный шаг = неконсистентность при следующем открытии) | Безтранзакционный `Exec` проще, но допускает расхождение схема↔версия при крахе → недетерминизм/повторный полушаг при рестарте |
| Реестр-срез `schemaMigrations` (а не единичный inline-Exec для outbox) | Расширяемость каркаса: ступени 2→3, 3→4 добавляются как элементы среза без переписывания раннера; индекс среза = пара версий (forward-only-инвариант на уровне структуры) | Inline один `CREATE TABLE outbox` проще сейчас, но не даёт каркаса для будущих миграций M3+; якорь §C-2a прямо требует именно реестр + раннер по образцу `nextCounter` |
