# Feature Specification: Каркас миграций схемы Store (forward-only)

**Feature Branch**: `019-store-schema-migrations`

**Created**: 2026-06-18

**Status**: Draft

**Input**: User description: "C2a — каркас миграций схемы Store (forward-only, отзыв D-AU-9). Forward-only механизм версионирования схемы SQLite внутри SQLiteStore через PRAGMA user_version; baselineVersion=1, currentSchemaVersion=2; migrate(db) между db.Exec(ddl) и return; реестр schemaMigrations со ступенью 1→2 = CREATE TABLE outbox + индекс; шаг миграции + бамп user_version атомарны в одной транзакции; MemoryStore миграций не имеет. Границы: создаётся только таблица outbox; Go-методы LoadOutbox/SaveOutbox и расширение Store 16→18 — НЕ в C2a (это C2b). Дифф строго в src/internal/store/."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Постоянная база данных автоматически получает актуальную версию схемы (Priority: P1)

Оператор-эксплуатант запускает любую команду Ladix, работающую с постоянным хранилищем
(`ladix serve`, `ladix start`, `ladix complete`, `ladix run --db`), указывая файл базы данных.
Файл может быть: совсем новым (несуществующим), либо созданным предыдущей версией Ladix
(«схема 006/007/018» без отметки версии), либо уже обновлённым актуальной версией. Во всех трёх
случаях открытие хранилища завершается успехом, схема приводится к актуальной версии, а ранее
сохранённые данные (экземпляры процессов, задачи, счётчики, состояние триггеров, события) остаются
нетронутыми.

**Why this priority**: Это единственная и центральная ценность фичи. До неё единственным способом
накатить изменение схемы был полный сброс/пересоздание базы (паллиатив эпохи M2, решение D-AU-9),
который УНИЧТОЖАЛ пользовательские данные при каждом изменении схемы. Отзыв D-AU-9 и переход на
forward-only обновление сохраняет данные между версиями продукта — обязательное условие надёжности
долгоживущего хранилища. Без этой истории фича не имеет смысла.

**Independent Test**: Полностью проверяется без какой-либо иной функциональности: открыть хранилище
на новом файле и убедиться, что отметка версии схемы равна актуальной и появилась целевая таблица;
повторить на файле «старой» схемы и убедиться, что версия поднялась, целевая таблица появилась, а
ранее вставленные данные читаются без потерь; повторно открыть уже обновлённый файл и убедиться, что
повторное открытие не падает и ничего не дублирует.

**Acceptance Scenarios**:

1. **Given** новый (несуществующий) файл базы, **When** открывается постоянное хранилище, **Then**
   отметка версии схемы равна актуальной (2) и целевая таблица `outbox` существует.
2. **Given** файл со «старой» схемой (базовые таблицы созданы, отметка версии = 0), куда заранее
   вставлены экземпляр процесса и задача, **When** открывается постоянное хранилище, **Then** отметка
   версии поднимается до актуальной (2), появляется таблица `outbox`, а ранее вставленные экземпляр и
   задача читаются без изменений.
3. **Given** файл, который уже обновлён до актуальной версии, **When** постоянное хранилище
   открывается повторно, **Then** открытие завершается успехом, отметка версии остаётся актуальной (2),
   таблица `outbox` не пересоздаётся и не дублируется, ошибок нет.
4. **Given** in-memory (непостоянное) хранилище, **When** оно создаётся, **Then** механизм миграций к
   нему не применяется (у непостоянной схемы нет версии), создание завершается штатно.

### Edge Cases

- **Отметка версии = 0 неоднозначна (новая ИЛИ до-версионная база)**: обе трактуются одинаково — как
  базовая версия (1). Базовые таблицы к этому моменту уже гарантированы существующей DDL-инициализацией
  («создать, если не существует»), поэтому различать «новая» и «до-версионная» не требуется; далее
  применяются миграции, начиная с 1→2.
- **Прерывание между шагом миграции и фиксацией отметки версии**: шаг изменения схемы и поднятие отметки
  версии выполняются в ОДНОЙ транзакции; при сбое до фиксации транзакция откатывается целиком — схема и
  отметка версии не расходятся (нет полупримененного шага).
- **Версия в базе выше актуальной (откат продукта на старую сборку)**: вне границ forward-only-модели;
  понижающих миграций нет; такая база не модифицируется (цикл применения миграций не выполняет ни одного
  шага, т.к. целевая версия не больше текущей). Поведение детерминированное (без изменений), потеря данных
  не происходит.
- **Повторный вызов на уже актуальной базе**: идемпотентен — ни одного шага миграции не применяется,
  отметка версии не меняется.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Постоянное хранилище ДОЛЖНО при каждом открытии приводить схему базы данных к актуальной
  версии (`currentSchemaVersion = 2`) посредством forward-only-механизма версионирования, основанного
  на отметке версии схемы в самой базе (`PRAGMA user_version`).
- **FR-002**: Базовая версия схемы ДОЛЖНА трактоваться как `baselineVersion = 1` и соответствовать
  существующей схеме «006/007/018» (таблицы экземпляров, задач, счётчиков, состояния триггеров, событий
  с индексами и сидом счётчиков), которая создаётся существующей DDL-инициализацией.
- **FR-003**: Отметка версии `0` (новая или до-версионная база) ДОЛЖНА трактоваться как базовая версия
  (1); после этого ДОЛЖНЫ применяться миграции, начиная со ступени 1→2.
- **FR-004**: Механизм ДОЛЖЕН вести упорядоченный реестр шагов миграции (`schemaMigrations`); ступень
  1→2 ДОЛЖНА создавать таблицу `outbox` и индекс `idx_outbox_instance` по DDL, приведённому в разделе
  Key Entities ДОСЛОВНО (без отклонений).
- **FR-005**: Каждый отдельный шаг миграции И поднятие отметки версии схемы ДОЛЖНЫ выполняться атомарно
  в ОДНОЙ транзакции; при ошибке любого из них транзакция ДОЛЖНА откатываться целиком, оставляя схему и
  отметку версии согласованными.
- **FR-006**: Механизм ДОЛЖЕН применять только те ступени, чья целевая версия превышает текущую отметку
  версии базы (forward-only); понижающих/обратных миграций НЕТ. Если текущая версия равна или больше
  актуальной, ни один шаг не применяется.
- **FR-007**: Открытие постоянного хранилища ДОЛЖНО быть идемпотентным относительно миграций: повторное
  открытие уже актуальной базы НЕ должно падать, повторно применять шаги или дублировать объекты схемы.
- **FR-008**: Миграция ДОЛЖНА сохранять ранее записанные данные базовых таблиц без изменений (накат
  схемы НЕ переинициализирует и НЕ сбрасывает базу — это и есть отзыв паллиатива D-AU-9).
- **FR-009**: Точка вызова миграций ДОЛЖНА располагаться при открытии постоянного хранилища ПОСЛЕ
  применения базовой DDL-инициализации и ДО возврата готового хранилища; ошибка миграции ДОЛЖНА
  приводить к неуспешному открытию хранилища (соединение закрывается, ошибка возвращается).
- **FR-010**: In-memory (непостоянное) хранилище НЕ ДОЛЖНО иметь механизма миграций (у него нет
  постоянной версионируемой схемы); создание непостоянного хранилища остаётся без изменений.
- **FR-011**: Контракт хранилища (интерфейс `Store`) ДОЛЖЕН остаться неизменным — 16 методов; фича НЕ
  добавляет публичных методов работы с таблицей `outbox` (`LoadOutbox`/`SaveOutbox` относятся к
  последующей фиче C2b). Двойной compile-time замок соответствия реализаций контракту остаётся двойным.
- **FR-012**: Изменения кода ДОЛЖНЫ быть строго локализованы в пакете постоянного хранилища
  (`src/internal/store/`): только инициализация хранилища + новый код миграций + тесты. Дифф пакетов
  вычислителя, движка, CLI и демона ДОЛЖЕН быть ПУСТЫМ.
- **FR-013**: Фича НЕ ДОЛЖНА добавлять внешних зависимостей и ДОЛЖНА быть полностью детерминированной
  (никакого недетерминированного поведения при миграции).

### Key Entities *(include if feature involves data)*

- **Отметка версии схемы** (`user_version`): целочисленная метка, хранимая в самой базе данных;
  отражает применённую версию схемы. Значения: `0` (трактуется как базовая = 1), `1` (базовая
  «006/007/018»), `2` (актуальная после данной фичи).
- **Реестр миграций** (`schemaMigrations`): упорядоченный список DDL-шагов forward-only; индекс ступени
  определяет, с какой версии на какую она поднимает. На момент фичи — ровно одна ступень: 1→2.
- **Таблица `outbox`** (создаётся ступенью 1→2; Go-методы доступа — вне границ этой фичи): ДОСЛОВНЫЙ DDL
  ступени 1→2:

  ```sql
  CREATE TABLE IF NOT EXISTS outbox (
      dedup_key    TEXT PRIMARY KEY,
      instance_id  TEXT NOT NULL,
      step_name    TEXT NOT NULL,
      effect_index INTEGER NOT NULL,
      kind         TEXT NOT NULL,
      target       TEXT NOT NULL,
      args_json    TEXT NOT NULL,
      result_json  TEXT,
      delivered    INTEGER NOT NULL DEFAULT 0,
      created_at   TEXT NOT NULL,
      delivered_at TEXT
  );
  CREATE INDEX IF NOT EXISTS idx_outbox_instance ON outbox(instance_id, step_name);
  ```

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Открытие постоянного хранилища на НОВОМ файле даёт отметку версии схемы = 2 и
  существующую таблицу `outbox` (100% случаев).
- **SC-002**: Открытие постоянного хранилища на файле «старой» схемы (отметка версии 0) поднимает её до
  версии 2, создаёт таблицу `outbox`, и при этом 100% ранее записанных данных базовых таблиц читаются
  без потерь и изменений.
- **SC-003**: Повторное открытие уже актуальной базы (версия 2) — идемпотентно: 0 повторно применённых
  шагов, 0 дублирующих объектов схемы, 0 ошибок; отметка версии остаётся 2.
- **SC-004**: Тест-инверсия: при удалении шага миграции 1→2 или поднятия отметки версии хотя бы один
  тест краснеет (отсутствие `outbox` / версия ≠ 2) — гарантия, что замки реально проверяют поведение.
- **SC-005**: Дифф вне пакета постоянного хранилища ПУСТОЙ (вычислитель, движок, CLI, демон не
  изменены); внешних зависимостей не добавлено.
- **SC-006**: Полный гейт сборки и проверок (`go build`, `go vet`, `gofmt`, `go test ./...`) зелёный.

## Assumptions

- **A-1**: Источник истины и каноничные константы/DDL/точка встройки — `docs/reliability-model.md`
  §C-2a (разделы §C-2a.1..§C-2a.4). Любая неоднозначность разрешается из него.
- **A-2**: Колонка `escalated` (поле `Task.Escalated`) — часть БАЗОВОЙ схемы (версия 1, существующая
  DDL-инициализация), а НЕ предмет миграции; данная фича её не трогает.
- **A-3**: Базовые таблицы к моменту вызова миграций гарантированно существуют, так как существующая
  DDL-инициализация использует «создать, если не существует» и выполняется при каждом открытии ДО
  миграций. Поэтому трактовка `user_version=0` как базовой версии (1) безопасна без отдельной проверки
  наличия таблиц.
- **A-4**: Ступень 1→2 — отдельностоящая таблица без внешних ключей, поэтому управление режимом внешних
  ключей внутри транзакции миграции не требуется (для актуального набора миграций неактуально).
- **A-5**: Постоянное хранилище удерживает ровно одно соединение к файлу базы; механизм миграций
  использует то же соединение (не открывает второе), что сохраняет «липкость» настроек и атомарность.
- **A-6**: Отметку версии схемы нельзя параметризовать связыванием значения как обычный параметр запроса
  — значение версии подставляется как доверенная внутренняя целочисленная константа (инъекция исключена,
  внешний ввод не участвует).
- **A-7**: Дедуп-логика, Go-структура записи `outbox`, методы доступа и сквозные тесты exactly-once —
  предмет последующей фичи C2b и НЕ входят в границы данной фичи; здесь создаётся только сама таблица.
