## Как дериватив доходит до combineBinary/combineUnary

`evalMetric` (metric_engine.go:26) → `evalAggExpr` (metric_engine.go:184). На непустом
наборе выживших записей:

- `*ast.BinaryExpr` (metric_engine.go:216-228): рекурсивно вычисляет `Left`/`Right` через
  `evalAggExpr`, затем `i.combineBinary(ex, left, right)` → диспетчер на `evalAdd`/`evalSubMul`/
  `evalDiv`/`evalFloorDiv`/`evalMod` (те же числовые гарды, что у голого `evalBinary`).
- `*ast.UnaryExpr` (metric_engine.go:230-235): `i.combineUnary(ex, operand)` → собственная
  реализация унарного `-`/`не` (НЕ делегирует в `evalUnary`; metric_engine.go:284-305).
- Агрегаты-листья: `сумма`/`количество` → `value.Целое`; `среднее` → `value.Дробное`;
  `мин`/`макс` → тип элементов проекции (для `сумма_заказа` это `Целое`). Подтверждено
  golden `TestGoldenSM10`: сумма=2000000/количество=2/мин=800000/макс=1200000 (печатаются без
  `.0` → Целое), среднее=1000000.0 (с `.0` → Дробное).

### КРИТИЧНО: короткое замыкание пустого окна (D4-1)

`evalMetric` (metric_engine.go:79-81): **до** спуска в `evalAggExpr`, если набор выживших
пуст, возвращается `emptyWindowResult(m.Aggregate)` (metric_engine.go:115-125). Корневой
единичный `сумма`/`количество` → `Целое 0`; **всё прочее** (включая ЛЮБОЙ деривативный
`BinaryExpr`/`UnaryExpr` на корне) → `value.None` коротким замыканием. **Следствие: краевые
ветки `combineBinary`/`combineUnary` НЕДОСТИЖИМЫ на пустом окне** — их надо строить на
**НЕПУСТОМ** окне. Стандартный непустой набор harness: `где: статус == "оплачен"` +
`период: ежемесячно` + `по_дате: дата(дата_заказа)` (фикстура `examples/data/sales.json`,
`FixedClock{2026-05-31}`) → 2 выживших записи (`сумма_заказа` = 1200000 и 800000).

## A1 — деление на ноль (FR-001)

Две **разные** ветки кода, обе текст «деление на ноль», обе несут `b.Pos()`:

- **Дробная `/`** — `evalDiv` (arith.go:163-165): `if rf == 0 { runtimeErr(b.Pos(), "деление на ноль") }`.
  Рецепт (стандартная фикстура, непустое окно): `агрегат: сумма(сумма_заказа) / (количество(запись) - количество(запись))`.
  Знаменатель: `количество(запись)` = Целое 2; `2 - 2` через `evalSubMul` → Целое 0; `/`
  промоутит к float → `rf == 0.0` → «деление на ноль». **`evalGolden`/`evalMetricErr`
  достаточно** — окно непустое, D4-1 не срабатывает.
  Альтернатива: `1 / (сумма(сумма_заказа) - сумма(сумма_заказа))` (числитель литерал-1,
  знаменатель 2000000-2000000=0).
- **Целочисленные `//` и `mod`** — `evalFloorDiv` (arith.go:177-179) и `evalMod`
  (arith.go:192-194): `if ri.V == 0 { … "деление на ноль" }`. Рецепты:
  `агрегат: сумма(сумма_заказа) // (количество(запись) - количество(запись))` (Целое//Целое0),
  `агрегат: сумма(сумма_заказа) % (количество(запись) - количество(запись))` (Целое%Целое0).
  Обе ветки целочисленные (оба операнда Целое) → попадают в `evalFloorDiv`/`evalMod`, не в `evalDiv`.

**Проверка позиции (Конституция IV / FR-001)**: `evalErr(t, err)` → `(line, col, msg)`;
ассертить `line >= 1 && col >= 1` (или конкретную координату оператора), не только `msg ==
"деление на ноль"`. Тип — `ОшибкаВыполнения` (`isRuntime`).

**Достижимость A1 div-zero на непустом окне: ПОДТВЕРЖДЕНА.** Окно непустое (paid+ежемесячно),
D4-1 короткозамкнул бы только пустое окно; нулевой знаменатель строится разностью
агрегатов на непустых данных, числовая ветка реальна.

## A2 — переполнение целого (FR-002)

Текст «переполнение целого числа», `ОшибкаВыполнения`, `b.Pos()`:

- **`evalAdd`** (arith.go:108-111 через `addInt64` :247-253): `агрегат: сумма(сумма_заказа) + 9223372036854775807`
  на непустом окне (сумма=2000000>0) → 2000000 + MaxInt64 → overflow. **Литерал
  `9223372036854775807` = MaxInt64 выразим** (в диапазоне int64, парсится как Целое).
- **`evalSubMul`** (arith.go:129-142 через `mulInt64` :263-277 / `subInt64` :255-261):
  умножение — `агрегат: сумма(сумма_заказа) * сумма(сумма_заказа)` даёт 2000000² = 4e12
  (НЕ overflow). Чтобы гарантированно переполнить через `*`, использовать литерал-множитель:
  `агрегат: сумма(сумма_заказа) * 9223372036854775807` (2000000 * MaxInt64 → overflow).
  Вычитание: `агрегат: (0 - 9223372036854775807) - сумма(сумма_заказа)` — но `0 - MaxInt64`
  = -MaxInt64 (не overflow), затем `- 2000000` = -(MaxInt64+2000000) → overflow `subInt64`.
- **`evalFloorDiv` `MinInt64 // -1`** (arith.go:180-183 через `floorDivInt64` :283-292):
  нужен числитель MinInt64. MinInt64 невыразим литералом (Edge Case спеки), строится
  арифметикой. Через дериватив с кастом-фикстурой A3 (поле = MinInt64, `мин(поле)` → Целое
  MinInt64): `агрегат: мин(поле) // (количество(запись) - количество(запись) - 1)` —
  знаменатель `2 - 2 - 1 = -1` (НЕ ноль, иначе сработает div-zero), числитель MinInt64 →
  `floorDivInt64(MinInt64, -1)` → ловушка `a == MinInt64 && b == -1` → overflow.
  (Если кастом-фикстура для A2 нежелательна — это **достижимо**, но требует фикстуры A3;
  `evalAdd` + `MaxInt64`-литерал на стандартной фикстуре — самый дешёвый A2-замок, его и
  выбрать минимумом; `evalSubMul`/`evalFloorDiv` — дополнительные ветки таблицы.)

**Достижимость A2: ПОДТВЕРЖДЕНА** (`evalAdd`/`evalSubMul` — литерал MaxInt64 на стандартной
фикстуре; `evalFloorDiv MinInt64//-1` — через кастом-фикстуру A3).

## A3 — унарный минус, combineUnary (FR-003, ЯДРО — 0% покрытия)

`combineUnary` `OpNeg` (metric_engine.go:286-294):
- `value.Целое` с `v.V == math.MinInt64` → `runtimeErr(u.Pos(), "переполнение целого числа")`;
- `value.Дробное` → `value.Дробное{V: -v.V}` (корректно);
- default → `typeErr` (это путь A5).

**Маршрутизация в combineUnary подтверждена**: `evalAggExpr` ветка `*ast.UnaryExpr`
(metric_engine.go:230-235) зовёт именно `i.combineUnary` (не `evalUnary`). Унарный `-` в
`агрегат:` → `UnaryExpr{Op: OpNeg}`.

- **`-MinInt64` → переполнение**: **кастом-фикстура** с записью, где числовое поле =
  `-9223372036854775808` (ровно MinInt64, **в диапазоне int64**, грузится строгим путём
  `sourceNumberToValue` как `Целое{MinInt64}` — `n.Int64()` парсит его без ошибки). Дериватив
  `агрегат: -(мин(поле))` на окне из этой записи → `мин` возвращает `Целое{MinInt64}` →
  `combineUnary(neg, Целое{MinInt64})` → ветка `v.V == math.MinInt64` → «переполнение целого
  числа». (Окно непустое — одна запись; D4-1 не мешает: корень — UnaryExpr на непустом окне.)
  ВАЖНО: `-9223372036854775808` записывается в JSON как одно число (минус — часть токена
  json.Number), `n.Int64()` парсит его как `-9223372036854775808` без переполнения.
- **`-Дробное` → корректно**: `агрегат: -(среднее(сумма_заказа))` на стандартной непустой
  фикстуре → `среднее` = `Дробное{1000000.0}` → `combineUnary(neg, Дробное)` →
  `Дробное{-1000000.0}` → `value.String` = `"-1000000.0"`. Без ошибки.

**Достижимость A3 `-MinInt64` через дериватив: ПОДТВЕРЖДЕНА** (поле = `-9223372036854775808`
грузится строгим путём как `Целое{MinInt64}`, `мин`/`макс`/`сумма` на единичном окне дают это
Целое, `combineUnary` ловит MinInt64). Это закрывает 0% покрытия `combineUnary` (SC-002).

## A4 — пропагация NaN / ±Inf через combineBinary (FR-004)

`combineBinary` для float-операндов делегирует в `evalAdd`/`evalSubMul`/`evalDiv` (float-ветки
arith.go), которые НЕ перехватывают `±Inf`/`NaN` — они пропагируются IEEE-754 как есть.
`value.String` печатает их как `"+Inf"`/`"-Inf"`/`"NaN"` (repr.go:80-82, отдельная первая
ветка без `.0`).

**КЛЮЧЕВАЯ НАХОДКА (проверено эмпирически)**: `json.Number("1e400").Float64()` возвращает
`f = +Inf, err != nil`. Строгий загрузчик источника (`source_loader.go:214-217`) на `err !=
nil` возвращает **JSON-ошибку**, а НЕ `+Inf` — значит **через float-overflow источника `±Inf`
в дериватив НЕ внести**. Зато `json.Number("1e300").Float64()` = `1e+300, err == nil`
(конечное), грузится строгим путём как `Дробное{1e300}`. И `1e300 * 1e300 = +Inf`,
`Inf - Inf = NaN` (проверено).

Рецепт (**кастом-фикстура** с float-полем `огромное` = `1e300`, окно из ≥1 записи):
- **+Inf**: `агрегат: среднее(огромное) * среднее(огромное)` → `Дробное{1e300} * Дробное{1e300}`
  через `evalSubMul` float-ветку (arith.go:149-150) → `Дробное{+Inf}`. Ассерт:
  `math.IsInf(v.(value.Дробное).V, +1)` ИЛИ `value.String(v) == "+Inf"`.
- **-Inf**: `агрегат: -(среднее(огромное) * среднее(огромное))` → combineUnary над `Дробное{+Inf}`
  → `Дробное{-Inf}` (`-(+Inf)`); ИЛИ `агрегат: среднее(огромное) * (0 - среднее(огромное))`.
  Ассерт `math.IsInf(…, -1)` / `"-Inf"`.
- **NaN**: `агрегат: (среднее(огромное) * среднее(огромное)) - (среднее(огромное) * среднее(огромное))`
  → `+Inf - +Inf` через `evalSubMul` float-ветку → `NaN`. **Ассерт через `math.IsNaN`, не
  через `==`** (Edge Case спеки: NaN != NaN). `value.String` = `"NaN"`.

Для каждого — проверить, что результат — `value.Дробное` (а не паника/None) и значение
соответствует IEEE-754; «без потери значения» = тип сохранён, спец-значение прошло насквозь.

**Достижимость A4 через дериватив: ПОДТВЕРЖДЕНА** (конечный `1e300` проходит строгий
загрузчик, перемножение конечных float → `+Inf`; `Inf - Inf` → `NaN`; всё через
`combineBinary`/`evalSubMul`). Альтернатива для NaN без кастом-фикстуры недостижима — нужно
два Inf-операнда, которых из стандартной фикстуры (макс 1200000) не получить одним binop.

## A5 — операнд None / Пусто в combineBinary / combineUnary (FR-005)

- **combineUnary default** (metric_engine.go:295-296): операнд не Целое/Дробное →
  `typeErr(u.Pos(), "унарный '-' нельзя применить к <тип>")`.
- **combineBinary type-mismatch**: `evalAdd` (arith.go:125) / `evalSubMul` (arith.go:153) /
  `binopMsg` → `typeErr "'<оп>' нельзя применить к <тип> и <тип>"`.

**Как получить None/Пусто-операнд в деривативе** (НЕ путать с пустым окном D4-1, Edge Case
спеки): операнд должен быть `value.None`/`value.Пусто` НА НЕПУСТОМ окне. Варианты:
- **Метрика-как-значение, дающая Пусто**: объявить метрику `пусто_м` с **пустым** окном
  (например `среднее(сумма_заказа)` + `период: ежедневно` → `value.None` по D4-1). Затем
  внешняя метрика на **непустом** окне с деривативом, ссылающимся на `пусто_м` как глобальное
  имя: `агрегат: -(пусто_м)` → `combineUnary(neg, None)` → default → «унарный '-' нельзя
  применить к Пусто». Для combineBinary: `агрегат: сумма(сумма_заказа) + пусто_м` →
  `evalAdd(Целое, None)` → type-mismatch → «'+' нельзя применить к Целое и Пусто».
  (Паттерн метрики-как-значения подтверждён `TestMetricAsValueReentrant`
  metric_engine_test.go:242 — метрика читается по имени из `агрегат:` внешней.)
- Проверить точный `TypeName()` у `value.None`/`value.Пусто` для exact-match сообщения
  (вероятно «Пусто»). Тип ошибки — `ОшибкаТипа` (`isType`), НЕ паника.

**Достижимость A5 через дериватив: ПОДТВЕРЖДЕНА** (метрика с пустым окном даёт `value.None`,
читается как глобаль в деривативе внешней метрики на непустом окне → None-операнд в
combine*; default-ветка/type-mismatch → typeErr). Если exact-match текста окажется хрупким —
ассертить `isType(err)` + `strings.Contains(msg, "нельзя применить")`, но предпочесть exact.

## A7 — толерантный контракт numberToValue → payloadNumberToValue (FR-008, золотой замок)

`jsonval/decode.go:135-147`: число без `.`/`e`/`E` в int64 → Целое; иначе (`±Inf` при
overflow Float64, err проигнорирован) → `Дробное`. Никогда не None. Рецепт (таблица):
- `PayloadToRecord('{"x": 1e400}')` → `rec.Get("x")` = `value.Дробное`, `math.IsInf(.V, +1)`.
- `'{"x": -1e400}'` → `Дробное`, `math.IsInf(.V, -1)`.
- `'{"x": 99999999999999999999}'` (целое-вне-диапазона, без точки) → `Дробное`, `math.IsInf(.V, 0)`
  (любой знак; `Int64()` падает → fallthrough в Float64; для очень большого без точки тоже
  `±Inf`). **Проверить эмпирически**: `99999999999999999999` через `Float64()` может дать
  конечный `1e20`, а НЕ `±Inf` — тогда ассертить `_, ok := …(value.Дробное); ok` (число НЕ
  деградирует в None и стало Дробным), без `IsInf`. Спека FR-008 требует «дробное ±Inf …
  число НИКОГДА не None»: для гарантированного ±Inf использовать `1e400`/`-1e400`; для
  «целое-вне-диапазона без точки» — ассертить `Дробное` (де-факто контракт, как существующий
  `TestPayloadToRecordValueTypes` для `big`). Существующий замок `big:99999999999999999999`
  (decode_test.go:31) уже проверяет «→ Дробное» — новый A7-тест ДОБАВЛЯЕТ `1e400`/`-1e400` →
  `±Inf` (ранее не покрыто) и фиксирует золотым замком, что None НЕ возникает.

## Часть B — асимметрия двух numberToValue (FR-009..FR-011)

**Почему имена должны различаться**: две функции с идентичным именем `numberToValue` несут
**прямо противоположные контракты**:

| | Строгий (источник) | Толерантный (payload) |
|---|---|---|
| Где | `eval/source_loader.go:211` | `jsonval/decode.go:135` |
| Форма | **метод** на `*Interpreter` | **свободная** функция |
| Подпись | `(decl, idx, field, n) (Value, error)` | `(n) Value` |
| Вне int64 (без точки) | **ошибка** `§SM-9.B` | **`±Inf`** (Float64 fallback) |
| Float overflow (`1e400`) | **ошибка** (JSON err) | **`±Inf`** (err проигнорирован) |
| None? | возможна ошибка | **никогда** (деградация лучше сбоя доставки) |
| Зачем | целостность данных источника | надёжность доставки события (§AU-5.2) |

Одинаковое имя — ловушка для сопровождающего: легко перепутать строгий путь с толерантным и
непреднамеренно изменить поведение (например «починить» строгий по образцу толерантного,
сломав `§SM-9.B`). Рейминг делает асимметрию **намеренной и читаемой**:
- `sourceNumberToValue` (строгий) — имя кодирует «число из строки **источника**».
- `payloadNumberToValue` (толерантный) — имя кодирует «число из **payload**».
- Каждая получает одну строку перекрёстной ссылки на близнеца («строгий двойник: …» /
  «толерантный двойник: …»; B3), сохраняя существующий поясняющий комментарий. Комментарий
  в шапке `jsonval/decode.go:11-14` уже фиксирует асимметрию словесно — рейминг закрепляет её
  в именах символов.

**У каждой ровно один call-site** (подтверждено грепом): строгий — `decodeValue`
(source_loader.go:158); толерантный — `DecodeValue` (decode.go:81). Рейминг = переименовать
символ + обновить один вызов + одна строка комментария. **Никаких других переименований**
(FR-015). Поведение байт-в-байт прежнее → существующие тесты + новые A6/A7 страхуют.

## Мутационная стратегия (FR-006 / SC-004)

Каждый замок обязан **краснеть при удалении соответствующего гарда**. Сводка «гард → мутация
→ что краснеет» (детальная таблица — в `contracts/test-locks.md`):

| Замок | Гард (файл:строка) | Мутация (для проверки) | Что обязано упасть |
|---|---|---|---|
| A1 `/` | `evalDiv` `if rf == 0` (arith.go:163) | убрать проверку → вернёт `Дробное{+Inf}` | ассерт «деление на ноль»+тип+Pos упадёт (получит `+Inf`, не ошибку) |
| A1 `//` | `evalFloorDiv` `if ri.V == 0` (arith.go:177) | убрать → паника `integer divide by zero` | тест упадёт (паника вместо типизированной ошибки) |
| A1 `mod` | `evalMod` `if ri.V == 0` (arith.go:192) | убрать → паника | тест упадёт |
| A2 add | `addInt64` overflow (arith.go:249) | вернуть `s, false` всегда | вернёт wrapped Целое, ассерт «переполнение» упадёт |
| A2 floorDiv | `floorDivInt64` MinInt64 ловушка (arith.go:284) | убрать → паника/wrap | тест упадёт |
| A3 `-MinInt64` | `combineUnary` `v.V == MinInt64` (metric_engine.go:289) | убрать → `-MinInt64` обернётся в MinInt64 | вернёт Целое, ассерт «переполнение» упадёт |
| A3 `-Дробное` | `combineUnary` Дробное-ветка (metric_engine.go:293) | заменить на default | вернёт typeErr вместо `-1000000.0` |
| A4 ±Inf/NaN | float-ветки `evalSubMul`/`evalDiv` (arith.go:149/166) | (характеризация) перехватить Inf→ошибка | ассерт `IsInf`/`IsNaN` упадёт (получит ошибку) |
| A5 None unary | `combineUnary` default (metric_engine.go:295) | заменить на panic/возврат | тест ждёт typeErr — упадёт |
| A5 None binary | `evalAdd`/`evalSubMul` type-mismatch (arith.go:125/153) | вернуть None молча | ассерт typeErr упадёт |
| A6 строгий | `n.Int64()` err → §SM-9.B (source_loader.go:221) | вернуть `Дробное` (как толерантный) | ассерт ошибки `§SM-9.B` упадёт (получит Дробное) |
| A7 толерантный | Float64-fallback (decode.go:145) | вернуть `None` на overflow | ассерт `Дробное`/`IsInf` упадёт (None != Дробное) |
| Рейминг | call-site обновлён | НЕ обновить вызов после рейминга | `go build` упадёт (символ не найден) — компиляционный замок |

Замки строятся характеризационно: фиксируют ТЕКУЩЕЕ поведение как эталон (FR-012:
прод-логика не меняется), поэтому мутация = удаление/инверсия гарда делает текущее поведение
недостижимым → красный тест.
