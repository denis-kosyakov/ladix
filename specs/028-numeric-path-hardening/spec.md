# Feature Specification: Харденинг числовых путей движка метрик

**Feature Branch**: `028-numeric-path-hardening`

**Created**: 2026-06-23

**Status**: Draft

**Input**: User description: "Харденинг числовых путей движка метрик Ladix: запереть тестами существующее поведение combineBinary/combineUnary и обоих numberToValue + развести опасный одноимённый нейминг двух numberToValue. Тесты-онли по числовым гардам (combine*/arith прод-логику НЕ менять) + чисто механический рефактор-рейминг двух одноимённых numberToValue (поведение НЕ меняется). Лексерный путь FLOAT-литерала → L-8 НЕ трогать (другой слой, остаётся отложенным)."

## Почему (контекст и проблема) *(mandatory)*

Числовая семантика движка метрик (`combineBinary` / `combineUnary` + арифметические
помощники в `arith.go`) реализует все критические краевые ветки: деление на ноль (для
дробного знаменателя `0.0` и для целочисленных операций `//` / `mod`), переполнение
целого (`evalAdd` / `evalSubMul` / `evalFloorDiv` `MinInt64 // -1`), унарный минус
(`-MinInt64` → переполнение, `-Дробное` → корректно), пропагация `NaN` / `±Inf` по
IEEE-754, и типовые ошибки на операндах `None` / `Пусто`. Эти ветки должны давать
**ошибку с номером строки**, а НЕ панику.

Проблема в том, что **`combineUnary` имеет 0% тестового покрытия**, а большинство
числовых краевых веток заперты только через **голые выражения** (eval-уровень), но не
**через дериватив метрики** — то есть путь, по которому формула метрики реально
исполняется в движке. Любая регрессия в этих ветках (тихая порча числовой семантики
или паника вместо корректной ошибки) сегодня прошла бы незамеченной по этому пути.

Вторая, независимая проблема — **опасная коллизия имён**: в кодовой базе существуют
**две функции `numberToValue` с противоположными контрактами**:

- **строгий** (метод на интерпретаторе, путь загрузки источника): целое вне диапазона
  `int64` → **ошибка выполнения** (`§SM-9.B`);
- **толерантный** (свободная функция, путь декодирования payload): число вне
  диапазона → **`±Inf`**, число НИКОГДА не деградирует в `None`.

Одинаковое имя для функций с прямо противоположной семантикой — ловушка для будущего
сопровождающего: легко спутать строгий путь с толерантным и непреднамеренно изменить
поведение. Эта фича разводит имена, делая асимметрию намеренной и читаемой.

Фича — **харденинг без изменения поведения**: новые тесты запирают существующую
числовую семантику через дериватив метрики и фиксируют оба контракта `numberToValue`;
прод-логика `combineBinary` / `combineUnary` / `arith.go` и числовая модель остаются
**байт-в-байт неизменными**; единственное изменение прод-кода — **механическое
переименование** двух одноимённых `numberToValue` (поведение не меняется).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Числовые краевые ветки заперты через дериватив метрики (Priority: P1)

Автор бизнес-программы пишет формулу метрики, которая может попасть в числовую краевую
ситуацию (деление на ноль, переполнение целого, унарный минус над предельным значением,
дробные `NaN` / `±Inf`, операнд `None` / `Пусто`). Движок гарантированно отвечает
понятной ошибкой с номером строки, а НЕ падает паникой и не подменяет числовую
семантику тихо. Это поведение заперто автоматическими тестами, исполняющими дериватив
метрики.

**Why this priority**: это ядро фичи и единственный класс риска, который она снимает —
тихая порча числовой семантики или паника вместо ошибки на числовом пути движка.
`combineUnary` сегодня имеет 0% покрытия; без его запирания регрессия прошла бы
незамеченной. Без US1 фича не имеет ценности.

**Independent Test**: построить интерпретатор метрики с формулой, провоцирующей каждую
краевую ветку, исполнить дериватив и проверить категорию ошибки, её сообщение и наличие
номера строки (а не только факт «не паника»). Каждый тест краснеет при удалении
соответствующего гарда.

**Acceptance Scenarios**:

1. **Given** формула метрики с делением, чей знаменатель равен нулю,
   **When** дериватив метрики вычисляется,
   **Then** возвращается ошибка выполнения «деление на ноль» **с номером строки**,
   гарантированно НЕ паника. (A1)
2. **Given** формула метрики, дающая переполнение целого (агрегат `+ MaxInt64`, либо
   `MinInt64`-кейсы),
   **When** дериватив метрики вычисляется,
   **Then** возвращается ошибка выполнения «переполнение целого числа». (A2)
3. **Given** формула метрики с унарным минусом над агрегатом: `-MinInt64` для целого и
   `-Дробное` для дробного,
   **When** дериватив метрики вычисляется,
   **Then** `-MinInt64` → ошибка выполнения «переполнение целого числа», а `-Дробное` →
   корректный результат (ядро — `combineUnary`). (A3)
4. **Given** формула метрики с дробными операндами, дающими `NaN` или `±Inf`,
   **When** дериватив метрики вычисляется через `combineBinary`,
   **Then** значение `NaN` / `±Inf` пропагируется по IEEE-754 как есть, без паники и без
   потери значения (`NaN` сравнивается через проверку «является NaN», а не через `==`).
   (A4)
5. **Given** формула метрики с операндом `None` / `Пусто` в `combineBinary` или
   `combineUnary`,
   **When** дериватив метрики вычисляется,
   **Then** возвращается типовая ошибка (не паника). (A5)

### User Story 2 — Оба контракта numberToValue заперты (Priority: P2)

Числа, приходящие из внешних данных, обрабатываются двумя разными путями с
противоположными контрактами. Строгий путь (значения полей в строке источника) отвергает
целое вне диапазона `int64` ошибкой. Толерантный путь (декодирование payload) никогда не
теряет число: значение вне диапазона `int64` становится дробным (целое чуть больше
диапазона — конечным дробным через Float64-fallback; астрономически большое `1e400` —
`±Inf`). Оба контракта заперты тестами, чтобы будущая правка не сломала ни строгость
одного, ни толерантность другого.

**Why this priority**: фиксирует де-факто контракты обоих путей до их переименования
(US3), чтобы рефактор имён был доказуемо нейтрален и чтобы противоположная семантика
была защищена регрессионными замками. Без US1-харденинга самостоятельной ценности
меньше — P2.

**Independent Test**: строгий путь — загрузить источник со строкой, поле которой
содержит целое вне диапазона `int64`, и проверить ошибку выполнения `§SM-9.B`.
Толерантный путь — декодировать payload-числа `1e400`, `-1e400` и целое-вне-диапазона
без точки (`99999999999999999999`) и проверить золотым замком, что результат — дробное
`+Inf` / `-Inf` / конечное дробное (`~1e20`) соответственно.

**Acceptance Scenarios**:

1. **Given** источник, у которого поле записи содержит целое число, выходящее за пределы
   диапазона `int64` (строгий путь),
   **When** источник загружается,
   **Then** возвращается ошибка выполнения «целое число вне диапазона» формата `§SM-9.B`
   (ранее не покрыто тестом). (A6)
2. **Given** payload-числа `1e400`, `-1e400` и целое-вне-диапазона без десятичной точки
   (`99999999999999999999`, толерантный путь),
   **When** payload декодируется,
   **Then** результаты — дробное `+Inf`, дробное `-Inf` и **конечное** дробное (`~1e20`,
   Float64-fallback, НЕ `±Inf`) соответственно; число НИКОГДА не деградирует в `None`
   (золотой замок фиксирует де-факто контракт). (A7)

---

### User Story 3 — Развести одноимённый нейминг numberToValue (Priority: P3)

Сопровождающий, читающий код двух путей обработки чисел, видит два разных имени с
явными перекрёстными ссылками друг на друга, а не две одноимённые функции с
противоположными контрактами. Асимметрия читается как намеренная.

**Why this priority**: чисто механический рефактор читаемости/безопасности
сопровождения; не меняет поведение и зависит от запертых контрактов US2 как страховки.
Реже всего влияет на пользователя напрямую — P3.

**Independent Test**: после переименования сборка и тесты зелёные; единственные
изменённые символы — два `numberToValue` и их вызовы; новые имена и перекрёстные
комментарии присутствуют.

**Acceptance Scenarios**:

1. **Given** строгий метод `numberToValue` в пути загрузки источника,
   **When** выполнено переименование,
   **Then** метод называется `sourceNumberToValue`, его единственный вызов (в декодере
   значения) обновлён, и сборка/тесты зелёные. (B1)
2. **Given** толерантная свободная функция `numberToValue` в пути декодирования payload,
   **When** выполнено переименование,
   **Then** функция называется `payloadNumberToValue`, её единственный вызов (в декодере
   payload-значения) обновлён, и сборка/тесты зелёные. (B2)
3. **Given** обе переименованные функции,
   **When** правка завершена,
   **Then** у каждой сохранён поясняющий комментарий контракта и добавлена одна строка
   перекрёстной ссылки на близнеца («строгий двойник: …» / «толерантный двойник: …»),
   чтобы асимметрия читалась как намеренная; имена НАМЕРЕННО разные, никаких других
   переименований не делается. (B3)

---

### Edge Cases

- **`-MinInt64` невыразим литералом**: минимальное целое `int64` нельзя записать
  отрицательным литералом; для проверки переполнения унарного минуса его строят
  арифметикой (`0 - 9223372036854775807 - 1`), как в существующих тестах
  переполнения умножения.
- **`NaN`-операнды не сравнимы через `==`**: ассерты на `NaN`-результат используют
  проверку «является NaN», а не равенство — иначе тест ложно провалился бы.
- **Пустое окно метрики даёт `Пусто`, не `None`-операнд**: пустое окно — штатный
  результат `Пусто`; его НЕ следует путать с операндом `None` арифметической операции
  (разные ветки типовой ошибки).
- **Деление на ноль — две разные ветки**: для дробного знаменателя (`rf == 0.0`) и для
  целочисленных операций (`//`, `mod`) деление на ноль обрабатывается **разными**
  ветками кода, но обе дают сообщение «деление на ноль»; оба пути проверяются отдельно.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ОБЯЗАНА запереть тестами через **дериватив метрики** деление на
  ноль (дробный знаменатель `0.0` и целочисленные `//` / `mod`), давая ошибку выполнения
  «деление на ноль» **с номером строки** и гарантированно НЕ панику (A1).
- **FR-002**: Система ОБЯЗАНА запереть тестами через дериватив метрики переполнение
  целого (`evalAdd` / `evalSubMul` / `evalFloorDiv` `MinInt64 // -1`), давая ошибку
  выполнения «переполнение целого числа» (A2).
- **FR-003**: Система ОБЯЗАНА запереть тестами через дериватив метрики унарный минус
  `combineUnary`: `-MinInt64` → ошибка выполнения «переполнение целого числа»,
  `-Дробное` → корректный результат. `combineUnary` (сегодня 0% покрытия) ОБЯЗАН
  реально прогоняться этими тестами (A3).
- **FR-004**: Система ОБЯЗАНА запереть тестами через дериватив метрики пропагацию
  `NaN` / `±Inf` по `combineBinary` на дробных операндах: значение пропагируется по
  IEEE-754 как есть, без паники и без потери (ассерт `NaN` — через проверку «является
  NaN», не через `==`) (A4).
- **FR-005**: Система ОБЯЗАНА запереть тестами через дериватив метрики операнд
  `None` / `Пусто` в `combineBinary` и `combineUnary` → типовая ошибка (не паника) (A5).
- **FR-006**: Каждый новый числовой тест (FR-001..FR-005) ОБЯЗАН проверять **категорию
  ошибки, её сообщение и тип** (а не только факт «не паника») и краснеть при удалении
  соответствующего гарда (мутационная чувствительность).
- **FR-007**: Система ОБЯЗАНА запереть **строгий** контракт `numberToValue`: целое вне
  диапазона `int64` в значении поля строки источника → ошибка выполнения формата
  `§SM-9.B` «целое число вне диапазона» (ранее не покрыто) (A6).
- **FR-008**: Система ОБЯЗАНА запереть **толерантный** контракт `numberToValue` золотым
  замком: payload-число `1e400` → дробное `+Inf`; `-1e400` → дробное `-Inf`;
  целое-вне-диапазона без точки (напр. `99999999999999999999`) → **конечное** дробное
  (Float64-fallback, `~1e20`, НЕ `±Inf`); число НИКОГДА не деградирует в `None` (A7).
- **FR-009**: Система ОБЯЗАНА переименовать строгий метод `numberToValue` пути загрузки
  источника в `sourceNumberToValue` и обновить его единственный вызов (в декодере
  значения) (B1).
- **FR-010**: Система ОБЯЗАНА переименовать толерантную свободную функцию
  `numberToValue` пути декодирования payload в `payloadNumberToValue` и обновить её
  единственный вызов (в декодере payload-значения) (B2).
- **FR-011**: Система ОБЯЗАНА сохранить у обеих переименованных функций их поясняющий
  комментарий контракта и добавить в каждую **одну строку перекрёстной ссылки** на
  близнеца («строгий двойник: …» / «толерантный двойник: …»), чтобы асимметрия читалась
  как намеренная. Имена НАМЕРЕННО разные; никаких других переименований не делается (B3).
- **FR-012**: Прод-логика `combineBinary`, `combineUnary` и `arith.go` ОБЯЗАНА остаться
  **байт-в-байт неизменной**; никакая числовая ветка не правится.
- **FR-013**: Числовая модель НЕ меняется: никакого big-int, никакого нового
  форматирования `±Inf` сверх фиксации текущего поведения декодирования.
- **FR-014**: Не вводится 0 новых операторов, 0 изменений wire-ключей и текстов ошибок
  (русские тексты остаются прежними), 0 новых ключевых слов / встроенных функций /
  кодов eval.
- **FR-015**: Единственное переименование прод-кода — два `numberToValue`; ничего больше
  не переименовывается.
- **FR-016**: Лексерный путь `FLOAT`-литерала → `L-8` НЕ трогается (другой слой,
  остаётся отложенным).

### Key Entities *(include if feature involves data)*

- **Числовое значение**: целое (`int64`) либо дробное (`float64`, допускает `NaN` /
  `±Inf`). Семантика комбинирования и арифметики не меняется; меняется только её
  тестовое покрытие.
- **Строгий преобразователь числа источника** (`sourceNumberToValue`, ранее
  `numberToValue`): метод пути загрузки источника; целое вне `int64` → ошибка `§SM-9.B`.
- **Толерантный преобразователь числа payload** (`payloadNumberToValue`, ранее
  `numberToValue`): свободная функция пути декодирования payload; вне диапазона →
  дробное `±Inf`; число никогда не становится `None`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `gofmt` чистый; `go build ./...` и `go vet ./...` без ошибок;
  `go test -race ./...` зелёное.
- **SC-002**: Унарный путь `combineUnary` реально прогоняется новыми тестами через
  дериватив метрики (был 0% покрытия → покрыт).
- **SC-003**: Оба контракта `numberToValue` запёрты тестами: строгий путь даёт ошибку на
  целом-вне-диапазона; толерантный путь даёт дробное `±Inf` на числе-вне-диапазона.
- **SC-004**: Каждый новый тест краснеет при удалении соответствующего гарда (проверка
  категории/сообщения/типа, не только «не паника»; мутационная чувствительность
  подтверждена).
- **SC-005**: Прод-поведение НЕ изменилось нигде, кроме механического переименования двух
  `numberToValue`; `combineBinary` / `combineUnary` / `arith.go` остаются байт-в-байт
  прежними.
- **SC-006**: 0 новых внешних зависимостей; 0 новых ключевых слов / встроенных функций /
  кодов eval; 0 новых операторов; тексты ошибок и wire-ключи неизменны.

## Assumptions

- Целевая аудитория — авторы бизнес-программ, чьи формулы метрик и внешние данные
  попадают в числовые краевые ситуации; durable-хранилище и фронтенд не затрагиваются.
- Существующее числовое поведение `combineBinary` / `combineUnary` / `arith.go`
  считается **корректным эталоном**; задача — зафиксировать его тестами, а не изменить.
- Тестовая инфраструктура и помощники (построение интерпретатора метрики, золотые
  ассерты значения, помощник проверки ошибки → строка/координата, запись JSON-источника,
  декодер payload, фиксированные часы) уже существуют и переиспользуются.
- Прогон проверок выполняется из каталога `src/` (`go build` / `go vet` / `go test
  -race ./...`).

## Out of Scope

- НЕ менять логику `combineBinary` / `combineUnary` / `arith.go` и числовую модель
  (никакого big-int, никакого нового форматирования `±Inf` сверх фиксации текущего
  декодирования).
- НЕ трогать лексерный путь `FLOAT`-литерала → `L-8` (другой слой, остаётся отложенным).
- НЕ добавлять операторы.
- НЕ менять wire-ключи и тексты ошибок (русские остаются).
- НЕ переименовывать ничего, кроме двух `numberToValue`.
- **Границы диффа**: строго в `src/internal/eval` (новые тесты + рейминг строгого
