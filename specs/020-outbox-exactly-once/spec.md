## User Scenarios & Testing *(mandatory)*

### User Story 1 - Эффект тела шага доставляется ровно один раз через рестарт демона (Priority: P1)

Автор процесса в Ladix описывает шаг с реальным внешним эффектом в теле (например, `уведомить crm(...)` — POST во внешнюю систему). Демон исполняет процесс, доставляет эффект, затем падает (краш/перезапуск) посреди продвижения инстанса. После рестарта демон поднимает незавершённый инстанс и переисполняет тело шага. Пользователь ожидает, что внешний эффект НЕ будет отправлен повторно: внешняя система получает ровно один POST, несмотря на рестарт.

**Why this priority**: Это несущий критерий надёжности золотого сценария §2 — без него durable-рестарт удваивает реальные побочные эффекты (дубль уведомления в CRM). Делает гарантию «реальный эффект в теле шага» безопасной к рестарту. Сама по себе закрывает вопрос «можно ли доверять автоматизации эффект с побочкой».

**Independent Test**: Прогнать усиленный §2 end-to-end под `serve` (CSV→метрика→триггер→процесс→`complete --данные`→авто-шаги→реальный эффект `crm`), вызвать рестарт mid-advance на той же durable `--db`, подсчитать число доставок эффекта `crm`. Значение РОВНО 1 — независимо проверяемо без знания внутренней реализации.

**Acceptance Scenarios**:

1. **Given** инстанс процесса дошёл до авто-шага с эффектом `уведомить crm(...)` и эффект успешно доставлен (POST = 1), **When** демон рестартует mid-advance и поднимает инстанс рестарт-сканом, переисполняя тело шага, **Then** эффект НЕ доставляется повторно — суммарный счётчик POST остаётся 1.
2. **Given** шаг с эффектом-выражением `вызвать ...`, результат которого присвоен переменной, и эффект уже доставлен, **When** тело шага переисполняется по рестарту, **Then** метод возвращает тот же ранее сохранённый результат БЕЗ повторного внешнего вызова, и логика процесса остаётся согласованной.
3. **Given** шаг с двумя эффектами в теле, **When** тело переисполняется, **Then** каждый из двух эффектов дедуплицируется независимо по своему порядковому номеру (ни один не «съедает» ключ другого).
4. **Given** эффект, исполняемый ВНЕ тела шага (тело метрики-триггера, тело эскалации, top-level `запустить`), **When** он диспатчится, **Then** дедуп через outbox НЕ применяется — поведение прежнее (идемпотентность обеспечивают существующие гарды `LastBool`/`Escalated`).

### User Story 2 - Демон устойчив к сбоям Store при проверке дедлайнов (Priority: P2)

Оператор запускает демон `serve` с проверкой дедлайнов задач. Если хранилище временно сбоит при листинге задач, загрузке инстанса или персисте флага эскалации, оператор ожидает, что демон НЕ упадёт (паника): сбой логируется, затронутая задача пропускается, остальная работа продолжается. Окно «эффект сработал — персист не успел» осознанно фиксируется как известная граница at-least-once, а не дефект.

**Why this priority**: P2 — это устойчивость уже корректного пути `checkDeadlines`: три fault-ветки сегодня не покрыты тестами. Делает поведение под сбоями Store наблюдаемым и зафиксированным замками, не меняя продакшен-логику.

**Independent Test**: Инъектировать fault-Store, чей метод (`ListPendingTasks` / `LoadInstance` / `SaveTask`) возвращает ошибку, прогнать фазу проверки дедлайнов и проверить: нет паники, есть точная лог-строка, остальные задачи обработаны. Проверяемо изолированно от P1.

**Acceptance Scenarios**:

1. **Given** Store, чей `ListPendingTasks` возвращает ошибку, **When** идёт фаза проверки дедлайнов, **Then** фаза не паникует, печатается лог-строка `checkDeadlines: листинг задач: <ошибка>`, происходит ранний возврат, демон жив и продолжает следующий тик.
2. **Given** Store, чей `LoadInstance` падает для одной задачи, **When** идёт проверка дедлайнов, **Then** эта задача пропускается (без эскалации, без паники), остальные задачи обрабатываются штатно.
3. **Given** Store, чей `SaveTask` (персист `Escalated`) падает ПОСЛЕ срабатывания тела эскалации, **When** идёт проверка дедлайнов, **Then** печатается лог-строка `checkDeadlines: персист Escalated задачи <id>: <ошибка>`; известное окно fire-then-persist (следующий тик/рестарт перешлёт = at-least-once) зафиксировано в комментарии теста как осознанная граница, не дефект.

---

### Edge Cases

- **Statement-форма эффекта** (`уведомить`, statement-`вызвать`): результат отбрасывается → в леджере хранится `Пусто`/None как детерминированный type-tagged blob (НЕ SQL `NULL`); на пропуске-по-дедупу метод возвращает `nil`/None.
- **Пустой payload на рестарте**: payload `--данные` эфемерен (на рестарте пуст); split «захват + эффект» гарантирует, что эффект-шаг читает durable-переменную (`итог`), а не пустой payload — арг-эвал на рестарте успешен. Краш в окне между завершением человеческого шага и персистом `присвоить итог = данные.итог` теряет payload — вне scope outbox (известная граница).
- **At-least-once окно**: краш между успешной доставкой эффекта и записью в леджер → ключ ещё не помечен delivered → повторная доставка на рестарте (at-least-once). Осознанная граница (§C-9 бэклог), закрываемая лишь идемпотентностью приёмника. Гейт §2 крашится ПОСЛЕ записи в леджер → ровно 1.
- **Дедуп на MemoryStore эфемерен** (нет durable-персиста) — гарантия рестарта проверяется на SQLite/`--db`; на Memory дедуп работает в пределах жизни процесса.
- **Чисто-CLI без `serve`**: инстанс, упавший mid-auto-step, переисполнится лишь при следующем подъёме `serve` (граница liveness — когда эффект доедет), не нарушая exactly-once (доставок ≤ 1 всегда).
- **Глубокая копия `Args`/времён в MemoryStore**: при Save/Load значения копируются, иначе мутация значений в движке протекла бы в леджер.

## Requirements *(mandatory)*

### Functional Requirements

**Леджер идемпотентности (хранилище):**

- **FR-001**: Система MUST предоставлять durable леджер доставленных эффектов тела шага, адресуемый ключом `(instance_id, step_name, effect_index)`; леджер консультируется в момент диспатча эффекта (не дренажится фоновым воркером).
- **FR-002**: Контракт Store MUST расширяться аддитивно с 16 до 18 методов: добавляются `LoadOutbox(dedupKey) → (запись, ошибка)` (не найдено → sentinel «запись не найдена») и `SaveOutbox(запись) → ошибка` (upsert по ключу дедупа). Базовые 16 сигнатур остаются байт-целыми.
- **FR-003**: Оба новых метода MUST быть реализованы в ОБЕИХ реализациях Store (in-memory и durable SQLite); двойной compile-замок соответствия (`_ Store = (*MemoryStore)(nil)`; `_ Store = (*SQLiteStore)(nil)`) расширяется на оба новых метода — отсутствие любого ломает сборку.
- **FR-004**: Запись леджера MUST содержать: ключ дедупа, идентификатор инстанса, имя шага, порядковый номер эффекта, вид эффекта (`вызвать`/`уведомить`), цель, аргументы (как список значений), результат (для `вызвать`; для `уведомить`/statement — None), флаг доставлено, временные штампы создания и доставки.
- **FR-005**: Сериализация записи в durable-хранилище MUST происходить внутри durable-реализации Store через существующий value-кодек (аргументы — как список значений; результат — как значение; None — как детерминированный type-tagged blob, НЕ SQL `NULL`). Слой eval НЕ импортирует Store.
- **FR-006**: In-memory реализация MUST делать глубокую копию аргументов и временных штампов при Save/Load, чтобы мутация значений в движке не протекала в леджер.
- **FR-007**: Методы леджера MUST читать/писать таблицу `outbox`, уже созданную миграцией схемы C2a (1→2); новых миграций/таблиц фича не вводит.

**Дедуп в движке:**

- **FR-008**: Дедуп через леджер MUST жить в effect-методах движка (`CallExternal`/`CallExternalResult`/`Notify`), а НЕ в декораторе внешнего вызывателя (у него нет контекста инстанс/шаг/индекс). Дедуп MUST добавляться в КАЖДЫЙ из трёх методов независимо (один из них вызывает внешний вызыватель напрямую, не делегируя другому).
- **FR-009**: Контракт ProcessRuntime MUST остаться ровно 8 методов с байт-целыми сигнатурами; дедуп — это новое поведение и новое внутреннее поле кадра движка, НЕ изменение интерфейса eval.
- **FR-010**: Дедуп MUST быть активен тогда и только тогда, когда есть активный кадр шага (`len(e.active) > 0`, т.е. внутри тела шага процесса); вне процесса (тело метрики-триггера, тело эскалации, top-level `запустить`) effect-методы MUST делегировать внешнему вызывателю напрямую, как прежде.
- **FR-011**: `effect_index` MUST быть детерминированным порядковым номером эффекта в теле текущего шага, считаемым от 0 при КАЖДОМ исполнении тела; хранится в новом поле кадра, сбрасывается в 0 в начале каждой итерации шага в `advance` (перед исполнением тела), инкрементируется в каждом effect-методе при активном кадре. На рестарте тот же эффект получает тот же индекс (тело идёт строго по порядку statement'ов).
- **FR-012**: Дедуп MUST автоматически быть активен во всех построенных движках (run/complete/start/serve/metric) без пер-командной проводки, поскольку живёт над общим инъектированным Store.

**Протокол диспатча (deliver-then-record + pre-check):**

- **FR-013**: При активном кадре шага каждый effect-метод MUST сначала консультировать леджер по ключу: если запись существует и помечена доставленной — НЕ вызывать внешний вызыватель, вернуть сохранённый результат (`вызвать` → сохранённый результат; `уведомить`/statement — None/nil) и остановиться.
- **FR-014**: Если записи нет (или не доставлена), метод MUST доставить эффект через внешний вызыватель, ЗАТЕМ при успехе записать в леджер запись с флагом доставлено и штампами (upsert). При ошибке доставки метод MUST вернуть ошибку (шаг провалится), а леджер НЕ помечать доставленным.
- **FR-015**: Окно между успешной доставкой эффекта и записью в леджер MUST трактоваться как осознанная граница at-least-once (зафиксирована в §C-9 бэклоге; закрываема лишь идемпотентностью приёмника). Гейт §2 крашится ПОСЛЕ записи в леджер → ровно 1.

**Устойчивость checkDeadlines (3 fault-ветки):**

- **FR-016**: При ошибке листинга задач в проверке дедлайнов система MUST логировать `checkDeadlines: листинг задач: <ошибка>`, делать ранний возврат и оставаться живой (без паники).
- **FR-017**: При ошибке загрузки инстанса для конкретной задачи система MUST пропускать (continue) эту задачу без паники и продолжать обработку остальных.
- **FR-018**: При ошибке персиста флага `Escalated` ПОСЛЕ срабатывания тела эскалации система MUST логировать `checkDeadlines: персист Escalated задачи <id>: <ошибка>`; это известное окно fire-then-persist (следующий тик/рестарт перешлёт = at-least-once) MUST быть зафиксировано в комментарии теста как осознанная граница, не дефект.

**Исполнимое усиление §2:**

- **FR-019**: Усиленный золотой сценарий §2 MUST стать исполнимым через эволюцию канонического примера `examples/контроль_плана.ladix`: в процесс `эскалация_плана` добавляются два авто-шага — `зафиксировать_итог после связаться_с_клиентом` (захват payload в durable-переменную через `присвоить`) и `уведомить_crm после зафиксировать_итог` (реальный эффект `уведомить crm(...)` в теле шага). Используются ТОЛЬКО существующие конструкции; арность процесса не меняется (один параметр).
- **FR-020**: Соответствующая запись в `examples/MANIFEST.md` MUST быть обновлена под эволюцию примера; затронутые golden-замки exact-match примера (CLI deadline-escalation golden, строка эффекта `crm`) MUST быть переснятыми co-land.

**Границы и инварианты:**

- **FR-021**: Фича MUST НЕ вводить новых ключевых слов, SE-кодов, eval-кодов, builtins или внешних зависимостей; текст §2 в charter НЕ редактируется этой фичей.
- **FR-022**: Дифф MUST ограничиваться `src/internal/store` + `src/internal/engine` + `src/internal/daemon` (тесты) + `examples` + тесты; дифф пакета eval MUST быть пустым (ProcessRuntime=8 цел, eval не импортирует store/engine); продакшен-код `cmd` MUST не меняться (кроме тестов serve при необходимости для гейт-теста; clock-путь serve.go не ломать).
- **FR-023**: Поведение MUST быть детерминированным (фиксированные часы FixedClock в тестах); durable-гарантия рестарта реальна на SQLite/`--db`.

### Key Entities *(include if feature involves data)*

- **Запись леджера (OutboxRecord)**: представляет один доставленный (или диспатчимый) эффект тела шага. Атрибуты: ключ дедупа `(инстанс, шаг, индекс эффекта)`; вид (`вызвать`/`уведомить`); цель; аргументы (список значений); результат (значение; None для statement-форм); флаг доставлено; штампы создания и доставки. Адресуется ключом дедупа; upsert по ключу. Хранится в таблице `outbox` (создана C2a).
- **Кадр активного шага (activeFrame)**: контекст исполнения текущего шага в движке. Расширяется внутренним полем `effectIndex` — счётчиком эффектов в теле текущей итерации шага; сбрасывается в 0 на старте итерации, инкрементируется на каждый effect-вызов. Несёт инстанс и окружение процесса для построения ключа дедупа.
- **Sentinel «запись не найдена» (ErrOutboxNotFound)**: маркер отсутствия записи в леджере, возвращаемый `LoadOutbox`; зеркалит существующий sentinel «состояние триггера не найдено».

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При прогоне усиленного §2 end-to-end под `serve` с рестартом mid-advance на той же durable `--db` число доставок внешнего эффекта `crm` РОВНО 1 (durable exactly-once гейт зелёный).
- **SC-002**: Контракт Store содержит ровно 18 методов; двойной compile-замок соответствия покрывает обе реализации обоими новыми методами (сборка падает при отсутствии любого).
- **SC-003**: Контракт ProcessRuntime остаётся ровно 8 методов с неизменёнными сигнатурами; пакет eval имеет пустой дифф (не импортирует store/engine).
- **SC-004**: Эффект, диспатчимый дважды под одним активным кадром и ключом, доставляется внешним вызывателем ровно один раз; второй диспатч — пропуск с возвратом сохранённого результата.
- **SC-005**: Два эффекта в одном теле шага дедуплицируются независимо (мутация `effect_index ≡ 0` приводит к красному тесту двух-эффектов — коллизия ключей).
- **SC-006**: Все 3 fault-ветки `checkDeadlines` покрыты реальными тестами надёжности: нет паники, точные лог-строки присутствуют, незатронутые задачи обработаны.
- **SC-007**: Мутпробы краснят: снятие pre-check → доставка дважды → durable-гейт красный; сломанный `effect_index` → тест двух-эффектов красный.
- **SC-008**: Усиленный §2 исполним как эволюция `examples/контроль_плана.ladix`; запись MANIFEST и затронутые golden обновлены; новых ключевых слов/SE/eval-кодов нет.

## Assumptions

- Таблица `outbox` уже создана миграцией схемы C2a (1→2); фича только читает/пишет её, новых миграций не вводит.
- Текст усиления §2 уже внесён владельцем в `docs/v2-charter.md` §2 и НЕ редактируется этой фичей; фича переносит его в исполнимый пример.
- Durable-гарантия рестарта проверяется на SQLite-хранилище с флагом `--db`; на in-memory дедуп эфемерен (в пределах жизни процесса) — это приемлемо.
- Гейт-тест exactly-once использует inline-const источник сценария (по образцу существующих M2 golden), изолированный от файловых golden примеров.
- Существующий рестарт-скан демона (`serve`) драйвит переисполнение тела шага; outbox решает «доставлять/пропустить». Чисто-CLI развёртывание без `serve` — граница liveness, не нарушение exactly-once.
- Окно at-least-once (доставка → запись в леджер) и окно fire-then-persist `Escalated` — известные осознанные границы, документируемые в комментариях тестов (§C-9 бэклог), закрываемые лишь идемпотентностью приёмника.
- Существующий value-кодек Store покрывает аргументы (как список) и результат (как значение, включая None как type-tagged blob); новых форматов сериализации не требуется.
