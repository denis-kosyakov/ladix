## D-1. Мост воспроизводимости: `go.mod` остаётся в `src/`

**Контекст.** `src/go.mod` лежит в `src/`, README даёт команды без `cd src` и
bare-команду `ladix` → из чистого клона сборка/тесты/запуск падают
(`cannot find main module`, `command not found: ladix`). Нужен мост между
каталогом сборки (`src/`) и каталогом запуска (корень, где `data/`, `data/sales.json`,
`examples/`). Якорь: §VF-1 + «Предрешённые развилки».

**Decision.** `go.mod` НЕ переносится; README выравнивается под фактическое
расположение: всем командам сборки/проверки/тестов предпослан `cd src`; ОДИН
канонический мост — «собрать в корень» `cd src && go build -o ../ladix ./cmd/ladix`,
затем запуск `./ladix run examples/...` из корня; тесты — `cd src && go test ./...`.
Мост проводится сквозь ВСЕ команды запуска (`run`/`serve`/`emit`/`metric`).
`src/README.md` получает краткий dev-блок из `src/` либо явную отсылку к корневому
README (не голую заглушку). Опционально допустим корневой `Makefile`
(`build`/`test`/`vet` делают `cd src && go ...`), но НЕ обязателен.

**Rationale.** Перенос `go.mod` — churn по всему дереву импортов и истории, риск
для готового, протестированного ядра; ради текстового исправления README это
несоразмерно. «Собрать в корень» даёт ОДИН рабочий путь: бинарник оказывается там,
откуда видны `data/`/`examples/`, и пользователь не угадывает переход между каталогами.

**Alternatives.**
- *Перенести `go.mod` в корень* — ОТКЛОНЁН: churn по дереву импортов/истории, вне
  скоупа финализации, риск для зелёных гейтов.
- *`go.work` в корне* — ОТКЛОНЁН: при `go.work` команда `go ... ./...` перечисляет
  пакеты под текущим cwd; из корня (где нет Go-пакетов) это даёт 0 пакетов, а не
  обход `src/`. Воспроизводимость через `go.work` иллюзорна.
- *`go install ./cmd/ladix` (на PATH)* — ОТКЛОНЁН как канон (рассматривался в §VF-1
  как альтернативный мост): зависит от `GOBIN`/`PATH` окружения пользователя, менее
  предсказуем, чем явный `-o ../ladix`. Оставлен только как возможное упоминание, не основной путь.

## D-2. Детерминизм примеров: golden + `FixedClock`, без пиннинга `сегодня()`

**Контекст.** Новые демо витрины (триггеры, процессы, метрика) и `выручка.ladix`
дата-зависимы: окна метрик берутся от `сегодня()`/часов планировщика, id процессов
генерируются. Скоуп §3 требует «детерминизм пинить». Якорь: §VF-5, §VF-6,
«Предрешённые развилки».

**Decision.** Любое новое демо с golden-проверкой строится на ИНЪЕКЦИИ `Clock`
(`FixedClock`) и/или встроенном прогоне во временной директории (`t.TempDir()` +
`os.WriteFile`, паттерн `src/cmd/ladix/trigger_golden_test.go`, §TR-9). `--db` — во
временной директории, id детерминированы (`p-000001`/`t-000001`), маска только
`<время>` дедлайна. Где окно/дата неизбежны (метрика `ежемесячно` в `выручка.ladix`)
— пинится exit 0 + отсутствие маркеров диагностик, а строгий байт-точный stdout
закрывается ОТДЕЛЬНЫМ run-golden с фикс-`Clock` и фикс-данными (§VF-6).

**Rationale.** `FixedClock` уже инъектируется в движок/CLI (паттерн §SM-10/§TR-9) —
переиспользование, не новый механизм. Это даёт зелёный прогон в любой день и
соблюдает принцип V (без `time.Now()`-глобала). `выручка.ladix` остаётся живой
бизнес-демо, а детерминизм его сценария доказывается рядом, не ломая сам пример.

**Alternatives.**
- *Пиннинг golden по текущему `сегодня()`* — ОТКЛОНЁН: тест становится дата-зависимым
  («флак» в другой день), нарушает «детерминизм обязателен».
- *Переписать `выручка.ladix` на фикс-дату* — ОТКЛОНЁН: убивает роль живого
  дата-зависимого демо; вместо этого — отдельный run-golden, `выручка.ladix` не трогаем.

## D-3. `тип(x)` — доковое выравнивание «зарезервировано v1», без активации

**Контекст.** `тип(x)` документирован как активная стдлиб-функция, но в рантайме
недостижим: лексер резервирует `тип` как ключевое слово
(`src/internal/lexer/keywords.go`), токен не доходит до парсера как вызов;
`печать(тип(5))` даёт reserved-word ошибку. Реализация (`builtins.go` +
`builtins_convert.go`) есть, но мертва; инвариант «РОВНО 35 активных» — по факту
достижимо 34. Якорь: §VF-3, «Вне скоупа».

**Decision.** Финализация ВЫРАВНИВАЕТ доки под фактический зарезервированный статус,
НЕ активирует функцию. `docs/stdlib.md` — пометить `тип(x)` «зарезервировано/недоступно
в v1»; `SPEC.md` §220/§343 — заменить «активные» примеры на «зарезервировано до v2» +
внести `тип` в §12-список отложенного; `docs/eval-model.md` — снять подразумевание, что
`тип(x)` уже работает; инвариант-коммент `builtins.go` «РОВНО 35 активных» — честная
сноска «`тип` зарегистрирован, но недостижим из-за резерва лексера; достижимо 34».
Регистрация/реализация `тип` НЕ удаляются (путь будущей активации); reserved-word
поведение НЕ меняется.

**Rationale.** Активация = новая языковая функциональность = OUT финализации.
Минимум churn: коммент-сноска честнее удаления регистрации и сохраняет путь к v2.
Доки перестают вводить читателя в заблуждение, поведение остаётся прежним.

**Alternatives.**
- *Активировать `тип(x)`* (снять резерв лексера) — ОТКЛОНЁН: новая функциональность,
  v2, явный OUT в §VF-3 и «Вне скоупа».
- *Удалить регистрацию/реализацию `тип`* — ОТКЛОНЁН: ломает путь будущей активации,
  больше churn, чем коммент-сноска.

## D-4. `CHECKLIST.md` — простановка `[x]` с доказательством файл:строка

**Контекст.** 0 из 50 пунктов-чекбоксов отмечены, хотя 49 подтверждаются
кодом/тестами/примерами; пункт `:54` «`examples/hello.lang`» имеет рассинхрон
расширения (`.lang` vs реальный `.ladix`). Якорь: §VF-4, «Предрешённые развилки».

**Decision.** Проставить `[x]` всем 50 пунктам-чекбоксам **с доказательством
файл:строка** (рядом с пунктом или в сопроводке): название/идея — README; переменные/
типы/области/ошибки — SPEC + `eval`; управляющие конструкции — `stmt.go` + тесты;
функции/рекурсия — `call.go` + `examples/функция.ladix`/`факториал.ladix` +
`call_test.go` TestRecursion; пять классов ошибок — `errors/*error.go` + golden-замки;
структура пакетов — раскладка + `main.go`. Пункт `:54`/`hello.lang` закрывается `[x]`
со сноской `.lang→.ladix` (реальный `examples/hello.ladix:1-2`). **Текст пунктов
чеклиста НЕ редактируется** (правка внешнего generic-шаблона чеклиста — вне скоупа). Доказательства,
которые прогоны (рекурсия 120/1, ошибка строка 5 колонка 14), пинятся фикс-входом/фикс-`Clock`.

**Rationale.** Функциональный контракт — внешний generic-шаблон чеклиста; правка его формулировок (включая
`.lang`) — изменение чужого артефакта, вне скоупа. `[x]` + доказательство делает
приёмку достоверной без переписывания функционального контракта. Сноска честно фиксирует известный
рассинхрон расширения.

**Alternatives.**
- *Отредактировать `.lang`→`.ladix` в тексте пункта* — ОТКЛОНЁН: правка функционального контракта, вне скоупа.
- *Оставить `:54` как `[ ]`* — ОТКЛОНЁН по умолчанию: hello-пример фактически есть
  (`hello.ladix`), честнее закрыть `[x]` + сноска (но §VF-4 допускает `[ ]` + сноска
  как запасной вариант — выбран `[x]`).

## D-5. Классы примеров витрины: 7 классов против скоупа §3

**Контекст.** `examples/` неполна: нет демо событие/расписание-триггеров,
мультиисточника/мультиметрики, полного цикла процесса; единственный негатив —
runtime деление-на-ноль. Формы УЖЕ поддержаны парсером/семантикой (есть как
тест-фикстуры `testdata/event.ladix`/`schedule.ladix` + unit-тесты движка). Якорь:
§VF-5.

**Decision.** Добавить демо ровно для 7 классов, каждый зарегистрировать в
`examples/MANIFEST.md` (файл / назначение / golden-stdout) и закрыть замком в
`cmd/ladix`:
1. **Событие-триггер** — `когда событие <Ident>: запустить процесс …` (из формы `testdata/event.ladix`).
2. **Расписание-триггер** — `когда расписание каждые Nдн` и/или `в "HH:MM"` (из `testdata/schedule.ladix`).
3. **Мультиисточник/мультиметрика** — ≥2 `источник` + ≥2 `метрика` в одном файле.
4. **Полный цикл процесса** — `run --db`→`tasks`→`complete`→пробуждение (детерминированный Store/`--db` во временной директории).
5. **Синтаксическая ошибка** (parse) — негатив.
6. **Тип/семантическая ошибка** — негатив.
7. **Ошибка процесса** (несуществующий процесс / неверная арность / runtime в шаге) — негатив.

Позитивы — байт-точный stdout (или exit+маркеры для дата-зависимых); негативы —
точный двухстрочный stderr (строка/колонка) + код 1. **Новой функциональности не
вводится** — только витрина уже работающих форм.

**Rationale.** 7 классов покрывают скоуп §3 функционального контракта «реализован весь скоуп» и
демонстрируют охват языка пользователю. Источник форм — существующие тест-фикстуры,
значит парсер/семантика гарантированно их принимают; финализация лишь переносит их
в `examples/` как витрину и закрывает замками.

**Alternatives.**
- *Один комбинированный негатив* — ОТКЛОНЁН: §VF-5 требует ТРИ ОТДЕЛЬНЫХ класса
  ошибок (синтаксис / тип-семантика / процесс), иначе скоуп §3 недоказан.
- *Добавить демо без замков* — ОТКЛОНЁН: §VF-5 требует регистрацию в `MANIFEST.md` +
  замок на каждый пример (иначе витрина не приёмочна).
